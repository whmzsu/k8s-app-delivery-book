## 25.1 问题与护栏：被半夜挡住的发布，多半不是策略太严，而是上线方式太急

如第 24 章开头所述，第六篇是前六篇护栏的汇总深化，不是最后才做安全。第 11 章已经在 CI 里拦下过错误字段，第 24 章把验签放到了准入侧，本章要回答的是：**这些护栏该用哪个引擎表达，怎样灰度上线才不会在半夜把整个发布挡住**。

先给本章的正式定义。**准入策略**是「在资源进入集群前 / 时，由 API Server 调用 webhook 执行的校验或变更规则」（`book/glossary.md` 把它与 CI 里的静态扫描明确区分：静态扫描不叫准入）。它有一条可测量的性质：对同一份清单，`kubectl apply --dry-run=server` 与真实提交会得到**相同**的允许 / 拒绝判定，且判定结果会落到审计日志与 PolicyReport。这条性质是本章「CI 与集群同源」的前提，也是检查清单里 `CL-25-03` 的判据 [R-25-1][R-25-2]。

三条高频反模式，按「现象 → 根因 → 本章护栏」展开：

**反模式一：一上来就全量 `enforce`。** 现象是团队读完 Pod Security Standards 觉得 `restricted` 最安全，一次性给所有命名空间打上 `enforce=restricted`；第二天早晨历史工作负载集体 `CreateContainerConfigError`，一批需要写临时目录的旧 Pod 起不来，发布全线卡死，最后只能把标签删掉、回到零护栏。根因是把「合规目标」当成了「上线第一步」，跳过了**看清违规面**这件事。本章护栏是三级渐进：`warn` 只把警告返回给提交者、`audit` 只记审计事件不阻断、`enforce` 才真正拒绝；先在 `warn` / `audit` 窗口里收集违规清单，逐个修完再推到 `enforce` [R-25-1]。

**反模式二：策略只在集群侧，CI 不校验。** 现象是开发者本地 `kubectl apply` 一切正常，提交 PR 后合并、Argo CD 2.x 同步（见第 14 章），到生产准入才被拒，一次反馈来回要十几分钟甚至跨一个人值守周期。根因是「判定规则」与「反馈时机」脱节：同一条规则只在最晚的一环生效。本章护栏是**同一份策略库在两处跑**：CI 里用 Kyverno CLI 对 `policies/tests/` 做单元测试与离线校验（与第 11 章的 conftest / kubeconform 分工见 SP-16：第 11 章管字段级与渲染产物校验，本章管策略规则的通过 / 拒绝样例）[R-25-5]，集群里由同一份 `ClusterPolicy` 执行准入，两处报错文案一致 [R-25-3]。

**反模式三：绕过流程靠口头打招呼。** 现象是某个紧急发布被策略拦住，值班同学在群里说一句「先放一下」，有人把策略改成 `Audit`，事后没人记得改回来，三个月后复盘发现这段时间根本没有阻断记录。根因是例外没有**载体、到期时间与审计链**。本章护栏是 `docs/policy-exception.md` 登记模板：每次降级必须写清日期、原因、影响的 SHA 与到期时间，变更进 Git（公理 5，见第 3 章），到期由复查强制失效 [R-25-6]。

> **本书观点（本章第 1 条结论，不需要外部背书）**
>
> **主张**：策略也是代码——进 Git、有单元测试、有灰度与绕过审批；**没有测试与灰度的策略，比没有策略更危险**。
>
> **论证**：没有策略时，风险是「已知但可接受」的，团队心里有数；有一条未经测试、一次性全量 enforce 的策略时，风险变成「未知且会随时触发」的——它可能在任何一次无关的发布上拒绝一个合法工作负载，而且因为没人跑过拒绝样例，值班同学无法立刻判断是策略写错还是清单写错。把策略当成代码，就自然要求三件事：可读的 diff、可重复跑的通过 / 拒绝用例、从 `Audit` 到 `Enforce` 的渐进开关。这三件事恰好把「未知」重新变回「已知」。
>
> **反例与适用前提**：这不等于「所有策略都必须先跑满两周观察窗」。对明确无历史包袱的新命名空间、或已由 CI 全量校验过的新策略，可以直接 `enforce`；主张针对的是**存量集群**与**跨团队共享的 ClusterPolicy**。另一个反例是极小型团队：只有几个人、一个命名空间、变更频率很低时，一套手工核对清单可能比引入策略引擎更划算——但即便如此，也应把「判定标准」写下来并留痕，否则一旦人员变动，口径就丢了。Thoughtworks Technology Radar 与 CNCF 安全白皮书都把「策略即代码」列为趋势与共识性指导，但本结论的论证不依赖它们背书 [R-25-6][R-25-7]。

## 25.2 落地策略与门禁：一个引擎、两处拦截、三级灰度

### 25.2.1 能力边界（不铺工具横比矩阵）

按 `book/decisions.md` U-04，本书只选**一个**示例实现：Kyverno 1.x（部署在命名空间 `kyverno`，策略命名 `order-demo-*`）。理由不是「它最好」，而是声明式策略好读、验签与校验规则能写在同一套 `ClusterPolicy` 里，第 24 章的验签策略与本章的加固策略不会各跑一套引擎 [R-25-3]。其余两者只作边界说明，不进入落地链路：

- **ValidatingAdmissionPolicy（VAP）** 是 Kubernetes 1.32 内置的轻量方案，用 CEL 表达式写在 API Server 里，不装任何控制器就能做简单校验；代价是只能校验、不能变更或生成资源，也没有内置的测试框架与策略报告。适合「只需要一条规则、不想引入 webhook 运维成本」的场景，本章给出完整可应用配置作为对比，但不作为 `order-demo` 的落地实现 [R-25-2]。
- **Gatekeeper 3.x** 用 Rego 写约束模板，表达力最强、适合跨组织复用复杂约束，代价是要维护 ConstraintTemplate 与 Rego 的学习成本。本书仅在能力边界处提及，**不作为示例实现**，也不与第 24 章的验签策略混用。

一句话判据：**简单校验优先看内置的 VAP；需要变更 / 生成 / 测试 / 灰度 / 报告，才上策略引擎。** 这条判据与第 5 章「最小工具集」的口径一致（见第 5 章），也是 SP-21 要求的「何时不该用」：只有一条规则时不该引入 Kyverno，跨命名空间统一治理时才该 [R-25-4]。

### 25.2.2 PSS 三级灰度判据表

| 阶段 | 命名空间标签 | 失败动作 | 观察指标 | 推进到下一级的条件 |
|---|---|---|---|---|
| 0 观察 | `warn=restricted`、`warn-version=v1.32` | 只向提交者回警告，Pod 照常创建 | CI 与 `kubectl` 输出里的警告条数 | 连续一个发布周期无新增警告 |
| 1 审计 | 加 `audit=restricted`、`audit-version=v1.32` | 不阻断，但写审计事件 / PolicyReport | 违规事件涉及的命名空间与工作负载清单 | 清单里的历史负载全部修完或登记例外 |
| 2 阻断 | 加 `enforce=baseline`、`enforce-version=v1.32` | 违规 Pod 直接拒绝创建 | 被拒请求数、误伤工单数 | 被拒请求全部为真实违规，无误伤 |
| 3 收紧（可选） | `enforce=restricted` | 同上，规则更严 | 同上 | 团队确认所有工作负载满足 `restricted` |

注意阶段 2 刻意停在 `baseline` 而不是一步到 `restricted`：`baseline` 挡住的是特权、宿主命名空间、宿主端口这类高危项，`restricted` 还会要求 `seccompProfile`、`allowPrivilegeEscalation: false` 等更细的字段。第 6 章的最小闭环已经带了 `runAsNonRoot` / `seccompProfile` / `capabilities.drop: ["ALL"]`，所以 `order-demo` 最终能到 `restricted`；但存量集群里的其他工作负载未必，先 `baseline` 再收紧才是灰度 [R-25-1][R-25-4]。

**`policies/order-demo-require-nonroot.yaml`** —— 唯一示例策略，两条规则：非 root 运行、禁止 privileged。`=(...)` 是 Kyverno 的「存在则必须等于」锚点，能覆盖「完全没写 securityContext」的情况 [R-25-3]。

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: order-demo-require-nonroot
spec:
  validationFailureAction: Enforce
  background: true
  failurePolicy: Fail
  rules:
    - name: require-run-as-nonroot
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - order-demo-dev
                - order-demo-staging
                - order-demo-prod
      validate:
        message: "所有工作负载必须声明 runAsNonRoot: true（见第 6 章、第 25 章）"
        pattern:
          spec:
            securityContext:
              runAsNonRoot: true
    - name: disallow-privileged
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - order-demo-dev
                - order-demo-staging
                - order-demo-prod
      validate:
        message: "不允许 privileged 容器（见第 25 章）"
        pattern:
          spec:
            containers:
              - =(securityContext):
                  =(privileged): false
```

**`.github/workflows/policy.yml`** —— CI 静态校验。策略库与集群准入同源，开发者在 PR 阶段就能拿到与生产一致的拒绝原因；conftest / kubeconform 的通用字段校验仍归第 11 章 [R-25-5]。

```yaml
name: policy
on:
  pull_request:
    paths:
      - "policies/**"
      - "deploy/**"
jobs:
  policy-test:
    runs-on: ubuntu-latest
    steps:
      - name: 检出源码
        uses: actions/checkout@v4
      - name: 策略单元测试（Kyverno CLI 1.x，与集群同源）
        run: |
          kyverno test policies/tests
      - name: 对渲染产物做离线策略校验（见第 11 章、第 14 章）
        run: |
          kyverno apply policies/order-demo-require-nonroot.yaml \
            --resource deploy/base/deployment.yaml
      - name: 拒绝样例必须在离线校验中失败（防止策略被改松）
        run: |
          if kyverno apply policies/order-demo-require-nonroot.yaml \
               --resource policies/tests/fail.yaml --set-background-scan=false \
               > /tmp/fail-check.out 2>&1; then
            if grep -qi 'pass' /tmp/fail-check.out && ! grep -qi 'fail\|violat\|blocked' /tmp/fail-check.out; then
              echo "FAIL：特权容器样例未被策略拦下" >&2
              exit 1
            fi
          fi
          cat /tmp/fail-check.out
```

**`policies/vap-nonroot-comparison.yaml`** —— VAP 内置轻量对比（Kubernetes 1.32，`admissionregistration.k8s.io/v1`）。**这是对比示例，不是 `order-demo` 的落地实现**；与上面的 Kyverno 策略不要同时启用，否则同一违规会产生两条拦截记录、灰度口径也不一致 [R-25-2]。

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: order-demo-nonroot-vap
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods"]
  validations:
    - expression: "object.spec.?securityContext.?runAsNonRoot.orValue(false) == true"
      message: "Pod 必须声明 runAsNonRoot: true（见第 25 章）"
    - expression: "object.spec.containers.all(c, !has(c.securityContext) || !has(c.securityContext.privileged) || c.securityContext.privileged == false)"
      message: "不允许 privileged 容器（见第 25 章）"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: order-demo-nonroot-vap-binding
spec:
  policyName: order-demo-nonroot-vap
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        app.kubernetes.io/name: order-demo
```

```markdown
# 策略例外登记（每次降级必须追加一行，变更进 Git）

| 登记日期 | 原因 | 影响 SHA | 降级策略 | 申请人 | 到期日期 | 恢复验证 |
|---|---|---|---|---|---|---|
| 2026-11-11 | 紧急发布被 disallow-privileged 误拦 | git-1a2b3c4 | order-demo-require-nonroot -> Audit | oncall | 2026-11-14 | 见 25.2.4 回滚验证 |

规则：
1. 到期日期不得为空，最长 3 天；到期未恢复由复查人直接 `kubectl apply -f policies/order-demo-require-nonroot.yaml`。
2. 降级只改变阻断强度，不删除策略、不删除审计事件。
3. 每条例外必须对应一次 `kyverno test policies/tests` 的重跑记录。
```

### 25.2.4 验证与回滚

**验证命令**（仓库根目录；已安装 `kyverno` CLI 1.x / kubectl，集群已部署 Kyverno 1.x 于命名空间 `kyverno`）：

```bash
kyverno version
kyverno test policies/tests
kyverno apply policies/order-demo-require-nonroot.yaml --resource policies/tests/fail.yaml
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/fail.yaml
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/pass.yaml
kubectl get clusterpolicy order-demo-require-nonroot \
  -o jsonpath='{.spec.validationFailureAction}{"\n"}'
kubectl -n order-demo-dev get policyreport -o yaml
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 策略单元测试 | `kyverno test` 四条断言全部通过，退出码 0 |
| CI 侧拦截特权容器 | `kyverno apply ... --resource fail.yaml` 输出含 `fail` / `violation`，`disallow-privileged` 命中 |
| 集群侧拦截特权容器 | `kubectl apply --dry-run=server -f fail.yaml` 返回非零，报错含 `不允许 privileged 容器` |
| 通过样例 | `pass.yaml` 的 server dry-run 返回成功，`pass` 判定 |
| 阻断强度 | `validationFailureAction` 为 `Enforce` |
| 审计留痕 | 命名空间存在 PolicyReport，违规请求可查（见第 26 章） |

前两行与第三、四行构成「两处拦截同一策略库」的完整证据：CI 用 `fail.yaml` 命中 `disallow-privileged`，集群用同一份 `fail.yaml` 的 dry-run 被同一条规则拒绝，报错文案一致 [R-25-3]。

**回滚 / 降级命令与步骤**。误伤（合法工作负载被拦）时的处理顺序是：先降级止血、再登记例外、再修策略、最后恢复，全程不删审计：

```bash
# 1) 止血：Enforce -> Audit，发布先恢复
kubectl apply -f policies/order-demo-require-nonroot-audit.yaml
kubectl get clusterpolicy order-demo-require-nonroot \
  -o jsonpath='{.spec.validationFailureAction}{"\n"}'

# 2) PSS 同步回退到只观察（去掉 enforce 标签）
kubectl label ns order-demo-dev order-demo-staging order-demo-prod \
  pod-security.kubernetes.io/enforce- \
  pod-security.kubernetes.io/enforce-version- --overwrite

# 3) 登记例外（写入 Git，带到期时间）
kubectl -n order-demo-dev describe pod <被误伤的 Pod 名>
# 按 docs/policy-exception.md 追加一行，注明原因、SHA、申请人、到期日期
git add docs/policy-exception.md policies/order-demo-require-nonroot-audit.yaml
git commit -m "chore(policy): audit-mode exception with expiry"

# 4) 修策略并跑测试；正式回退走 git revert
git revert HEAD
kyverno test policies/tests
kubectl apply -f policies/order-demo-require-nonroot.yaml
kubectl apply -f policies/pss-baseline.yaml
```

紧急情况下可 `kubectl delete clusterpolicy order-demo-require-nonroot`，但这会让审计链断一截，只允许作为最后手段，且必须在例外登记里写明；生产变更仍须回到 Git（公理 5，见第 3 章）。

**回滚验证**：

```bash
kyverno test policies/tests
kubectl get clusterpolicy order-demo-require-nonroot \
  -o jsonpath='{.spec.validationFailureAction}{"\n"}'
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/pass.yaml
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/fail.yaml
kubectl get ns order-demo-dev \
  -o jsonpath='{.metadata.labels.pod-security\.kubernetes\.io/enforce}{"\n"}'
kubectl -n order-demo-dev get policyreport -o yaml
```

通过标准：`validationFailureAction` 回到 `Enforce`；`pass.yaml` 成功、`fail.yaml` 再次被拒；命名空间 `enforce` 标签回到 `baseline`；降级窗口内的违规事件仍保留在 PolicyReport 与审计日志里。**回滚没有验证过，就不允许继续发布**（母版 `CL-G-07`）。
