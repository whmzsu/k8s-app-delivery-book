## 25.1 问题与护栏：被半夜挡住的发布，多半不是策略太严，而是上线方式太急

如第 24 章开头所述，第六篇是前六篇护栏的汇总深化，不是最后才做安全。第 11 章已经在 CI 里拦下过错误字段，第 24 章把验签放到了准入侧，本章要回答的是：**这些护栏该用哪个引擎表达，怎样灰度上线才不会在半夜把整个发布挡住**。

先给本章的正式定义。**准入策略**是「在资源进入集群前 / 时，由 API Server 调用 webhook 执行的校验或变更规则」（`book/glossary.md` 把它与 CI 里的静态扫描明确区分：静态扫描不叫准入）。它有一条可测量的性质：对同一份清单，`kubectl apply --dry-run=server` 与真实提交会得到**相同**的允许 / 拒绝判定，且判定结果会落到审计日志与 PolicyReport。这条性质是本章「CI 与集群同源」的前提，也是检查清单里 `CL-25-03` 的判据 [R-25-1][R-25-2]。

三条高频反模式，按「现象 → 根因 → 本章护栏」展开：

**反模式一：一上来就全量 `enforce`。** 现象是团队读完 Pod Security Standards 觉得 `restricted` 最安全，一次性给所有命名空间打上 `enforce=restricted`；第二天早晨历史工作负载集体 `CreateContainerConfigError`，一批需要写临时目录的旧 Pod 起不来，发布全线卡死，最后只能把标签删掉、回到零护栏。根因是把「合规目标」当成了「上线第一步」，跳过了**看清违规面**这件事。本章护栏是三级渐进：`warn` 只把警告返回给提交者、`audit` 只记审计事件不阻断、`enforce` 才真正拒绝；先在 `warn` / `audit` 窗口里收集违规清单，逐个修完再推到 `enforce` [R-25-1]。

**反模式二：策略只在集群侧，CI 不校验。** 现象是开发者本地 `kubectl apply` 一切正常，提交 PR 后合并、Argo CD 3.x 同步（见第 14 章），到生产准入才被拒，一次反馈来回要十几分钟甚至跨一个人值守周期。根因是「判定规则」与「反馈时机」脱节：同一条规则只在最晚的一环生效。本章护栏是**同一份策略库在两处跑**：CI 里用 Kyverno CLI 对 `policies/tests/` 做单元测试与离线校验（与第 11 章的 conftest / kubeconform 分工见 SP-16：第 11 章管字段级与渲染产物校验，本章管策略规则的通过 / 拒绝样例）[R-25-5]，集群里由同一份 `ClusterPolicy` 执行准入，两处报错文案一致 [R-25-3]。

**反模式三：绕过流程靠口头打招呼。** 现象是某个紧急发布被策略拦住，值班同学在群里说一句「先放一下」，有人把策略改成 `Audit`，事后没人记得改回来，三个月后复盘发现这段时间根本没有阻断记录。根因是例外没有**载体、到期时间与审计链**。本章护栏是 `docs/policy-exception.md` 登记模板：每次降级必须写清日期、原因、影响的 SHA 与到期时间，变更进 Git（公理 5，见第 3 章），到期由复查强制失效 [R-25-6]。

> **本书观点（本章第 1 条结论，不需要外部背书）**
>
> **主张**：策略也是代码——进 Git、有单元测试、有灰度与绕过审批；**没有测试与灰度的策略，比没有策略更危险**。
>
> **论证**：没有策略时，风险是「已知但可接受」的，团队心里有数；有一条未经测试、一次性全量 enforce 的策略时，风险变成「未知且会随时触发」的——它可能在任何一次无关的发布上拒绝一个合法工作负载，而且因为没人跑过拒绝样例，值班同学无法立刻判断是策略写错还是清单写错。把策略当成代码，就自然要求三件事：可读的 diff、可重复跑的通过 / 拒绝用例、从 `Audit` 到 `Enforce` 的渐进开关。这三件事恰好把「未知」重新变回「已知」。
>
> **反例与适用前提**：这不等于「所有策略都必须先跑满两周观察窗」。对明确无历史包袱的新命名空间、或已由 CI 全量校验过的新策略，可以直接 `enforce`；主张针对的是**存量集群**与**跨团队共享的 ClusterPolicy**。另一个反例是极小型团队：只有几个人、一个命名空间、变更频率很低时，一套手工核对清单可能比引入策略引擎更划算——但即便如此，也应把「判定标准」写下来并留痕，否则一旦人员变动，口径就丢了。Thoughtworks Technology Radar 与 CNCF 安全白皮书都把「策略即代码」列为趋势与共识性指导，但本结论的论证不依赖它们背书 [R-25-6][R-25-7]。

### 25.1.1 合成案例：一次全量 enforce 让存量工作负载集体起不来

> 本案例为**合成案例**，综合 §25.1 反模式一的典型现象编写，用于把根因与分级恢复路径讲透，不对应任何真实事件 [R-25-8]。

**现场**。某平台组决定本周收尾 PSS 收紧，策略 PR 做了两件事：给全集群**所有**命名空间统一打上 `pod-security.kubernetes.io/enforce=restricted`（包括系统命名空间与其他团队的命名空间），同时把 `order-demo-require-nonroot` 从 `Audit` 一步推到 `Enforce`。CI 的 policy 工作流只对 `policies/**` 触发，而这个 PR 改的是命名空间标签渲染文件，策略测试根本没有跑。合并后 Argo CD 自动同步（见第 14 章）。

前 20 分钟风平浪静：enforce 标签不影响**已在运行**的 Pod——它们是历史版本创建的，不会被追溯驱逐。故障从第一个「日常事件」开始：节点维护触发驱逐、晚高峰触发 HPA 扩容（见第 18 章）、某团队发版触发滚动更新——这些操作都要**新建 Pod**，而新建全部被拒。集群进入「存量还能跑、增量起不来」的慢性失血状态：

- 事件流刷屏：`pods "api-7d9f" is forbidden: violates PodSecurity "restricted:v1.32": allowPrivilegeEscalation != false ...`；
- 扩容失败：HPA 反复算出新副本数，Pod 始终 `FailedCreate`；
- 滚动更新卡死：`ProgressDeadlineExceeded`，旧 Pod 已删、新 Pod 未起；
- 需要写临时目录的旧镜像 Pod 起不来，状态 `CreateContainerConfigError`；系统命名空间的 DaemonSet 驱逐后无法回补，监控出现节点空洞。

值班同学面对的不是一条告警，而是十几条互不相干的告警（见第 22 章面向症状的告警口径），根因被淹没——这正是全量 enforce 的隐藏代价：它把「策略判定」耦合进了所有不相关团队的发布路径 [R-25-1]。

**分级恢复**：先止血、再恢复容量、再收敛违规面、最后恢复阻断，全程不删审计。

**阶段 0｜判定影响面（目标 ≤ 5 分钟）**。先分清拒绝来自 PSS 还是 Kyverno，再统计 enforce 覆盖面：

```bash
# PSS 拒绝：事件文案含 violates PodSecurity
kubectl get events -A --field-selector reason=FailedCreate | grep -c 'violates PodSecurity'
# Kyverno 拒绝：对一个通过样例做 server dry-run，看报错是否为策略 message
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/pass.yaml
# 统计哪些命名空间被打上了 enforce
kubectl get ns -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.labels.pod-security\.kubernetes\.io/enforce}{"\n"}{end}'
```

**阶段 1｜止血（目标 ≤ 15 分钟）**。只降「阻断强度」，不删策略、不删记录：移除全量 enforce 标签（保留 warn / audit 继续收集违规清单），并把 Kyverno 策略降回 `Audit`：

```bash
kubectl get ns -o name | xargs kubectl label \
  pod-security.kubernetes.io/enforce- pod-security.kubernetes.io/enforce-version-
kubectl apply -f policies/order-demo-require-nonroot-audit.yaml
kubectl get clusterpolicy order-demo-require-nonroot \
  -o jsonpath='{.spec.validationFailureAction}{"\n"}'
```

通过标准：`pass.yaml` 的 server dry-run 恢复成功，且事件流 5 分钟内不再出现新的 `violates PodSecurity`。

**阶段 2｜恢复容量**。旧 Pod 尚在的工作负载只需确认扩容通道恢复，不必重启；旧 Pod 已删、新 Pod 起不来的立即重建：

```bash
kubectl -n <受影响命名空间> rollout restart deploy/<受影响负载>
kubectl -n <受影响命名空间> rollout status deploy/<受影响负载>
```

同时在 `docs/policy-exception.md` 登记本次全量降级：日期、原因、影响的 SHA、申请人、到期日期（最长 3 天）与恢复验证方式，并 `git commit`——应急操作也必须回到 Git（公理 5，见第 3 章）。

**阶段 3｜收敛违规面**。Kyverno background scan 恢复后自动补齐存量扫描结果，从 PolicyReport 与审计事件导出违规清单，按命名空间分派修复。典型修复只是给存量工作负载补几行 `securityContext`，例如对 api 的 Deployment：

```yaml
# deploy/base/deployment.yaml（api）新增的字段，镜像、端口、探针等其余契约字段不动
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: api
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
```

**阶段 4｜恢复阻断**。按 25.2.2 判据表逐级推进：`enforce=baseline` 先行，且只对本章三个 `order-demo-*` 命名空间生效；其他团队的命名空间各自跑自己的 warn → audit → enforce 灰度，**平台组不再代打标签**。全部通过 25.2.4 的回滚验证判据后，本次例外关闭。

**复盘**。根因不是策略太严，而是三件事同时缺位：PR 没有 scope 约束（可以给不属于 `order-demo` 的命名空间打 enforce 标签）、CI 没有强制跑策略测试（改标签的路径绕过了 policy 工作流）、动手前没有先看清违规面。对应三条整改：`ClusterPolicy` 的 `match` 显式限定三个 `order-demo-*` 命名空间；任何触及 PSS 标签渲染文件的 PR 都强制执行策略测试与 25.2.4 的通过标准；例外登记从「事后补记」改为「降级动作的前置条件」。这与本章开头「没有测试与灰度的策略，比没有策略更危险」互为印证。

## 25.2 落地策略与门禁：一个引擎、两处拦截、三级灰度

### 25.2.1 能力边界（不铺工具横比矩阵）

按 `book/decisions.md` U-04，本书只选**一个**示例实现：Kyverno 1.x（部署在命名空间 `kyverno`，策略命名 `order-demo-*`）。理由不是「它最好」，而是声明式策略好读、验签与校验规则能写在同一套 `ClusterPolicy` 里，第 24 章的验签策略与本章的加固策略不会各跑一套引擎 [R-25-3]。其余两者只作边界说明，不进入落地链路：

- **ValidatingAdmissionPolicy（VAP）** 是 Kubernetes 1.32 内置的轻量方案，用 CEL 表达式写在 API Server 里，不装任何控制器就能做简单校验；代价是只能校验、不能变更或生成资源，也没有内置的测试框架与策略报告。适合「只需要一条规则、不想引入 webhook 运维成本」的场景，本章给出完整可应用配置作为对比，但不作为 `order-demo` 的落地实现 [R-25-2]。
- **Gatekeeper 3.x** 用 Rego 写约束模板，表达力最强、适合跨组织复用复杂约束，代价是要维护 ConstraintTemplate 与 Rego 的学习成本。本书仅在能力边界处提及，**不作为示例实现**，也不与第 24 章的验签策略混用。

一句话判据：**简单校验优先看内置的 VAP；需要变更 / 生成 / 测试 / 灰度 / 报告，才上策略引擎。** 这条判据与第 5 章「最小工具集」的口径一致（见第 5 章），也是 SP-21 要求的「何时不该用」：只有一条规则时不该引入 Kyverno，跨命名空间统一治理时才该 [R-25-4]。

### 25.2.2 PSS 三级灰度判据表

| 阶段 | 命名空间标签 | 失败动作 | 观察指标 | 推进到下一级的条件 |
|---|---|---|---|---|
| 0 观察 | `warn=restricted`、`warn-version=v1.32` | 只向提交者回警告，Pod 照常创建 | CI 与 `kubectl` 输出里的警告条数 | 连续一个发布周期无新增警告 |
| 1 审计 | 加 `audit=restricted`、`audit-version=v1.32` | 不阻断，但写审计事件 / PolicyReport | 违规事件涉及的命名空间与工作负载清单 | 清单里的历史负载全部修完或登记例外 |
| 2 阻断 | 加 `enforce=baseline`、`enforce-version=v1.32` | 违规 Pod 直接拒绝创建 | 被拒请求数、误伤工单数 | 被拒请求全部为真实违规，无误伤 |
| 3 收紧（可选） | `enforce=restricted` | 同上，规则更严 | 同上 | 团队确认所有工作负载满足 `restricted` |

注意阶段 2 刻意停在 `baseline` 而不是一步到 `restricted`：`baseline` 挡住的是特权、宿主命名空间、宿主端口这类高危项，`restricted` 还会要求 `seccompProfile`、`allowPrivilegeEscalation: false` 等更细的字段。第 6 章的最小闭环已经带了 `runAsNonRoot` / `seccompProfile` / `capabilities.drop: ["ALL"]`，所以 `order-demo` 最终能到 `restricted`；但存量集群里的其他工作负载未必，先 `baseline` 再收紧才是灰度 [R-25-1][R-25-4]。

### 25.2.3 完整可应用配置（Kubernetes 1.32+，Kyverno 1.x）

**`policies/pss-baseline.yaml`** —— 阶段 2 的目标状态；命名空间与公共标签沿用第 6 章冻结契约，只增量添加 PSS 标签。

```yaml
  name: order-demo-staging

    app.kubernetes.io/name: order-demo

    pod-security.kubernetes.io/enforce-version: v1.32
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: v1.32

---
apiVersion: v1
kind: Namespace

  name: order-demo-prod

    app.kubernetes.io/name: order-demo

    pod-security.kubernetes.io/enforce-version: v1.32
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: v1.32
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/warn-version: v1.32
```

灰度命令（从阶段 0 逐级推进，每级都先观察再动手；`--overwrite` 只改标签、不动其他字段）：

```bash
kubectl label ns order-demo-dev order-demo-staging order-demo-prod \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/warn-version=v1.32 --overwrite
kubectl label ns order-demo-dev order-demo-staging order-demo-prod \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/audit-version=v1.32 --overwrite
kubectl label ns order-demo-dev order-demo-staging order-demo-prod \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/enforce-version=v1.32 --overwrite
kubectl apply -f policies/pss-baseline.yaml
```

**`policies/order-demo-require-nonroot.yaml`** —— 唯一示例策略，两条规则：非 root 运行、禁止 privileged。`=(...)` 是 Kyverno 的「存在则必须等于」锚点，能覆盖「完全没写 securityContext」的情况 [R-25-3]。

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: order-demo-require-nonroot
spec:
  validationFailureAction: Enforce
  background: true
  failurePolicy: Fail
  rules:
    - name: require-run-as-nonroot
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - order-demo-dev
                - order-demo-staging
                - order-demo-prod
      validate:
        message: "所有工作负载必须声明 runAsNonRoot: true（见第 6 章、第 25 章）"
        pattern:
          spec:
            securityContext:
              runAsNonRoot: true
    - name: disallow-privileged
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - order-demo-dev
                - order-demo-staging
                - order-demo-prod
      validate:
        message: "不允许 privileged 容器（见第 25 章）"
        pattern:
          spec:
            containers:
              - =(securityContext):
                  =(privileged): false
```

**`policies/order-demo-require-nonroot-audit.yaml`** —— 灰度 / 误伤回滚版，仅把 `validationFailureAction` 改为 `Audit`，其余与上面逐字相同；`kubectl apply` 覆盖即降级。

**`policies/tests/pass.yaml`** —— 通过样例，字段沿用第 6 章契约。

```yaml
apiVersion: v1
kind: Pod
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 策略单元测试 | `kyverno test` 四条断言全部通过，退出码 0 |

| 审计留痕 | 命名空间存在 PolicyReport，违规请求可查（见第 26 章） |

**回滚 / 降级命令与步骤**。误伤（合法工作负载被拦）时的处理顺序是：先降级止血、再登记例外、再修策略、最后恢复，全程不删审计：

```bash
  pod-security.kubernetes.io/enforce-version- --overwrite
```

### 25.2.5 mutate / generate 与第 9 章 ConfigMap 的联动

validate 只能拦，不能补默认值，也不能为新环境铺底座。Kyverno 1.x 的另两类规则正好补位：**mutate** 在资源通过准入时原位补字段，**generate** 在触发资源（这里是命名空间）出现时生成目标资源。`order-demo` 对它们的用法收敛为一组生成 + 一组注入，都围绕第 9 章的 `order-demo-config` 展开；分工判据一句话：**mutate 只做无争议、幂等、Git 里也写得出来的默认值；generate 只做命名空间级底座；有争议的判定一律交给 validate** [R-25-3]。

**先讲一个必须避开的坑：generate 遇上 immutable，不能用 `synchronize`。** 第 9 章起 `order-demo-config` 是 `immutable: true` 的 ConfigMap——这类对象一旦创建就**不可原位更新**（immutable 的收益正是省掉 watch 广播并防止运行中被改，见第 9 章）。而 Kyverno generate 的 `synchronize: true` 会在源资源变化后**回写更新**目标资源，撞上 immutable 就会持续报 `Invalid argument: ... immutable`，generate 的后台任务卡死在错误里。所以本例显式取 `synchronize: false`：骨架只生成一次，之后键值变化一律走 Git 晋升（见第 9 章、第 14 章），漂移由 GitOps 收敛兜底。

```yaml
# policies/order-demo-generate-config.yaml（Kyverno 1.x）
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: order-demo-generate-config
spec:
  background: true
  rules:
    - name: generate-order-demo-config-skeleton
      match:
        any:
          - resources:
              kinds: ["Namespace"]
              names: ["order-demo-*"]   # names 支持通配符，只覆盖本应用命名空间
      generate:
        apiVersion: v1
        kind: ConfigMap
        name: order-demo-config
        namespace: "{{ request.object.metadata.name }}"
        synchronize: false             # immutable 对象不可回写更新，见本节说明
        data:
          metadata:
            labels:
              app.kubernetes.io/name: order-demo
          immutable: true
          data:
            LOG_LEVEL: "info"
```

生成的骨架只覆盖「命名空间先建、第 9 章 Git 清单尚未 apply」的窗口期，让新环境至少有一份不可变的配置可引用；清单晋升进来之后以 Git 为准，两者字段冲突时按第 9 章的口径先删后建。`LOG_LEVEL` 只是骨架示例项，生产键集合以第 9 章 Git 清单为准。

**mutate：给漏写引用的 Pod 补上 `order-demo-config`。** 第 9 章的口径是容器通过 `envFrom` 读这份 ConfigMap，新写的 Deployment 偶尔会漏掉这一段——与其等 Pod 起来后行为不对，不如在准入时补齐。写这条规则必须知道两个语义边界：其一，strategic merge 按 `name` 合并容器列表，`(name): "*"` 锚点匹配每个容器；其二，`envFrom` 是**无合并键的列表**，strategic merge 对它是整体替换，会覆盖容器自己声明的其他 `envFrom`（例如第 9 章经 ESO 注入的 Secret 引用）。因此用前置条件收紧：**只要任一容器已写了 envFrom，整个 Pod 一律跳过注入**，交给 validate 与 CI 兜底 [R-25-3]。

```yaml
# policies/order-demo-mutate-envfrom.yaml（Kyverno 1.x）
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: order-demo-mutate-envfrom
spec:
  background: false                    # mutate 只在准入链路实时生效
  rules:
    - name: inject-config-envfrom
      match:
        any:
          - resources:
              kinds: ["Pod"]
              namespaces:
                - order-demo-dev
                - order-demo-staging
                - order-demo-prod
      preconditions:
        all:
          - key: "{{ request.object.spec.containers[?envFrom] | length(@) }}"
            operator: Equals
            value: 0
      mutate:
        patchStrategicMerge:
          spec:
            containers:
              - (name): "*"
                envFrom:
                  - configMapRef:
                      name: order-demo-config
```

**mutate 的真正代价：与 GitOps 的漂移。** 准入变更只改了集群里那一个对象，Git 清单里并没有 `envFrom`，Argo CD 下一次比对就会报 OutOfSync（见第 14 章），严重时被当作漂移「纠正」掉，注入字段随之消失。所以被注入的字段必须回到 Git：首选把 `envFrom` 写进 `deploy/base/deployment.yaml`（25.2.3 的 pass.yaml 就显式携带了完整安全字段，同一条纪律），策略只在漏网时兜底；若团队坚持由策略注入而不进 Git，必须在 Argo CD 的 `ignoreDifferences` 里显式豁免并登记理由——豁免也是例外，同样要走 25.2.7 的审批与到期。

**验证与回滚**：

```bash
# 离线验证 mutate：server dry-run 返回的就是注入后的对象
kubectl -n order-demo-dev apply --dry-run=server -o yaml -f policies/tests/pass.yaml \
  | grep -A3 'envFrom'
# 生成验证：新建沙箱命名空间，应出现骨架 ConfigMap 且不可原位更新
kubectl create ns order-demo-sandbox
kubectl -n order-demo-sandbox get cm order-demo-config \
  -o jsonpath='{.immutable}{"\n"}'
kubectl -n order-demo-sandbox delete cm order-demo-config
kubectl delete ns order-demo-sandbox
```

通过标准：dry-run 输出中每个容器的 `envFrom[0].configMapRef.name` 为 `order-demo-config`；沙箱命名空间的 `immutable` 为 `true`。回滚：`git revert` 对应策略 PR 后 `kubectl apply` 覆盖即可；应急时可 `kubectl delete clusterpolicy order-demo-generate-config order-demo-mutate-envfrom`（最后手段，须登记，口径同 25.2.4）；已生成的骨架 ConfigMap 保留在命名空间里，由 Git 接管或显式删除。

### 25.2.6 策略变更从 PR 到生产：全链路时序与三个留痕点

策略是代码，就要能回答三个问题：**这条规则是谁、在哪个环节、依据什么证据放行或拦下的**。下面用一次真实形态的策略变更——「把 `disallow-privileged` 的 message 改得更具体」——串起全链路。文字时序如下（①②③为留痕点）：

```text
开发者 ──提 PR（改 policies/ 或 deploy/）──▶ GitHub
 │                              │
 │              ①【留痕点：CI】policy.yml 触发
 │              kyverno test 四条断言 + 离线校验（25.2.3）
 │              → check run 结果记录在 PR 页面
 ▼
review + merge ──▶ main
 │
Argo CD 检测到 policies/ 变化并同步（见第 14 章）
 │
sync：apply ClusterPolicy ──▶ Kyverno 热加载策略
 │
开发者 / 流水线提交工作负载（Pod 创建或滚动更新出新 Pod）
 │
 │              ②【留痕点：准入】API Server 调 Kyverno webhook
 │              → 同步返回 allow / deny 与 message
 │              → API Server 审计日志记录本次判定
 ▼
对象进入集群（或被拒绝）
 │
 │              ③【留痕点：审计】background scan 周期重扫存量资源
 │              → 违规写入命名空间级 PolicyReport
 │              → 与第 26 章的审计链路衔接
 ▼
三处留痕可回溯：CI 证明「PR 时规则没有被改松」；
准入证明「提交时被哪条规则以什么文案拒绝」；
审计证明「存量资源此刻是否合规」。
```

| 环节 | 触发 | 执行者 | 留痕载体 | 查询方式 | 失败时的表现 |
|---|---|---|---|---|---|
| CI【留痕点①】 | PR 触及 `policies/**` 或 `deploy/**` | `policy.yml`（25.2.3） | GitHub check run：四条断言结果与离线校验输出 | PR Checks 页或 `gh run view <id>` | check 不通过，PR 无法合并 |
| 准入【留痕点②】 | Pod 创建 / 更新请求 | Kyverno admission webhook | API Server 审计日志 + 同步返回的 deny message | `kubectl apply --dry-run=server -f policies/tests/fail.yaml` 复现同一报错 | 提交方直接收到 `不允许 privileged 容器` |
| 审计【留痕点③】 | background scan 周期执行 | Kyverno 后台扫描 | 命名空间级 PolicyReport | `kubectl -n order-demo-dev get policyreport -o yaml` | 违规条目出现 fail 记录，可联动告警（见第 22 章） |

三个留痕点各有不可替代的作用：**CI 留痕**防「策略被改松」——25.2.3 的 CI 第三步专门验证拒绝样例必须失败；**准入留痕**是唯一与真实提交同源的判定（server dry-run 复现的是同一条判定路径，这正是 §25.1 准入策略那条可测量性质），也是例外审批的证据来源；**审计留痕**覆盖存量——准入只看新建与更新，存量资源的合规状态只有 background scan 能回答，PolicyReport 因此成为 25.2.2 灰度判据表观察指标的载体。三处缺一不可：只有 CI 会漏「绕过 Git 的手工提交」；只有准入会漏「历史存量」；只有审计给不了提交时的即时反馈。第 26 章的 RBAC 与审计在此基础上补齐「**谁**提交的」这最后一环 [R-25-3][R-25-5]。

### 25.2.7 跨团队共享 ClusterPolicy 的例外审批流与到期自动失效

25.1 反模式三与 25.2.3 的 `docs/policy-exception.md` 解决了「登记」问题，但跨团队共享的 `ClusterPolicy` 还有一个结构性矛盾：**策略本体是全局的，例外是局部的**。A 团队为排障临时需要一个 privileged 调试容器，若把 `validationFailureAction` 改成 `Audit`，全公司所有命名空间的拦截同时失效；事后忘了改回来，等于给所有人开了一张无限期豁免。所以例外的落点必须从「改策略」前移到「策略之外的载体」。`order-demo` 自家三个命名空间的整段降级仍按 25.2.4 处理（影响面就是自家）；**跨团队场景一律用例外资源，不动 `ClusterPolicy` 本体** [R-25-3]。

**载体：Kyverno 1.x 的 PolicyException，且必须带 `expiration`。** 它不为 `ClusterPolicy` 改一个字段，只对「指定命名空间内的指定对象、指定规则」豁免；`expiration` 到期后引擎自动忽略该例外，不需要任何人动手：

```yaml
# policies/exceptions/2026-11-11-privileged-debug.yaml（Kyverno 1.x，expiration 需较新 1.x 版本）
apiVersion: kyverno.io/v1
kind: PolicyException
metadata:
  name: privileged-debug-2026-11-11
  namespace: order-demo-dev          # PolicyException 是命名空间级资源
spec:
  policyName: order-demo-require-nonroot
  ruleNames:
    - disallow-privileged
  expiration: "2026-11-14T00:00:00Z" # 到期自动失效；最长 3 天，与登记表规则一致
  conditions:
    any:
      - key: "{{ request.object.metadata.name }}"
        operator: Equals
        value: "privileged-debug"    # 只豁免点名对象，见下方验证
```

**审批流（全部走 Git，见第 14 章）**：申请人提例外 PR——同时新增上述 PolicyException 文件并在 `docs/policy-exception.md` 追加一行，两处字段一一对应；`CODEOWNERS` 把 `policies/exceptions/` 设为双人必需评审：平台组策略 Owner 判「这条豁免是否可接受」，目标命名空间属主团队判「是否真的需要」；合并后 Argo CD 自动同步，例外即时生效，全程 `ClusterPolicy` 零改动、其他团队零感知。例外到期也不需要任何人「改回来」——这是与反模式三的本质区别：**降级的可逆性内建在资源里，而不是内建在人的记忆里。**

**到期自动失效的闭环**。PolicyException 过期后引擎不再豁免：同一点名对象下次提交或被 background scan 扫到时重新被拒、重新出现在 PolicyReport——失效本身自动留痕。再配一道每日定时核对，确认没有「已过期却未归档」的例外文件：

```yaml
# .github/workflows/policy-exception-expiry.yml
name: policy-exception-expiry
on:
  schedule:
    - cron: "0 9 * * *"
jobs:
  check-expired-exceptions:
    runs-on: ubuntu-latest
    steps:
      - name: 检出源码
        uses: actions/checkout@v4
      - name: 已过期但仍入库的例外必须清理
        run: |
          today=$(date -u +%Y-%m-%dT%H:%M:%SZ)
          found=0
          for f in policies/exceptions/*.yaml; do
            exp=$(yq '.spec.expiration' "$f")
            if [ "$exp" != "null" ] && [ "$exp" \< "$today" ]; then
              echo "过期例外未归档：$f (expired at $exp)" >&2
              found=1
            fi
          done
          exit $found
```

核对失败即提醒平台组开「关闭例外」的 PR：把文件移入 `policies/exceptions/archive/` 归档，并在登记表补上「恢复验证」结果——历史记录保留，但不允许过期例外继续躺在生效目录里。

**验证与回滚**：

```bash
kubectl -n order-demo-dev apply -f policies/exceptions/2026-11-11-privileged-debug.yaml
# 例外窗口内：豁免只命中点名的 privileged-debug；其他特权 Pod 仍被拒
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/fail.yaml
# background scan 后，PolicyReport 中 disallow-privileged 对豁免对象不再报违规
kubectl -n order-demo-dev get policyreport -o yaml | grep -B2 -A5 privileged-debug
```

通过标准：`fail.yaml`（对象名 `privileged-fail`，不在例外条件内）仍被拒，证明豁免是局部的；`privileged-debug` 在窗口内可创建，到期后同一 dry-run 恢复被拒。回滚：`git revert` 例外 PR（删除 PolicyException）即立即恢复全额阻断，无需触碰 `ClusterPolicy`。

### 25.2.8 四类规则的适用边界：validate / mutate / generate / verifyImages 各自「何时不该用」

25.2.3 与 25.2.5 已把 validate、mutate、generate 三类规则用在具体场景里，第 24 章的验签门禁用的是第四类 verifyImages。四类规则共享同一份 `ClusterPolicy` 与同一条准入链路，但回答的问题不同，误用方式也不同。判据表：

| 规则类型 | 回答的问题 | 何时不该用 | 误用的典型后果 | 本书落点 |
|---|---|---|---|---|
| validate | 这个对象允许进入集群吗 | 需要「改一下就能通过」的场景——那是 mutate 或修清单的活；也不该校验运行时状态（副本数、错误率属于监控口径，见第 20 / 21 章） | 提交者拿到 deny 却不知道怎么改，策略沦为口头问询的触发器 | 25.2.3 |
| mutate | 能否安全地补一个无争议默认值 | 注入内容存在团队分歧时；注入字段是另一条 validate 规则的通过条件时（见下） | 25.2.5 已写的 GitOps 漂移；「删掉 mutate 即集体违规」的隐性耦合 | 25.2.5 |
| generate | 新命名空间要不要自动铺底座 | 目标对象同时被 Git 或其他控制器管理（25.2.5 的 immutable 坑）；生成应用级工作负载——应用清单归 Git（公理 5，见第 3 章） | 双向写互相覆盖，控制循环打架 | 25.2.5 |
| verifyImages | 这个镜像是不是我们构建并签名的 | 约束「容器怎么运行」时（那是 PSS / validate 的职责）；对系统组件镜像仓库无差别启用时 | 与 PSS 重复表达同一约束、灰度口径分裂；节点重建时系统组件镜像被拒，集群自举失败 | 第 24 章 |

validate 的边界一句话：**它只对「提交时的对象」做判定**。想「拒绝副本数为奇数的 Deployment」语法上完全可行，但那是容量策略，应在第 18 章的 HPA 口径里处理；把性能类判断塞进准入，只会在每次发布同步时制造莫名的拒绝与更长的反馈回路 [R-25-3]。

mutate 在 25.2.5 的三条判据（无争议、幂等、Git 里也写得出来）之外补第四条：**注入字段不得成为另一条 validate 规则的通过条件**。反例：若 validate 要求 `runAsNonRoot: true` 而 mutate 注入它，mutate 策略一旦被删除或降级，validate 依旧 Fail——整批没写字段的存量清单集体被拒，且没人记得两条策略之间有依赖。判据：每条 validate 的通过条件都必须由清单自己满足（或由 25.2.5 的 Git 兜底路径满足），mutate 只能锦上添花，不能雪中送炭 [R-25-3]。

verifyImages 与第 24 章的分工是：策略本体、签名流水线、验签失败处置都在第 24 章，本章只补两条边界。其一，verifyImages 挡的是「镜像来源」，PSS / validate 挡的是「运行形态」，二者不可互替，也不可重复表达同一条约束——否则同一违规两处报错、灰度口径分裂，这正是 25.2.3 里 VAP 对比示例「不要同时启用」注释的同一逻辑。其二，match 必须排除平台组件镜像仓库：把验签范围拉到 `kube-system`，等于把集群自举与签名基础设施绑死，签名服务的一次抖动会放大成节点回补失败 [R-25-3]。

### 25.2.9 准入 webhook 的失败模式与性能：Fail / Ignore 的取舍

前面所有小节都默认「webhook 会被调用并正常返回」，但准入策略的可用性风险恰恰藏在这个默认里。API Server **同步**调用 Kyverno 的 admission webhook：调用失败（副本全灭、网络抖动、耗时超过上限——API Server 对单个准入调用的默认超时为 10 秒）时，按 `failurePolicy` 二选一：`Ignore`（fail open，放行）或 `Fail`（fail closed，拒绝）。`ClusterPolicy` 的 `spec.failurePolicy` 就是给这条链路按策略定口径的开关，25.2.3 的示例策略已取 `Fail` [R-25-2][R-25-3]。

按策略类型分口标的决策表：

| 策略类型 | 建议 failurePolicy | 理由 | 策略失效时的后果 |
|---|---|---|---|
| 安全类 validate（如 require-nonroot） | Fail | fail open 等于「引擎挂了就回到零护栏」，与 25.1 反模式三同构 | 可用性代价：引擎不可用期间所有匹配的 Pod 创建被拒 |
| 验签门禁 verifyImages（第 24 章） | Fail | 同上，且供应链门禁失效的审计代价更高 | 同上 |
| mutate 默认值注入（25.2.5） | Ignore | 注入缺失只是清单不完整，CI 与 Git 兜底 | 注入暂时失效，漂移由 GitOps 收敛 |
| 纯观察类（`validationFailureAction: Audit`） | Ignore | 本来就不阻断，fail closed 没有安全收益 | 观察数据短暂缺失 |

超时的两个语义要分清。其一，API Server **不重试**准入调用：对 Fail 类策略，一次超时或失联就是一次拒绝，不存在「再试一次就过了」——所以「偶发超时导致发布失败」在 Fail 口径下表现为「偶发拒绝」，值班容易误判成策略误伤而去做 25.2.4 的降级，实际该做的是查引擎负载。其二，超时上限是双刃：设得过小，background scan 高峰或镜像验签抖一下就把合法提交判死；设得过大，引擎真挂掉时每次 Pod 创建都要白等满上限，故障被放大成全集群发布停摆。判据：超时上限取正常准入耗时 P99 的 2–3 倍，而不是拍脑袋取最大值；扩容阈值（见第 18 章）把准入耗时当作前兆指标，在逼近上限之前先扩副本。

fail closed 的代价必须显式接受而不是默认忍受：Kyverno 崩溃式不可用期间，HPA 扩容（见第 18 章）、滚动更新、DaemonSet 回补全部停在 Pod 创建这一步——症状与 25.1.1 合成案例相同，但根因是「引擎死了」而不是「策略拒绝」。区分两者是排障第一步：

```bash
# 策略 deny：报错文案是策略 message（如「不允许 privileged 容器」）
# webhook 失联：报错含 connection refused / timeout / failed calling webhook
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/pass.yaml
kubectl -n kyverno get pods
```

一个关键事实能省掉大量误判：**Kyverno 在优雅退出时会主动摘除自己的准入注册**，所以滚动升级、正常缩容这类运维动作不会留下 fail closed 的注册；真正危险的只有崩溃式全灭（节点故障把所有副本同时带走）[R-25-3]。缓解按优先级三步：

1. 副本 ≥ 2 并配 `PodDisruptionBudget`（见第 8 章），部署在独立节点池，避免与业务负载一起被驱逐；
2. match 收窄（25.2.3 只匹配三个 `order-demo-*` 命名空间）不只是性能手段，也是**爆炸半径**手段——API Server 只对匹配资源调用 webhook，收窄后引擎抖动影响的提交面同步变小 [R-25-3]；
3. 准入延迟纳入观测：Kyverno 暴露准入响应耗时指标，用第 21 章的 Prometheus 抓取、按第 22 章口径告警——耗时持续逼近超时上限本身就是「引擎要挂」的前兆症状。

应急止血（最后手段，先 `get` 确认名称再 `delete`，并按 25.2.7 登记）：

```bash
# 摘除 Kyverno 的准入注册，让 API Server 不再调用（而非调用失败后拒绝）
kubectl get validatingwebhookconfigurations -l app.kubernetes.io/name=kyverno -o name
kubectl delete validatingwebhookconfigurations -l app.kubernetes.io/name=kyverno
# 恢复后 Kyverno 会自动重注册；用 fail.yaml 的 dry-run 确认拦截回归：
kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/fail.yaml
```

选「摘注册」而不是 25.2.4 的「删 ClusterPolicy」：前者不动策略与审计链，引擎恢复后注册自动回来、拦截全额回归；后者会断审计链，只该在策略本身写错时使用。两者都必须登记例外——止血动作本身也是变更。

### 25.2.10 策略回归门禁：测试要拦的是「策略退化」，不只是「清单违规」

25.2.3 的 policy.yml 已让 CI 跑起 `kyverno test`，但那只回答「测试存在且通过」；策略作为代码，真正的回归风险是**策略被改松、改偏、改出范围**而测试照样绿。把门禁从「测试存在」升级为「测试必须覆盖变更类型」：

| 变更类型 | PR 必跑 | 夜间端到端 | 额外要求 |
|---|---|---|---|
| 改 message / 注释 | `kyverno test` | 否 | 无 |
| 改 pattern / 锚点 | `kyverno test` | 是 | pass / fail 样例断言不得删除或反向 |
| 改 match 范围 | `kyverno test` | 是 | 同步新增边界样例（见下） |
| 改 `validationFailureAction`（Audit → Enforce） | `kyverno test` | 是 | PR 附 25.2.2 观察窗口证据，否则打回 |
| 新增规则 | `kyverno test` | 是 | 新规则必须有独立 fail 样例 |
| 动 webhook 配置 / `failurePolicy` | — | 是（staging 先行） | 按 25.2.9 判据表评审后放行 |

最容易漏的是「改 match 范围」：把 namespaces 列表改错（拼错、删掉一个环境），现有四条断言**全部照常通过**——因为 pass.yaml 与 fail.yaml 都在范围内，按原语义判定。所以范围类变更必须同步新增两个边界样例：一个**范围外**命名空间的违规 Pod（期望 pass，证明没有误伤别人），一个**范围内**新环境的违规 Pod（期望 fail，证明没有漏拦）。测试样例要贴着判定的**边界**，而不是贴着正常路径——与第 11 章「提交一个错误字段被 CI 拦下」同源。

**夜间端到端的定位（本书观点，不需要外部背书）**：

> **主张**：`kyverno test` 是规则级单元测试，够格做 PR 门禁；「策略与集群真实链路」（webhook 注册、PolicyReport 生成、background scan 落账）只有在真实集群里才能验证，应放 nightly 而非 PR 门禁。Chainsaw（Kyverno 团队的集群级场景测试工具，0.x）在 kind（见第 11 章版本矩阵）里按「apply 策略 → 提交违规对象 → 断言被拒」编排步骤，适合承担这一层。
>
> **论证**：PR 门禁的预算是分钟级，每次 PR 起一个真实集群会拖到十分钟级，团队很快会用「跳过 CI」对抗门禁——门禁越重越容易被绕过；nightly 的预算是小时级，能承载真实集群用例。两层各司其职：CI 管「规则语义没有退化」，nightly 管「链路行为符合预期」。
>
> **反例与适用前提**：单集群、策略少于十条、发布频率低的团队，可只用 `kyverno test` 加人工按 25.2.4 验证清单在 staging 跑一遍；引入 chainsaw 的前提是策略数量与变更频率大到「人工回归开始漏项」。反向反例：不要把 chainsaw 用例挪到 PR 门禁——它验证的是链路而非语义，PR 阶段起集群纯属浪费。

```yaml
# policies/e2e/privileged-rejected-test.yaml（chainsaw 0.x，nightly 于 kind 中执行）
apiVersion: chainsaw.kyverno.io/v1alpha1
kind: Test
metadata:
  name: privileged-pod-rejected
spec:
  steps:
    - try:
        - apply:
            file: ../order-demo-require-nonroot.yaml
        - apply:
            file: ../tests/fail.yaml
          expect:
            - check:
                ($error != null): true   # 违规 Pod 必须被准入拒绝，断言报错存在
```

运行前置：kind 集群已按第 11 章版本矩阵创建、Kyverno 1.x 已安装于命名空间 `kyverno`。命令与通过标准：

```bash
chainsaw test policies/e2e
kubectl -n order-demo-dev get policyreport -o yaml | grep -c disallow-privileged
```

通过标准：chainsaw 退出码 0；PolicyReport 计数大于 0，证明 background scan 落账与准入口径一致。nightly 红灯按第 22 章口径开出带 runbook 链接的告警，处置入口是 25.2.9 的失败模式判别命令。
