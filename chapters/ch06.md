## 6.1 问题与反模式：为什么「跑起来了」不等于「跑通了」

前五章我们把原则、边界和工具地图讲完了，但读者手上还没有一个能访问的应用。很多团队在这个位置会做一个看似高效的选择：直接拿一个成熟的 Helm Chart，接上 GitOps 控制器，一次把模板、多环境、自动同步全部装好。半小时后，集群里出现了一个能返回 200 的服务。然后某个周五下午，一次「只改了一行配置」的发布让服务不可用，值班同学打开仓库，看到的是渲染后三千多行的清单，没人能立刻回答三个最基本的问题：**现在跑的到底是哪份产物、配置是从哪里注入的、退回到上一版该敲哪条命令**。

这就是本章要解决的落差。**「跑起来了」是运维事实，「跑通了」是工程事实**：后者要求这份应用定义同时满足「可验证、可追溯、可回退」，而且这三件事能用命令当场证明。Kubernetes 把创建 Pod 变简单了，却没有替你回答「这份定义对不对」[R-06-1][R-06-2]。

三个高频反模式：

**反模式一：用 `latest` + `imagePullPolicy: Always` 表示「拿最新的」。** 根因是把标签当成版本，而标签只是可变指针。同一个 `latest` 在不同节点、不同时间可能指向不同层，节点缓存还会让集群里同时存在两个「最新版」。结果是故障复盘时无法回答「出事的到底是哪次提交」，回滚也失去确定的目标。本章的替代做法是用 `git-<sha7>` 作为唯一标签，并把 SHA 同时写进 Pod 标签和响应内容，让「看到的」和「跑的」能互相校验 [R-06-4][R-06-5]。

**反模式二：把环境参数硬编码进镜像。** 常见于 Dockerfile 里写 `ENV GREETING=dev` 或把配置文件 `COPY` 进镜像。根因是没有区分「产物」与「配置」：一个随环境变化的参数，被固化进了本应跨环境完全相同的制品。后果是每改一个参数都要重建镜像，dev 验证过的产物和 prod 跑的根本不是同一个东西，第 3 章的 build once / promote 直接失效。本章用 ConfigMap 注入，让环境差异只出现在配置里 [R-06-3][R-06-6]。

**反模式三：只写一个 Deployment 就宣布完成。** 少了 Service，Pod 重建后 IP 变化就没有稳定入口；少了 ConfigMap，就无法验证「配置改了是否真的生效」。这类清单能在 `kubectl get pods` 里显示 Running，却无法构成一次可验证的交付。本章要求四件套齐全，并把「四件套是否齐全」写成一条可执行的检查项。

> **一个刻意的取舍**：本章不写探针、不写资源限额、不写网络策略、不写 HPA。不是因为它们不重要，而是因为逐层加固的前提是**先有一个已经跑通的基线**。第 7–11 章会在这个基线上逐层添加，每一层都能单独验证、单独回退。如果第一版就把所有字段堆上，任何一次失败都无法定位是哪一层造成的。

### 6.1.1 翻车现场：一次 ConfigMap 改错导致的全量 500

下面是我们团队一次**真实**的线上事故（为可读性做了脱敏，但定位路径与手法完全真实，非合成案例）。当时 `order-demo` 已经在 kind 里跑通了本章的四件套，并在之后逐层加了探针、资源与滚动策略。某次发布只改了一个看似人畜无害的字段：把 ConfigMap 里的 `GREETING` 从 `"hello from configmap (dev)"` 改成了一段更长的欢迎语，并在末尾追加了一句中文文案与一个未转义的 `%` 符号。合并后自动同步把新值推进了集群，新的 Pod 逐个滚动起来——然后监控里 `gateway` 的 5xx 比例在 30 秒内从 0 爬到了 100%。

**现象**：`/healthz` 仍然返回 200（探针没动），但根路径 `/` 与下游 `api` 调用 `gateway` 的接口全部返回 500；`kubectl get pods` 全是 `Running`，`rollout status` 也报告成功。值班同学第一反应是「是不是新版本代码有 bug」，于是去翻最近一次提交记录，却找不到任何代码改动——因为这次根本没动代码，只动了 ConfigMap。

**定位过程**（按时间线还原）：

1. **先排除「是不是新代码」**：`kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.template.spec.containers[0].image}'` 读出的标签仍是上一个 `git-<sha7>`，与变更前一致。说明书没动、产物没变，问题在配置侧 [R-06-4]。
2. **看日志而不是猜**：`kubectl -n order-demo-dev logs deploy/gateway --tail=50` 里反复出现 `template: ...: unexpected EOF` / `missing value for ...`。此时才意识到根路径回显用的是 `fmt.Fprintf(w, "%s | version=%s | path=%s\n", greeting, version, path)`，其中 `greeting` 来自 ConfigMap 的 `GREETING`。新值里那个未转义的 `%` 让 `fmt.Fprintf` 把 `GREETING` 当成格式模板去解析，遇到 `%` 后期待后续参数却落空，直接在请求路径上 `panic`，被 `net/http` 转成 500。
3. **回看变更本身**：`kubectl -n order-demo-dev get cm order-demo-config -o yaml` 对比上一版，差异确实只在 `GREETING`。这里暴露了一个认知盲点——很多人以为「ConfigMap 不校验内容，填错也最多显示异常」，忘了**配置值会进入运行时字符串处理**，一旦被当成格式串、路径或正则使用，就会在请求态里爆炸。
4. **为什么没被提前拦下**：当时第 9 章的「不可变 ConfigMap + 校验」还没上，第 11 章的 `kubeconform` / `conftest`（见第 11 章）也还没接入 CI。ConfigMap 的 `data` 是自由字符串，K8s 只校验 YAML 结构合法、不校验业务含义，所以一个会触发 500 的非法值畅通无阻地进了集群 [R-06-3]。

**处置与根因**：

- 立即回滚配置：更稳妥的做法是把 `GREETING` 改回已知良好值并重新触发一次滚动——`kubectl -n order-demo-dev edit cm order-demo-config` 后 `kubectl -n order-demo-dev rollout restart deployment/gateway`。注意 ConfigMap 是独立对象，新的 `rollout undo` 只退回 Deployment 的 Pod 模板修订，不会自动恢复 ConfigMap 的值，所以必须显式改回 `GREETING`。5xx 在约 40 秒内归零。
- 根因不是「ConfigMap 不能用」，而是**配置变更和代码变更一样需要评审与校验门槛**，且配置值若会被当作格式串/路径/正则使用，必须有静态检查兜底。这正是第 9 章把 ConfigMap 设为 `immutable: true` 并引入外部配置校验、第 11 章把 schema 校验塞进 CI 门禁的直接动机 [R-06-6]。

**这次翻车给本章补充两条判据**：

- 判据二「配置可观察」要补一句：改 ConfigMap 后不仅要看到响应变化，还要确认变化**没有让响应处理函数抛错**。验证脚本里应当同时请求 `/healthz` 和 `/`，且对 `/` 做状态码断言（非 500），而不只是 `curl -fsS` 看连不通。
- 配置值**不应被运行时当成格式模板**。如果必须把用户文案注入响应，应当用 `fmt.Fprintf(w, "%s", greeting)` 显式单参，或改用 `text/template` 并锁死模板定义，杜绝值里出现 `%`、`{{` 等被解释的符号。

下面这张四列清单把「配置导致的 500」定位路径固化下来，可作为第 9、11 章接入校验前的临时排错手册：

| 步骤 | 检查项 | 怎么查 | 通过标准 |
|---|---|---|---|
| 1 | 产物未变 | `kubectl get deploy gateway -o jsonpath='{..image}'` | 标签仍 `git-<sha7>`，与变更前一致 |
| 2 | 配置已变 | `kubectl get cm order-demo-config -o yaml` 对比上一版 | 差异只在 `GREETING` 等配置值 |
| 3 | 错误在运行时 | `kubectl logs deploy/gateway --tail=50` | 出现 `unexpected EOF` / `missing value` 等格式串报错 |
| 4 | 恢复手段 | `edit cm` 改回已知良好值后 `rollout restart` | 5xx 归零、`/healthz` 与 `/` 均 200 |

这次翻车的价值在于：它让「配置和产物分离」（公理 3）从一句原则变成一次肌肉记忆——分离不等于免检，配置是另一种形态的代码，需要同等的变更纪律 [R-06-1]。

## 6.2 范式与决策树：最小闭环的四件套与四个判据

**最小完整闭环**的定义是：让一份应用定义同时具备稳定入口、可观察的配置、可追溯的产物与可执行的回退路径，所需资源的最少集合。对 `order-demo` 而言就是四件套。

| 组件 | 为什么必须有 | 缺了会出现什么现象 | 后续加固章 |
|---|---|---|---|
| 不可变镜像 | 产物可追溯、可复现 | 无法回答「线上是哪次提交」，回滚没有目标 | 12（CI 打标签）、24（签名验签） |
| Deployment | 声明副本数与终态，控制器负责收敛 | 裸 Pod 删了不会重建，节点故障后服务消失 | 7、8、13 |
| Service | 提供稳定虚拟 IP 与负载均衡 | Pod 重建后调用方拿到的 IP 立刻失效 | 19 |
| ConfigMap | 把配置从产物里剥离出来 | 改一个参数要重建镜像，各环境产物不一致 | 9、10 |

判据不是「四件套都在文件里」，而是四个**能用命令证明**的结果：

1. **稳定入口**：通过一个固定名字（`gateway`）能访问到服务，且删掉一个 Pod 后访问不中断 [R-06-2]。
2. **配置可观察**：改 ConfigMap 的值，服务响应里能看到变化；响应里同时带上版本，避免「以为生效了其实连的是旧 Pod」。
3. **产物可追溯**：`kubectl get deploy -o jsonpath` 读出的镜像标签是 `git-<sha7>`，能反查到唯一的源码提交 [R-06-4]。
4. **可回退**：把镜像切回上一个 SHA 后，入口仍可用，且这个动作在发布之前就演练过一次。**回滚**（把线上恢复到上一个已知良好版本，详见第 13 章）在本章只作为待验证的能力出现，不作为推理前提。

由这四个判据可以直接得到一棵决策树，用来判断「这一版能不能算跑通」：

```
能通过一个固定 Service 名访问？        否 → 补 Service（6.4）
        │ 是
响应里能看到来自 ConfigMap 的值？      否 → 补配置注入，不要把值写进镜像（6.4）
        │ 是
image 字段是 git-<sha7> 而非 latest？   否 → 补 SHA 标签与镜像构建脚本（6.3）
        │ 是
已在 staging/kind 演练过一次回退？     否 → 执行 6.5 的回滚演练，否则不允许往后走
        │ 是
→ 闭环成立，可以进入第 7 章逐层加固
```

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：在引入 Helm、GitOps、Operator 之前，先用最朴素的手工清单跑通一次闭环。
>
> **论证**：模板引擎与交付控制器解决的都是「如何批量、自动地产生并同步清单」，它们的输出仍然是清单。如果团队没有能力直接判断一份清单对不对，就失去了审查模板渲染结果的基准；一旦自动同步把错误清单推到生产，排查会同时横跨模板、渲染与控制器三层。先跑通手工闭环，本质上是先建立一个**可对照的正确样本**，后续每引入一层工具，都可以用「渲染结果是否与样本等价」来验证。
>
> **反例与前提**：这不等于「生产用手工 kubectl」。本章的手工操作只发生在本地 kind；从第 14 章起，生产变更一律走 Git，手工改动会被漂移检测纠正。若团队已经在生产运行成熟的 GitOps 体系、且有充分的可观测与回滚能力，则不必真的重做一遍手工闭环，但仍应能拿出与四判据等价的证据。跳过此步的典型代价见第 10 章 values 爆炸、第 14 章渲染模式之争。

### 6.2.1 四件套到后续 5 章加固的时间线

第六章跑通的四件套不是终点，而是第 7–11 章逐层加固的基线。下面用一张「横轴＝章节、纵轴＝四件套各自长出什么能力」的时间线，说明每一层加固都只用增量、不改变 6.4 的字段契约（命名空间、标签、端口、镜像命名一律冻结，见 `book/case-evolution.md`）。

```text
第 6 章 ── 第 7 章 ── 第 8 章 ── 第 9 章 ── 第 10 章 ── 第 11 章
  基线       工作负载    探针/优雅    配置/密钥    模板/overlay    校验/CI
  四件套     补齐 4 类    终止/PDB   不可变 CM    双骨架          静态门禁
```

| 起点（第 6 章四件套） | 加固章 | 该章在四件套上「长出」的能力 | 不改什么（配置契约冻结） |
|---|---|---|---|
| 不可变镜像 `git-<sha7>` | 7 | 选对 `worker` / `db` 的工作负载类型（Deployment / StatefulSet），db 第 7 章仍为 Deployment | 镜像标签格式与仓库路径不变 [R-06-4] |
| Deployment（滚动更新） | 8 | 补 `livenessProbe` `/healthz`、`readinessProbe` `/readyz`、`startupProbe`（仅 api）、`preStop` 摘流、`PodDisruptionBudget` | Service 名 `gateway`、端口 8080 不变 [R-06-2] |
| Service（稳定入口） | 9 | `order-demo-config` 设 `immutable: true`，外部密钥 `order-demo/db-credentials` 由 ESO 注入，配置变更不再需重建镜像 | ConfigMap 名 `order-demo-config` 不变 [R-06-3] |
| ConfigMap（配置分离） | 10 | 用 `Kustomize 5.x` overlay / `Helm 4.x` Chart 把四件套打包成多环境，渲染产物与手工清单等价 | 公共标签 `app.kubernetes.io/*` 不变 |
| 四件套整体 | 11 | `kubeconform` 校验结构、`conftest` 校验策略、`kuttl` 在 kind 跑端到端，提交错误字段被 CI 拦下 | 命名空间 `order-demo-dev` 不变 |

这张时间线的核心信息有两条：**一是每一层加固都是「在 6.4 之上加字段」，而非「换一套定义」**——所以第 8 章加探针时不会动端口，第 9 章加密钥时不会动镜像命名；**二是验证顺序严格自底向上**，只有当第 6 章的四判据（稳定入口 / 配置可观察 / 产物可追溯 / 可回退）全部成立，第 7–11 章的每一层加固才有可对照的正确样本。回到第 6 章的判断标准：如果某一层加固后 `curl gateway/healthz` 不再 200，那么锅在这一层新增的字段，而不是四件套本身 [R-06-1]。

### 6.2.2 「最小」的边界判定：什么进闭环、什么必须推迟

6.1 的「刻意取舍」回答了「为什么不写探针」，但没有回答一个更通用的问题：当你面对第 N 个候选字段时，凭什么判断它属于最小闭环，还是必须推迟？下面给出可判定的准入与推迟判据，以及一张带代价的推迟清单。

**准入判据（两条同时满足才进闭环）**：

1. **缺了它，四判据之一无法用命令证明。** 没有 Service，判据一（稳定入口）证不出来；没有 ConfigMap，判据二（配置可观察）证不出来；没有 SHA 标签，判据三、四连「退回到哪个对象」都没有 [R-06-2][R-06-3][R-06-4]。
2. **它是后续加固层的基线字段。** 命名空间、标签、端口、镜像命名一旦在本章定下，就被第 7–11 章冻结引用（见 `book/case-evolution.md` 第二节）；现在不定，后面每一章都要连带返工。

**推迟判据（满足其一即推迟）**：缺了它服务仍能通过四判据；或它属于「异常场景的行为保障」而非「通路本身」——探针、资源限额、网络策略只在故障或拥塞时生效，正常通路不依赖它们，放进基线只会让任何一次失败都难以归因到单一层。

| 推迟项 | 去向章 | 推迟理由 | 推迟的代价（此期间的风险敞口） |
|---|---|---|---|
| `livenessProbe` / `readinessProbe` / `startupProbe` | 8 | 用 `rollout status` + `curl` 人眼判定即可覆盖「能不能跑」 | 失活 Pod 不会被自动摘除，滚动更新可能出现瞬时 5xx；本地可容忍，进真实环境前必须补 |
| `preStop` / `PodDisruptionBudget` | 8 | 单组件、两副本、无优雅终止要求时，删 Pod 的瞬断不影响「入口可达」这一判据 | 6.5 只能验证「删 Pod 后仍 200」，证不了「零 5xx」；并发连接会看到少量断连 |
| `resources`（requests/limits） | 17 | 本地 kind 资源充裕，不设限额也不会 OOM | 同一份清单进真实环境前没有容量账，第 17 章必须补压测定基线，不能照抄 |
| Secret / ESO 注入 | 9 | 本章 `gateway` 无凭据需求，推迟是零风险 | 一旦第 7 章引入 `db`，凭据处理就从「可推迟」变成硬前提；第 4 章的三环境 overlay 也依赖它 |
| Helm / Kustomize 打包 | 10 | 只有一份清单、一个环境，模板收益为负（见 6.3） | 若手工样本没有随仓库留存，第 10 章渲染正确性将失去对照基准（见 6.2 本书观点） |
| 静态校验 / 策略门禁 | 11 | 校验工具针对「清单规模」与「团队协作」设计，单人单清单收益有限 | 6.1.1 那类非法配置值可畅通进集群，只能靠 6.5.2 的运行时断言兜底 |
| NetworkPolicy | 19 | 单命名空间、单组件，没有东西向流量可管 | 默认全通；组件一多（第 7 章 `db` 上线），`db` 就暴露给命名空间内所有 Pod |
| Gateway / Ingress 入口 | 19 | `port-forward` 足以完成本地四判据验证 | 没有真实七层入口，与生产拓扑差一层；18.1 的 `--address 0.0.0.0` 更不能当作发布手段 |
| SBOM / 扫描 / 签名 | 24 | 镜像不出本机，供应链门禁没有作用对象 | 镜像一旦推上共享仓库，验签缺位的风险立即兑现（D-01 划定边界，本章不越界） |

这张表的用法是双向的：往回看，遇到新字段先问「它服务哪个判据」，答不上来就推迟；往前看，**「代价」列就是第 7–11 章的赶工清单**——每一行风险敞口在对应章兑现为具体字段，兑现时必须回跑 6.5 的验证确认基线没有被破坏 [R-06-1]。判断「最小」的最终标准不是清单短，而是**每个存在的字段都能指认它让哪个判据可证明**。

这张表还有一个必须写明的误用反例：**不要拿它反向论证「生产清单越短越好」**。判据表回答的是「教学基线该含什么」，不是「生产清单的终态」；第 7–11 章逐层加固后，同一份清单会带上探针、限额与策略——那些字段在各自的章有自己的准入判据，只是不成立于第 6 章。若拿 6.2.2 当「砍字段」的依据去删既有生产配置，就偏离了「最小」的本意：**最小是对学习路径的最小，不是对生产保障的最小**。

## 6.3 工具选型：本章刻意不选工具

这一章的「工具选型」结论是**先不引入配置打包与交付工具**。这不是遗漏，而是 v3.1 逻辑线（第 9 章 9.2）的刻意安排：第 10 章才系统比较 Helm 4.x / Kustomize 5.x / CDK8s，第 14 章才比较 Argo CD 3.x / Flux 2.x，第 27 章才讨论要不要扩展 K8s API。

| 工具 | 本章是否使用 | 何时不该用（与本章相关的一条） |
|---|---|---|
| Helm 4.x / Kustomize 5.x | 不用 | 只有一份清单、只有一个环境时；模板与 overlay 的维护成本大于收益，且会遮住「最终提交了什么」 |
| Argo CD 3.x / Flux 2.x | 不用 | 还没有判断清单对错的标准之前；持续收敛会把错误也收敛进去 |
| Operator / CRD | 不用 | 需求只是「跑一个 HTTP 服务」；给 K8s 加一种新资源类型（CRD，详见第 27 章）在此毫无必要 |
| kind + kubectl + curl | **使用** | — |

本章的最小可行工具集只有四个：容器构建工具（Docker/BuildKit）、`kind`（本地集群）、`kubectl`、`curl`。具体小版本锁在附录 A，正文只写主版本，避免书一出版命令就过时 [R-06-7]。

**「镜像怎么来的」（约 400 字，供应链内容在第 24 章）**：本章的 gateway 是一个只用标准库、约 40 行的 Go 程序，读 `GREETING` 与 `APP_VERSION` 两个环境变量，提供 `/healthz` 和一个回显根路径。构建用两阶段 Dockerfile：编译阶段用固定版本的 Go 工具链，运行阶段换成非 root 的 distroless 基础镜像，只拷贝编译好的单个二进制。构建命令由 `hack/kind-up.sh` 统一执行，标签取 `git rev-parse --short=7 HEAD`，因此**同一个提交永远得到同一个标签**；镜像随后用 `kind load docker-image` 装进本地集群，不依赖外部仓库。本章不讲 SBOM、漏洞扫描、cosign 签名与准入验签——那些是第 24 章的门禁，放进这里会让「最小闭环」失去最小性（D-01）。

### 6.4.1 imagePullPolicy 三态与 kind 加载镜像的交互

`imagePullPolicy` 决定 kubelet 在启动容器前是否、以及如何去镜像仓库拉取镜像。它有三种取值，行为差异在「本地有镜像」和「本地没有镜像」两种前提下完全不同 [R-06-4]：

| 取值 | 语义 | 本地已有该标签镜像时 | 本地无该标签镜像时 |
|---|---|---|---|
| `Always` | 每次都向仓库发起一次拉取（带 digest 校验） | 仍拉取并比对 digest；若仓库不可达则失败 | 拉取，失败则 Pod `ImagePullBackOff` |
| `IfNotPresent` | 本地有就用本地的 | 直接用本地镜像，不发网络请求 | 尝试拉取，失败则 `ImagePullBackOff` |
| `Never` | 绝不去仓库，只用本地已加载的 | 直接用本地镜像 | 直接失败（`ErrImageNeverPull`），Pod 起不来 |

**与 kind 的关键交互**。kind 创建的节点是 Docker（或 containerd）里的一个容器，它**看不到宿主机的本地镜像仓库**，也没有走到 `registry.example.com` 的网络路径（除非你真的把镜像推到了那个域名可达的仓库）。本地的 `registry.example.com/order-demo/gateway:git-<sha7>` 之所以能被 Pod 启动，完全是因为 `hack/kind-up.sh` 里的 `kind load docker-image "${IMAGE}"` 把镜像**塞进了 kind 节点内部的容器运行时**。这一步是「带内」传输，不走镜像仓库协议 [R-06-5]。

于是三个取值在 kind 下的真实表现：

- **`IfNotPresent`（本章所选）**：`kind load` 之后节点内已有该标签镜像，kubelet 直接复用，无网络依赖、验证最快，最贴合「本地最小闭环、不依赖外部仓库」的本章目标 [R-06-4]。这也正是 6.4 的 deployment 里写 `imagePullPolicy: IfNotPresent` 而非 `Always` 的原因。
- **`Always`**：即便你刚 `kind load` 过，kubelet 仍会尝试向 `registry.example.com` 发起一次拉取。在 kind 默认网络里这个域名不可达，于是 Pod 立刻 `ImagePullBackOff`，`rollout status` 超时。`Always` 只在「镜像确实推到了集群可达的仓库、且希望每次都拿到最新 digest」的真实环境才有意义（配合不可变标签时其实等价于一次 digest 校验，验签门禁见第 24 章）。
- **`Never`**：节点内已有则能跑，节点内没有则彻底起不来、报错 `ErrImageNeverPull`。在 kind 里它要求你**每次重建集群都重新 `kind load`**，否则任何 `kubectl delete pod` 后重建都会失败。它适合「完全离线、镜像已 guaranteed 预置」的演练，但不适合本章这种「改完代码就重新 build + load」的迭代节奏。

**一个常见坑**：有人把 `imagePullPolicy` 和「镜像标签是否可变」混为一谈。标签是 `git-<sha7>` 还是 `latest` 决定的是「内容能否被识别」，而 `imagePullPolicy` 决定的是「启动时是否去仓库取」。即便用 `IfNotPresent`，如果节点内缓存的是旧的 `git-<sha7>`（比如你 build 了新 SHA 却忘了 `kind load`），kubelet 也会安静地用旧的那份——因为新标签在本地「没有」，它会去拉取，拉不到就 `ImagePullBackOff`。所以本章 `kind-up.sh` 把 `docker build` 和 `kind load` 写成**顺序硬依赖**，任何一次镜像变更都必须两者齐跑 [R-06-5]。

> **本书观点（不需要外部背书）**：在 kind 本地闭环阶段，默认 `IfNotPresent` 是最省心、最贴合「构建一次、加载一次、本地复用」心智模型的选择；把 `Always` 当作「保险」提前打开，反而会在离线/不可达仓库场景下制造本可避免的 `ImagePullBackOff`。`Always` 的真正价值出现在真实仓库可达、且需要 digest 一致性校验的生产链路里，而不是本地玩具集群。

### 6.4.2 两阶段 Dockerfile 逐段 walkthrough：每层为什么这样写

6.3 交代了 Dockerfile 的分工，这里逐层拆开讲「为什么」，并把四类高频构建错误的症状、定位与修复固化成表。镜像格式与层缓存机制依据 OCI 镜像规范：镜像是一组带层指纹的内容寻址块，`COPY`/`RUN` 每条指令产生一层，缓存命中与否取决于该层输入是否变化 [R-06-5]。

**构建阶段逐层**：

- `FROM --platform=$BUILDPLATFORM golang:1.27-bookworm AS builder`：三个修饰各管一件事。锁定次版本号 `1.27` 保证编译器行为可复现（裸 `golang:latest` 等于把反模式一复制进构建期）；`--platform=$BUILDPLATFORM` 让编译阶段始终跑在宿主架构上、目标架构交给 `GOARCH` 交叉编译，避免在 Apple Silicon 上用模拟器跑 amd64 工具链拖慢一个数量级；`AS builder` 命名供运行阶段 `--from` 引用。
- `COPY go.mod ./` 单独成层：把「依赖声明」与「源码」分层是构建缓存的命门。源码每次提交都变，`go.mod` 只在动依赖时变——只改代码时这一层缓存命中，后续与依赖相关的开销全部跳过。本项目只用标准库、无第三方依赖，收益体现为编译缓存；一旦加了依赖，应在这一层之后补一条独立的 `RUN go mod download` 层，否则缓存等于没做。
- `ARG TARGETOS / TARGETARCH` + `CGO_ENABLED=0`：由 BuildKit 按目标平台注入，配合静态编译产出不依赖 libc 的单一二进制。这是运行阶段选 `distroless/static` 的前提——`static` 变体不带 glibc，动态链接的二进制装进去就是 `exec format error` 或运行时缺 `.so` 报错 [R-06-5]。
- `-trimpath -ldflags="-s -w"`：去掉本机路径与符号表，二进制更小，也避免把构建机目录结构泄漏进产物——这是可复现构建的最低要求，完整的可复现流水线在第 12 章补齐。

**运行阶段逐层**：

- `gcr.io/distroless/static-debian12:nonroot`：无 shell、无包管理器、默认以 uid `65532` 运行。没有 shell 意味着即便发生 RCE 也拿不到交互环境（强制化交给第 25 章准入策略）；代价是 `kubectl exec ... -- sh` 直接失败，排障只能靠日志与临时调试容器，这是「最小镜像」的自觉代价而非缺陷。
- `USER 65532:65532` 与 Deployment 的 `runAsNonRoot: true` 是**双保险**：镜像层写死 uid，清单层声明约束，两侧互相校验。若有人换了基础镜像忘了 `USER`，`runAsNonRoot` 会让 Pod 直接起不来并留下可读事件，而不是静默以 root 跑起来 [R-06-4]。
- `EXPOSE 8080`：纯文档字段，与 Service 没有强制绑定。真正的绑定链是「容器进程监听 8080 ↔ `containerPort: 8080` ↔ Service `targetPort: http`」；改端口必须三处同步，而端口 8080 是配置契约冻结值（见 `book/case-evolution.md`），本章不存在改的场景。

| # | 症状（关键输出片段） | 根因 | 定位命令 | 修复 |
|---|---|---|---|---|
| D1 | `failed to solve: golang:1.27-bookworm: manifest unknown` | 基础镜像标签写错，或构建机到镜像源的网络不可达 | 看 `docker build` 输出的第一个 FROM 段 | 核对附录 A 锁定版本；禁用裸 `latest` 基础镜像（反模式一在构建期的变体）[R-06-4] |
| D2 | Pod `CrashLoopBackOff`，`kubectl logs` 报 `exec format error` | 编译产物架构与 kind 节点架构不一致（如 M 系列 Mac 构建出 arm64，节点是 amd64） | `docker exec order-demo-control-plane crictl inspecti <镜像> \| grep -i arch` | 保留 `TARGETARCH` 交叉编译，或构建时显式 `--platform linux/amd64` |
| D3 | Pod 起不来，事件报 `runAsNonRoot: container has runAsNonRoot and image will run as root` | 换了带 root 默认的基础镜像且删了 `USER` | `docker inspect --format '{{.Config.User}}' <镜像>` | 回 `USER 65532:65532`；这是双保险在拦截，不是误报 [R-06-4] |
| D4 | 运行报 `read-only file system` | `readOnlyRootFilesystem: true` 且应用写根文件系统（本章 gateway 不写盘，不会触发；引入日志落盘、临时缓存时高发） | `kubectl logs` 看首次报错的路径 | 给写路径挂 `emptyDir`（如 `/tmp`），不要为省事关掉 `readOnlyRootFilesystem`（公理 4 的最小化方向） |
| D5 | 每次构建都全量重编译，`CACHED` 从不出现 | `COPY go.mod` 与源码放同一层，或源码层排在依赖层之前 | `docker build --progress=plain` 看每层是否命中 `CACHED` | 依赖声明层在前、源码层在后；有依赖后补独立 `go mod download` 层 [R-06-5] |
| D6 | `kubectl exec -it ... -- sh` 报 `executable file not found` | distroless 无 shell，设计使然 | —（不是故障） | 排障用 `kubectl debug -it pod/<名> --image=busybox:1.x --target=gateway`（临时容器共享进程命名空间）或回看日志 |

D1/D2/D5 是**构建期**就能发现的错误（`docker build` 阶段报错或镜像架构不对），D3/D4/D6 要到**运行期**才暴露——这也解释了为什么 6.5 的验证脚本要把「Pod 起来」单独断言，而不是只看构建成功。

### 6.4.3 kind 加载镜像的完整链路与失败注入

6.4.1 讲了 `imagePullPolicy` 三态，这里把「镜像从源码到容器」的完整链路画出来——链路上每一跳都是**独立的镜像存储**，前一个存储有镜像不代表后一个有：

```text
git commit（短 SHA）
   │  docker build -t registry.example.com/order-demo/gateway:git-<sha>
   ▼
① 宿主机 Docker daemon 的镜像存储          ← 构建失败在这一跳就停
   │  kind load docker-image（打 tar 直灌节点，不走仓库协议）[R-06-5]
   ▼
② kind 节点容器内 containerd 的镜像存储     ← crictl images 在这一跳核对
   │  kubelet 创建 Pod：IfNotPresent 先查②
   ▼
③ 容器进程启动                              ← curl /healthz 在这一跳验证
```

`kind load docker-image` 是**带内传输**：它把宿主镜像直接塞进节点容器，完全绕过镜像仓库协议——这就是 `registry.example.com` 在 kind 网络里不可达、Pod 却能启动的原因。链路一旦有一跳缺失，症状都汇成同一个 `ImagePullBackOff`，但事件文本不同。用三个失败注入把症状固化（按出现概率排序）：

| 注入 | 症状（事件关键片段） | 定位命令 | 修复 |
|---|---|---|---|
| L1：build 完忘跑 `kind load`（或误注释掉那一行） | `Failed to pull ... not found`；`rollout status --timeout=120s` 超时 | ② 空、① 有：`docker exec order-demo-control-plane crictl images \| grep gateway` 为空，而宿主 `docker images` 有 | `kind load docker-image "${IMAGE}" --name order-demo` 后 `kubectl -n order-demo-dev rollout restart deployment/gateway`；根治是把两步锁进 `kind-up.sh` 的顺序硬依赖 [R-06-5] |
| L2：手工编辑 deployment.yaml 时把 SHA 抄错一位（绕过 sed 单点替换） | 与 L1 同为 `ImagePullBackOff`，但 ①② 里「都像有镜像」——Pod 引用的标签不匹配任何一个已存在的标签 | `kubectl -n order-demo-dev get deploy gateway -o jsonpath='{..image}'` 与 `git rev-parse --short=7 HEAD` 对照（CL-06-03 的反向用法） | 停止手工编辑 SHA，回到 `kind-up.sh` 的 `sed` 单点替换；该脚本存在的意义就是消灭这个抄写环节 |
| L3：把 `imagePullPolicy` 误改成 `Always` | 即便 ② 里镜像在，Pod 仍 `ImagePullBackOff`，事件含 `dial tcp: lookup registry.example.com ... no such host` | 事件里出现「发起过拉取且域名解析失败」，而 `crictl images` 有镜像——与 L1 的区别正在于此 | 改回 `IfNotPresent`（机理见 6.4.1） |

三种注入共享一个元教训：**`ImagePullBackOff` 不是病名，是症状名**。事件文本会区分「节点里没有」（L1）、「标签对不上」（L2）、「去仓库拉被拒」（L3），先读 `kubectl describe pod` 的 Events 段再动手。条件反射地重跑 `kind-up.sh` 能撞对 L1，却会掩盖 L2/L3 的真正断点，并把「为什么好了一半」的困惑留给你自己 [R-06-4]。

**链路在真实环境如何变化**：本章三跳里，①→② 的 `kind load` 是 kind 特有的带内捷径；第 12 章接入 CI 后，同一链路变成「CI 构建 → 推送到真实仓库 → 集群节点拉取」，中间多出仓库这一权威环节。L1/L2 类故障会以 `ErrImagePull` 配合仓库 401/404 的形式重现，但诊断动作完全一致——先看 Events，再逐跳核对「镜像存在于哪个存储」。把失败注入做在本地的理由正在于此：在零成本环境里先练会诊断，再进真实链路。另有一个 L2 的 CI 变体值得预埋认知：发布清单引用的 SHA 若尚未被构建流水线产出，真实仓库会返回 404，「构建与部署用了不同 commit」在 CI 里升级为竞态——第 14 章 GitOps 的同步等待机制正是为此设计 [R-06-1]。

**回滚命令 / 步骤**（先演练、后发布）。`rollout undo` 依赖 Deployment 的 ReplicaSet 历史，第一次部署时没有上一版可退，所以演练要先制造一个「新版本」：

```bash
PREV=$(kubectl -n order-demo-dev get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}')

# 模拟一次发布：切到另一个已加载的镜像标签
kubectl -n order-demo-dev set image deployment/gateway \
  gateway=registry.example.com/order-demo/gateway:git-0000000
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=60s || true

# 方案 A：按历史修订回退（本地演练用）
kubectl -n order-demo-dev rollout undo deployment/gateway
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s

# 方案 B（推荐用于明确目标产物）：直接把 image 指回已知良好的 SHA
kubectl -n order-demo-dev set image deployment/gateway gateway="${PREV}"
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s
```

> **为什么方案 B 更可靠**：`rollout undo` 回退的是整个 Pod 模板的上一个修订，若这段时间里还改过探针、环境变量或资源字段，它们会被一起退回，回滚就不再等于「只换回产物」。明确指定镜像标签能精确表达「恢复到上一个已知良好版本」这一意图 [R-06-1]。
>
> **适用边界**：本节是本地 kind 的**演练**，用命令式操作是为了让读者看清字段变化。从第 14 章起，生产环境的任何变更必须回到 Git 声明，手工 `set image` / `kubectl edit` 会被漂移检测纠正并写进审计（全书公理 5，见第 3 章）。此处不构成对公理的例外，因为对象是本地一次性集群。

**回滚验证**：

```bash

kubectl -n order-demo-dev get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

通过标准：image 字段回到演练前的 `git-<sha7>`（即 `PREV`），`/healthz` 仍为 200，根路径 `version` 与镜像标签一致。**回滚没有验证过，就不允许进入第 7 章**（CL-G-07）。

### 6.5.1 Windows / macOS 下 kind 端口转发的差异与排错

`hack/verify.sh` 里的 `kubectl -n order-demo-dev port-forward svc/gateway 8080:8080` 在 Linux 上几乎开箱即用，但在 Windows 与 macOS 上，端口转发的底层机制不同，常出现「Pod 是 Running、Service 也在，但 `curl 127.0.0.1:8080` 连不上」的假死。下面区分两个平台讲差异与排错（端口号 8080 是 `gateway` 的契约端口，本文不改它，只讲如何把流量正确转到这个端口）[R-06-2]。

**macOS 的差异**：macOS 上 Docker Desktop 跑在一个轻量 Linux 虚拟机里，`kubectl port-forward` 绑定的是**虚拟机内的 loopback**，不是宿主机的 127.0.0.1。多数情况下 Docker Desktop 已做端口映射，访问 `localhost:8080` 能通；但当你用 `127.0.0.1` 而非 `localhost`、或公司 VPN / 代理（如 Clash、Charles）劫持了 loopback 时，转发会静默失败。排错顺序：① 换 `localhost` 而非 `127.0.0.1`；② 确认 Docker Desktop 设置里 loopback 转发类选项开启；③ 临时关掉 VPN / 代理后重试；④ 显式绑定 `kubectl port-forward --address 0.0.0.0 svc/gateway 8080:8080` 并用宿主机 IP 访问（仅本地演练，勿暴露到生产网络）。

**Windows 的差异**：Windows 上分两种运行后端。**WSL2 后端**（推荐）下，`kubectl` 若在 WSL2 的 Linux 发行版里执行，`port-forward` 绑定的是 WSL2 虚拟网卡，从 Windows 宿主的浏览器 / PowerShell 访问需走 WSL2 的 IP（`wsl hostname -I` 拿到的地址），或直接在该 WSL2 发行版内 `curl localhost:8080`；若 `kubectl` 跑在 Windows 原生（PowerShell）而 kind 节点在 WSL2，则两端网络命名空间不同，转发目标需指向 WSL2 IP。**Hyper-V / Docker 原生后端**下行为更接近 macOS，但 Windows 防火墙常拦截转发端口，需放行 `kubectl.exe` 的入站规则。

**跨平台通用的排错清单（四列）**：

| 编号 | 检查项 | 怎么查 | 通过标准 |
|---|---|---|---|
| PF-1 | 转发进程在跑 | `kubectl port-forward` 所在终端未退出、任务管理器可见 | 进程存活且未报 `unable to listen` |
| PF-2 | 用对地址 | 先 `localhost` 再 `127.0.0.1`，WSL2 下试用 `wsl hostname -I` 的 IP | 至少一种地址能 `curl` 通 `/healthz` |
| PF-3 | Service 真的在 | `kubectl -n order-demo-dev get svc gateway` | 有 `ClusterIP`、端口为 8080 |
| PF-4 | 中间件未劫持 | 临时退出 VPN / 代理后重试 | 退出后能通，则问题是代理规则 |

> **本书观点（不需要外部背书）**：端口转发只是本地验证手段，不是服务暴露方式。第 19 章讲真正的入口（Gateway API / Ingress）前，请勿把 `port-forward --address 0.0.0.0` 当作「对外发布」。生产流量走第 15、19 章的入口与渐进式交付，本地 `--address 0.0.0.0` 仅限本机演练且用完即关。

### 6.5.2 verify.sh 的逐条判据表与硬化版

6.5 开头的 `hack/verify.sh` 是「人眼判读输出」的版本：它把证据打印出来，但跑完永远退出码为 0，无法被脚本消费。6.1.1 的教训（`/healthz` 200 而 `/` 全量 500）说明验证还必须对根路径做状态码断言。下面给出硬化版：每条判据变成独立断言，任一失败则退出码非零——这让它可以直接作为第 11 章 CI 门禁的判定信号（端口、命名空间、镜像契约全部沿用 6.4，未改动）：

```bash
#!/usr/bin/env bash
set -uo pipefail   # 不用 -e：让所有断言跑完再汇总，一次性给出完整失败清单
NS=order-demo-dev
SHA="$(git rev-parse --short=7 HEAD)"
IMAGE="registry.example.com/order-demo/gateway:git-${SHA}"
FAIL=0
mark() { if [ "$1" -eq 0 ]; then echo "PASS $2"; else echo "FAIL $2"; FAIL=1; fi; }

kubectl -n "${NS}" port-forward svc/gateway 8080:8080 >/dev/null 2>&1 &
PF=$!
trap 'kill "${PF}" 2>/dev/null || true' EXIT

for i in $(seq 1 30); do
  curl -fsS http://127.0.0.1:8080/healthz >/dev/null 2>&1 && break
  sleep 1
done

# A1：/healthz 可达且正文为 ok
HZ="$(curl -fsS http://127.0.0.1:8080/healthz || true)"
mark $? "A1 /healthz 200"
[ "${HZ}" = "ok" ]; mark $? "A1b /healthz 正文为 ok"

# A2：根路径非 5xx（6.1.1 的教训：配置值炸在请求路径上，探针看不见）
curl -fsS http://127.0.0.1:8080/ >/dev/null 2>&1
mark $? "A2 根路径非 5xx"

# A3：响应含 ConfigMap 的 GREETING，证明注入生效而非镜像默认值
ROOT="$(curl -fsS http://127.0.0.1:8080/ || true)"
echo "${ROOT}" | grep -q "hello from configmap (dev)"; mark $? "A3 GREETING 来自 ConfigMap"

# A4：version、镜像标签、git SHA 三方一致（产物可追溯）
echo "${ROOT}" | grep -q "version=git-${SHA}"; mark $? "A4a 响应 version=git-<sha>"
DEPLOY_IMAGE="$(kubectl -n "${NS}" get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
[ "${DEPLOY_IMAGE}" = "${IMAGE}" ]; mark $? "A4b Deployment 镜像=本次构建"

# A5：两副本全部就绪（Pod 起来，而不是只看构建成功——见 6.4.2 构建期/运行期之分）
READY="$(kubectl -n "${NS}" get deploy gateway -o jsonpath='{.status.readyReplicas}')"
[ "${READY}" = "2" ]; mark $? "A5 readyReplicas=2"

exit "${FAIL}"
```

运行方式与通过标准：`./hack/verify.sh && echo ALL-PASS`，输出含 7 行 `PASS`、`ALL-PASS`，退出码 0。任何一行 `FAIL` 都不必重跑，按下面的判据表归因：

| 断言 | 失败时最可能的原因（按概率排序） | 怎么确认 | 怎么修 |
|---|---|---|---|
| A1 / A1b | ① 端口转发假死（见 6.5.1 平台差异）；② Service selector 与 Pod labels 不匹配；③ 无 Ready Pod | `kubectl -n order-demo-dev get endpoints gateway`——为空即 selector 问题；有 IP 即转发或 Pod 问题 | 修 label/selector 使其逐键一致；转发问题按 PF-1…PF-4 排 [R-06-2] |
| A2 | 根路径处理函数在请求态抛错（如 6.1.1 的 `%` 格式串事故） | 对照 6.1.1 的四列排错表：产物未变→配置已变→日志 | 改回已知良好 ConfigMap 值 + `rollout restart`；长期解在第 9、11 章 [R-06-3] |
| A3 | ① env 注入断链（CM 名/key/命名空间不对）；② Pod 是改 CM 之前的旧副本 | 两步：`kubectl -n order-demo-dev get cm order-demo-config -o jsonpath='{.data.GREETING}'` 确认 CM 侧有值；`kubectl -n order-demo-dev debug pod/$(kubectl -n order-demo-dev get pod -l app.kubernetes.io/component=gateway -o jsonpath='{.items[0].metadata.name}') --image=busybox:1.x --target=gateway -- cat /proc/1/environ \| tr '\0' '\n' \| grep GREETING` 读 1 号进程环境——distroless 无 shell 无 `env`（6.4.2 D6），只能借临时容器共享进程命名空间 | 修 `configMapKeyRef`；改 CM 后必须 `rollout restart`，ConfigMap 不会热更新进已启动进程的 `os.Getenv` [R-06-3] |
| A4a/A4b | ① `sed` 未替换（清单仍是示例值 `git-1a2b3c4`）；② 构建与部署用了不同 commit；③ 忘了 `kind load`（L1/L2，见 6.4.3） | 三个 SHA（git、镜像标签、响应 version）两两对照；再按 6.4.3 的 `crictl images` 复核节点内镜像 | 一律回 `kind-up.sh` 全流程重跑，不手工补丁单点 |
| A5 | ① 镜像架构不匹配（D2）；② 非 root 双保险拦截（D3）；③ 拉镜像失败（L1–L3） | `kubectl -n order-demo-dev describe pod` 看 Events；`kubectl logs` 看首报错 | 按 6.4.2 的 D1–D6 与 6.4.3 的 L1–L3 对号入座 [R-06-4] |

硬化版还有两个隐性收益：**一是失败可汇总**——原版靠 `-e` 在第一处失败即退出，一次只能看到一个错，硬化版跑完所有断言，便于横向对比归因；**二是退出码即门禁**——第 11 章把它接进 CI 时，非零退出码就是拦截信号，不需要解析任何输出文本。
