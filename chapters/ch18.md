## 18.1 问题与反模式：副本挤在一个区、HPA 反复跳、账单看不懂，其实是同一件事

**合成案例**（本书统一采用虚构合成场景，不指向任何真实事故）。大促压测那天，值班同学连着遇到三件看似无关的事：第一，`api` 的副本全被调度到同一个可用区，那个区做一次节点维护，入口就整体不可用；第二，HPA 只看了 CPU 平均值，队列里积压的订单越来越多却「扩不动」，后来有人同时开了 VPA 的 `Auto` 模式在线改 requests，结果 HPA 改副本数、VPA 改 Pod 模板，两个控制器对着同一个 Deployment 反复改写，副本在 4 和 9 之间来回跳了一下午；第三，月末账单涨了，有人看总金额太高就缩了节点组，P99 与错误预算（一个窗口内允许不可用的额度，详见第 20 章）悄悄恶化，直到告警响了才被发现 [R-18-8][R-18-9]。

三件事其实共享一个根因：**「稳、快、省」三个目标被塞进了同一个旋钮，却没有分清哪一层该动哪个参数**。副本放在哪是调度层，副本随什么信号增减是弹性层，节点够不够是基础设施层，钱花在谁身上是归因层。四层混在一起调，任何一次「优化」都会同时动到别的层，抖动和账单失控只是表象 [R-18-8]。行业调查也长期把「成本可见性」与「弹性配置」列为容器平台的主要运维挑战，这正是本章把「压测触发扩容且无抖动」和「成本可归因」一起写成可验证动作的原因 [R-18-11]。

三个反模式，按「现象 → 根因 → 本章替代做法」拆开：

**反模式一：副本挤在单可用区，或只靠一条反亲和了事。** 现象是 AZ 故障时整条链路一起消失。根因是 `podAntiAffinity` 只表达「不要和谁放一起」，并不保证在多个拓扑域之间按数量均匀打散；而 `topologySpreadConstraints` 才是以「域之间副本数差不超过 maxSkew」为目标的约束，二者作用不同，亲和/反亲和与污点容忍解决的是「放哪、不放哪」，拓扑分布解决的是「放得均不均」[R-18-1][R-18-2]。本章的替代做法是用 `topologySpreadConstraints` 跨 `topology.kubernetes.io/zone` 强制打散，再叠一条跨节点的柔性约束（见 18.4）。

**反模式二：HPA 与 VPA 同时对同一资源的在线调整，或用 CPU 均值做唯一扩缩指标。** 现象是副本数反复震荡、队列积压时扩不动。根因有两类：一是 HPA（改副本）与 VPA（在线改 requests）同时写同一个 Deployment，前者的分母正是后者改的 requests，形成互相扰动 [R-18-3][R-18-6]；二是对队列驱动的工作负载，CPU 平均值与「还有多少活没干」几乎不相关，指标滞后于真实压力 [R-18-4]。本章的替代做法是明确边界：HPA 只改副本、VPA 只用 `Off`/`Initial` 模式离线调 requests、队列型负载交给 KEDA 的事件/队列指标 [R-18-4][R-18-6]。

**反模式三：只看总账单就删节点。** 现象是账单降了、SLO（对服务可靠性的量化承诺，详见第 20 章）也降了。根因是没有任何按组件/环境的成本归因，无法区分「省下的钱」和「被牺牲的容量」[R-18-10]。本章的替代做法是**先归因、再优化**：用相对占比报表定位到具体组件，再联动第 20 章错误预算判断能不能缩，且全书只给相对比例与归因口径，不写任何云厂商单价 [R-18-10]。这条是本章「本书观点」，18.2 给完整论证。

> **一个刻意的边界**：本章的 `topologySpreadConstraints`、HPA 字段都加在第 17 章那份 Deployment 上，是增量，不动命名空间、标签、端口与 `api` 的冻结资源基线（requests `100m/128Mi`、limits `500m/256Mi`）。HPA 的利用率分母正是这个 requests，改了基线就会让整章的阈值失效（见第 17 章）。

## 18.2 范式与决策树：稳、快、省三层各管什么

先把四层职责钉死，这是后面所有参数取舍的前提。

**调度层**回答「Pod 放在哪」。三件工具作用不同且会互相干扰：`nodeSelector` / `affinity` 与 `antiAffinity` 表达「倾向放哪、别和谁挨着」；`taints` / `tolerations` 表达「这批节点保留给谁」；`topologySpreadConstraints` 表达「各拓扑域之间副本数差不超过多少」[R-18-1][R-18-2]。把「跨 AZ 均匀」寄托在反亲和上是错的，因为反亲和没有域间计数这个概念。

**弹性层**回答「副本随什么信号变」，四件套各管一段，见表 18-1 的「作用层」一列。HPA（Kubernetes 1.32，`autoscaling/v2`）依据指标改副本数；VPA 1.x 依据历史用量改 requests，适合有状态或离线负载的「调准」而非在线即时扩缩；KEDA 2.x 用队列长度、事件数这类外部信号驱动副本，甚至能缩到零；Karpenter 1.x 与 Cluster Autoscaler 1.x 负责的是**节点**，不是 Pod——副本扩出来之后没有节点可放，才轮到它们加机器 [R-18-3][R-18-4][R-18-5][R-18-6][R-18-7]。

> KEDA 2.x 的 ScaledObject、Karpenter 1.x 的 NodePool 都是 CRD（给 K8s 加一种新资源类型，详见第 27 章）；本章只使用它们，不展开自定义资源的设计。

**抖动治理**是本章最值得写透的一段。绝大多数弹性抖动不是算法不够先进，而是三个可枚举的原因：指标窗口过短、缩容冷却时间不足、多个控制器同时改同一对象 [R-18-8]。HPA 的 `behavior` 字段就是为此存在的——`scaleUp.stabilizationWindowSeconds: 0` 让扩容跟得上突发，`scaleDown.stabilizationWindowSeconds: 300` 让缩容必须等压力回落五分钟才动作；再配合 `policies` 限制每 60 秒的扩缩步长，副本数就不会在阈值附近来回跳 [R-18-3]。过载场景下的级联扩容同样要靠冷却窗口兜住，否则上游一抖动就把下游和节点层一起拖进扩容风暴 [R-18-9]。

表 18-1　弹性参数调优表（取值来自压测，不是拍脑袋）

| 参数 | 本章取值 | 依据 | 抖动风险 |
|---|---|---|---|
| HPA 主指标 | `Resource/cpu`，`averageUtilization: 60` | 同步 HTTP 服务的 CPU 与 RPS 相关性好，kind 里由 `metrics-server 0.7.x` 直接提供，可复现 | 对队列型负载滞后；生产应补业务指标（见 18.3 diff） |
| 扩容稳定窗口 | `0s` | 突发流量要快扩 | 过大会错过峰值 |
| 缩容稳定窗口 | `300s` | 防「压力一降就缩、马上又扩」 | 过短是反复扩缩的首要原因 |
| 扩容步长 | `Percent 100` / `Pods 2` per 60s，取 Max | 快速追上但不过冲 | 步长过小跟不上，过大造成容量浪费 |
| 缩容步长 | `Percent 50` per 60s，取 Min | 缓慢放掉副本 | 步长过大会误伤在途请求 |
| 副本上下限 | `min 2` / `max 10` | 容量账（见第 13 章）与第 17 章 Quota `requests.cpu: "4"` 对齐 | `max` 超过配额会把扩容卡成 Pending |
| KEDA 冷却 | `cooldownPeriod: 300` | 与 HPA 缩容窗口同口径，避免两套冷却打架 | 与 HPA 窗口不一致会各自为政 |

**决策树**（判断该动哪一层）：

```
副本是否跨 >= 2 个可用区？              否 → topologySpreadConstraints（18.4），先解决「稳」
        │ 是
扩缩信号来自「Pod 负载」还是「外部队列」？ 队列/事件 → KEDA 2.x ScaledObject（18.4）
        │ Pod 负载
是否需要长期把 requests 调准？            是 → VPA 1.x，用 Off/Initial，不与 HPA 同改 CPU
        │ 否 → HPA（autoscaling/v2 + behavior 冷却窗口）
扩容后节点够不够？                        否 → Karpenter 1.x / Cluster Autoscaler 1.x（节点层）
        │ 是
有没有按组件/环境的成本归因？             否 → 先建归因口径，再谈任何「省钱」动作（本书观点）
        │ 是 → 联动第 20 章错误预算决定能否缩容
```

### 18.2.1 HPA `behavior` 压测对照：stabilizationWindowSeconds 取 0/60/300s 的三组曲线

`behavior` 里最容易被照抄默认值、也最需要压测定值的字段是 `stabilizationWindowSeconds`。它的语义是：计算目标副本数时，只看「过去这个窗口内的推荐值」——扩容方向（`scaleUp`）取窗口内最大推荐值、缩容方向（`scaleDown`）取窗口内最小推荐值，窗口越长，动作越保守 [R-18-3]。Kubernetes 默认 `scaleUp` 为 0（立即跟随）、`scaleDown` 为 300（默认等五分钟），但默认值未必匹配你的流量形状，必须用压测证明取值，而不是照抄 [R-18-3][R-18-8]。

**实验设置**（合成压测，kind 三节点按 18.4 `hack/kind-multi-az.sh` 打好 zone 标签）：三组配置只改 `behavior` 中两个方向的窗口值，其余字段——`policies`（扩 `Percent 100` / `Pods 2` per 60s 取 `Max`，缩 `Percent 50` per 60s 取 `Min`）、`minReplicas: 2`、`maxReplicas: 10`、主指标 CPU 60%——与 18.4 基线逐字相同，保证窗口是唯一变量。流量形状：T+0 用 `load-test.sh` 加压把 CPU 冲到 90% 并维持，T+8 分钟撤压。

### 18.2.2 HPA 指标选择的完整判据：四种指标、目标值定法与选错的后果

表 18-2 里 HPA 那行只写了「CPU/内存/自定义/外部指标」，这一小节把「怎么选、目标值怎么定、选错会怎样」补成可判定表。`autoscaling/v2` 支持四类指标源，判据核心只有一条：**指标必须与「想保护的服务能力」单调相关**——指标涨、服务能力真的在降，HPA 才有正确的因果可循 [R-18-3]。

表 18-7　HPA 指标类型判据表

| 指标类型 | 适用负载 | 目标值怎么定 | 选错的典型后果 |
|---|---|---|---|
| `Resource`/CPU | 同步 HTTP/RPC，CPU 与 RPS 相关性好 | 压测出单副本满载 RPS，取其 60%~70% 对应的利用率 | CPU 被 limit 节流后利用率失真，HPA「扩不动」 |
| `Resource`/内存 | 与请求量弱相关的缓存/守护型负载 | 只适合「只扩不缩」语义：`scaleDown` 窗口拉到极长或不配 | 泄漏或缓存增长推着副本只增不减，直到 `maxReplicas` |
| `Pods` 自定义 | 有明确「每副本业务量」口径的指标（如每副本在途订单） | 目标 = 单副本安全业务量，由压测与容量账（第 13 章）共同给出 | 业务口径未登记就接入 HPA，语义漂移无人发现 |
| `External` 外部 | 信号在集群之外（如外部消息队列深度） | 目标 = 全体副本可消化的处理速率上限 | 与 KEDA 2.x 职责重叠，两套扩缩同时生效 [R-18-4] |

四条判据展开。**第一，CPU 不是万能默认值。** 除了对队列型负载失真（反模式二已拆过），还有一类更隐蔽的失真：CPU 被 limit 节流之后，用量被压在 limit 附近，「利用率看起来不高」，HPA 完全判断不出真实压力。判据是压测时确认目标 RPS 下无节流（`container_cpu_cfs_throttled_periods` 不增长，指标口径见第 21 章），否则先把 limit 抬到无节流水位再定阈值。**第二，内存做主指标几乎总是错的，除非你要的就是「只扩不缩」。** 内存与请求量通常不单调——缓存、泄漏、语言运行时的堆策略都会让内存「自己涨」；唯一合理用法是把内存当保险丝，配超长 `scaleDown` 窗口让它只向外扩、不自动收回。**第三，目标值的三步定法（本书观点，不需要外部背书）**：压测定出单副本安全水位 → 目标利用率 = 安全水位再留 30%~40% 余量（本章 60% 即由 18.2.1 压测反推）→ 用 18.2.1 的三组压测验证窗口内无抖动。目标值定到 90% 以上是常见错误：任何请求毛刺都直接顶破阈值，行为上等价于没有冷却。**第四，选错的后果只有三型，排查时对号入座**：扩不动（指标与真实压力脱钩，见反模式二）、只扩不缩（棘轮效应，见内存一行）、扩了也没用（瓶颈根本不在副本数——典型是把 `db` 连接池打满后继续扩 `api`，只会让排队从应用层转移到连接池，见第 16 章）。

把三步定法落到本章冻结基线上验算一遍，顺便说明为什么基线不能动：HPA 的利用率分母是 **requests** 而非 limits，即 `api` 的 `100m` [R-18-3]。压测得单副本在 CPU 用量 100m（恰好用满 requests 口径的 100%）、且无节流时支撑约 50 RPS；取 60% 目标，触发扩容的每副本水位约为 30 RPS，静态 2 副本即约 60 RPS 开始扩容；`maxReplicas: 10` 的理论容量约 500 RPS，与第 13 章容量账的峰值需求对照，确认上下限不是拍的。若有人把 requests 改成 `200m`，同样的 60% 就变成 120m 才触发——所有阈值、压测结论与表 18-4 的曲线一夜之间全部作废，这正是 requests 基线被设为冻结字段的原因。

### 18.2.3 VPA 与 HPA 的边界：为什么不能同时 `Auto`，三种模式各自适用

**「不能同时用」是一条能从公式推出来的结论，不是风格偏好。** HPA 的副本公式是 `desiredReplicas = ceil(currentReplicas × currentUtilization / targetUtilization)`，其中 `currentUtilization = 当前用量 / requests` [R-18-3]——分母 `requests` 恰好是 VPA `Auto` 模式要在线改写的值。把两个控制器同时指向一个 Deployment，会走出这样的循环：VPA 抬高 requests → 利用率分母变大、数值下降 → HPA 认为「负载变轻」开始缩容 → 每副本承担的负载上升、利用率回升 → HPA 扩容 → VPA 再调 requests……两个控制器各按自己的同步周期写同一个对象，产生比 18.2.1 组一更难诊断的抖动：组一的抖动只体现在副本数上，这里连每个 Pod 的资源规格都在变，`kubectl get pods -o wide` 每次看到的 requests 都不同 [R-18-6]。18.1 合成案例里「副本在 4 和 9 之间来回跳了一下午」正是这个循环的样子。

表 18-8　VPA 三种 `updateMode` 判据表 [R-18-6]

| `updateMode` | 行为 | 适用 | 不适用 / 代价 |
|---|---|---|---|
| `Off` | 只计算推荐值写入 `status.recommendation`，不改任何对象 | 建立用量基线：跑满一个流量周期，把推荐值与压测曲线对照后，经 Git 修订下一版 requests | 想要「自动省钱」的场景——它不自动改任何东西 |
| `Initial` | 只在 Pod 创建时应用推荐值，存量 Pod 不动 | 与 HPA 共存的安全形态：扩出来的新副本按推荐 requests 启动，存量基线不受扰动 | 期望自动纠偏存量负载——它做不到 |
| `Auto` | 在线改 Pod 模板并驱逐重建 | 无 HPA、副本数不可随意增减的负载（有状态组件、单副本守护进程） | 与 HPA 同管一个 Deployment；重建有状态 DB 会造成中断并打乱拓扑分布 |

两条落地纪律。**第一，`Auto` 的重建会破坏本章已建好的两样东西**：`topologySpreadConstraints` 的均匀分布（重建瞬间副本会挤向同一域，等价于回到反模式一），以及 HPA 的指标分母——这条跨章约束的具体含义就在这里：`api` 的 requests `100m/128Mi` 是 `averageUtilization: 60` 的分母，任何 VPA 都不得以 `Auto` 作用于 `api`，CL-18-03 检查的就是这条。**第二，推荐实践是「VPA 做参谋、人做决定」（本书观点，不需要外部背书）**：用 `Off` 模式跑一个完整流量周期（如两周），把 `status.recommendation.target` 与压测曲线对照，确认偏差稳定后，以一次普通变更走 Git 提交新基线——基线修订是带回滚方案的变更（公理 6），不是控制器的即兴发挥。`Initial` 的适用窗口很窄：只在你已经信任推荐值、且只想让新副本受益时启用；若推荐值本身异常，新副本会带着错误的 requests 进入集群并挤占第 17 章 `requests.cpu: "4"` 的配额，把扩容卡成 `Pending`——这是表 18-1「副本上下限」一行警告的另一种触发方式。把判据落到 `order-demo` 四个组件上就是一张三行结论：`api` 由 HPA 管，VPA 至多用 `Off` 观察基线；`gateway` 同理，且 `64Mi` 的 requests 本身极小，VPA 推荐值的噪声占比高，参考价值有限；`worker` 的副本已由 KEDA 按队列驱动，若再加 VPA `Auto` 就是给一个对象挂两个控制器，与 18.3 的接入顺序纪律冲突；`db` 是 StatefulSet（第 7 章起），`Auto` 的驱逐重建会打断主从复制，调 requests 只能走维护窗口加 Git 变更。

### 18.2.4 成本归因的完整方法：三个维度、showback 与 chargeback 的分界、优化动作的 SLO 前置检查

18.4 的 `cost-report.sh` 只演示了一个命名空间内的按组件占比，完整的归因方法要回答三个问题：钱花在哪个**组件**、哪个**环境**、哪个**团队**。三个维度正好对应三份报表，且都只依赖已有口径，不需要新建标签体系：组件取公共标签 `app.kubernetes.io/component`（第 6 章契约）；环境取命名空间——`order-demo-{env}` 本身就是环境边界（第 4 章）；团队在标签未统一前用「命名空间 → 团队」映射表维护，不要为归因再造第四套标签（标签口径分裂是第 5 章工具堆叠警戒线的变体）[R-18-10]。

维度定了，下一步是决定报表**推不推到扣费**，即 showback 与 chargeback 的分界（分界判据为本书观点，不需要外部背书；归因口径本身沿用 [R-18-10]）：

表 18-9　showback 与 chargeback 判据表

| | showback（只出账不扣费） | chargeback（分摊进团队预算） |
|---|---|---|
| 定义 | 各维度相对占比报表，团队自主决定是否行动 | 报表金额进入团队成本核算，甚至影响考核 |
| 前提 | 标签覆盖率 ≥ 90%，归因口径经各团队确认 | 标签覆盖率 ≥ 98%、口径有书面约定、至少一个季度 showback 稳定运行、新团队有免责期 |
| 典型失败模式 | 报表无人看（说明维度选错了，不是方法错了） | 标签缺失导致错误扣费 → 团队对报表失去信任 → 从此没人再看 |
| 本章建议 | 一切成本工作的起点 | showback 稳定后再评估；多数平台做到 showback 已经够用 |

标签覆盖率可以用一条命令量化（通过标准：缺 `app.kubernetes.io/component` 标签的 Pod 数为 0；不为 0 时先按第 6 章契约补标签，再谈任何归因报表）：

```bash
kubectl get pods --all-namespaces \
  -o jsonpath='{range .items[*]}{.metadata.labels.app\.kubernetes\.io/component}{"\n"}{end}' \
  | awk '/^$/{c++} END{print c+0 " 个 Pod 缺 component 标签"}'
```

最后一层是**如何避免「成本优化伤 SLO」**：每一类优化动作都要有前置检查，把「省下的钱」和「被牺牲的容量」分开——这是 18.2 本书观点「先归因再优化」的执行细则 [R-18-9][R-18-10]：

表 18-10　优化动作 × SLO 前置检查表

| 优化动作 | 直接 SLO 风险 | 前置检查 | 通过标准 |
|---|---|---|---|
| 降 requests（修订基线） | HPA 分母变小、阈值提前触发、诱发抖动 | 改基线后重跑 18.2.1 三组压测 | 观察窗口无抖动、P99 不抬升 |
| 缩 `maxReplicas` | 容量上限下降，突发流量打满 | 对照第 13 章容量账复核 | `maxReplicas × 单副本安全 RPS ≥ 峰值需求` |
| 缩静态节点 / 换竞价实例 | 节点回收触发驱逐，副本重排 | 18.5 多可用区演练 + PDB 确认 | 驱逐期间就绪端点 ≥ `minReplicas` |
| 机型替换 / 更激进的 consolidation | Pod 频繁迁移、在途请求受扰 | 复核 18.3.1「何时不该用」 | 迁移率与 5xx 无相关性 |

发起闸门统一回到第 20 章：**错误预算余量充足才允许发起成本优化变更**——预算紧张期的「省钱」本质是把可用性拿来换钱。每次优化都按普通变更走 Git 与回滚方案（公理 5、6），变更前后的 `cost-report.sh` 输出与压测曲线留档对照，这四份留档就是「这次优化没有伤 SLO」的唯一证据。

用一次合成优化把「归因 → 检查 → 验收」串成闭环：压测日之后的 `cost-report.sh` 显示 `api` 占命名空间 requests 的 58%、`gateway` 占 12%，结合第 21 章用量曲线发现 `api` 的 CPU 用量长期只有 requests 的 35%——这是「降 requests」的候选信号。按表 18-10 走前置检查：修订基线走 Git（公理 5），重跑 18.2.1 三组压测确认无抖动、P99 不抬升；变更后复跑归因报表，`api` 占比降到 44%，错误预算消耗与上周持平，优化可验收；若占比降了但 P99 抬升，则按回滚方案还原基线，并在归因报表上标注「该组件不可再缩」。注意闭环里出现的全是相对占比与压测判据，没有一个具体单价——这套方法在价格波动的多云环境里同样成立 [R-18-10]。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：成本归因先于成本优化；没有按组件/环境的归因，任何「省钱」动作都无法验证效果，因此不应被批准。
>
> **论证**：一次缩容、降配或换机型，本质是一次影响 SLO 的变更，必须可验证（全书公理 6「回滚方案先行」与第 20 章错误预算同理）。验证需要一个对照基线：变更前这个组件占多少、变更后占多少、P99 与错误预算有没有变。没有按 `app.kubernetes.io/component` 与环境的归因，就只能拿到一个总金额，而总金额同时受流量增长、新功能上线、节点池调整影响，无法把「省下的」和「牺牲的」分开。归因口径也只需相对比例——某组件 requests 之和 / 命名空间 requests 之和——完全不需要任何云厂商单价，价格随区域与合约变动，写进书里当天就过时。
>
> **反例与适用前提**：这不等于「所有团队都要上一套成本平台」。单集群、固定节点、成本不敏感的内部工具，或者利用率已经压到极高、没有可优化空间的场景，可以暂缓归因。但只要准备做任何缩容、降配或竞价实例替换，就必须先有可对照的归因基线，否则无法自证没有伤到 SLO。跳过此步的典型代价见第 5 章「工具堆叠」警戒线与第 20 章的错误预算冻结规则。

## 18.3 工具选型：弹性工具对比（含「何时不该用」）

选型矩阵见表 18-2。这是选型章，L1 引用覆盖互相竞争的工具官方文档（见 18.7）。每个工具都回答「什么时候不该用」，避免把弹性栈堆成第 5 章批评的工具堆叠。

表 18-2　弹性与归因工具选型矩阵

| 工具（主版本） | 作用层 | 指标 | 何时不该用 | 抖动风险 | 回滚方式 |
|---|---|---|---|---|---|
| HPA（Kubernetes 1.32，autoscaling/v2） | Pod 副本数 | CPU/内存/自定义/外部指标 | 负载由队列深度驱动、或有状态组件副本不可随意增减；此时用 HPA 会「扩不动」 | 窗口过短、指标滞后 | `delete -f deploy/base/hpa.yaml`，副本回静态基线 |
| VPA 1.x | 垂直 requests | 历史用量分位数 | 与 HPA 同时对同一资源开 `Auto`；在线改有状态 DB 的 requests 会触发重建 | 与 HPA 互相改写 | 删除 VPA 对象，还原 Pod 模板 requests |
| KEDA 2.x | 事件驱动副本（可缩到 0） | 队列长度 / 外部事件 | 纯同步 HTTP 流量、无队列或事件源；或要求常驻副本却忘配 `minReplicaCount` | ScaledObject 与另一 HPA 同时管同一 Deployment | 删除 ScaledObject，KEDA 生成的 HPA 随之清理 |
| Karpenter 1.x | 节点 | Pending Pod / 容量需求 | 固定节点组、无云弹性伸缩权限、或集群小到节点层弹性收益为负 | 节点频繁增删导致 Pod 反复迁移 | 删除 NodePool，回退到静态节点组 |
| Cluster Autoscaler 1.x | 节点组 | Pending Pod / 节点利用率 | 需要异构实例快速选型（此场景 Karpenter 1.x 更合适）；或托管节点组已自动扩 | 与 HPA 扩容节奏不匹配 | 把节点组缩回静态大小 |
| OpenCost 1.x | 成本归因 | 资源用量 × 相对权重 | 只需要总账单、不需要按组件拆分；或公共标签口径尚未统一 | 标签缺失导致归因失真 | 删除采集/归因配置，报表停发 |

### 18.3.1 节点层两种范式：Karpenter 的「按需求选型」vs Cluster Autoscaler 的「按组扩缩」

节点层只有两个候选（见表 18-2），但两者底层范式完全不同，选错会在扩容高峰期暴露。

**Cluster Autoscaler（CA，1.x）** 以「节点组」为最小调度单位：它盯着 Unschedulable 的 Pod，去增删你预先在云上定义好的节点组（AWS ASG / GCP MIG / Azure VMSS）。新增节点必须属于某个已有节点组，因此**异构实例选型在 CA 这里是「预先开好几个节点组」的减法题**——想临时换一类机型，得先改节点组定义，CA 再按组扩。CA 对每个节点组独立决策，**不做跨组的智能整合**，节点组之间容易留下碎片。官方文档的工作对象就是节点组（autoscaler 项目），这也是表 18-2「何时不该用」里那句「需要异构实例快速选型时 Karpenter 更合适」的根因 [R-18-7]。

**Karpenter（1.x）** 的范式相反：它聚合所有 Pending Pod 的资源请求，直接决定「该起一台什么规格的机器」，实例类型来自 NodePool 里 `karpenter.sh/instance-type` 的约束与权重，不依赖静态节点组。一个 NodePool 可以同时候选多类机型，Karpenter 在每次调度时做 bin-packing，挑最贴合当下负载的组合。更关键的是 **consolidation**：负载低谷时 Karpenter 会主动把 Pod 重新整合到更少、更便宜的节点上并终止被腾空的节点，把「缩容」从被动等待变成主动优化 [R-18-5]。CA 在这件事上保守得多——它只在节点长期空置且能被安全驱逐时才缩，且仍以节点组为单位。

**差异落到决策上**：
- 异构实例快速选型、想把机型选择交给调度器 → Karpenter 胜（单 NodePool 多类型，无需预先开组）。
- 已经有托管节点组、或合规要求实例类型走白名单审计 → CA 更省心，节点组白名单本身即可被审计；Karpenter 的开放式机型候选反而要额外加 `karpenter.sh/instance-type` 约束才满足审计。
- 成本优化的主动性 → Karpenter 的 consolidation 天然持续 bin-pack；CA 更像「够用不挪」。

**「何时不该用」的硬案例**：某合规集群要求所有节点必须来自预批准的机型白名单、且变更要进变更单。这里上 Karpenter 若不收紧 `instance-type` 约束，会绕过机型审计；上 CA 则节点组白名单天然合规。另一个反面：集群规模小（十几节点）、且没有任何云弹性伸缩权限（节点由工单申请），节点层弹性收益为负，两种工具都不该上，老老实实用静态节点组，把弹性留给 HPA 这一层就够了。

回滚上两者也不同：Karpenter 是删 NodePool 回退到静态节点组；CA 是把节点组缩回静态大小。任一情况下都要先确认没有 Pending Pod 依赖弹性节点，否则回退会卡住调度 [R-18-5][R-18-7]。

**最小接入 diff 与顺序**：先在 Deployment 加 `topologySpreadConstraints`（调度，无副作用）→ 再上 HPA（先只扩不缩，`scaleDown` 窗口设长）→ 再上 KEDA ScaledObject（确认它没有与 HPA 指向同一 Deployment）→ 再评估节点层 → 最后接成本归因。顺序反了会很难定位抖动来自哪一层。

**生产接入 HPA 业务指标的 diff**（kind 演示用 CPU，生产把主指标换成业务指标，见第 21 章指标口径）：

```yaml
# deploy/base/hpa.yaml 中 metrics 段的等价替换（业务指标需 Prometheus Adapter，见第 21 章）
metrics:
  - type: Pods
    pods:
      metric:
        name: orders_in_flight
      target:
        type: AverageValue
        averageValue: "30"
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80    # CPU 退为兜底，不再是唯一指标
```

> 这段 diff 正是反模式二的修正：队列积压时 `orders_in_flight` 会先涨，CPU 还没反应过来副本就已经扩了。它依赖第 21 章的可观测栈，因此本章 18.4 的可复现配置仍以 CPU 为主指标，不把演示绑死在 Adapter 上。

### 18.3.2 业务指标经 Prometheus Adapter 接入 HPA：完整链路与基数陷阱（本书观点）

上面那段 `orders_in_flight` 的 diff 要真正可应用，中间还差一条完整链路。本小节把链路钉死并指出基数陷阱；**机制与陷阱均为本书观点，不需要外部背书（Prometheus Adapter 官方文档链接将随引用解析轮次补入 R-18-x）**。

链路四跳，任何一跳断了 HPA 都拿不到数：

1. **应用暴露**：`api` 进程暴露 `orders_in_flight`，标签只带 `pod`、`namespace` 这类低基数维度；指标口径先在第 21 章的指标登记表定下来，再谈接入。
2. **Prometheus 2.x 抓取**：第 21 章 ServiceMonitor 的 relabel 会把 `pod` / `namespace` 写进每个 series 的标签——没有这两个标签，下一跳无从映射。
3. **Prometheus Adapter 翻译**：Adapter 按规则把 PromQL 查询暴露成 `custom.metrics.k8s.io` APIService，HPA 的 `metrics.type: Pods` 就是从这里逐 Pod 取值。
4. **HPA 查询**：`pods.metric.name` 必须等于规则里 `as:` 改出的名字，否则 HPA 报 `FailedGetPodsMetric`，而指标本身其实是好的。

完整规则配置（`apiVersion: v1`，Prometheus Adapter 0.x，Kubernetes 1.32+；经第 21 章 Prometheus 抓取后生效，规则可并入 Adapter 的主配置）：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: adapter-orders-in-flight-rule
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: api
    app.kubernetes.io/managed-by: argocd
data:
  config.yaml: |
    rules:
      - seriesQuery: 'orders_in_flight{namespace="order-demo-dev",pod!=""}'
        resources:
          overrides:
            namespace:
              resource: namespace
            pod:
              resource: pod
        name:
          matches: "^orders_in_flight$"
          as: orders_in_flight_per_pod
        metricsQuery: 'sum(<<.Series>>{<<.LabelMatchers>>}) by (<<.GroupBy>>)'
```

三段规则各司其职：`seriesQuery` 圈定候选 series（即 Adapter 认识哪些指标）；`resources.overrides` 把指标标签映射回 K8s 对象，HPA 请求 `/pods/<pod>/orders_in_flight_per_pod` 时 Adapter 才知道该查谁；`metricsQuery` 是真正执行的 PromQL，`<<.Series>>`、`<<.LabelMatchers>>`、`<<.GroupBy>>` 由 Adapter 按请求注入。

三个基数陷阱，每个都对应一类真实翻车：

- **陷阱一：`seriesQuery` 过宽。** 不带指标名与命名空间过滤，Adapter 会把匹配到的全部 series 缓存在内存里，基数一大就内存暴涨、APIService 超时，HPA 侧表现为反复 `FailedGetResourceMetric`。约束：`seriesQuery` 必须同时带指标名与命名空间过滤。
- **陷阱二：`metricsQuery` 把 `pod` 维度聚合掉。** 写成 `sum by (namespace)` 之后，Pods 类型的 HPA 拿不到逐 Pod 值，`AverageValue` 的「每副本平均」语义失真。约束：`by (<<.GroupBy>>)` 必须保留，让请求中的 `pod` 维度传下去。
- **陷阱三：高基数标签混进指标。** `order_id`、`user_id` 级别的标签会让 series 数爆炸，Prometheus 自身先受害（基数治理口径见第 21 章），Adapter 其次被拖垮。约束：HPA 业务指标只带 `pod` / `namespace` / 组件级标签，明细维度留给日志与链路（第 21 章）。

验证与回滚：`kubectl get --raw /apis/custom.metrics.k8s.io/v1beta1/namespaces/order-demo-dev/pods/*/orders_in_flight_per_pod` 应返回每 Pod 一条的 JSON；`kubectl -n order-demo-dev describe hpa api-hpa` 应出现 `orders_in_flight_per_pod` 的当前值与目标值。失败处置：先跑 `get --raw` 分辨是 Adapter 侧（404 或空结果，回查标签映射）还是 HPA 侧（`as:` 名字不匹配），再逐跳排查。回滚即删掉规则 ConfigMap，并把主指标退回 18.4 的 CPU 基线——18.4 那份 `hpa.yaml` 本身就是本小节的回滚态。

**升级 / 回滚路径**：KEDA 2.x 与 Karpenter 1.x 是集群级控制器，升级按附录 A 锁定的小版本走；本章清单的升级只需 `kubectl apply -k deploy/overlays/dev`。回滚按接入逆序 delete，且**先删 HPA/ScaledObject 再回退 Deployment**——否则控制器会在回退过程中持续改写副本数。生产回退按 18.5 走 Git。

**逐条通过标准**：

| 判据 | 期望结果 |
|---|---|
| 跨 AZ 打散 | `api` 副本分布在 ≥ 2 个 `topology.kubernetes.io/zone`，`kubectl get pods -o wide` 的 NODE 列不集中在同一节点 |
| 压测触发扩容 | `api-hpa` 的 `desiredReplicas` 从 2 上升到 ≥ 4，`currentCPU` 随负载上升 |
| 冷却期内无抖动 | 120s 观察窗口内副本序列单调不回落，无「升—降—升」；停止负载后 300s 内副本保持 |
| HPA / VPA 无冲突 | 只有 `api-hpa` 管理 `api` 副本；不存在作用于 `api` 的 VPA `Auto` 对象；`worker` 只被 KEDA 生成的 HPA 管理 |
| 成本可归因 | `cost-report.sh` 输出按组件/命名空间的相对占比，报表内无任何具体云厂商单价 |
| 基线未漂移 | `api` 的 requests 仍为 `100m/128Mi`、limits 仍为 `500m/256Mi`（见第 17 章） |

最后一项是 requests 基线这道闸门：HPA 一旦顺手改了 requests，前五项全部失去意义。

**多可用区故障注入演练：摘掉一整个 zone 后的副本重排**（kind 演练；生产等价场景是 zone 网络隔离或机房维护，演练编排见第 23 章）

演练需要一件 18.4 没有的对象：`api` 的 PDB。第 8 章只为 `gateway` 落了 `minAvailable: 1` 的 PDB，`api` 按同一范式补一份（完整可应用，`apiVersion: policy/v1`，Kubernetes 1.32+；不动任何冻结字段）：

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: api
    app.kubernetes.io/managed-by: argocd
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: api
```

注入步骤（先记录初始分布，再摘 az-c）：

```bash
NS=order-demo-dev
kubectl -n "${NS}" apply -f deploy/base/pdb-api.yaml
kubectl -n "${NS}" scale deployment/api --replicas=6        # 三域均摊后为 2/2/2
kubectl -n "${NS}" get pods -l app.kubernetes.io/component=api -o wide   # 记录初始分布

AZC_NODE=$(kubectl get nodes -l topology.kubernetes.io/zone=az-c -o jsonpath='{.items[0].metadata.name}')
kubectl cordon "${AZC_NODE}"
kubectl label node "${AZC_NODE}" topology.kubernetes.io/zone-   # 摘标签＝让该拓扑域从调度器视野消失
kubectl -n "${NS}" get pods -l app.kubernetes.io/component=api \
  --field-selector "spec.nodeName=${AZC_NODE}" -o name \
  | xargs kubectl -n "${NS}" delete    # 删 Pod 模拟节点失联；非驱逐 API，PDB 不拦截（语义见第 8 章）
```

摘掉 az-c 之后，集群里发生的事按时间线展开，每一步都能直接观测：

表 18-6　摘掉 az-c 后的副本重排时序

| 时刻 | 事件 | 观测点 | 判据 |
|---|---|---|---|
| T+0 | az-c 节点被 cordon 且摘掉 zone 标签，其上 2 个 `api` Pod 被删除（模拟失联） | `kubectl get nodes -L topology.kubernetes.io/zone` 少一个域 | 该域退出 eligible 集合 [R-18-1] |
| T+0~5s | 失效 Pod 从 Service Endpoint 摘除，就绪端点 6→4 | `kubectl -n order-demo-dev get endpoints api` | 端点数随删除同步减少（第 8 章 Endpoint 语义） |
| T+5s | Deployment 控制器发现实际副本 < 期望，创建 2 个替代 Pod | `kubectl -n order-demo-dev get pods -w` | 新 Pod 进入 `Pending` |
| T+5~20s | 调度器按 `topologySpreadConstraints` 在剩余 az-a/az-b 两域计算 `maxSkew: 1`，`DoNotSchedule` 强制两域差 ≤1 | `kubectl describe pod <new-pod>` 事件含 `topology spread constraints` | 两域各补 1，落点 3/3 [R-18-2] |
| T+20s~1min | 新 Pod 通过 `/startup`、`/readyz` 后进 Endpoint | Pod `READY 1/1` | 可用副本回到 6 |
| T+1min | 重排完成：az-a=3、az-b=3；若无跨 zone 强制约束（反模式一），6 副本可能全部挤向剩余可达节点 | `-o wide` 的 NODE 列 | `maxSkew ≤ 1` 成立 |
| 恢复期 | 运维以 `drain` 下线 az-c 节点维修时，驱逐 API 受 `api-pdb` 限制并发驱逐数（`ALLOWED DISRUPTIONS`）；PDB 不拦 OOM 与宕机（第 8 章） | `kubectl -n order-demo-dev get pdb api-pdb` | 驱逐逐个进行，可用副本不低于 `minAvailable` |
| T+恢复 | az-c 重新打标签并 `uncordon`，下一轮扩容/重排自动回填三域 | 分布回到 2/2/2 | 三域回填 [R-18-2] |

这次演练钉死三个结论：第一，`whenUnsatisfiable: DoNotSchedule` 才是「重排后仍然均匀」的根，`ScheduleAnyway` 只在约束恰好能满足时才起作用；第二，PDB 在此保护的不是「zone 失联」本身——`delete Pod` 不走驱逐 API，故障注入与真实宕机都不会被 PDB 拦——而是恢复期人为 `drain` 的并发度，把 PDB 当 zone 故障兜底正是第 8 章批过的误读；第三，演练结束必须恢复现场，否则后续压测的分布判据全部失真。

恢复与验证命令：

```bash
NS=order-demo-dev
kubectl label node "${AZC_NODE}" topology.kubernetes.io/zone=az-c --overwrite
kubectl uncordon "${AZC_NODE}"
kubectl -n "${NS}" get pods -l app.kubernetes.io/component=api -o wide
kubectl -n "${NS}" get pdb api-pdb
```

通过标准：注入期间就绪端点 ≥ `minReplicas`（2）；重排后剩余域副本差 ≤1；恢复 az-c 后三域回填为 2/2/2；`api-pdb` 的 `ALLOWED DISRUPTIONS ≥ 1`。失败处置：出现 `Pending` 先查 `whenUnsatisfiable` 与第 17 章 Quota；就绪端点跌破 2 说明副本下限与 PDB/Quota 的联动失效，回 18.4 核对 `minReplicas` 与 PDB selector 是否只圈住 `api`。
