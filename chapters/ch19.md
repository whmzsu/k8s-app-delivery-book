## 19.1 问题与反模式：三处重试、一次证书过期、一条没人查得动的 DNS

**合成案例**（本书统一采用虚构合成场景，不指向任何真实事故）。团队最早用 Ingress 加一堆 `nginx.ingress.kubernetes.io/*` 注解配超时和重试；后来为了做 mTLS 又加了 Istio Sidecar，客户端 SDK 里本来就有一层重试。于是同一次下游调用被重试了三层：网关 2 次、Sidecar 3 次、SDK 3 次，下游一抖动就放大成 18 次请求，把小故障直接推成重试风暴 [R-19-8]。同一周还发生了两件事：一张人工续期的证书忘了换，HTTPS 入口全站 502；NetworkPolicy 只给入站加了白名单、没限制出站，一个被入侵的 `worker` 可以直连外部地址。偶发的 `Temporary failure in name resolution` 更让人无从下手——值班分不清该查 CoreDNS、查 Service 的 Endpoint，还是查刚刚收紧的网络策略。网络、DNS 与证书类故障在公开复盘里长期是「定位路径不成文」的重灾区，本章因此把「未授权 Pod 无法访问 `db`」写成可验证动作，并把 DNS 定位路径写成检查项 [R-19-11]。

入口选型的根子在于 **Ingress 已经停止演进**：它只有一个资源、一个角色，路由之外的能力全靠各实现自定义的注解表达，换一个控制器就要重写一遍注解，且应用开发者与运维改的是同一份对象。Gateway API 1.x 是它的继任者，按角色把入口拆成 `GatewayClass`（基础设施提供方）、`Gateway`（运维管监听器与证书）、`HTTPRoute`（应用团队管路由），能力进 `spec` 而不是进注解 [R-19-1][R-19-10]。这三类资源都是 CRD（给 K8s 加一种新资源类型，详见第 27 章）；本章只使用它们，不展开自定义资源的设计。

三个反模式，按「现象 → 根因 → 本章替代做法」拆开：

**反模式一：只给入站加白名单、不限制出站。** 现象是数据外联无约束、被入侵的 Pod 可以直连外部。根因是 NetworkPolicy 的语义是「默认允许、加了策略才拒绝」——只写入站规则时，出站仍是全放行 [R-19-4]。本章的替代做法是显式写**双向默认拒绝基线**（`default-deny-ingress` + `default-deny-egress`），再用组件白名单逐条放通，见 19.4。

**反模式二：重试在网关、Sidecar、客户端各配一遍。** 现象是故障时被放大成重试风暴，且层层都有超时，实际生效的是最短的那个，没人能说清一次调用到底会重试几次。根因是把「可靠性」当成「每一层都兜一下」，忽略了重试是乘法不是加法 [R-19-8][R-19-7]。本章的替代做法是**单层负责**：超时写在 `HTTPRoute` 的 `timeouts`，重试与熔断只写在 Envoy Gateway 1.x 的 `BackendTrafficPolicy` 一处，Sidecar 与客户端禁用重试 [R-19-6]。

**反模式三：证书靠人工续期。** 现象是到期即全站不可用，而且往往发生在节假日。根因是证书有效期是一个会自己走到的死线，人工日历不可靠 [R-19-5]。本章的替代做法是用 cert-manager 1.x 的 `Certificate` 声明 `duration` 与 `renewBefore`，让续期成为控制循环，并把「到期前 N 天未续期」挂成告警（见第 22 章）[R-19-5]。

> **一个刻意的边界**：第 6 章的 `gateway` 应用 Service（8080）、`api`（8081）、`db`（5432）是配置契约，本章全部沿用；Gateway API 的 `Gateway` 资源 `order-demo-gw` 是**另一个对象**，由 Envoy Gateway 1.x 创建的数据面 Service 承载，与 `gateway` 应用 Service 不冲突。HTTPRoute 把 `/orders` 路由到 `gateway:8080`，再由 `gateway` 组件转发到 `api:8081`，组件链路不变（见第 6 章）。

## 19.2 范式与决策树：流量治理的每一层各管什么

先把分层钉死，这是「该不该上网格」与「重试放哪」的共同前提。见表 19-1。

表 19-1　流量治理分层（每层只管自己那一段）

| 层 | 资源 / 机制 | 管什么 | 不该管什么 |
|---|---|---|---|
| 集群内发现 | `Service`（ClusterIP，Kubernetes 1.32） | 稳定虚拟 IP、L4 负载均衡、DNS 名 | 七层路由、TLS 终止、重试策略 |
| 南北向入口 | `GatewayClass` / `Gateway` / `HTTPRoute`（Gateway API 1.x） | 入口监听、路由、TLS 终止、请求超时 | 集群内东西向细粒度策略 |
| 网络策略 | `NetworkPolicy`（networking.k8s.io/v1） | L3/L4 允许清单、双向默认拒绝 | 七层鉴权、基于身份的 mTLS |
| 入口扩展策略 | `BackendTrafficPolicy`（Envoy Gateway 1.x） | 重试、熔断、连接池 | 跨服务全链路身份 |
| 服务网格（可选） | Istio 1.x | 东西向 mTLS、细粒度流量、统一遥测 | 只需要一个入口时的简单路由 |
| 证书 | `Certificate`（cert-manager 1.x） | 签发、自动续期 | 流量路由 |

表里的第一层由 `Service`（ClusterIP）提供稳定虚拟 IP 与 L4 负载均衡，Pod 重建后 IP 变化不会让调用方失效 [R-19-2]；它只负责「找得到」，不负责任何七层行为（见第 6 章）。

**唯一示例实现**按 `book/decisions.md` 的 U-05 与 `case-evolution.md` 第五节固定值：`GatewayClass: eg`、`Gateway` 名 `order-demo-gw`、`HTTPRoute` 名 `gateway-route`，数据面为 Envoy Gateway 1.x；**Istio 1.x 只在选型矩阵作对比**，不进入本章任何可应用清单 [R-19-1][R-19-6][R-19-9]。`eg` 这个 GatewayClass 由 Envoy Gateway 1.x 安装时提供，本章只引用、不重复创建——同一示例全书只用一个实现，正是为了避免第 15 章与本章各选一套导致示例跑不通（SP-15，见第 15 章）。

**超时、重试、熔断、mTLS 的分层结论**：

- **超时**写在离调用方最近且可观测的一层，即 `HTTPRoute.spec.rules[].timeouts`（`request` 总超时、`backendRequest` 后端超时），它是 Gateway API 的 `spec` 字段而非注解，换实现不失效 [R-19-1]。
- **重试与熔断**只在 `BackendTrafficPolicy` 配一次：`retry.numRetries: 2`、`circuitBreaker` 限连接与并发重试。Sidecar 与客户端 SDK 一律不再配重试，否则就是反模式二的乘法放大 [R-19-6][R-19-8]。
- **mTLS** 要分清两种需求。南北向 TLS 终止由 `Gateway` 的 `tls.mode: Terminate` 加 `certificateRefs` 完成，Gateway API 本身就够；而「东西向、基于工作负载身份的全链路 mTLS」需要服务网格（Istio 1.x）或 Envoy Gateway 的 `BackendTLSPolicy` 做上游证书校验 [R-19-7]。本章唯一示例实现不含网格，因此**不启用全链路 mTLS**；是否值得为此引入网格，正是下面决策树要回答的问题，也是第 5 章「工具堆叠」警戒线的具体案例 [R-19-9]。

**DNS 疑难定位路径**（写成可复用的顺序，检查清单 CL-19-05 会考它）：

```
解析失败 / 偶发超时
  → 1. 查 CoreDNS 1.x 自身：kubectl -n kube-system get pods -l k8s-app=kube-dns
  → 2. 查名字与 search 域：kubectl run -it --rm dns-debug --image=busybox:1.36 \
         -- nslookup api.order-demo-dev.svc.cluster.local
         （短名依赖 search 域与 ndots，跨命名空间务必用 FQDN）
  → 3. 查 Service 是否有 Endpoint：kubectl -n order-demo-dev get endpoints api
  → 4. 查 NetworkPolicy 是否放通 DNS：default-deny-egress 下必须显式放行 UDP/53
  → 5. 查目标 Pod 是否 Ready：readiness 失败会从 Endpoint 摘除（见第 8 章）
```
把顺序写死很重要：默认拒绝 egress 之后最先「看起来像 DNS 挂了」的，其实是网络策略没放通 `kube-dns` 的 53 端口 [R-19-3][R-19-4]。本章 19.4 的 `allow-dns` 策略就是为这一步留的口子。

**证书有效期**：cert-manager 1.x 依据 `Certificate.spec.duration` 与 `renewBefore` 自动续期，状态字段 `status.notAfter` 与 `status.renewalTime` 可直接读；`kubectl get certificate` 的 `READY` 必须为 `True`。私钥由控制器写进 Secret（`order-demo-tls`），按全书公理 9 不入 Git [R-19-5]。到期告警与 runbook 见第 22 章。

**「该不该上网格」决策树**：

```
需要东西向 mTLS / 细粒度流量策略 / 统一遥测？   否 → 不上网格：Gateway API + NetworkPolicy 已够
        │ 是
团队能承担数据面运维成本（注入、升级、资源、排障）？ 否 → 不上网格：先用 Gateway API 超时/重试 + NetworkPolicy
        │ 是
入口实现是否已统一且不与网格冲突？              否 → 先按 U-05 定唯一入口（eg），再评估
        │ 是 → 上网格；但重试/超时仍只在一层配置，不叠三层
```

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：服务网格不是默认项。只有当确实需要 mTLS、细粒度流量策略或统一可观测，且团队能承担数据面运维成本时才值得上。
>
> **论证**：网格解决的是「东西向、跨服务、基于身份」的问题，而一个应用的入口路由、超时、重试、TLS 终止，Gateway API 1.x 加一层 `BackendTrafficPolicy` 就能覆盖，且不需要给每个 Pod 注入 Sidecar。引入网格的代价是实打实的：数据面资源开销、注入与升级的发布节奏、多一层可观测与排障心智。合成案例里的重试风暴不是网格的 bug，而是「三层都配了重试」这一决策缺失的结果——先加网格反而让层数更多、更难说清一次调用到底重试了几次。先把入口与网络策略两层做对，再判断剩下的需求是否真的非网格不可。
>
> **反例与适用前提**：这不等于「永远不上网格」。多团队、多语言、需要统一的 mTLS 身份与跨服务流量策略、且已有平台团队专职维护数据面时，网格的收益会超过成本；合规要求全链路加密的环境也可能把它变成硬要求。本结论的前提是「以单一入口为主的中小规模应用、团队尚无专职平台能力」。第 5 章的工具堆叠警戒线与第 21 章的遥测方案，都是这个判断的配套依据。

## 19.3 工具选型：Gateway API 实现选型（含「何时不该用」）

选型矩阵见表 19-2。**唯一示例实现取 `book/decisions.md` 的固定值**（`eg` / `order-demo-gw` / `gateway-route`），其余实现只在矩阵里作对比，不写进 19.4 的可应用清单 [R-19-1][R-19-10]。

表 19-2　Gateway API 实现选型矩阵

| 实现（主版本） | 标准符合度 | 流量能力 | 运维成本 | 何时不该用 | 回滚方式 |
|---|---|---|---|---|---|
| **Envoy Gateway 1.x（唯一示例）** | Gateway API 原生，按角色拆资源 | 路由、超时、重试、熔断 | 低–中（无 Sidecar） | 需要完整东西向 mTLS 与网格级遥测（此场景该上网格） | 删 `HTTPRoute`/`Gateway`，回退 Ingress 或旧入口 |
| Istio 1.x（仅对比） | Gateway API 兼容 + 自有 CRD | mTLS、细粒度流量、统一遥测 | 高（Sidecar / Ambient） | 只需要一个入口、团队无力运维数据面 | 卸载控制面、摘掉注入标签 |
| Cilium 1.x（仅对比） | Gateway API 支持 + eBPF | 路由与网络策略一体 | 中（依赖 eBPF CNI） | 集群 CNI 不是 Cilium，或只需要标准入口 | 关闭 Gateway API 特性 |
| NGINX Gateway Fabric 1.x / Ingress NGINX 1.x（仅对比） | Gateway API / Ingress | 基础路由 | 低 | 需要角色拆分与可移植路由（Ingress 注解不可移植） | 保留 Ingress 注解回退 |
| cert-manager 1.x（配套） | — | 证书签发 / 自动续期 | 低 | 证书由外部 PKI 统一签发、不需集群内续期 | 删 `Certificate`，回退外部证书 |

表 19-3　NetworkPolicy 基线（默认拒绝双向 + 组件白名单）

| 方向 | 基线策略 | 放通项 | 被拒绝的典型流量 |
|---|---|---|---|
| Ingress | `default-deny-ingress` | 数据面→`gateway:8080`、`gateway`→`api:8081`、`api`→`db:5432` | 未授权 Pod 直连 `db:5432` |
| Egress | `default-deny-egress` | 所有 Pod→`kube-dns` UDP/TCP 53、`gateway`→`api:8081`、`api`/`worker`→`db:5432` | 被入侵 Pod 外联任意地址 |
| 说明 | `podSelector: {}` 选中命名空间全部 Pod | 能力取决于 CNI 是否实现 NetworkPolicy（见一致性备注） | — |

**Ingress → Gateway API 最小接入 diff**（把注解里的能力搬回 `spec`）：

```diff
- apiVersion: networking.k8s.io/v1
- kind: Ingress
- metadata:
-   name: order-demo
-   annotations:
-     nginx.ingress.kubernetes.io/proxy-read-timeout: "5"
-     nginx.ingress.kubernetes.io/proxy-next-upstream-tries: "2"
- spec:
-   rules:
-     - host: order-demo.example.com
-       http:
-         paths:
-           - path: /orders
-             pathType: Prefix
-             backend:
-               service:
-                 name: gateway
-                 port:
-                   number: 8080
+ apiVersion: gateway.networking.k8s.io/v1
+ kind: Gateway
+ metadata:
+   name: order-demo-gw
+ spec:
+   gatewayClassName: eg
+   listeners:
+     - name: http
+       protocol: HTTP
+       port: 80
+ # HTTPRoute: timeouts.request: 5s（取代 proxy-read-timeout 注解）
+ # BackendTrafficPolicy: retry.numRetries: 2（取代 proxy-next-upstream-tries，且只此一处）
```

> 两条注解一条进 `HTTPRoute.spec.rules[].timeouts`、一条进 `BackendTrafficPolicy`，且重试不再允许在 Sidecar / SDK 重复出现 [R-19-1][R-19-6][R-19-8]。

**升级 / 回滚路径**：先并行安装 Envoy Gateway 1.x 并确认 `eg` GatewayClass 就绪 → 再提交 `Gateway` / `HTTPRoute`（与旧 Ingress 用不同 hostname 或路径前缀并存）→ 用 `net-verify.sh` 验证新链路 → 切 DNS / 入口指向 → 最后删旧 Ingress。回滚按逆序，应急时先删 NetworkPolicy 默认拒绝（见 19.5，注意这是**安全降级**），再删 Gateway/HTTPRoute。生产回退按 19.5 走 Git。

## 19.4 落地配置（完整可应用文件，Kubernetes 1.32+）

> 沿用 `book/case-evolution.md` 配置契约：命名空间 `order-demo-dev`、Service 名 `gateway` 8080 / `api` 8081 / `db` 5432、公共标签、`app.kubernetes.io/managed-by: argocd`。`GatewayClass: eg` 由 Envoy Gateway 1.x 安装时提供，本章只引用。`gateway.envoyproxy.io/v1alpha1` 与 `cert-manager.io/v1` 的小版本锁附录 A。

**`deploy/net/gateway.yaml`**（`apiVersion: gateway.networking.k8s.io/v1`，Gateway API 1.x）

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: order-demo-gw
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
spec:
  gatewayClassName: eg
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "order-demo.example.com"
      tls:
        mode: Terminate
        certificateRefs:
          - name: order-demo-tls
            kind: Secret
      allowedRoutes:
        namespaces:
          from: Same
```

> `GatewayClass: eg`、`Gateway` 名 `order-demo-gw` 是 U-05 固定值，不得改写 [R-19-1][R-19-6]。`certificateRefs` 指向 cert-manager 生成的 `order-demo-tls` Secret（见 `certificate.yaml`），私钥不入 Git。

**`deploy/net/httproute.yaml`**（`apiVersion: gateway.networking.k8s.io/v1`，Gateway API 1.x）

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: gateway-route
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
spec:
  parentRefs:
    - name: order-demo-gw
      sectionName: http
    - name: order-demo-gw
      sectionName: https
  hostnames:
    - "order-demo.example.com"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /orders
      timeouts:
        request: 5s
        backendRequest: 4s
      backendRefs:
        - name: gateway
          port: 8080
```

> `HTTPRoute` 名 `gateway-route` 为 U-05 固定值。超时写在这里，是唯一一处请求级超时；`backendRefs` 指向契约里的 `gateway` Service 8080，不绕过 `gateway` 组件 [R-19-1]。

**`deploy/net/backendtrafficpolicy.yaml`**（`apiVersion: gateway.envoyproxy.io/v1alpha1`，Envoy Gateway 1.x）

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
metadata:
  name: gateway-route-policy
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: gateway-route
  retry:
    numRetries: 2
    retryOn:
      - "5xx"
      - "connect-failure"
      - "reset"
    perRetryBackOff:
      baseInterval: 100ms
      maxInterval: 1s
  circuitBreaker:
    maxConnections: 1024
    maxPendingRequests: 256
    maxParallelRequests: 512
    maxParallelRetries: 64
```

> 重试与熔断**只在这一处**配置，Sidecar 与客户端 SDK 禁用重试 [R-19-6][R-19-8]。`gateway.envoyproxy.io/v1alpha1` 是 Envoy Gateway 扩展策略，字段随 1.x 小版本演进，精确取值锁附录 A；部署前用 `kubectl explain backendtrafficpolicy.spec` 校准字段名。

**`deploy/net/networkpolicy-default-deny.yaml`**（`apiVersion: networking.k8s.io/v1`，Kubernetes 1.32+）

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  podSelector: {}
  policyTypes:
    - Ingress
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  podSelector: {}
  policyTypes:
```

> `duration: 2160h`（90 天）、`renewBefore: 360h`（到期前 15 天续期）让有效期成为可观测、可告警的量，而不是人工日历 [R-19-5]。kind 复现取 `selfSigned` Issuer；生产应替换为 ACME 或企业 CA Issuer，替换只改 `issuerRef`，不动 `Gateway`。私钥由 cert-manager 写入 Secret，不入 Git（公理 9，见第 9/26 章）。

**`hack/net-policy-test.sh`**（演示未授权 Pod 无法访问 `db:5432`，可复制执行）

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-dev

echo "== 授权链路：component=api 的 Pod 访问 db:5432 应成功 =="
kubectl -n "${NS}" run net-policy-authorized --rm -i --restart=Never \
  --labels='app.kubernetes.io/name=order-demo,app.kubernetes.io/component=api' \
  --image=busybox:1.36 --command -- sh -c \
  'nc -z -w2 db 5432 && echo "api->db: ALLOWED (expected)" || echo "api->db: BLOCKED (unexpected)"'

echo "== 未授权链路：component=probe 的 Pod 访问 db:5432 应失败 =="
kubectl -n "${NS}" run net-policy-unauthorized --rm -i --restart=Never \
  --labels='app.kubernetes.io/name=order-demo,app.kubernetes.io/component=probe' \
  --image=busybox:1.36 --command -- sh -c \
  'nc -z -w2 db 5432 && echo "UNEXPECTED: reachable" || echo "probe->db: DENIED (expected)"'

echo "== 已生效的策略清单 =="
kubectl -n "${NS}" get networkpolicy
```

> 两个临时 Pod 用同一 `app.kubernetes.io/name`、不同 `component` 标签，只差在白名单是否匹配；`allow-dns` 保证二者都能解析 `db`，因此失败原因可干净地归因到 `db` 的入站策略，而不是 DNS 被拦 [R-19-4]。

**`hack/net-verify.sh`**（入口、路由、证书有效期验证，可复制执行）

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-dev

echo "== GatewayClass 就绪 =="
kubectl get gatewayclass eg

echo "== Gateway / HTTPRoute 状态 =="
kubectl -n "${NS}" get gateway,httproute
kubectl -n "${NS}" get gateway order-demo-gw \
  -o jsonpath='{.status.conditions[?(@.type=="Accepted")].status}{"\n"}'
kubectl -n "${NS}" get httproute gateway-route \
  -o jsonpath='{.status.parents[0].conditions[?(@.type=="Accepted")].status}{"\n"}'

echo "== 证书有效期与续期时间 =="
kubectl -n "${NS}" get certificate order-demo-tls
kubectl -n "${NS}" get certificate order-demo-tls \
  -o jsonpath='{.status.notAfter}{"\t"}{.status.renewalTime}{"\n"}'

echo "== 经 Gateway API 入口访问 /orders =="
GW_SVC=$(kubectl -n envoy-gateway-system get svc -o name 2>/dev/null \
  | grep 'envoy-' | head -1 | cut -d/ -f2 || true)
if [ -z "${GW_SVC}" ]; then
  echo "提示：未探测到 Envoy Gateway 1.x 数据面 Service，可显式设置 GW_SVC 后重跑；对象状态已验证"
else
  kubectl -n envoy-gateway-system port-forward "svc/${GW_SVC}" 8080:80 >/dev/null 2>&1 &
  PF=$!
  trap 'kill "${PF}" 2>/dev/null || true' EXIT
  for i in $(seq 1 20); do
    curl -fsS -H 'Host: order-demo.example.com' \
      http://127.0.0.1:8080/orders >/dev/null 2>&1 && break
    sleep 1
  done
  curl -i -H 'Host: order-demo.example.com' http://127.0.0.1:8080/orders
fi
```

| 重试单层 | 只有 `BackendTrafficPolicy` 配置 `retry`；`HTTPRoute` 无重复重试、客户端/Sidecar 未启用 |
| 应用链路 | `get endpoints` 三者均有就绪地址；`verify.sh` 通过且 `healthz` 为 200 |
