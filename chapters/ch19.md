## 19.1 问题与反模式：三处重试、一次证书过期、一条没人查得动的 DNS

**合成案例**（本书统一采用虚构合成场景，不指向任何真实事故）。团队最早用 Ingress 加一堆 `nginx.ingress.kubernetes.io/*` 注解配超时和重试；后来为了做 mTLS 又加了 Istio Sidecar，客户端 SDK 里本来就有一层重试。于是同一次下游调用被重试了三层：网关 2 次、Sidecar 3 次、SDK 3 次，下游一抖动就放大成 18 次请求，把小故障直接推成重试风暴 [R-19-8]。

先把这个乘法摊开看，因为它比直觉大得多：**2 × 3 × 3 = 18**。每一层的人都在想「我加两次重试，容错好一点」，没有人在想「我加的是乘数」。这是分布式系统里最容易犯的一类错——**加法思维套在乘法结构上**。而它发作的方式也很偏心：平时一次都不重试（一切正常），出事时一次性重试 18 次（把抖动放大成雪崩）。**你只在最不该加压的时刻加压。**同一周还发生了两件事：一张人工续期的证书忘了换，HTTPS 入口全站 502；NetworkPolicy 只给入站加了白名单、没限制出站，一个被入侵的 `worker` 可以直连外部地址。偶发的 `Temporary failure in name resolution` 更让人无从下手——值班分不清该查 CoreDNS、查 Service 的 Endpoint，还是查刚刚收紧的网络策略。网络、DNS 与证书类故障在公开复盘里长期是「定位路径不成文」的重灾区，本章因此把「未授权 Pod 无法访问 `db`」写成可验证动作，并把 DNS 定位路径写成检查项 [R-19-11]。

入口选型的根子在于 **Ingress 已经停止演进**：它只有一个资源、一个角色，路由之外的能力全靠各实现自定义的注解表达，换一个控制器就要重写一遍注解，且应用开发者与运维改的是同一份对象。Gateway API 1.x 是它的继任者，按角色把入口拆成 `GatewayClass`（基础设施提供方）、`Gateway`（运维管监听器与证书）、`HTTPRoute`（应用团队管路由），能力进 `spec` 而不是进注解 [R-19-1][R-19-10]。这三类资源都是 CRD（给 K8s 加一种新资源类型，详见第 27 章）；本章只使用它们，不展开自定义资源的设计。

三个反模式，按「现象 → 根因 → 本章替代做法」拆开：

**反模式一：只给入站加白名单、不限制出站。** 现象是数据外联无约束、被入侵的 Pod 可以直连外部。根因是 NetworkPolicy 的语义是「默认允许、加了策略才拒绝」——只写入站规则时，出站仍是全放行 [R-19-4]。本章的替代做法是显式写**双向默认拒绝基线**（`default-deny-ingress` + `default-deny-egress`），再用组件白名单逐条放通，见 19.4。

**反模式二：重试在网关、Sidecar、客户端各配一遍。** 现象是故障时被放大成重试风暴，且层层都有超时，实际生效的是最短的那个，没人能说清一次调用到底会重试几次。根因是把「可靠性」当成「每一层都兜一下」，忽略了重试是乘法不是加法 [R-19-8][R-19-7]。本章的替代做法是**单层负责**：超时写在 `HTTPRoute` 的 `timeouts`，重试与熔断只写在 Envoy Gateway 1.x 的 `BackendTrafficPolicy` 一处，Sidecar 与客户端禁用重试 [R-19-6]。

这里还有个更隐蔽的坑：**层层都有超时，实际生效的是最短那个。**于是你在一处把超时调到 10 秒，却发现 3 秒就断了，因为上游某个你没注意的地方写着 3 秒。这类配置的失效方式是「静默生效」——它不报错，只是让你的调整不起作用，而你会误以为自己改的地方不对。

**反模式三：证书靠人工续期。** 现象是到期即全站不可用，而且往往发生在节假日。根因是证书有效期是一个会自己走到的死线，人工日历不可靠 [R-19-5]。本章的替代做法是用 cert-manager 1.x 的 `Certificate` 声明 `duration` 与 `renewBefore`，让续期成为控制循环，并把「到期前 N 天未续期」挂成告警（见第 22 章）[R-19-5]。

**写错到底长什么样**。这里最值得对照的不是「少写一条规则」，而是「策略写全了、也合法、却让集群悄悄断网」。差别只有三行：

```diff
 spec:
   podSelector:
     matchLabels: { app: api }
   policyTypes:
   - Ingress
   - Egress
   ingress:
   - from:
     - podSelector: { matchLabels: { app: gateway } }
+  egress:
+  - to:
+    - namespaceSelector:
+        matchLabels: { kubernetes.io/metadata.name: kube-system }
+    ports:
+    - protocol: UDP
+      port: 53
```

后果：`policyTypes` 里写了 `Egress`、却没有一条 egress 规则，语义是**出站全部拒绝**——包括去 CoreDNS 的 53 端口。这份策略完全合法：`apply` 成功、`describe` 无异常、`kubectl get netpol` 显示它老老实实在那儿。症状是 Pod 里所有域名突然解析失败，报 `Temporary failure in name resolution`，正是本章开头那条「查不动」的 DNS。判据：**只要 `policyTypes` 出现 `Egress`，第一件事是放通 DNS**（`kube-system` 的 UDP 53），再按组件逐条加白；顺序反了，你会先花一小时怀疑 CoreDNS，而它一直好好的（[R-19-4]）。

> **一个刻意的边界**：第 6 章的 `gateway` 应用 Service（8080）、`api`（8081）、`db`（5432）是配置契约，本章全部沿用；Gateway API 的 `Gateway` 资源 `order-demo-gw` 是**另一个对象**，由 Envoy Gateway 1.x 创建的数据面 Service 承载，与 `gateway` 应用 Service 不冲突。HTTPRoute 把 `/orders` 路由到 `gateway:8080`，再由 `gateway` 组件转发到 `api:8081`，组件链路不变（见第 6 章）。

## 19.2 范式与决策树：流量治理的每一层各管什么

先把分层钉死，这是「该不该上网格」与「重试放哪」的共同前提。见表 19-1。

这一节存在的唯一理由，是回答一个非常具体的问题：**出故障时，这一条该找谁。**流量问题最难的地方从来不是配置，而是**症状和层之间没有一对一关系**——「502」可能是证书、可能是路由、可能是 Endpoint 为空、可能是上游 Pod 挂了、也可能是 DNS 解析到了旧 IP。所以下面这张表的读法不是「每层能干什么」，而是「**每层坏了会长什么样**」。

表 19-1　流量治理分层（每层只管自己那一段）

| 层 | 资源 / 机制 | 管什么 | 不该管什么 |
|---|---|---|---|
| 集群内发现 | `Service`（ClusterIP，Kubernetes 1.32） | 稳定虚拟 IP、L4 负载均衡、DNS 名 | 七层路由、TLS 终止、重试策略 |
| 南北向入口 | `GatewayClass` / `Gateway` / `HTTPRoute`（Gateway API 1.x） | 入口监听、路由、TLS 终止、请求超时 | 集群内东西向细粒度策略 |
| 网络策略 | `NetworkPolicy`（networking.k8s.io/v1） | L3/L4 允许清单、双向默认拒绝 | 七层鉴权、基于身份的 mTLS |
| 入口扩展策略 | `BackendTrafficPolicy`（Envoy Gateway 1.x） | 重试、熔断、连接池 | 跨服务全链路身份 |
| 服务网格（可选） | Istio 1.x | 东西向 mTLS、细粒度流量、统一遥测 | 只需要一个入口时的简单路由 |
| 证书 | `Certificate`（cert-manager 1.x） | 签发、自动续期 | 流量路由 |

表里的第一层由 `Service`（ClusterIP）提供稳定虚拟 IP 与 L4 负载均衡，Pod 重建后 IP 变化不会让调用方失效 [R-19-2]；它只负责「找得到」，不负责任何七层行为（见第 6 章）。

**唯一示例实现**按本书选型基线与配置契约固定值：`GatewayClass: eg`、`Gateway` 名 `order-demo-gw`、`HTTPRoute` 名 `gateway-route`，数据面为 Envoy Gateway 1.x；**Istio 1.x 只在选型矩阵作对比**，不进入本章任何可应用清单 [R-19-1][R-19-6][R-19-9]。`eg` 这个 GatewayClass 由 Envoy Gateway 1.x 安装时提供，本章只引用、不重复创建——同一示例全书只用一个实现，正是为了避免第 15 章与本章各选一套导致示例跑不通（见第 15 章）。

**超时、重试、熔断、mTLS 的分层结论**：

- **超时**写在离调用方最近且可观测的一层，即 `HTTPRoute.spec.rules[].timeouts`（`request` 总超时、`backendRequest` 后端超时），它是 Gateway API 的 `spec` 字段而非注解，换实现不失效 [R-19-1]。
- **重试与熔断**只在 `BackendTrafficPolicy` 配一次：`retry.numRetries: 2`、`circuitBreaker` 限连接与并发重试。Sidecar 与客户端 SDK 一律不再配重试，否则就是反模式二的乘法放大 [R-19-6][R-19-8]。
- **mTLS** 要分清两种需求。南北向 TLS 终止由 `Gateway` 的 `tls.mode: Terminate` 加 `certificateRefs` 完成，Gateway API 本身就够；而「东西向、基于工作负载身份的全链路 mTLS」需要服务网格（Istio 1.x）或 Envoy Gateway 的 `BackendTLSPolicy` 做上游证书校验 [R-19-7]。本章唯一示例实现不含网格，因此**不启用全链路 mTLS**；是否值得为此引入网格，正是下面决策树要回答的问题，也是第 5 章「工具堆叠」警戒线的具体案例 [R-19-9]。

### 19.2.1 复现实验：三层重试如何放大成 18 次，以及逐层收敛

19.1 合成案例里的「18 次」是乘法，本小节把它变成一次可复现的实验：在唯一示例实现之外搭一套**临时实验对象**，先复现三层叠加的放大倍数，再一层层拆掉，用同一个计数器下游量出每一步的真实请求数。实验对象用完即拆，不进入 19.4 可应用清单、不改任何契约值；Istio 1.x 仅作为「Sidecar 层」的复现载体在实验中出现，这与其「仅在选型矩阵作对比」的口径不冲突 [R-19-7][R-19-8]。

**实验口径**：放大倍数 = 一次用户请求最终到达下游的总尝试次数，三层相乘：SDK 层 3 次 × 网关层 2 次 × Sidecar 层 3 次 = 18 次 [R-19-8]。三层分别由 `curl --retry 2`（SDK 层，最多 3 次尝试）、Envoy Gateway 1.x `BackendTrafficPolicy` 的 `numRetries: 1`（网关层，总尝试 2 次）、Istio 1.x `VirtualService` 的 `retries.attempts: 2`（Sidecar 层；Istio 1.x 口径下 attempts 计重试次数，总尝试 = attempts + 1 = 3 次）承载。合成案例里 Sidecar 层位于 gateway 应用与 api 之间，实验里由 `retry-lab-relay` 这个被注入 Sidecar 的「调用方 Pod」等价承载——重试放大是乘法，只取决于各层次数，不取决于层的位置。字段口径随小版本可能差异，实验一律以计数器实测为准，生产字段用 `kubectl explain` 校准（同 19.4）。

**第 0 步　前提与计数器下游**（要求集群已装 Istio 1.x；无 Istio 的集群可只做 SDK 层与网关层两段）。计数器下游永远返回 503，并把每个到达的请求写进访问日志——它就是「抖动的下游」+「计数器」二合一：

```bash
istioctl install --set profile=minimal -y   # 实验用；生产唯一实现仍是 Envoy Gateway

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: retry-lab-downstream-conf
  namespace: order-demo-dev
data:
  nginx.conf: |
    events {}
    http {
      access_log /dev/stdout;
      error_log /dev/stderr notice;
      server {
        listen 8081;
        location / { return 503; }
      }
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: retry-lab-downstream
  namespace: order-demo-dev
spec:
  replicas: 1
  selector:
    matchLabels: {app: retry-lab-downstream}
  template:
    metadata:
      labels: {app: retry-lab-downstream}
    spec:
      containers:
        - name: downstream
          image: nginx:1.27-alpine
          ports:
            - containerPort: 8081
          volumeMounts:
            - {name: conf, mountPath: /etc/nginx}
      volumes:
        - name: conf
          configMap: {name: retry-lab-downstream-conf}
---
apiVersion: v1
kind: Service
metadata:
  name: retry-lab-downstream
  namespace: order-demo-dev
spec:
  selector: {app: retry-lab-downstream}
  ports:
    - {port: 8081, targetPort: 8081}
EOF
```

验证：`kubectl -n order-demo-dev get pods -l app=retry-lab-downstream` 为 `Running`。

**第 1 步　搭三层链路**。`retry-lab-relay` 是被 Sidecar 注入的「调用方」（等价合成案例里的 gateway 应用 Pod），自身零重试；实验 `HTTPRoute` 复用唯一的 `order-demo-gw`，只新增实验 hostname：

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: retry-lab-relay-conf
  namespace: order-demo-dev
data:
  nginx.conf: |
    events {}
    http {
      server {
        listen 8080;
        location / {
          proxy_pass http://retry-lab-downstream.order-demo-dev.svc.cluster.local:8081;
        }
      }
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: retry-lab-relay
  namespace: order-demo-dev
spec:
  replicas: 1
  selector:
    matchLabels: {app: retry-lab-relay}
  template:
    metadata:
      labels: {app: retry-lab-relay}
      annotations:
        sidecar.istio.io/inject: "true"   # Sidecar 层的载体
    spec:
      containers:
        - name: relay
          image: nginx:1.27-alpine
          ports:
            - containerPort: 8080
          volumeMounts:
            - {name: conf, mountPath: /etc/nginx}
      volumes:
        - name: conf
          configMap: {name: retry-lab-relay-conf}
---
apiVersion: v1
kind: Service
metadata:
  name: retry-lab-relay
  namespace: order-demo-dev
spec:
  selector: {app: retry-lab-relay}
  ports:
    - {port: 8080, targetPort: 8080}
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: retry-lab-route
  namespace: order-demo-dev
spec:
  parentRefs:
    - name: order-demo-gw
      sectionName: http
  hostnames:
    - "retry-lab.example.com"
  rules:
    - matches:
        - path: {type: PathPrefix, value: /orders}
      backendRefs:
        - name: retry-lab-relay
          port: 8080
---
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
metadata:
  name: retry-lab-policy
  namespace: order-demo-dev
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: retry-lab-route
  retry:
    numRetries: 1          # 网关层总尝试 2 次
    retryOn: ["5xx"]
---
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: retry-lab-vs
  namespace: order-demo-dev
spec:
  hosts:
    - "retry-lab-downstream.order-demo-dev.svc.cluster.local"
  http:
    - route:
        - destination: {host: retry-lab-downstream.order-demo-dev.svc.cluster.local}
      retries:
        attempts: 2        # Istio 1.x 口径：总尝试 = attempts + 1 = 3 次
        perTryTimeout: 2s
        retryOn: "gateway-error,connect-failure,reset"
EOF
```

**第 2 步　单个请求实测 18**：

```bash
GW_SVC=$(kubectl -n envoy-gateway-system get svc -o name | grep 'envoy-' | head -1 | cut -d/ -f2)
kubectl -n envoy-gateway-system port-forward "svc/${GW_SVC}" 18080:80 >/dev/null 2>&1 &
PF=$!
sleep 2
cnt() { kubectl -n order-demo-dev logs deploy/retry-lab-downstream --container=downstream 2>/dev/null \
        | grep -c 'GET /orders' || true; }
BEFORE=$(cnt)
curl -s -o /dev/null -w 'user_request_http_code=%{http_code}\n' \
  -H 'Host: retry-lab.example.com' http://127.0.0.1:18080/orders --retry 2
AFTER=$(cnt)
echo "downstream_hits=$((AFTER-BEFORE))"
kill "${PF}" 2>/dev/null || true
```

通过标准：`downstream_hits=18` 且 `user_request_http_code=503`。若所用 Istio 1.x 小版本把 `attempts` 解释为总尝试次数，实测会是 12——无论 18 还是 12，量到的都是乘法，收敛结论不变；把实测值记进复盘。

**第 3 步　压测放大**。故障期间并发 100 个用户请求（每个仍带 SDK 层 3 次尝试）：

```bash
kubectl -n envoy-gateway-system port-forward "svc/${GW_SVC}" 18080:80 >/dev/null 2>&1 &
PF=$!
BEFORE=$(cnt)
seq 1 100 | xargs -P 4 -I{} curl -s -o /dev/null \
  -H 'Host: retry-lab.example.com' http://127.0.0.1:18080/orders --retry 2
AFTER=$(cnt)
echo "downstream_hits=$((AFTER-BEFORE))"   # 通过标准：约 1800（18 × 100）
kill "${PF}" 2>/dev/null || true
```

下游单位时间真正能消化的请求是固定的，放大的 1800 次里绝大多数是重复劳动——这就是把一次小故障推成重试风暴的算术 [R-19-8]。

**第 4 步　逐层收敛**（每步重跑第 2 步的单请求命令，记下 hits）：

```bash
# 摘 Sidecar 层
kubectl -n order-demo-dev patch virtualservice retry-lab-vs --type=json \
  -p='[{"op":"remove","path":"/spec/http/0/retries"}]'
# 网关层恢复单层口径（终态）
kubectl -n order-demo-dev patch backendtrafficpolicy retry-lab-policy --type=json \
  -p='[{"op":"replace","path":"/spec/retry/numRetries","value":2}]'
# 全关对照
kubectl -n order-demo-dev delete backendtrafficpolicy retry-lab-policy
```

| 步骤 | 操作 | 单请求实测 hits |
|---|---|---|
| 0 | 三层全开（基线复现） | 18 |
| 1 | 摘 SDK 层（同一 curl 去掉 `--retry 2`） | 6 |
| 2 | 摘 Sidecar 层 | 2 |
| 3 | 网关层恢复单层口径（终态，`numRetries: 2`） | 3 |
| 4 | 全关对照（删 `BackendTrafficPolicy`） | 1 |

判读：步骤 3 正是 19.4 生产配置的口径——重试只留在网关一层、总尝试 3 次，配合 `circuitBreaker.maxParallelRetries` 给最坏情况限幅；步骤 4 说明「零重试」会把瞬时抖动直接砸给用户，所以收敛目标从来不是「不重试」，而是「单层 + 有界 + 可解释」[R-19-6][R-19-8]。Sidecar 与 SDK 层的重试在 19.4 唯一示例实现中不存在，这正是本实验给出的决策依据。

**第 5 步　拆除实验环境**：

```bash
kubectl -n order-demo-dev delete httproute/retry-lab-route \
  backendtrafficpolicy/retry-lab-policy virtualservice/retry-lab-vs \
  svc/retry-lab-relay svc/retry-lab-downstream \
  deploy/retry-lab-relay deploy/retry-lab-downstream \
  configmap/retry-lab-relay-conf configmap/retry-lab-downstream-conf
kubectl -n order-demo-dev get gateway,httproute | grep -c retry-lab   # 通过标准：0
```

拆除后重跑 19.5 的验证命令并全部通过，确认实验没有污染唯一示例实现。

**DNS 疑难定位路径**（写成可复用的顺序，检查清单 CL-19-05 会考它）：

```
解析失败 / 偶发超时
  → 1. 查 CoreDNS 1.x 自身：kubectl -n kube-system get pods -l k8s-app=kube-dns
  → 2. 查名字与 search 域：kubectl run -it --rm dns-debug --image=busybox:1.36 \
         -- nslookup api.order-demo-dev.svc.cluster.local
         （短名依赖 search 域与 ndots，跨命名空间务必用 FQDN）
  → 3. 查 Service 是否有 Endpoint：kubectl -n order-demo-dev get endpoints api
  → 4. 查 NetworkPolicy 是否放通 DNS：default-deny-egress 下必须显式放行 UDP/53
  → 5. 查目标 Pod 是否 Ready：readiness 失败会从 Endpoint 摘除（见第 8 章）
```
把顺序写死很重要：默认拒绝 egress 之后最先「看起来像 DNS 挂了」的，其实是网络策略没放通 `kube-dns` 的 53 端口 [R-19-3][R-19-4]。本章 19.4 的 `allow-dns` 策略就是为这一步留的口子。

**`ndots`、`search` 域与 DNS 放大疑难**：定位路径第 2 步强调「跨命名空间务必用 FQDN」，背后是一个具体机制。`dnsPolicy: ClusterFirst` 的 Pod 拿到的 `/etc/resolv.conf` 默认是三个 search 域（`<ns>.svc.cluster.local`、`svc.cluster.local`、`cluster.local`）加 `options ndots:5` [R-19-3]：查询名的点数少于 5，就先当「可能是短名」，逐个追加 search 域去试。两个直接后果：

- **外部域名被放大**：`order-demo.example.com` 只有 2 个点，会先被当成短名去试 `order-demo.example.com.order-demo-dev.svc.cluster.local` 等三个不存在的名字，全部 NXDOMAIN 之后才解析成功。每次外部调用白白多 3 次查询，短连接高并发时就是 CoreDNS 1.x 的无谓负载。
- **失败形态是超时不是报错**：CoreDNS 1.x 的 `cache` 插件对成功结果有缓存，但 NXDOMAIN 类结果的缓存行为取决于 `cache` 插件的 denial 配置，默认偏保守——放大量在低峰期被成功缓存掩盖，高峰期以「偶发 `Temporary failure in name resolution` / DNS 超时」的形态暴露，正与 19.1 的现象同源。

**排查与收敛**（机制依据 [R-19-3]；具体取值为本书观点）：

```bash
# 1. 看 Pod 实际生效的 resolv.conf，不要凭记忆假设
kubectl -n order-demo-dev exec deploy/gateway -- cat /etc/resolv.conf
# 通过标准：search 三域 + options ndots:5；不符先查 dnsPolicy/dnsConfig

# 2. 短名与 FQDN 对照：短名依赖 search 域 + ndots 才能命中
kubectl -n order-demo-dev run dns-debug --rm -i --restart=Never --image=busybox:1.36 -- \
  sh -c 'nslookup db.order-demo-dev.svc.cluster.local; nslookup db'
# 通过标准：两条都能解析；裸短名试到第 1 个 search 域才命中，跨命名空间短名会先空跑 1–2 个域
```

收敛三板斧，按侵入性从小到大：① 应用代码对外部域名一律写**带尾点的 FQDN**（`order-demo.example.com.`），一行改动消除 3 次无效查询；② 对确有需要的组件用 `dnsConfig` 显式调低阈值——例如 `ndots: 2`，0 点短名 `api`/`db` 仍走 search 域命中、行为不变，2 点及以上的外部域名则直接当绝对名解析；③ 集群规模上去、CoreDNS 成为瓶颈后再评估 NodeLocal DNSCache，把缓存推到节点级。`dnsConfig` 增量（叠加在 `dnsPolicy: ClusterFirst` 之上，Kubernetes 1.32+）：

```yaml
# gateway Deployment 的 pod template spec 增量
dnsConfig:
  options:
    - name: ndots
      value: "2"
```

验证：`kubectl -n order-demo-dev exec deploy/gateway -- cat /etc/resolv.conf` 应出现 `options ndots:2`；回滚即删除该段、渲染产物 diff 归零（见第 10/14 章）。这也是 DNS 定位路径（CL-19-05）里「短名为什么有时命中不了」的底层原因。

**证书有效期**：cert-manager 1.x 依据 `Certificate.spec.duration` 与 `renewBefore` 自动续期，状态字段 `status.notAfter` 与 `status.renewalTime` 可直接读；`kubectl get certificate` 的 `READY` 必须为 `True`。私钥由控制器写进 Secret（`order-demo-tls`），按全书公理 9 不入 Git [R-19-5]。到期告警与 runbook 见第 22 章。

**「该不该上网格」判定表**：

| 级 | 判据（按序自问） | 命中 → 结论 |
|---|---|---|
| 1 | 需要东西向 mTLS / 细粒度流量策略 / 统一遥测？ | **否** → 不上网格：Gateway API + NetworkPolicy 已够。**是** → 进入第 2 级 |
| 2 | 团队能承担数据面运维成本（注入、升级、资源、排障）？ | **否** → 不上网格：先用 Gateway API 超时 / 重试 + NetworkPolicy。**是** → 进入第 3 级 |
| 3 | 入口实现是否已统一且不与网格冲突？ | **否** → 先按选型基线定唯一入口（eg），再评估。**是** → 上网格；但重试 / 超时仍只在一层配置，不叠三层 |

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：服务网格不是默认项。只有当确实需要 mTLS、细粒度流量策略或统一可观测，且团队能承担数据面运维成本时才值得上。
>
> **论证**：网格解决的是「东西向、跨服务、基于身份」的问题，而一个应用的入口路由、超时、重试、TLS 终止，Gateway API 1.x 加一层 `BackendTrafficPolicy` 就能覆盖，且不需要给每个 Pod 注入 Sidecar。引入网格的代价是实打实的：数据面资源开销、注入与升级的发布节奏、多一层可观测与排障心智。合成案例里的重试风暴不是网格的 bug，而是「三层都配了重试」这一决策缺失的结果——先加网格反而让层数更多、更难说清一次调用到底重试了几次。先把入口与网络策略两层做对，再判断剩下的需求是否真的非网格不可。
>
> **反例与适用前提**：这不等于「永远不上网格」。多团队、多语言、需要统一的 mTLS 身份与跨服务流量策略、且已有平台团队专职维护数据面时，网格的收益会超过成本；合规要求全链路加密的环境也可能把它变成硬要求。本结论的前提是「以单一入口为主的中小规模应用、团队尚无专职平台能力」。第 5 章的工具堆叠警戒线与第 21 章的遥测方案，都是这个判断的配套依据。

### 19.2.2 Gateway API 资源模型：职责边界、所有权与跨命名空间引用

19.1 只交代了「按角色拆成三类资源」，本小节把三件事讲透：每类资源各自管什么、谁有权改它、引用跨了命名空间时护栏在哪。这是排障时「查谁」的前提——入口 503 时，先分清问题出在哪一类资源，再找对应的负责人与 Git 目录。

表 19-1a　Gateway API 三类资源的职责与所有权

| 资源 | 作用域 | 管什么 | 谁拥有 / 谁改 | 生效判据 |
|---|---|---|---|---|
| `GatewayClass` | 集群级 | 声明「存在一类网关实现」；`spec.controllerName` 指向唯一采纳它的控制器 | 基础设施 / 平台团队；本章只引用 `eg`，不创建 | `status.conditions` 中 `Accepted=True` |
| `Gateway` | 命名空间级 | 监听器：端口、协议、TLS 证书、`allowedRoutes` 准入范围 | 运维 / 平台团队 | `Accepted` 与 `Programmed` 均为 `True` |
| `HTTPRoute` | 命名空间级 | hostname 匹配、路径规则、`timeouts`、`backendRefs` | 应用团队（`order-demo` 开发者） | `status.parents[].conditions` 中 `Accepted=True` 且 `ResolvedRefs=True` |

三类资源是三层所有权，角色拆分正是 Gateway API 对 Ingress 的核心修正 [R-19-1][R-19-10]：平台团队改 `Gateway` 不需要应用团队评审；应用团队改 `HTTPRoute` 也摸不到监听器与证书。落到实践是一条纪律：三类对象在 Git 仓库里按角色分目录存放、分别 review（见第 10/14 章），不允许应用团队「顺手」改 `Gateway`。

**一个混合所有权的反模式**：应用团队为了快，直接给 `Gateway` 加一个 listener（新域名加新证书）。现象是证书监听器悄然漂移、`Gateway` 的变更记录里混进了应用侧改动，出了问题没人说得清这张证书谁负责；根因是把三类资源的所有权当成了「谁都能改」；替代做法是应用团队只提 `HTTPRoute`——新 hostname 挂到既有 listener，确需新监听器时由平台侧在 `Gateway` 目录变更并单独 review [R-19-10]。判据：`Gateway` 对象的变更提交者应始终是平台侧，`git log` 可查；这条纪律在第 14 章的 GitOps 晋升里同样成立，谁来改 `Gateway` 不因走不走流水线而松动。

**绑定机制**：`HTTPRoute` 用 `parentRefs` 挂到 `Gateway` 的具体监听器（`sectionName`）；19.4 的 `gateway-route` 同时挂 `http` 与 `https` 两个 listener，所以 `status.parents` 会各出现一条。绑定是否真正生效以 status 为准——Route 对象存在不等于流量走得通：

```bash
kubectl -n order-demo-dev get httproute gateway-route \
  -o jsonpath='{range .status.parents[*]}{.parentRef.name}/{.parentRef.sectionName}{"\t"}{.conditions[*].type}={.conditions[*].status}{"\n"}{end}'
# 通过标准：order-demo-gw/http 与 order-demo-gw/https 各一条，Accepted=True
```

hostname 的匹配规则也要知道：生效主机名 = Route 的 `hostnames` 与 listener 的 `hostname`（若监听器指定了）的交集；两边没有交集时 Route 可能仍是 `Accepted=True` 但 `reason` 为不匹配类原因，流量不会进来——这是「Route 看着正常、域名却 404」的经典误判点，看 conditions 不够，要看 `reason`。同为绑定失败，`reason` 不同处置完全不同：

表 19-1b　HTTPRoute 绑定失败的 `reason` 判读

| `reason` | 含义 | 处置 |
|---|---|---|
| `NoMatchingParent` | 没有任何 listener 接受该 Route | 查 `parentRefs` 的 `name`/`sectionName` 是否拼错、被引用 `Gateway` 是否存在 |
| `NotAllowedByListeners` | listener 的 `allowedRoutes` 不放行本命名空间 | 按下文 allowedRoutes 判据改 `Selector` 或收敛 Route 位置，不要放开 `All` |
| `NoMatchingListenerHostname` | listener 与 Route 的 hostname 无交集 | 对齐 Route `hostnames` 与 listener `hostname` |

```bash
kubectl -n order-demo-dev get httproute gateway-route \
  -o jsonpath='{range .status.parents[*]}{.conditions[*].reason}{"\n"}{end}'
# 通过标准：两条均为 Accepted（无 reason 输出即无失败原因）
```

**allowedRoutes：监听器的准入范围**。`Gateway.spec.listeners[].allowedRoutes` 决定哪些命名空间的 Route 允许挂上来：`from: Same`（默认，仅本命名空间）、`from: Selector`（按命名空间标签选）、`from: All`（全部）。19.4 显式写 `from: Same`，语义与默认一致，写出来的目的是让 review 可见。两条判据：① 面向生产入口的 `Gateway` 禁止 `from: All`，除非有第 25 章准入策略兜底——否则任何租户都能把路由挂到你的证书与域名上；② 确需跨命名空间挂载时用 `Selector` 加目标命名空间标签，而不是放开 `All`：

```yaml
      allowedRoutes:   # 多团队共享入口时的放宽写法（模式示例，非 order-demo 契约）
        namespaces:
          from: Selector
          selector:
            matchLabels:
              gateway-access: order-demo   # 仅打了该标签的命名空间可挂载
```

**跨命名空间引用与 ReferenceGrant**。`allowedRoutes` 管的是「Route 能否挂到 Gateway」，它不管「Route 能否引用别的命名空间的后端」。后者由 `ReferenceGrant` 把关，且 grant 必须创建在**被引用资源所在**的命名空间：它声明的语义是「我授权谁引用我」，而不是「我要引用谁」——方向写反是最常见的误配 [R-19-1]。多团队共享一个入口 Gateway、Route 引用其他团队的 Service 时的模式示例（`order-demo` 唯一实现不需要此对象）：

```yaml
# 多团队共享入口场景的模式示例，不属于 order-demo 配置契约；
# 必须创建在被引用的 Service 所在命名空间
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-order-route-to-service
  namespace: order-backend            # 被引用资源所在命名空间
spec:
  from:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      namespace: platform-ingress     # 发起引用的 Route 所在命名空间
  to:
    - group: ""
      kind: Service
      name: api                       # 尽量写具体 name；不写即放行该组内全部 Service
```

这个护栏的失败形态很阴险：没有 grant 时引用不会报错拒绝，而是 Route 状态变为 `ResolvedRefs=False`、`reason: RefNotPermitted`，请求持续 503，不看 status 完全看不出原因。判据：跨命名空间引用每开一条都要有对应的 grant 对象与 review 记录；`order-demo` 三环境中 Route 与后端同命名空间，保持零 grant 是最省心的默认。

### 19.2.3 重试预算、超时逐层分配与「何时不该重试」

19.2.1 证明了重试是乘法，本小节给出可判定的配置算术：每层超时怎么分配、重试预算怎么算、哪些情形禁止重试。19.4 `BackendTrafficPolicy` 的每个字段都对应这里的一条判据，而不是抄模板。

**超时逐层分配**，自外向内、逐层收紧：

表 19-1c　order-demo 超时逐层分配与判据

| 层 | 超时 | 取值 | 分配判据 |
|---|---|---|---|
| 用户 → 网关 | `HTTPRoute.timeouts.request` | 5s | 最外层兜底，覆盖含重试与退避的全部路径 |
| 网关 → `gateway` 应用 | `timeouts.backendRequest` | 4s | request − 1s：给响应回传与抖动留余量 |
| `gateway` → `api:8081` | 客户端 SDK 请求超时 | ≤ 4s 且禁重试 | 必须 ≤ 上层剩余额度；重试只留网关一层（见 19.2.1） |
| `api` → `db:5432` | SQL 语句超时 | ≤ 2s | 给 api 留出组包与序列化余量 |

判据只有一条：**每层超时必须小于上层的剩余额度**；上层超时天然截断下层的一切重试。

**request 与重试链的算术**是这条判据最容易被忽略的推论：契约取值下，总尝试 3 次 × `backendRequest` 4s + 两轮退避（100ms 起、封顶 1s）≈ 最坏 12.3s，远大于 `request` 5s——第三次尝试几乎必然被 request 超时截断，实际最坏总尝试约 2 次，用户最坏等待 5s。这不是配置错误，而是必须显式做出的取舍：5s 把用户侧尾延迟钉死，代价是 `numRetries: 2` 的第三次尝试形同虚设。判据：希望 N 次尝试完整跑完，则 `request ≥ N × backendRequest + Σ退避`；做不到时，request 就是隐式重试上限——先想清楚要「完整重试」还是「快速失败」，再定数值。本书取「快速失败」：入口是用户等待的第一现场，宁可 5s 返回错误并触发熔断，也不让用户挂到 12s（字段语义 [R-19-6]，取舍为本书观点）。

**重试预算的两个口径** [R-19-8]：

- **单请求口径**：`numRetries: 2` → 最坏 3 次尝试，放大系数 ≤ 3，即下游最坏要承受 3 倍请求量。容量规划若只按 1.2× 正常流量留冗余，这个差额就必须由熔断兜住。
- **集群口径**：`circuitBreaker.maxParallelRetries: 64` 限制的是**同时在途的重试请求**，与 `maxParallelRequests: 512` 约 1/8。判据：重试维度限额必须显著小于总限额——故障期重试挤占正常请求的并发，等于把下游故障转嫁给所有用户；SRE 的自适应重试预算思想是「重试流量占比超阈值即熔」，本章用固定并发上限实现同等效果。

**熔断四维的判读顺序**。19.4 `circuitBreaker` 的四个字段各管一段队列，过载时按此判读，而不是把数值调大了事：`maxConnections`（到上游的 TCP 连接数）→ `maxPendingRequests`（连接满后排队等待的请求数）→ `maxParallelRequests`（同时在途的请求并发）→ `maxParallelRetries`（其中重试请求的并发）。过载时先满连接、再满队列、最后满并发，呈现为网关快速返回 503 而不是整体挂死——这正是熔断「快速失败」的正确形态。定位时看两处：指标 `envoy_cluster_upstream_rq_pending_overflow`（排队溢出计数）与 access log 的 `UO` 响应标志（upstream overflow）。判据：溢出计数增长说明触发的是熔断保护而非后端报错，处置方向是容量与弹性（见第 17/18 章），而不是调大熔断阈值——调大只是把雪崩点推迟 [R-19-6][R-19-8]。

**何时不该加重试**（每条对应 `retryOn` 取值的一个反例）：

| 情形 | 为什么不能重试 | 本章做法 |
|---|---|---|
| 非幂等请求（下单、扣款类 POST） | 超时不代表失败：服务端可能已扣款成功、只是响应没回来，重试就是双扣 | 网关重试只对幂等语义安全的方法开启；非幂等接口靠幂等键与应用层去重，与第 16 章 expand–contract 是同一思想 |
| 下游过载（503 来自过载而非故障） | 重试火上浇油，把「慢」推成「雪崩」 | 靠 `perRetryBackOff` 退避加熔断限并发，而不是盲目重试 [R-19-8] |
| 不可恢复的 4xx | 401/404/422 重试一万次结果相同 | `retryOn` 只含 `5xx`/`connect-failure`/`reset`，天然不含 4xx |
| 长连接 / 流式响应（SSE、gRPC stream） | 请求级重试语义不成立：半途重放等于重新开始 | 入口层不配重试，靠连接层重连与应用层恢复 |
| 错误预算耗尽（见第 20 章） | 重试同时消耗下游容量与错误预算 | 冻结非必要变更，而不是给重试加码 |

**把判据代回 19.1 的合成案例**：三层各配一次重试，逐层套上面的判据——SDK 层 3 次：违反「上层超时截断下层重试」，且 SDK 无法感知熔断与预算，应禁；Sidecar 层 3 次：违反「重试只留一层」与集群口径 1/8 的比例纪律，把放大系数推到 9；网关层 2 次：层的位置正确，但三层叠加后放大到 18。结论不是「三层都错」，而是**判据只允许有一层满足**——把同一套判据拿去审任何一份网关配置，都应得出唯一合法的形态。这也是 19.2.1 收敛表的理论依据。

### 19.2.4 DNS 解析完整链路：Pod → CoreDNS → 上游

19.2 的五步定位路径与 `ndots` 讲了「怎么查」，本小节把链路本身讲全：一次 `nslookup api` 从 Pod 到拿到 A 记录，中间每跳是什么、坏在哪一跳会呈现什么症状。

**「偶发解析失败」为什么最难查**（依同类事故共性还原，非原话）：

> **值班**：`worker` 日志里有 `Temporary failure in name resolution`，一天几次。
> **同事**：CoreDNS 挂了？
> **值班**：`kubectl get pod -n kube-system` 看着都在 Running。
> **同事**：那可能是 Service 没有 Endpoint。
> **值班**：`get endpoints api` 有啊，三个。
> **同事**：……那要不要看看是不是只有 `worker` 有问题？

最后这个反问才是关键的一步，因为前面三轮排查都默认了「**是基础设施坏了**」。而这句报错最会误导人的地方是它听起来像网络问题——它其实只说了一件事：**这次解析没在超时内拿到应答。**超时不等于服务挂了，可能是 CoreDNS 某一跳慢了一拍、可能是 UDP 丢了一个包、可能是 `ndots` 让它在错误的域上白试了几轮、也可能只是那个 Pod 恰好赶上了某个副本的 GC。**这类「偶发」的排查顺序，应该从「谁受影响」开始，而不是从「谁挂了」开始。**

链路四跳：

1. **Pod → kube-dns**：Pod 内 resolver 读 `/etc/resolv.conf`，`nameserver` 指向 `kube-dns` Service 的 ClusterIP，请求以 UDP 为主 [R-19-2][R-19-3]。
2. **kube-dns → CoreDNS Pod**：ClusterIP 经 kube-proxy 均衡到某个 CoreDNS Pod 的 53 端口；默认两个副本，单副本抖动在现象上表现为「偶发、按节点分布」。
3. **CoreDNS 内部**：按 Corefile 依次处理——`kubernetes` 插件对 `cluster.local` 做权威应答（数据来自 watch API Server 的 Service/Endpoint，不查网络）；`cache` 插件缓存成功与 NXDOMAIN 结果；`forward` 插件把其余名字转给节点上游 DNS（云环境为 VPC DNS）。
4. **上游 → 回程**：上游返回后逐跳回到 Pod。

判据：`cluster.local` 内的名字永远不该走到 `forward`——若 CoreDNS 日志出现对 `cluster.local` 名字的转发，说明 `kubernetes` 插件的 zone 配置被改坏，属集群级故障，立即回滚 CoreDNS 的 Corefile。

**症状映射**（坏在哪一跳 → 什么现象 → 怎么确认）：

表 19-1d　DNS 四跳故障的症状与确认命令

| 坏在哪 | 症状 | 确认命令 |
|---|---|---|
| 第 1 跳：Pod 无 resolv.conf / `dnsPolicy` 配错 | 所有域名秒级报错 | `kubectl -n order-demo-dev exec deploy/gateway -- cat /etc/resolv.conf` |
| 第 2 跳：NetworkPolicy 拦 UDP/53 或 `kube-dns` 无 Endpoint | 约五秒超时而非报错 | `kubectl -n kube-system get endpoints kube-dns`（定位路径第 4 步） |
| 第 3 跳：CoreDNS Pod OOM / 重启循环 | 全集群偶发失败、自愈后复发 | `kubectl -n kube-system get pods -l k8s-app=kube-dns` 看 `RESTARTS`；`logs` 找 panic/OOM |
| 第 4 跳：上游 DNS 超时或被拦 | 只有外部域名失败，`cluster.local` 正常 | dns-debug Pod 内、外域名对照（下） |

核心结论：**「内不通、外通」查第 1–3 跳，「外不通、内通」查第 4 跳，「全不通」先查第 1–2 跳**。这一条二分把 19.1 里「分不清该查 CoreDNS 还是查 Endpoint」的困惑收敛成两次对照实验：

```bash
kubectl -n order-demo-dev run dns-split --rm -i --restart=Never --image=busybox:1.36 -- \
  sh -c 'nslookup api.order-demo-dev.svc.cluster.local; nslookup order-demo.example.com.'
# 通过标准：内部名字必通；外部名字不通则问题收敛到第 4 跳（上游）
```

**连接复用与错误码指标**。CoreDNS 对上游默认 UDP、连接随用随建；高 QPS 下大量短连接经 conntrack 做 5 元组 NAT，复用竞争呈现「毫秒级偶发超时」——量级不高时无需处理，先量化再动手：

```bash
kubectl -n kube-system port-forward "$(kubectl -n kube-system get pods -l k8s-app=kube-dns -o name | head -1 | cut -d/ -f2)" 9153:9153 >/dev/null 2>&1 &
PF=$!; sleep 1
curl -s 127.0.0.1:9153/metrics | grep -E '^coredns_(dns_responses_total|forward_requests_total)'
kill "${PF}" 2>/dev/null || true
```

判读：`dns_responses_total` 按 `rcode` 分组——`SERVFAIL` 持续增长指向第 4 跳上游；大量 `NXDOMAIN` 且集中在追加了 search 域后缀的名字上，是 19.2 `ndots:5` 放大问题复发的信号。另有一个传输层细节：UDP 应答超过 512 字节会被截断、客户端转 TCP 重发，若 CoreDNS 日志见 TCP fallback 集中，多半是异常大的记录（如过长的 TXT）进入了解析路径，先查谁写入了这些记录，而不是急着扩容。

**应用侧缓存的陷阱**：链路四跳之外还有半跳——应用进程内的 HTTP 连接池与 DNS 缓存库。它们把解析结果缓存几十秒乃至进程生命周期，症状与 CoreDNS 故障极难区分：扩容或摘除旧 Pod 后，新实例迟迟接不到流量、已删除的旧 Pod 仍有请求打进来。判读：`kubectl -n order-demo-dev get endpoints` 已更新而流量不切，问题就在这半跳；处置是给应用侧缓存设较短 TTL（与第 8/13 章滚动更新的摘流传播时间对齐），而不是反复重启 CoreDNS。

**何时不该动**：不要为了「DNS 有点慢」直接改 `dnsPolicy: Default`——那会绕过 `cluster.local` 解析，Service 短名全部失效，是用可用性换吞吐的错误交易；NodeLocal DNSCache 也只在 19.2 三板斧用尽、CoreDNS 确实成为瓶颈后才评估。CoreDNS 副本数的判据是集群 DNS QPS 而非节点数（本书观点），默认两副本之外先看上面的指标再扩。

### 19.3.1 mTLS 与 Ambient：Envoy Gateway 1.x 与 Istio 1.x 的能力差异与运维成本对照

19.2 已把 mTLS 拆成两种需求（南北向 TLS 终止 / 东西向身份 mTLS）。这一小节把两种实现的能力边界与运维成本摊开，作为「该不该上网格」决策树第 2 步（数据面运维成本）的判据 [R-19-7][R-19-9]。

表 19-2a　mTLS / Ambient 能力对照（Envoy Gateway 1.x vs Istio 1.x）

| 维度 | Envoy Gateway 1.x | Istio 1.x（Sidecar 模式） | Istio 1.x（Ambient 模式） |
|---|---|---|---|
| 证书模型 | 显式声明：`Gateway` listener 证书 + `BackendTLSPolicy` 校验上游 | 自动：istiod 按 SPIFFE 身份签发并轮换（默认 24h） | 同左，由 ztunnel 承担 |
| 南北向客户端证书 | `ClientTrafficPolicy` 可要求并校验客户端证书 | `PeerAuthentication` / `DestinationRule` 配置 | 经 waypoint 配置 |
| 东西向 mTLS | 不覆盖：只保护显式声明的链路，未声明的 Pod-to-Pod 流量仍是明文 | 网格内全量：`PeerAuthentication: STRICT` 按命名空间/全网生效 | 网格内全量：ztunnel 对命名空间/服务账号自动 mTLS |
| L7 能力挂载点 | `BackendTrafficPolicy` 等 CRD 直接挂 Gateway/HTTPRoute | 挂在 Pod 内 proxy | 显式挂 waypoint（L4 与 L7 分离） |
| 策略生效范围 | 仅入口一段 | 全链路（含东西向） | 全链路（含东西向） |

关键差异是**默认行为**：Envoy Gateway 1.x 是「不声明就不保护」，Istio 1.x 是「进了网格默认保护、STRICT 一开全网加密」。这决定了两者不是同类工具的竞争，而是不同安全边界的取舍：前者把 mTLS 当成入口的逐条配置，后者把它当成网格的属性 [R-19-6][R-19-7]。

**Ambient 模式改变的正是成本结构**（ Istio 1.24 起进入 GA）：

- **Sidecar 模式**：每个业务 Pod 多一个 proxy 容器，资源开销与 Pod 数量线性相关；每次网格升级都意味着全量业务 Pod 重注入/重建，发布节奏被网格绑架。
- **Ambient 模式**：数据面拆成 ztunnel（节点级 DaemonSet，只做 L4 mTLS）+ waypoint（按需部署的 L7 代理）；业务 Pod 与数据面解耦，网格升级不再要求业务 Pod 重建，资源开销从「每 Pod 一份」变成「每节点一份 + 按需 waypoint」。代价是新的故障域与排障路径：L4/L7 分离后，「这条流量为什么走了/没走 waypoint」成为新的排查问题 [R-19-7][R-19-9]。

表 19-2b　运维成本对照（相对比例，不给单价；归因口径见第 18 章）

| 成本项 | Envoy Gateway 1.x | Istio Sidecar | Istio Ambient |
|---|---|---|---|
| 初始接入 | 低：装控制器 + 写 Gateway/HTTPRoute | 中：注入标签/注解 + VirtualService/DestinationRule 学习成本 | 中：ambient 命名空间 label + ztunnel/waypoint 概念 |
| 资源开销 | 每集群一份数据面 | 每 Pod 一份 proxy | 每节点 ztunnel + 按需 waypoint |
| 升级成本 | 控制器/数据面滚动升级，业务无感 | 业务 Pod 全量重注入 | istiod/ztunnel/waypoint 各自升级，业务无感 |
| 排障路径 | 入口一段，CRD status 可读 | Pod 内 + 控制面 + CNI 三处 | 组件更多，ztunnel/waypoint 边界需先判 |
| 覆盖缺口 | 未声明的上游链路不保护 | 无（网格内全覆盖） | 无（网格内全覆盖） |

**结论**（呼应 19.2 决策树第 2 步）：如果 mTLS 需求只有「入口这一段 + 显式声明的上游链路」，Envoy Gateway 1.x 的 `BackendTLSPolicy`/`ClientTrafficPolicy` 够用且便宜；如果需求是「全链路、按身份、默认加密」，那是网格的领域——Sidecar 与 Ambient 之间怎么选，主要看团队是否已被「升级即全量重注入」绑架，被绑架就优先评估 Ambient。`order-demo` 的唯一示例实现保持 Envoy Gateway 单层，完整理由见 19.2 的本书观点块 [R-19-6][R-19-7][R-19-9]。

表 19-3　NetworkPolicy 基线（默认拒绝双向 + 组件白名单）

| Ingress | `default-deny-ingress` | 数据面→`gateway:8080`、`gateway`→`api:8081`、`api`→`db:5432` | 未授权 Pod 直连 `db:5432` |

### 19.3.2 Ingress 注解 → Gateway API 字段迁移映射与灰度切流

19.3 的最小 diff 只搬了两条注解；真实的 Ingress 迁移要面对一整张注解清单。映射总原则：**能进 `spec` 的进 `spec`（跨实现可移植），实现专属的进该实现的扩展策略（换实现要重写），无法表达的先明确放弃并记录差异**——不允许把注解原样贴到新实现上碰运气 [R-19-1][R-19-10]。

表 19-4　常用 Ingress 注解 → Gateway API 字段映射（Kubernetes 1.32 + Envoy Gateway 1.x）

| 旧注解（Ingress NGINX 1.x） | 新位置 | 字段 / 写法 | 备注 |
|---|---|---|---|
| `proxy-read-timeout` / `proxy-send-timeout` | `HTTPRoute.spec.rules[].timeouts` | `request` / `backendRequest` | 标准 spec，见 19.4 |
| `proxy-next-upstream-tries` | `BackendTrafficPolicy.spec.retry.numRetries` | Envoy Gateway 1.x 扩展策略 | 重试只此一处（见 19.2.1） |
| `canary-weight` | `HTTPRoute.spec.rules[].backendRefs[].weight` | 标准 spec | 金丝雀接第 15 章 |
| `rewrite-target` | `HTTPRoute.spec.rules[].filters[].urlRewrite` | 标准 filter | 路径重写进 spec |
| `force-ssl-redirect` | `HTTPRoute` 的 `requestRedirect` filter（挂在 HTTP listener 的规则上） | 标准 filter | HTTP→HTTPS 跳转 |
| `ssl-passthrough` | `Gateway.spec.listeners[].tls.mode: Passthrough` | 标准 spec | TLS 终止点后移，证书由后端持有 |
| `whitelist-source-range` | 无标准等价 | 下沉：NetworkPolicy 限来源 + 第 25 章准入策略 | 不再当入口注解 |
| `proxy-body-size` | 视实现扩展策略而定 | 先在 Envoy Gateway 1.x 文档确认等价字段；无等价则回应用层校验 | 迁移差异显式记录，不得静默丢失 |

**灰度切流步骤**（与下面的升级/回滚路径衔接，每步都有通过标准与回退动作）：

1. **影子验证**：`Gateway`/`HTTPRoute` 用独立 hostname（如 `order-demo-canary.example.com`）上线，业务 DNS 不动。通过标准：`net-verify.sh` 对新 hostname 返回 200，且 `Accepted`/`Programmed` 均为 `True`。
2. **小流量**：DNS 权重记录 5%（或内网 hosts 指向），观察 5xx 与 p99（指标口径见第 20 章）。回退：DNS 权重回 0，分钟级生效。
3. **对半切**：50%。旧 Ingress 必须保留到本步通过为止。
4. **全量 + 拆旧**：100% 后删旧 Ingress 与全部注解。此后的回退只能靠重建 Ingress——这正是第 3 步之前旧 Ingress 不许删的原因。
5. 每步都回 Git（公理 5）：hostname 与权重的变更走渲染产物 diff review，见第 10/14 章。

每步统一通过标准：入口成功率不低于基线、p99 劣化小于 10%、`CL-19-01` 与 `CL-19-04` 不回归。失败处置：回退 DNS 权重；同一批注解两次失败，就把迁移拆成更小的注解批次重走 1–4。

**升级 / 回滚路径**：先并行安装 Envoy Gateway 1.x 并确认 `eg` GatewayClass 就绪 → 再提交 `Gateway` / `HTTPRoute`（与旧 Ingress 用不同 hostname 或路径前缀并存）→ 用 `net-verify.sh` 验证新链路 → 切 DNS / 入口指向 → 最后删旧 Ingress。回滚按逆序，应急时先删 NetworkPolicy 默认拒绝（见 19.5，注意这是**安全降级**），再删 Gateway/HTTPRoute。生产回退按 19.5 走 Git。

### 19.3.3 入口流量可观测性：access log、trace 头透传与指标命名

网关是全链路流量的必经点：第 20 章的 SLI、第 15 章金丝雀的判定指标、第 21 章的分布式追踪，取数的源头都在这一段。本小节把入口层观测的三件套钉死。

**access log**。Envoy Gateway 1.x 数据面的访问日志由 `EnvoyProxy` 资源（`gateway.envoyproxy.io/v1alpha1`）开启，通过 `GatewayClass` 的 `parametersRef` 挂载——它改变的是 `eg` 这一类网关的行为，属**平台层配置**，不放进 `deploy/net/`，但必须入 Git 并走 review（公理 5）。字段随小版本演进，部署前用 `kubectl explain envoyproxy.spec.telemetry` 校准（同 19.4 对扩展策略的口径）[R-19-6]：

```yaml

apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: eg-config
  namespace: envoy-gateway-system
spec:
  telemetry:
    accessLog:
      enable: true
      format: text
      text: |
        [%START_TIME%] "%REQ(:METHOD)% %REQ(:PATH)%" %RESPONSE_CODE% \
        duration=%RESPONSE_DURATION_MS%ms traceparent=%REQ(TRACEPARENT)% x-request-id=%REQ(X-REQUEST-ID)%
      sinks:
        - type: File
          file:
            path: /dev/stdout
```

```bash
# 挂载到 GatewayClass 并验证（本地演练环境）
kubectl patch gatewayclass eg --type=merge -p \
  '{"spec":{"parametersRef":{"group":"gateway.envoyproxy.io","kind":"EnvoyProxy","name":"eg-config","namespace":"envoy-gateway-system"}}}'
POD=$(kubectl -n envoy-gateway-system get pods -o name | grep envoy | head -1)
kubectl -n envoy-gateway-system logs "${POD}" | grep 'GET /orders'
```

通过标准：日志行包含状态码、耗时毫秒数与 `traceparent`/`x-request-id` 两个字段。日志判据是**五要素**：时间、方法与路径、状态码、耗时、request id——缺 request id 的网关日志在排障时无法与后端日志对齐。格式取 text 还是 JSON：text 利于人读、JSON 利于机器收——走下文 OpenTelemetry sink 进 Loki 时用 JSON（`format: json`，字段映射在 `json` 段声明）可省去解析规则，本地演练用 text 即可；判据是日志格式全集群统一、不因组件而异，这是第 21 章统一采集的前提。何时不该全量开：dev 环境低流量下全量访问日志只是无谓成本，按环境分级（dev 只留错误级、prod 全量），采样与集中采集见第 21 章。

**从文件日志到集中采集**（衔接第 21 章）。File sink 只适合本地演练与排障对照；prod 应把 access log 直接发给 OTel Collector（`sinks` 支持 `type: OpenTelemetry`），复用第 21 章的采集管道统一导出到 Loki——避免网关日志与应用日志走两条采集链路（字段随小版本演进，`kubectl explain` 校准；host/port 为示意，对齐第 21 章 Collector 的实际部署）：

```yaml
      # prod：替换上面的 File sink
      sinks:
        - type: OpenTelemetry
          openTelemetry:
            host: otel-collector.observability.svc.cluster.local
            port: 4317
```

判据：网关 access log 与应用日志最终落在同一套查询界面、可用同一 request id 字段检索——做不到就等于回到「网关日志一套、应用日志一套，各查各的」的前链路状态。

**trace 头透传契约**（衔接第 21 章）。三条规则，gateway 组件是执行者：① 收到合法的 W3C `traceparent` 头就**原样透传、绝不重生成**——重生成会打断追踪的父子 span 关系，第 21 章的 Tempo 链路直接断链；② 入口没有该头时由 gateway 组件生成 `traceparent` 与 `X-Request-ID`，并把 `X-Request-ID` 放进响应头回给调用方，让用户报障时可提供；③ gateway、api、worker 的应用日志必须记录同一 request id——链路系统不可用时，按 request id 检索日志是排障的降级路径（见第 21/23 章）。反模式：入口代理改写或剥离 trace 头，各服务日志各记录各的 id，排障只能靠时间戳猜。

**指标命名**。入口层指标是 SLI 的原料（SLI = 成功请求数 / 总请求数，见第 20 章）。Envoy 数据面暴露的 Prometheus 指标带 `envoy_` 前缀，本章用到三族：`envoy_cluster_upstream_rq_total`（按后端集群分组的总请求）、`envoy_cluster_upstream_rq_5xx`（上游 5xx 计数）、`envoy_cluster_upstream_rq_time_bucket`（上游时延直方图，p99 的来源）[R-19-6]。口径判据：SLI 一律从网关的**出口侧**取数——网关视角的 5xx 已包含后端失败的请求，第 15 章金丝雀判定与第 20 章错误预算都复用同一口径，避免「入口报 99.9%、后端报 99.5%」的对账难题。应用自身的业务指标（带 `app.kubernetes.io/component` 标签的 `http_server_requests` 类）在第 21 章统一命名与采集，入口层不重复造轮子。

本地核对三族指标确实存在且按后端分组（指标端点端口随小版本可能变化，以官方文档校准）：

```bash
kubectl -n envoy-gateway-system port-forward \
  "$(kubectl -n envoy-gateway-system get pods -o name | grep envoy | head -1 | cut -d/ -f2)" 19001:19001 >/dev/null 2>&1 &
PF=$!; sleep 1
curl -s 127.0.0.1:19001/metrics \
  | grep -E '^envoy_cluster_(upstream_rq_total|upstream_rq_5xx|upstream_rq_time_bucket)' | head -5
kill "${PF}" 2>/dev/null || true
# 通过标准：能看到按后端集群分组的三族指标行
```
