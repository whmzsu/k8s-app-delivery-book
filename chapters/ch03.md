## 3.1 问题与反模式：当工期、故障压力或历史包袱与原则冲突

原则谁都会说。「产物要可追溯」「配置要分离」「先有回滚再发布」——贴在墙上的时候没有争议。真正的问题是：周五下午要赶一个修复，仓库里还留着上一个时代的 `latest`，SLO 和告警「下周补」，这时哪几条可以让一步，哪几条一步都不能退？

第 1 章事故里，H1（`latest` 被覆盖）、H5（没有回滚方案）、H8（告警无 runbook）三条都落在这一章。**声明式终态只保证「按你写的收敛」，不保证「你写的对」**（见第 2 章）；这一章要给出那套「写得对」的默认底线。官方文档把配置、镜像、密钥的最佳实践分散在若干页里 [R-03-2]，但「一次变更的默认底线」需要被显式列成可判定的清单。

三个高频反模式（现象 → 根因 → 本章替代做法）：

**反模式一：每个环境各构建一次「测试包」。** 现象是「dev 测过了，prod 上线还是出问题」，一查两个环境跑的根本不是同一份产物。根因是把「构建」当成了每个环境的准备步骤——**构建 build** 的白话是「由某个源码提交生成唯一不可变制品的过程，带 git SHA 标识」（正式定义详见第 6 章），它应该只发生一次。本章的替代做法是 **build once / promote**：一次构建产出唯一制品，跨环境**晋升 promote** 时只改配置、不改产物 [R-03-6]。

**反模式二：用 `latest` + `imagePullPolicy: Always` 图省事。** 现象是节点间版本不一致、故障复盘答不出「出事的是哪次提交」、回滚没有确定目标。根因是把可变标签当成了版本：`latest` 只是指针，同一标签在不同节点、不同时间可能指向不同层，节点缓存还会让集群里同时存在两个「最新版」[R-03-2]。**不可变镜像**的白话是「一旦推送不再修改，标签与内容一一对应」（正式定义详见第 6 章）；本章的替代做法是固定 `git-<sha7>` 标签，并把 SHA 同时写进 Pod 标签与响应内容。

**反模式三：「先上线，SLO 和告警下周补」。** 现象是出事时没有判定标准，只能靠人肉判断「是不是该回滚」，告警阈值是拍脑袋定的。根因是把观测当作发布之后的补遗，而不是发布的前置判据 [R-03-7]。本章的替代做法是给出 **1 页最小 SLO 卡片**（3.4），让「发布冻结」从第一天就有可填写的判据；SLO 的正式体系到**第 20 章**才展开，这里只给白话与占位模板，不拿它当推理前提。

> 一句话回答本章核心问题：**当工期、故障压力或历史包袱与原则冲突时，这七条默认一步不退；确需让步，必须写明前提、补偿措施与有效期，走 3.2 的「例外机制」**。

## 3.2 范式与决策树：七条主线公理与「越线」的判定

先把本书在第 1 章 1.5 首次亮相的**七条主线公理**展开成可判定的速查表。表中「越线的可观察现象」一律是能敲命令看出来的，不是感觉。

> **全书不可协商项共 9 条**＝本表 **7 条主线公理**＋下方 **2 条衍生护栏**。衍生护栏由主线公理派生（8 由公理 5 的排障侧推出、9 由公理 3 的凭据侧推出），与主线公理**同等不可协商**，只是落地章不在本章、故单列。计数口径与本章 3.2 的公理表一致，全书不得出现「七条」与「九条」混用。

| # | 公理 | 一句话 | 越线的可观察现象 | 对应落地章 |
|---|---|---|---|---|
| 1 | build once, promote | 同一制品跨环境晋升，不为每个环境重新构建 | dev / staging / prod 的 image 字段 SHA 不同 | 6、12、14 |
| 2 | 不可变镜像 + git SHA 标签 | 禁用 `latest`，标签与内容一一对应 | `kubectl get deploy -o jsonpath='{..image}'` 出现 `latest` [R-03-2] | 6、12、24 |
| 3 | 配置与镜像分离 | 环境差异只体现在配置，不体现在产物 | 改一个参数要重建镜像；镜像里硬编码环境值 [R-03-5] | 9、10 |
| 4 | 非 root 最小镜像 | 默认以非 root 运行 | `securityContext` 缺 `runAsNonRoot: true`、镜像以 root 启动 [R-03-4] | 6、25 |
| 5 | Git 为唯一真相 | 生产变更只允许走 Git，禁止手工 `kubectl edit` 改生产 | 审计日志里出现针对生产的手工变更 [R-03-1] | 14、26 |
| 6 | 回滚方案先行 | 没有验证过的回滚方案，不允许发布 | staging 找不出一次带时限、带验证结果的回滚演练 [R-03-7] | 13、16 |
| 7 | SLO 先行于告警 | 先有 SLO 与错误预算，再据此设计告警 | 告警阈值无 SLI / 无窗口 / 无冻结规则 [R-03-7] | 20、22 |

**衍生护栏（2 条，由主线公理派生，与七条主线公理同等不可协商）**：

| # | 衍生护栏 | 派生自 | 落地章 |
|---|---|---|---|
| 8 | SSH 禁入生产：排障走可观测与 runbook，不登机器 | 公理 5（Git 为唯一真相）的排障侧约束 | 23 |
| 9 | 密钥、Terraform state、`.env` 一律不入 Git | 公理 3（配置与镜像分离）的凭据侧约束 | 4、26 |

> 这 2 条不进上面的主线速查表，是因为它们的「越线现象」不是单条变更能敲命令直接看出的，而是组织与工程纪律；但任何章节给出的建议都不得与它们冲突，违反时同样必须走 3.2 的「例外机制」。

**晋升 promote 的正式定义**（本章是它的定义章）：把**已构建的同一制品**逐级送到不同环境，只改配置不改产物。它的可验证判据是：三环境 `image` 字段完全相同（同为 `registry.example.com/order-demo/gateway:git-<sha7>`），差异只出现在 ConfigMap / overlay 的配置项里。这与「重新打包发到生产」「推到仓库就叫发布」严格区分；**回滚 rollback** 则是把线上恢复到上一个已知良好版本（正式定义详见第 13 章），不等于「修一下再发一版」，也不等于数据回退。

公理 3 里的「密钥不入 Git」由官方 `Secret` 语义支撑：Secret 与 ConfigMap 是两类对象，凭据应走外部注入而非明文清单 [R-03-3]；具体注入方案在第 9 章，每环境独立凭据的地形在第 4 章。公理 7 涉及的 **SLI**（白话：可直接测量的好坏比例，如成功请求数 / 总请求数）与**错误预算**（白话：在一个窗口内允许不可用的额度；耗尽则冻结非必要发布）都在**第 20 章**正式定义，本章不得用它们推导告警阈值或发布结论。

由速查表直接得到一棵决策树，用来对任意一次变更快速判定「是否越线」：

```
这次改动让产物变了吗（重建镜像 / 换标签 / 硬编码环境值）？
        是 → 违反公理 1/2/3，改配置而不是改产物（3.4）
        │ 否
production 的变更来自 Git 声明吗？
        否 → 违反公理 5，回第 14 章堵手工入口
        │ 是
发布前在 staging 演练过回滚方案吗？
        否 → 违反公理 6，禁止发布（见第 13 章）
        │ 是
告警有 SLO / 错误预算作依据吗（正式定义详见第 20 章）？
        否 → 违反公理 7，回第 20 章
        │ 是
→ 未越线；确需破例，走「例外机制」登记，不得默认放行
```

> **本书观点（本章第 1 条主张，不需要外部背书）**
>
> **主张**：这七条是「默认不可协商」；例外必须写明**前提、补偿措施与有效期**，临时的让步不能变成长期事实。
>
> **论证**：公理的价值在于「默认不讨论」。如果每次赶工都能口头绕过，团队很快会分不清「哪次是经批准的例外、哪次是偷懒」，事故复盘也失去基线。把例外落成一条带有效期的登记，等于给让步装了到期自动失效的开关：到期后要么续期并重新论证，要么回到默认（3.5 的回滚动作就是「删除例外登记、恢复基线」）。
>
> **反例与适用前提**：这不等于「任何场景都不能临时破例」。本地 kind 一次性实验、无真实流量的灾备演练，本来就不在公理约束范围内（也不构成例外）。前提是**存在需要多人协作、跨环境晋升的生产变更**；第 31 章的反模式速查会收录「例外忘了到期」这类典型退化。例外登记表模板见 3.4。

### 3.2.1 破例的真实代价复盘：九条不可协商项各一段

> 本节是 3.2「例外机制」的代价侧论证：每破一条公理一次，组织就临时失去一项默认能力。以下场景均标注「合成案例」，用于量化代价，非真实事件。计数口径与全书一致，为「7 主线 + 2 衍生护栏 = 9 条不可协商项」。

**公理 1｜build once, promote。** 合成案例：某电商大促前为修一个 prod 专属缺陷，单独给生产构建了一份 `git-prod-hotfix` 镜像，dev 与 staging 仍是 `git-1a2b3c4`。上线后 prod 出现只在生产复现的空指针，dev 环境怎么也复现不出。根因是把「构建」当成了按环境准备的步骤，产物不再唯一。代价有三：其一，排障无从下手，三位工程师跨三天才靠逐行比对猜出差异来自多构建；其二，事故复盘答不出「prod 此刻跑的到底是哪份代码」，事后审计失去基线；其三，回滚目标 `git-1a2b3c4` 早已不是线上版本，所谓「回滚」反而把流量切到了一个未被验证过的旧构建。补偿：立即销毁 `git-prod-hotfix`，把修复合回主干以同一 SHA 重新走晋升，并在 CI 加「三环境 image 字段 SHA 必须一致」关卡（见第 11、12 章）。破这条公理的代价本质是「可追溯性归零」——而可追溯是回滚、审计、演练一切动作的前提 [R-03-6]。

**公理 2｜不可变镜像 + git SHA 标签。** 合成案例：某服务长期用 `latest` + `imagePullPolicy: Always`。一次节点池扩容后，新节点拉到的 `latest` 已是三天后的新层，旧节点仍是旧层，集群里同时存在两个「最新版」。一次线上报错，没人能答出「出事的是哪次提交」，回滚更没有确定目标——`latest` 永远指向「现在」，不像 `git-<sha7>` 那样锁定内容。根因是把可变标签当成了版本：`latest` 只是指针，节点缓存与拉取时机都会让同标签指向不同层 [R-03-2]。代价：故障复盘周期从小时级拉长到数天，因为要先反推「到底哪个层是凶手」；灰度与回滚全部失效，因为不存在一个可重复指向的「上一个良好版本」。补偿：立刻给所有镜像打 `git-<sha7>` 标签并把 SHA 同时写进 Pod 标签与响应头 `APP_VERSION`，新节点与旧节点从此指向同一不可变层；不可变镜像的长期兜底由签名验签门禁负责（见第 24 章）。破这条公理的代价是「版本身份丢失」。

**公理 3｜配置与镜像分离。** 合成案例：某团队把数据库地址、特性开关硬编码进 Dockerfile，改一个环境参数就得重新构建镜像。一次 staging 到 prod 的晋升，因为重建了镜像，prod 实际跑的是一份「带 staging 配置残留」的新构建，数据库连接串指向了错误的实例。根因是环境差异被写进了产物，违反「配置与镜像分离」：配置本应只存在于 ConfigMap / overlay，产物保持同一份 [R-03-5]。代价：晋升不再等价于「只改配置」，跨环境的一致性保证彻底失效；一次本应秒级的配置切换变成一次完整重建与重新回归，发布窗口被拖长。更隐蔽的代价是密钥风险——硬编码诱使开发者把凭据也塞进镜像层，而镜像层一旦推送就难以彻底清除（见公理 9）。补偿：把所有环境相关值移出镜像，统一走 ConfigMap（第 9 章起 `immutable: true`）与外部密钥注入（第 9 章），镜像回到单一 `git-<sha7>` [R-03-3]。破这条公理的代价是「晋升语义被破坏 + 凭据泄漏面扩大」。

**公理 4｜非 root 最小镜像。** 合成案例：某容器以 root 启动，并在运行时用 `apt` 装了一个调试包。一次镜像层被供应链投毒，恶意脚本借着 root 权限直接读写宿主机的 `/proc` 与挂载卷，横向移动几乎无阻力。根因是默认没有以非 root 运行，且 `readOnlyRootFilesystem` 未开启，攻击面被不必要地放大 [R-03-4]。代价：单容器失陷迅速升级为宿主机级风险，安全事件从「应用层」跃迁到「集群级」，事件定级与通报范围完全不同；事后取证还要区分「root 带来的额外损伤」与「原本就该有的损伤」，归责困难。补偿：在 `securityContext` 固定 `runAsNonRoot: true`、`allowPrivilegeEscalation: false`、`readOnlyRootFilesystem: true`、`capabilities.drop: ["ALL"]`，并以 `seccompProfile: RuntimeDefault` 收口（见第 25 章策略强制）。破这条公理的代价是「攻击面与定级成本同时放大」。

**公理 5｜Git 为唯一真相。** 合成案例：一次紧急修复，值班工程师直接 `kubectl edit` 改了 prod 的副本数与资源上限，没走 Git。三天后另一位工程师按 Git 里的旧清单 `kubectl apply`，把那次手工改动无声抹掉，线上再次抖动。根因是生产变更离开了 Git 这条唯一真相，集群实际状态与声明状态产生漂移，且没有任何审计轨迹 [R-03-1]。代价：其一，漂移不可见，下一次声明式收敛会把「好的人工修复」也冲掉；其二，事故复盘找不到「是谁、何时、改了什么」，责任与根因都模糊；其三，SSH / 直连改生产的习惯会自然滑向公理 8 被一并破坏。补偿：所有生产变更回到 Git 声明，手工改动视为漂移由 GitOps 控制器纠正（见第 14 章），越权尝试由 RBAC 与审计留痕（见第 26 章）。破这条公理的代价是「真相分裂 + 审计断点」。

**公理 6｜回滚方案先行。** 合成案例：一次常规发布前，团队认为「上次发得挺顺，这次应该也没事」，跳过了 staging 的回滚演练。上线后新版本引发连锁报错，值班慌乱中执行 `kubectl rollout undo`，却因新清单改了数据库迁移方向、旧版本无法兼容而回滚失败。根因是回滚方案没有在发布前验证过——「有方案」不等于「方案能用」[R-03-7]。代价：本可分钟级恢复的故障被拖成数小时的生产中断；更严重的是，回滚失败让团队失去最后的止血手段，只能现场改代码发新版本，又回到违反公理 5 的老路。补偿：发布前必须在 staging 用同一份回滚命令跑一次带时限、带验证结果的演练，并把结果记入 `docs/principles-checklist.md`；数据面回滚另见第 16 章。破这条公理的代价是「止血手段在需要时失效」。

**公理 7｜SLO 先行于告警。** 合成案例：某服务上线时只有一句「可用性要好」的口号，没有量化 SLO。一次依赖超时导致错误率缓慢爬升，告警阈值却拍脑袋设在「5xx > 50%」——等触发时用户早已大面积报错半小时。根因是把观测当成了发布后的补遗，而非发布的前置判据，告警没有 SLI / 窗口 / 错误预算作依据 [R-03-7]。代价：告警要么不响（阈值太松）、要么乱响（阈值太紧），on-call 在噪音中麻木；更致命的是「该不该回滚」没有客观判据，值班只能凭感觉，决策质量随人员经验剧烈波动。补偿：从第一天就用第 3 章的 1 页最小 SLO 卡片填出 SLI、窗口、目标与冻结规则（字段口径见 [R-03-8]，正式体系见第 20 章），让「发布冻结」成为可填写、可判定的动作。破这条公理的代价是「告警失准 + 回滚决策无基线」。

**公理 8（衍生护栏）｜SSH 禁入生产。** 合成案例：prod 出现偶发超时，工程师为「快一点」直接 SSH 登入节点 `docker exec` 进容器改了日志级别与连接池参数，问题暂时缓解。一周后该容器被调度重建，改动丢失，故障复现且无人记得当初改了什么；更糟的是这次直登绕过了所有可观测采样，链路里缺了一段关键证据。根因是把「登机器」当作合法排障手段，破坏了由公理 5 派生的排障侧护栏：排障应走可观测与 runbook，不登机器 [R-03-1]。代价：其一，临时改动不可持久、不可审计、不可复现；其二，直登操作不被观测覆盖，故障证据链断裂，后续 Chaos 演练（见第 23 章）也难还原真实路径；其三，这种习惯会反向侵蚀公理 5。补偿：所有排障走可观测栈与 runbook（见第 21、22、23 章），确需保留的临时调整写成 Git 声明的配置并走发布。破这条护栏的代价是「排障不可复现 + 证据链断裂」。

**公理 9（衍生护栏）｜密钥不入 Git。** 合成案例：某次把包含数据库口令的 `.env` 误提交进 Git 仓库，三个月后才在例行扫描中发现。即便立刻轮换口令，历史提交里仍留着明文，且无法在不改写历史的前提下彻底清除；同时 `Terraform state` 里也含云凭据，被内部镜像仓库间接暴露。根因是把凭据写进了本应只存声明的 Git，违反了由公理 3 派生的凭据侧护栏：密钥、Terraform state、`.env` 一律不入 Git [R-03-3]。代价：凭据泄漏面从「运行集群」扩大到「所有能克隆仓库的人 + 备份 + 派生 fork」，轮换成本与通报范围陡增；即便改用外部注入，历史明文仍需按泄漏事件处置。补偿：凭据走 External Secrets Operator 注入（键名 `order-demo/db-credentials`，Vault 路径 `order-demo/db-credentials` 含 `/`，不得当对象名，见第 9、26 章），Git 只存 `Secret` 引用；`.env` 与 `terraform.tfstate` 加入 `.gitignore` 与预提交扫描（见第 24 章）。破这条护栏的代价是「凭据泄漏面指数级扩大」。

### 3.2.2 公理冲突时的优先级与权衡：紧急止血下的可判定排序

> 九条公理在常态下互不冲突，但在「线上正在报错」的止血窗口会互相挤压。最常见的挤压是公理 5（Git 为唯一真相）与公理 6（回滚方案先行）：回滚要快，而 Git 流程看起来慢。这一节给出可判定的裁决规则，让值班不需要在压力下临场解释原则。

**三条裁决规则（按顺序适用）**

- **规则一（止血优先，但只对「预案内动作」生效）**：正在发生的用户可见故障期间，恢复服务的公理（6 回滚，以及它依赖的公理 2「确定回滚目标」）优先于记录与流程类公理（5 Git 真相、1 build once）。但「止血优先」只覆盖**预案内动作**——发布前已在 staging 验证过的回滚方案、runbook 里登记过的命令。这些方案的原文来自 Git（演练记录、runbook 都入仓），因此执行它们不构成对公理 5 的违反，而是**Git 预授权**。
- **规则二（预案外动作的三条件豁免）**：预案之外的止血动作才是真正的冲突区，满足以下三条才被豁免，缺一即视为违规并走例外追责：① 双人在场（操作人 + 一名确认人，确认人在审计记录中留名）；② 动作可逆（止血结束后能撤销，或能被 GitOps 收敛覆盖）；③ 事后 2 小时内在 Git 补一条说明性 PR，写明改了什么、为什么、影响范围。补 PR 不是补救流程，而是把这次改动重新纳入唯一真相，否则下一次声明式收敛会把它无声抹掉（见 3.2.1 公理 5 案例）[R-03-1]。
- **规则三（止血豁免有清单边界，四类动作永不豁免）**：无论多紧急，以下动作不得以「止血」名义做出：紧急回退用 `latest`——摧毁「上一个已知良好版本」的确定性，等于放弃公理 6 的前提 [R-03-2]；给 prod 单独构建 hotfix 镜像——违反公理 1，正确路径是修复合入主干、一次构建出新 SHA、按晋升走（见 3.2.1 公理 1 案例）[R-03-6]；把凭据写入 Git 或镜像——公理 9 没有紧急条款，宁可走临时外部注入（见第 9 章）；让紧急调试容器以 root 常驻——公理 4，确需临时提权走例外登记 + 到期自动失效。

**常见冲突对裁决表**

| 冲突对 | 裁决 | 一句话理由 |
|---|---|---|
| 公理 6 vs 公理 5（紧急回滚来不及走 Git） | 预案内回滚直接执行（Git 预授权）；预案外回滚先执行、2 小时内补 PR | 回滚的目标版本与方案本身都源自 Git |
| 公理 1 vs 紧急 hotfix | 禁止 prod 专属构建；合入主干走同一 SHA 晋升，staging 至少跑冒烟 + 回滚验证 | 多一份产物，可追溯归零 |
| 公理 3 vs 紧急改参数 | 禁止改产物；走 ConfigMap / 环境变量声明，哪怕慢几分钟 | 环境差异一旦进产物，晋升语义失效 |
| 公理 7 vs 止血期告警噪音 | 允许加临时降噪规则，但必须登记有效期 ≤ 7 天的例外 | 降噪是让步不是新基线 |
| 公理 8 vs「登机器最快」 | 不豁免；排障走可观测与 runbook（见第 21、22、23 章） | 直登动作不被观测覆盖，证据链断裂 |

**止血窗口的开启与关闭判据**：豁免窗口不靠感觉判定。开启 = 用户可见故障且错误率超出 SLO 卡片的预算口径（此处仅作白话判据，SLO / SLI / 错误预算的正式定义见第 20 章）；关闭 = 错误率回到预算内且 3.5 的回滚验证全部通过。窗口关闭后，九条公理立即恢复默认不可协商，规则二豁免过的动作进入补 PR 与例外登记流程。

**适用前提与反例**：本节裁决规则只适用于「多人协作、跨环境晋升的生产止血窗口」。本地 kind 一次性实验、无真实流量的灾备演练，本就不在公理约束范围内，也就不存在「冲突」可言（与 3.2 本书观点的适用前提一致）；把这两类场景硬套进裁决表，反而会让豁免流程变成新的官僚负担。

### 3.2.3 公理落地的组织维度：责任人 × 审计方式 × 处置

> 公理写进 CI 只是「机器侧」的拦截；另一半在组织侧——每条公理要有明确的责任人、周期性的审计方式与违反时的处置动作，否则 CI 漏拦的违例会长期潜伏。下表覆盖全部 9 条不可协商项（7 主线 + 2 衍生护栏）。责任人是**角色**而非具体个人：换人不换责任，交接时把本表作为交接清单。

| # | 公理 / 护栏 | 责任人（角色） | 审计方式（周期） | 违反的可观察信号 | 处置 |
|---|---|---|---|---|---|
| 1 | build once, promote | 应用团队 Tech Lead | 每次晋升时 CI 比对三环境渲染产物 SHA；每季抽查晋升记录 | 三环境 image 字段 SHA 不一致 | 阻断晋升，回 3.4 对齐 SHA [R-03-6] |
| 2 | 不可变镜像 + SHA 标签 | 发布负责人 | 每次合并 CI 扫 image 字段；每月全量清单扫描；仓库侧开启标签不可覆盖 | 出现 `latest` 或同一标签被重复推送 | 拒绝合并；仓库侧重建不可覆盖标签 |
| 3 | 配置与镜像分离 | 应用团队 Tech Lead | conftest 扫描硬编码环境值（每次合并）；季度抽查 Dockerfile | 改一个参数需要重建镜像 | 配置外移 ConfigMap / 外部注入（见第 9 章）[R-03-5] |
| 4 | 非 root 最小镜像 | 安全负责人 | 第 25 章 Kyverno 准入 audit 报表，每周复盘 | audit 模式出现 `runAsNonRoot` 缺失记录 | 修正 securityContext，audit→enforce [R-03-4] |
| 5 | Git 为唯一真相 | 平台负责人 | 第 26 章审计日志周报：生产写操作逐条比对 Git PR | 生产写操作找不到对应 PR | 视为漂移由 GitOps 纠正，责任人补登记（见第 14 章）[R-03-1] |
| 6 | 回滚方案先行 | SRE on-call | 每次发布前查演练记录；每季核查演练覆盖率 | 演练缺失或距上次演练超过 30 天 | 冻结发布直到补演练 [R-03-7] |
| 7 | SLO 先行于告警 | SRE 负责人 | 季度 SLO 卡片评审（正式体系见第 20 章） | 告警阈值无 SLI / 窗口 / 冻结规则依据 | 告警下线，按第 20 章重做 |
| 8 | SSH 禁入生产（衍生护栏） | 安全负责人 | 月度核对生产节点审计日志中的交互式登录会话 | 生产节点出现交互式 SSH 会话 | 回收权限；排障改走 runbook（见第 23 章） |
| 9 | 密钥不入 Git（衍生护栏） | 安全负责人 | 预提交扫描（每次提交）+ 每日仓库历史扫描（见第 24 章） | 扫描器命中凭据模式 | 立即轮换凭据，按泄漏事件处置（见第 26 章）[R-03-3] |

三条使用说明：

- **审计必须产出可归档的证据**（报表、日志、演练记录），不能靠口头确认；没有证据的审计等于没审。
- **本表与 3.3.1 的 CI 映射表是同一公理的两个时间维度**：CI 管「变更进入集群前的机器拦截」（秒级、每次变更），本表管「周期性的人工审计」（周 / 月 / 季，覆盖 CI 漏拦与流程退化）。两表任一发现违例，处置栏是唯一出口，不允许「私下改掉就算了」。
- **信号全部可观察**：与 3.2 速查表口径一致，本表「违反的可观察信号」一列只收能敲命令或导出报表确认的现象，不收「感觉团队纪律变差」这类不可判定的描述。

### 3.3.1 七条公理 × CI 校验关卡映射表

> 公理要「默认不可协商」，就必须在变更进入集群前被机器拦下。下表把七条主线公理映射到 CI 校验关卡；落地工具与版本矩阵见第 11 章（kubeconform / conftest / kuttl + kind 版本矩阵），一次性构建见第 12 章（CI 一次构建产出带 SHA 的镜像）。衍生护栏（公理 8 / 9）的强制更多在准入层（第 25 章）与 Git 预提交扫描（第 24 章），不在本表。

| 公理 | CI 校验关卡 | 工具（详见第 11 / 12 章） | 失败处置 |
|---|---|---|---|
| 1 build once, promote | 三环境 image 字段 SHA 一致 | CI 比对 dev / staging / prod 渲染产物 | 阻断合并，回 3.4 统一 SHA [R-03-6] |
| 2 不可变镜像 + git SHA 标签 | 镜像标签非 `latest`、含 `git-<sha7>` | kubeconform + 正则校验 image 字段 | 拒绝，回 3.4 diff |
| 3 配置与镜像分离 | 镜像内无硬编码环境值 | conftest 策略扫描 | 拒绝，配置外移（见第 9 章）[R-03-5] |
| 4 非 root 最小镜像 | `securityContext.runAsNonRoot: true` 且 `readOnlyRootFilesystem: true` | conftest / 第 25 章 Kyverno 预检 | 拒绝，回 3.4 修正 [R-03-4] |
| 5 Git 为唯一真相 | 变更来自 Git PR，无手工补丁混入 | CI 比对渲染产物与 Git 声明 | 阻断，回第 14 章 [R-03-1] |
| 6 回滚方案先行 | staging 回滚演练记录存在且带时限 | CI 检查演练结果与时限 | 阻断发布（CL-G-07）[R-03-7] |
| 7 SLO 先行于告警 | 最小 SLO 卡片四项填全 | CI 校验 ConfigMap 字段非空 | 阻断，回 3.4 模板 [R-03-8] |

这张表与 3.6 的上线检查清单互为镜像：CI 关卡在网上拦「未提交的错」，清单在发布前拦「人没走的流程」。两者都指向同一条公理，只是关卡位置不同——CI 是「左移的护栏」，清单是「发布前的最后一道签字」。第 11 章会给出把上表前四行落成 conftest 策略的最小写法，第 12 章负责让「一次构建产出唯一 `git-<sha7>` 镜像」成为默认事实，从而让公理 1 / 2 在源头就不会被打破。

```yaml
  labels:
```

> 这张卡片解决 9.7 指出的「SLO 先行」与章序矛盾：正式定义在第 20 章，但发布冻结判据不能等到第 20 章才第一次出现。因此本章只给**可填写的模板**与白话，字段命名 `service / sli / window / objective / freeze_rule` 与第 1 章引出版、第 20 章正式定义保持一致；**此处不定义 SLO、不推导阈值、不用「SLO 不达标」作为不发布的理由**。口径一致性由第 1、3、20 章共同约束 [R-03-8]。

### 3.4.2 最小 SLO 卡片一页说明：SLI 采集点与窗口选择理由

> 本节只把 3.4 的卡片「怎么填、采集点放哪、窗口为什么这么选」讲清楚，仍是白话与占位；SLO / SLI / 错误预算的正式定义见第 20 章，本文档不定义、不推导阈值、不把它当发布决策前提。其字段口径与 [R-03-8] 一致，避免与第 20 章正式体系脱节。

**卡片一页说明（可直接打印贴在值班室）**

- **service**：填 `gateway` / `api` / `worker` / `db` 之一。`order-demo` 对外用户体感集中在 `gateway`（端口 8080）与 `api`（端口 8081），SLO 优先覆盖这两条。
- **sli**：填「成功请求数 / 总请求数」这类可直接测量的好坏比例。注意 SLI 必须「业务可感」——用 CPU 使用率这类业务无感指标充数会被第 20 章判为无效 [R-03-8]。
- **window**：填统计窗口，如 `28d` 或 `7d`（选择理由见下）。
- **objective**：填目标百分比，如 `99.9`。
- **freeze_rule**：填「错误预算耗尽则冻结非必要发布」（错误预算＝窗口内允许不可用的额度，正式定义见第 20 章）。

**SLI 采集点（放哪、采什么）**

- **gateway（8080）**：在 `gateway` 暴露 `/metrics`，由 Prometheus 抓取 HTTP 状态码与时延；SLI 取「2xx/3xx 响应数 ÷ 总请求数」。这是用户体感的第一道门，采集点放网关而非下游。
- **api（8081）**：同样抓 `/metrics` 的 `orders` 读写成功率；若走 OTel，可由第 21 章的 OTel Collector 统一收口指标、日志、链路，避免每组件各埋一套。
- **db（5432）**：SLI 取连接池可用率与慢查询比例，采集点在 PostgreSQL Exporter，而非在应用层硬埋点（避免把观测耦合进业务代码）。
- **worker**：无监听端口，SLI 取「成功处理任务数 ÷ 入队任务数」，由任务队列指标提供；没有请求成功率可采时，用「任务成功率」替代。

**窗口选择理由（白话）**

- 选 `28d`：错误预算按「一个月」摊销更稳，单日抖动不会立刻耗尽预算，适合对外承诺型 SLO；缺点是信号慢，需配合短窗看趋势。
- 选 `7d`：对迭代快、容错低的服务更灵敏，能更早触发发布冻结；缺点是偶发尖峰容易误伤发布节奏。
- 实务上用「长窗定承诺、短窗看趋势」双窗口：长窗算错误预算、短窗给告警提前量。两者口径必须与第 20 章正式体系一致，否则本章卡片填得再满，到第 20 章也会被重新对齐 [R-03-8]。

**`docs/principles-exceptions.md`（例外登记模板，可打印）**


### 3.4.1 例外机制的审批流与到期自动检查脚本

> 例外不是「口头说一声」，而是一条带有效期、可审计、到期自动失效的登记。本节把 3.2 的「例外机制」落成可执行的审批流与脚本，并与第 25 章策略门禁衔接。公理口径仍为「7 主线 + 2 衍生护栏 = 9 条」，任何一条被破例都需走此流程。

**审批流（四步，缺一不可）**

1. **提申请**：发起人在 `docs/principles-exceptions.md` 新增一行 `| EXC-<n> | <公理> | <前提> | <补偿措施> | <有效期至 YYYY-MM-DD> | <责任人> |`。前提必须写清「为什么这次必须破例」，补偿措施写清「破例期间如何兜底」，有效期不得超过 30 天。
2. **双签批**：需要一名同级评审 + 一名本章公理责任人签字；涉及生产变更还需 SRE on-call 轮值确认。七条主线公理的对应 owner 见 3.2 速查表的「对应落地章」。
3. **入仓即生效**：合并进 Git 后，例外才被认可；任何未登记的破例视为违规，按漂移处理（见第 14 章）。
4. **到期处置**：到 `有效期至` 当日，脚本（见下）自动标记到期；要么发起人提交续期 PR 重新论证，要么执行 3.5 回滚步骤恢复基线，不得「默默继续」。

**与第 25 章策略门禁的衔接**：第 25 章用 Kyverno 1.x 在准入层拦截特权容器、缺失 `runAsNonRoot` 等违例（对应公理 4）。例外机制可与之对接——把「已登记且未过期的 EXC 行」作为策略的豁免来源：Kyverno `ClusterPolicy` 在放行前先查例外登记表，过期或未登记的破例一律拒绝。这样「原则不可协商」既在文档层（本章）也在准入层（第 25 章）被强制执行，两层互为备份 [R-03-4]。注意：豁免只缩小准入拦截范围，不豁免公理 5（生产变更仍须来自 Git）与公理 9（凭据仍不入 Git）。

**到期自动检查脚本（可复制，本地或 CI 定时跑）**

```bash
#!/usr/bin/env bash
# check-exceptions.sh —— 扫描 docs/principles-exceptions.md 中过期的 EXC 行
# 用法：./check-exceptions.sh [今天 YYYY-MM-DD，缺省取 UTC 今日]
set -euo pipefail
TODAY="${1:-$(date -u +%Y-%m-%d)}"
REG="docs/principles-exceptions.md"
EXIT=0
echo "== 例外到期检查 @ ${TODAY} =="
while IFS='|' read -r _ id axiom premise comp until owner; do
  id="$(echo "$id" | tr -d ' ')"; until="$(echo "$until" | tr -d ' ')"; owner="$(echo "$owner" | tr -d ' ')"
  [ -z "$id" ] && continue
  case "$id" in EXC-*) ;; *) continue ;; esac
  if [[ "$until" < "$TODAY" ]]; then
    echo "❌ 过期例外 ${id}（公理 ${axiom}，责任人 ${owner}，应于 ${until} 前处置）"
    EXIT=1
  else
    echo "✅ 有效例外 ${id}（公理 ${axiom}，至 ${until}）"
  fi
done < <(grep '^| EXC-' "$REG")
[ "$EXIT" -eq 0 ] && echo "全部例外在有效期内" || echo "存在过期例外，请续期或执行 3.5 回滚"
exit $EXIT
```

**验证命令与通过标准**：

```bash
# 注入一条已过期例外后跑脚本，应退出码非 0
printf '| EXC-1 | 公理4 | 调试需要 | 限定命名空间 | 2026-01-01 | alice |\n' >> docs/principles-exceptions.md
./check-exceptions.sh 2026-11-11
echo "退出码应为 1（检测到过期）"
# 清理测试行，恢复登记表（见 3.5 回滚步骤 2）
git checkout ch03-principles -- docs/principles-exceptions.md
```

通过标准：脚本退出码 0 表示无过期；非 0 时列出需处置的 `EXC-` 行。可挂到 CI 每日定时任务（见第 12 章）或作为第 25 章门禁前的预检，过期即阻断合并。该脚本不修改任何集群资源、不触碰配置契约，仅读取 Markdown 登记表，安全项 `CL-S-01` / `CL-S-04` 不受影响。

**CI 拦截未登记例外：违例 × 例外登记对账脚本**

前文讲了「例外怎么登记、怎么到期」，还差最后一环：**未登记的破例如何在 CI 被机器拦下**。机制是「对账」：CI 的策略扫描（conftest / Kyverno 预检，工具与版本矩阵见第 11、25 章）报出违例后不直接失败，而是把每条违例与 `docs/principles-exceptions.md` 对账——存在一行**未过期、且公理编号匹配**的 EXC 登记才算豁免，并在日志中打印豁免来源；否则 CI 失败，逼发起人要么修正违例本身，要么走双签补登记。这样「例外必须显式登记」从纪律变成机器强制，与到期检查脚本、第 25 章准入门禁构成三层兜底 [R-03-4]。

对账规则四条：

1. 豁免按「公理编号 + 对象」精确匹配，补偿措施栏必须写明豁免仅限的对象范围（如「仅限 gateway 的 staging 灰度期」）；
2. 过期例外不豁免——对账前先跑 3.4.1 的到期检查脚本，存在过期行即整体失败；
3. 公理 5 与公理 9 **不可豁免**：生产变更来自 Git、凭据不入 Git 没有例外条款；
4. 豁免命中必须在 CI 日志打印 `EXC-<n>` 编号，供 3.2.3 的周期审计回溯。

```bash
#!/usr/bin/env bash
# check-exception-coverage.sh —— CI 违例 × 例外登记对账
# 输入：violations.txt，每行格式 VIOLATION|<公理编号>|<对象描述>（由 conftest 输出转换生成）
# 用法：./check-exception-coverage.sh violations.txt [今天 YYYY-MM-DD，缺省取 UTC 今日]
set -euo pipefail
VIOL="${1:?用法: check-exception-coverage.sh violations.txt [YYYY-MM-DD]}"
TODAY="${2:-$(date -u +%Y-%m-%d)}"
REG="docs/principles-exceptions.md"
EXIT=0
while IFS= read -r line; do
  [ -z "$line" ] && continue
  axiom="$(echo "$line" | cut -d'|' -f2 | tr -d ' ')"
  obj="$(echo "$line" | cut -d'|' -f3 | tr -d ' ')"
  hit=""; hit_until=""
  while IFS='|' read -r _ id exc_axiom _ _ until _; do
    id="$(echo "$id" | tr -d ' ')"; exc_axiom="$(echo "$exc_axiom" | tr -d ' ')"; until="$(echo "$until" | tr -d ' ')"
    case "$id" in EXC-*) ;; *) continue ;; esac
    if [ "$exc_axiom" = "$axiom" ] && [ ! "$until" \< "$TODAY" ]; then hit="$id"; hit_until="$until"; break; fi
  done < <(grep '^| EXC-' "$REG")
  if [ -n "$hit" ]; then
    echo "✅ 违例 [${obj}]（公理 ${axiom}）由例外 ${hit} 豁免，有效期至 ${hit_until}"
  else
    echo "❌ 未登记例外：[${obj}]（公理 ${axiom}）——修正违例，或走双签补 EXC 登记"
    EXIT=1
  fi
done < "$VIOL"
exit $EXIT
```

**验证命令与通过标准**：

```bash
# 造两条违例：一条已被登记豁免（公理 4，未过期），一条未登记
printf 'VIOLATION|公理4|deployment/gateway(order-demo-staging): runAsNonRoot 缺失\n' > /tmp/violations.txt
printf 'VIOLATION|公理4|deployment/worker(order-demo-staging): readOnlyRootFilesystem 缺失\n' >> /tmp/violations.txt
printf '| EXC-2 | 公理4 | 灰度期调试需要 | 豁免仅限 gateway | 2027-01-01 | alice |\n' >> docs/principles-exceptions.md
./check-exception-coverage.sh /tmp/violations.txt 2026-11-11
echo "退出码应为 1（worker 一条未登记）"
# 删除未登记的那条再跑，应全部豁免、退出码 0
grep -v 'worker' /tmp/violations.txt > /tmp/violations-2.txt
./check-exception-coverage.sh /tmp/violations-2.txt 2026-11-11
echo "退出码应为 0（gateway 由 EXC-2 豁免）"
# 清理测试行，恢复登记表（见 3.5 回滚步骤 2）
git checkout ch03-principles -- docs/principles-exceptions.md
```

通过标准：未登记的违例使 CI 失败并列出对象；已登记且未过期的违例放行、日志含 `EXC-` 编号；过期登记一律不放行。脚本只读登记表与违例清单，不触碰集群资源与配置契约。第 11 章给出把 conftest 原始输出转换为 `VIOLATION|公理|对象` 行的最小写法，第 25 章的 Kyverno 准入门禁复用同一张登记表作为豁免来源。
