## 3.1 问题与反模式：当工期、故障压力或历史包袱与原则冲突

原则谁都会说。「产物要可追溯」「配置要分离」「先有回滚再发布」——贴在墙上的时候没有争议。真正的问题是：周五下午要赶一个修复，仓库里还留着上一个时代的 `latest`，SLO 和告警「下周补」，这时哪几条可以让一步，哪几条一步都不能退？

第 1 章事故里，H1（`latest` 被覆盖）、H5（没有回滚方案）、H8（告警无 runbook）三条都落在这一章。**声明式终态只保证「按你写的收敛」，不保证「你写的对」**（见第 2 章）；这一章要给出那套「写得对」的默认底线。官方文档把配置、镜像、密钥的最佳实践分散在若干页里 [R-03-2]，但「一次变更的默认底线」需要被显式列成可判定的清单。

三个高频反模式（现象 → 根因 → 本章替代做法）：

**反模式一：每个环境各构建一次「测试包」。** 现象是「dev 测过了，prod 上线还是出问题」，一查两个环境跑的根本不是同一份产物。根因是把「构建」当成了每个环境的准备步骤——**构建 build** 的白话是「由某个源码提交生成唯一不可变制品的过程，带 git SHA 标识」（正式定义详见第 6 章），它应该只发生一次。本章的替代做法是 **build once / promote**：一次构建产出唯一制品，跨环境**晋升 promote** 时只改配置、不改产物 [R-03-6]。

**反模式二：用 `latest` + `imagePullPolicy: Always` 图省事。** 现象是节点间版本不一致、故障复盘答不出「出事的是哪次提交」、回滚没有确定目标。根因是把可变标签当成了版本：`latest` 只是指针，同一标签在不同节点、不同时间可能指向不同层，节点缓存还会让集群里同时存在两个「最新版」[R-03-2]。**不可变镜像**的白话是「一旦推送不再修改，标签与内容一一对应」（正式定义详见第 6 章）；本章的替代做法是固定 `git-<sha7>` 标签，并把 SHA 同时写进 Pod 标签与响应内容。

**反模式三：「先上线，SLO 和告警下周补」。** 现象是出事时没有判定标准，只能靠人肉判断「是不是该回滚」，告警阈值是拍脑袋定的。根因是把观测当作发布之后的补遗，而不是发布的前置判据 [R-03-7]。本章的替代做法是给出 **1 页最小 SLO 卡片**（3.4），让「发布冻结」从第一天就有可填写的判据；SLO 的正式体系到**第 20 章**才展开，这里只给白话与占位模板，不拿它当推理前提。

> 一句话回答本章核心问题：**当工期、故障压力或历史包袱与原则冲突时，这七条默认一步不退；确需让步，必须写明前提、补偿措施与有效期，走 3.2 的「例外机制」**。

## 3.2 范式与决策树：七条主线公理与「越线」的判定

先把本书在第 1 章 1.5 首次亮相的**七条主线公理**展开成可判定的速查表。表中「越线的可观察现象」一律是能敲命令看出来的，不是感觉。

> **全书不可协商项共 9 条**＝本表 **7 条主线公理**＋下方 **2 条衍生护栏**。衍生护栏由主线公理派生（8 由公理 5 的排障侧推出、9 由公理 3 的凭据侧推出），与主线公理**同等不可协商**，只是落地章不在本章、故单列。计数口径与 `glossary.md` 第二节一致，全书不得出现「七条」与「九条」混用。

| # | 公理 | 一句话 | 越线的可观察现象 | 对应落地章 |
|---|---|---|---|---|
| 1 | build once, promote | 同一制品跨环境晋升，不为每个环境重新构建 | dev / staging / prod 的 image 字段 SHA 不同 | 6、12、14 |
| 2 | 不可变镜像 + git SHA 标签 | 禁用 `latest`，标签与内容一一对应 | `kubectl get deploy -o jsonpath='{..image}'` 出现 `latest` [R-03-2] | 6、12、24 |
| 3 | 配置与镜像分离 | 环境差异只体现在配置，不体现在产物 | 改一个参数要重建镜像；镜像里硬编码环境值 [R-03-5] | 9、10 |
| 4 | 非 root 最小镜像 | 默认以非 root 运行 | `securityContext` 缺 `runAsNonRoot: true`、镜像以 root 启动 [R-03-4] | 6、25 |
| 5 | Git 为唯一真相 | 生产变更只允许走 Git，禁止手工 `kubectl edit` 改生产 | 审计日志里出现针对生产的手工变更 [R-03-1] | 14、26 |
| 6 | 回滚方案先行 | 没有验证过的回滚方案，不允许发布 | staging 找不出一次带时限、带验证结果的回滚演练 [R-03-7] | 13、16 |
| 7 | SLO 先行于告警 | 先有 SLO 与错误预算，再据此设计告警 | 告警阈值无 SLI / 无窗口 / 无冻结规则 [R-03-7] | 20、22 |

**衍生护栏（2 条，由主线公理派生，与七条主线公理同等不可协商）**：

| # | 衍生护栏 | 派生自 | 落地章 |
|---|---|---|---|
| 8 | SSH 禁入生产：排障走可观测与 runbook，不登机器 | 公理 5（Git 为唯一真相）的排障侧约束 | 23 |
| 9 | 密钥、Terraform state、`.env` 一律不入 Git | 公理 3（配置与镜像分离）的凭据侧约束 | 4、26 |

> 这 2 条不进上面的主线速查表，是因为它们的「越线现象」不是单条变更能敲命令直接看出的，而是组织与工程纪律；但任何章节给出的建议都不得与它们冲突，违反时同样必须走 3.2 的「例外机制」。

**晋升 promote 的正式定义**（本章是它的定义章）：把**已构建的同一制品**逐级送到不同环境，只改配置不改产物。它的可验证判据是：三环境 `image` 字段完全相同（同为 `registry.example.com/order-demo/gateway:git-<sha7>`），差异只出现在 ConfigMap / overlay 的配置项里。这与「重新打包发到生产」「推到仓库就叫发布」严格区分；**回滚 rollback** 则是把线上恢复到上一个已知良好版本（正式定义详见第 13 章），不等于「修一下再发一版」，也不等于数据回退。

公理 3 里的「密钥不入 Git」由官方 `Secret` 语义支撑：Secret 与 ConfigMap 是两类对象，凭据应走外部注入而非明文清单 [R-03-3]；具体注入方案在第 9 章，每环境独立凭据的地形在第 4 章。公理 7 涉及的 **SLI**（白话：可直接测量的好坏比例，如成功请求数 / 总请求数）与**错误预算**（白话：在一个窗口内允许不可用的额度；耗尽则冻结非必要发布）都在**第 20 章**正式定义，本章不得用它们推导告警阈值或发布结论。

由速查表直接得到一棵决策树，用来对任意一次变更快速判定「是否越线」：

```
这次改动让产物变了吗（重建镜像 / 换标签 / 硬编码环境值）？
        是 → 违反公理 1/2/3，改配置而不是改产物（3.4）
        │ 否
production 的变更来自 Git 声明吗？
        否 → 违反公理 5，回第 14 章堵手工入口
        │ 是
发布前在 staging 演练过回滚方案吗？
        否 → 违反公理 6，禁止发布（见第 13 章）
        │ 是
告警有 SLO / 错误预算作依据吗（正式定义详见第 20 章）？
        否 → 违反公理 7，回第 20 章
        │ 是
→ 未越线；确需破例，走「例外机制」登记，不得默认放行
```

> **本书观点（本章第 1 条主张，不需要外部背书）**
>
> **主张**：这七条是「默认不可协商」；例外必须写明**前提、补偿措施与有效期**，临时的让步不能变成长期事实。
>
> **论证**：公理的价值在于「默认不讨论」。如果每次赶工都能口头绕过，团队很快会分不清「哪次是经批准的例外、哪次是偷懒」，事故复盘也失去基线。把例外落成一条带有效期的登记，等于给让步装了到期自动失效的开关：到期后要么续期并重新论证，要么回到默认（3.5 的回滚动作就是「删除例外登记、恢复基线」）。
>
> **反例与适用前提**：这不等于「任何场景都不能临时破例」。本地 kind 一次性实验、无真实流量的灾备演练，本来就不在公理约束范围内（也不构成例外）。前提是**存在需要多人协作、跨环境晋升的生产变更**；第 31 章的反模式速查会收录「例外忘了到期」这类典型退化。例外登记表模板见 3.4。

## 3.3 工具选型：本章刻意不选工具，只提出要求

本章是公理章，产出的是判据而不是流水线，因此**不引入任何新的配置打包 / 交付 / 门禁工具**。按 9.6「不硬凑工具选型矩阵」，这里沿用样板章的笔法：把「本章刻意不用什么、为什么」写清楚即可。第 10 章比较 Helm 3.x / Kustomize 5.x，第 14 章比较 Argo CD 2.x / Flux 2.x，第 24 章落地签名验签门禁，第 25 章落地 Kyverno 1.x 策略。

| 工具 | 本章是否使用 | 何时不该用（与本章相关的一条） |
|---|---|---|
| Helm 3.x / Kustomize 5.x | 不用 | 只想表达「产物不可变」时；模板与 overlay 会遮住「最终提交了哪个 SHA」 |
| Argo CD 2.x / Flux 2.x | 不用 | 七条公理还没确立之前；持续收敛会把未审的例外也收敛进去 |
| cosign / Kyverno 1.x（签名验签门禁） | 不用 | 需求只是「提出签名要求」；门禁实现归第 24 章，本章不写实现（SP-18） |
| kubectl + git | **使用** | — |

本章只提出一个**要求**、不写实现：公理 2 的「不可变镜像」最终需要签名验签来兜底，但签名步骤的归属由第 12 章（CI 产出制品）与第 24 章（加门禁）分工，唯一示例实现按 `book/decisions.md` 取 Kyverno 1.x 与 cosign，本章不另造一套 [R-03-6]。唯一示例实现的其余固定值（Argo CD 2.x、Kustomize 5.x overlay、Gateway API、ESO 等）同样只在后续各自首次出现的章节展开。

apiVersion: apps/v1
kind: Deployment

  name: gateway
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: kubectl
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: gateway
        version: git-1a2b3c4
        app.kubernetes.io/managed-by: kubectl
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: gateway
          image: registry.example.com/order-demo/gateway:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
          env:
            - name: APP_VERSION
              value: git-1a2b3c4
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]

## 3.5 验证与回滚（回滚方案先于发布方案）

**验证命令**：

```bash
# 公理 1 / 2：无 latest、三环境产物一致
kubectl -n order-demo-dev get deploy -o jsonpath='{..image}{"\n"}'
kubectl -n order-demo-staging get deploy -o jsonpath='{..image}{"\n"}'
kubectl -n order-demo-prod get deploy -o jsonpath='{..image}{"\n"}'
kubectl -n order-demo-dev describe pod -l app.kubernetes.io/component=gateway | grep -i image

# 最小闭环仍可用（沿用第 6 章脚本）
./hack/verify.sh

# 公理 7：最小 SLO 卡片四项填全
kubectl -n order-demo-dev get cm order-demo-slo-card -o jsonpath='{.data.sli}{"\n"}{.data.window}{"\n"}{.data.objective}{"\n"}{.data.freeze_rule}{"\n"}'
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| image 字段 | 三环境全为 `registry.example.com/order-demo/gateway:git-<sha7>`，**无 `latest`** |
| `describe pod` | 输出不含 `latest`，`imagePullPolicy` 为 `IfNotPresent` |
| 产物一致性 | dev / staging / prod 的 SHA 完全相同，差异仅在配置 [R-03-2] |
| `hack/verify.sh` | `/healthz` 返回 200，根路径 `version` 与镜像标签一致 |
| 最小 SLO 卡片 | `sli` / `window` / `objective` / `freeze_rule` 四项均有值，且字段名与第 20 章口径一致 |

最后一项只检查「填全了没有」，不检查数值是否合理——那是第 20 章的事。

**回滚命令 / 步骤**（本章不产生新的运行态资源；「回滚」指例外到期后恢复默认、把清单改回原则基线）：

```bash
# 1) 把清单改回原则基线（消除所有临时让步）
kubectl apply -f deploy/base/namespace.yaml
kubectl apply -f deploy/base/deployment.yaml
kubectl apply -f deploy/base/service.yaml
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s

# 2) 例外到期：把登记表恢复为初始模板（删除所有 EXC- 登记行）
git checkout ch03-principles -- docs/principles-exceptions.md

# 3) 确认没有遗留例外
grep -c '^| EXC-' docs/principles-exceptions.md || true
```

> **为什么这样回滚**：例外不是「改个配置」，而是「临时改变了默认」。只把清单改回去、却把例外登记留着，下一次值班会以为这条让步仍然有效。因此回滚必须同时做两件事：清单回到基线、登记表清空。回滚方案先于发布方案是公理 6；生产环境的这类变更必须来自 Git（公理 5，见第 3 章与第 14 章），本节 `kubectl apply` 只用于本地 kind 演练。

**回滚验证**：

```bash
kubectl -n order-demo-dev get deploy -o jsonpath='{..image}{"\n"}'
kubectl -n order-demo-dev describe pod -l app.kubernetes.io/component=gateway | grep -i image
grep -c '^| EXC-' docs/principles-exceptions.md || true
```

通过标准：image 回到 `git-<sha7>` SHA 标签（无 `latest`）、例外登记表 `EXC-` 行数为 0、`hack/verify.sh` 仍返回 200。**例外没清空、或清单没回到 SHA 标签，就不允许进入第 4 章**（CL-G-01、CL-G-07）。
