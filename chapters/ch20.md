## 20.1 问题与反模式：大盘很绿，为什么没人敢说「可以继续发」

**合成案例**。周五 16:40，`order-demo` 的 gateway 完成一次常规发布。十几分钟后，客服转来几条「下单页偶发报错」，值班同学打开监控大盘：CPU 曲线平稳，内存没有爬升，Pod 全是 `Running`，`readyz` 全绿。真正变了的只有入口 5xx 的比例，可它既没有告警，也没人知道「涨到多少算不能忍」。争到 18:00，没人拿得出一句能被复核的话——**大盘回答的是「机器忙不忙」，没人回答「用户还好不好，以及现在这一版还能不能继续放」**。

注意 18:00 这个时点的性质：**争了一个多小时，争的不是事实，是判据。**事实在 16:52 就已经摆在大盘上了（5xx 在涨），缺的是「涨到多少算数、由谁说了算」这一句事先约定好的话。没有这句话，同样的数据可以支撑五种结论，而每种结论都能找到支持它的人——**这不是沟通问题，是契约缺席时的必然结果。**

这不是监控没装，而是判定标准没建。第 3 章把「SLO 先行于告警」写成了公理 7，并在一张 1 页最小 SLO 卡片里留了五个待填字段；本章才给这些字段正式、可测量、能驱动决策的定义。可用性目标不是一句口号，它必须落到「什么算一次好事件、在什么窗口里统计、超了额度谁来喊停」这三件事上 [R-20-4]。

三个高频反模式：

**反模式一：用 CPU 使用率当 SLI。** 现象是开头那一幕——用户已经拿到 5xx，资源曲线却一切正常，因为资源使用率衡量的是「系统忙不忙」，不是「用户这次请求成没成」。根因是把因果链上下游搞反了：CPU 高可能只是结果， CPU 正常也完全挡不住依赖超时、连接池耗尽、配置改错这类直接伤到用户的故障。本章的替代做法是只取**用户可感事件**做 SLI，即 gateway 入口上「有效请求里返回非 5xx 的比例」，把资源指标留给第 17 章的容量与饱和度分析 [R-20-4][R-20-6]。

这条反模式特别难纠正，因为它不是无知，而是**习惯**：CPU 是第一个被接进监控的指标，也是所有模板的默认项，于是它成了「有没有问题」的默认答案。而它测的其实是**你自己的机器**，不是**别人的体验**——这两件事平时高度相关，出故障时恰好脱钩。

**反模式二：目标写 99.99% 却没有预算策略。** 现象是目标定得很漂亮，决策时仍旧拍脑袋：「四个九」没有配套「谁批准例外、耗尽之后冻结什么、什么时候解冻」，等价于没有写。根因是把 SLO 当成对外承诺的口号，而不是产品与平台之间的**消耗额度**。错误预算的意义恰恰在于把「可用性与变更速度」摆到同一张账上：预算没花完，团队有权利快速发布；花完了，就得用冻结换回可靠性 [R-20-5]。本章要求目标必须与窗口、冻结阈值、例外审批人、解除条件一起成文，单给一个百分比不算定义完成。

「四个九」之所以流行，是因为它读起来像一个态度，而不像一个数字。**它真正的含义是「一个月只能坏 4 分 19 秒」**——这句话一旦写出来，会议室里就会有人开始算「那我们每次发布要多久」。**所以目标写不出来往往不是不知道怎么写，是不想知道那个数。**

**反模式三：只设一个窗口，或者干脆不设窗口。** 现象是「全年 99.9%」这类目标：一次 20 分钟的短故障能把全年额度吃掉大半，而一次持续低烈度的慢性劣化却因为被长窗口摊薄而长期不触发任何动作。根因是单一时间尺度同时承担了「快速止血」和「季度复盘」两种职责。本章的替代做法是一套滚动窗口加**快燃尽 / 慢燃尽双窗口**：短窗口负责 paging，长窗口负责趋势与 ticket，两者都由同一份错误预算推导 [R-20-3][R-20-4]。

双窗口的必要性可以用一句反问确认：**今天下午那次 20 分钟故障，在「全年」这个尺度上是什么？**是一根几乎看不见的毛刺。而在「一小时」这个尺度上，它是全站不可用。同一件事在两个尺度上的严重性差了两个数量级——**所以不能只用一个尺度去判「要不要叫人」和「要不要改季度计划」。**

> 三条反模式指向同一个缺口：**没有可测量的 SLI，就没有预算；没有预算，就没有发布判定**。第 1 章事故里 H8「告警响了却没有 runbook」的更深层原因也在这里：那条告警背后没有能说清「现在算不算坏、坏了该冻结什么」的 SLO（见第 22 章）。

## 20.2 范式与决策树：把五个字段填成一份能判定的契约

本章是 **SLO、SLI、错误预算** 的正式定义章。此前章节（见第 3 章）只在卡片层面给白话与占位，从本章起三者可以作为推理前提。

先说清这一章真正难在哪：**难的不是写目标，是写分母。**「99.9% 可用」看起来是一句话，落到可测量就必须回答「哪些请求算进来」——探针算不算、4xx 算不算、客户端超时算不算、被限流拒掉的算不算。**每一个「算不算」都是一次立场选择，而它们会直接改变这个数的含义。**所以下面的定义会写得有点啰嗦，因为它就是在替你把这些选择一次做完。

**SLI（Service Level Indicator）** 是「可直接测量的好坏比例」：一个分子、一个分母、一个测量点、一组排除项，四者缺一即不可测量。对 `order-demo` 的 gateway，本书定义为：

- **有效请求（分母）**：落到 `gateway` Service 8080 端口的 HTTP 请求，且 `route` 不属于探针路径 `/healthz`、`/readyz`、`/startup`（见第 8 章）。探针是平台自测流量，不是用户可感事件，计入分母会稀释真实的坏事件。
- **成功请求（分子）**：有效请求里 `status_code` 不属于 `5..` 的那些。4xx 属于用户侧或调用方错误，不计为服务失效；若某个 4xx 实为网关误判，属于 SLI 口径修订，走例外审批而不是临时改数。
- **测量点**：入口侧 `gateway`，由第 21 章的 OTel Collector 采集并落为 `order_demo_http_requests_total`；在客户端测会漏掉连不进来的请求，在 `api` 层测会漏掉网关自身故障。指标名与 label 白名单见第 21 章的规范表。
- **排除项**：探针路径、发布窗口内的主动压测流量、已知的演练注入（第 23 章），三者必须在记录规则里显式过滤，否则预算会被自己人吃掉。

**SLO** = SLI + 目标 + 时间窗口，是「对服务可靠性的量化承诺」。**错误预算** = 1 − SLO，是「在一个窗口内允许不可用的额度」；99.9% 的 28 天滚动目标，等价于允许 0.1% 的坏请求，按量换算就是这 28 天里可以「花掉」的失败请求总数。预算是额度而非目标：花得慢说明还有变更余量，花得快就说明该用冻结换稳定 [R-20-4][R-20-5]。

### 多服务 SLO 组合与「用户旅程 SLI」的拼装

先看一个合成算例：`gateway` 28 天 99.9%、`api` 28 天 99.5%，两张大盘都绿，可用户从点「提交订单」到看见成功页，成功率只有 `0.999 × 0.995 ≈ 0.994`——低于任何一份单服务契约，更够不到对外口头承诺的「四个九」。这不是谁算错了，而是把**服务 SLO** 当成了**旅程 SLO**：用户在意的是「这次下单成没成」，不是「某一段的 2xx 比例」。

三条组合规则（本章观点，论证与反例见下）：

1. **记账点唯一**：对外错误预算只在旅程入口记一次账，其余服务只做诊断。
2. **乘积只用于独立失效域**：调用链上的失败已经被入口计入一次，再乘一次是双重惩罚；只有真正独立的依赖（第三方支付、`db`、DNS）才进乘积。
3. **诊断 SLO 不设冻结阈值**：诊断口径用于定位与容量，若也挂冻结，一次故障会冻结两次、两次故障会冻结三个团队。

| 层 | SLI 口径 | 目标示例 | 进不进入对外预算 | 用来干什么 |
|---|---|---|---|---|
| 旅程（下单） | `gateway` 上 `route=~"/orders\|/orders/.*"` 的非 5xx 比例 | 99.9 | **是，唯一账本** | 冻结判定、对外承诺 |
| `gateway` 全量 | 非探针 route 的非 5xx 比例 | 99.9 | 否（本章示例口径） | 入口健康、容量 |
| `api` | `service="api"` 的非 5xx 比例 | 99.5 | 否 | 定位是哪一段掉的 |
| `worker` | 超时关单率 / 积压时长 | 99.0（示例） | 否（独立周会） | 异步质量 |
| `db` | 连接可用性 | 99.95 | 否 | 依赖健康 |

**拼装五步**

**第一步，画旅程、标同步/异步分界**。下单＝`POST /orders`（`gateway` → `api` → `db`，同步）＋`worker` 超时关单与通知（异步）。分界线决定记账点在哪。

**第二步，选记账点**。同步段在 `gateway` 记一次成败；异步段没有入口请求，单独记。

**第三步，写 PromQL**。旅程是 `route` 的子集，不是新指标，分子分母与 §20.4 同源：

```promql
sum(rate(order_demo_http_requests_total{
  service="gateway",
  route=~"/orders|/orders/.*",
  status_code!~"5.."
}[5m]))
/
sum(rate(order_demo_http_requests_total{
  service="gateway",
  route=~"/orders|/orders/.*"
}[5m]))
```

记录规则沿用 §20.4 的命名约定：`sli:order_demo_journey_checkout:ratio_rate5m`。

**第四步，校验分母**。旅程分母必须 ≤ 全量分母，两者之差应等于被排除的其它 route 之和；差值对不上说明路由正则漏了改版后的路径（如 `/orders/v2`），属口径缺陷而不是流量变化。

**第五步，配预算**。只给旅程口径配 `objective` 与冻结，其余服务只配告警等级（见第 22 章），避免多份账本互相打架。

**从目标反推单段要求**：若旅程承诺 99.9%，且三段是独立串联，每段需要 `0.999^(1/3) ≈ 99.9667%`——意味着要把 `api` 从 99.5 抬到 99.97，成本远高于收益。

| 串联段数 | 每段最低目标（旅程 99.9%） | 现实性 |
|---|---|---|
| 2 | 99.95% | 常见，两段独立失效域 |
| 3 | 99.9667% | 需架构去耦（重试、降级、缓存兜底） |
| 5 | 99.98% | 通常不现实：应改为降级设计，而不是加目标 |

**反例与适用前提**：若 `gateway` 对 `api` 做了重试与缓存兜底，入口成功率会高于 `api` 成功率，此时「入口合成」会掩盖 `api` 的慢性劣化——所以 `api` 仍要保留诊断 SLO 与慢燃尽告警，只是不参与冻结。若旅程跨多个入口（App / H5 / 开放 API），记账点要按入口分别建，不能合并成一条：合并后低流量入口的坏事件会被高流量入口摊薄。

**`worker` 没有入口请求怎么办**：它的 SLI 用「超时关单率＝超过承诺时限仍未关单的订单数 / 应关单订单数」，7 天滚动，目标按业务可接受的漏关比例定（示例 99.0%），窗口内应关单量不足 200 单时改用绝对量（漏关 ≤ 1 单）。它的指标不在第 21 章 `metric-naming.md` 的当前白名单内，因此本章只把口径写进契约、用 `db` 侧对账查询计算，不新造指标名、也不进 `promtool` 规则；待第 21 章登记该指标后再迁入规则，避免两套名字并存。

**本章示例的边界**：§20.4 的 `gateway-availability` 仍按 Service 全量 route 记账，适合单旅程场景；只有 `gateway` 承载多条旅程且目标不同时才拆分子旅程，且拆分属于口径修订，须先走 §20.5 的修订流程。

### 与第 3 章「1 页最小 SLO 卡片」字段一一对照

第 3 章的 `order-demo-slo-card` 只要求把五个字段填全、不检查数值是否合理；本章把同样的五个字段从「占位」升级为「判定」。字段名与取值口径逐字保持一致，不另起一套：

| 第 3 章卡片字段 | 卡片里的白话/占位 | 本章正式定义 | 落点 |
|---|---|---|---|
| `service` | `"gateway"` | SLO 作用对象＝服务名 + 用户旅程「下单请求经 gateway 到 api」 | `slo.yaml` 的 `spec.service` |
| `sli` | `"成功请求数 / 总请求数"` | 分子＝非 5xx 有效请求，分母＝有效请求，含测量点与排除项 | `sli-recording-rules.yaml` 的 `sli:order_demo_http_success:ratio_rate5m` |
| `window` | `"28d"` | 28 天滚动窗口；另设 1h / 6h / 3d 三个燃尽观察窗 | `spec.timeWindow` + 记录规则 |
| `objective` | `"99.9"` | 目标 99.9%，即错误预算 0.1% | `spec.objectives[].target: 0.999` |
| `freeze_rule` | `"错误预算耗尽则冻结非必要发布"` | 冻结阈值、冻结范围、例外审批人、解除条件四项成文 | `docs/slo-contract.md` |

> 差异只有一处且必须写明：第 3 章卡片落在 `order-demo-dev` 供填写，本章正式卡片落在 `order-demo-prod` 用于发布判定；**字段名、取值口径、单位完全一致**，环境差异只体现在命名空间与签字人，不体现在 SLO 数字上（配置契约见第 6 章、见第 4 章）。

### 错误预算窗口与冻结规则

| 项 | 取值 | 判据含义 |
|---|---|---|
| 主窗口 | 28 天滚动 | 与月度发布节奏对齐，短故障不会被摊薄到「全年」 |
| 预算方法 | Occurrences（按请求数） | 与 SLI「成功/有效」同口径，不引入时间片的主观加权 |
| 快燃尽窗口 | 1h + 5m，燃尽率 ≥ 14.4 | 1 小时花掉 2% 预算，paging（见第 22 章） |
| 慢燃尽窗口 | 6h + 30m，燃尽率 ≥ 6 | 6 小时花掉 5% 预算，ticket + 复核 |
| 趋势窗口 | 3d，燃尽率 ≥ 1 | 慢性劣化进周会复盘，不半夜叫人 |
| 冻结阈值 | 28d 剩余预算 ≤ 0 | 冻结**非必要发布**：功能发布、依赖升级、配置重构 |
| 冻结豁免 | 修故障的回滚、安全补丁、预算耗尽本身的止血变更 | 豁免不等于放行，须登记例外编号与到期时间 |
| 例外审批人 | 业务负责人 + 平台负责人双签 | 单方面由平台定目标不会被执行 |
| 解除条件 | 滚动窗口滚出坏事件后剩余预算 > 0，且连续 3 个快窗口无燃尽告警 | 不是「等下周一」，而是可查询的指标条件 |

燃尽率的定义是「单位时间消耗的预算 / 该时间窗应得预算」，14.4 这个数来自「1 小时花掉 28 天预算的 2%」：28 天＝672 小时，2% 预算对应 13.44 小时，672 ÷ 13.44 ≈ 50，习惯上取 14.4（对应 1h 消耗 2% 预算的近似倍数，不同资料取值略有差异，本书统一以本节规则文件为准）[R-20-3][R-20-4]。**关键不在小数，而在阈值必须从预算推导、且快/慢窗口同源**。

### 预算方法取舍：Occurrences、Timeslices 与低流量下的置信度

OpenSLO 1.x 的 `budgetingMethod` 只有两个合法取值：`Occurrences` 与 `Timeslices` [R-20-1]。选错方法不会报错，只会让账本和用户体感脱节——同一个 28 天窗口、同一个 99.9%，两种方法算出的「还剩多少」可以相差数倍。

- **Occurrences（按事件）**：预算＝窗口内允许的坏事件**个数**。28 天 100 万请求、目标 99.9%，允许 1,000 个坏请求，用掉 400 个就是消耗 40%。
- **Timeslices（按时间片）**：把窗口切成等长片（`timeSliceWindow`，如 5m），片内 SLI ≥ `timeSliceTarget` 记为「好片」，预算＝允许的坏片**个数**。28 天 ÷ 5m ＝ 8,064 片，99.9% 允许 8 个坏片，第 9 个坏片一出现就耗尽。

| 维度 | Occurrences | Timeslices |
|---|---|---|
| 计量单位 | 坏请求 / 坏任务个数 | 坏时间片个数 |
| 一次 10 秒全站 5xx（入口 200 QPS） | 记约 2,000 个坏事件，可能一次吃掉大半预算 | 只坏 1–2 片，占比极小 |
| 低 QPS 接口（1 请求/分钟） | 单个请求即 100% 权重，噪声极大 | 每片 0 或 1 个请求，退化成二值信号 |
| 慢性劣化（0.3% 持续一天） | 按请求累积，敏感 | 每片都超阈值才算坏片，同样敏感 |
| 表达「最长不可用时长」 | 不能直接表达 | 可直接换算：99.9% / 30 天 ≈ 43 分钟 |
| PromQL 实现 | `increase(bad)/increase(total)`，一条规则 | 需先按片判定再计数，得用子查询或逐片记录规则 |
| 何时不该用 | 流量极低、事件粒度粗（如每日批任务） | 多 route 混合流量（低 QPS 路由被切片稀释）、要按「受影响用户数」计量时 |

**本章为何仍选 Occurrences**：它与 SLI「成功 / 有效」同口径，可被 `increase` 逐行复核，28 天长窗口下也不需要人为设定切片边界 [R-20-2]。`slo.yaml` 里保留的 `timeSliceTarget` / `timeSliceWindow` 在 Occurrences 下**不参与预算计算**，只作为观测切片与将来换方法时的对照字段——删掉它们会让「换方法」变成一次无法对比的跳跃。

**何时必须换成 Timeslices**：异步批任务（没有请求刻度）、单次失败代价极高但 QPS 极低的接口（日终结算）、以及合同直接用「月度不可用不超过 43 分钟」表述的场景。这类服务的用户体感是「多久不能用」，不是「错了几个请求」。

**低流量下比例型 SLI 的置信度**（本节推导，不引用外部来源）：零故障时，95% 置信的失败率上限约为 `3/N`（rule of three）。要在 28 天里「零故障也敢说 ≤ 0.1%」，需要 `N ≥ 3 / 0.001 = 3,000` 个有效请求。

| 28 天有效请求 N | 零故障时 95% 上限 ≈ 3/N | 能否断言 ≤ 0.1% | 折算每小时请求 |
|---|---|---|---|
| 500 | 0.60% | 不能 | ≈ 0.7 |
| 3,000 | 0.10% | 临界，不能说「有余量」 | ≈ 4.5 |
| 30,000 | 0.010% | 可以 | ≈ 45 |
| 1,000,000 | 0.0003% | 有富余 | ≈ 1,488 |

再往前推一步：1 小时快窗要确认 14.4 的燃尽率，这 1 小时里至少要出现约 3 个坏请求才不被噪声淹没；按 1h 坏率 1.44% 反推，28 天有效请求需 ≥ 约 14 万。低于这个量级，「快燃尽 paging」在数学上就无法在 1 小时内成立——不是规则写错了，是样本不够。

| 28 天有效请求 | 可用口径 | 具体做法 |
|---|---|---|
| < 3,000 | 放弃比例型做 paging | 绝对量 SLI：月度坏事件 ≤ k 次；加合成探测补样本 |
| 3,000 – 140,000 | 比例型可做 28d 与 6h，1h 用绝对量兜底 | 28d 比例 + 6h 慢燃尽 + 1h 绝对量（见下） |
| ≥ 140,000 | 全套双窗 | §20.4 默认规则 |

绝对量兜底只加一条判定规则，不改 `budgetingMethod`，也不改 `objective`：

```yaml
        - alert: GatewayBadRequestsAbsolute
          expr: >-
            sum(increase(order_demo_http_requests_total{
              service="gateway",
              route!~"/healthz|/readyz|/startup",
              status_code=~"5.."
            }[1h])) >= 3
          for: 5m
          labels:
            severity: paging
            service: gateway
          annotations:
            summary: "gateway 1h 内坏请求 >= 3（低流量绝对量兜底）"
            runbook: "docs/runbooks/gateway-fast-burn.md"
```

这段挂在 `order-demo-error-budget` 组内，与 §20.4 末尾两条 `- alert:` 一样只作口径示意，生产告警集由第 22 章统一承载。启用后要验证「同一小时内 `sum(increase(...))` 与 `sli:order_demo_http_valid:rate5m` 的积分一致（误差 ≤ 1%）」，并且**只对低流量服务开启**：高流量服务的 paging 仍由燃尽率承担，两者同时开会让一次故障叫两次人（抑制规则见第 22 章）。

**合成探测补样本**：对低流量服务加一条每分钟一次的只读请求（`route="/orders"`，不新增排除项），把 N 抬到可判定量级。合成探测的失败必须与真实请求同口径计入，**不能单独建一条「探测可用性 SLO」**——那会把「用户能不能下单」偷换成「探测能不能连通」，正是 §20.1 反模式一的变体。

**方法混用的两个坑**：一是同一服务 28 天用 Occurrences、快窗却按「坏片数」判定，两条线不同源，会出现「预算还剩 30%，快窗却一直在响」；二是把 Timeslices 的 `timeSliceTarget` 直接读成 `objective`，于是 99.9% 被解释成「每个 5 分钟片都 99.9%」，比 28 天 99.9% 严苛得多，正常发布也会被自己的阈值挡住。

**怎么验证选对了**：拿上一个窗口的历史数据按两种方法离线回放，把两条预算曲线与当期用户投诉、工单时间对齐；哪条曲线的拐点和投诉同时出现，就选哪条。回放只需 `promtool query range` 跑同一对 `increase` 表达式，不新增仓库文件，也不改任何已生效规则。

### 发布冻结判定决策树

```
本周剩余预算 > 0？                    否 → 冻结非必要发布，走例外审批（20.4）
        │ 是
近 1h / 5m 快燃尽 ≥ 14.4？           是 → 暂停发布并 paging，先止血（第 22、23 章）
        │ 否
近 6h 慢燃尽 ≥ 6？                   是 → 允许已开始的发布收尾，禁止新开，建 ticket
        │ 否
本次变更是否在冻结豁免清单内？        否 → 正常放行，按第 13 章回滚方案先行
        │ 是
→ 放行但登记例外编号、审批人、到期时间，下次复盘核对（CL-G-10）
```

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：告警阈值与发布冻结规则必须由同一份错误预算推导；先建告警再补 SLO，等于没有判定标准。同时，SLO 是产品与平台的双向契约，必须有业务方签字，单方面由平台定的目标不会被执行。
>
> **论证**：告警回答「现在要不要叫人」，冻结回答「现在能不能改」，两者其实是同一个问题的两种时间尺度：都在问「坏到什么程度就超出了我们 agreed 的额度」。若先按经验拍一个「5xx > 1% 告警」，再补一个「99.9% SLO」，两条线彼此无关，值班时就会出现「告警响了但预算还剩很多」或「预算耗尽却没告警」的错位。反过来，从 `1 − SLO` 出发，燃尽率阈值、冻结阈值、豁免范围都能被一条算式复核。至于签字：冻结会挡住业务排期，只有批准排期的人也批准了额度，冻结才不会在第一次冲突时被绕过。
>
> **反例与适用前提**：这不等于「所有服务都必须 99.9% / 28 天」。内部离线 `worker`（见第 7 章）没有用户可感的在线请求，用成功率做 SLI 不成立，应改用「任务积压时长 / 超时关单率」；刚上线的服务流量太小，比例型 SLI 会被单个请求剧烈拉扯，应先用绝对量观察一个窗口再定目标。若组织已有跨部门签署的可靠性契约与独立审批流，可直接沿用其窗口与阈值，但仍须能拿出「阈值由预算推导」的等价证据，否则本书的推导链不成立。

**`observability/sli-recording-rules.yaml`——Prometheus 3.x 记录与告警规则（实现层）**

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: order-demo-slo-rules
  namespace: observability
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
    role: alert-rules
spec:
  groups:
    - name: order-demo-sli
      interval: 30s
      rules:
        - record: sli:order_demo_http_good:rate5m
          expr: >-
            sum(rate(order_demo_http_requests_total{
              service="gateway",
              route!~"/healthz|/readyz|/startup",
              status_code!~"5.."
            }[5m]))
        - record: sli:order_demo_http_valid:rate5m
          expr: >-
            sum(rate(order_demo_http_requests_total{
              service="gateway",
              route!~"/healthz|/readyz|/startup"
            }[5m]))
        - record: sli:order_demo_http_success:ratio_rate5m
          expr: >-
            sli:order_demo_http_good:rate5m
            / clamp_min(sli:order_demo_http_valid:rate5m, 0.0001)
        - record: sli:order_demo_http_bad:ratio_rate5m
          expr: '1 - sli:order_demo_http_success:ratio_rate5m'
    - name: order-demo-error-budget
      interval: 30s
      rules:
        - record: slo:order_demo_gateway:error_budget_ratio
          expr: '1 - 0.999'
        - record: slo:order_demo_gateway:burn_rate_1h
          expr: >-
            avg_over_time(sli:order_demo_http_bad:ratio_rate5m[1h])
            / on() group_left() slo:order_demo_gateway:error_budget_ratio
        - record: slo:order_demo_gateway:burn_rate_6h
          expr: >-
            avg_over_time(sli:order_demo_http_bad:ratio_rate5m[6h])
            / on() group_left() slo:order_demo_gateway:error_budget_ratio
        - record: slo:order_demo_gateway:burn_rate_3d
          expr: >-
            avg_over_time(sli:order_demo_http_bad:ratio_rate5m[3d])
            / on() group_left() slo:order_demo_gateway:error_budget_ratio
        - record: slo:order_demo_gateway:budget_consumed_ratio_28d
          expr: >-
            sum_over_time(sli:order_demo_http_bad:ratio_rate5m[28d])
            * 300
            / on() group_left()
            (sum_over_time(sli:order_demo_http_valid:rate5m[28d]) * 300 * 0.001)
        - record: slo:order_demo_gateway:release_freeze
          expr: 'slo:order_demo_gateway:budget_consumed_ratio_28d >= 1'
        - alert: GatewayErrorBudgetFastBurn
          expr: >-
            slo:order_demo_gateway:burn_rate_1h >= 14.4
            and slo:order_demo_gateway:burn_rate_5m >= 14.4
          for: 2m
          labels:
            severity: paging
            service: gateway
          annotations:
            summary: "gateway 错误预算快燃尽（1h 燃尽率 >= 14.4）"
            runbook: "docs/runbooks/gateway-fast-burn.md"
            slo: "gateway-availability"
        - alert: GatewayErrorBudgetSlowBurn
          expr: 'slo:order_demo_gateway:burn_rate_6h >= 6'
          for: 15m
          labels:
            severity: ticket
            service: gateway
          annotations:
            summary: "gateway 错误预算慢燃尽（6h 燃尽率 >= 6）"
            runbook: "docs/runbooks/gateway-slow-burn.md"
            slo: "gateway-availability"
```

> `burn_rate_5m` 由同一份 `sli:order_demo_http_bad:ratio_rate5m` 在 5 分钟窗口上取均值，规则文件里以 `avg_over_time(sli:order_demo_http_bad:ratio_rate5m[5m])` 展开；上式 `GatewayErrorBudgetFastBurn` 的第二个条件在完整规则中写作 `avg_over_time(sli:order_demo_http_bad:ratio_rate5m[5m]) / on() group_left() slo:order_demo_gateway:error_budget_ratio >= 14.4`，与 1h 条件同源，避免快窗口单靠一次抖动触发。冻结判定 `release_freeze` 为布尔记录规则（1＝冻结），供第 22 章路由与 `hack/budget-report.sh` 直接查询；它只表达判定，真正的冻结动作由发布门禁读取，不在本规则里改集群。本节末尾两条 `- alert:` 只是判定链自检的最小示意，生产告警集由第 22 章 `alert-rules.yaml` 统一承载（见第 22 章），接入生产前按其章内说明处理，避免重复评估。

**`docs/slo-contract.md`——与第 3 章卡片字段一一对应的完整模板（业务签字版）**

```markdown
# order-demo / gateway 可用性 SLO 契约

## 一、卡片字段（字段名与 ch03 `order-demo-slo-card` 逐字一致）
- service: gateway
- sli: 非 5xx 有效请求数 / 有效请求数
- window: 28d（滚动）
- objective: 99.9
- freeze_rule: 28 天剩余错误预算 <= 0 时冻结非必要发布

## 二、可测量定义（第 20 章正式口径）
- 有效请求：gateway Service 8080 上 route 不属于 /healthz /readyz /startup 的 HTTP 请求
- 成功请求：有效请求中 status_code 不属于 5.. 的请求
- 测量点：入口 gateway，指标 order_demo_http_requests_total（命名规范见第 21 章）
- 排除项：探针流量、发布窗口主动压测、演练注入
- 分母为 0 的处理：clamp_min 保护，分母为 0 时 SLI 记为 1，不产生坏事件

## 三、错误预算与窗口
- 错误预算 = 1 - 0.999 = 0.001（按 Occurrences 计）
- 快燃尽：1h / 5m 双窗 >= 14.4 → paging（第 22 章）
- 慢燃尽：6h >= 6 → ticket；3d >= 1 → 周会复盘
- 冻结判定：slo:order_demo_gateway:release_freeze == 1

- 冻结范围：功能发布、依赖升级、配置重构
- 豁免范围：回滚、安全补丁、止血变更（须登记例外）
- 例外审批：业务负责人 + 平台负责人双签
- 例外登记：编号 EXC-YYYYMMDD-NN、前提、补偿措施、到期时间（沿用第 3 章例外机制）
- 解除条件：剩余预算 > 0 且连续 3 个快窗口无燃尽告警

| 角色 | 姓名 | 签字日期 | 备注 |
|---|---|---|---|
| 业务负责人 | <填写> | <YYYY-MM-DD> | 批准额度与冻结对排期的影响 |
| 平台负责人 | <填写> | <YYYY-MM-DD> | 批准测量点与规则实现 |
| 值班代表 | <填写> | <YYYY-MM-DD> | 确认 paging 路由可达（第 22 章） |
- 生效日期：<YYYY-MM-DD>
- 复审周期：每季度一次，或在两次预算耗尽后提前复审
- 变更方式：仅通过本文件 + observability/ 下规则文件的 PR，禁止在 UI 改数
```

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：SLO 契约里「业务方签字」不是走形式的表格，而是冻结规则能否被执行的前提；字段表、预算表、冻结表、签字表必须凑齐才算一份完整 SLO。
>
> **论证**：冻结会直接挡住业务排期。若只有平台单方面定了 99.9%，第一次撞上大促排期时，最省事的做法一定是临时把目标调低或口头放行，规则随即失效。让批准排期的人也批准额度，冲突就变成了「按我们共同签的账办事」，而不是「平台卡业务」。四张表分别对应「测什么、允许多少、超了怎么办、谁认账」，缺任何一张，决策都会退回拍脑袋。
>
> **反例与适用前提**：对纯内部、无外部 SLA、且业务与平台同属一个小组的工具类服务，双签可简化为一次评审记录；但「谁批准例外」这一栏不能空。对已有正式 SLA 合同且罚则明确的对外服务，SLO 目标应不宽于合同，冻结规则可更严，不能更松。

**`hack/budget-report.sh`——本周预算消耗与冻结判定（完整可复制）**

```bash
#!/usr/bin/env bash
set -euo pipefail

PROM="${PROM:-http://prometheus.observability.svc.cluster.local:9090}"
SERVICE="${SERVICE:-gateway}"
WINDOW="${WINDOW:-28d}"

query() {
  curl -fsS --data-urlencode "query=$1" "${PROM}/api/v1/query" \
    | jq -r '.data.result[0].value[1] // "NaN"'
}

GOOD="$(query "sum(increase(order_demo_http_requests_total{service=\"${SERVICE}\",route!~\"/healthz|/readyz|/startup\",status_code!~\"5..\"}[${WINDOW}]))")"
VALID="$(query "sum(increase(order_demo_http_requests_total{service=\"${SERVICE}\",route!~\"/healthz|/readyz|/startup\"}[${WINDOW}]))")"
CONSUMED="$(query "slo:order_demo_gateway:budget_consumed_ratio_28d")"
FREEZE="$(query "slo:order_demo_gateway:release_freeze")"

awk -v g="${GOOD}" -v v="${VALID}" -v c="${CONSUMED}" 'BEGIN {
  sli = (v + 0 > 0) ? g / v : 1;
  printf "SLI(28d)=%.6f  有效请求=%.0f  成功请求=%.0f\n", sli, v, g;
  printf "错误预算消耗=%.2f%%  剩余=%.2f%%\n", c * 100, (1 - c) * 100;
}'
if [ "${FREEZE}" = "1" ]; then
  echo "判定：冻结非必要发布（走 docs/slo-contract.md 例外审批）"
  exit 2
else
  echo "判定：预算未耗尽，可按第 13 章回滚方案先行原则发布"
fi
```

> 脚本用集群内地址 `prometheus.observability.svc.cluster.local:9090`，不依赖外部网络；`exit 2` 让发布流水线把「冻结」当硬失败，而不是打印一行警告后继续 [R-20-5][R-20-6]。

### 预算耗尽后业务要求破例：一次完整冲突复盘与双签流程

**合成案例**（接 §20.1 的周五发布，数字为便于复盘的合成值）。冻结规则写完了不等于能用：真正的考验是预算耗尽、而业务排期不能等的那一天。

| 时间 | 事件 | 证据 | 决策 |
|---|---|---|---|
| 11-13 16:40 | `gateway` 常规发布 `git-9f8e7d6` | 第 13 章滚动更新完成 | 放行 |
| 11-13 17:02 | 全站 5xx 100%，连接池配置回退失效 | `order_demo_http_requests_total{status_code=~"5.."}` 瞬间拉满 | 值班按第 22 章 paging |
| 11-13 17:11 | `kubectl rollout undo` 完成，5xx 归零 | 回滚验证见 §20.5 | 止血 |
| 11-13 17:40 | `release_freeze=1`，28 天剩余预算 −7% | 9 分钟全站不可用约花掉 22% 预算，此前已用 85% | 自动冻结非必要发布 |
| 11-16 09:30 | 业务负责人要求周一发大促版本 | 合同承诺 11-18 上线 | 提出破例 |
| 11-16 10:15 | 平台拒绝，援引契约第四节 | `docs/slo-contract.md` 第四节 | 升级到技术负责人 |
| 11-16 14:00 | 三方会，三个「省事方案」被否 | 见下 | 走例外 |
| 11-16 16:30 | 双签 `EXC-20261116-01`，附四条约束 | PR #412 两条 approve | 有限放行 |
| 11-17 10:00 | 灰度 5% 观察 30 分钟，再扩到 100% | 5xx 0.05%，限流阈值未触发 | 完成 |
| 11-20 16:30 | 例外到期，门禁要求关闭 | 到期检查脚本 | 回收 |

**那场三方会**（依同类冲突共性还原，非原话）：

> **业务**：合同写了 11-18 上线，这个改不了。你们冻结到什么时候？
> **平台**：预算已经负数，按契约要冻结到下个窗口。
> **业务**：那能不能把目标从 99.9 调到 99.5？反正用户感知不到那个差别。
> **平台**：目标一改，这个季度的账就没法对了。
> **业务**：那就这一次，改回来就行，我会在会上说明。
> **平台**：……说明给谁？三个月后看这个数的人，不会知道今天这个会。

最后这个反问是整场会的转折点。**「临时改一下」这个提议在技术上完全可行、在人情上非常合理**，它唯一的问题是**破坏了账本的可比性**——而账本的价值恰恰来自「三个月后的人也能看懂」。所以双签流程保护的从来不是流程本身，是**那个不在场的人**。

**三个被否掉的「省事方案」，每个都对应一条禁令**

1. **把 `objective` 从 0.999 改成 0.995**——否决。改目标等于改账本，事后无法回答「这个季度到底承诺了什么」。`objective` 只能在季度复审时改，**例外期内禁止修改**（复审节奏已写进契约第五节）。
2. **临时删掉 `release_freeze` 规则，「发完再补」**——否决。规则是 Git 里的声明，删掉它等于让所有服务同时解冻；而且删除动作本身不会留下「谁批的」证据，事后只能靠聊天记录推断。
3. **把功能发布改名叫「配置重构」绕过冻结**——否决。冻结范围本来就含配置重构（§20.4 契约第四节），改名只是把冲突从流程挪到复盘里，下一次会更难谈。

**复盘：三处失守、两处做对**

- 失守一：3 天趋势窗口两周前就在报警（预算从 100% 磨到 85%），但「慢燃尽」被当成 ticket 静音，没进周会。教训是慢燃尽必须有固定接收人，否则等于没有 [R-20-4]。
- 失守二：第一版例外单只写了「因大促破例」，没有补偿措施与到期时间，导致到期时没人能判断「破例是否兑现」。
- 失守三：到期回收靠日历提醒，漏了一天；后来改成 CI 门禁，逾期即失败。
- 做对一：值班先止血再讨论冻结，没有在 5xx 还在涨的时候开会——冻结是治理动作，不能和止血抢同一个时间窗。
- 做对二：冻结由规则算出（`release_freeze=1`）而不是某个人拍板，所以争论的起点是「怎么解」，不是「谁说了算」。

**双签流程：五步，每步都有可查证据**

| 步 | 谁 | 输入 | 产出（证据） | 失败处置 |
|---|---|---|---|---|
| 1 申请 | 业务负责人 | 变更对象（镜像 SHA 或 PR）、为什么不能等、影响面 | 例外单草稿（PR 描述） | 缺「为什么不能等」→ 退回 |
| 2 评估 | 平台 / 值班 | 当前剩余预算、快慢燃尽、补偿措施是否可验证 | 评估结论：同意 / 附条件 / 拒绝 | 补偿不可验证 → 拒绝 |
| 3 双签 | 业务负责人 + 平台负责人 | 例外单 + 评估结论 | PR 上两个 approve | 缺一签 → CI 拒绝合并 |
| 4 生效 | 值班 | 合并后的 `EXC` 编号 | `docs/slo-contract.md` 表格新增一行 | 只有口头放行 → 视为未生效 |
| 5 回收 | 平台 | 到期时间 | 关闭记录 + 一次复盘结论 | 逾期未关 → 门禁失败 |

**例外单六个必填字段**（缺任一项即视为无效申请）：

- `EXC-YYYYMMDD-NN`：编号，与 `docs/slo-contract.md` 表格、PR 标题三处一致；
- **变更对象**：具体到 `git-<sha7>` 或 PR 号，不接受「大促版本」这类指代；
- **前提**：为什么不能等到预算恢复（合同、监管、不可延期的外部事件），这是唯一能被复核的正当性来源；
- **影响面**：当前缺口（本例 −7%）与本次变更预计再消耗多少预算；
- **补偿措施**：必须可验证——灰度比例、观察时长、限流阈值、回滚演练的时间戳，四者至少写三项；
- **到期时间**：默认 ≤ 72 小时；安全补丁可放宽到 ≤ 7 天，但仍须写明补丁编号。

```bash
# 1. 例外单是否过期未关闭（ISO 日期可直接按字典序比较）
TODAY="$(date +%F)"
grep -E '^\| EXC-' docs/slo-contract.md | awk -F'|' -v today="${TODAY}" '
  { gsub(/^ +| +$/, "", $5); if ($5 != "" && $5 < today) { print "过期未关闭: "$2; bad=1 } }
  END { exit bad }'

# 2. 冻结期内 observability/ 的每次变更都能对上一条例外或一次季度复审
git log --since="$(date -d '-28 day' +%F)" --oneline -- observability/ docs/slo-contract.md
```

通过标准：第 1 段退出码 0（无过期例外）；第 2 段里每一次提交都能对上一条 `EXC-` 或一次已记录的季度复审。

**例外不是解冻**：账本一个数字都不动，放行的只是「这一条变更、在这几条约束下、到这个时间为止」。所以预算恢复前其它功能发布仍然冻结；例外也不能被延展成第二条——第二次申请必须重新评估，并先说明第一次的补偿措施是否兑现 [R-20-5][R-20-6]。

**破例期间的值守加强**：例外生效的 72 小时内，该服务的告警等级从 `ticket` 临时升为 `paging`，值班表上单列一名备份；限流阈值与灰度比例写进变更单，值班可以不经二次审批直接按预案回滚。这条加严不是不信任业务，而是承认「预算为负时发布，风险已经由团队共同承担」，值守强度必须与之匹配。

**破例之后的额度修复计划**：例外只回答「这次能不能发」，不回答「账本怎么回正」。本例不做任何回填，靠三件事让预算自然滚出：一是把连接池上限固化进 `order-demo-config`（第 9 章起 `immutable: true`），消除同一类配置回退；二是把 3 天趋势告警的接收人从值班群改成周会主持人，让慢燃尽有人看；三是把大促期间的变更窗口收窄到每天 10:00–16:00，避开客服人力最薄的时段。随着 28 天滚动窗口逐步把 9 分钟的坏事件滚出去，`release_freeze` 自行回到 0——解冻由指标算出，不需要任何人宣布，这也是它能在下一次冲突里继续被相信的原因。

**与公理 5 的关系**：例外单本身也是一次 Git 变更，走 PR + 双签，不用聊天记录或邮件批准；口头批准在复盘时无法证明「当时谁认了这个额度」（见第 3 章）。


### SLI 口径修订的变更流程：修订 → 例外审批 → 规则回归单测

口径修订是最容易被「顺手改一下」的动作：把新路由加进排除项、把 4xx 从坏事件里拿掉、把旅程从全量 route 里拆出来、低流量服务改绝对量。每一次都同时改变分子、分母与历史可比性，因此必须当成一次有审批、有回归、有暗跑期的变更，而不是在 Prometheus UI 里改一行表达式 [R-20-1][R-20-6]。

```
[0] 触发：口径偏差证据
     · 新路由未进排除项 / 4xx 语义被判错 / 旅程拆分 / 低流量转绝对量
     产出：查询语句 + 时间窗 + 受影响请求数，写进 PR 描述（不接受「感觉不准」）
                         │
                         ▼
[1] 修订：同改三处声明
     observability/slo.yaml · observability/sli-recording-rules.yaml · docs/slo-contract.md
                         │
                         ▼ 闸门 A：promtool check rules 退出码 0
[2] 例外审批：EXC 编号 + 业务负责人、平台负责人双签（§20.4）
                         │
                         ▼ 闸门 B：无 EXC 编号的 observability/ 变更，CI 拒绝合并
[3] 回归单测：新增口径用例，同时保留旧用例做对照（用例矩阵见下）
                         │
                         ▼ 闸门 C：promtool test rules 全绿，四类用例齐全
[4] 暗跑 7 天：新旧两条记录规则并行，只有一条有判定权
                         │
                         ▼ 闸门 D：两口径差异 ≤ 预算的 10%
[5] 切主口径：release_freeze 指向新规则，旧规则标 deprecated 保留一个窗口
                         │
                         ▼ 闸门 E：切换后首小时 budget-report.sh 与暗跑末值一致
[6] 归档：契约版本 +1，记录断点日期与「预算不追溯」说明
```

| 闸门 | 命令 | 通过标准 | 失败处置 |
|---|---|---|---|
| A 语法 | `promtool check rules observability/sli-recording-rules.yaml` | 退出码 0 | 回 §20.4 修规则，禁止注释掉表达式过关 |
| B 授权 | `git log --oneline -- docs/slo-contract.md` 与 PR 审批记录对照 | 有本期 `EXC-` 编号，业务与平台各一个 approve | 回 §20.4 补签，CI 拒绝合并 |
| C 回归 | `promtool test rules observability/sli-rules-test.yaml` | 四类用例全绿（见下表） | 补用例，不得删旧用例换绿 |
| D 暗跑 | 新旧规则并行 7 天，对照 `./hack/budget-report.sh` | 两口径差异 ≤ 预算的 10%，差异来源写进 PR | 回 [1] 重写口径；差异无法解释则放弃本次修订 |
| E 切换 | 切换后首小时查 `slo:order_demo_gateway:release_freeze` | 与暗跑末值一致，无跳变 | `git revert` 回旧口径，例外保持未关闭 |
| F 归档 | `git log -1 --stat -- docs/slo-contract.md` | 契约版本 +1，断点日期已写 | 补记录，否则下次修订没有基线 |

**口径修订必须带的四类单测**（新增口径时全部保留，只增不删）：

| 用例 | 输入序列 | 期望 | 防的是什么 |
|---|---|---|---|
| 探针排除 | `/healthz` 高流量 + `/orders` 部分 503 | 探针不进分母，坏率不被稀释 | 有人为「降低坏率」把探针算进分母 |
| 4xx 归属 | `/orders` 400 与 503 各半 | 400 计好事件，503 计坏事件 | 把用户侧错误算成服务失效，或反向掩盖真故障 |
| 分母为 0 | 整个窗口无请求 | SLI 记 1，不触发冻结 | 夜间无流量误判「预算耗尽」 |
| 新口径边界 | 新增 route 的 5xx | 按新口径计入，旧口径不再计入 | 两套口径并存，同一批坏请求被记两次 |

**两条硬规则**：

1. **不追溯**：口径修订只从生效时刻起算，不重算历史预算、不回填已花掉的额度。契约里写清断点日期，否则同一条曲线会有两个含义，季度复盘无法对账。
2. **不并行**：新旧口径不得同时驱动 `release_freeze`。暗跑期只有一条规则有判定权，另一条只写指标；并行判定会让「冻结」变成掷硬币，也会让 §20.4 的例外单失去唯一的事实依据。
