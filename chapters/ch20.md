## 20.1 问题与反模式：大盘很绿，为什么没人敢说「可以继续发」

**合成案例**。周五 16:40，`order-demo` 的 gateway 完成一次常规发布。十几分钟后，客服转来几条「下单页偶发报错」，值班同学打开监控大盘：CPU 曲线平稳，内存没有爬升，Pod 全是 `Running`，`readyz` 全绿。真正变了的只有入口 5xx 的比例，可它既没有告警，也没人知道「涨到多少算不能忍」。争到 18:00，没人拿得出一句能被复核的话——**大盘回答的是「机器忙不忙」，没人回答「用户还好不好，以及现在这一版还能不能继续放」**。

这不是监控没装，而是判定标准没建。第 3 章把「SLO 先行于告警」写成了公理 7，并在一张 1 页最小 SLO 卡片里留了五个待填字段；本章才给这些字段正式、可测量、能驱动决策的定义。可用性目标不是一句口号，它必须落到「什么算一次好事件、在什么窗口里统计、超了额度谁来喊停」这三件事上 [R-20-4]。

三个高频反模式：

**反模式一：用 CPU 使用率当 SLI。** 现象是开头那一幕——用户已经拿到 5xx，资源曲线却一切正常，因为资源使用率衡量的是「系统忙不忙」，不是「用户这次请求成没成」。根因是把因果链上下游搞反了：CPU 高可能只是结果， CPU 正常也完全挡不住依赖超时、连接池耗尽、配置改错这类直接伤到用户的故障。本章的替代做法是只取**用户可感事件**做 SLI，即 gateway 入口上「有效请求里返回非 5xx 的比例」，把资源指标留给第 17 章的容量与饱和度分析 [R-20-4][R-20-6]。

**反模式二：目标写 99.99% 却没有预算策略。** 现象是目标定得很漂亮，决策时仍旧拍脑袋：「四个九」没有配套「谁批准例外、耗尽之后冻结什么、什么时候解冻」，等价于没有写。根因是把 SLO 当成对外承诺的口号，而不是产品与平台之间的**消耗额度**。错误预算的意义恰恰在于把「可用性与变更速度」摆到同一张账上：预算没花完，团队有权利快速发布；花完了，就得用冻结换回可靠性 [R-20-5]。本章要求目标必须与窗口、冻结阈值、例外审批人、解除条件一起成文，单给一个百分比不算定义完成。

**反模式三：只设一个窗口，或者干脆不设窗口。** 现象是「全年 99.9%」这类目标：一次 20 分钟的短故障能把全年额度吃掉大半，而一次持续低烈度的慢性劣化却因为被长窗口摊薄而长期不触发任何动作。根因是单一时间尺度同时承担了「快速止血」和「季度复盘」两种职责。本章的替代做法是一套滚动窗口加**快燃尽 / 慢燃尽双窗口**：短窗口负责 paging，长窗口负责趋势与 ticket，两者都由同一份错误预算推导 [R-20-3][R-20-4]。

> 三条反模式指向同一个缺口：**没有可测量的 SLI，就没有预算；没有预算，就没有发布判定**。第 1 章事故里 H8「告警响了却没有 runbook」的更深层原因也在这里：那条告警背后没有能说清「现在算不算坏、坏了该冻结什么」的 SLO（见第 22 章）。

## 20.2 范式与决策树：把五个字段填成一份能判定的契约

本章是 **SLO、SLI、错误预算** 的正式定义章。此前章节（见第 3 章）只在卡片层面给白话与占位，从本章起三者可以作为推理前提。

**SLI（Service Level Indicator）** 是「可直接测量的好坏比例」：一个分子、一个分母、一个测量点、一组排除项，四者缺一即不可测量。对 `order-demo` 的 gateway，本书定义为：

- **有效请求（分母）**：落到 `gateway` Service 8080 端口的 HTTP 请求，且 `route` 不属于探针路径 `/healthz`、`/readyz`、`/startup`（见第 8 章）。探针是平台自测流量，不是用户可感事件，计入分母会稀释真实的坏事件。
- **成功请求（分子）**：有效请求里 `status_code` 不属于 `5..` 的那些。4xx 属于用户侧或调用方错误，不计为服务失效；若某个 4xx 实为网关误判，属于 SLI 口径修订，走例外审批而不是临时改数。
- **测量点**：入口侧 `gateway`，由第 21 章的 OTel Collector 采集并落为 `order_demo_http_requests_total`；在客户端测会漏掉连不进来的请求，在 `api` 层测会漏掉网关自身故障。指标名与 label 白名单见第 21 章的规范表。
- **排除项**：探针路径、发布窗口内的主动压测流量、已知的演练注入（第 23 章），三者必须在记录规则里显式过滤，否则预算会被自己人吃掉。

**SLO** = SLI + 目标 + 时间窗口，是「对服务可靠性的量化承诺」。**错误预算** = 1 − SLO，是「在一个窗口内允许不可用的额度」；99.9% 的 28 天滚动目标，等价于允许 0.1% 的坏请求，按量换算就是这 28 天里可以「花掉」的失败请求总数。预算是额度而非目标：花得慢说明还有变更余量，花得快就说明该用冻结换稳定 [R-20-4][R-20-5]。

### 与第 3 章「1 页最小 SLO 卡片」字段一一对照（SP-02）

第 3 章的 `order-demo-slo-card` 只要求把五个字段填全、不检查数值是否合理；本章把同样的五个字段从「占位」升级为「判定」。字段名与取值口径逐字保持一致，不另起一套：

| 第 3 章卡片字段 | 卡片里的白话/占位 | 本章正式定义 | 落点 |
|---|---|---|---|
| `service` | `"gateway"` | SLO 作用对象＝服务名 + 用户旅程「下单请求经 gateway 到 api」 | `slo.yaml` 的 `spec.service` |
| `sli` | `"成功请求数 / 总请求数"` | 分子＝非 5xx 有效请求，分母＝有效请求，含测量点与排除项 | `sli-recording-rules.yaml` 的 `sli:order_demo_http_success:ratio_rate5m` |
| `window` | `"28d"` | 28 天滚动窗口；另设 1h / 6h / 3d 三个燃尽观察窗 | `spec.timeWindow` + 记录规则 |
| `objective` | `"99.9"` | 目标 99.9%，即错误预算 0.1% | `spec.objectives[].target: 0.999` |
| `freeze_rule` | `"错误预算耗尽则冻结非必要发布"` | 冻结阈值、冻结范围、例外审批人、解除条件四项成文 | `docs/slo-contract.md` |

> 差异只有一处且必须写明：第 3 章卡片落在 `order-demo-dev` 供填写，本章正式卡片落在 `order-demo-prod` 用于发布判定；**字段名、取值口径、单位完全一致**，环境差异只体现在命名空间与签字人，不体现在 SLO 数字上（配置契约见第 6 章、见第 4 章）。

### 错误预算窗口与冻结规则

| 项 | 取值 | 判据含义 |
|---|---|---|
| 主窗口 | 28 天滚动 | 与月度发布节奏对齐，短故障不会被摊薄到「全年」 |
| 预算方法 | Occurrences（按请求数） | 与 SLI「成功/有效」同口径，不引入时间片的主观加权 |
| 快燃尽窗口 | 1h + 5m，燃尽率 ≥ 14.4 | 1 小时花掉 2% 预算，paging（见第 22 章） |
| 慢燃尽窗口 | 6h + 30m，燃尽率 ≥ 6 | 6 小时花掉 5% 预算，ticket + 复核 |
| 趋势窗口 | 3d，燃尽率 ≥ 1 | 慢性劣化进周会复盘，不半夜叫人 |
| 冻结阈值 | 28d 剩余预算 ≤ 0 | 冻结**非必要发布**：功能发布、依赖升级、配置重构 |
| 冻结豁免 | 修故障的回滚、安全补丁、预算耗尽本身的止血变更 | 豁免不等于放行，须登记例外编号与到期时间 |
| 例外审批人 | 业务负责人 + 平台负责人双签 | 单方面由平台定目标不会被执行 |
| 解除条件 | 滚动窗口滚出坏事件后剩余预算 > 0，且连续 3 个快窗口无燃尽告警 | 不是「等下周一」，而是可查询的指标条件 |

燃尽率的定义是「单位时间消耗的预算 / 该时间窗应得预算」，14.4 这个数来自「1 小时花掉 28 天预算的 2%」：28 天＝672 小时，2% 预算对应 13.44 小时，672 ÷ 13.44 ≈ 50，习惯上取 14.4（对应 1h 消耗 2% 预算的近似倍数，不同资料取值略有差异，本书统一以本节规则文件为准）[R-20-3][R-20-4]。**关键不在小数，而在阈值必须从预算推导、且快/慢窗口同源**。

### 发布冻结判定决策树

```
本周剩余预算 > 0？                    否 → 冻结非必要发布，走例外审批（20.4）
        │ 是
近 1h / 5m 快燃尽 ≥ 14.4？           是 → 暂停发布并 paging，先止血（第 22、23 章）
        │ 否
近 6h 慢燃尽 ≥ 6？                   是 → 允许已开始的发布收尾，禁止新开，建 ticket
        │ 否
本次变更是否在冻结豁免清单内？        否 → 正常放行，按第 13 章回滚方案先行
        │ 是
→ 放行但登记例外编号、审批人、到期时间，下次复盘核对（CL-G-10）
```

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：告警阈值与发布冻结规则必须由同一份错误预算推导；先建告警再补 SLO，等于没有判定标准。同时，SLO 是产品与平台的双向契约，必须有业务方签字，单方面由平台定的目标不会被执行。
>
> **论证**：告警回答「现在要不要叫人」，冻结回答「现在能不能改」，两者其实是同一个问题的两种时间尺度：都在问「坏到什么程度就超出了我们 agreed 的额度」。若先按经验拍一个「5xx > 1% 告警」，再补一个「99.9% SLO」，两条线彼此无关，值班时就会出现「告警响了但预算还剩很多」或「预算耗尽却没告警」的错位。反过来，从 `1 − SLO` 出发，燃尽率阈值、冻结阈值、豁免范围都能被一条算式复核。至于签字：冻结会挡住业务排期，只有批准排期的人也批准了额度，冻结才不会在第一次冲突时被绕过。
>
> **反例与适用前提**：这不等于「所有服务都必须 99.9% / 28 天」。内部离线 `worker`（见第 7 章）没有用户可感的在线请求，用成功率做 SLI 不成立，应改用「任务积压时长 / 超时关单率」；刚上线的服务流量太小，比例型 SLI 会被单个请求剧烈拉扯，应先用绝对量观察一个窗口再定目标。若组织已有跨部门签署的可靠性契约与独立审批流，可直接沿用其窗口与阈值，但仍须能拿出「阈值由预算推导」的等价证据，否则本书的推导链不成立。

## 20.3 工具选型：本章不引入新后端，只做「表达层 + 实现层」

第 20 章不新增采集或存储组件。按 D-06 裁决，本章的 L1 依据由 **OpenSLO 1.x 规范**（表达层）与 **Prometheus 3.x 记录/告警规则官方文档**（实现层）共同提供；整套唯一示例实现仍取 `decisions.md`：OTel Collector → Prometheus / Loki / Tempo，长期指标用 Thanos 或兼容远端存储（见第 21 章）。本章只用其中的 Prometheus 规则引擎把 SLI 与预算算出来 [R-20-1][R-20-2][R-20-3]。

| 工具 | 主版本 | 本章角色 | 何时不该用 |
|---|---|---|---|
| OpenSLO | 1.x（`openslo/v1`） | 把 SLO 写成与厂商无关的声明式契约，供人审阅与跨工具交换 | 只想要一条 Prometheus 告警、没有跨工具/跨团队交换需求时；多一层抽象反而没人维护 |
| Prometheus 记录规则 / 告警规则 | 3.x | 落地 SLI 分子分母、多窗口燃尽率、冻结判定 | 指标尚未采集到位时（依赖第 21 章）；规则写好了没有数据，等于空跑 |
| Sloth / Pyrra（SLO 生成器） | 0.x | 由简写 SLO 自动生成多窗口燃尽规则 | 团队需要逐行评审规则（本书要求）、或已有等价记录规则时；生成器会遮住推导过程 |
| 托管 SLO  SaaS | — | 跨云统一看板与报表 | 指标必须出集群、或预算判定要进 Git 门禁时；判定逻辑落在外部，无法 `git revert` 回退 |
| Thanos / 兼容远端存储 | 0.x | 28 天以上长期指标与全局查询（第 21 章） | 只要 2 周本地保留、无跨集群查询时；引入对象存储与 compactor 是纯增成本 |

**最小接入 diff**：本章只新增 `observability/slo.yaml`、`observability/sli-recording-rules.yaml`、`observability/sli-rules-test.yaml`、`docs/slo-contract.md`、`hack/budget-report.sh` 五个仓库文件，不改应用镜像、不改 Deployment 字段，因此**不涉及产物晋升**（见第 12 章）。规则由 Kustomize 5.x overlay 挂到 `observability` 命名空间的 Prometheus 3.x rule 配置，随 Argo CD 2.x 同步（见第 14 章）；`git-<sha7>` 标签与 `order-demo-config` 的既有契约一律不动。

**升级 / 回滚路径**：改目标、改窗口、改阈值都只改这五个文件，走 PR + `promtool test rules` 后由 Argo CD 收敛；升级 Prometheus 小版本时先跑规则单测再切，`promtool check rules` 是硬门禁（§20.5）。回滚不碰集群命令式状态，见 §20.5。工具小版本锁在附录 A，正文只写主版本 [R-20-2]。

## 20.4 落地配置（完整可应用文件，Kubernetes 1.32+，Prometheus 3.x / OpenSLO 1.x）

> 全部文件沿用配置契约：服务 `gateway`、端口 8080、探针路径 `/healthz` `/readyz` `/startup`、公共标签 `app.kubernetes.io/name=order-demo`、镜像 `registry.example.com/order-demo/gateway:git-<sha7>`；`managed-by` 自第 14 章起为 `argocd`。`git-1a2b3c4` 为示例 SHA。适用 K8s 版本 1.32+，Prometheus / OpenSLO 小版本指向附录 A。

**`observability/slo.yaml`——OpenSLO 1.x 契约（表达层）**

```yaml
apiVersion: openslo/v1
kind: SLO
metadata:
  name: gateway-availability
  displayName: "gateway 下单入口可用性"
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  service: gateway
  description: "下单请求经 gateway 到 api 的非 5xx 比例，探针路径不计入有效请求"
  indicator:
    metadata:
      name: gateway-availability-sli
    spec:
      ratioMetric:
        counter: true
        good:
          source: prometheus
          queryType: promql
          query: >-
            sum(rate(order_demo_http_requests_total{
              service="gateway",
              route!~"/healthz|/readyz|/startup",
              status_code!~"5.."
            }[5m]))
        total:
          source: prometheus
          queryType: promql
          query: >-
            sum(rate(order_demo_http_requests_total{
              service="gateway",
              route!~"/healthz|/readyz|/startup"
            }[5m]))
  timeWindow:
    - duration: 28d
      isRolling: true
  budgetingMethod: Occurrences
  objectives:
    - displayName: "28 天可用性 99.9%"
      target: 0.999
      timeSliceTarget: 0.999
      timeSliceWindow: 5m
```

**`observability/sli-recording-rules.yaml`——Prometheus 3.x 记录与告警规则（实现层）**

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: order-demo-slo-rules
  namespace: observability
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
    role: alert-rules
spec:
  groups:
    - name: order-demo-sli
      interval: 30s
      rules:
        - record: sli:order_demo_http_good:rate5m
          expr: >-
            sum(rate(order_demo_http_requests_total{
              service="gateway",
              route!~"/healthz|/readyz|/startup",
              status_code!~"5.."
            }[5m]))
        - record: sli:order_demo_http_valid:rate5m
          expr: >-
            sum(rate(order_demo_http_requests_total{
              service="gateway",
              route!~"/healthz|/readyz|/startup"
            }[5m]))
        - record: sli:order_demo_http_success:ratio_rate5m
          expr: >-
            sli:order_demo_http_good:rate5m
            / clamp_min(sli:order_demo_http_valid:rate5m, 0.0001)
        - record: sli:order_demo_http_bad:ratio_rate5m
          expr: '1 - sli:order_demo_http_success:ratio_rate5m'
    - name: order-demo-error-budget
      interval: 30s
      rules:
        - record: slo:order_demo_gateway:error_budget_ratio
          expr: '1 - 0.999'
        - record: slo:order_demo_gateway:burn_rate_1h
          expr: >-
            avg_over_time(sli:order_demo_http_bad:ratio_rate5m[1h])
            / on() group_left() slo:order_demo_gateway:error_budget_ratio
        - record: slo:order_demo_gateway:burn_rate_6h
          expr: >-
            avg_over_time(sli:order_demo_http_bad:ratio_rate5m[6h])
            / on() group_left() slo:order_demo_gateway:error_budget_ratio
        - record: slo:order_demo_gateway:burn_rate_3d
          expr: >-
            avg_over_time(sli:order_demo_http_bad:ratio_rate5m[3d])
            / on() group_left() slo:order_demo_gateway:error_budget_ratio
        - record: slo:order_demo_gateway:budget_consumed_ratio_28d
          expr: >-
            sum_over_time(sli:order_demo_http_bad:ratio_rate5m[28d])
            * 300
            / on() group_left()
            (sum_over_time(sli:order_demo_http_valid:rate5m[28d]) * 300 * 0.001)
        - record: slo:order_demo_gateway:release_freeze
          expr: 'slo:order_demo_gateway:budget_consumed_ratio_28d >= 1'
        - alert: GatewayErrorBudgetFastBurn
          expr: >-
            slo:order_demo_gateway:burn_rate_1h >= 14.4
            and slo:order_demo_gateway:burn_rate_5m >= 14.4
          for: 2m
          labels:
            severity: paging
            service: gateway
          annotations:
            summary: "gateway 错误预算快燃尽（1h 燃尽率 >= 14.4）"
            runbook: "docs/runbooks/gateway-fast-burn.md"
            slo: "gateway-availability"
        - alert: GatewayErrorBudgetSlowBurn
          expr: 'slo:order_demo_gateway:burn_rate_6h >= 6'
          for: 15m
          labels:
            severity: ticket
            service: gateway
          annotations:
            summary: "gateway 错误预算慢燃尽（6h 燃尽率 >= 6）"
            runbook: "docs/runbooks/gateway-slow-burn.md"
            slo: "gateway-availability"
```

> `burn_rate_5m` 由同一份 `sli:order_demo_http_bad:ratio_rate5m` 在 5 分钟窗口上取均值，规则文件里以 `avg_over_time(sli:order_demo_http_bad:ratio_rate5m[5m])` 展开；上式 `GatewayErrorBudgetFastBurn` 的第二个条件在完整规则中写作 `avg_over_time(sli:order_demo_http_bad:ratio_rate5m[5m]) / on() group_left() slo:order_demo_gateway:error_budget_ratio >= 14.4`，与 1h 条件同源，避免快窗口单靠一次抖动触发。冻结判定 `release_freeze` 为布尔记录规则（1＝冻结），供第 22 章路由与 `hack/budget-report.sh` 直接查询；它只表达判定，真正的冻结动作由发布门禁读取，不在本规则里改集群。本节末尾两条 `- alert:` 只是判定链自检的最小示意，生产告警集由第 22 章 `alert-rules.yaml` 统一承载（见第 22 章），接入生产前按其「一致性备注」处理，避免重复评估。

**`docs/slo-contract.md`——与第 3 章卡片字段一一对应的完整模板（业务签字版）**

```markdown
# order-demo / gateway 可用性 SLO 契约

## 一、卡片字段（字段名与 ch03 `order-demo-slo-card` 逐字一致）
- service: gateway
- sli: 非 5xx 有效请求数 / 有效请求数
- window: 28d（滚动）
- objective: 99.9
- freeze_rule: 28 天剩余错误预算 <= 0 时冻结非必要发布

## 二、可测量定义（第 20 章正式口径）
- 有效请求：gateway Service 8080 上 route 不属于 /healthz /readyz /startup 的 HTTP 请求
- 成功请求：有效请求中 status_code 不属于 5.. 的请求
- 测量点：入口 gateway，指标 order_demo_http_requests_total（命名规范见第 21 章）
- 排除项：探针流量、发布窗口主动压测、演练注入
- 分母为 0 的处理：clamp_min 保护，分母为 0 时 SLI 记为 1，不产生坏事件

## 三、错误预算与窗口
- 错误预算 = 1 - 0.999 = 0.001（按 Occurrences 计）
- 快燃尽：1h / 5m 双窗 >= 14.4 → paging（第 22 章）
- 慢燃尽：6h >= 6 → ticket；3d >= 1 → 周会复盘
- 冻结判定：slo:order_demo_gateway:release_freeze == 1

## 四、冻结规则
- 冻结范围：功能发布、依赖升级、配置重构
- 豁免范围：回滚、安全补丁、止血变更（须登记例外）
- 例外审批：业务负责人 + 平台负责人双签
- 例外登记：编号 EXC-YYYYMMDD-NN、前提、补偿措施、到期时间（沿用第 3 章例外机制）
- 解除条件：剩余预算 > 0 且连续 3 个快窗口无燃尽告警

## 五、签字与生效
| 角色 | 姓名 | 签字日期 | 备注 |
|---|---|---|---|
| 业务负责人 | <填写> | <YYYY-MM-DD> | 批准额度与冻结对排期的影响 |
| 平台负责人 | <填写> | <YYYY-MM-DD> | 批准测量点与规则实现 |
| 值班代表 | <填写> | <YYYY-MM-DD> | 确认 paging 路由可达（第 22 章） |
- 生效日期：<YYYY-MM-DD>
- 复审周期：每季度一次，或在两次预算耗尽后提前复审
- 变更方式：仅通过本文件 + observability/ 下规则文件的 PR，禁止在 UI 改数
```

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：SLO 契约里「业务方签字」不是走形式的表格，而是冻结规则能否被执行的前提；字段表、预算表、冻结表、签字表必须凑齐才算一份完整 SLO。
>
> **论证**：冻结会直接挡住业务排期。若只有平台单方面定了 99.9%，第一次撞上大促排期时，最省事的做法一定是临时把目标调低或口头放行，规则随即失效。让批准排期的人也批准额度，冲突就变成了「按我们共同签的账办事」，而不是「平台卡业务」。四张表分别对应「测什么、允许多少、超了怎么办、谁认账」，缺任何一张，决策都会退回拍脑袋。
>
> **反例与适用前提**：对纯内部、无外部 SLA、且业务与平台同属一个小组的工具类服务，双签可简化为一次评审记录；但「谁批准例外」这一栏不能空。对已有正式 SLA 合同且罚则明确的对外服务，SLO 目标应不宽于合同，冻结规则可更严，不能更松。

**`hack/budget-report.sh`——本周预算消耗与冻结判定（完整可复制）**

```bash
#!/usr/bin/env bash
set -euo pipefail

PROM="${PROM:-http://prometheus.observability.svc.cluster.local:9090}"
SERVICE="${SERVICE:-gateway}"
WINDOW="${WINDOW:-28d}"

query() {
  curl -fsS --data-urlencode "query=$1" "${PROM}/api/v1/query" \
    | jq -r '.data.result[0].value[1] // "NaN"'
}

GOOD="$(query "sum(increase(order_demo_http_requests_total{service=\"${SERVICE}\",route!~\"/healthz|/readyz|/startup\",status_code!~\"5..\"}[${WINDOW}]))")"
VALID="$(query "sum(increase(order_demo_http_requests_total{service=\"${SERVICE}\",route!~\"/healthz|/readyz|/startup\"}[${WINDOW}]))")"
CONSUMED="$(query "slo:order_demo_gateway:budget_consumed_ratio_28d")"
FREEZE="$(query "slo:order_demo_gateway:release_freeze")"

awk -v g="${GOOD}" -v v="${VALID}" -v c="${CONSUMED}" 'BEGIN {
  sli = (v + 0 > 0) ? g / v : 1;
  printf "SLI(28d)=%.6f  有效请求=%.0f  成功请求=%.0f\n", sli, v, g;
  printf "错误预算消耗=%.2f%%  剩余=%.2f%%\n", c * 100, (1 - c) * 100;
}'
if [ "${FREEZE}" = "1" ]; then
  echo "判定：冻结非必要发布（走 docs/slo-contract.md 例外审批）"
  exit 2
else
  echo "判定：预算未耗尽，可按第 13 章回滚方案先行原则发布"
fi
```

> 脚本用集群内地址 `prometheus.observability.svc.cluster.local:9090`，不依赖外部网络；`exit 2` 让发布流水线把「冻结」当硬失败，而不是打印一行警告后继续 [R-20-5][R-20-6]。
