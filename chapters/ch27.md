## 27.1 问题与反模式：一个重复动作，值不值得给集群加一种新资源

**合成案例**（教学合成，非真实事件）：某平台组接到「每天凌晨调一次 `gateway` 副本数」的需求，有人提议「写成 Operator，最云原生」。集群从 1.31 升到 1.32，未加 schema 校验的 CRD 字段被拒绝、控制器起不来；因没配告警，业务静默降级两天才被发现。想卸载时，CR 实例的 `metadata.finalizers` 挂着 `ops.example.com/cleanup`，控制器已不在，对象卡在 `Terminating`、命名空间删不掉 [R-27-2][R-27-4][R-27-5]。复盘时才问出第一天就该问的：**一个 CronJob 加一行 HPA 就能做完，为什么要给集群增加一种新资源类型？**

这不是 K8s 缺陷，控制器 / finalizer / 版本校验都在按文档工作，失控的是**决策**：把「有个重复动作」直接等价于「该写 Operator」[R-27-1][R-27-7]。第 5 章已把「引入 CRD」列为需书面论证的选项，本章把那条警戒线展开成可判定的决策树。

三个高频反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：把一次性或周期性脚本包装成 Operator。** 现象是多了一套要升级、要备份、要值班的控制器，业务只得到「每天改一个数」；根因是把「自动化」和「扩展 API」混为一谈。替代做法是先走 27.2 五选一决策树，把「原生资源 / 配置打包 / CI 脚本 / Webhook 或策略」四种更轻的方式逐一排除，只剩「确实需要持续观测并收敛」时才落在自定义控制器 [R-27-7][R-27-8]。

**反模式二：reconcile 里做长耗时阻塞，把 `status` 当数据库。** 现象是 worker 被慢调用占满、其他对象饿死，控制器重启后状态失真；根因是混淆了 `spec`（期望，人写）与 `status`（观测结果，控制器写），把中间状态持久化进 `status` 供下一轮读取——循环一旦依赖上一轮中间态，就不再幂等、不再可重入 [R-27-2][R-27-4]。替代做法是短循环 + 幂等 + 重入队列，见第 28 章。

**反模式三：只定义 `v1alpha1`，从不规划版本迁移。** 现象是升级时 API Server 拒绝旧对象、转换 webhook 仓促上阵、存量的 CR 无处可去；根因是把 CRD 当成「一份配置」而不是「一个有生命周期的 API」。本章的替代做法是把版本迁移路径、storage 版本轮转、卸载残留检查写进引入前的负债清单 [R-27-5]。

### 27.1.1 深度复盘：一次「脚本包装成 Operator」的升级失败（合成案例）

本节开头的合成案例只有一句结论。把 41 天摊成时间线才看得清：升级失败从不是一次事故，而是五个决策依次埋下的坑，**每个坑在当时都「看起来是对的」**。

| 日期 | 做了什么 | 当时看起来对的地方 | 后来成为根因的地方 |
|---|---|---|---|
| D0 | 业务提「每天 00:05 把 `gateway` 调到 3 副本，08:00 调回 2」，每周 7 次 | 指令明确、终态清楚 | 终态就是副本数，`HPA` + `CronJob` 已能表达（决策树第 ① 项） |
| D2 | 平台组用 Kubebuilder 4.x 起骨架，定 `v1alpha1`，字段 `spec.replicas` + `spec.reason` | 脚手架默认生成 schema，「有校验了」 | 只有单版本、无迁移路径；`reason` 纯装饰，无人读取 [R-27-5] |
| D5 | Helm 装控制器与 CRD，Argo CD 同步；脚本每天 `kubectl apply` 一份 CR | 一次提交，两条路径都能改副本 | CR 由脚本生成、不落 Git，漂移无人知（公理 5 的反面） |
| D18 | 为「周末不同」加 `spec.schedule.timezone`（`type: string`），并**设为 `required`** | 新对象一定带时区，数据更干净 | 在 alpha 版本上做破坏性变更，存量 3 个 CR 全都没有该字段 |
| D20 | CRD 变更与控制器镜像同一批发版 | 一条流水线发完，省一次评审 | 没有先后顺序与观察窗口 [R-27-5] |
| D21 02:00 | 所有 reconcile 报 `spec.schedule.timezone: Required value`，副本数不再变化 | `kubectl get pods` 全绿，控制器「在跑」 | 健康检查只测进程存活，不测「能不能写 `status`」 |
| D23 09:00 | 业务方投诉「早上很卡」才发现 | — | 没有「最后一次成功协调时间」告警（第 22 章） |

**定位过程**（六步，每步都有可判定的判据，不要在第一步就 `describe` 一切）：

```bash
# 第 1 步：控制器进程活着吗？先排除「Pod 挂了」这个最常见的误判
kubectl -n ops-system get pods -l control-plane=controller-manager
# 判据：READY 1/1、RESTARTS 0 → 进程活着，问题不在「起不来」，而在「每轮都失败」

# 第 2 步：是「个别对象失败」还是「全量失败」？用错误条数对比对象数
kubectl -n order-demo-prod get scaleschedule --no-headers | wc -l
kubectl -n ops-system logs deploy/scaleschedule-controller --since=10m | grep -c 'Reconciler error'
# 判据：两个数字同阶（3 个对象 / 10 分钟内 3 的整数倍条错误）→ 每轮都撞同一堵墙，不是个别脏数据

# 第 3 步：把失败原因捞出来——控制器未必把原因打到第一行
kubectl -n ops-system logs deploy/scaleschedule-controller --tail=100 | grep -i 'invalid\|required value'
kubectl -n order-demo-prod get events --sort-by=.lastTimestamp | tail -20

# 第 4 步：区分「schema 拒绝」与「权限拒绝」——两者处置完全不同
kubectl -n order-demo-prod get scaleschedule order-demo-prod-nightly -o yaml \
  | sed -n '/^spec:/,/^status:/p'
# 判据：spec 里没有 schedule.timezone → 存量对象缺字段，属校验失败；若为 RBAC 问题会直接报 forbidden

# 第 5 步：把 CRD 的「已建立」与「已存版本」一起看
kubectl get crd scaleschedules.ops.example.com \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}{.status.storedVersions}{"\n"}'
# 判据：NamesAccepted / Established 均为 True → 类型注册没问题，失败发生在对象写入阶段 [R-27-3]

# 第 6 步：手工复现一次写入，把「读失败」与「写失败」彻底分开
kubectl -n order-demo-prod annotate scaleschedule order-demo-prod-nightly \
  probe=manual-$(date +%s) --dry-run=server -o yaml >/dev/null
# 判据：返回 Required value → 该对象本身过不了校验，控制器每轮都会被同一堵墙挡住
```

第 6 步是关键分水岭：如果 `annotate --dry-run=server` 成功、只有控制器失败，问题在控制器（字段名拼错、`status` 写错子资源）；如果像本案一样失败，问题在对象与 schema，控制器是无辜的。**把「控制器坏了」与「控制器被拒绝」分开，能省掉一半排查时间。**

**止血与回填**（两步走，禁止一步到位）。新增必填字段是破坏性变更，正确顺序是 expand（可选 + 默认值 + 回填）→ contract（收紧为 `required`），与第 16 章的数据库 expand–contract 同构。生产上只有一条合法路径：`git revert` 那个把 `timezone` 设为 `required` 的 PR，由第 14 章控制器同步回上一版；下面的 `kubectl patch` 是本地 kind 复现形态，用于演练「没有 Git 时会发生什么」，**不在生产执行**（公理 5）。

```bash
# 0) 先备份 CRD 与全部 CR —— 回退前必须有，且必须在改之前
kubectl get crd scaleschedules.ops.example.com -o yaml > /tmp/crd-$(date +%Y%m%d).yaml
kubectl -n order-demo-prod get scaleschedules.ops.example.com -o yaml > /tmp/cr-$(date +%Y%m%d).yaml

# 1) 止血：把 required 收回到只有 replicas（先让协调恢复，不是最终状态）
kubectl patch crd scaleschedules.ops.example.com --type=json -p='[
  {"op":"replace","path":"/spec/versions/0/schema/openAPIV3Schema/properties/spec/required","value":["replicas"]}
]'

# 2) 回填：字段已可选，此时给每个存量对象补值才不会被拒
for cr in $(kubectl -n order-demo-prod get scaleschedules.ops.example.com -o name); do
  kubectl -n order-demo-prod patch "$cr" --type=merge \
    -p '{"spec":{"schedule":{"timezone":"Asia/Shanghai"}}}'
done

# 3) 验证协调恢复：错误归零、status 有推进
kubectl -n ops-system logs deploy/scaleschedule-controller --since=5m | grep -c 'Reconciler error'
kubectl -n order-demo-prod get scaleschedule order-demo-prod-nightly \
  -o jsonpath='{.status.observedGeneration}{" "}{.metadata.generation}{"\n"}'
# 通过标准：错误计数为 0；observedGeneration == generation → 这一代 spec 真的被协调过

# 4) 收紧回到 required 是第二个 PR：等回填跑满一个发布窗口，且新对象 100% 带该字段后再做
```

**五条可复用判据**：① 先分清「进程活着」与「协调成功」，`Running` 不是健康 [R-27-2]；② alpha 版本上禁止加必填字段，要加就走 expand–contract；③ CRD 变更与控制器镜像分两个 PR，中间留观察窗口；④ 必须有「最后一次成功协调时间」告警，而不是只告 `Pod` 不 `Ready`（第 22、28 章）；⑤ 卸载路径在引入那天就写好——finalizer 不会等你准备好。

**发布顺序本身也是一条判据**，而且方向取决于变更类型：**新增可选字段**时，CRD 必须先于控制器发布，否则新控制器写的字段会被旧 schema 剪枝掉；**收紧校验（加 `required`、收窄 `enum`、改类型）**时，必须反过来——先发能兼容旧数据的控制器、再发 CRD，并把存量回填夹在中间。本案错在把「收紧校验」按「新增字段」的顺序发了：CRD 与控制器同一批，等于同时换掉读方与写方的约定，中间没有一瞬间是自洽的。这条判据可以用一句话验收：**任何时刻，集群里正在服务的 CRD 版本必须能被正在运行的控制器完整读写**。

最后算一次账：该动作的年化收益 = 每天 2 次 × 1 分钟 × 365 ≈ **12 人时/年**；而 Operator 年化维护 ≥ 12 人日/年（见 27.2.2 矩阵），再加这次 2 天排查与两轮发布窗口，收益成本比约 1:10 倒挂。真正该用的是 `HPA`（按负载，见第 18 章）加一个 `CronJob` 定时调整 `minReplicas`，终态仍由原生对象表达——决策树第 ① 项，命中即停 [R-27-8][R-27-9]。

> **本章是三个术语的正式定义章**：CRD、Operator、finalizer。控制循环定义见第 2 章，本章不重复（SP-17）；第 5、16 章的白话伏笔在此兑现。定义之前不拿它们当推理前提。

## 27.2 范式与决策树：什么时候真的需要扩展 K8s API

**CRD（CustomResourceDefinition）** 的本书定义：给 Kubernetes 增加一种自定义资源类型。可验证形态是两条命令都能给出结果——`kubectl api-resources --api-group=<group>` 能列出一个新的 `kind`，且 `kubectl get <kind> -A` 能返回该类型的对象；只往 etcd 里塞数据、没有注册类型，不算 CRD [R-27-3]。

**Operator** 的本书定义：**CRD + 协调循环**。它把某个领域的运维知识编码进控制器，让集群持续把实际状态收敛到 `spec` 声明的期望状态；`status` 只承载观测结果 [R-27-1]。注意这个定义是「组合式」的：只有 CRD 没有控制器，是一张需要人去填的表；只有控制器没有 CRD，是在运维别人定义的对象。两者齐备才叫 Operator。

由此得到三条不可混用的语义，每条都能用命令证伪 [R-27-4]：

| 语义 | 谁写 | 表达什么 | 违反时可观察的现象 |
|---|---|---|---|
| `spec` | 人 / Git | 期望状态 | 控制器去改 `spec`，等于自己改自己的输入 |
| `status` | 控制器 | 观测结果 | 把「下一步该做啥」写进 `status`，控制器重启后流程走偏 |
| `metadata.finalizers` | 控制器 | 删除前必须完成的清理 | 清理没跑完就摘掉，外部资源（PVC、云上实例）永久残留 |

**协调循环（reconciliation）** 是控制循环在 Operator 语境下的形态：持续比对实际状态与期望状态并收敛。第 2 章已定义控制循环，这里只补三条工程约束，它们都是可测的 [R-27-2]：① **幂等**——同一份 `spec` 反复触发，副作用只发生一次（用 `observedGeneration` 去重）；② **可重入**——循环在任何一行被中断后重跑，结果不变；③ **容忍重复事件**——Informer 会重复投递，控制器不能假设「收到一次 = 只做一次」。这三条是第 28 章幂等性测试要验的东西，本章只立判据。

**finalizer 的正式定义**（兑现第 16 章白话伏笔）：它是 `metadata.finalizers` 里的一组清理钩子标记。对象被 DELETE 且该字段非空时，API Server **不会真正删除对象**，只设 `metadata.deletionTimestamp`、把对象留在 `Terminating`；持有该 finalizer 的控制器完成外部清理后必须主动移除这一项，删除才继续 [R-27-4]。卡住只有三种根因：控制器不在了、无对应 RBAC、清理逻辑报错。可验证判据：`kubectl get <kind> <name> -o yaml` 里 `deletionTimestamp` 与 `finalizers` 同时非空，就是「被挡住」而非「kubectl 卡了」（命令见 27.5）。这也解释了第 16 章卸载清单为何必须「先删实例、等清理、最后删控制器」，以及为何禁止 `--force --grace-period=0` 或手工 patch 跳过清理。

**本章要回答的决策问题**：有个重复运维动作，到底该用哪种扩展方式？下面这棵决策树按「成本从低到高」排列，命中即停，越往下长期负债越重 [R-27-9]：

```
这个动作的终态能用原生资源表达吗？
  （Deployment / StatefulSet / CronJob / HPA / PDB）            是 → ① 原生资源，停
        │ 否
差异只是「同源清单在不同环境取不同值」？                        是 → ② 配置打包（Helm 4.x / Kustomize 5.x），停
        │ 否
动作是一次性或周期性的，没有「持续比对并收敛」的需求？            是 → ③ CI 脚本 / CronJob，停
        │ 否
需求是「在对象进集群前校验或改写它」，不需要长期运行状态？        是 → ④ Webhook 或策略（VAP / Kyverno 1.x），停
        │ 否
需要持续观测 + 收敛 + 有明确领域模型，
且团队能长期承担 CRD 负债（版本、备份、卸载、告警、责任人）？      是 → ⑤ 自定义控制器（CRD + Operator，Kubebuilder 4.x，见第 28 章）
        │ 否
→ 写一份「本项目不写 Operator」的 ADR，回 27.3 在前四种里选一种
```

**扩展方式五选一判据表**（列含适用前提 / 维护成本 / 何时不该用 / 退出方式）：

| 方式 | 适用前提 | 维护成本 | 何时不该用 | 退出方式 |
|---|---|---|---|---|
| ① 原生资源 | 终态能由 `Deployment` / `CronJob` / `HPA` / `PDB` 直接表达 | 最低，随 K8s 版本走 | 需要跨多个资源协同、且协同逻辑有领域语义时 | 删清单即可，无类型残留 |
| ② 配置打包（Helm 4.x / Kustomize 5.x） | 差异只是同源清单的参数化 | 低，渲染产物可 review | 需要按运行时状态动态决策时（模板是静态的） | 保留渲染产物，换生成器，见第 5、10 章 |
| ③ CI 脚本 / CronJob | 一次性或周期性动作，无持续收敛需求 | 低，进流水线即可审计 | 动作必须响应对象状态变化、或被手工改动后自动纠正时 | 删流水线步骤 / 删 CronJob |
| ④ Webhook 或策略（VAP / Kyverno 1.x） | 只需在准入时校验或变更，不持有运行时状态 [R-27-6] | 中，策略库与 CI 侧同库 | 需要在对象创建之后持续调谐、或调用外部慢 API 时 | 策略先置 `audit` → 删策略 → 卸载，见第 25 章 |
| ⑤ 自定义控制器（CRD + Operator） | 有明确领域模型、需要持续观测并收敛、有人长期负责负债 [R-27-1] | 高：版本迁移、备份、卸载、告警、RBAC 全要负责 | 前四种任一能解决时；20 人团队无平台组时（见第 5 章警戒线） | 先删全部 CR 实例 → 确认 finalizer 清空 → 再删 CRD → 最后卸载控制器，见 27.5 |

### 27.2.1 决策树的三个量化判据

27.2 决策树里，第 ⑤ 项的条件是「团队能长期承担 CRD 负债」——这句话不可判定，落到评审会上就会变成「我们觉得能扛」。本节把它拆成三个能算的数，任一不过就停在 ⑤ 之前，并把被否的那个数写进 ADR 的「不选的理由」栏。

**判据一：年化手工工时 `H`（决定「值不值得自动化」）**

```
H = f × t × 52 / 60      f = 每周手工执行次数，t = 单次耗时（分钟）
阈值：H ≥ 40 人时/年 才进入「该自动化」的讨论；H < 40 直接回 ① 或 ③
```

40 人时约等于一个小型迭代的人力，低于它，任何自动化的**评审与维护成本**都超过收益。注意这条只回答「要不要自动化」，不回答「要不要扩展 API」——27.1.1 里的团队把 `H` 算对了（他们确实每天要动两次），却跳过了判据二，于是答错了题。

**判据二：漂移可容忍窗口 `T_tol`（决定「要不要控制器」）**

`T_tol` = 对象被改坏到业务可感知之间最长的时间；`T_script` = 你能接受的最密巡检周期（`CronJob` 5 分钟一轮已算激进，1 分钟一轮的轮询本身就有成本）。

- `T_tol ≥ T_script` → ③ 脚本 / `CronJob` 够，因为「最坏延迟 = 一个巡检周期」仍在容忍内；
- `T_tol < T_script`，或业务要求「对象一被改就纠回」这类**事件驱动**语义 → 才轮到 ⑤，因为轮询在物理上做不到。

`order-demo` 的实测值：副本数被改错，业务影响要到下一个流量高峰才显现，`T_tol` ≈ 2 小时；`CronJob` 10 分钟一轮，`T_script` = 10 分钟。`T_tol` 比 `T_script` 大一个数量级，脚本足够，控制器是过度设计。

**判据三：负债承载率 `R`（决定「养不养得起」）**

每个 CRD 的年化维护成本按 **12 人日**估（版本迁移 3、K8s 升级兼容 2、值班与告警处置 4、备份与卸载演练 2、文档与交接 1；每项的交付物见 27.2.2 矩阵，逐项可验收）：

```
R = (平台组年可支配工程工时 × 20%) / (12 人日 × 现存 CRD 数 + 12 人日)
阈值：R ≥ 1 才允许新增一个 CRD；R < 1 时 ADR 必须写「暂不引入」并给复评触发条件
```

20% 是「平台组把八成工时交给业务线支撑」这一常见分配下留给自身工具建设的上限，本章取它作保守值；`R < 1` 说明新增的这个 CRD 会挤占已有 CRD 的维护预算，九项负债里必然有某几项静默失守。

| 判据 | 阈值 | 不通过时停在 | 证据要落在哪 |
|---|---|---|---|
| ① 年化手工工时 `H` | ≥ 40 人时/年 | ① 原生资源（或 ③ 的轻量形态） | ADR 里写实测 `f` 与 `t`，不写「很频繁」 |
| ② 漂移窗口 `T_tol` | `T_tol ≥ T_script` 时停 ③；`T_tol < T_script` 才可进 ⑤ | ③ CI 脚本 / `CronJob` | 一次真实漂移的「发生到发现」时长 |
| ③ 负债承载率 `R` | ≥ 1 | ④ 之后写「暂不引入」 | 平台组工时台账 + 现有 CRD 清单 |

**代入 `order-demo` 的算术**（三票全否，这就是 ADR 0003 里那句「收益是想象出来的，成本是确定的」的来历）：判据一，`f=7`、`t=5` → `H ≈ 30` 人时/年 < 40，连「该自动化」都不成立，`HPA` 直接表达终态；判据二，`T_tol` ≈ 2 小时 > `T_script` = 10 分钟，脚本足够；判据三，现存 CRD 为 0、平台组可支配工时为 0（无专职平台），分子为 0 → `R = 0`，任何一个 CRD 都养不起。三条判据都指向同一个结论，比「我们觉得不需要」有力得多 [R-27-7][R-27-9]。

**反模式：只算判据一就开工。** 现象是「确实很烦，确实该自动化，所以写 Operator」；根因是把「自动化」偷换成「扩展 API」。判据一通过只证明「该有自动化」，第 ①–④ 项全都是自动化的合法形态，第 ⑤ 项额外要求的是**持续收敛 + 长期负债承载**，必须由判据二、三单独放行。

**一个三项都过的例子**（说明这组判据不是「一律否掉」）：某平台组要给「云上负载均衡」做生命周期管理——手工开一次要 40 分钟、每周 5 次，`H ≈ 173` 人时/年，判据一通过；证书与后端实例会被人手工改动，业务要求 30 秒内纠回，`T_tol` = 30 秒 < `T_script` = 5 分钟，判据二通过（轮询做不到，必须事件驱动）；平台组 5 人、可支配工时 × 20% 折算约 200 人日/年，现存 CRD 3 个、新增后 `R` ≈ 4.2，判据三通过。三项都过，才是「决策树命中第 ⑤ 项」，而不是「我们想写 Operator」。

**CRD 设计检查清单**（决定写之前逐条打勾）：是否同时定义了 `spec` 与 `status` 子资源；`spec` 是否有 `openAPIV3Schema` 且带 `required` / 取值域；`status` 是否只含可重新观测到的字段；是否规划了 `v1alpha1 → v1beta1 → v1` 的迁移与 storage 版本轮转；是否写明「谁负责升级、怎么备份、怎么卸载」；控制器 SA 是否最小化（`CL-S-02`）；控制器自身是否有健康告警；退出路径是否成文 [R-27-3][R-27-5]。

**长期负债清单**（每引入一个 CRD 就背上，直到卸载那天）：① 版本迁移与转换 webhook；② CR 实例的备份与恢复；③ 卸载残留（finalizer、PVC、云上资源、CRD 本身）；④ 与 K8s 大版本的升级兼容；⑤ 控制器 RBAC 与凭据轮换；⑥ 控制器自身的可观测与告警；⑦ 领域模型的文档与值班 runbook；⑧ 责任人（离职交接）；⑨ 退出路径与替换成本 [R-27-5][R-27-8]。这九项没有一项是「装完就有人管」的。

### 27.2.2 九项负债 × 责任人矩阵

27.2 的九项负债清单只说了「欠什么」，没说「谁还、多久还一次」。**没有责任人的负债等于没有负债**——它不会消失，只会在第一次人事变动时静默违约。下表把每项负债落成「一份可验收的交付物 + 一个具名的人 + 一个复核周期」，可以直接贴进引入该 CRD 的 ADR（示例编号 0004，不复用 0003「不写 Operator」那份）；「A」是唯一负责人，「R」是必须参与的人。

| 编号 | 负债项 | 可验收交付物 | A（唯一负责人） | R（协作） | 复核周期 | 失守后的可观察症状 |
|---|---|---|---|---|---|---|
| L1 | 版本迁移与转换 | 双版本 CRD 清单、转换策略说明（`None` 还是 Webhook）、一次轮转演练记录 | 平台组 CRD Owner | 应用组（确认字段语义） | 每季度 + 每次加版本 | 集群升级后存量对象读不出，或读出「合法但错」的字段（27.5.1） |
| L2 | CR 实例备份与恢复 | CR 是否纳入第 16 章备份范围的书面结论、一次恢复到新集群的演练 | 平台组 SRE | 备份 Owner | 每季度 | 集群重建后 CR 全丢，控制器「空转」、下游对象无人管 |
| L3 | 卸载残留 | 卸载 runbook（CR → finalizer 清空 → CRD → 控制器）、一次完整卸载演练 | 平台组 CRD Owner | 无 | 引入前一次 + 每年 | 命名空间卡 `Terminating`、PVC 与云上实例永久残留 [R-27-4] |
| L4 | K8s 大版本兼容 | 兼容矩阵（弃用 API、schema 严格化项）、升级前检查项 | 平台组集群 Owner | 无 | 每次集群升级 | 升级窗口内 CRD `apply` 被拒、控制器起不来（27.1.1） |
| L5 | RBAC 与凭据轮换 | 最小权限 `Role` 清单、`ServiceAccount` token 与证书轮换记录 | 平台组安全 Owner | 安全评审（第 26 章） | 每半年 | 控制器持 `cluster-admin`，或 token 过期后整夜停摆（`CL-S-02`） |
| L6 | 控制器可观测与告警 | 三条健康告警（无成功协调 / 错误率 / 队列深度）+ 每条挂 runbook 链接 | 平台组 on-call Lead | 告警 Owner（第 22 章） | 每季度 | 静默降级数天无人知（27.1.1 的 D21–D23）[R-27-2] |
| L7 | 领域模型文档与值班 runbook | 字段语义表、5 个高频故障的处置步骤 | 平台组 CRD Owner | 应用组 | 每次字段变更 | 全组只有一个人看得懂这份 CRD |
| L8 | 责任人（含备份人） | ADR 尾部「Owner / Backup / 交接清单」三行，姓名可查 | 平台组负责人 | 直属主管 | 每半年 + 离职时 | bus factor = 1，休假即无人能发布或回滚 |
| L9 | 退出路径与替换成本 | 退出步骤、替换成本档位（高 / 中 / 低）、数据迁移说明 | 平台组 CRD Owner | 架构评审 | 每年 | 明知不好用也换不掉，工具从「选择」变成「既成事实」（第 5 章） |

四条使用规则，缺一条这张表就会退化成装饰：

1. **A 必须是人，不是团队**。「平台组」不是责任人，责任分散等于无人负责；写姓名或工号，写不出就说明还没准备好引入。
2. **Backup 必须实操过一次**，不是挂名。L3 的卸载演练与 L1 的轮转演练，至少有一次由 Backup 亲自动手，否则「备份人」只是纸面角色。
3. **任一项填不出交付物，该 CRD 不得进 staging**——这与第 28 章 28.2 决策树最后一道门禁同源，避免「先上再补文档」。
4. **离职即触发交接**：把 L1–L9 逐项过一遍，并当场演练一次卸载；交接记录进 ADR，不进聊天记录。

可查性也给了：ADR 头部三行必须能被一条命令验出来，否则评审时又回到「口头确认」。

```bash
grep -nE '^(Owner|Backup|交接清单):' docs/adr/0004-crd-maintenancewindow.md
# 通过标准：三行都存在，且 Owner / Backup 后是具体人名（非「平台组」这类团队名）
# 失败处置：补不齐就不引入；已引入的，把它列进下一季度平台组 OKR 的「负债清偿」项
```

**反模式：矩阵填满但全是团队名。** 现象是九行都「有负责人」，出事时九个人都说「不是我这条线」；根因是把 RACI 当填表作业。判据很硬：任一 `L` 项的 A 栏写团队名，该项即视为**无责任人**，按第 5 章警戒线「答不出谁负责升级 / 备份 / 卸载」直接判为越线 [R-27-8]。

**季度复核开成 30 分钟，只过三件事**：① 这一季有没有 `L` 项的交付物过期（比如「有 L3 卸载 runbook、但最近一次演练是 11 个月前」就足够触发重排）；② 上一个季度有没有发生过「本应由矩阵内某人处理、结果没人处理」的事件，有就调 A 栏；③ 现存 CRD 数量与 `R` 值重算一遍（27.2.1 判据三），`R` 掉到 1 以下时先冻结新增，而不是先加人。不要把复核开成版本发布会——`L1` 的轮转演练本身就是一次发布，它属于 27.5.1，不占这 30 分钟。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：「什么时候不该写 Operator」比「怎么写」更重要；**每引入一个 CRD 都是长期负债**，默认答案应该是「不写」。
>
> **论证**：前四种解决「产生或校验一份声明」，第五种解决「持续维护一个领域 API」——成本从「一次脚本」变成没有终点的责任链：版本要迁、实例要备份、卸载要清残留、控制器要告警。多一种资源类型并不改善变更入口、产物追溯与回滚能力，只会多一份要维护的 API 契约。决策树「成本从低到高、命中即停」正是为逼出「本项目不写 Operator」这句有据的理由。
>
> **反例与适用前提**：这不等于「永远不许写 Operator」。领域模型确实复杂、前四种都无法表达、且有专人承担九项负债时，自定义控制器是正确解（见第 28 章；现成评估见第 29 章）。前提是**存在多人协作、需要持续收敛的领域对象**；本地实验不在此列。跳过决策树的代价见 27.1 合成案例。

## 27.3 工具选型：本章刻意不新增集群工具

按 `book/decisions.md` 的「唯一示例实现」原则，本章不引入任何新的集群侧工具：配置打包仍是 Kustomize 5.x overlay、对外分发仍是 Helm 4.x、策略仍是 Kyverno 1.x 与 VAP、交付仍是 Argo CD 2.x，GitOps 晋升模型沿用第 14 章。本章的产出是**两份文档 + 一份教学 CRD**，不是一套要运维的控制器。下表把决策树里出现的工具摆在一起，每列都含「何时不该用」；主版本在此出现，小版本锁附录 A [R-27-9]。

| 工具 / 方式（主版本） | 管什么 | 谁来用 | 何时不该用 | 升级 / 回滚路径 |
|---|---|---|---|---|
| 原生资源（K8s 1.32 内置） | 终态与调度 | 应用方 | 需要跨资源协同的领域逻辑时 | 随集群升级；回滚 `git revert` + `kubectl apply -k` |
| Kustomize 5.x / Helm 4.x | 同源清单的参数化 | 应用方 | 需要运行时动态决策时 [R-27-9] | 独立 PR 升版本；渲染产物归档即可回退 |
| CI 脚本 / CronJob（K8s 内置） | 一次性 / 周期动作 | 应用方 / 平台 | 需要持续收敛时 | 改流水线 / 删 CronJob |
| Kyverno 1.x / VAP（K8s 1.32 内置） | 准入校验与变更 [R-27-6] | 平台方 | 需要持有运行时状态时 | 策略先 `audit` 灰度，见第 25 章 |
| Kubebuilder 4.x + controller-runtime 0.x | 自定义控制器脚手架 [R-27-5] | 平台团队 | 前四种任一能解决时（本章结论） | 见第 28 章；先删 CR 再降级控制器 |

**最小接入 diff**（相对 `ch26` 的仓库，只有文档与教学清单，无生产清单变更）：

```diff
+ docs/decision-tree-extension.md      # 五选一决策树与判据表（27.4 给出全文）
+ docs/adr/0003-no-operator.md         # order-demo 不写 Operator 的书面理由
+ operator/crd-sample.yaml             # 教学用最小 CRD，仅讲 spec/status/finalizer 语义
+ operator/cr-sample.yaml              # 教学用 CR 实例，演示 finalizer 删除语义
~ docs/toolmap.md                      # 第 5 层「扩展与运行时」留空理由补上本章 ADR 编号
```

**升级 / 回滚路径**：两份文档走 PR，改错了 `git revert` 即可；教学 CRD 只在本地一次性 kind 集群里 `apply` 与 `delete`，不进任何 `gitops/rendered/<env>/` 目录，因此不进入第 14 章的晋升链，也不构成生产变更。真正需要引入 CRD 的项目，其升级路径是「版本迁移 PR → staging 验证转换 webhook → prod 轮转 storage 版本」，回滚顺序见 27.5，深度展开见第 28 章。

> **为什么本章要留一份「教学 CRD」**：不写 Operator 的结论，不能靠「我们觉得不需要」支撑，得靠能读懂 CRD 到底增加了什么。给一份能 `apply --dry-run=server`、能删、能看到 finalizer 行为的最小样例，读者才具备评估第 29 章那些现成 Operator 的能力。**它显式标注「仅为教学」，与 ADR 的「不写 Operator」不矛盾**（卡片最易打架点）：样例注册在 `ops.example.com` 这个教学 group，不碰 `order-demo` 的任何命名空间、标签、端口或镜像。

适用：出现一个重复运维动作，需要判断要不要扩展 K8s API。

```markdown
# ADR 0003：order-demo 不写 Operator

- 状态：已接受（2026-11-10）
- 问题域：第七篇演进轴，是否扩展 K8s API
- 候选：① 原生资源 ② 配置打包 ③ CI 脚本 / CronJob ④ Webhook 或策略 ⑤ 自定义控制器
- 何时不该用：前四种任一能解决时；20 人团队无平台组、无法承担 CRD 九项负债时
- 选了什么：第 1–4 项（HPA、Kustomize 5.x overlay、CI 定时任务、Kyverno 1.x + VAP）
- 不选的理由：
  - ⑤ 自定义控制器：当前四类运维动作均无「需要持续观测并收敛的领域模型」，
    引入后会背上版本迁移、备份、卸载残留、告警、RBAC、责任人等长期负债，
    收益是想象出来的，成本是确定的（与第 5 章过度工程警戒线一致）。
- 退出路径：当前不引入 CRD，故无类型残留；未来若引入，按 27.5 顺序
  先删 CR 实例 → 确认 finalizer 清空 → 删 CRD → 卸载控制器。
- 退出成本：无（未引入）；对照第 5 章替换成本表，CRD / Operator 类为「高」。
- 版本锁定：不适用；K8s 1.32 基线，小版本见附录 A。
- 复评周期：每新增一类重复运维动作时重跑决策树；每次 K8s 大版本升级复评一次。
- 责任人：平台组（决策）／ 应用组（逐项结论）
- 后果：正向——集群不新增 API 类型，升级与卸载路径保持简单；
  负向——若未来出现真需要持续收敛的领域对象，须重新走本 ADR 的复评。
```

**`conversion.strategy` 什么时候够用**（这是本章最容易被跳过的一格）：

| 变更类型 | `None` 够吗 | 说明 |
|---|---|---|
| 只新增 apiVersion，字段名与语义完全不变 | 够 | API Server 只改 `apiVersion` 字面量，etcd 里的对象原样读出，本章演练就是这一种 |
| 字段改名、类型变化、必填项变化 | **不够** | `None` 不报错、只是把旧对象当新版本读出来，字段对不上就是「合法但错」，比报错更危险 [R-27-3] |
| 同一字段语义变化（如 `replicas` 从「期望值」改为「上限」） | **不够** | 必须 Webhook 做值转换，并对存量对象做一次数据回填（expand–contract） |

两版 schema 一旦不一致，`conversion` 段必须换成下面这段（**替换块，不是独立文件**；换成它之后整份清单才可 `apply`，但 webhook 服务端本身属于第 28 章范围，此处只给 CRD 侧声明）：

```yaml
# 替换上面的 conversion: {strategy: None}，其余部分不变。
# 前提：ops-system/maintenancewindow-webhook 已就绪且 TLS 证书有效（证书轮换即负债 L5）。
  conversion:
    strategy: Webhook
    webhook:
      conversionReviewVersions: ["v1"]
      clientConfig:
        service:
          namespace: ops-system
          name: maintenancewindow-webhook
          path: /convert
```

> **代价说清楚**：Webhook 把「一个字段改名」变成「一条必须常驻、必须有证书、必须被监控的调用链」。API Server 在**每次读写**该类型对象时都会调用它，它挂了就等于这类对象整体不可用。Kubebuilder 4.x 的 `Hub()` / `ConvertTo` / `ConvertFrom` 能生成骨架，但骨架不解决证书轮换与告警——那两项在 27.2.2 的 L5、L6 里 [R-27-5]。这也是为什么 27.2.1 的判据三（负债承载率）要把「每加一个版本」算进年化成本。上面引用的 `ops-system` 命名空间是控制器所在位置，**本章不创建它**（本章只创建 `ops.example.com` 的两个资源，均落在 `order-demo-prod`），webhook 服务端本身属第 28 章范围。

### 27.5.1 演练：`storage` 从 `v1alpha1` 轮转到 `v1beta1`

这是 27.2 负债 L1 的那次演练。**回退写在前面**，因为 storage 轮转是少数「改错就不可逆」的变更：切过去之后若新版本 schema 更窄，旧版本就读不回来那些字段。

**回退方案（先读这一段再动手）**：

```bash
# 0) 回退前先导出全部 CR —— schema 收窄就是数据丢失，备份是唯一兜底
kubectl -n order-demo-prod get maintenancewindows.ops.example.com -o yaml \
  > /tmp/mw-backup-$(date +%Y%m%d%H%M).yaml

# 1) 先打开旧版本的服务（若已置 served: false）
kubectl patch crd maintenancewindows.ops.example.com --type=json -p='[
  {"op":"replace","path":"/spec/versions/0/served","value":true}
]'

# 2) 把 storage 切回 v1alpha1 —— 前提是 v1beta1 期间写入的对象能被 v1alpha1 无损表达
kubectl patch crd maintenancewindows.ops.example.com --type=json -p='[
  {"op":"test","path":"/spec/versions/0/name","value":"v1alpha1"},
  {"op":"replace","path":"/spec/versions/0/storage","value":true},
  {"op":"replace","path":"/spec/versions/1/storage","value":false}
]'

# 3) 验证：storage 已指回 v1alpha1，且旧客户端能正常读
kubectl get crd maintenancewindows.ops.example.com \
  -o jsonpath='{range .spec.versions[*]}{.name}{"\t"}{.storage}{"\n"}{end}'
kubectl -n order-demo-prod get maintenancewindows.v1alpha1.ops.example.com order-demo-prod-nightly
# 注意：storedVersions 此时多半是 ["v1alpha1","v1beta1"] —— 回退同样要跑一次写回循环才会收敛
```

**演练步骤**（本地一次性 kind 集群，前置：27.4.1 的 `operator/crd-dual.yaml` 已 apply，`storage=v1alpha1`、两版均 `served`）：

```bash
# 第 1 步：确认版本矩阵，别靠记忆
kubectl get crd maintenancewindows.ops.example.com \
  -o jsonpath='{range .spec.versions[*]}{.name}{"\t"}{.served}{"\t"}{.storage}{"\n"}{end}'
# 期望：v1alpha1 true true / v1beta1 true false

# 第 2 步：用旧版本写一个对象，记下 UID
kubectl apply -f operator/cr-sample.yaml          # apiVersion 为 ops.example.com/v1alpha1
kubectl -n order-demo-prod get maintenancewindows.v1alpha1.ops.example.com \
  order-demo-prod-nightly -o jsonpath='{.metadata.uid}{"\n"}'

# 第 3 步：用新版本读同一个对象 —— storage 未切换时也能读，因为 served=true
kubectl -n order-demo-prod get maintenancewindows.v1beta1.ops.example.com \
  order-demo-prod-nightly -o jsonpath='{.metadata.uid}{"\n"}{.apiVersion}{"\n"}'
# 判据：UID 与第 2 步一致、apiVersion 显示 v1beta1 → 同一对象两种视图，不是两份数据

# 第 4 步：切 storage（test 守卫，防止数组下标与预期不符时静默改错版本）
kubectl patch crd maintenancewindows.ops.example.com --type=json -p='[
  {"op":"test","path":"/spec/versions/1/name","value":"v1beta1"},
  {"op":"replace","path":"/spec/versions/1/storage","value":true},
  {"op":"replace","path":"/spec/versions/0/storage","value":false}
]'
kubectl get crd maintenancewindows.ops.example.com -o jsonpath='{.status.storedVersions}{"\n"}'
# 关键教学点：storedVersions 仍是 ["v1alpha1"] —— 切 storage 不会重写 etcd 里的存量对象

# 第 5 步：逐对象写回，逼 etcd 用新版本落盘，这才叫「轮转」
for cr in $(kubectl -n order-demo-prod get maintenancewindows.ops.example.com -o name); do
  kubectl -n order-demo-prod get "$cr" -o json \
    | jq 'del(.status, .metadata.managedFields)' \
    | kubectl replace -f -
done
kubectl get crd maintenancewindows.ops.example.com -o jsonpath='{.status.storedVersions}{"\n"}'
# 期望：["v1beta1"]；若仍含 v1alpha1，说明还有对象未被写回（查是否有 CR 处于 Terminating）
# 也可能是 apiserver 的 storedVersions 重算尚未触发：对 CRD 做一次无实质变更的 annotate 再查
kubectl annotate crd maintenancewindows.ops.example.com \
  ops.example.com/rotated-at=$(date +%Y%m%d%H%M) --overwrite

# 第 6 步：确认无旧版本写入后，关掉 v1alpha1 的 served
kubectl patch crd maintenancewindows.ops.example.com --type=json -p='[
  {"op":"replace","path":"/spec/versions/0/served","value":false}
]'
kubectl -n order-demo-prod get maintenancewindows.v1alpha1.ops.example.com order-demo-prod-nightly
# 期望：明确报「这个版本 / 资源类型找不到」（no matches for kind 或 could not find the requested
# resource，文案随 kubectl 版本不同），而不是 NotFound 说对象不存在——对象还在，只是没有这个视图
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 双版本可读 | 同一 `metadata.uid` 在 `v1alpha1` 与 `v1beta1` 下都能取到，`apiVersion` 不同 |
| storage 已切换 | `spec.versions[*].storage` 只有 `v1beta1` 为 `true` |
| 存量已重写 | `status.storedVersions` 只含 `v1beta1`，无 `v1alpha1` 残留 |
| 旧版本已停服 | 请求 `v1alpha1` 报「版本 / 类型找不到」，而对象本身未被删除 |
| 回退已演练 | 本节开头的回退步骤在同一集群完整跑过一次并恢复可读（`CL-G-07`） |

**为什么不能把第 4 步和第 5 步合成一步**：直接 apply 一份 `storage: v1beta1` 的新 CRD 看着更省事，实际是把两件事压成一次不可回滚的操作——切 storage 只改「以后写哪里」，全量重写才改「已经写在哪」。合并之后 `status.storedVersions` 会长期停在 `["v1alpha1","v1beta1"]` 的双值状态，而你以为已经迁完了。双值本身不是错误，但它**不会自愈**：只有对象被再次写入才会消掉，于是这项要当告警看，不能当信息看，否则半年后关旧版本时才发现还有对象没搬。

若 `conversion` 用的是 Webhook，第 5 步的全量重写会把调用量放大到「对象数 × 2」（读一次、写一次），而一次 1000 对象的 `list` 就是 1000 次 webhook 调用。演练时要盯 webhook 的 P99 与错误率，**不要放在业务高峰做全量重写**——这是「转换 webhook 成为读写路径上的单点」的具体形态，也是 27.2.2 里 L5 要定期轮换证书的原因 [R-27-3]。

**三条纪律**：① 生产上这六步必须拆成两个 PR（切 storage 一个、停旧版本一个），中间留一个发布窗口，因为「切完立刻停旧版本」等于没有回退余地；② CRD 变更照旧走 Git，`kubectl patch` 只在演练集群用（公理 5）；③ 轮转不要放在业务高峰，`storedVersions` 未清算前不要宣布迁移完成——这也是 27.2.2 里 L1 的验收标准 [R-27-5]。
