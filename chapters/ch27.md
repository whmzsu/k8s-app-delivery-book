## 27.1 问题与反模式：一个重复动作，值不值得给集群加一种新资源

**合成案例**（教学合成，非真实事件）：某平台组接到「每天凌晨调一次 `gateway` 副本数」的需求，有人提议「写成 Operator，最云原生」。集群从 1.31 升到 1.32，未加 schema 校验的 CRD 字段被拒绝、控制器起不来；因没配告警，业务静默降级两天才被发现。想卸载时，CR 实例的 `metadata.finalizers` 挂着 `ops.example.com/cleanup`，控制器已不在，对象卡在 `Terminating`、命名空间删不掉 [R-27-2][R-27-4][R-27-5]。复盘时才问出第一天就该问的：**一个 CronJob 加一行 HPA 就能做完，为什么要给集群增加一种新资源类型？**

这不是 K8s 缺陷，控制器 / finalizer / 版本校验都在按文档工作，失控的是**决策**：把「有个重复动作」直接等价于「该写 Operator」[R-27-1][R-27-7]。第 5 章已把「引入 CRD」列为需书面论证的选项，本章把那条警戒线展开成可判定的决策树。

三个高频反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：把一次性或周期性脚本包装成 Operator。** 现象是多了一套要升级、要备份、要值班的控制器，业务只得到「每天改一个数」；根因是把「自动化」和「扩展 API」混为一谈。替代做法是先走 27.2 五选一决策树，把「原生资源 / 配置打包 / CI 脚本 / Webhook 或策略」四种更轻的方式逐一排除，只剩「确实需要持续观测并收敛」时才落在自定义控制器 [R-27-7][R-27-8]。

**反模式二：reconcile 里做长耗时阻塞，把 `status` 当数据库。** 现象是 worker 被慢调用占满、其他对象饿死，控制器重启后状态失真；根因是混淆了 `spec`（期望，人写）与 `status`（观测结果，控制器写），把中间状态持久化进 `status` 供下一轮读取——循环一旦依赖上一轮中间态，就不再幂等、不再可重入 [R-27-2][R-27-4]。替代做法是短循环 + 幂等 + 重入队列，见第 28 章。

**反模式三：只定义 `v1alpha1`，从不规划版本迁移。** 现象是升级时 API Server 拒绝旧对象、转换 webhook 仓促上阵、存量的 CR 无处可去；根因是把 CRD 当成「一份配置」而不是「一个有生命周期的 API」。本章的替代做法是把版本迁移路径、storage 版本轮转、卸载残留检查写进引入前的负债清单 [R-27-5]。

> **本章是三个术语的正式定义章**：CRD、Operator、finalizer。控制循环定义见第 2 章，本章不重复（SP-17）；第 5、16 章的白话伏笔在此兑现。定义之前不拿它们当推理前提。

## 27.2 范式与决策树：什么时候真的需要扩展 K8s API

**CRD（CustomResourceDefinition）** 的本书定义：给 Kubernetes 增加一种自定义资源类型。可验证形态是两条命令都能给出结果——`kubectl api-resources --api-group=<group>` 能列出一个新的 `kind`，且 `kubectl get <kind> -A` 能返回该类型的对象；只往 etcd 里塞数据、没有注册类型，不算 CRD [R-27-3]。

**Operator** 的本书定义：**CRD + 协调循环**。它把某个领域的运维知识编码进控制器，让集群持续把实际状态收敛到 `spec` 声明的期望状态；`status` 只承载观测结果 [R-27-1]。注意这个定义是「组合式」的：只有 CRD 没有控制器，是一张需要人去填的表；只有控制器没有 CRD，是在运维别人定义的对象。两者齐备才叫 Operator。

由此得到三条不可混用的语义，每条都能用命令证伪 [R-27-4]：

| 语义 | 谁写 | 表达什么 | 违反时可观察的现象 |
|---|---|---|---|
| `spec` | 人 / Git | 期望状态 | 控制器去改 `spec`，等于自己改自己的输入 |
| `status` | 控制器 | 观测结果 | 把「下一步该做啥」写进 `status`，控制器重启后流程走偏 |
| `metadata.finalizers` | 控制器 | 删除前必须完成的清理 | 清理没跑完就摘掉，外部资源（PVC、云上实例）永久残留 |

**协调循环（reconciliation）** 是控制循环在 Operator 语境下的形态：持续比对实际状态与期望状态并收敛。第 2 章已定义控制循环，这里只补三条工程约束，它们都是可测的 [R-27-2]：① **幂等**——同一份 `spec` 反复触发，副作用只发生一次（用 `observedGeneration` 去重）；② **可重入**——循环在任何一行被中断后重跑，结果不变；③ **容忍重复事件**——Informer 会重复投递，控制器不能假设「收到一次 = 只做一次」。这三条是第 28 章幂等性测试要验的东西，本章只立判据。

**finalizer 的正式定义**（兑现第 16 章白话伏笔）：它是 `metadata.finalizers` 里的一组清理钩子标记。对象被 DELETE 且该字段非空时，API Server **不会真正删除对象**，只设 `metadata.deletionTimestamp`、把对象留在 `Terminating`；持有该 finalizer 的控制器完成外部清理后必须主动移除这一项，删除才继续 [R-27-4]。卡住只有三种根因：控制器不在了、无对应 RBAC、清理逻辑报错。可验证判据：`kubectl get <kind> <name> -o yaml` 里 `deletionTimestamp` 与 `finalizers` 同时非空，就是「被挡住」而非「kubectl 卡了」（命令见 27.5）。这也解释了第 16 章卸载清单为何必须「先删实例、等清理、最后删控制器」，以及为何禁止 `--force --grace-period=0` 或手工 patch 跳过清理。

**本章要回答的决策问题**：有个重复运维动作，到底该用哪种扩展方式？下面这棵决策树按「成本从低到高」排列，命中即停，越往下长期负债越重 [R-27-9]：

```
这个动作的终态能用原生资源表达吗？
  （Deployment / StatefulSet / CronJob / HPA / PDB）            是 → ① 原生资源，停
        │ 否
差异只是「同源清单在不同环境取不同值」？                        是 → ② 配置打包（Helm 3.x / Kustomize 5.x），停
        │ 否
动作是一次性或周期性的，没有「持续比对并收敛」的需求？            是 → ③ CI 脚本 / CronJob，停
        │ 否
需求是「在对象进集群前校验或改写它」，不需要长期运行状态？        是 → ④ Webhook 或策略（VAP / Kyverno 1.x），停
        │ 否
需要持续观测 + 收敛 + 有明确领域模型，
且团队能长期承担 CRD 负债（版本、备份、卸载、告警、责任人）？      是 → ⑤ 自定义控制器（CRD + Operator，Kubebuilder 4.x，见第 28 章）
        │ 否
→ 写一份「本项目不写 Operator」的 ADR，回 27.3 在前四种里选一种
```

**扩展方式五选一判据表**（列含适用前提 / 维护成本 / 何时不该用 / 退出方式）：

| 方式 | 适用前提 | 维护成本 | 何时不该用 | 退出方式 |
|---|---|---|---|---|
| ① 原生资源 | 终态能由 `Deployment` / `CronJob` / `HPA` / `PDB` 直接表达 | 最低，随 K8s 版本走 | 需要跨多个资源协同、且协同逻辑有领域语义时 | 删清单即可，无类型残留 |
| ② 配置打包（Helm 3.x / Kustomize 5.x） | 差异只是同源清单的参数化 | 低，渲染产物可 review | 需要按运行时状态动态决策时（模板是静态的） | 保留渲染产物，换生成器，见第 5、10 章 |
| ③ CI 脚本 / CronJob | 一次性或周期性动作，无持续收敛需求 | 低，进流水线即可审计 | 动作必须响应对象状态变化、或被手工改动后自动纠正时 | 删流水线步骤 / 删 CronJob |
| ④ Webhook 或策略（VAP / Kyverno 1.x） | 只需在准入时校验或变更，不持有运行时状态 [R-27-6] | 中，策略库与 CI 侧同库 | 需要在对象创建之后持续调谐、或调用外部慢 API 时 | 策略先置 `audit` → 删策略 → 卸载，见第 25 章 |
| ⑤ 自定义控制器（CRD + Operator） | 有明确领域模型、需要持续观测并收敛、有人长期负责负债 [R-27-1] | 高：版本迁移、备份、卸载、告警、RBAC 全要负责 | 前四种任一能解决时；20 人团队无平台组时（见第 5 章警戒线） | 先删全部 CR 实例 → 确认 finalizer 清空 → 再删 CRD → 最后卸载控制器，见 27.5 |

**CRD 设计检查清单**（决定写之前逐条打勾）：是否同时定义了 `spec` 与 `status` 子资源；`spec` 是否有 `openAPIV3Schema` 且带 `required` / 取值域；`status` 是否只含可重新观测到的字段；是否规划了 `v1alpha1 → v1beta1 → v1` 的迁移与 storage 版本轮转；是否写明「谁负责升级、怎么备份、怎么卸载」；控制器 SA 是否最小化（`CL-S-02`）；控制器自身是否有健康告警；退出路径是否成文 [R-27-3][R-27-5]。

**长期负债清单**（每引入一个 CRD 就背上，直到卸载那天）：① 版本迁移与转换 webhook；② CR 实例的备份与恢复；③ 卸载残留（finalizer、PVC、云上资源、CRD 本身）；④ 与 K8s 大版本的升级兼容；⑤ 控制器 RBAC 与凭据轮换；⑥ 控制器自身的可观测与告警；⑦ 领域模型的文档与值班 runbook；⑧ 责任人（离职交接）；⑨ 退出路径与替换成本 [R-27-5][R-27-8]。这九项没有一项是「装完就有人管」的。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：「什么时候不该写 Operator」比「怎么写」更重要；**每引入一个 CRD 都是长期负债**，默认答案应该是「不写」。
>
> **论证**：前四种解决「产生或校验一份声明」，第五种解决「持续维护一个领域 API」——成本从「一次脚本」变成没有终点的责任链：版本要迁、实例要备份、卸载要清残留、控制器要告警。多一种资源类型并不改善变更入口、产物追溯与回滚能力，只会多一份要维护的 API 契约。决策树「成本从低到高、命中即停」正是为逼出「本项目不写 Operator」这句有据的理由。
>
> **反例与适用前提**：这不等于「永远不许写 Operator」。领域模型确实复杂、前四种都无法表达、且有专人承担九项负债时，自定义控制器是正确解（见第 28 章；现成评估见第 29 章）。前提是**存在多人协作、需要持续收敛的领域对象**；本地实验不在此列。跳过决策树的代价见 27.1 合成案例。

## 27.3 工具选型：本章刻意不新增集群工具

按 `book/decisions.md` 的「唯一示例实现」原则，本章不引入任何新的集群侧工具：配置打包仍是 Kustomize 5.x overlay、对外分发仍是 Helm 3.x、策略仍是 Kyverno 1.x 与 VAP、交付仍是 Argo CD 2.x，GitOps 晋升模型沿用第 14 章。本章的产出是**两份文档 + 一份教学 CRD**，不是一套要运维的控制器。下表把决策树里出现的工具摆在一起，每列都含「何时不该用」；主版本在此出现，小版本锁附录 A [R-27-9]。

| 工具 / 方式（主版本） | 管什么 | 谁来用 | 何时不该用 | 升级 / 回滚路径 |
|---|---|---|---|---|
| 原生资源（K8s 1.32 内置） | 终态与调度 | 应用方 | 需要跨资源协同的领域逻辑时 | 随集群升级；回滚 `git revert` + `kubectl apply -k` |
| Kustomize 5.x / Helm 3.x | 同源清单的参数化 | 应用方 | 需要运行时动态决策时 [R-27-9] | 独立 PR 升版本；渲染产物归档即可回退 |
| CI 脚本 / CronJob（K8s 内置） | 一次性 / 周期动作 | 应用方 / 平台 | 需要持续收敛时 | 改流水线 / 删 CronJob |
| Kyverno 1.x / VAP（K8s 1.32 内置） | 准入校验与变更 [R-27-6] | 平台方 | 需要持有运行时状态时 | 策略先 `audit` 灰度，见第 25 章 |
| Kubebuilder 4.x + controller-runtime 0.x | 自定义控制器脚手架 [R-27-5] | 平台团队 | 前四种任一能解决时（本章结论） | 见第 28 章；先删 CR 再降级控制器 |

**最小接入 diff**（相对 `ch26` 的仓库，只有文档与教学清单，无生产清单变更）：

```diff
+ docs/decision-tree-extension.md      # 五选一决策树与判据表（27.4 给出全文）
+ docs/adr/0003-no-operator.md         # order-demo 不写 Operator 的书面理由
+ operator/crd-sample.yaml             # 教学用最小 CRD，仅讲 spec/status/finalizer 语义
+ operator/cr-sample.yaml              # 教学用 CR 实例，演示 finalizer 删除语义
~ docs/toolmap.md                      # 第 5 层「扩展与运行时」留空理由补上本章 ADR 编号
```

**升级 / 回滚路径**：两份文档走 PR，改错了 `git revert` 即可；教学 CRD 只在本地一次性 kind 集群里 `apply` 与 `delete`，不进任何 `gitops/rendered/<env>/` 目录，因此不进入第 14 章的晋升链，也不构成生产变更。真正需要引入 CRD 的项目，其升级路径是「版本迁移 PR → staging 验证转换 webhook → prod 轮转 storage 版本」，回滚顺序见 27.5，深度展开见第 28 章。

> **为什么本章要留一份「教学 CRD」**：不写 Operator 的结论，不能靠「我们觉得不需要」支撑，得靠能读懂 CRD 到底增加了什么。给一份能 `apply --dry-run=server`、能删、能看到 finalizer 行为的最小样例，读者才具备评估第 29 章那些现成 Operator 的能力。**它显式标注「仅为教学」，与 ADR 的「不写 Operator」不矛盾**（卡片最易打架点）：样例注册在 `ops.example.com` 这个教学 group，不碰 `order-demo` 的任何命名空间、标签、端口或镜像。

```markdown
# 扩展方式五选一决策树（order-demo）

适用：出现一个重复运维动作，需要判断要不要扩展 K8s API。
原则：成本从低到高、命中即停；越往下长期负债越重。

## 决策顺序
1. 终态能用原生资源（Deployment / StatefulSet / CronJob / HPA / PDB）表达 → 用原生资源，结束。
2. 差异只是同源清单在不同环境取不同值 → 用 Kustomize 5.x overlay / Helm 3.x，结束。
3. 动作是一次性 / 周期性、无需持续收敛 → 用 CI 脚本 / CronJob，结束。
4. 只需在准入时校验或变更、不持有运行时状态 → 用 VAP / Kyverno 1.x，结束。
5. 需要持续观测 + 收敛 + 有明确领域模型，且能承担 CRD 九项负债 → 自定义控制器，
   工程实践见第 28 章；优先评估现成 Operator，见第 29 章。
6. 以上都不满足，或团队无法承担负债 → 写「不写 Operator」的 ADR，回第 1–4 项。

## order-demo 四类运维动作逐项结论
| 动作 | 命中项 | 结论 | 理由 |
|---|---|---|---|
| 每天按峰值调 gateway 副本数 | 1 | 原生资源 HPA | 终态是副本数，HPA 直接表达，无领域模型 |
| 三环境 GREETING / 域名不同 | 2 | Kustomize 5.x overlay | 同源清单参数化，晋升只改 overlay |
| 每周生成一次备份校验报告 | 3 | CI 定时任务 | 周期性、无持续收敛需求 |
| 禁止特权容器 / 明文 Secret 进集群 | 4 | Kyverno 1.x + VAP | 准入时校验，不需要运行时状态（见第 25 章） |

## 结论
四类动作全部由第 1–4 项解决，第 5 项不命中：本项目不写 Operator。
ADR：docs/adr/0003-no-operator.md
```

**`docs/adr/0003-no-operator.md`**：

```markdown
# ADR 0003：order-demo 不写 Operator

- 状态：已接受（2026-11-10）
- 问题域：第七篇演进轴，是否扩展 K8s API
- 候选：① 原生资源 ② 配置打包 ③ CI 脚本 / CronJob ④ Webhook 或策略 ⑤ 自定义控制器
- 何时不该用：前四种任一能解决时；20 人团队无平台组、无法承担 CRD 九项负债时
- 选了什么：第 1–4 项（HPA、Kustomize 5.x overlay、CI 定时任务、Kyverno 1.x + VAP）
- 不选的理由：
  - ⑤ 自定义控制器：当前四类运维动作均无「需要持续观测并收敛的领域模型」，
    引入后会背上版本迁移、备份、卸载残留、告警、RBAC、责任人等长期负债，
    收益是想象出来的，成本是确定的（与第 5 章过度工程警戒线一致）。
- 退出路径：当前不引入 CRD，故无类型残留；未来若引入，按 27.5 顺序
  先删 CR 实例 → 确认 finalizer 清空 → 删 CRD → 卸载控制器。
- 退出成本：无（未引入）；对照第 5 章替换成本表，CRD / Operator 类为「高」。
- 版本锁定：不适用；K8s 1.32 基线，小版本见附录 A。
- 复评周期：每新增一类重复运维动作时重跑决策树；每次 K8s 大版本升级复评一次。
- 责任人：平台组（决策）／ 应用组（逐项结论）
- 后果：正向——集群不新增 API 类型，升级与卸载路径保持简单；
  负向——若未来出现真需要持续收敛的领域对象，须重新走本 ADR 的复评。
```

**`operator/crd-sample.yaml`**（教学用最小 CRD，讲 `spec` / `status` / 版本语义）：

```yaml
# 合成教学样例：仅用于讲 spec/status/finalizer 语义，不建议给 order-demo 写 Operator。
# 与 docs/adr/0003-no-operator.md 配套；用完按 27.5 删除。
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: maintenancewindows.ops.example.com
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: kubectl
spec:
  group: ops.example.com
  scope: Namespaced
  names:
    plural: maintenancewindows
    singular: maintenancewindow
    kind: MaintenanceWindow
    shortNames:
      - mw
  versions:
    - name: v1alpha1
      served: true
      storage: true
      # 教学：只给一个版本，刻意演示「不规划迁移」的反模式三。
      # 生产必须同时规划 v1beta1 / v1 与转换 webhook，见 27.2 负债清单。
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [replicas]
              properties:
                replicas:
                  type: integer
                  minimum: 1
                  maximum: 20
                reason:
                  type: string
            status:
              type: object
              properties:
                observedGeneration:
                  type: integer
                appliedReplicas:
                  type: integer
                phase:
                  type: string
                  enum: [Pending, Applied, Failed]
      subresources:
        status: {}
      additionalPrinterColumns:
        - name: Replicas
          type: integer
          jsonPath: .spec.replicas
        - name: Phase
          type: string
          jsonPath: .status.phase
        - name: Age
          type: date
          jsonPath: .metadata.creationTimestamp
```

> `subresources.status: {}` 把 `status` 变成独立子资源：人 `apply` 时写进 `status` 的字段会被 API Server 忽略，只有控制器能通过 `/status` 端点更新它。这正是 27.2「`spec` 人写、`status` 控制器写」的机器强制形态 [R-27-4]；`openAPIV3Schema` 的 `required` 与 `minimum/maximum` 则是「可校验」而非「靠文档约定」[R-27-3]。

**`operator/cr-sample.yaml`**（教学用 CR 实例，演示 finalizer 删除语义）：

```yaml
# 合成教学样例：演示 finalizer 卡住的现象，不用于生产扩缩容。
apiVersion: ops.example.com/v1alpha1
kind: MaintenanceWindow
metadata:
  name: order-demo-prod-nightly
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: kubectl
  finalizers:
    - ops.example.com/cleanup
spec:
  replicas: 3
  reason: "教学用：演示 finalizer 删除语义，不用于生产扩缩容"
status:
  phase: Pending
```

> 上面的 `status.phase` 在 `apply` 时会被忽略（status 是子资源），这是正确的教学点：它证明「观测结果只能由控制器写」。`finalizers` 里那一项没有对应控制器去清理，因此 27.5 删除它时会稳定卡在 `Terminating`——这正是要读者亲手看到的 finalizer 语义 [R-27-4]。

**回滚命令 / 步骤**（先演练、后发布；本节即演练本身）。顺序不能反：先删 CR 实例，再删 CRD，否则实例变孤儿、卡在删除中 [R-27-4]：

```bash

kubectl -n order-demo-prod delete maintenancewindow order-demo-prod-nightly \
  --wait=true --timeout=15s || true
kubectl -n order-demo-prod get maintenancewindow order-demo-prod-nightly \
  -o jsonpath='{.metadata.deletionTimestamp}{"\n"}{.metadata.finalizers}{"\n"}' || true

# 2) 教学 CRD 没有控制器执行清理，故由教学者显式移除 finalizer。
#    仅此教学样例允许：生产 CRD 必须由控制器完成清理后自行移除，禁止手工 patch 跳过清理（见第 16、23 章）。
kubectl -n order-demo-prod patch maintenancewindow order-demo-prod-nightly \
  --type=merge -p '{"metadata":{"finalizers":[]}}' || true

# 3) 确认已无 CR 实例，再删 CRD
kubectl get maintenancewindows -A --ignore-not-found=true
kubectl delete crd maintenancewindows.ops.example.com --ignore-not-found=true

# 4) 文档侧回到上一版声明（本章文档若已提交）
git revert <ADR / 决策树文档的 commit> || true
```

> **为什么教学样例可以摘 finalizer**：`ops.example.com/cleanup` 在这里没有对应的清理逻辑，是为演示「卡住」而挂的空标记，移除它不会跳过任何真实清理。生产环境里 finalizer 背后是 PVC、云上实例或外部注册，手工 patch 掉等于把那些资源永久遗留，所以第 16 章列为禁止动作。本章只操作本地一次性集群，且 ADR 明确「本项目不引入 CRD」，**不构成对全书公理 5（生产变更只允许走 Git）的例外**：`gitops/rendered/<env>/` 一行未动。

**回滚验证**：

```bash

kubectl api-resources --api-group=ops.example.com || true
kubectl -n order-demo-prod get all -l app.kubernetes.io/name=order-demo
./hack/verify.sh
```

通过标准：`kubectl get crd` 与 `api-resources` 中已无 `ops.example.com` 的类型、无 `Terminating` 残留对象、`order-demo` 原有工作负载未变、`verify.sh` 的 `/healthz` 仍为 200。**卸载没演练过、finalizer 行为没亲眼看过，就不允许把任何 CRD 带进第 28 章**（CL-G-07）。
