## 2.1 问题与反模式：我明明改了，怎么一会儿又变回去了

第 1 章的事故里，14:34 有人 `kubectl edit` 直接改了运行中的 Pod，想「先加一行环境变量」，几秒后被改了回去（H2）。当时的判断是「K8s 抽风了」。这一章要把这个判断彻底翻过来：**这不是工具故障，而是声明式终态的必然结果**。

读者来这一章时，通常带着一个具体的困惑：我 `kubectl edit` 改了副本数，怎么一会儿又被改回去？K8s 到底在替我管什么？要回答它，得先把三件事分开——**期望状态**（写进声明里的）、**实际状态**（集群里此刻跑着的）、**控制器**（持续比对二者并收敛的那段逻辑）。Kubernetes 的控制器会不断把实际状态拉向期望状态 [R-02-1]；你直接改运行对象，等于只动了「实际状态」，控制器下一次循环就会按声明把它纠正回去 [R-02-2]。这不是 bug，是模型本身。

三个高频反模式（每条按「现象 → 根因 → 本章替代做法」）：

**反模式一：把 Pod 当虚拟机，登录后改文件或改镜像。** 现象是「我进容器改了配置，重启后全没了」「`kubectl edit pod` 改字段报 Forbidden，或者改完一会儿 Pod 就消失了」。根因是把 Pod 当成了可长期持有、可就地修改的执行单元；实际上 Pod 是**可调度的、可被丢弃的最小执行单元**，它由上层控制器按 Pod 模板生成，字段大多不可变，删了会被重建 [R-02-4]。本章的替代做法是用 `hack/show-owner-chain.sh` 打印 `Deployment → ReplicaSet → Pod` 的 owner 链，看清楚「这个 Pod 是谁生的、归谁管」，然后通过改**声明**去改内容（见 2.4、2.5）。

**反模式二：平台方与应用方职责不分，双方都能改同一份清单。** 现象是「副本数到底该谁定」「一次漂移没人认领」。根因是没有划清「谁写声明、谁维护控制器」：控制器和收敛机制属于平台侧，期望状态写什么属于应用侧，两者都伸手就会互相覆盖。本章给一张责任边界表（2.2），把「改副本数」「改镜像」「改控制器行为」分别归到人 [R-02-5]。

**反模式三：以为「改了就生效」，分不清到底改了哪一层。** 现象是有人 `kubectl scale` 之后欢呼「生效了」，有人 `kubectl edit pod` 之后抱怨「没生效」，两边都没意识到自己改的是不同的对象。根因是没建立「运行对象 / 声明对象 / Git 声明」三层视角。本章的决策树（2.2）就是用来当场判定「这次改动改的是哪一层、会不会被收敛」。

> **一个刻意的边界**：本章只讲**机制**——控制器怎么收敛、owner 链怎么级联——**不评价自愈的好坏**。「自愈会不会误伤」「漂移检测该不该自动纠正」是第 14 章的问题；本章若提前下结论，会和那里的「自愈误伤」讨论打架。同样，本章讲的控制循环与第 27 章的协调循环是同一机制在不同深度的展开，正式定义只在此处给一次（SP-17），第 27 章不再重复定义。

## 2.2 范式与决策树：期望状态 → 控制器 → 实际状态

先把本书的基准术语定准。**应用 application** 是「一组共同交付、共同回滚的工作负载与配置的最小单元」——对 `order-demo` 而言，`gateway`、`api`、`worker`、`db` 及其配置共同构成一个应用，单独一个 `Deployment` 或单个 `Pod` 都不是「应用」。这个定义是可验证的：把任意一个组件单独回滚而其余不动，若交付结果不再自洽，就说明你拆错了一个应用。这套术语所处的云原生语境由 CNCF 的定义给出 [R-02-7]。

**控制循环 reconciliation**（本章正式定义）：控制器持续比对**实际状态**与**期望状态**并收敛，直至二者一致。它不是「K8s 自动帮你修好一切」——收敛的目标是你写的那份声明，声明写错，控制器会稳定地维持错误。它的可验证形式就是 2.5 的删 Pod 实验：删掉一个 Pod（实际状态偏离），控制器立刻按 `ReplicaSet` 的 Pod 模板新建（收敛回期望状态）。协调循环在第 27 章作为 Operator 的机制再深入，本章不展开。

**OwnerReference** 决定级联删除与重建：每个 Pod 的 `metadata.ownerReferences` 指向生成它的 `ReplicaSet`，`ReplicaSet` 再指向 `Deployment` [R-02-3]。所以删 `Deployment` 会级联删掉 `ReplicaSet` 与 Pod，而删单个 Pod 只会触发重建——这正是「Pod 不是虚机」在 API 层面的证据。

还有一个梯度问题：本章会用到「**清单 manifests**」（描述期望状态的 YAML/JSON 声明文件，正式定义详见第 10 章）和「**工作负载 workload**」（承载应用进程的 K8s 资源，如 `Deployment` / `StatefulSet` / `Job`，正式定义详见第 7 章）。在正式定义章之前，本章只把它们当「写声明的文件」和「跑进程的资源」来用，不拿它们推导任何结论。

**本章要回答的决策问题**：声明式终态之下，「改配置」和「改运行状态」到底有什么区别，谁有权改？答案是一张责任边界表。

| 层 | 谁写声明 | 谁维护控制器 / 收敛机制 | 出问题找谁 |
|---|---|---|---|
| 控制面（API Server、调度器） | K8s 项目 | 集群管理员 / 平台方 | 平台方 |
| 平台机制（GitOps、策略、网络插件） | 平台方 | 平台方 | 平台方 |
| 应用期望状态（`deploy/base` 等清单） | **应用方** | `Deployment` / `ReplicaSet` 等内置控制器 | 应用方 |
| 运行对象（Pod） | 无——由控制器按模板生成 | 控制器 | 不要手改，先看 owner 链 |

> **本书观点（本章第 1 条主张，不需要外部背书）**
>
> **主张**：平台方管「收敛机制」，应用方管「期望状态写什么」。这条边界是可操作的，不是组织口号。
>
> **论证**：控制器的行为由平台侧决定（装了什么控制器、开了什么自愈策略），而「副本数、镜像、探针、配置」这些字段表达的是应用意图，只有应用方知道正确值。把两者混在一起，会出现两类典型事故：平台方擅自改了应用清单、应用方去改控制器配置。事故里的 H2 与 H7 都是这条边界失守的后果。边界一旦划清，「谁有权改副本数」就有唯一答案：应用方在声明里改，平台方保证改声明会被收敛。
>
> **反例与适用前提**：这不等于「应用方永远不能碰控制器」。一个小团队里同一个人兼任两角，边界表现为「同一份 PR 里区分清楚哪些是平台配置、哪些是应用声明」即可，不必设两拨人。前提仍是**存在多人协作的变更**；单人本地实验无需这套划分。

由「三层视角」直接得到一棵决策树，用来当场判定一次改动会有什么结果：

```
你改的是运行对象（Pod / 容器里）的字段？    是 → 会被 ReplicaSet 按 Pod 模板收敛或重建；
        │ 否                                  想持久就改声明（2.4），别手改 Pod
你改的是 Deployment 的 .spec（声明对象）？   是 → 这是合法的期望状态变更，会生效；
        │ 否                                  但生产里它必须来自 Git（见第 14 章）
你改的是 Git 里的清单？                    是 → 唯一持久的真相入口（见第 14 章）
        │ 否
→ 你在动控制器 / 平台机制本身 → 归平台方，按责任边界表找人
```

这里要纠正一个流传很广的误解：**`kubectl scale` 改的是 `Deployment.spec.replicas`，它本身就是期望状态，在原生 K8s 里会生效、不会被「改回去」**。真正「改了不生效」的是直接改运行对象；而「手工改声明也会被纠正」只发生在有持续收敛的 GitOps 体系里——那是第 14 章的漂移纠正，不是本章 L0 环境的行为 [R-02-1][R-02-2]。把这一点讲准，读者才不会用错误的心智模型去理解后面每一章。

## 2.3 工具选型：本章刻意不选工具

这一章的「工具选型」结论和样板章一致：**先不引入任何配置打包与交付工具**。本章要建的是心智模型，不是流水线；在还没能力判断「一份清单对不对」之前就装上模板引擎与 GitOps 控制器，只会把错误也一起收敛进去。第 10 章才系统比较 Helm 3.x / Kustomize 5.x，第 14 章才比较 Argo CD 2.x / Flux 2.x，第 27 章才谈要不要扩展 K8s API。

| 工具 | 本章是否使用 | 何时不该用（与本章相关的一条） |
|---|---|---|
| Helm 3.x / Kustomize 5.x | 不用 | 只有一个环境、只想看清「改声明会怎样」时；模板与 overlay 会遮住「到底提交了什么」 |
| Argo CD 2.x / Flux 2.x | 不用 | 还没建立「期望状态 / 实际状态」的概念之前；持续收敛会把错误也收敛进去 |
| Operator / CRD | 不用 | 需求只是「解释一次收敛」；给 K8s 加一种新资源类型（CRD，详见第 27 章）在此毫无必要 |
| kind + kubectl + curl | **使用** | — |

本章最小工具集只有四个：`kind`（本地集群，版本见附录 A）、`kubectl`（随 Kubernetes 1.32）、`curl`、`bash`。它们不产生任何「需要选型」的决策，因此本章没有选型矩阵，只有上一节的判据表与责任边界表——按 9.6「避免为凑模板而注水」，这里不硬塞工具对比。先从裸清单理解模型，再引入自动化，是 Kelsey Hightower 那类教学路径一贯的次序 [R-02-6]。

## 2.4 落地配置（完整可应用文件，Kubernetes 1.32+，`apiVersion: apps/v1`）

> 全部字段沿用 `book/case-evolution.md` 配置契约：命名空间 `order-demo-dev`、镜像 `registry.example.com/order-demo/gateway:git-<sha7>`、端口 8080、公共标签 `app.kubernetes.io/*` 与 `version=<SHA>`，`managed-by=kubectl`（第 6 章冻结值，切换归第 10/14 章）。本章的清单是第 6 章最小闭环的同一份 base，只用来演示声明值；探针、资源限额等加固留到第 7–11 章逐层添加。

**`deploy/base/deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: kubectl
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: gateway
        version: git-1a2b3c4
        app.kubernetes.io/managed-by: kubectl
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: gateway
          image: registry.example.com/order-demo/gateway:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
          env:
            - name: APP_VERSION
              value: git-1a2b3c4
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
```

**`deploy/base/service.yaml`**（删 Pod 实验需要稳定入口，Service 一并给出，字段沿用契约）

```yaml
apiVersion: v1

metadata:
  name: gateway
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway

  type: ClusterIP
  selector:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway

      port: 8080
      targetPort: http
      protocol: TCP
```

**`deploy/base/namespace.yaml`**

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
```

**`hack/show-owner-chain.sh`**（打印 `Deployment → ReplicaSet → Pod` 的 owner 链）

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-dev

echo "== Deployment =="
kubectl -n "${NS}" get deploy gateway \
  -o jsonpath='{.metadata.name}{" | uid="}{.metadata.uid}{"\n"}'

RS=$(kubectl -n "${NS}" get rs \
  -l app.kubernetes.io/component=gateway \
  -o jsonpath='{.items[0].metadata.name}')
echo "== ReplicaSet =="
kubectl -n "${NS}" get rs "${RS}" \
  -o jsonpath='{.metadata.name}{" | owner="}{.metadata.ownerReferences[0].name}{" | replicas="}{.status.replicas}{"\n"}'

echo "== Pods（owner 应指向上面的 ReplicaSet） =="
kubectl -n "${NS}" get pods -l app.kubernetes.io/component=gateway \
  -o custom-columns='POD:.metadata.name,OWNER:.metadata.ownerReferences[0].name,OWNER_KIND:.metadata.ownerReferences[0].kind,STATUS:.status.phase' \
  --no-headers
```

应用这一组文件（顺序固定，先命名空间）：

```bash
kubectl apply -f deploy/base/namespace.yaml
kubectl apply -f deploy/base/deployment.yaml
kubectl apply -f deploy/base/service.yaml
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s
```

## 2.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（本地 kind 一次性集群，需已安装 kind / kubectl / curl；`hack/show-owner-chain.sh` 需先 `chmod +x`）：

```bash
chmod +x hack/show-owner-chain.sh
./hack/show-owner-chain.sh

# 演示 A：改「运行对象」——删 Pod，观察控制循环收敛
kubectl -n order-demo-dev delete pod -l app.kubernetes.io/component=gateway --wait=false
sleep 3
kubectl -n order-demo-dev get pods -l app.kubernetes.io/component=gateway
./hack/show-owner-chain.sh

# 演示 B：改「声明对象」——scale 生效，再由 apply 声明覆盖回去
kubectl -n order-demo-dev scale deploy/gateway --replicas=5
kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}{"\n"}'
kubectl apply -f deploy/base/deployment.yaml
kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}{"\n"}'
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| owner 链 | `show-owner-chain.sh` 输出三级：`Deployment/gateway` → `ReplicaSet/gateway-…` → 2 个 Pod，且每个 Pod 的 `OWNER_KIND` 为 `ReplicaSet` [R-02-3] |
| 删 Pod 后（演示 A） | 副本数自动回到 2，新 Pod 名与旧的不同，owner 链不变——证明收敛由控制器按 Pod 模板完成 [R-02-1] |
| `scale` 后（演示 B） | `.spec.replicas` 读数为 **5**，即改声明会生效，不会被原生 K8s「改回去」 |
| `apply` 声明后 | `.spec.replicas` 回到 **2**，即清单里的声明值覆盖手工改动，`apply` 让实际状态回到期望状态 [R-02-2] |
| Service 入口 | `kubectl -n order-demo-dev get svc gateway` 的 `PORT(S)` 为 `8080/TCP`，删 Pod 期间入口不变 |

演示 A 与演示 B 必须**一起看**：前者证明「改运行对象会被收敛」，后者证明「改声明会生效、而声明才是真相」。第 14 章会再加一层：生产环境由 GitOps 控制器持续比对 Git 声明，届时连演示 B 这种手工 `scale` 也会被漂移检测纠正——但那是 L2 的能力，不属于本章 L0 的原生行为。

**回滚命令 / 步骤**（先演练、后发布）。本章的唯一「回滚」是把集群拉回清单里的声明值：

```bash
kubectl apply -f deploy/base/namespace.yaml
kubectl apply -f deploy/base/deployment.yaml
kubectl apply -f deploy/base/service.yaml
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s
```

> **适用边界**：本节是本地 kind 的**演练**，用 `kubectl scale` / `delete pod` 这类命令式操作，是为了让读者亲眼看清字段与收敛过程。从第 14 章起，生产环境的任何变更必须回到 Git 声明，手工 `kubectl edit` / `scale` 会被漂移检测纠正并写进审计（全书公理 5，见第 3 章）。本节对象是一次性本地集群，不构成对公理的例外。

**回滚验证**：

```bash
./hack/show-owner-chain.sh
kubectl -n order-demo-dev get deploy,replicaset,pod -l app.kubernetes.io/component=gateway
kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}{"\n"}'
```

通过标准：owner 链完整、`ReplicaSet` 与 Pod 数与 `deploy/base/deployment.yaml` 一致、`.spec.replicas` 为 2。**没验证过 owner 链与收敛，就不允许把「我懂声明式了」带进第 3 章**（CL-G-03）。
