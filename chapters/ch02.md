## 2.1 问题与反模式：我明明改了，怎么一会儿又变回去了

第 1 章的事故里，14:34 有人 `kubectl edit` 直接改了运行中的 Pod，想「先加一行环境变量」，几秒后被改了回去（H2）。当时的判断是「K8s 抽风了」。这一章要把这个判断彻底翻过来：**这不是工具故障，而是声明式终态的必然结果**。

读者来这一章时，通常带着一个具体的困惑：我 `kubectl edit` 改了副本数，怎么一会儿又被改回去？K8s 到底在替我管什么？要回答它，得先把三件事分开——**期望状态**（写进声明里的）、**实际状态**（集群里此刻跑着的）、**控制器**（持续比对二者并收敛的那段逻辑）。Kubernetes 的控制器会不断把实际状态拉向期望状态 [R-02-1]；你直接改运行对象，等于只动了「实际状态」，控制器下一次循环就会按声明把它纠正回去 [R-02-2]。这不是 bug，是模型本身。

三个高频反模式（每条按「现象 → 根因 → 本章替代做法」）：

**反模式一：把 Pod 当虚拟机，登录后改文件或改镜像。** 现象是「我进容器改了配置，重启后全没了」「`kubectl edit pod` 改字段报 Forbidden，或者改完一会儿 Pod 就消失了」。根因是把 Pod 当成了可长期持有、可就地修改的执行单元；实际上 Pod 是**可调度的、可被丢弃的最小执行单元**，它由上层控制器按 Pod 模板生成，字段大多不可变，删了会被重建 [R-02-4]。本章的替代做法是用 `hack/show-owner-chain.sh` 打印 `Deployment → ReplicaSet → Pod` 的 owner 链，看清楚「这个 Pod 是谁生的、归谁管」，然后通过改**声明**去改内容（见 2.4、2.5）。

**反模式二：平台方与应用方职责不分，双方都能改同一份清单。** 现象是「副本数到底该谁定」「一次漂移没人认领」。根因是没有划清「谁写声明、谁维护控制器」：控制器和收敛机制属于平台侧，期望状态写什么属于应用侧，两者都伸手就会互相覆盖。本章给一张责任边界表（2.2），把「改副本数」「改镜像」「改控制器行为」分别归到人 [R-02-5]。

**反模式三：以为「改了就生效」，分不清到底改了哪一层。** 现象是有人 `kubectl scale` 之后欢呼「生效了」，有人 `kubectl edit pod` 之后抱怨「没生效」，两边都没意识到自己改的是不同的对象。根因是没建立「运行对象 / 声明对象 / Git 声明」三层视角。本章的决策树（2.2）就是用来当场判定「这次改动改的是哪一层、会不会被收敛」。

> **一个刻意的边界**：本章只讲**机制**——控制器怎么收敛、owner 链怎么级联——**不评价自愈的好坏**。「自愈会不会误伤」「漂移检测该不该自动纠正」是第 14 章的问题；本章若提前下结论，会和那里的「自愈误伤」讨论打架。同样，本章讲的控制循环与第 27 章的协调循环是同一机制在不同深度的展开，正式定义只在此处给一次，第 27 章不再重复定义。

## 2.2 范式与决策树：期望状态 → 控制器 → 实际状态

先把本书的基准术语定准。**应用 application** 是「一组共同交付、共同回滚的工作负载与配置的最小单元」——对 `order-demo` 而言，`gateway`、`api`、`worker`、`db` 及其配置共同构成一个应用，单独一个 `Deployment` 或单个 `Pod` 都不是「应用」。这个定义是可验证的：把任意一个组件单独回滚而其余不动，若交付结果不再自洽，就说明你拆错了一个应用。这套术语所处的云原生语境由 CNCF 的定义给出 [R-02-7]。

**控制循环 reconciliation**（本章正式定义）：控制器持续比对**实际状态**与**期望状态**并收敛，直至二者一致。它不是「K8s 自动帮你修好一切」——收敛的目标是你写的那份声明，声明写错，控制器会稳定地维持错误。它的可验证形式就是 2.5 的删 Pod 实验：删掉一个 Pod（实际状态偏离），控制器立刻按 `ReplicaSet` 的 Pod 模板新建（收敛回期望状态）。协调循环在第 27 章作为 Operator 的机制再深入，本章不展开。

### 2.2.1 白话图解：控制器是怎么「一直盯着」集群的

很多人第一次理解声明式终态时，心里想的是「我提交一份声明，K8s 跑一次去把它对齐，然后就完事了」。这是错的。控制循环（reconciliation）**不是一次性动作，而是一个永不退出的持续循环**：它每隔很短时间就重新看一眼「实际状态离期望状态还差多少」，差多少补多少 [R-02-1]。换句话说，收敛是进行时，不是完成时。

为什么必须是持续的？因为实际状态无时无刻不在「漂移」：节点会宕机、Pod 会被驱逐、有人会误删、依赖的镜像仓库会抽风、可用区会出网络抖动。如果收敛只在你提交声明那一刻跑一次，那么几分钟后的一次节点故障就会让集群永远偏离声明，而你毫无察觉。声明式系统的精髓恰恰在于：**实际状态一旦偏离期望，就会被下一次循环自动拉回**，哪怕偏离发生在你提交声明很久之后。

下面这张白话图解把「控制器内部」拆成三块，帮你建立正确直觉。

```
┌─────────────────────────────────────────────────────────────┐
│ 你的声明（期望状态）                                          │
│   Deployment.spec.replicas: 2  ──写入──▶  API Server（etcd）  │
└─────────────────────────────────────────────────────────────┘
                          │
        ┌─────────────────┴──────────────────┐
        ▼                                     ▼
【Informer】                              【Workqueue（限速队列）】
 ① LIST：启动先全量拉一次所有相关对象        事件去重：同一对象连续 10 个
 ② WATCH：之后只收「增量事件」(Add/Update/   "Pod 变了" 合并成 1 个待处理项
    Delete)，几乎零成本                  重试：处理失败按指数退避重新入队
 ③ 本地维护一份缓存(Store)，不每个事件        保证：抖动/临时的 API 超时
   都打 API Server                                      不致永久丢失收敛
        │ 事件 →                          │
        └──────────▶ 入队 ◀───────────────┘
                          │
                          ▼
                  【Controller 循环】
             不断从队列取出对象，执行 reconcile：
               1. 从缓存/API 读「实际状态」
               2. 从声明读「期望状态」
               3. 算 diff，发动作（建/删/改 Pod）
               4. 更新 status，回到队列等下一个事件
```

三块各自的职责：

- **Informer 负责「感知」**。它先用一次 `LIST` 把当前全量对象拉进本地缓存，之后只通过 `WATCH` 长连接接收增量事件。这意味着控制器几乎不反复打 API Server，也不靠「定时轮询全量」——既省资源又低延迟。本地缓存让你查对象状态时不用每次都访问 etcd。

- **Workqueue 负责「绝不漏、绝不崩」**。这是「持续而非一次性」的关键保险。同一对象在 1 秒内被改了 10 次，队列只把它当 1 个待办；某次 reconcile 因 API 超时失败了，队列按指数退避把它重新放回去；哪怕 informer 漏了个事件，控制器还有**周期性 resync（默认约 5 分钟强制把所有对象重新入队一次）**，相当于「兜底体检」，保证最终一定会收敛。

- **Controller 循环负责「算与做」**。它从队列拿一个对象的 key，去读实际状态和期望状态，算出差异，发出创建/删除/修改动作，然后更新 status。这一圈叫一次 reconcile。reconcile 必须是**幂等**的：跑一次和跑一百次结果一样，这正是「持续循环」安全的前提。

把这三块连起来你就明白了：**收敛之所以是持续而非一次性，是因为「实际状态 → 期望状态」的差距随时会被外部事件重新打开，而控制器的设计目标就是「无论差距何时出现，下一次循环都把它关上」** [R-02-1]。这也是为什么第 1 章那个「改了又被改回去」的现象不是抽风：你只动了实际状态（Pod），控制器下一圈就按声明把它纠正——它根本不知道也不关心你「手动改过」，它只在乎声明。

> **本章观点（机制层面，不需额外背书）**：`level-triggered`（基于状态）而非 `edge-triggered`（基于事件）是这套设计的底层哲学——控制器关心「现在差多少」，而非「刚才发生了什么」。这和第 27 章 Operator 的 reconcile 是同一套心智，第 27 章只会加「自定义资源 + 自定义逻辑」，不会改这个循环模型。

**OwnerReference** 决定级联删除与重建：每个 Pod 的 `metadata.ownerReferences` 指向生成它的 `ReplicaSet`，`ReplicaSet` 再指向 `Deployment` [R-02-3]。所以删 `Deployment` 会级联删掉 `ReplicaSet` 与 Pod，而删单个 Pod 只会触发重建——这正是「Pod 不是虚机」在 API 层面的证据。

### 2.2.2 OwnerReference 与 finalizer：级联删除到底谁先谁后

2.2 已经给过 `OwnerReference` 的结论：每个 Pod 的 `metadata.ownerReferences` 指向 `ReplicaSet`，`ReplicaSet` 指向 `Deployment`，于是删 owner 会级联带走 dependent [R-02-3]。但「级联删除」内部其实有两套机制在配合——`OwnerReference` 决定「该不该带走」，`finalizer` 决定「带走前要不要先干点清理活」。把先后关系讲清楚，既能避免「对象卡在 `Terminating` 删不掉」的经典事故，也为第 27 章 Operator 的 `finalizer` 用法埋好伏笔。

先说 `OwnerReference` 这一侧。Kubernetes 有个叫 **Garbage Collector（GC）** 的控制器，它持续扫描所有对象的 owner 关系，构造成一棵依赖树。当你删除一个 owner（比如 `Deployment`）且没加 `propagationPolicy: Orphan`，GC 会把它的所有 dependent（如 `ReplicaSet`）也标记为删除，再顺着 `ReplicaSet → Pod` 一路带下去。所以级联的方向永远是 **owner → dependent**，由 `OwnerReference` 这条边定义，而不是反过来。

再说 `finalizer` 这一侧。它是对象 `metadata.finalizers` 里的一个字符串列表，相当于「删除前必须完成的清理任务清单」。当一个对象还有 finalizer 时，你发起删除，API Server 不会真删它，而是给它打上 `deletionTimestamp`、状态变成 `Terminating`，然后**停住**，等到「负责这个 finalizer 的控制器」把清理活干完、主动把 finalizer 从列表里移除，对象才会真正消失。典型场景：PVC 删之前要先把绑定的 PV 解绑并回收；带 Operator 的自定义资源删之前要先把外部资源（比如一个云数据库实例）清掉。

那么两者在「删一个 Deployment」时到底谁先谁后？顺序是这样的：

1. **你发起删除 `Deployment`**。API Server 看到它身上若还有 finalizer（原生 `Deployment` 通常没有，但假设你加了，或平台侧注入了），先给它打 `deletionTimestamp`，进入 `Terminating`，**此时 GC 不会立刻级联删它的 dependents**。
2. **负责该 finalizer 的控制器执行清理**（例如平台方在删除前备份当前副本分布），完成后把 finalizer 移除。
3. **`Deployment` 的 finalizer 清空后，它才真正从 etcd 删除**；与此同时 GC 开始处理它的 dependents（那个 `ReplicaSet`）。
4. **`ReplicaSet` 进入删除流程**：同样，若它身上有 finalizer，先等控制器清理、移除 finalizer，才真正删除；删掉 `ReplicaSet` 后，GC 再级联删它名下的 Pod。Pod 一般无 finalizer，直接被回收。

一句话记忆：**finalizer 是「删自己之前的清场」，OwnerReference 是「删完自己之后带走小弟」**。`finalizer` 不解决级联，它只解决「我自己删不掉之前必须先做什么」；`OwnerReference` 才解决「我没了之后谁跟着没」。二者串成一条有序的删除链。

这里最危险的坑是 **finalizer 卡死**：如果负责某个 finalizer 的控制器挂了、或者清理逻辑永远报错（比如外部系统超时且没退避），对象就会永远卡在 `Terminating`，既删不掉也用不了，还占着名字和配额。排障命令是看 `kubectl get <资源> -o jsonpath='{.metadata.finalizers}'` 和 `deletionTimestamp`；第 27 章会强调：凡是你自己在 Operator 里加的 finalizer，**清理逻辑必须幂等、必须能在控制器重启后继续推进**，否则就是埋雷。

> **预告第 27 章**：本章只把 `OwnerReference` 与 `finalizer` 当「内置机制」讲清楚（谁先谁后、为什么会卡）。第 27 章「扩展方式五选一决策树」里，当你决定「要不要自己写 Operator / CRD」时，`finalizer` 会从配角变成主角——自定义资源的清理（外部资源回收、PVC 解绑）几乎都靠它，而它的幂等性与卡死处置正是「该不该写 Operator」的关键判据之一。那里会给你一张「本项目不写 Operator」的理由清单，本章不必提前下结论。

还有一个梯度问题：本章会用到「**清单 manifests**」（描述期望状态的 YAML/JSON 声明文件，正式定义详见第 10 章）和「**工作负载 workload**」（承载应用进程的 K8s 资源，如 `Deployment` / `StatefulSet` / `Job`，正式定义详见第 7 章）。在正式定义章之前，本章只把它们当「写声明的文件」和「跑进程的资源」来用，不拿它们推导任何结论。

**本章要回答的决策问题**：声明式终态之下，「改配置」和「改运行状态」到底有什么区别，谁有权改？答案是一张责任边界表。

| 层 | 谁写声明 | 谁维护控制器 / 收敛机制 | 出问题找谁 |
|---|---|---|---|
| 控制面（API Server、调度器） | K8s 项目 | 集群管理员 / 平台方 | 平台方 |
| 平台机制（GitOps、策略、网络插件） | 平台方 | 平台方 | 平台方 |
| 应用期望状态（`deploy/base` 等清单） | **应用方** | `Deployment` / `ReplicaSet` 等内置控制器 | 应用方 |
| 运行对象（Pod） | 无——由控制器按模板生成 | 控制器 | 不要手改，先看 owner 链 |

> **本书观点（本章第 1 条主张，不需要外部背书）**
>
> **主张**：平台方管「收敛机制」，应用方管「期望状态写什么」。这条边界是可操作的，不是组织口号。
>
> **论证**：控制器的行为由平台侧决定（装了什么控制器、开了什么自愈策略），而「副本数、镜像、探针、配置」这些字段表达的是应用意图，只有应用方知道正确值。把两者混在一起，会出现两类典型事故：平台方擅自改了应用清单、应用方去改控制器配置。事故里的 H2 与 H7 都是这条边界失守的后果。边界一旦划清，「谁有权改副本数」就有唯一答案：应用方在声明里改，平台方保证改声明会被收敛。
>
> **反例与适用前提**：这不等于「应用方永远不能碰控制器」。一个小团队里同一个人兼任两角，边界表现为「同一份 PR 里区分清楚哪些是平台配置、哪些是应用声明」即可，不必设两拨人。前提仍是**存在多人协作的变更**；单人本地实验无需这套划分。

### 2.2.3 Server-Side Apply 与字段归属：责任边界细化到「字段」

2.2 的责任边界表把权责划分到了「谁写声明、谁维护控制器」这一层。但当真实集群里**多个主体（应用方、平台方的策略注入器、GitOps 控制器、Helm）都在改同一个 `Deployment`** 时，文件级的责任边界就不够用了——它们改的可能是同一个对象的同一个或不同字段，谁覆盖谁、谁的改动算数，必须有更细的规则。Kubernetes 的 **Server-Side Apply（SSA，服务端应用）** 把责任边界从「谁写整个文件」推进到「谁拥有哪个字段」[R-02-2]。

先对比两种 apply。传统的 **client-side apply** 把一份 `last-applied-configuration` 注解塞进对象，靠客户端做「三方 diff（上次、现在文件、集群当前）」来合并。问题是：当第二个工具（比如平台的准入 Webhook 或另一套 GitOps）也改了同一个对象，三方 diff 经常算不清「这字段到底谁改的」，结果是**静默覆盖或合并失败**，责任再也追不回来。

**Server-Side Apply 换了思路**：每个字段在 API Server 端都记录「哪个 manager（字段管理者）拥有它」。你以 `app-team` 这个 field-manager 提交镜像与副本，平台方以 `platform-policy` 这个 field-manager 注入安全上下文与调度约束——**不同 manager 改不同字段时，两者可以和平共存**；只有当两个 manager 都声明拥有同一个字段、且值不一致时，API Server 才会**直接报错（conflict）**，而不是默默让后到的覆盖先到的。

这对本书的责任边界意味着三点：

- **平台与应用第一次能在「同一份对象」上分工而不打架**。平台方稳定拥有「高频注入的安全上下文 / 调度约束」这类字段，应用方拥有「镜像、副本数、业务 env」这类字段；谁越界改了对方的字段，冲突立刻可见，而不是等线上出问题才回溯。
- **责任边界从组织承诺变成可审计的事实**。字段归属写在对象元数据里，`kubectl get deployment -o jsonpath='{.metadata.managedFields}'` 能直接看到每个字段归谁——这正是 2.2 本书观点的「平台管收敛机制、应用管期望状态」在 API 层面的落地证据 [R-02-5]。
- **它不推翻公理 5（Git 为唯一真相）**。SSA 解决的是「同一集群内多管理者如何不互相踩」，而「生产变更必须回 Git」是更上游的约束：即便用了 SSA，应用方的那个 field-manager 也应当是 GitOps 控制器（如 `argocd`），而不是某人的本地 `kubectl`。SSA 让多控制器写同一资源时的冲突可见、可审计，但真相入口仍然是 Git。

```bash
# 应用方：以 server-side apply 提交，field-manager 标识身份（复用本章 deploy/base/deployment.yaml）
kubectl apply --server-side --field-manager=app-team -f deploy/base/deployment.yaml

# 查看字段到底归谁：冲突排查的第一手证据
kubectl get deployment gateway -n order-demo-dev -o jsonpath='{.metadata.managedFields}' | python3 -m json.tool
```

> **本章观点（不需外部背书）**：SSA 的字段归属是 2.2 责任边界表的「字段级补强」，不是替代。它的前提是「存在多个管理者写同一资源」；若你的环境只有一个 GitOps 控制器统一收敛，字段归属的冲突价值会降低，但 `managedFields` 仍可作为审计线索。不要把 SSA 当成「可以放心手工改生产」的借口——它只让多源写入的边界更清晰，不降低「生产变更回 Git」的刚性要求（公理 5）。

由「三层视角」直接得到一棵决策树，用来当场判定一次改动会有什么结果：

```
你改的是运行对象（Pod / 容器里）的字段？    是 → 会被 ReplicaSet 按 Pod 模板收敛或重建；
        │ 否                                  想持久就改声明（2.4），别手改 Pod
你改的是 Deployment 的 .spec（声明对象）？   是 → 这是合法的期望状态变更，会生效；
        │ 否                                  但生产里它必须来自 Git（见第 14 章）
你改的是 Git 里的清单？                    是 → 唯一持久的真相入口（见第 14 章）
        │ 否
→ 你在动控制器 / 平台机制本身 → 归平台方，按责任边界表找人
```

这里要纠正一个流传很广的误解：**`kubectl scale` 改的是 `Deployment.spec.replicas`，它本身就是期望状态，在原生 K8s 里会生效、不会被「改回去」**。真正「改了不生效」的是直接改运行对象；而「手工改声明也会被纠正」只发生在有持续收敛的 GitOps 体系里——那是第 14 章的漂移纠正，不是本章 L0 环境的行为 [R-02-1][R-02-2]。把这一点讲准，读者才不会用错误的心智模型去理解后面每一章。

### 2.2.4 一张大表看透「改了会怎样」＋一次误操作复盘

把 2.1 的三层视角、2.2 的决策树和刚才的 SSA 串起来，落到一张「三层视角 × 三种改法 × 三种结果」的对照大表上。读这张表的方法：先看你「改的是哪一层（运行对象 / 声明对象 / Git 声明）」，再看「你用哪种改法」，最后一列就是「实际会发生什么、归谁负责」。

| 三层视角 | 三种改法（典型命令） | 收敛机制是否介入 | 三种结果之一 | 在什么前提下会变成另一种结果 | 责任人 |
|---|---|---|---|---|---|
| **运行对象**（Pod 实际跑着的内容） | `kubectl edit pod` 改 env / `kubectl delete pod` | 是——`ReplicaSet` 按 Pod 模板重建或纠正 | **被收敛**：改动被丢弃，Pod 被按声明重建 [R-02-1] | 永远是这行的「受害者」，除非你改成改声明 | 没人该手改；先看 owner 链 |
| **声明对象**（如 `Deployment.spec`） | `kubectl scale` / `kubectl edit deploy` | 否（原生 K8s）——`replicas` 本身就是期望状态，会生效 | **生效且持久**（在本章 L0 原生环境）[R-02-2] | 一旦进入第 14 章 GitOps：手工改声明会被漂移检测纠正回 Git 值 | 应用方（但生产须来自 Git） |
| **Git 声明**（仓库里的清单） | 改 YAML 后 `git commit` + `kubectl apply` / Argo CD 同步 | 是——GitOps 控制器持续比对并收敛 | **唯一持久的真相入口**；最终都会收敛到这里 [R-02-2] | 若没接 GitOps（L0），则等同于「声明对象」那一行的结果 | 应用方，平台方保证收敛 |

这张表把本章最容易混淆的三件事一次说清：**改 Pod 永远会被收敛**（你以为改了，其实下一圈就没了）；**`kubectl scale` 在原生 K8s 是会生效的**（它改的是期望状态本身，不是运行对象）；**只有当 GitOps 接管后，手工改声明才会被「改回去」**——而且那是漂移纠正，不是本章 L0 的行为。把这张表和第 14 章对照着看，心智模型才闭环。

下面用一次误操作复盘，把「看错层」的代价讲具体。**（合成案例，复盘基于多个团队真实踩坑模式归纳，非单一真实事件。）**

> **事故复盘：把 Pod 当虚机改，发布时全丢**
>
> **时间线**
> - D1 14:20 值班同事发现 `api` 容器里一处超时阈值偏小，为「先止血」直接 `kubectl exec` 进容器改了配置文件，又 `kubectl edit pod` 加了个环境变量。他看到进程读了新值，以为「生效了」。
> - D1 14:35 该 Pod 因节点维护被驱逐，控制器按 `ReplicaSet` 模板新建 Pod——**新建的 Pod 用的是镜像里的原始配置，D1 14:20 的所有手工改动瞬间归零**。
> - D3 一次常规发布（`kubectl apply` 新 SHA）触发滚动更新，全部 Pod 重建，他两周来在容器里累积的 3 处「临时改动」彻底消失，线上出现与 D1 相同但更隐蔽的超时故障。
>
> **现象**：「我明明改过、当时也生效了，怎么过几天又错了？」
>
> **根因**：改动落在**运行对象层**（Pod），而该层由控制器按 Pod 模板持续收敛（见上表第一行）。他以为改的是「配置」，实际改的是「会被随时覆盖的临时态」；所谓「当时生效」只是两次收敛之间的窗口，不是持久状态。
>
> **对照决策树**：这次操作在 2.2 决策树的第一问就判死了——「你改的是运行对象的字段 → 会被收敛或重建；想持久就改声明」。
>
> **教训（可写进 runbook）**：① 任何「先止血」的临时改 Pod，必须在同一个值班班次内转成 Git 里的声明改动，否则必丢；② 用 `./hack/show-owner-chain.sh` 看一眼，确认你动的对象有没有 owner——有 owner 的就不该手改；③ 把「改了运行对象」列为告警信号：审计里一旦出现对运行对象的 `edit`，直接当作一次潜在的配置丢失风险来追。

> **本书观点（不需额外背书）**：这张大表与复盘共同说明，声明式终态下「改的层」比「改的动作」更决定结果。把层认错，再熟练的 `kubectl` 也是在给控制器制造待收敛的偏差。第 14 章会在这张表上加第四列「GitOps 接管后的真实结果」，此处先按 L0 原生行为讲准。

### 2.2.5 三种对象管理方式的完整对比：命令式命令、命令式对象配置与声明式对象配置

Kubernetes 官方把「怎么管理对象」分成三种方式，它们不是同一件事的三个名字，而是**提交语义完全不同**的三种方式 [R-02-2]。分清三者，2.2.4 大表里每个操作的归属才能坐实。

| 方式 | 代表操作 | 提交语义 | 可复现 / 可审计 | 多人多工具协作 | 适用场景 |
|---|---|---|---|---|---|
| 命令式命令 | `kubectl run` / `create` / `expose` / `scale` | 直接对集群里的对象下指令，无清单 | 无清单即无审计，事后无法复现 | 极差：别人不知道你执行过什么 | 本地探索、一次性 kind 集群里的临时实验 |
| 命令式对象配置 | `kubectl create -f` / `replace -f` | 「执行这份文件」：create 只建不更，replace 按文件全量替换 | 有清单，但语义是动作而非终态 | 差：replace 会抹掉清单之外、集群侧已有的字段（如其他控制器注入的） | 单人维护、单对象一次性创建 |
| 声明式对象配置 | `kubectl apply -f`（或 GitOps 控制器同步） | 「让集群与这份文件对齐」：先 diff，再只把文件涉及的字段收敛到文件值 | 完整 | 好：不碰文件之外的字段，多 field-manager 可共存（见 2.2.3 SSA） | 一切需要长期维护的环境 |

关键差别在后两行：**文件可以完全相同，语义不同**。`replace` 是「把对象变成这份文件」，没有出现在文件里的字段会被清掉；`apply` 是「把这份文件涉及的字段对齐到文件值」，文件之外的字段一律不动 [R-02-2]。这正是 2.2.3 字段归属问题的根源：命令式替换天然只认一份文件，声明式收敛天然保留其他管理者的字段。

**迁移路径**是一条单向条：① 命令式命令 → 固化成清单：用 `kubectl get deploy gateway -n order-demo-dev -o yaml > gateway.yaml` 把敲过的命令导出，删掉 `status` 等运行时字段后转为 `apply` 管理；② 命令式对象配置 → 声明式：把 `create`/`replace` 改为 `apply`，注意 `replace` 曾抹掉的集群侧字段不会因切换而自动恢复，需在源头清单里显式补齐后再 apply。一条可执行的判据：**凡是要执行第二次的操作，不允许停留在命令式命令**。

迁移实操（本章 L0 环境即可演练，与 2.5 演示 B 同源）：

```bash
# ① 命令式命令：手动扩到 4 副本（此刻真相只在执行者的操作历史里，无文件承载）
kubectl -n order-demo-dev scale deploy/gateway --replicas=4

# ② 固化：把当前对象导出为清单底稿（需删掉 status、metadata.uid 等运行时字段后再修整）
kubectl -n order-demo-dev get deploy gateway -o yaml > gateway.exported.yaml

# ③ 声明化：把期望状态重新写准（.spec.replicas: 2），用清单收敛掉命令式的残留值
kubectl apply -f deploy/base/deployment.yaml
kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}{"\n"}'
# 通过标准：输出为 2，即声明值覆盖了无文件承载的命令式改动
```

这一段就是「命令式的改动没有真相」的直观证明：第 ① 步的值不存在于任何清单，下一次 `apply` 就被声明覆盖，而声明进 Git 后可以被审、被晋升、被回滚。

为什么 Kubernetes 选声明式？官方明确推荐声明式对象配置作为多人、多环境下的默认方式 [R-02-2]。更深一层的原因在于：只有「终态声明 + 持续比对」这套语义，控制器才有资格接管「保持一致」这件事——意图（声明里写什么）与执行（怎么达成、何时重试）被解耦，人不在场时系统仍会收敛。这是 Borg/Omega 一脉「把运维知识固化进编排系统」的延续 [R-02-5]；命令式操作每次都依赖人在场且人在状态，无法支撑第 14 章 GitOps 与公理 5（Git 为唯一真相）。

### 2.2.6 「改运行对象 vs 改期望状态」操作负面清单

2.2.4 的大表给的是「层 × 结果」，这里落到具体命令上，做成一张值班时可直接查的负面清单。判据只有一句话：**操作结束后，真相（正确状态的唯一来源）在哪里？** 真相还在你手上或容器里，就注定被收敛或丢失 [R-02-2]。

| 操作 | 改的层 | 短期现象 | 终局（本次或 GitOps 接管后） | 正确替代 |
|---|---|---|---|---|
| `kubectl exec` 进容器改文件 | 运行对象内部（连声明都不碰） | 进程读到新值，「生效了」 | Pod 一重建即归零（见 2.2.4 复盘） | 改 ConfigMap 或清单里的 env，再 `apply` |
| `kubectl edit pod` | 运行对象 | 多数字段直接 Forbidden 或改后被重建 | 被 `ReplicaSet` 按 Pod 模板重建 | 用 owner 链找到该改的那份清单，改 Pod 模板 |
| `kubectl scale deploy` | 声明对象（`.spec.replicas`） | 生效 | L0 持久；GitOps 后被漂移纠正回 Git 值 | 副本数进 Git，走 PR |
| `kubectl set image` / `kubectl patch` | 声明对象（指定字段） | 生效 | 绕开变更入口与审计；GitOps 后被纠正 | 改 Git 清单；紧急止血也须当班次回 Git（公理 5） |
| `kubectl edit deploy` | 声明对象 | 生效 | 同上，且 `managedFields` 记录混乱，事后说不清谁改的 | 改 Git 清单 |
| `kubectl replace` / `apply --force` | 声明对象，但语义是全量替换 | 生效 | 清单之外、其他控制器注入的字段被抹掉 | 用 `apply`；确需变更时在清单里显式写全字段 |
| 「删了重建就修好」 | 触发删除＋重建 | 对象回来了，故障依旧 | 声明没改，重建回来的就是同一个错误状态 | 先修声明，再 `apply` 让收敛完成重建 |
| 改了本地 YAML 没执行 apply | 哪层都没改 | 「怎么没生效？」 | 集群与文件都停在原地 | `kubectl apply -f` + `rollout status` 验证 |

两个高频误判值得点名。其一，「删了重建」不是修复：删除与重建都只是收敛动作（见 2.2.7），收敛的输入仍是那份没改的声明，所以重建出来的还是同一个故障态——先改声明、再让控制器重建，顺序不能反。其二，`scale` 不在「必死名单」里：它改的是声明对象，在 L0 生效且持久；生产里禁止它是因为它绕开了 Git 入口（公理 5），不是因为「会被改回去」（公理 5 的边界见第 3 章 3.2）。这张清单也可以当值班自查题用：每次异常处置收尾时，回看本次用过的命令落在哪一行——若落在 `exec` / `edit pod` 两行，本次处置产生的任何改动都已注定丢失，必须当班次补一份声明改动进 Git，否则等同于把故障原样埋回。

### 2.2.7 幂等与「删除也是收敛」：控制循环的完整闭环

2.2.1 给过 reconcile 的定义「算 diff、发动作」，但有两个性质决定这套循环敢不敢永远跑下去。

**幂等是循环安全的前提**。reconcile 必须满足「跑一次和跑一百次，集群结果一样」。以 `ReplicaSet` 为例：它的 reconcile 不是「数一下缺几个、闭眼建够」，而是每一轮都从「期望 2 副本 vs 实际 N 副本」重新计算 diff——缺 1 建 1，多 1 删 1，这一轮做完就退出，等下一个事件再重新算 [R-02-1]。之所以必须如此，是因为 workqueue 会因失败退避而重新入队、resync 会周期性全量重入队（见 2.2.1）：**同一个对象被重复 reconcile 是常态而非异常**。只有幂等，重复执行才不会累积副作用。反过来，幂等写坏的自定义控制器，重复执行会重复创建资源——第 28 章把「reconcile 幂等性测试」列为 Operator 验收项，根子就在这里。

**删除不是收敛的旁路，而是收敛动作本身**。期望状态既能说「要有 2 个副本」，也能说「一个都不要」（`.spec.replicas: 0`）或「这个对象不该存在」（把对象从清单删掉再 `apply`）。控制器通过**删除实际对象**来满足这些期望：缩容删 Pod、GC 沿 owner 链级联删 `ReplicaSet` 与 Pod（2.2.2 的删除链）[R-02-3]，都是同一循环里「向下方向的收敛」。2.5 演示 A 里你删 Pod、控制器补建，与这里控制器删 Pod、副本数降回 0，是同一个 reconcile 的两个方向——收敛的方向由声明决定，不由动作的方向决定。2.5 演示 B 的后半段（`apply` 把 `.spec.replicas` 从 5 收敛回 2）就是「向下收敛」的可复现实验：控制器删掉多余的 3 个 Pod，命令与通过标准见 2.5。

finalizer 在这个视角下的作用就清楚了：**它让「删除」也变成一个带重试的收敛子循环**。finalizer 未清空时，对象只被打上 `deletionTimestamp` 而不真正消失；负责它的控制器把「清理外部资源、解绑存储」当作一次 reconcile 幂等地推进，成功才摘掉 finalizer，失败则下一轮重试。所以对象卡在 `Terminating` 不是系统异常，而是「删除这个收敛动作正在重试」——正确的处置入口不是反复 `delete --force`，而是查 `metadata.finalizers` 列表、定位清理控制器为何不推进（2.2.2 已给排障命令）。错误心智把删除当瞬时事件，看到 `Terminating` 就慌；正确心智把删除当成与创建对等的收敛过程：**创建是「让实际状态长成声明」，删除是「让实际状态退回声明之外」**。这一视角在第 16 章（StatefulSet 的删除语义）与第 27 章（自定义资源的 finalizer 设计）都会再次用到。

## 2.3 工具选型：本章刻意不选工具

这一章的「工具选型」结论和样板章一致：**先不引入任何配置打包与交付工具**。本章要建的是心智模型，不是流水线；在还没能力判断「一份清单对不对」之前就装上模板引擎与 GitOps 控制器，只会把错误也一起收敛进去。第 10 章才系统比较 Helm 4.x / Kustomize 5.x，第 14 章才比较 Argo CD 3.x / Flux 2.x，第 27 章才谈要不要扩展 K8s API。

| 工具 | 本章是否使用 | 何时不该用（与本章相关的一条） |
|---|---|---|
| Helm 4.x / Kustomize 5.x | 不用 | 只有一个环境、只想看清「改声明会怎样」时；模板与 overlay 会遮住「到底提交了什么」 |
| Argo CD 3.x / Flux 2.x | 不用 | 还没建立「期望状态 / 实际状态」的概念之前；持续收敛会把错误也收敛进去 |
| Operator / CRD | 不用 | 需求只是「解释一次收敛」；给 K8s 加一种新资源类型（CRD，详见第 27 章）在此毫无必要 |
| kind + kubectl + curl | **使用** | — |

本章最小工具集只有四个：`kind`（本地集群，版本见附录 A）、`kubectl`（随 Kubernetes 1.32）、`curl`、`bash`。它们不产生任何「需要选型」的决策，因此本章没有选型矩阵，只有上一节的判据表与责任边界表——按 9.6「避免为凑模板而注水」，这里不硬塞工具对比。先从裸清单理解模型，再引入自动化，是 Kelsey Hightower 那类教学路径一贯的次序 [R-02-6]。

## 2.4 落地配置（完整可应用文件，Kubernetes 1.32+，`apiVersion: apps/v1`）

> 全部字段沿用配置契约：命名空间 `order-demo-dev`、镜像 `registry.example.com/order-demo/gateway:git-<sha7>`、端口 8080、公共标签 `app.kubernetes.io/*` 与 `version=<SHA>`，`managed-by=kubectl`（第 6 章冻结值，切换归第 10/14 章）。本章的清单是第 6 章最小闭环的同一份 base，只用来演示声明值；探针、资源限额等加固留到第 7–11 章逐层添加。

**`deploy/base/deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: kubectl
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
  strategy:
    type: RollingUpdate

      maxSurge: 1
```

**`hack/show-owner-chain.sh`**（打印 `Deployment → ReplicaSet → Pod` 的 owner 链）

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-dev

echo "== Deployment =="
kubectl -n "${NS}" get deploy gateway \
  -o jsonpath='{.metadata.name}{" | uid="}{.metadata.uid}{"\n"}'

RS=$(kubectl -n "${NS}" get rs \
  -l app.kubernetes.io/component=gateway \
  -o jsonpath='{.items[0].metadata.name}')
echo "== ReplicaSet =="
kubectl -n "${NS}" get rs "${RS}" \
  -o jsonpath='{.metadata.name}{" | owner="}{.metadata.ownerReferences[0].name}{" | replicas="}{.status.replicas}{"\n"}'

echo "== Pods（owner 应指向上面的 ReplicaSet） =="
kubectl -n "${NS}" get pods -l app.kubernetes.io/component=gateway \
  -o custom-columns='POD:.metadata.name,OWNER:.metadata.ownerReferences[0].name,OWNER_KIND:.metadata.ownerReferences[0].kind,STATUS:.status.phase' \
  --no-headers
```

```bash
kubectl apply -f deploy/base/service.yaml

```

## 2.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（本地 kind 一次性集群，需已安装 kind / kubectl / curl；`hack/show-owner-chain.sh` 需先 `chmod +x`）：

```bash
chmod +x hack/show-owner-chain.sh
./hack/show-owner-chain.sh

# 演示 A：改「运行对象」——删 Pod，观察控制循环收敛
kubectl -n order-demo-dev delete pod -l app.kubernetes.io/component=gateway --wait=false
sleep 3
kubectl -n order-demo-dev get pods -l app.kubernetes.io/component=gateway
./hack/show-owner-chain.sh

# 演示 B：改「声明对象」——scale 生效，再由 apply 声明覆盖回去
kubectl -n order-demo-dev scale deploy/gateway --replicas=5
kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}{"\n"}'
kubectl apply -f deploy/base/deployment.yaml
kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}{"\n"}'
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| owner 链 | `show-owner-chain.sh` 输出三级：`Deployment/gateway` → `ReplicaSet/gateway-…` → 2 个 Pod，且每个 Pod 的 `OWNER_KIND` 为 `ReplicaSet` [R-02-3] |
| 删 Pod 后（演示 A） | 副本数自动回到 2，新 Pod 名与旧的不同，owner 链不变——证明收敛由控制器按 Pod 模板完成 [R-02-1] |
| `scale` 后（演示 B） | `.spec.replicas` 读数为 **5**，即改声明会生效，不会被原生 K8s「改回去」 |
| `apply` 声明后 | `.spec.replicas` 回到 **2**，即清单里的声明值覆盖手工改动，`apply` 让实际状态回到期望状态 [R-02-2] |
| Service 入口 | `kubectl -n order-demo-dev get svc gateway` 的 `PORT(S)` 为 `8080/TCP`，删 Pod 期间入口不变 |

演示 A 与演示 B 必须**一起看**：前者证明「改运行对象会被收敛」，后者证明「改声明会生效、而声明才是真相」。第 14 章会再加一层：生产环境由 GitOps 控制器持续比对 Git 声明，届时连演示 B 这种手工 `scale` 也会被漂移检测纠正——但那是 L2 的能力，不属于本章 L0 的原生行为。

**回滚命令 / 步骤**（先演练、后发布）。本章的唯一「回滚」是把集群拉回清单里的声明值：

```bash
kubectl apply -f deploy/base/namespace.yaml
kubectl apply -f deploy/base/deployment.yaml
kubectl apply -f deploy/base/service.yaml
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s
```

> **适用边界**：本节是本地 kind 的**演练**，用 `kubectl scale` / `delete pod` 这类命令式操作，是为了让读者亲眼看清字段与收敛过程。从第 14 章起，生产环境的任何变更必须回到 Git 声明，手工 `kubectl edit` / `scale` 会被漂移检测纠正并写进审计（全书公理 5，见第 3 章）。本节对象是一次性本地集群，不构成对公理的例外。

**回滚验证**：

```bash
./hack/show-owner-chain.sh
kubectl -n order-demo-dev get deploy,replicaset,pod -l app.kubernetes.io/component=gateway
kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}{"\n"}'
```

通过标准：owner 链完整、`ReplicaSet` 与 Pod 数与 `deploy/base/deployment.yaml` 一致、`.spec.replicas` 为 2。**没验证过 owner 链与收敛，就不允许把「我懂声明式了」带进第 3 章**（CL-G-03）。
