## 21.1 问题与反模式：三套系统都装了，为什么还是串不起来

**合成案例**。周二 10:12，`order-demo` 下单接口的 p99 从 180ms 涨到 2.4s。值班同学打开三个标签页：Prometheus 里看到 gateway 5xx 抬了一点，Loki 里刷出一堆超时日志，Tempo 里能看到慢调用散落在 `api → db` 之间。三处都有数据，却没有一处能回答「这条具体的失败请求到底走了哪几跳、在哪一跳变慢」。最后靠一个人在三个系统里手工比对时间戳和用户 ID，花了 40 分钟才定位到是 `api` 的一次连接池耗尽——而这段时间里，第 23 章的 runbook 本可以让止血在 5 分钟内完成。

问题不在采集量，而在**关联键缺失**：指标按聚合计数存、日志按行存、链路按 trace 存，三者没有共同的 `trace_id`，就不可能从一条告警下钻到一次请求。OpenTelemetry 的语义约定正是为解决这件事而存在——它规定 `trace_id`、`span_id`、`service.name` 等字段在三类信号里用同一套名字与编码，跨信号关联才有前提 [R-21-1]。

三个高频反模式：

**反模式一：把 `user_id` / `order_id` 写进指标 label。** 现象是 Prometheus 时间序列数量随订单量线性增长，最终 TSDB 内存被打满、查询超时甚至 OOM。根因是 label 的每一个取值组合都会生成一条独立序列，用户 ID 这类无界维度会把序列数放大到不可控。本章的替代做法是**采集前定 label 白名单**：只保留 `service`、`component`、`method`、`route`、`status_code`、`le` 六个低基数维度，其余一律在 Collector 里丢弃；高基数信息放日志与链路，不放指标 [R-21-3]。

**反模式二：只采指标不采链路。** 现象是「知道错误率涨了，但不知道是哪一跳」，跨服务问题只能靠猜、靠翻代码。根因是把三大信号当成三份独立报表，而不是一次请求的三个投影。本章要求 `trace_id` 贯通：应用把 `trace_id` 写进结构化日志、随响应头返回、并作为指标 exemplar 的关联键，于是「指标异常 → exemplar 取到 trace_id → 日志/链路按 id 捞」成为一条可脚本化的路径 [R-21-1][R-21-6]。

**反模式三：全量日志不采样。** 现象是存储与检索成本随流量上涨，查一次日志要等十几秒，真正有用的错误日志被淹没在 200 成功日志里。根因是把「可观测」误解为「全留」。本章用**尾部采样**：错误链路、慢链路 100% 保留，正常链路按比例采样；日志侧错误与慢请求全采、正常请求按比例采样，成本只随有效信号增长，不随总流量线性增长 [R-21-5][R-21-2]。

> 三者的共同教训：**采集不是越多越好，关联才是**。第 20 章定义的 SLI 依赖 `order_demo_http_requests_total`，本章负责把它采出来、命名好、并与日志链路串上；命名一旦与第 15、20、22 章不一致，四章示例会同时失效（SP-09、SP-15）。

## 21.2 范式与决策树：统一采集层 + 三类信号各归其位

本章要回答的决策问题是：**指标、日志、链路该怎么采集、存储与关联，才能既查得动又不被 cardinality 拖垮**。

**采集拓扑**（唯一示例实现取 `decisions.md`）：应用侧 OTel SDK 通过 OTLP 把三类信号发给 **OTel Collector 0.x**；Collector 作为统一采集层做过滤、脱敏、采样与分流，再分别导出到 Prometheus 3.x（指标）、Loki 3.x（日志）、Tempo 2.x（链路）；长期指标由 Thanos 0.x 或兼容远端存储承接 [R-21-2][R-21-7]。请求入口沿用第 19 章的 Gateway API 固定值：`GatewayClass: eg`、`Gateway` 名 `order-demo-gw`、`HTTPRoute` 名 `gateway-route`，流量经它到 `gateway` Service 8080，再由 `api` 8081、`db` 5432 承载（见第 19 章、见第 6 章）。

| 信号 | 采集点 | 落地后端 | 关联键 | 回答的问题 |
|---|---|---|---|---|
| 指标 Metrics | Collector `otlp` → `prometheus` exporter :8889 | Prometheus 3.x / Thanos 0.x | `service` + `route` + exemplar `trace_id` | 有多少、多快、错多少（第 20 章 SLI 的数据源） |
| 日志 Logs | 应用 stdout 结构化 JSON → Collector `loki` exporter | Loki 3.x | `trace_id` + `span_id` | 这一次的上下文、报错栈、入参摘要 |
| 链路 Traces | 应用 OTel SDK → Collector `tail_sampling` → `otlp` exporter | Tempo 2.x | `trace_id` | 走了哪几跳、时间花在哪一跳 |

**四大黄金信号**（延迟、流量、错误、饱和度）是组织监控的**用户视角** [R-21-8]；**RED**（Rate / Errors / Duration）是面向请求型服务的精简版 [R-21-9]，**USE**（Utilization / Saturation / Errors）是面向资源的检查法 [R-21-10]。三者不是互相替代的清单：黄金信号告诉你「该看哪四类」，RED 把服务侧指标收敛成三列，USE 提醒你别漏掉「资源明明没满但队列已排长」这种饱和度问题。对 `order-demo`：`gateway`/`api` 用 RED，`db` 与节点用 USE，整体大盘按黄金信号分栏 [R-21-8][R-21-9][R-21-10]。

**排障路径判据表**（决定先打开哪个系统）：

| 现象 | 先查 | 判定 | 下钻到 |
|---|---|---|---|
| 「整体是不是坏了」 | Prometheus 黄金信号大盘 | SLI 是否跌破第 20 章窗口阈值 | 触发第 22 章告警 |
| 「哪一类请求坏了」 | 按 `route` / `status_code` 聚合 | 定位到具体接口与错误码 | exemplar 取 `trace_id` |
| 「这一跳为什么慢」 | Tempo 按 `trace_id` 看瀑布图 | 找到耗时最长的 span | 该服务的日志上下文 |
| 「资源还是代码问题」 | USE：饱和度 / 队列 / 错误 | 饱和度异常 → 第 17、18 章；否则看日志栈 | 第 23 章 runbook |

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：仪表盘必须分层——服务总览 → 组件下钻 → 排障视图；把全部图表堆在一页，会让值班在真正需要定位时更慢。
>
> **论证**：总览页的职责只有一个，就是回答「现在整体好不好、坏在哪一类」，因此它应当只有少量能一眼判读的图；下钻页按组件聚合 RED/USE，排障页才放高基数的分位数、exemplar 与日志跳转。三层各自的读者与动作不同：总览给值班、下钻给 owner、排障给正在救火的人。把所有图塞进一页，等于让值班每次告警都要在一屏里重新做一次信息筛选，告警越紧急，筛选越慢。
>
> **反例与适用前提**：这三层不是三个必须独立的系统，一个 Grafana 11.x 里用变量与链接跳转即可实现；对只有一个服务、三个人值班的小团队，总览与下钻可以合并成一页，但「排障视图与总览分离」不能省——第 23 章 runbook 的定位耗时，很大一部分就来自在总览页里翻找单条 trace。若团队已有成熟的服务目录与自动下钻（按 `service.name` 自动跳转），分层可由工具代劳，但仍须保证总览页不承载高基数明细。

## 21.3 工具选型：后端矩阵与「何时不该用」

| 工具 | 主版本 | 保留期 / 查询能力 | 成本归因 | 何时不该用 | 回滚方式 |
|---|---|---|---|---|---|
| OTel Collector | 0.x | 不存数据，只做采集与分流 | 与实例数成正比，占比最小 | 只有单一信号、且已有稳定采集链路时；多一层网关纯增运维面 | `rollout undo`（§21.5） |
| Prometheus | 3.x | 本地默认 15 天；PromQL 聚合与告警最强 | 内存/本地盘为主，随序列数线性增长 | 需要跨年趋势、跨集群全局查询时；本地保留期不够 | `apply -k` 回上一 tag |
| Thanos / 兼容远端存储（Mimir 3.x） | 0.x / 3.x | 对象存储长期保留、全局查询、降采样 | 对象存储 + compactor 计算，随保留期增长 | 只要 2 周本地数据、无跨集群查询时；引入对象存储是纯增成本 | 关闭 `remoteWrite` 即可退回本地 |
| Loki | 3.x | LogQL 按 label 检索，不做全文索引 | 只索引 label，成本随日志量与保留期增长 | 要做全文检索 / 复杂文本分析时；该用检索型引擎 | `apply -k` 回上一 tag |
| Tempo | 2.x | 按 `trace_id` 查，支持 OTLP 接收 | 对象存储为主，随采样率与保留期增长 | 没有埋点、拿不到 `trace_id` 时；链路数据无从查起 | `apply -k` 回上一 tag |
| Grafana | 11.x | 统一查询与仪表盘，不存数据 | 近乎固定 | 只想用单一后端自带 UI 时；多做一层但收益有限 | Dashboard 走 Git 回退 |
| 托管可观测 SaaS | — | 免运维、跨集群统一 | 按 ingest 量计费，只给相对比例（见第 18 章归因口径） | 指标/日志必须留在集群内、或判定逻辑要进 Git 门禁时 | 停用 exporter 即止 |

**唯一示例实现**：OTel Collector 0.x → Prometheus 3.x + Loki 3.x + Tempo 2.x，长期指标走 Thanos 0.x；Mimir、Istio、托管 SaaS 仅在矩阵作对比。流量入口 Gateway API 与演练工具 Chaos Mesh 的取值沿用 `decisions.md`（见第 19、23 章）[R-21-2][R-21-4][R-21-5][R-21-6][R-21-7]。

**最小接入 diff**：新增 `observability/` 下 5 个文件与一个 `ServiceMonitor`，不改应用 Deployment 的镜像标签 `git-<sha7>`，不改 `order-demo-config`；只在 Pod 上加 `prometheus.io/*` 注解与 OTLP 环境变量。规则文件沿用第 20 章 `PrometheusRule` 的 `role: alert-rules` 标签由 Operator 自动挂载 [R-21-4]。

**升级 / 回滚路径**：Collector 小版本升级先改镜像 tag 走 PR，用 `verify-signal-chain.sh` 验证三类信号仍可关联；后端升级按 Loki → Tempo → Prometheus → Thanos 顺序，每步停顿一个采集周期观察。整体回滚用 `git checkout <上一 tag> -- observability/` 后 `kubectl -n observability apply -f observability/otel-collector.yaml -f observability/prometheus.yaml -f observability/loki-tempo.yaml`，再由 Argo CD 2.x 收敛（见第 14 章）；采集端应急可只降采样、不回退后端（§21.5）。小版本锁在附录 A，正文只写主版本 [R-21-3]。

> `ruleSelector` 命中第 20 章 `PrometheusRule` 的 `role: alert-rules` 标签，SLI 记录规则与本章抓取自动合流 [R-21-4]。`metricRelabelings` 是 cardinality 第二道闸：即便应用侧误加了 label，抓取时仍会丢弃 [R-21-3]。`enableFeatures: ["exemplar-storage"]` 打开 exemplar，让 `trace_id` 能从指标下钻到链路；`remoteWrite` 把长期指标交给 Thanos [R-21-7]。`prometheus` Service 供第 20 章 `budget-report.sh` 查询。

**`observability/metric-naming.md`——命名规范与 label 白名单（第 15、20、22 章共用）**

```markdown
# order-demo 指标命名规范（唯一口径）

## 一、命名格式
- 前缀 order_demo_，单位后缀用 Prometheus 惯例：_total（Counter）、_seconds（Histogram 桶）、_bucket / _sum / _count。
- 记录规则按 level:metric:operations 命名（见第 20 章），如 sli:order_demo_http_success:ratio_rate5m。

## 二、应用侧指标（由 OTel SDK 导出、Collector 转 Prometheus）
| 指标 | 类型 | 允许 label | 用途 |
|---|---|---|---|
| order_demo_http_requests_total | Counter | service, component, method, route, status_code | SLI 分子/分母（第 20 章） |
| order_demo_http_request_duration_seconds_bucket | Histogram | service, component, method, route, le | p50/p99 延迟、慢链路判定 |
| order_demo_http_requests_in_flight | Gauge | service, component | 饱和度 / 流量（USE） |
| order_demo_db_pool_wait_seconds_bucket | Histogram | service=api, component=api, le | db 连接池排队（第 23 章定位） |

## 三、label 白名单（白名单外一律 drop）
- 允许：service, component, method, route, status_code, le, job, instance。
- 禁止：user_id, order_id, trace_id, span_id, client_ip, pod_ip, session_id, email。
- 理由：前六类取值有界；后八类无界，会把时间序列数放大到 OOM（见 21.1）。
- trace_id 只走 exemplar 与日志字段，不做 metric label。

## 四、日志字段（结构化 JSON，OTel 语义约定）
- 必填：timestamp, level, service.name, trace_id, span_id, message。
- 选填：http.method, http.route, http.status_code, error.type。
- 脱敏：Authorization、password、card_no 在 Collector 的 transform/redact_logs 中替换，禁止明文入库。

## 五、采样口径
- 链路：ERROR 与 latency > 1000ms 全采；其余 probabilistic 10%。
- 日志：5xx 与慢请求全采；2xx 按 10% 采样，由 Collector 的 tail_sampling 同口径决定。
- 演练注入的流量（第 23 章）带 drill=true 标签，单独保留，不进 SLI 分母。
```

> 这张表是 SP-09、SP-15 的落点：第 20 章 SLI 记录规则、第 22 章告警规则、第 23 章 runbook 查询命令，都只能使用本表登记的指标名与 label，不得各起一套 [R-21-3]。

**`hack/verify-signal-chain.sh`——一条请求串起指标、日志、链路（完整可复制）**

```bash
#!/usr/bin/env bash
set -euo pipefail

NS=order-demo-prod
PROM="http://prometheus.observability.svc.cluster.local:9090"
LOKI="http://loki.observability.svc.cluster.local:3100"
TEMPO="http://tempo.observability.svc.cluster.local:3200"

kubectl -n "${NS}" port-forward svc/gateway 8080:8080 >/dev/null 2>&1 &
kubectl -n observability port-forward svc/prometheus 9090:9090 >/dev/null 2>&1 &
kubectl -n observability port-forward svc/loki 3100:3100 >/dev/null 2>&1 &
kubectl -n observability port-forward svc/tempo 3200:3200 >/dev/null 2>&1 &
PF_PIDS=$(jobs -p)
trap 'kill ${PF_PIDS} 2>/dev/null || true' EXIT
sleep 3

TRACE_ID="$(curl -fsS -D - -o /dev/null http://127.0.0.1:8080/orders \
  | awk -F': ' 'tolower($1)=="x-trace-id" {gsub(/\r/,"",$2); print $2}')"
[ -n "${TRACE_ID}" ] || { echo "FAIL: no X-Trace-Id in response header"; exit 1; }
echo "trace_id=${TRACE_ID}"

echo "== 1) 指标：按 trace_id 查 exemplar =="
curl -fsS --data-urlencode \
  'query=order_demo_http_request_duration_seconds_bucket{service="gateway",route="/orders"}' \
  --data-urlencode "start=$(date -u -d '-5 min' +%Y-%m-%dT%H:%M:%SZ)" \
  --data-urlencode "end=$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  "${PROM}/api/v1/query_exemplars" \
  | jq -r --arg t "${TRACE_ID}" '.data[].exemplars[]? | select(.labels.trace_id==$t) | "exemplar trace_id=\(.labels.trace_id) value=\(.value)"'

echo "== 2) 日志：Loki 按 trace_id 捞结构化行 =="
curl -fsS --data-urlencode \
  "query={app=\"order-demo\"} |= \"${TRACE_ID}\"" \
  --data-urlencode "limit=20" \
  "${LOKI}/loki/api/v1/query_range" \
  | jq -r '.data.result[0].values[][1]'

echo "== 3) 链路：Tempo 按 trace_id 取瀑布 =="
curl -fsS "${TEMPO}/api/traces/${TRACE_ID}" \
  | jq -r '.batches[].scopeSpans[].spans[] | "\(.name) duration_ms=\((.endTimeUnixNano|tonumber - .startTimeUnixNano|tonumber)/1000000)"'

echo "PASS: same trace_id resolved in metrics / logs / traces"
```

> 脚本证明的是「同一条请求在三类信号里可关联」：响应头拿到 `trace_id` → Prometheus exemplar 命中 → Loki 日志命中 → Tempo 瀑布命中。三者都非空才算通过，缺一类就说明关联键在某一段断了 [R-21-1][R-21-6]。集群内地址均由 `port-forward` 提供，不依赖外部网络。
