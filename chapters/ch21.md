## 21.1 问题与反模式：三套系统都装了，为什么还是串不起来

**合成案例**。周二 10:12，`order-demo` 下单接口的 p99 从 180ms 涨到 2.4s。值班同学打开三个标签页：Prometheus 里看到 gateway 5xx 抬了一点，Loki 里刷出一堆超时日志，Tempo 里能看到慢调用散落在 `api → db` 之间。三处都有数据，却没有一处能回答「这条具体的失败请求到底走了哪几跳、在哪一跳变慢」。最后靠一个人在三个系统里手工比对时间戳和用户 ID，花了 40 分钟才定位到是 `api` 的一次连接池耗尽——而这段时间里，第 23 章的 runbook 本可以让止血在 5 分钟内完成。

问题不在采集量，而在**关联键缺失**：指标按聚合计数存、日志按行存、链路按 trace 存，三者没有共同的 `trace_id`，就不可能从一条告警下钻到一次请求。OpenTelemetry 的语义约定正是为解决这件事而存在——它规定 `trace_id`、`span_id`、`service.name` 等字段在三类信号里用同一套名字与编码，跨信号关联才有前提 [R-21-1]。

那 40 分钟的浪费很有代表性：**人成了三套系统之间的连接器。**你能看到的每一处都正确——指标没错、日志没错、链路没错——但「把三处对上」这件事没有任何机器在做，只能由一个疲惫的人在三个标签页之间比对时间戳。**这其实是本书反复出现的一个模式：当系统缺少关联键，代价不会消失，只会转移成某个人的手工劳动。**

三个高频反模式：

**反模式一：把 `user_id` / `order_id` 写进指标 label。** 现象是 Prometheus 时间序列数量随订单量线性增长，最终 TSDB 内存被打满、查询超时甚至 OOM。根因是 label 的每一个取值组合都会生成一条独立序列，用户 ID 这类无界维度会把序列数放大到不可控。本章的替代做法是**采集前定 label 白名单**：只保留 `service`、`component`、`method`、`route`、`status_code`、`le` 六个低基数维度，其余一律在 Collector 里丢弃；高基数信息放日志与链路，不放指标 [R-21-3]。

这条有个几乎必然的上当路径：**先在小流量环境验证，一切正常。**测试环境一天几十单，`order_id` 只有几十个取值，序列数看起来完全健康；等上了生产，同样的配置在一小时内爆炸。**它的危险期刚好落在「测试通过」和「生产上线」之间**，而这段时间通常是信心最高的时候。

**反模式二：只采指标不采链路。** 现象是「知道错误率涨了，但不知道是哪一跳」，跨服务问题只能靠猜、靠翻代码。根因是把三大信号当成三份独立报表，而不是一次请求的三个投影。本章要求 `trace_id` 贯通：应用把 `trace_id` 写进结构化日志、随响应头返回、并作为指标 exemplar 的关联键，于是「指标异常 → exemplar 取到 trace_id → 日志/链路按 id 捞」成为一条可脚本化的路径 [R-21-1][R-21-6]。

**反模式三：全量日志不采样。** 现象是存储与检索成本随流量上涨，查一次日志要等十几秒，真正有用的错误日志被淹没在 200 成功日志里。根因是把「可观测」误解为「全留」。本章用**尾部采样**：错误链路、慢链路 100% 保留，正常链路按比例采样；日志侧错误与慢请求全采、正常请求按比例采样，成本只随有效信号增长，不随总流量线性增长 [R-21-5][R-21-2]。

「全留」这个决定的代价曲线很特别：**它在决定时看起来免费，在半年后变成一笔没人心甘情愿砍的支出。**因为那时已经有人在依赖它查过问题，删任何一类日志都要先说服一批人。所以采样策略要在第一天定，那时的争论成本最低——**这也是一种「前置决策」：越晚做，做它的成本越高。**

> 三者的共同教训：**采集不是越多越好，关联才是**。第 20 章定义的 SLI 依赖 `order_demo_http_requests_total`，本章负责把它采出来、命名好、并与日志链路串上；命名一旦与第 15、20、22 章不一致，四章示例会同时失效。

### 21.1.1　现场复盘：cardinality 爆炸导致 Prometheus OOM（合成案例）

反模式一值得给一次完整的现场：它发生时最先坏掉的不是业务，而是监控本身，值班容易把「观测后端挂了」当成另一个独立故障，从而错过真正的窗口。

**翻车现场**。合成案例。周三 09:40，`order-demo-prod` 上线一个小需求：下单接口增加按店铺维度的统计。开发给 `order_demo_http_requests_total` 加了一个 `shop_id` label，理由是「报表要按店铺拆」。该维度取值无界，而上线前 `promtool check metrics` 只校验命名规范、不校验基数；本章的两道闸当时都是按「已知禁用维度」维护的，`shop_id` 不在名单里，畅通无阻地写进了 TSDB。

**加这行 label 时的对话**（合成案例，直接引语）：

> **开发**：报表要按店铺拆，我在指标上挂个 `shop_id` 就完事了。
> **SRE**：label 会乘进序列数，店铺有多少个？
> **开发**：现在是两百多个，但测试环境只有三个，跑了一周完全正常。
> **SRE**：两百多不算多吧。行，先上。
> （一小时后）**值班**：Prometheus 一直在 OOM。

这段对话里最该被记住的是「**测试环境只有三个，跑了一周完全正常**」——它不是敷衍，是一份真实的观察结果，而且逻辑上没有瑕疵：小基数下这个改动确实无害。问题在于**指标的序列数是乘出来的**：两百多个店铺 × 六个方法 × 十几个路由 × 若干状态码，很快就不是「两百多」，而是「几十万」。**在基数问题上，测试环境的验证结论几乎总是乐观的，因为它缺的恰好是被乘的那个维度。**

时间线：09:40 新版本 `git-<sha7>` 发布，抓取间隔 15s；10:05 head 序列数从基线约 6 万爬到 25 万；10:35 `prometheus-order-demo-0` 内存触及 limits `memory: 1Gi`，容器 `OOMKilled`；10:35–11:10 进入重启循环——head WAL 回放本身要吃几分钟内存与 CPU，回放未完成又被 OOM 杀掉；另一副本抓取同一批序列，同步恶化。期间第 20 章 SLI 记录规则断样本、`budget-report.sh` 查询超时，值班看到的第一现象是「监控自己挂了」。

**定位过程**（每步带判读标准）：

1. 先确认死因，不要先重启：
```bash
kubectl -n observability get pod prometheus-order-demo-0 \
  -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\n"}'
# 通过标准：输出 OOMKilled，而非 CrashLoopBackOff 的其他根因
```

2. 趁容器存活间隙（或查仍在存活的另一副本），读 TSDB 自报的序列构成：
```bash
curl -fsS http://prometheus.observability.svc.cluster.local:9090/api/v1/status/tsdb \
  | jq '{headSeries: .data.headStats.numSeries,
         topSeries: .data.seriesCountByMetricName[:5],
         topLabelValues: .data.labelValueCountByLabelName[:5]}'
```
判读：`headSeries` 相对基线翻倍以上即异常；`topLabelValues` 出现 `shop_id` 且取值数在十万量级，即元凶。
3. 交叉验证基数归属（只数 label 取值数，不拉全量样本）：
```bash
curl -fsS --data-urlencode \
  'query=count(count by (shop_id) (order_demo_http_requests_total))' \
  http://prometheus.observability.svc.cluster.local:9090/api/v1/query \
  | jq -r '.data.result[0].value[1]'
# 通过标准：返回值即 shop_id 当前取值数；按 21.4 白名单该维度本不应存在，正常为 0
```
4. 归因到代码：`git log -p --since="3 hours ago" -- order-demo/ | grep -n shop_id`，把引入 label 的提交、tag 与序列数爬升起点对齐，确认因果。

**应急处置**（顺序不可颠倒，对应 CL-21-02 失败处置：禁止先扩容 Prometheus 硬扛）：

- 第一刀在抓取端，先断供给：给两个 ServiceMonitor 追加一条 `metricRelabelings`，在抓取时丢弃该维度——`- regex: "shop_id"` + `action: labeldrop`，随后 `kubectl -n observability apply -f observability/prometheus.yaml`。注意：这一刀只让序列**不再增长**，head 里的旧序列要等 TSDB 出块压缩（默认 2 小时）后才释放内存，内存回落以小时计，不要用「看起来没降」否定这一刀。
- 第二刀回到 Git：`git checkout ch20-slo -- order-demo/` 把引入 `shop_id` 的版本退回上一 tag（公理 5、公理 6），由 Argo CD 3.x 收敛（见第 14 章）。
- 第三刀补策略：把 `shop_id` 写进 `metric-naming.md` 禁用清单与 Collector 的 `transform/drop_high_cardinality`，让「白名单外一律 drop」从按名单拒绝升级为按策略拒绝——新维度不再需要等人登记才会被拦 [R-21-2]。

**验证与复盘**：`/api/v1/status/tsdb` 的 `headSeries` 回落到基线 ±20% 内；`verify-signal-chain.sh` 重新 PASS。按店铺拆分的报表需求改走「日志字段 + 记录规则」：店铺维度进 Loki 结构化字段与仪表盘下钻变量（§21.2.1），指标侧只保留 top N 店铺的预聚合记录规则 [R-21-4]。复盘制度化动作两条：CI 把「新指标必须先登记 `metric-naming.md`」作为合并门禁（见第 11 章）；对 `prometheus_tsdb_head_series` 增设基线 1.5 倍的告警阈值，让下一次爬坡在 10 分钟内被看见，而不是等 OOM [R-21-3]。

## 21.2 范式与决策树：统一采集层 + 三类信号各归其位

本章要回答的决策问题是：**指标、日志、链路该怎么采集、存储与关联，才能既查得动又不被 cardinality 拖垮**。

这个问题的两半互相牵制：**想查得动，就要多留字段；不想被拖垮，就要少留字段。**而工程上唯一可行的解法不是找平衡点，是**分层**——把「贵而少」放指标、把「全而贱」放日志与链路，再用一个 ID 把三者缝起来。所以本章的主线不是三选一，是「**先决定每类信息住哪层，再决定怎么连**」。

**采集拓扑**（唯一示例实现取 本书选型基线）：应用侧 OTel SDK 通过 OTLP 把三类信号发给 **OTel Collector 0.x**；Collector 作为统一采集层做过滤、脱敏、采样与分流，再分别导出到 Prometheus 3.x（指标）、Loki 3.x（日志）、Tempo 3.x（链路）；长期指标由 Thanos 0.x 或兼容远端存储承接 [R-21-2][R-21-7]。请求入口沿用第 19 章的 Gateway API 固定值：`GatewayClass: eg`、`Gateway` 名 `order-demo-gw`、`HTTPRoute` 名 `gateway-route`，流量经它到 `gateway` Service 8080，再由 `api` 8081、`db` 5432 承载（见第 19 章、见第 6 章）。

| 信号 | 采集点 | 落地后端 | 关联键 | 回答的问题 |
|---|---|---|---|---|
| 指标 Metrics | Collector `otlp` → `prometheus` exporter :8889 | Prometheus 3.x / Thanos 0.x | `service` + `route` + exemplar `trace_id` | 有多少、多快、错多少（第 20 章 SLI 的数据源） |
| 日志 Logs | 应用 stdout 结构化 JSON → Collector `loki` exporter | Loki 3.x | `trace_id` + `span_id` | 这一次的上下文、报错栈、入参摘要 |
| 链路 Traces | 应用 OTel SDK → Collector `tail_sampling` → `otlp` exporter | Tempo 3.x | `trace_id` | 走了哪几跳、时间花在哪一跳 |

**四大黄金信号**（延迟、流量、错误、饱和度）是组织监控的**用户视角** [R-21-8]；**RED**（Rate / Errors / Duration）是面向请求型服务的精简版 [R-21-9]，**USE**（Utilization / Saturation / Errors）是面向资源的检查法 [R-21-10]。三者不是互相替代的清单：黄金信号告诉你「该看哪四类」，RED 把服务侧指标收敛成三列，USE 提醒你别漏掉「资源明明没满但队列已排长」这种饱和度问题。对 `order-demo`：`gateway`/`api` 用 RED，`db` 与节点用 USE，整体大盘按黄金信号分栏 [R-21-8][R-21-9][R-21-10]。

**排障路径判据表**（决定先打开哪个系统）：

| 现象 | 先查 | 判定 | 下钻到 |
|---|---|---|---|
| 「整体是不是坏了」 | Prometheus 黄金信号大盘 | SLI 是否跌破第 20 章窗口阈值 | 触发第 22 章告警 |
| 「哪一类请求坏了」 | 按 `route` / `status_code` 聚合 | 定位到具体接口与错误码 | exemplar 取 `trace_id` |
| 「这一跳为什么慢」 | Tempo 按 `trace_id` 看瀑布图 | 找到耗时最长的 span | 该服务的日志上下文 |
| 「资源还是代码问题」 | USE：饱和度 / 队列 / 错误 | 饱和度异常 → 第 17、18 章；否则看日志栈 | 第 23 章 runbook |

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：仪表盘必须分层——服务总览 → 组件下钻 → 排障视图；把全部图表堆在一页，会让值班在真正需要定位时更慢。
>
> **论证**：总览页的职责只有一个，就是回答「现在整体好不好、坏在哪一类」，因此它应当只有少量能一眼判读的图；下钻页按组件聚合 RED/USE，排障页才放高基数的分位数、exemplar 与日志跳转。三层各自的读者与动作不同：总览给值班、下钻给 owner、排障给正在救火的人。把所有图塞进一页，等于让值班每次告警都要在一屏里重新做一次信息筛选，告警越紧急，筛选越慢。
>
> **反例与适用前提**：这三层不是三个必须独立的系统，一个 Grafana 11.x 里用变量与链接跳转即可实现；对只有一个服务、三个人值班的小团队，总览与下钻可以合并成一页，但「排障视图与总览分离」不能省——第 23 章 runbook 的定位耗时，很大一部分就来自在总览页里翻找单条 trace。若团队已有成熟的服务目录与自动下钻（按 `service.name` 自动跳转），分层可由工具代劳，但仍须保证总览页不承载高基数明细。

### 21.2.1　三层仪表盘的结构、变量与跳转定义

本节用「结构表 + panel 清单 + 变量定义」把三个仪表盘定义到可落地的程度：Dashboard 以 JSON 放 `observability/dashboards/`，经 ConfigMap 挂进 Grafana 11.x，与代码同走 Git（公理 5），导入即可复现 [R-21-8]。

变量定义（三个仪表盘共用，级联过滤）：

| 变量 | 定义 | 类型 | 说明 |
|---|---|---|---|
| `$env` | `label_values(order_demo_http_requests_total, namespace)` | Query | 取值即 `order-demo-prod` 等，联动第 4 章三环境 |
| `$service` | `label_values(order_demo_http_requests_total{namespace=~"$env"}, service)` | Query | 级联于 `$env` |
| `$route` | `label_values(order_demo_http_requests_total{service=~"$service"}, route)` | Query | 级联于 `$service` |
| `$trace_id` | 无默认值 | Textbox | 排障页人工粘贴，来自告警或响应头 |

| 层 | Dashboard（uid） | Panel 清单 | 明细上限 |

### 21.2.2　三类信号的写入侧分工：一条信息该放进哪类信号

§21.2 的判据表回答的是「查询时先打开哪个系统」；本节补另一半：**新需求出现时，这条信息在采集侧该放进哪类信号**。这是比查询路径更靠前的决策，放错了事后再怎么调仪表盘都救不回来——§21.1.1 的 `shop_id` 事故就是「该进日志与报表的信息被塞进了指标」的完整现场。

判定用五个维度，每个维度三类信号的答案都不同：

| 维度 | 指标 | 日志 | 链路 |
|---|---|---|---|
| 承载的信息形态 | 预聚合的数值：多少、多快、错多少 | 单次事件的完整上下文：栈、入参摘要 | 一次请求的跨跳路径与耗时分解 |
| 维度基数要求 | 每个维度必须有界（§21.1） | 无所谓，字段随意加 | 属性可带高基数，但只随采样量留存 |
| 回答问题的方式 | 算术聚合：sum / rate / 分位数 | 按 label 检索 + 全文过滤 | 按 `trace_id` 精确取瀑布 |
| 查询成本与延迟 | 毫秒级，数小时窗口随手查 | 秒到十几秒，窗口越大越慢 | 按 id 毫秒级；不带 id 扫描则又贵又慢 |
| 成本随什么增长 | 序列数（基数），与流量无关 | 总行数 × 保留期（§21.3.1） | span 数 × 采样率 × 保留期（§21.3.1） |

**写入侧决策表**（新需求来了先过这张表，再动手埋点）：

| 需求表述 | 放哪 | 为什么不放别处 |
|---|---|---|
| 「下单接口每分钟多少次、5xx 多少」 | 指标 Counter（`order_demo_http_requests_total`） | 要反复算趋势，必须便宜且可聚合；日志正常请求已按 10% 采样，日志侧 rate 出来的是采样后口径，不能当真相源 |
| 「下单 p99 多少、SLO 超没超」 | 指标 Histogram（`..._request_duration_seconds_bucket`） | 分位数要跨副本聚合，只有 Histogram 做得到，Summary 不行（§21.4.2） |
| 「这次请求为什么 500」 | 日志（错误栈、入参摘要）+ 链路（哪一跳慢） | 单次事件的上下文进指标，就等于把 §21.1.1 的 cardinality 事故再演一遍 |
| 「这个用户/订单最近做了什么」 | 日志结构化字段，用 `trace_id` 关联 | 无界维度禁入指标；链路 span 属性只放请求处理内的技术事实，不当业务档案 |
| 「db 连接池排队多严重」 | 指标 Histogram（`order_demo_db_pool_wait_seconds_bucket`）+ USE 判读 | 资源饱和度要连续趋势与告警阈值；第 17 章 OOMKilled 定位同样先看指标再开日志 |
| 「worker 的超时关单队列积压了吗」 | 指标 Gauge（队列长度）+ 链路（消费 span） | worker 无请求视角，RED 不适用；用 USE 的队列/饱和度列（§21.2） |

两条反模式收尾：

- **用日志画趋势图**。LogQL 确实能对行计数算 rate，但每张图都是一次实时扫描，比查预聚合指标贵一个数量级，大盘刷新几秒一次时最先压垮的是 Loki；更要命的是口径——本章日志正常请求按 10% 采样（§21.4、`metric-naming.md` 五），日志侧算出的「请求率」是采样后比例，与第 20 章 SLI 对不上。**趋势与告警只认指标**，日志图只放排障页当单次佐证 [R-21-5]。
- **把 span 属性当业务明细库**。给每个 span 塞 `order.item_count`、`user.tier` 之类的业务字段，看起来「顺手多记一点」，实际是让 Tempo 从「技术事实存储」膨胀成「业务数据副本」，存储按 span 数 × 属性大小双重放大（§21.3.1 公式）；且这些属性同样要过脱敏审查（`CL-S-03`），业务字段里的手机号、地址是高频泄漏点。span 属性只放排障必需的技术事实 [R-21-6]。

> **本书观点（本章第 5 条结论，不需要外部背书）**
>
> **主张**：任一事实只设一类信号作为唯一真相源，其余信号只携带关联键（`trace_id`/`span_id`），不复制数值。
>
> **论证**：同一数值进两类信号，两处口径必然漂移——采样率、保留期、聚合窗口都不同，排障时拿到两个对不上的答案比没有答案更糟，且没人能裁决哪个是真的。第 20 章 SLI 只认 `order_demo_http_requests_total`，日志与链路里的请求信息只作现场还原、不参与任何比率计算，正是这一主张的落地；§21.1 开篇的合成案例里「三个标签页三个数字对不上」，本质就是真相源不唯一。
>
> **反例与适用前提**：例外是纯关联键的复制——exemplar 携带的 `trace_id` 来自与日志同一个请求上下文，这类复制不构成真相源冲突，反而是跨信号下钻的前提（§21.4.1）。若团队已有统一遥测中台把三类信号从同一事件流派生，真相源可上移到事件层，但三类信号内部仍须各留一个明确的聚合口径 owner，否则只是把漂移从中台前移到了仪表盘。

| 工具 | 主版本 | 保留期 / 查询能力 | 成本归因 | 何时不该用 | 回滚方式 |

**唯一示例实现**：OTel Collector 0.x → Prometheus 3.x + Loki 3.x + Tempo 3.x，长期指标走 Thanos 0.x；Mimir、Istio、托管 SaaS 仅在矩阵作对比。流量入口 Gateway API 与演练工具 Chaos Mesh 的取值沿用本书选型基线（见第 19、23 章）[R-21-2][R-21-4][R-21-5][R-21-6][R-21-7]。

### 21.3.1　Loki / Tempo 保留期与采样率的成本测算（联动第 18 章）

第 18 章立了成本讨论的两条规矩：**先归因、再优化**，与**只给相对比例、不写任何云厂商单价**（按 `app.kubernetes.io/component` 与环境拆相对占比，`cost-report.sh` 输出归因报表）。可观测后端的三类存储是最容易被总账单掩盖的成本项，本节把选型矩阵里的「成本归因」列展开成可测算的公式与决策表。

三条近似公式（只看倍数关系，系数取 1 即可比出放大倍数）：

| 信号 | 存储量 ∝ | 本章参数 | 每个旋钮的杠杆 |
|---|---|---|---|
| 日志（Loki） | 平均行大小 × 行/s × **采样率** × **保留期** | 30d，正常请求 10% 采样 | 保留期翻倍即成本翻倍；采样率 10%→100% 放大 10 倍 |
| 链路（Tempo） | 平均 span 大小 × span/s × **采样率** × **保留期** | 72h，基线 10% | 保留期杠杆最大（72h→7d 放大 2.3 倍）；采样率同上 |
| 指标（Prometheus / Thanos） | 序列数 × 采样频率 × **保留期** | 本地 15d + Thanos 长期 | 与采样率无关，只随基数与保留期增长（§21.1.1） |

**合成测算**。生产按 120 行日志/s、400 span/s 估（合成假设；真实值用 `loki_distributor_bytes_received_total` 与 `tempo_distributor_spans_received_total` 的 5 分钟增量除以 300 换算）：日志未采样 30 天约是「10% 采样」的 10 倍量级，而错误与慢请求全采的部分通常只占 1%–2% 流量——**全采的保障几乎不花钱**，这是 §21.1 反模式三「按有效信号计成本」的量化版 [R-21-5]。链路同理：10% 基线把 Tempo 存储压到全采的约 1/10，错误/慢链路 100% 保留意味着排障能力不随采样打折，打折的只是「正常链路也能随手翻」这个低频需求 [R-21-6]。建议口径：三类信号存储合计占集群存储的相对比例控制在个位数百分比量级，超了先砍保留期、再砍采样率，进第 18 章归因报表。

**调参决策表**（每次只动一个旋钮，与第 18 章「一层只动一个参数」同源）：

| 症状 | 先动 | 动作 | 不动什么 |
|---|---|---|---|
| 存储/检索成本高、但要保留长回溯 | 采样率 | 正常链路基线 10%→5% 或 1%（改 Collector `tail_sampling`，走 Git PR） | 错误/慢链路全采不动，第 23 章 runbook 能力不变 |
| 排障经常要回看数天前 | 保留期 | Loki `retention_period` 30d→60d、Tempo `block_retention` 72h→7d | 采样率不动；保留期是线性成本，先算倍数再批 |
| 成本尖峰突发 | 归因 | 第 18 章 `cost-report.sh` + 本章 distributor 指标定位是哪类信号、哪个命名空间 | 先归因再调参，不做「全栈降配」 |

突发尖峰的归因是本节与第 18 章的联动点：故障期错误率抬升会让「错误全采」的日志与链路临时放大，这部分增长应归因为「故障处置成本」，在第 18 章的相对占比报表里单独成列，不与常态成本混算——否则故障复盘时容易把采样策略误判成常态超支。

保留期变更走 Git 并验证（公理 5、公理 6）：

```bash

kubectl -n observability apply -f observability/loki-tempo.yaml
kubectl -n observability rollout status deploy/loki --timeout=120s
# 验证 1：生效中的保留期
curl -fsS http://loki.observability.svc.cluster.local:3100/config | grep -A1 retention_period
# 验证 2：改前后对比日增量（相对比例，不换算单价）
curl -fsS -G http://prometheus.observability.svc.cluster.local:9090/api/v1/query \
  --data-urlencode 'query=sum(rate(loki_distributor_bytes_received_total[5m]))' \
  | jq -r '.data.result[0].value[1]'
```

通过标准：改动后 distributor 日增量与预期倍数一致；`verify-signal-chain.sh` 仍 PASS（保留期调整不允许破坏三类关联）。回滚：`git checkout ch20-slo -- observability/loki-tempo.yaml` 后重新 apply，由 Argo CD 3.x 收敛（见第 14 章）。

### 21.3.2　分环境观测口径：dev/staging 各采多少、留多久

§21.3.1 的旋钮在三个环境（见第 4 章）不应拧到同一档位。观测栈是「环境差异只体现在配置，不体现在产物」（公理 3）的观测侧实例：三类信号的采集与存储配置按环境用 Kustomize 5.x overlay 覆写，Collector 镜像与 pipeline 结构三环境完全一致，差异只落在采样率、保留期与「是否接 Thanos」三个旋钮上——Collector 已按 `deployment.environment` resource 属性区分来源（§21.4），环境判定不依赖另起一套配置。

| 旋钮 | dev | staging | prod |
|---|---|---|---|
| 链路采样 | 100% 全采 | 100% 全采 | ERROR/慢链路全采，其余 10%（§21.4） |
| 日志采样 | 全采 | WARN+ 全采，INFO 10% | WARN+ 全采，INFO 10%（§21.4） |
| Loki 保留 | 7d | 14d | 30d（§21.3.1） |
| Tempo 保留 | 48h | 72h | 72h（§21.3.1） |
| Thanos / 长期指标 | 不接 | 不接 | 接（`remoteWrite`，§21.4） |

判据写清楚，避免逐条争论：

- **dev 全采的理由是复现价值，不是流量小**。dev 的流量是演练与复现流量，每一条 trace 都对应一个「有人正在调的问题」；采样省下的存储趋近于零，丢掉的现场却条条有价。反过来，dev 也不需要长保留——问题当天就解决或复现，留 7 天只为对齐一周的开发节奏。
- **staging 链路必须全采**：第 23 章故障演练、第 15 章金丝雀验证都在 staging 执行，注入的故障 span 若被采样丢弃，演练结论就是「看起来成功」，护栏验证整体失真。staging 是唯一一个「链路完整性 > 成本」的环境。
- **Thanos 只接 prod**：长期趋势与跨月对比只在生产有意义，dev/staging 各养一套对象存储 + compactor 是纯增成本，省下的这部分在第 18 章归因报表里单列，作为「观测成本随环境收敛」的正面证据。

反例两条：三环境共用 prod 的 10% 采样参数（staging 演练失真，见上）；或图省事把 dev/staging 的保留期也拉到 30 天（三套环境的存储成本同倍增长，而 dev 的第 8 天数据几乎无人查询）。本书口径：**采样与保留按「环境里数据被查的频率」定，不按「集群规模」定**。

落地方式与回滚：参数覆写走 `overlays/<env>/observability-patch.yaml`（与第 4 章 overlay 骨架同层），改动走 Git 并由 Argo CD 3.x 收敛；验证用 `loki_distributor_bytes_received_total` 换算的日增量对照上表倍数（方法见 §21.3.1），回滚即 `git checkout` 回上一 overlay tag（公理 5、公理 6）。

### 21.4.1　OTel 语义约定与 Prometheus 命名互转、exemplar 存储参数调优

**命名互转规则**。OTel 语义约定的指标名是点分格式并显式带单位（如 `http.server.request.duration`，单位 `s`），Collector 的 `prometheus` exporter 写出 :8889 时做一次机械转换 [R-21-1][R-21-2]。转换只有三条规则，记住就能心算出同一个名字在两端的写法：

| OTel 侧名称 | 类型 / 单位 | Prometheus 侧名称 | 规则 |
|---|---|---|---|
| `order.demo.http.requests` | Sum（单调） | `order_demo_http_requests_total` | 点号 → 下划线；单调 Sum 追加 `_total` |
| `http.server.request.duration` | Histogram，单位 `s` | `http_server_request_duration_seconds_bucket` | 点号 → 下划线；`s` → `_seconds`；Histogram 展开为 `_bucket/_sum/_count` |
| `http.server.active_requests` | UpDownCounter | `http_server_active_requests` | 非单调 Gauge 类不追加 `_total` |
| `db.client.connection.wait_time` | Histogram，单位 `s` | `db_client_connection_wait_seconds_bucket` | 同第二行 |

两条本书决策：

- **order-demo 的应用指标在 SDK 侧直接按 Prometheus 惯例命名**（`order_demo_*`），即源码里就写 `order_demo_http_requests_total`，把上表互转规则留给 OTel 标准语义指标。理由：第 15、20、22、23 章必须逐字引用同一指标名，中间隔一层翻译规则会显著提高漂移概率；`_total`、`_seconds_bucket` 后缀要求以 Prometheus 官方实践为准 [R-21-3]。
- **OTel 语义约定的 `service.name`、`http.route` 等作为 label 来源**，映射进 §21.4 白名单的 `service`、`route`。`resource_to_telemetry_conversion.enabled: true` 会把 resource 属性整体升为 metric label，这是有基数风险的开关，本章只允许 `deployment.environment`、`service.namespace` 两个取值有界的属性留在 resource 里，其余一律不开 [R-21-2]。

记录规则侧沿用 `level:metric:operations` 命名（`sli:order_demo_http_success:ratio_rate5m`），聚合的输入指标名与上表输出名逐字一致 [R-21-4]。

**exemplar 存储参数调优**。`trace_id` 从指标跳到链路，靠三个环节同时打开：Collector `prometheus` exporter 的 `enable_open_metrics: true` 让 exemplar 随样本以 OpenMetrics 注释写出 [R-21-2]；Prometheus `enableFeatures: ["exemplar-storage"]` 打开内存环形缓冲；Grafana 数据源把 `trace_id` 指向 Tempo（§21.2.1）。链条上唯一需要**调参**的是缓冲区：

- 参数在配置文件为 `storage.exemplars.max_exemplars`（裸二进制对应 flag `--storage.exemplars.exemplars-limit`），默认 **100000**，支持运行时调整；Operator 部署经 `enableFeatures` 打开后即取默认值。
- 容量要按「序列数 × 抓取频率」测算而不是拍脑袋：本章登记的两个 Histogram 在 gateway + api 合计约 250 条 `_bucket` 序列，15s 抓取意味着每分钟新增约 1000 个 exemplar，默认缓冲只覆盖约 100 分钟。第 22 章告警的判定窗口加值班响应时长常常超过 1 小时，超窗的历史 exemplar 已被环形覆盖，「按图索骥」会失败。
- 本书观点：缓冲区下限 = 想覆盖的下钻窗口 × 每分钟 exemplar 速率；按「告警 for 窗口 + 30 分钟调查期」估算，本章规模设 `max_exemplars: 500000` 覆盖约 8 小时，内存增量在几十 MiB 量级，代价可忽略。适用前提：只把指标侧 exemplar 当「下钻入口」，长期回溯交给 Tempo 按 `trace_id` 持有；想把窗口拉到数天的正确做法是延长 Tempo 侧能力（§21.3.1），而不是无限加大 exemplar 缓冲。

### 21.4.2　Prometheus 指标类型完整讲解：四类类型、bucket 选择与 rate/increase

§21.4.1 解决了「名字怎么写」，本节解决「类型怎么选、桶怎么定、查询函数怎么用」——这三件事决定指标采出来之后能不能回答问题，类型选错是最常见的埋点返工原因，且返工要连动第 15、20、22 章的引用口径。

四类指标类型一览（对齐 `metric-naming.md` 已登记指标）[R-21-3]：

| 类型 | 语义 | order-demo 对应 | 适用 | 陷阱 |
|---|---|---|---|---|
| Counter | 只增不减的单调累计值，进程重启归零重计 | `order_demo_http_requests_total` | 请求数、错误数、任务数 | 原始值画图毫无意义，必须经 `rate`/`increase`；重启造成 reset 断崖，查询函数必须能吃掉 reset（`rate`/`increase` 会自动处理，手工相减不会） |
| Gauge | 可升可降的即时值 | `order_demo_http_requests_in_flight` | 队列长度、连接数、内存 | 不能用 `rate`；看趋势用 `avg_over_time`，看峰值用 `max_over_time`，看「是否长期贴顶」用 `max_over_time` 比 `avg` 更能暴露饱和 |
| Histogram | 客户端分桶计数 + `_sum`/`_count` | `..._request_duration_seconds_bucket`、`order_demo_db_pool_wait_seconds_bucket` | 延迟、大小的分布与分位数 | 桶边界决定你能回答什么问题（下文）；序列数 =（桶数 + 3）× label 组合，是 cardinality 的隐藏大头（§21.1） |
| Summary | 客户端预计算的分位数 + `_sum`/`_count` | 未采用 | 单实例、绝不跨副本聚合的分位数 | 分位数在客户端算好、无法跨实例聚合，多副本场景必然算错（下文） |

**Summary 在本章场景必然出错**：`api` 是多副本 Deployment（见第 8 章），若用 Summary 输出 p99，仪表盘上 `avg(..._p99)` 得到的是「各副本 99 分位的平均」——慢请求集中在某一副本时，真实整体 p99 可能是它的数倍，而且没有任何查询能从 Summary 的预计算值里恢复出真实分位。这就是 `metric-naming.md` 只登记 Histogram 不登记 Summary 的原因；Summary 仅适用于「单实例进程内自用、绝不跨副本聚合」的场合，一旦组件可能扩到多副本就换 Histogram [R-21-3]。

**Histogram bucket 怎么选**（本书决策，适用于本章登记的两个 Histogram）：

- 规则一：**SLO 阈值必须是一个桶边界**。第 20 章 gateway 的延迟目标线、`tail_sampling` 的 slow-always 阈值 1000ms（§21.4）、桶边界里的 `1`，三处对齐后「p99 是否超标」与「慢链路是否保留」用的才是同一条分界线；若桶是 0.8 与 1.6 而目标是 1s，SLO 判定只能落在插值上，误差随分布漂移且不可审计。
- 规则二：**分位数读数精度由桶密度决定**。`histogram_quantile` 只能对落在桶内的分位数做线性插值：p99 落在 [1, 2.5] 桶内时，插值对真实分布形状一无所知。业务关键区间（本章为 100ms–1s）桶要密，尾部（>5s）可以疏——反正到那里已经是事故，读数精度不再重要。
- 规则三：**先算序列数再定桶数**。每个 Histogram 产生（桶数 + 3）条序列（每桶一条 `_bucket` + `_sum` + `_count`），乘以 label 组合数才是真实账。本章 duration Histogram 取 11 个桶：`0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10`，覆盖 5ms–10s 且 1s 是边界；db 池等待取 8 个桶：`0.001, 0.005, 0.01, 0.05, 0.1, 0.5, 1, 5`——正常排队在 10ms 以内，这一段必须密，否则「池子要不要扩」根本没有判据（见第 17 章）。
- 反例：照抄客户端库默认桶（往往从 2.5ms 均匀铺到 10s、30+ 桶）而不裁剪，序列数直接翻倍，其中一半桶在正常运行时永远没有样本——桶不在多，在对齐问题。

**rate / increase / irate 判定表**（本书经验口径；PromQL 语义以官方查询文档为准，本章无对应登记条目，故不挂角标）：

| 你要回答的问题 | 用什么 | 窗口 | 为什么 |
|---|---|---|---|
| 当前请求速率、SLI 成功率（第 20 章） | `rate(...[5m])` | ≥ 4 个抓取周期（15s 抓取 → 至少 1m，取 5m 求稳） | 平均速率对 reset 鲁棒，是比率分母最稳的选择 |
| 「过去 1 小时一共错了多少次」 | `increase(...[1h])` | 覆盖问题窗口 | 返回窗口内的估计增量，长窗口下外推误差可忽略 |
| 告警里的瞬时尖峰 | `irate(...[1m])` | 短窗口 | 只看最后两个样本，反应最快但抖动大，适合「突发」类告警，不适合画趋势与 SLI |
| 短窗口小流量计数 | 避免 `increase[1m]` | — | Prometheus 会把窗口两端外推，15s 抓取下 1m 只有 4 个样本，低流量时误差可能放大数倍；改用 `rate` × 秒数或拉长窗口 |

与既有内容的衔接：第 20 章记录规则 `sli:order_demo_http_success:ratio_rate5m` 就是上表第一行的实物 [R-21-4]；第 15 章金丝雀的指标判定同样吃这张表——金丝雀分析窗口若短于 4 个抓取周期，`rate` 会因样本不足而抖动，把正常流量误判成异常（反之亦然），「5% 流量观察 10 分钟」这类窗口设计里有一半是给抓取周期留的。

**三个查询函数的典型误用**（多副本场景下都会静默算错，不出任何报错）：

| 误用 | 为什么错 | 正确写法 |
|---|---|---|
| `avg(rate(..._total[5m])) by (service)` | 多副本时把「每个实例各自的速率」平均，半数副本没流量会被稀释掉一半，SLI 分母偏大 | 先 `sum(rate(...)) by (service)` 聚合再参与比率 |
| `histogram_quantile(0.99, rate(..._bucket[5m]))` 不带聚合 | 对每个实例的桶各自算分位线再拼结果，多副本下不是整体 p99 | `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))` |
| `rate(order_demo_http_requests_in_flight[5m])` | Gauge 不是单调计数器，rate 出来的是「在途数的平均变化率」，语义无用 | 看水位 `avg_over_time`，看饱和 `max_over_time` |

这三个误用共有的根因是**把「逐实例计算」与「先聚合再计算」搞混**：涉及比率、分位数的表达式，聚合（`sum by`）必须在函数（`rate` 之后、`histogram_quantile` 之前）的正确层级完成。第 20 章记录规则之所以写成两条中间规则再合成 SLI，就是为了让聚合层级显式化、可审计 [R-21-4]。

### 21.4.3　Collector pipeline 机制：三段顺序、背压与采样的真实代价

§21.4 给出的 `otel-collector.yaml` 能跑通，但三段流水线**为什么这样排**、下游变慢时会发生什么、`tail_sampling` 与日志采样实际花多少内存，决定你敢不敢在生产上改它——也决定故障时「观测先于业务挂掉」会不会发生在你身上。

**三段执行模型与顺序铁律**。一条 pipeline 是 receiver → processors（严格按声明顺序）→ exporter 的单向流；三条 pipelines 相互独立，但共享同一个 Collector 进程的内存，指标侧 cardinality 失控会直接挤压链路采样缓存。processor 顺序有两条铁律 [R-21-2]：

1. `memory_limiter` 必须放第一个。它靠周期性拒绝新数据自保；排在 transform 之后等于让脱敏与基数清洗先吃满内存再被限流，限流丢掉的恰好是已经处理过的高价值数据，纯浪费 CPU。
2. `batch` 必须放最后一个。它的职责是把前面处理完的数据攒批发送；放在中间只会让后续 processor 在批间空转，并把整条 pipeline 的处理延迟放大一个批周期（本章为 5s）。

**背压链条与 sending_queue**。下游变慢（Tempo 卡顿、Loki 限流）时的真实行为链：exporter 发送阻塞 → 无缓冲则失败重试或丢数据、有 `sending_queue` 则先入队 → 队列打满后 batch 阻塞 → memory_limiter 拒收新数据 → receiver 返回 UNAVAILABLE → 应用侧 OTel SDK 重试 → **应用进程内存堆积**。观测层的过载会一路传导成应用层的内存压力，这就是为什么 §21.4 在 `otlp/tempo` 导出端补了 `sending_queue: 5000` 与 `retry_on_failure`（指数退避 5s→30s，最长重试 5m 后放弃）：queue_size 按「下游恢复时间内单副本的上游吞吐」估——本章单副本约 200 span/s，5000 条约等于下游中断 25s 的缓冲。调大缓冲换的是「短暂抖动不丢数据」，代价是 Collector 内存与宕机时的丢失窗口同时变大，不能无脑上调。logs/errors 管道不带队列缓存同样成立（Loki 接收端限流时保 WARN 以上日志优先送达，靠的是两条管道独立重试）。

**采样的真实代价与分层口径**。三类信号的「全采 / 按比例采」最终落在这几个组件的参数上：

| 信号 / 内容 | 策略 | 落在哪 | 内存/成本代价 |
|---|---|---|---|
| 链路：ERROR、> 1s | 100% | `tail_sampling` 的 errors-always / slow-always | 全部缓冲到 decision_wait，无法省 |
| 链路：其余 | 10%（概率决策） | `tail_sampling` 的 baseline-sample | 丢弃发生在 Collector 内存缓冲之后，缓冲量仍按全量 trace 数计 |
| 日志：WARN 及以上 | 100% | `logs/errors` 管道 | 无采样开销，只有脱敏 |
| 日志：DEBUG/INFO 正常请求 | 10% | `logs/baseline` 管道的 `probabilistic_sampler` | 丢弃在入队前，几乎零成本 |
| 指标 | 全采、不采样 | 无采样组件 | 成本随基数不随流量（§21.3.1）；对指标做采样会直接破坏 `rate` 计算的正确性，属禁止操作 |

`tail_sampling` 的两个参数要自洽核对：decision_wait 10s 内每个 trace 缓存在内存，缓冲量 ≈ `expected_new_traces_per_sec`(1000) × 10s = 1 万条 trace；`num_traces`(100000) 是缓存上限，余量 10 倍即健康。若流量涨 10 倍而这两个参数没跟着改，缓存驱逐会先于内存告警出现——**错误链路开始漏采**，且没有任何报错，只能靠 §21.1 复盘里「告警与链路对不上」这类现象间接发现。

`logs/errors` + `logs/baseline` 双管道的设计意图（对应 `metric-naming.md` 五的口径）：两条管道互斥（WARN 以上 / WARN 以下），所以不存在重复入库；`probabilistic_sampler` 带 `hash_seed`，对携带 `trace_id` 的日志做**确定性**哈希决策——同一 trace 的 INFO 日志要么全保留要么全丢弃，不会出现「同一次请求的日志一半有一半没有」。注意它与链路侧 10% 是两次独立决策：比例一致但结果不重合，排障时某个 trace 在 10% 基线里没捞到 INFO 日志属预期行为，其 WARN 以上日志仍在；要完整现场就走 Tempo 瀑布 + 错误日志。

> **本书观点（本章第 6 条结论，不需要外部背书）**
>
> **主张**：`tail_sampling` 依赖「一个 trace 的全部 span 到达同一个 Collector 实例」这一前提；`replicas: 2` + 普通 Service 随机分发不满足该前提，规模放大前必须显式处理。
>
> **论证**：`gateway` 与 `api` 各自的 SDK 按连接把 span 发给 Service，kube-proxy 逐连接分发，同一条 trace 的 span 完全可能拆到两个副本——错误 span 落在副本 B 时，副本 A 只看到「看起来正常」的前半段并按策略丢弃，Tempo 里留下半条 trace，且 10% 基线实际退化为「按 span 而非按 trace 采样」。当前规模能容忍（span/s 低、decision_wait 足够容纳绝大多数 trace 的到达窗），但这是规模放大的第一个断点：`verify-signal-chain.sh` 偶发只取到半条瀑布时，先查这里再查应用埋点。
>
> **反例与适用前提**：不要在发现半条 trace 后直接把 Collector 缩回 `replicas: 1` 了事——那是把分片问题换成单点问题。正确演进是两层拓扑：接入层（可多副本）只做 batch、经 `load_balancing` exporter 按 traceID 路由；采样层集中做 `tail_sampling`。该形态的完整配置如下，迁移触发条件写在这里，避免将来凭记忆重构：

```yaml
# 演进形态（span/s 超出单组决策容量或出现半条 trace 时迁移，非当前基线）：
# 接入层 otel-collector 的 traces pipeline 改为：
    exporters:
      load_balancing/tempo_sampling:
        protocol:
          otlp:
            tls:
              insecure: true
        resolver:
          dns:
            hostname: otel-sampling-gw.observability.svc.cluster.local
    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [memory_limiter, resource, batch]
          exporters: [load_balancing/tempo_sampling]
# 采样层独立 Deployment otel-sampling-gw（可多副本，LB 已按 traceID 路由）：
# 承接 §21.4 现有 tail_sampling 配置与 otlp/tempo exporter，配置逐字平移即可。
```

迁移的验证与回滚口径与 §21.5 完全一致：`verify-signal-chain.sh` 三段关联仍 PASS 才算迁移成功；失败即 `git checkout` 回本章基线，两层拓扑的回滚就是删掉采样层、恢复单层 pipeline，因为 `load_balancing` 只是转发、不持有状态。
