## 26.1 问题与护栏：隔离的边界在哪，权限与凭据怎么发、怎么收

如第 24 章开头所述，第六篇是前六篇护栏的汇总深化，不是最后才做安全。第 6 章就写下了 `automountServiceAccountToken: false`，第 9 章把 `order-demo/db-credentials` 挪出 Git、改由外部注入，第 14 章用 GitOps 堵住手工变更，第 19 章让 NetworkPolicy 默认拒绝，第 24 / 25 章把产物与清单的准入收紧到可验证。本章收的是最后一块：**机器身份与人的权限**。

先把三个本书口径钉住，避免被官方文档带偏：

- **RBAC**（基于角色的访问控制）一句话白话：把「谁能对哪些资源做什么」写成 `Role` 与 `RoleBinding`，由 API Server 在每次请求时判定 [R-26-3]。
- **ServiceAccount** 一句话白话：给 Pod 用的机器身份，区别于给人用的 User；它默认会带一个可调用 API Server 的 token [R-26-2][R-26-5]。
- **命名空间不是安全边界**，沿用第 4 章的同一措辞：它只做组织与配额隔离，同集群内的横向移动要靠额外策略层补偿（见第 4 章、第 19 章）[R-26-6]。

三条高频反模式，按「现象 → 根因 → 本章护栏」展开：

**反模式一：给所有 Pod 默认挂载 ServiceAccount token。** 现象是所有 Deployment 都不写 `automountServiceAccountToken`，每个 Pod 的 `/var/run/secrets/kubernetes.io/serviceaccount/token` 都可被容器内进程读取；一旦某个 Web 服务被打穿，攻击者拿到的不只是这台容器，还有一张能调 API Server 的身份凭证。根因是把「默认配置」当成了「无害配置」，而 K8s 出于兼容默认会挂载 token。本章护栏是：所有 ServiceAccount 与 Pod 模板显式 `automountServiceAccountToken: false`，只有确实需要调 API 的组件（如 `api` 读自己的 ConfigMap）才按 Role 精确授权并单独开启；这也正是 CIS Kubernetes Benchmark 对 ServiceAccount 与 RBAC 的基线要求 [R-26-7][R-26-2][R-26-5]。

**反模式二：把命名空间当安全边界。** 现象是两个团队共用一个集群，各给一个命名空间，就宣布「已经隔离了」；后来 A 团队的 Pod 通过 ClusterIP 直接访问到 B 团队的 `db`，或利用一个有 `cluster-admin` 的共享 SA 跨命名空间读 Secret。根因是命名空间只隔离了**对象的命名与配额**，没有隔离网络、没有隔离节点、也没有隔离控制面权限。本章护栏是用「失效场景表」逐条列出挡不住什么，并对每条给出补偿措施：NetworkPolicy 默认拒绝（见第 19 章）、按 SA 分权、敏感租户拆独立集群或独立云账号（见第 4 章、第 30 章）[R-26-6][R-26-3]。

**反模式三：长期 Access Key 写进配置。** 现象是 `deploy/` 里有一份带 `AWS_ACCESS_KEY_ID` 的 Secret 清单，或者 CI 里存着一把多年没换的云厂密钥；轮换要改多处、泄露了没人知道、离职同学的副本也收不回来。根因是把「机器身份」当成「静态字符串」管理，凭据的全生命周期（分发、轮换、吊销）没有任何一环是自动的。本章护栏是两层：集群内密钥由 External Secrets Operator 从 Vault 动态注入并定期刷新，云厂资源访问走 Workload Identity / IRSA 的短期令牌，凭据不再落进 Git 或镜像（公理 9，见第 3 章）；同时用审计日志把「谁在什么时候读了哪个 Secret」留痕 [R-26-1][R-26-9][R-26-11]。NIST SP 800-190 把容器环境的凭据风险明确覆盖到分发、轮换与吊销全周期，而不只是「别写进镜像」[R-26-1]。

> **一个作用域声明**：本章不重复第 9 章的密钥注入方案（External Secrets Operator 0.x + Vault 1.x 的选型与 `ExternalSecret` 基础字段），只补上「动态刷新与短期机器身份」这一层；也不重复第 19 章的 NetworkPolicy 规则，只在隔离失效表里引用它作为补偿。SP-08 要求两章口径不冲突，做法是沿用同一 Vault 路径 `order-demo/db-credentials` 与同一键名，不另起一套。

## 26.2 落地策略与门禁：最小权限、动态凭据、可审计

### 26.2.1 权限基线表

基线表既是设计，也是 §26.3 检查清单的判据来源。`order-demo` 的三个组件都不需要 `cluster-admin`，也不需要一个「万能 SA」。

| 主体 | 允许动作 | 资源范围 | 依据 | 何时收紧 |
|---|---|---|---|---|
| `system:serviceaccount:order-demo-dev:api` | `get` | `configmaps/order-demo-config`（限定 `resourceNames`） | 第 9 章不可变 ConfigMap 由 Pod 启动时读取 [R-26-3] | 一旦不需要读配置，删掉整条 Role；禁止扩到 `secrets` |
| `system:serviceaccount:order-demo-dev:gateway` | 无 K8s API 权限 | — | 纯 HTTP 入口，token 不挂载 [R-26-5] | 任何新增 `verbs` 都视为误伤信号 |
| `system:serviceaccount:order-demo-dev:worker` | `get` | `configmaps/order-demo-config` | 与 `api` 同构，异步任务只读配置 | 若改由环境变量注入，则收回 Role |
| `order-demo-prod:api`（云上资源） | 短期令牌换取临时凭据 | 云厂 IAM Role `order-demo-api` | Workload Identity / IRSA，RFC 级机器身份 [R-26-8] | 出现任何长期 Access Key 立即吊销并轮换 |
| 人（值班 / 开发） | 通过 Git 声明变更，集群只读 | 由 GitOps 控制器以自身 SA 执行（见第 14 章） | 公理 5：生产无手工变更通道 | 出现 `kubectl edit` 记录即按 `CL-S-04` 处置 |

注意第二行：`gateway` 的「无 K8s API 权限」不是遗漏，而是基线。第 6 章的最小闭环里它就不挂载 token，本章把这个事实写进 SA 定义，让它可被 `kubectl get sa -o yaml` 验证 [R-26-5][R-26-7]。

### 26.2.2 隔离失效场景表

| 场景 | 命名空间能否挡住 | 补偿措施 |
|---|---|---|
| A 租户 Pod 直连 B 租户 Service（ClusterIP） | **挡不住**，K8s 网络默认全通 | NetworkPolicy 默认拒绝 + 按标签放行，见第 19 章 |
| 共享 SA 被绑定到 `cluster-admin` | **挡不住**，ClusterRole 跨所有命名空间 | 按 SA 拆 Role / RoleBinding，禁用 cluster-admin 泛用 [R-26-3] |
| 同节点上两个租户的容器共享内核 | **挡不住**，命名空间不是内核边界 | 敏感租户拆独立集群 / 独立云账号，见第 4 章、第 30 章；配合 `restricted` 级 PSS（见第 25 章） |
| 节点被攻破后读取 kubelet 凭据 | **挡不住** | 节点最小权限、审计日志、禁用生产 SSH（见 26.2.3 本书观点）[R-26-4] |
| 有人手工 `kubectl edit` 改生产 | **挡不住** | GitOps 漂移纠正（见第 14 章）+ 审计留痕 [R-26-4] |

这张表的用法不是「读完就放心」，而是逐行回答「我们集群里这一行由谁补偿、怎么验证」。第 4 章给出环境边界，第 30 章给出集群 / 账号边界，本章只负责把「挡不住」写清楚并挂上补偿，三处措辞保持一致（SP-12）。

### 26.2.3 完整可应用配置（Kubernetes 1.32+）

**`deploy/base/serviceaccount.yaml`** —— 三个组件的专属 SA，显式关闭 token 自动挂载；staging / prod 由 Kustomize 5.x overlay 复用同一份（见第 10 章），命名空间按契约替换。

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: gateway
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
automountServiceAccountToken: false
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: api
automountServiceAccountToken: false
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: worker
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: worker
automountServiceAccountToken: false
```

对第 6 章 `deploy/base/deployment.yaml` 的增量 diff（只加一行 `serviceAccountName`，不改动任何已冻结字段）：

```diff

+      serviceAccountName: api
```

**`policies/rbac/order-demo-api-role.yaml`** —— 最小权限基线。不给 Secret 权限的**唯一正确表达是规则里不写**：RBAC 没有显式拒绝语义，写 `verbs: []` 会被 apiserver 直接拒绝（`verbs: Required value`，真集群 server dry-run 实测，见 D-29）。想在 code review 里显式声明「这里故意不授权」，用注释，而不是用一条非法规则 [R-26-3]。

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: order-demo-api
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["order-demo-config"]
    verbs: ["get"]
  # 故意不写 secrets 规则：RBAC 没有显式拒绝，写 verbs: [] 会被 apiserver 拒绝
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: order-demo-api
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
subjects:
  - kind: ServiceAccount
    name: api
    namespace: order-demo-dev
roleRef:
  kind: Role
  name: order-demo-api
  apiGroup: rbac.authorization.k8s.io
```

**`policies/rbac/order-demo-workload-identity.yaml`** —— 机器身份接入。Workload Identity / IRSA 一句话白话：让 Pod 用 Kubernetes 的 ServiceAccount 身份去云厂 IdP 换一张短期令牌，SDK 自动刷新，配置里不再出现长期 Access Key。下面以 AWS IRSA 为唯一示例，GCP Workload Identity 的等价 annotation 写在注释里，按云厂二选一填写 [R-26-8][R-26-1]。

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api
  namespace: order-demo-prod
  annotations:
    eks.amazonaws.com/role-arn: "arn:aws:iam::123456789012:role/order-demo-api"
    # GCP Workload Identity 改用下面一行，并把 GSA 绑定到该 KSA：
    # iam.gke.io/gcp-service-account: "order-demo-api@example-project.iam.gserviceaccount.com"
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: api
automountServiceAccountToken: false
```

> AWS SDK 通过 projected ServiceAccount token 与 OIDC 联合自动换取临时凭据，轮换与吊销由 IdP 承担；这正是反模式三的对立面。注意 `arn:aws:iam::123456789012:role/...` 是示例账号 ID，实际值由 IaC 注入（见第 30 章），不写进本章配置仓库的明文凭据。短期令牌的 TTL、信任策略与审计由云厂侧管理，本章只看「集群里有没有长期 Key」这一条判据 [R-26-8]。

**`policies/rbac/externalsecret.yaml`** —— 动态凭据：沿用第 9 章的 Vault 路径 `order-demo/db-credentials`，`refreshInterval: 1h` 让 ESO 定期重拉；Vault 侧把数据库凭据配成动态、带 TTL，轮换不需要重建镜像（见第 9 章）[R-26-1][R-26-2]。

```yaml
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: order-demo-vault
  namespace: order-demo-dev
spec:
  provider:
    vault:
      server: "http://vault.vault.svc:8200"
      path: "secret"
      version: "v2"
      auth:
        kubernetes:
          mountPath: "kubernetes"
          role: "order-demo-api"
          serviceAccountRef:
            name: api
---
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: order-demo-db-credentials
  namespace: order-demo-dev
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: order-demo-vault
    kind: SecretStore
  target:
    name: order-demo-db-credentials
    creationPolicy: Owner
  data:
    - secretKey: username
      remoteRef:
        key: order-demo/db-credentials
        property: username
    - secretKey: password
      remoteRef:
        key: order-demo/db-credentials
        property: password
```

> K8s `Secret` 对象名不能含 `/`，故 `metadata.name` 用连字符；Vault 侧路径仍严格沿用第 9 章契约的 `order-demo/db-credentials`，SP-08 的两章口径因此一致。`refreshInterval` 与 Vault 动态凭据的 TTL 共同决定轮换节奏，两者都要短于凭据泄露后的可接受暴露窗口 [R-26-1][R-26-9]。

**`policies/rbac/audit-policy.yaml`** —— 审计策略。规则按「第一个匹配生效」排列：先丢弃高频噪声，再完整记录 Secret / RBAC 与工作负载变更，最后对只读请求记元数据 [R-26-4]。

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  - level: None
    resources:
      - group: ""
        resources: ["events"]
      - group: "coordination.k8s.io"
        resources: ["leases"]
  - level: RequestResponse
    resources:
      - group: ""
        resources: ["secrets", "serviceaccounts", "serviceaccounts/token"]
      - group: "rbac.authorization.k8s.io"
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
  - level: RequestResponse
    verbs: ["create", "update", "patch", "delete", "deletecollection"]
    resources:
      - group: "apps"
        resources: ["deployments", "statefulsets"]
      - group: ""
        resources: ["pods", "configmaps"]
  - level: Metadata
    verbs: ["get", "list", "watch"]
```

### 26.2.4 本书观点：SSH 禁入生产

> **本书观点（本章第 2 条结论，不需要外部背书）**
>
> **主张**：**SSH 禁入生产**——排障走可观测与 runbook，不登机器。这是全书公理 8（见第 3 章），本章把它落到权限与凭据层。
>
> **论证**：允许 SSH 登生产节点，等于同时破坏了三条已经建好的护栏：其一，任何手工 `kubectl edit` / 改文件都无法被 GitOps 的漂移检测纠正（见第 14 章）；其二，节点上的 kubelet 凭据、容器运行时 socket 与临时文件都暴露给登录者，最小 RBAC 与审计留痕形同虚设；其三，登录行为本身几乎没有结构化审计，「谁在什么时候改了什么」无法回答。反过来，把排障入口收敛到指标、日志、链路与 runbook（见第 21、22、23 章），每一次处置都会自然留下可复查的记录，也更接近「可回滚、可审计」的目标。SRE 类著作对「以可观测与自动化替代登机操作」有长期讨论，但本结论的论证不依赖它背书 [R-26-10]。
>
> **反例与适用前提**：这不等于「任何时候都不允许任何人接触节点」。集群初始安装、内核级故障取证、云厂硬件故障排查确实可能需要带外访问，但那是**受控的、有工单与到期时间的 break-glass 流程**，不是日常排障通道，且必须写入例外登记（模板见第 25 章 `docs/policy-exception.md`）。另一个反例是本地 kind 与开发环境：本章的禁令只针对 `order-demo-prod`，本地集群用 `docker exec` 查审计日志正是本书验证命令的一部分，不构成对公理的例外。第 23 章的现场处置给出了「不登机器也能定位并止血」的完整 runbook 集合。

### 26.2.5 验证与回滚

**验证命令**（仓库根目录；集群按 `hack/kind-audit.yaml` 起来后执行）：

```bash
kubectl apply -f deploy/base/serviceaccount.yaml
kubectl apply -f policies/rbac/order-demo-api-role.yaml
kubectl apply -f policies/rbac/externalsecret.yaml
kubectl apply -f policies/rbac/order-demo-workload-identity.yaml

# 1) 越权请求被 RBAC 拒绝
kubectl -n order-demo-dev auth can-i --as=system:serviceaccount:order-demo-dev:api get secrets
kubectl -n order-demo-dev auth can-i --as=system:serviceaccount:order-demo-dev:api get configmap/order-demo-config

# 2) 用真实的 SA token 发一次越权请求，制造审计事件
TOKEN="$(kubectl -n order-demo-dev create token api --duration=10m)"
APISERVER="$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')"
kubectl --server="${APISERVER}" --insecure-skip-tls-verify --token="${TOKEN}" \
  -n order-demo-dev get secret order-demo-db-credentials 2>&1 | tee /tmp/forbidden.out

# 3) 审计留痕
docker exec order-demo-control-plane \
  grep '"forbidden"' /var/log/kubernetes/audit.log | tail -n 3
docker exec order-demo-control-plane \
  grep 'system:serviceaccount:order-demo-dev:api' /var/log/kubernetes/audit.log | tail -n 3

# 4) SA 与隔离基线
kubectl -n order-demo-dev get sa api \
  -o jsonpath='{.automountServiceAccountToken}{"\n"}'
kubectl -n order-demo-prod get sa api -o yaml
kubectl -n order-demo-prod get networkpolicy
kubectl -n order-demo-dev get role,rolebinding order-demo-api
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 越权读 Secret | `auth can-i ... get secrets` 返回 `no`；真实 token 请求报 `forbidden` |
| 合法读 ConfigMap | `auth can-i ... get configmap/order-demo-config` 返回 `yes` |
| 审计留痕 | 日志里能同时查到 `forbidden` 与 `system:serviceaccount:order-demo-dev:api`，且含 `secrets` 的 objectRef |
| SA 加固 | `automountServiceAccountToken` 为 `false`，三个 SA 均无 `cluster-admin` 绑定 |
| 动态凭据 | `ExternalSecret` 状态 `SecretSynced`，Vault 路径为 `order-demo/db-credentials`，仓库内无明文 Key |
| 机器身份 | prod 的 `api` SA 带 `eks.amazonaws.com/role-arn` annotation，无长期 Access Key |
| 生产无 SSH | `order-demo-prod` 存在默认拒绝 NetworkPolicy；无 `pods/exec` 到节点的通道（见第 23、19 章） |

第 2 步与第 3 步构成「越权被 RBAC 拒绝并留审计」的完整证据链：`auth can-i` 是判定能力的快速检查，真实 token 请求才是让 API Server 真正写下 `forbidden` 审计事件的动作 [R-26-3][R-26-4]。

**回滚 / 降级命令与步骤**。权限收紧出问题（如某组件因缺权限起不来）时，先回到上一个已知良好版本，再登记例外；**不要直接给 `cluster-admin` 止血**：

```bash
# 1) 取上一个 tag 的 RBAC 基线并应用（可复制执行，见 case-evolution.md 的 tag 命名）
PREV_TAG="$(git describe --tags --abbrev=0 HEAD^)"
git show "${PREV_TAG}:policies/rbac/order-demo-api-role.yaml" > /tmp/prev-api-role.yaml
kubectl apply -f /tmp/prev-api-role.yaml

# 2) 应急临时授权：写入例外登记，带到期时间，绝不写 cluster-admin
kubectl -n order-demo-dev describe pod <起不来的 Pod 名>
printf '%s\n' "date=$(date -u +%F) reason=rbac-rollback sha=$(git rev-parse --short=7 HEAD) expires=$(date -u -d '+2 days' +%F)" \
  >> docs/tenant-isolation-checklist.md
git add docs/tenant-isolation-checklist.md policies/rbac/order-demo-api-role.yaml
git commit -m "chore(rbac): temporary least-privilege exception with expiry"

# 3) 正式回退：撤销本次变更，回到 Git 声明
git revert HEAD
kubectl apply -f policies/rbac/order-demo-api-role.yaml
```

> 生产变更必须回到 Git（公理 5，见第 3 章）。`kubectl apply` 在这里是把「Git 里已回退的声明」重新同步到集群，不是绕过 GitOps 的手工改动；`order-demo-prod` 的实际收敛仍由 Argo CD 2.x 完成（见第 14 章）。

**回滚验证**：

```bash
kubectl -n order-demo-dev auth can-i --as=system:serviceaccount:order-demo-dev:api get secrets
kubectl -n order-demo-dev auth can-i --as=system:serviceaccount:order-demo-dev:api get configmap/order-demo-config
kubectl -n order-demo-dev get sa api \
  -o jsonpath='{.automountServiceAccountToken}{"\n"}'
kubectl -n order-demo-dev get role,rolebinding order-demo-api
docker exec order-demo-control-plane \
  grep '"forbidden"' /var/log/kubernetes/audit.log | tail -n 3
./hack/verify.sh
kubectl -n order-demo-dev get externalsecret order-demo-db-credentials \
  -o jsonpath='{.status.conditions[0].message}{"\n"}'
```

通过标准：越权读 Secret 仍为 `no`、合法读 ConfigMap 仍为 `yes`（说明基线没被改松）；`automountServiceAccountToken` 仍为 `false`；降级窗口内的 `forbidden` 审计事件完整保留（证据链未断）；第 6 章的 `hack/verify.sh` 通过；`ExternalSecret` 仍为同步成功状态。**回滚没有验证过，就不允许继续发布**（母版 `CL-G-07`）。
