## 26.1 问题与护栏：隔离的边界在哪，权限与凭据怎么发、怎么收

如第 24 章开头所述，第六篇是前六篇护栏的汇总深化，不是最后才做安全。第 6 章就写下了 `automountServiceAccountToken: false`，第 9 章把 `order-demo/db-credentials` 挪出 Git、改由外部注入，第 14 章用 GitOps 堵住手工变更，第 19 章让 NetworkPolicy 默认拒绝，第 24 / 25 章把产物与清单的准入收紧到可验证。本章收的是最后一块：**机器身份与人的权限**。

先把三个本书口径钉住，避免被官方文档带偏：

- **RBAC**（基于角色的访问控制）一句话白话：把「谁能对哪些资源做什么」写成 `Role` 与 `RoleBinding`，由 API Server 在每次请求时判定 [R-26-3]。
- **ServiceAccount** 一句话白话：给 Pod 用的机器身份，区别于给人用的 User；它默认会带一个可调用 API Server 的 token [R-26-2][R-26-5]。
- **命名空间不是安全边界**，沿用第 4 章的同一措辞：它只做组织与配额隔离，同集群内的横向移动要靠额外策略层补偿（见第 4 章、第 19 章）[R-26-6]。

三条高频反模式，按「现象 → 根因 → 本章护栏」展开：

**反模式一：给所有 Pod 默认挂载 ServiceAccount token。** 现象是所有 Deployment 都不写 `automountServiceAccountToken`，每个 Pod 的 `/var/run/secrets/kubernetes.io/serviceaccount/token` 都可被容器内进程读取；一旦某个 Web 服务被打穿，攻击者拿到的不只是这台容器，还有一张能调 API Server 的身份凭证。根因是把「默认配置」当成了「无害配置」，而 K8s 出于兼容默认会挂载 token。本章护栏是：所有 ServiceAccount 与 Pod 模板显式 `automountServiceAccountToken: false`，只有确实需要调 API 的组件（如 `api` 读自己的 ConfigMap）才按 Role 精确授权并单独开启；这也正是 CIS Kubernetes Benchmark 对 ServiceAccount 与 RBAC 的基线要求 [R-26-7][R-26-2][R-26-5]。

**反模式二：把命名空间当安全边界。** 现象是两个团队共用一个集群，各给一个命名空间，就宣布「已经隔离了」；后来 A 团队的 Pod 通过 ClusterIP 直接访问到 B 团队的 `db`，或利用一个有 `cluster-admin` 的共享 SA 跨命名空间读 Secret。根因是命名空间只隔离了**对象的命名与配额**，没有隔离网络、没有隔离节点、也没有隔离控制面权限。本章护栏是用「失效场景表」逐条列出挡不住什么，并对每条给出补偿措施：NetworkPolicy 默认拒绝（见第 19 章）、按 SA 分权、敏感租户拆独立集群或独立云账号（见第 4 章、第 30 章）[R-26-6][R-26-3]。

**反模式三：长期 Access Key 写进配置。** 现象是 `deploy/` 里有一份带 `AWS_ACCESS_KEY_ID` 的 Secret 清单，或者 CI 里存着一把多年没换的云厂密钥；轮换要改多处、泄露了没人知道、离职同学的副本也收不回来。根因是把「机器身份」当成「静态字符串」管理，凭据的全生命周期（分发、轮换、吊销）没有任何一环是自动的。本章护栏是两层：集群内密钥由 External Secrets Operator 从 Vault 动态注入并定期刷新，云厂资源访问走 Workload Identity / IRSA 的短期令牌，凭据不再落进 Git 或镜像（公理 9，见第 3 章）；同时用审计日志把「谁在什么时候读了哪个 Secret」留痕 [R-26-1][R-26-9][R-26-11]。NIST SP 800-190 把容器环境的凭据风险明确覆盖到分发、轮换与吊销全周期，而不只是「别写进镜像」[R-26-1]。

> **一个作用域声明**：本章不重复第 9 章的密钥注入方案（External Secrets Operator 0.x + Vault 1.x 的选型与 `ExternalSecret` 基础字段），只补上「动态刷新与短期机器身份」这一层；也不重复第 19 章的 NetworkPolicy 规则，只在隔离失效表里引用它作为补偿。第 9 章与本章口径必须一致，做法是沿用同一 Vault 路径 `order-demo/db-credentials` 与同一键名，不另起一套。

## 26.2 落地策略与门禁：最小权限、动态凭据、可审计

### 26.2.1 权限基线表

基线表既是设计，也是 §26.3 检查清单的判据来源。`order-demo` 的三个组件都不需要 `cluster-admin`，也不需要一个「万能 SA」。

| 主体 | 允许动作 | 资源范围 | 依据 | 何时收紧 |
|---|---|---|---|---|
| `system:serviceaccount:order-demo-dev:api` | `get` | `configmaps/order-demo-config`（限定 `resourceNames`） | 第 9 章不可变 ConfigMap 由 Pod 启动时读取 [R-26-3] | 一旦不需要读配置，删掉整条 Role；禁止扩到 `secrets` |
| `system:serviceaccount:order-demo-dev:gateway` | 无 K8s API 权限 | — | 纯 HTTP 入口，token 不挂载 [R-26-5] | 任何新增 `verbs` 都视为误伤信号 |
| `system:serviceaccount:order-demo-dev:worker` | `get` | `configmaps/order-demo-config` | 与 `api` 同构，异步任务只读配置 | 若改由环境变量注入，则收回 Role |
| `order-demo-prod:api`（云上资源） | 短期令牌换取临时凭据 | 云厂 IAM Role `order-demo-api` | Workload Identity / IRSA，RFC 级机器身份 [R-26-8] | 出现任何长期 Access Key 立即吊销并轮换 |
| 人（值班 / 开发） | 通过 Git 声明变更，集群只读 | 由 GitOps 控制器以自身 SA 执行（见第 14 章） | 公理 5：生产无手工变更通道 | 出现 `kubectl edit` 记录即按 `CL-S-04` 处置 |

注意第二行：`gateway` 的「无 K8s API 权限」不是遗漏，而是基线。第 6 章的最小闭环里它就不挂载 token，本章把这个事实写进 SA 定义，让它可被 `kubectl get sa -o yaml` 验证 [R-26-5][R-26-7]。

权限与凭据不是「配好就完」：它们各有一条从申请到吊销的全生命周期。把每个阶段的动作与审计留痕点画出来，出事时才知道去哪里找证据、收权时才知道要收哪些东西（[R-26-4][R-26-1]）。下面这张图是 `order-demo` 三类权限 / 凭据（K8s RBAC、ESO 注入的外部凭据、Workload Identity 临时凭据）共用的生命周期视图：

```text
[申请]──▶[评审]──▶[发放]──▶[使用]──▶[轮换]──▶[吊销]──▶[复盘]
 Git PR    双人      CI 门禁 +   每次请求   定期 / 事件  到期 / 事件  postmortem
 （人的权限）review   GitOps 同步  鉴权判定   自动刷新     收回权限     更新基线
```

| 阶段 | 动作与触发条件 | 执行主体 | 审计留痕点 | 到期 / 回收机制 |
|---|---|---|---|---|
| 申请 | 人的权限需求一律走 Git PR 改 Role / RoleBinding 清单；机器凭据不「申请」，由 ESO 与 Workload Identity 按基线自动发放 | 开发 / 平台团队 | Git PR 与评审记录（不在 K8s 审计里） | 未合并即不存在 |
| 评审 | 双人 review；CI 用 conftest 拒绝 `cluster-admin` 与通配 `verbs`（见第 25 章） | 审批人 + CI | PR 记录、CI 报告 | 无需——不生效 |
| 发放 | Argo CD 3.x 同步生效（见第 14 章） | GitOps 控制器 | K8s 审计：RBAC 对象 create / update 为 RequestResponse [R-26-4] | RoleBinding 引用的 SA 被删即失效 [R-26-3] |
| 使用 | 每次请求由 API Server 逐条判定；越权产生 `forbidden` 事件 | API Server | K8s 审计：普通读 Metadata、Secret / RBAC 写 RequestResponse [R-26-4] | projected token 随 Pod 销毁失效；`kubectl create token` 带 TTL [R-26-5] |
| 轮换 | ESO 每 `refreshInterval: 1h` 重拉 Vault；Workload Identity 每次换发新临时凭据 | ESO / 云 SDK | 云侧：每次 `AssumeRoleWithWebIdentity` 进云厂审计；集群侧：`serviceaccounts/token` 的 create | Vault 动态凭据 TTL 与 `refreshInterval` 共同决定暴露窗口（判据见 §26.2.3）[R-26-1][R-26-9] |
| 吊销 | 删 RoleBinding / 收紧云侧信任策略 / 删 Pod；工单类授权到期由回收器自动删除 | 人 + 自动回收器 | K8s 审计：delete 事件；云侧：信任策略变更记录 | 本节所有授权都必须回答「何时到期」，无永久授权 |
| 复盘 | 每次事故 / 演练后更新基线表与检查清单 | 全团队 | postmortem 文档（入 Git） | 复盘结论回填基线表「何时收紧」列 |

这张表有三种用法。其一，任何一条权限都必须能回答「它的到期机制是什么」，回答不出来就按反模式处理；其二，「使用」阶段的 `forbidden` 事件是免费的入侵检测信号——§26.2.5 的验证命令正是靠它构造证据链；其三，「吊销」永远先于「复盘」执行，先止血、再取证、后反思，顺序颠倒会让证据链断在半路（完整走一遍的过程见 §26.2.2 的合成案例复盘）。

**RBAC 作用域、聚合与三个高危权限：越权大多不是「没配 RBAC」，而是「配大了」。** 权限基线表回答的是「该给什么」，这一段补上「怎么给才不会给多」：一次请求的判定结果由 Role 的规则与 RoleBinding 的作用域共同决定，三种作用域组合各有明确适用前提 [R-26-3]：

| 组合 | 生效范围 | 适用前提 | 典型误用 |
|---|---|---|---|
| `Role` + `RoleBinding` | 单个命名空间 | 权限只在绑定所在的命名空间生效 | 在每个命名空间重复贴一份本该共享的只读规则模板 |
| `ClusterRole` + `RoleBinding` | 绑定所在的那个命名空间 | 复用一套规则定义、按命名空间逐一授权 | 误当成「全局授权」——它不跨命名空间，也不会被多个命名空间共享 |
| `ClusterRole` + `ClusterRoleBinding` | 全集群所有命名空间 | 仅平台级运维主体，且必须带到期机制 | 给业务 SA 绑 `cluster-admin` 或宽松聚合角色 |

第二条是最常被误解的组合：`ClusterRole` 只是**权限定义**，`ClusterRoleBinding` 才是**全集群发放**；同一个 `ClusterRole` 被 20 个命名空间的 `RoleBinding` 引用，权限就只在那 20 个命名空间内生效。`order-demo` 的判定规则：组件 SA 一律用第一条组合；确需第二条时，每个新增 `RoleBinding` 都计入变更评审；第三条只允许平台团队申请，且套用 §26.2.4 break-glass 的到期回收机制，不允许永久持有 [R-26-3]。

权限基线表用 `resourceNames` 把 `get` 钉到具体对象，但它有两个容易踩的边界：其一，`resourceNames` 对 `list` / `watch` / `deletecollection` 这类**不点名**的动词不生效——若有人把规则里的 `get` 扩成 `list`，等于绕过钉名拿到该类型全量清单；其二，对 `create` 这类作用于集合的动词同样不适用。判据：`resourceNames` 只与 `get` / `update` / `patch` / `delete` 这类显式点名动词搭配，且把「含 `resourceNames` 的规则里是否混入了不点名动词」列为 CI 门禁检查项（写法见第 25 章）。

聚合 `ClusterRole` 让「配大了」变得更隐蔽。`aggregationRule` 按 label 选择器把其他 ClusterRole 的规则自动吸进聚合角色，`rules` 由控制器填充、手写无效 [R-26-3]：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: order-demo-platform-readonly
aggregationRule:
  clusterRoleSelectors:
    - matchLabels:
        rbac.order-demo.io/aggregate-to-platform-readonly: "true"
# rules 不手写：任何带上述标签的 ClusterRole 会被自动吸入
```

风险在「静默变大」：某天有人新建一个带 `rbac.order-demo.io/aggregate-to-platform-readonly: "true"` 标签的 ClusterRole，聚合角色立刻多出它的全部规则——没有 diff 提醒，没有评审拦截。判据：聚合角色只用于平台只读基线，该标签本身视为受 Git 管理的资源（见第 14 章），CI 门禁拒绝把标签打在任何含 `secrets` 规则的角色上（写法见第 25 章）。

**三个高危权限，每一个都等效于「把别人的权限借给自己」**[R-26-3]：

- **`escalate`**：对 `roles` / `clusterroles` 持有 `escalate` 的主体，可以在创建或修改 Role 时写入**自己并不具备**的权限，等于自我提权。没有它，API Server 会拒绝你把自己没有的权限写进 Role——这是「不能凭空造权」的唯一保证。
- **`bind`**：对 `rolebindings` 持有 `bind`，可以把一个自己无权授予的 Role 绑给任何主体（包括自己）。CI 部署 SA 若同时能 `create` RoleBinding、又知道某个 admin Role 的名字，就构成一条完全不需要 `cluster-admin` 的提权路径。
- **`impersonate`**：对 `users` / `serviceaccounts` 持有 `impersonate`，可以冒充任意身份调 API；审计事件里的 `user` 字段会变成被冒充者，取证必须结合 impersonation 相关留痕才能还原真实操作者（必留痕清单见 §26.2.3 审计部分）。

组合判据：`escalate` 与 `impersonate` 全集群只允许在 break-glass 工单有效期内临时持有（§26.2.4）；CI 的 GitOps SA 只给 Role / RoleBinding 的 `create` / `update`，**不给** `escalate`——它只能维护 Git 里预先声明的最小规则集，改规则必须回 Git PR [R-26-3]。

**`system:authenticated` 误用**是最后一条高频越权：把 group `system:authenticated` 写进 RoleBinding 的 subjects，等于把权限发给**全集群每一个已认证身份**——包括每个 Pod 的 SA。合成一例：某团队为「方便调试」建了一条 subjects 为 `system:authenticated`、规则为 `secrets get` 的 RoleBinding，从此任何被攻破的容器都自动获得读本集群 Secret 的能力，命名空间边界形同虚设——这正是 §26.2.2 隔离失效表第二行的另一个变体。检查与处置：

```bash
# 检索绑定到 system:authenticated 的授权（通过标准：除内置保留项外无业务命中）
kubectl get rolebindings,clusterrolebindings -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.subjects[*].name}{"\n"}{end}' \
  | grep 'system:authenticated'
```

命中即按反模式处置：改成显式列出 SA / 用户的 RoleBinding，走 Git PR 评审。日常自审用 `kubectl auth can-i --list --as=system:serviceaccount:order-demo-dev:api` 对照基线表逐行核对，用 `kubectl auth whoami` 确认当前实际身份（1.28+ 可用）[R-26-3]。

### 26.2.2 隔离失效场景表

| 场景 | 命名空间能否挡住 | 补偿措施 |
|---|---|---|
| A 租户 Pod 直连 B 租户 Service（ClusterIP） | **挡不住**，K8s 网络默认全通 | NetworkPolicy 默认拒绝 + 按标签放行，见第 19 章 |
| 共享 SA 被绑定到 `cluster-admin` | **挡不住**，ClusterRole 跨所有命名空间 | 按 SA 拆 Role / RoleBinding，禁用 cluster-admin 泛用 [R-26-3] |
| 同节点上两个租户的容器共享内核 | **挡不住**，命名空间不是内核边界 | 敏感租户拆独立集群 / 独立云账号，见第 4 章、第 30 章；配合 `restricted` 级 PSS（见第 25 章） |
| 节点被攻破后读取 kubelet 凭据 | **挡不住** | 节点最小权限、审计日志、禁用生产 SSH（见 26.2.3 本书观点）[R-26-4] |
| 有人手工 `kubectl edit` 改生产 | **挡不住** | GitOps 漂移纠正（见第 14 章）+ 审计留痕 [R-26-4] |

这张表的用法不是「读完就放心」，而是逐行回答「我们集群里这一行由谁补偿、怎么验证」。第 4 章给出环境边界，第 30 章给出集群 / 账号边界，本章只负责把「挡不住」写清楚并挂上补偿，三处措辞保持一致。

**合成案例复盘：共享 SA 被打穿后的跨命名空间读 Secret——取证与收权。** 以下为合成案例，用于演示完整处置流程；命名空间 `tenant-a` 与 SA `platform-ops` 均为虚构，不属于 `order-demo` 配置契约，按合成案例约定不得冒充真实事件 [R-26-11]。

背景：某集群早期为图省事，建了一个跨团队共享的 SA `platform-ops`，绑定到自建 ClusterRole `platform-ops-admin`，其中包含**所有命名空间** `secrets` 的 `get` / `list`（本意是给一个配置同步工具用）。租户 A 的 Web 服务 `checkout-web` 的 Pod 又因「方便排障」没有关闭 token 自动挂载，于是把这张高权限共享 token 带进了容器。某日 `checkout-web` 被一个 RCE 漏洞打穿，攻击者读出 token，直接向 API Server 发起 `GET /api/v1/namespaces/order-demo-prod/secrets/order-demo-db-credentials`，拿到了数据库凭据。命名空间边界与上表第二行的预测完全一致：挡不住 [R-26-6][R-26-3]。

处置按「先取证、再收权、后轮换、终复盘」的顺序走，五步如下。

**第一步：取证优先于删除。** 应急的本能是马上删权限，但删除动作本身会改写现场——RoleBinding 删掉之后，就再也无法回答「当时它到底能做什么」。所以第一小时只做只读操作，把审计日志按主体与时间窗拉出来并固化副本：

```bash
# 锁定事发窗口内共享 SA 的全部 Secret 访问记录（只读，不动现场）
docker exec order-demo-control-plane sh -c \
  "grep 'system:serviceaccount:tenant-a:platform-ops' /var/log/kubernetes/audit.log" \
  | grep '"secrets"' | grep -E '"(get|list|watch)"' > /tmp/evidence.log

# 固化原始日志副本作为证据，并确认命中非 0
docker cp order-demo-control-plane:/var/log/kubernetes/audit.log \
  /tmp/audit-$(date -u +%Y%m%dT%H%M%SZ).log
wc -l /tmp/evidence.log    # 通过标准：行数 > 0
```

**第二步：还原攻击路径。** 从 `/tmp/evidence.log` 按时间顺序读三件事：`sourceIPs` 是否来自 `checkout-web` 的 Pod 网段；`userAgent` 是否为裸 HTTP 客户端（curl、Go http，而不是正常控制器的 UA）；`responseStatus.code` 是否出现 `200`——`403` 只是「试过」，`200` 才是「读到了」[R-26-4]：

```bash
# 逐条还原：时间 / 来源 IP / 动作 / 对象 / 结果码
grep -o '"stageTimestamp":"[^"]*"\|"sourceIPs":\[[^]]*\]\|"verb":"[^"]*"\|"resource":"[^"]*"\|"name":"[^"]*"\|"code":[0-9]*' \
  /tmp/evidence.log

# 统计读取成功的次数与对象清单（200 即已实际读到内容，内容按已泄露处理）
grep -c '"code":200' /tmp/evidence.log
grep -o '"name":"[a-z0-9-]*"' /tmp/evidence.log | sort | uniq -c | sort -rn
```

**第三步：圈定暴露面。** 「读到」的对象必须视为已泄露，但暴露面不止审计里出现过的——还要算上它「有权读但还没读」的全部对象。权限计算不依赖审计日志是否恰好记录过：

```bash
# 该 SA 的完整权限
kubectl auth can-i --as=system:serviceaccount:tenant-a:platform-ops list secrets -A
# 它通过哪些绑定拿到权限（逐条列出，收权时不漏）
kubectl get clusterrolebinding,rolebinding -A -o yaml | grep -B6 'name: platform-ops'
# 绑定到的 ClusterRole 到底给了什么
kubectl get clusterrole platform-ops-admin -o yaml
```

**第四步：收权（分钟级，按顺序执行）。** 先断「新请求」，再灭「存量 token」，两者缺一不可：

```bash
# 1) 解绑权限：删除把共享 SA 连到宽松 ClusterRole 的绑定（含各命名空间的 RoleBinding）
kubectl delete clusterrolebinding platform-ops-cluster-binding
kubectl -n tenant-a delete rolebinding platform-ops-binding

# 2) 灭存量 token：bound token 随 Pod 销毁立即失效，删除挂载该 token 的全部 Pod [R-26-5]
kubectl -n tenant-a delete pod -l app=checkout-web

# 3) 清遗留的长期 token（仅 legacy token 模式才存在；bound token 集群通常没有）
kubectl -n tenant-a get secrets \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.type}{"\n"}{end}' \
  | awk '$2 == "kubernetes.io/service-account-token" {print $1}' \
  | xargs -r kubectl -n tenant-a delete secret

# 4) 验证收权完成
kubectl auth can-i --as=system:serviceaccount:tenant-a:platform-ops get secrets -A   # 期望：no
# 事发 token 的留存副本再请求一次，期望 401（token 已随 Pod 销毁失效）
```

**第五步：凭据作废与恢复。** 权限收了不等于凭据安全：凡审计里出现 `code: 200` 的 Secret，内容一律按已泄露处理。`order-demo-db-credentials` 的轮换要记在 Vault 头上——数据库侧换掉旧密码后，强制 ESO 立即重拉，让 Pod 里的旧值在下一次同步前作废。这正是动态凭据相对静态 Secret 的价值：泄露的不是一个「永久的字符串」，而是一个可以被服务端作废的短周期值 [R-26-1][R-26-2]：

```bash
# Vault 侧轮换完成后，强制 ESO 立即同步（不等 refreshInterval 的下一个周期）
kubectl -n order-demo-prod annotate externalsecret order-demo-db-credentials \
  force-sync="$(date -u +%Y-%m-%dT%H:%M:%SZ)" --overwrite
# 确认同步成功
kubectl -n order-demo-prod get externalsecret order-demo-db-credentials \
  -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'   # 期望：True
# 数据库侧：撤销旧密码的登录能力（PostgreSQL 操作见第 16 章有状态运维口径）
```

最后是复盘：把共享 SA 拆成按用途的专属 SA，`automountServiceAccountToken: false` 补齐到每个 SA 与 Pod 模板（见 §26.2.3 基线配置），确认审计策略完整覆盖 `secrets` 与 RBAC 对象，postmortem 归档并回填 §26.2.2 隔离失效表每一行的「由谁补偿、怎么验证」[R-26-11]。

**收权通过标准**：

| 判据 | 期望结果 |
|---|---|
| 证据链 | 事发窗口审计日志副本已固化，含主体、时间、objectRef、结果码 [R-26-4] |
| 权限 | `auth can-i --as=... get secrets` 在所有命名空间返回 `no`，无残留绑定 |
| token | 事发 token 的任何副本再请求均报 `401` |
| 凭据 | 所有被 `200` 读过的 Secret 内容已轮换，`ExternalSecret` 恢复 `Ready: True` |
| 复盘 | postmortem 归档，基线表与 `docs/tenant-isolation-checklist.md` 已更新 |

**`policies/rbac/order-demo-workload-identity.yaml`** —— 机器身份接入。Workload Identity / IRSA 一句话白话：让 Pod 用 Kubernetes 的 ServiceAccount 身份去云厂 IdP 换一张短期令牌，SDK 自动刷新，配置里不再出现长期 Access Key。下面以 AWS IRSA 为唯一示例，GCP Workload Identity 的等价 annotation 写在注释里，按云厂二选一填写 [R-26-8][R-26-1]。

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api
  namespace: order-demo-prod
  annotations:
    eks.amazonaws.com/role-arn: "arn:aws:iam::123456789012:role/order-demo-api"
    # GCP Workload Identity 改用下面一行，并把 GSA 绑定到该 KSA：
    # iam.gke.io/gcp-service-account: "order-demo-api@example-project.iam.gserviceaccount.com"
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: api
automountServiceAccountToken: false
```

> AWS SDK 通过 projected ServiceAccount token 与 OIDC 联合自动换取临时凭据，轮换与吊销由 IdP 承担；这正是反模式三的对立面。注意 `arn:aws:iam::123456789012:role/...` 是示例账号 ID，实际值由 IaC 注入（见第 30 章），不写进本章配置仓库的明文凭据。短期令牌的 TTL、信任策略与审计由云厂侧管理，本章只看「集群里有没有长期 Key」这一条判据 [R-26-8]。

上面配置里那句「SDK 自动换取」背后是一条四段信任链，值得拆开看清楚——因为**链上任何一环配错，故障表现都是同一个 403**，事先知道每一环在哪里、怎么验证，排障才不至于从头猜起 [R-26-8]：

1. **集群 Issuer**：托管集群控制面内置一个 OIDC 签发者，为每个 Pod 的 projected ServiceAccount token 签名，并对外公开发现文档（`/.well-known/openid-configuration`）与公钥集（JWKS）。以 AWS 为例，issuer 形如 `https://oidc.eks.cn-north-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE`（示例 ID，实际值由集群 IaC 产出）。
2. **云侧 IdP 注册**：在 IAM 里把上述 issuer URL 与根 CA 指纹注册为 OIDC identity provider——云厂从此「认识」这个集群。
3. **IAM Role 信任策略**：Role 的信任策略用 `Condition` 把 `sub` 钉死为 `system:serviceaccount:order-demo-prod:api`、`aud` 钉死为 `sts.amazonaws.com`。`sub` 同时包含命名空间与 SA 名，这是防冒用的关键：别的命名空间即使建一个同名 `api` SA，也换不出凭据 [R-26-8]。
4. **换发临时凭据**：Pod 内 SDK 用挂载的 token 调 `AssumeRoleWithWebIdentity`，换到一组带 TTL 的临时 AK / SK / session token（TTL 可缩到 15 分钟），到期自动换发。集群里全程不存在长期 Access Key（公理 9，见第 3 章）[R-26-1][R-26-9]。

| 环节 | 配置位置 | 断链后果 | 定位方法 |
|---|---|---|---|
| Issuer | 集群控制面 | 云厂不认识 token，换发被拒 | `aws iam list-open-id-connect-providers` 与集群 issuer URL 逐字比对 [R-26-8] |
| IdP 注册 | 云厂 IAM | issuer 或指纹不符即被拒 | 核对注册的 CA 指纹与 issuer |
| 信任策略 sub / aud | IAM Role 信任策略 | `AccessDenied`，但 token 本身有效 | 解开 token 的 JWT payload，把 `sub` / `aud` 与 Condition 逐字比对 |
| SA annotation | K8s SA（本节 `order-demo-workload-identity.yaml`） | SDK 不知道要换发，退回默认凭据链并失败 | `kubectl get sa api -o yaml` 看 `eks.amazonaws.com/role-arn` [R-26-8] |

**吊销演练**（演练不是事故，做完必须还原信任策略；步骤为演示用合成步骤，可复制执行）：

```bash
# 0) 演练前确认链路可用：手工模拟 SDK 的换发动作
TOKEN="$(kubectl -n order-demo-prod create token api --audience=sts.amazonaws.com --duration=900)"
aws sts assume-role-with-webidentity \
  --role-arn arn:aws:iam::123456789012:role/order-demo-api \
  --role-session-name revocation-drill \
  --web-identity-token "$TOKEN" > /tmp/drill-before.json   # 期望：返回临时凭据三件套

# 1) 第一把闸：改信任策略，把 sub 换成一个不存在的 SA（等效删除该条信任）
aws iam update-assume-role-policy --role-name order-demo-api --policy-document '{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Federated": "arn:aws:iam::123456789012:oidc-provider/oidc.eks.cn-north-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE"},
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "oidc.eks.cn-north-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE:sub": "system:serviceaccount:order-demo-prod:revoked",
        "oidc.eks.cn-north-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE:aud": "sts.amazonaws.com"
      }
    }
  }]
}'

# 2) 验证：新换发被拒
TOKEN2="$(kubectl -n order-demo-prod create token api --audience=sts.amazonaws.com --duration=900)"
aws sts assume-role-with-webidentity \
  --role-arn arn:aws:iam::123456789012:role/order-demo-api \
  --role-session-name revocation-drill-2 \
  --web-identity-token "$TOKEN2"    # 期望：AccessDenied，退出码非 0

# 3) 关键观察：演练 0) 换到的临时凭据在 TTL 内仍然可用——吊销只挡「新发」，不回收「存量」
#    用 /tmp/drill-before.json 里的凭据配置环境变量后执行，TTL 内仍成功：
aws sts get-caller-identity

# 4) 恢复信任策略（sub 改回 system:serviceaccount:order-demo-prod:api 后再验证换发重新成功）
aws iam update-assume-role-policy --role-name order-demo-api --policy-document file://trust-policy.json
```

第 3 步是本演练最重要的发现：**临时凭据的吊销语义是「不再新发」，不是「立即作废」**。补偿措施有两个：把换发 TTL 收到下限（15 分钟），把 Role 的权限边界收敛到该组件真正需要的最小集合——存量凭据即使被偷，可用窗口与杀伤半径都被压到最小 [R-26-1][R-26-9]。另外两把闸按影响面从小到大备用：删除挂载该 token 的 Pod（projected token 随 Pod 销毁失效 [R-26-5]）；轮换集群 OIDC 签发密钥（影响全集群所有 Workload Identity，只在确认集群级泄露时使用）。

审计留痕两侧都要看：云侧每次 `AssumeRoleWithWebIdentity` 换发（成功与被拒）都有云厂审计记录；集群侧 `kubectl create token` 对应 `serviceaccounts/token` 的 create 请求，本节的审计策略把它列为 RequestResponse，所以演练全程在两边都留有完整证据 [R-26-4][R-26-8]。

**演练通过标准**：第 0 步换发成功；第 2 步新换发返回 `AccessDenied`；第 3 步存量凭据在 TTL 内仍可用（证实吊销语义）；第 4 步恢复后换发重新成功；全程换发动作在云侧审计可查。

**服务账户令牌投影：audience、expirationSeconds 与三种令牌的对照。** 上面吊销演练用的 `kubectl create token` 是手工签发；Pod 里长期使用的令牌靠 projected ServiceAccount token 卷自动签发与换发。默认挂载的真正问题是「audience 太宽」：一张不限定 audience 的 token 对 API Server 全局有效，谁拿到都能拿去调 API Server——§26.2.2 合成案例里攻击者读出的正是这种 token。显式投影把 audience 收窄到唯一接收方 [R-26-5]：

```yaml
# 教学对照：IRSA webhook 为带 role-arn annotation 的 Pod 自动生成的等效投影。
# 前提：Pod 已设 automountServiceAccountToken: false，token 只经此投影发出。
apiVersion: v1
kind: Pod          # 以 Pod 为例；Deployment 中写入 spec.template.spec 同一位置
metadata:
  name: api
  namespace: order-demo-prod
spec:
  serviceAccountName: api
  automountServiceAccountToken: false
  containers:
    - name: api
      image: registry.example.com/order-demo/api:git-1a2b3c4
      volumeMounts:
        - name: sa-token
          mountPath: /var/run/secrets/tokens
          readOnly: true
  volumes:
    - name: sa-token
      projected:
        sources:
          - serviceAccountToken:
              audience: sts.amazonaws.com   # 只对持有该 audience 校验的接收方有效
              expirationSeconds: 3600       # 按下方判据表选取
              path: api-token
```

`audience` 的意义：接收方（云厂 STS、Vault 的 kubernetes auth 等）会校验 token 的 `aud` 声明与自己的注册值一致才接受；收窄后，这张 token 即使被偷走，也不能拿去调 API Server 或其他未注册 aud 的服务。**前提**：接收方必须真的校验 audience，否则收窄只是自我安慰——接入时把 `audience` 与接收方配置里的 audiences 逐字对齐。audience 配错的失败现场很固定：token 本身有效，但接收方返回 401 / `InvalidIdentityToken`（Vault 报 audience 不匹配，STS 报 `InvalidIdentityToken`），表现为「四段信任链表格」里 aud 断链的同款症状。三步定位：解开 JWT 看 `aud` 声明；与接收方注册的 audiences 逐字比对（大小写与结尾斜杠都会导致不等）；修正投影或接收方配置后重新签发验证 [R-26-5][R-26-8]。`expirationSeconds` 的判据：kubelet 在令牌用到约 80% 有效期（或超过 24 小时）时自动换发，Pod 无需重启 [R-26-5]：

| 取值 | 泄露后最大暴露窗口 | 适用前提 | 何时不该用 |
|---|---|---|---|
| 86400（默认） | 最长 1 天 | 接收方可信、网络面已收敛（见第 19 章） | 高敏感换发链路（如 STS）——窗口太长 |
| 3600 | 最长 1 小时 | 生产默认推荐 | 无 |
| 600（下限） | 最长 10 分钟 | 极高敏感或演练 | 接收方对 token 有超过有效期的缓存（换发跟不上校验） |

不再建议低于 600：TokenRequest API 对 projected token 的最短有效期为 600 秒，更小的值会被 API Server 拒绝 [R-26-5]。

三种令牌的对照，同时是「令牌泄露处置」的分诊表（完整取证与收权流程见 §26.2.2，此处不重复）[R-26-2][R-26-5][R-26-8]：

| 令牌类型 | 签发者 | 有效期 | 吊销方式 | 泄露处置强度 |
|---|---|---|---|---|
| legacy token Secret（`kubernetes.io/service-account-token`） | API Server | **永不过期** | 删除 Secret；必要时轮换集群签名密钥 | 按「永久泄露」处置：删 Secret + 轮换签名密钥，§26.2.2 第四步即为此设计 |
| bound projected token（本章推荐） | API Server | `expirationSeconds`（600s–1d），kubelet 自动换发 | 删除挂载它的 Pod 即失效 | 删 Pod；最坏暴露窗口就是 `expirationSeconds` |
| OIDC 联邦换发的云凭据（IRSA） | 云厂 STS | TTL（可收至 15 分钟） | 信任策略挡「新发」，TTL 了结「存量」（见 §26.2.3 吊销演练） | 改信任策略 + 等 TTL 过期 + 收敛 Role 权限边界 |

分诊的第一问永远是「它是哪一类」：legacy token 没有过期这回事，必须按永久泄露强度走；bound token 的最坏窗口就是 `expirationSeconds`——这正是把生产默认压到 3600 的理由；云凭据则交给 TTL 与信任策略。集群内不应残留 legacy token Secret，对应的合规基线见 CIS Kubernetes Benchmark 的 ServiceAccount 条目 [R-26-7]。

**`policies/rbac/externalsecret.yaml`** —— 动态凭据：沿用第 9 章的 Vault 路径 `order-demo/db-credentials`，`refreshInterval: 1h` 让 ESO 定期重拉；Vault 侧把数据库凭据配成动态、带 TTL，轮换不需要重建镜像（见第 9 章）[R-26-1][R-26-2]。

```yaml
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: order-demo-vault
  namespace: order-demo-dev
spec:
  provider:
    vault:
      server: "http://vault.vault.svc:8200"
      path: "secret"
      version: "v2"
      auth:
        kubernetes:
          mountPath: "kubernetes"
          role: "order-demo-api"
          serviceAccountRef:
            name: api
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: order-demo-db-credentials
  namespace: order-demo-dev
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: order-demo-vault
    kind: SecretStore
  target:
    name: order-demo-db-credentials
    creationPolicy: Owner
  data:
    - secretKey: username
      remoteRef:
        key: order-demo/db-credentials
        property: username
    - secretKey: password
      remoteRef:
        key: order-demo/db-credentials
        property: password
```

> K8s `Secret` 对象名不能含 `/`，故 `metadata.name` 用连字符；Vault 侧路径仍严格沿用第 9 章契约的 `order-demo/db-credentials`，两章口径因此一致。`refreshInterval` 与 Vault 动态凭据的 TTL 共同决定轮换节奏，两者都要短于凭据泄露后的可接受暴露窗口 [R-26-1][R-26-9]。

**`policies/rbac/audit-policy.yaml`** —— 审计策略。规则按「第一个匹配生效」排列：先丢弃高频噪声，再完整记录 Secret / RBAC 与工作负载变更，最后对只读请求记元数据 [R-26-4]。

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  - level: None
    resources:
      - group: ""
        resources: ["events"]
      - group: "coordination.k8s.io"
        resources: ["leases"]
  - level: RequestResponse
    resources:
      - group: ""
        resources: ["secrets", "serviceaccounts", "serviceaccounts/token"]
      - group: "rbac.authorization.k8s.io"
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
  - level: RequestResponse
    verbs: ["create", "update", "patch", "delete", "deletecollection"]
    resources:
      - group: "apps"
        resources: ["deployments", "statefulsets"]
      - group: ""
        resources: ["pods", "configmaps"]
  - level: Metadata
    verbs: ["get", "list", "watch"]
```

这份 `audit-policy.yaml` 能跑通，但要它真正在事故里救场，取决于两件容易做错的事：level 的取舍与规则的顺序。

四个 level 的语义与成本，选型的判据是「这路请求丢了什么证据会致命」[R-26-4]：

| level | 记什么 | 体积 | 用在哪 |
|---|---|---|---|
| `None` | 不记录 | — | 高频低价值噪声（events、leases），不记录它们正是为了别淹掉关键事件 |
| `Metadata` | 请求元数据 + 响应码 | 小 | 常规只读请求；**403 / 401 判定结果在这个 level 也留痕** |
| `Request` | 元数据 + 请求体 | 中 | 需要看「请求带了什么」但响应体太大（如大对象 list） |
| `RequestResponse` | 元数据 + 请求体 + 响应体 | 大 | Secret、RBAC、token 等高价值对象的全量留痕 |

两个常见误判。其一，以为 `Metadata` 级别「不够取证」：`forbidden` 是 API Server 的判定结果，写在响应的 `responseStatus` 里，`Metadata` 级也会记录——常规只读流量用 `Metadata` 兜底并不丢越权证据，丢的只是请求 / 响应体。其二，规则顺序排错：审计规则**第一个匹配生效，后面的全部短路**。合成一例：把上面的兜底 `Metadata` 规则误挪到文件最前面，`secrets` 的 `RequestResponse` 规则永远轮不到——日志照样在涨，没人发现异常，直到 §26.2.2 的取证时刻才发现在场证据只有元数据，无法回答「读到了什么内容」。排错判据只有一条：**专用规则在前、兜底在后**；每新增一条规则，就用一次 §26.2.5 的 `forbidden` 演练验证留痕级别。

必留痕事件清单，audit-policy 逐条对号 [R-26-4]：

| 事件 | 最低 level | 为什么必留 |
|---|---|---|
| `secrets` 的 get / list / watch 与全部写操作 | `RequestResponse` | 泄露取证要还原「读了什么」（§26.2.2 第三步靠 `code: 200` 计数） |
| RBAC 对象的全部写操作 | `RequestResponse` | 回答「谁改了权限」；§26.2.1 的 `escalate` 提权在审计里只表现为对 Role / ClusterRole 的写请求 |
| `serviceaccounts/token` 的 create（含 `kubectl create token`） | `RequestResponse` | 手工签发 token 是 §26.2.3 演练与攻击者冒用的共同入口 |
| `pods/exec`、`pods/attach` | `RequestResponse` | 容器内执行是最直接的现场破坏方式，必须与公理 8（SSH 禁入生产）对账 |
| `impersonate` 动词的请求 | `RequestResponse` | 冒充后审计 `user` 字段换成被冒充者，只有 impersonation 留痕能还原真实操作者 |
| 其余被拒请求（401 / 403） | `Metadata`（结果含于 responseStatus） | 免费的入侵检测信号（§26.2.1 用法二） |

针对这些事件的通用取证命令包（与 §26.2.2 针对单一 SA 的取证互补，按事件类型检索）：

```bash
# 1) 全部越权判定按主体聚合（对应基线表逐一对号；对不上的主体即展开 §26.2.2 处置）
docker exec order-demo-control-plane sh -c \
  "grep '\"forbidden\"' /var/log/kubernetes/audit.log" \
  | grep -o '"user":"system:serviceaccount:[^"]*"' | sort | uniq -c | sort -rn

# 2) 谁在变更权限：RBAC 写操作的操作者与对象（人的操作应紧跟在对应 Git PR 之后，公理 5）
docker exec order-demo-control-plane sh -c \

# 通过标准：level 为 Metadata 或 RequestResponse；若为 None，审计策略规则顺序已排错
```

### 26.2.4 本书观点：SSH 禁入生产

> **本书观点（本章第 2 条结论，不需要外部背书）**
>
> **主张**：**SSH 禁入生产**——排障走可观测与 runbook，不登机器。这是全书公理 8（见第 3 章），本章把它落到权限与凭据层。
>
> **论证**：允许 SSH 登生产节点，等于同时破坏了三条已经建好的护栏：其一，任何手工 `kubectl edit` / 改文件都无法被 GitOps 的漂移检测纠正（见第 14 章）；其二，节点上的 kubelet 凭据、容器运行时 socket 与临时文件都暴露给登录者，最小 RBAC 与审计留痕形同虚设；其三，登录行为本身几乎没有结构化审计，「谁在什么时候改了什么」无法回答。反过来，把排障入口收敛到指标、日志、链路与 runbook（见第 21、22、23 章），每一次处置都会自然留下可复查的记录，也更接近「可回滚、可审计」的目标。SRE 类著作对「以可观测与自动化替代登机操作」有长期讨论，但本结论的论证不依赖它背书 [R-26-10]。
>
> **反例与适用前提**：这不等于「任何时候都不允许任何人接触节点」。集群初始安装、内核级故障取证、云厂硬件故障排查确实可能需要带外访问，但那是**受控的、有工单与到期时间的 break-glass 流程**，不是日常排障通道，且必须写入例外登记（模板见第 25 章 `docs/policy-exception.md`）。另一个反例是本地 kind 与开发环境：本章的禁令只针对 `order-demo-prod`，本地集群用 `docker exec` 查审计日志正是本书验证命令的一部分，不构成对公理的例外。第 23 章的现场处置给出了「不登机器也能定位并止血」的完整 runbook 集合。

观点块里说 break-glass 是「受控的、有工单与到期时间的流程」，这句话要有实物才成立。工单模板放在 `docs/break-glass-ticket.md`，与第 25 章的例外登记一一对应：

```markdown
# Break-glass 带外访问工单（BG-YYYYMMDD-NNN）

- 申请人 / 审批人：<不得为同一人；审批人为当班 SRE 负责人>
- 集群与范围：order-demo-prod / <具体节点或控制面组件>
- 事由：<内核级故障取证 / 云厂硬件排查；说明为什么 runbook 与可观测栈不够用>
- 触碰的公理与例外性质：公理 8 的登记例外（见第 3 章），有效期以本工单到期时间为准
- 授权对象：临时 RoleBinding `bg-<工单号>`，绑定最小 Role（如仅 `nodes/proxy` 的 `get`），不得 cluster-admin
- 生效 / 到期（UTC）：2026-11-11T10:00Z → 2026-11-11T14:00Z（最长 4 小时，到期由回收器自动删除）
- 全程留痕：K8s 审计日志 + 终端会话录制；使用期间的每次 token create 均入审计 [R-26-4]
- 收尾义务：到期后 24 小时内归档复盘，并同步更新第 25 章例外登记
- 状态：OPEN / EXPIRED / REVOKED
```

到期自动回收不靠人的记性，靠一个每小时的 CronJob：扫描带 `order-demo.io/break-glass=true` 标签的 RoleBinding，注释里的到期时间（UTC）一过即删。回收器自身不带该标签，避免被自己回收 [R-26-3][R-26-4]：

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: break-glass-reaper
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
automountServiceAccountToken: true   # 回收器是集群内唯一显式开 token 的工作负载，Role 只给到 rolebindings
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: break-glass-reaper
  namespace: order-demo-prod
rules:
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["rolebindings"]
    verbs: ["get", "list", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: break-glass-reaper
  namespace: order-demo-prod
subjects:
  - kind: ServiceAccount
    name: break-glass-reaper
    namespace: order-demo-prod
roleRef:
  kind: Role
  name: break-glass-reaper
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: break-glass-reaper
  namespace: order-demo-prod
spec:
  schedule: "0 * * * *"          # 每小时整点回收，到期授权的最大残留窗口为 1 小时
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: break-glass-reaper
          restartPolicy: OnFailure
          containers:
            - name: reaper
              image: registry.k8s.io/kubectl:v1.32.0   # 版本钉死，不用 latest（公理 2）
              command: ["/bin/sh", "-c"]
              args:
                - |
                  set -eu
                  NOW="$(date -u +%s)"
                  for rb in $(kubectl -n order-demo-prod get rolebindings \
                        -l order-demo.io/break-glass=true -o name); do
                    EXP="$(kubectl -n order-demo-prod get "$rb" \
                      -o jsonpath='{.metadata.annotations.order-demo\.io/expires-at}')"
                    if [ "$(date -u -d "$EXP" +%s)" -lt "$NOW" ]; then
                      kubectl -n order-demo-prod delete "$rb"
                      echo "expired break-glass binding removed: $rb"
                    fi
                  done
```

验证回收器（人工造一个已到期的测试绑定，等下一个整点）：

```bash
# 造一个已到期的测试绑定（测试 Role 与生产工单的授权对象无关，仅用于演练）
kubectl -n order-demo-prod create role bg-drill-role --verb=get --resource=configmaps
kubectl -n order-demo-prod create rolebinding bg-drill --role=bg-drill-role \
  --serviceaccount=order-demo-prod:api
kubectl -n order-demo-prod annotate rolebinding bg-drill \

kubectl -n order-demo-prod get rolebinding bg-drill    # 期望：NotFound
```

回收器的 delete 事件本身也进审计日志，与工单、例外登记一起构成「谁收的权、什么时候收的」三方对账。任何一次 break-glass 的使用（token create、RoleBinding create、被授权对象发出的每一笔请求）都在审计里，这就是公理 8 允许带外访问、却仍要求全程可审计的落点。

### 26.2.5 验证与回滚

**验证命令**（仓库根目录；集群按 `hack/kind-audit.yaml` 起来后执行）：

```bash
kubectl apply -f deploy/base/serviceaccount.yaml
kubectl apply -f policies/rbac/order-demo-api-role.yaml
kubectl apply -f policies/rbac/externalsecret.yaml
kubectl apply -f policies/rbac/order-demo-workload-identity.yaml

APISERVER="$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')"

docker exec order-demo-control-plane \

docker exec order-demo-control-plane \
  grep 'system:serviceaccount:order-demo-dev:api' /var/log/kubernetes/audit.log | tail -n 3

# 4) SA 与隔离基线
kubectl -n order-demo-dev get sa api \
  -o jsonpath='{.automountServiceAccountToken}{"\n"}'
kubectl -n order-demo-prod get sa api -o yaml
kubectl -n order-demo-prod get networkpolicy
kubectl -n order-demo-dev get role,rolebinding order-demo-api
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 越权读 Secret | `auth can-i ... get secrets` 返回 `no`；真实 token 请求报 `forbidden` |
| 合法读 ConfigMap | `auth can-i ... get configmap/order-demo-config` 返回 `yes` |
| 审计留痕 | 日志里能同时查到 `forbidden` 与 `system:serviceaccount:order-demo-dev:api`，且含 `secrets` 的 objectRef |
| SA 加固 | `automountServiceAccountToken` 为 `false`，三个 SA 均无 `cluster-admin` 绑定 |
| 动态凭据 | `ExternalSecret` 状态 `SecretSynced`，Vault 路径为 `order-demo/db-credentials`，仓库内无明文 Key |
| 机器身份 | prod 的 `api` SA 带 `eks.amazonaws.com/role-arn` annotation，无长期 Access Key |
| 生产无 SSH | `order-demo-prod` 存在默认拒绝 NetworkPolicy；无 `pods/exec` 到节点的通道（见第 23、19 章） |

第 2 步与第 3 步构成「越权被 RBAC 拒绝并留审计」的完整证据链：`auth can-i` 是判定能力的快速检查，真实 token 请求才是让 API Server 真正写下 `forbidden` 审计事件的动作 [R-26-3][R-26-4]。

**回滚 / 降级命令与步骤**。权限收紧出问题（如某组件因缺权限起不来）时，先回到上一个已知良好版本，再登记例外；**不要直接给 `cluster-admin` 止血**：

```bash
# 1) 取上一个 tag 的 RBAC 基线并应用（可复制执行，见附录 D 的 tag 命名）

kubectl apply -f /tmp/prev-api-role.yaml

# 2) 应急临时授权：写入例外登记，带到期时间，绝不写 cluster-admin
kubectl -n order-demo-dev describe pod <起不来的 Pod 名>
printf '%s\n' "date=$(date -u +%F) reason=rbac-rollback sha=$(git rev-parse --short=7 HEAD) expires=$(date -u -d '+2 days' +%F)" \
  >> docs/tenant-isolation-checklist.md
git add docs/tenant-isolation-checklist.md policies/rbac/order-demo-api-role.yaml
git commit -m "chore(rbac): temporary least-privilege exception with expiry"

# 3) 正式回退：撤销本次变更，回到 Git 声明
git revert HEAD
kubectl apply -f policies/rbac/order-demo-api-role.yaml
```

> 生产变更必须回到 Git（公理 5，见第 3 章）。`kubectl apply` 在这里是把「Git 里已回退的声明」重新同步到集群，不是绕过 GitOps 的手工改动；`order-demo-prod` 的实际收敛仍由 Argo CD 3.x 完成（见第 14 章）。
