## 13.1 问题与反模式：想回滚，却没有回滚方案

前十二章解决了「产物是什么、怎么唯一地造出来」。从这一章起，产物要开始在生产承载真实流量——这是**发布**（让某个版本的制品在生产开始承载真实流量，并可按预案退出，正式定义见第 1 章原则、本章展开）第一次成为一章的主角。第 1 章事故里最贵的那一分钟，就发生在这一环。

**合成案例**（基于多起公开事故的合成，非真实事件）：订单服务要上线一个新版本，把订单金额字段从 `amount` 拆成 `amount_cents` 与 `currency`，发版通知里写着「出问题就回滚」。发布十分钟后 5xx 开始上升，值班同学真正动手时连撞三堵墙：第一，没人写下上一版的镜像 SHA 和回退命令，`kubectl rollout history deployment/gateway` 里最近的几个修订混着上周改探针、改环境变量的记录，`--to-revision` 该填几没人敢定；第二，硬着头皮 `kubectl rollout undo` 退回上一个修订后，旧代码读不到已经被 `ALTER TABLE DROP COLUMN` 改掉的表结构，报错比发布前更密集；第三，数据库迁移是单向的，数据已经写成了新格式，退回去也没有旧数据可读。最后的处置是「赶紧修一下再发一版」——而按本书口径，**把回滚说成「修一下再发一版」是明令禁止的误用**（见术语表）。这次故障持续了远超过「切一次流量」的时间 [R-13-5][R-13-9]。

三个反模式：

**反模式一：「先发再说，坏了就回滚」，但从未演练过回滚。** 现象是故障时找不到命令、权限不够、或者 `undo` 之后服务更糟；根因是把「回滚」当成一个随时可用的动作，而不是一份**先于发布就写好、并演练过**的方案。替代做法是发布门禁强制要求一条回滚演练记录：有明确目标产物、有命令、有时限、有验证结果、有责任人，缺一项就阻断发布 [R-13-7][R-13-9]。

**反模式二：`maxUnavailable: 0` + `maxSurge: 1` 看起来最稳，却没算节点余量。** 现象是滚动更新卡在 `Progressing=False`，新 Pod 一直 `Pending`，`Available` 副本数掉不下来也上不去；根因是「零不可用」需要额外先起一个 Pod，而集群里没有那一个人的可分配资源。替代做法是在发布前把容量账算成一张表，用数字而不是直觉回答「峰值需要几个 Pod、节点还剩多少」[R-13-1][R-13-2]。这与第 8 章 H3「新 Pod 永远不 Ready」是同一族问题的容量那一半。

**反模式三：蓝绿切流后立刻把旧版本删掉。** 现象是切流五分钟后发现问题，回退时旧 ReplicaSet 已被清理，没有回退目标；根因是把「切换完成」当成了「发布结束」。替代做法是保留旧版本到观察窗口结束，窗口长度由错误预算与业务风险决定（见第 20 章），而不是由部署脚本的清理步骤决定 [R-13-5]。

还有最隐蔽的一条：**schema 不兼容时，应用层的回滚是假回滚**。上面案例里第二、三堵墙都不是 Kubernetes 的问题，而是数据格式已经不允许新旧版本共存。它无法靠选一种更聪明的部署策略解决，只能靠第 16 章的 expand–contract 迁移范式；本章在 13.2 把它作为「本书观点」显式立为边界。以上反模式的**方法论**参照公开发布 / 回滚失败事故复盘 [R-13-9]；该来源只支撑「这类失效模式确实存在」，不证明合成案例真实发生。

## 13.2 范式与决策树：容量账、回退速度与一份算数的回滚方案

本章要回答的决策问题是：**在「容量有限、必须可回退」的约束下，一次发布该选哪种策略，回滚方案怎么写才算数？**

先把本章的正式定义落到可验证的形态。**回滚**（把线上恢复到上一个已知良好版本，必须先有方案再有发布）不是一条命令，而是一份六要素文档：触发条件、目标产物（明确到 `git-<sha7>`）、执行命令、完成时限、验证方式、责任人。缺任何一项，「我们会回滚」都不算一份方案。这是全书公理 6「回滚方案先行」在本章的可执行版本 [R-13-7][R-13-8]。

**策略选型矩阵**（本章主矩阵，列含「何时不该用」）：

| 策略 | 容量成本 | 回退速度 | 流量控制粒度 | 适用前提 | 何时不该用 | 回滚命令 |
|---|---|---|---|---|---|---|
| 滚动更新 RollingUpdate | 低，峰值 `replicas + maxSurge` | 慢，需再滚一次 | 无，按比例自然替换 | 新旧版本可共存、schema 兼容、有节点余量 | 需要秒级整体回退；新旧版本不能共存；节点余量不足 | `kubectl rollout undo` 或明确 SHA 回退（见 13.5） |
| 蓝绿 Blue/Green | 高，约双倍副本与资源 | 快，切一次 Service selector | 全量或零，无中间态 | 有双倍容量、无长连接粘滞、schema 兼容 | 没有双倍容量；有状态会话无法整体切换；成本敏感 | 把 `gateway` Service 的 selector 切回 `version=<旧sha7>` |
| 金丝雀 Canary | 中，少量额外副本 | 中，取决于放量台阶 | 按请求比例 / 按副本比例 | 有用户可感的指标可判定、愿意接受分批时长 | 没有 SLI 与判定指标；只想「手动分批看看」 | 见 13.5；自动回滚见第 15 章 |

> 关于第三行的术语：**渐进式交付**在这条矩阵里第一次出现，它的白话是「先给一小部分流量，指标没问题再继续」（详见第 15 章正式定义）。本章只用它标注「金丝雀这一格最终由哪一章实现」，**不拿它当推理前提**；按概念梯度，它的正式定义在第 15 章，本章不越界展开。同理，蓝绿与金丝雀的经典定义分别来自 [R-13-5][R-13-6]，本书不改写其含义，只补上容量与回滚这两列。

**容量计算表**（`api` 组件，配置契约基线：requests `cpu: 100m, memory: 128Mi`；limits `cpu: 500m, memory: 256Mi`；调度按 requests 计）。设单节点可分配余量为 `cpu: 800m, memory: 2Gi`，这是示例值，真实数值须按节点规格校准（见一致性备注）。

| 场景 | 副本数 | maxSurge | maxUnavailable | 峰值 Pod 数 | 最少可用 Pod | 峰值 requests（cpu / mem） | 节点余量是否够 | 结论 |
|---|---|---|---|---|---|---|---|---|
| A 默认滚动 | 4 | 1 | 0 | 5 | 4 | `500m / 640Mi` | 够 | 可发布，仍有 1 个 Pod 的零不可用保障 |
| B 高峰余量紧张 | 4 | 1 | 0 | 5 | 4 | `500m / 640Mi` | 余量仅 `300m`，**不够** | 新 Pod `Pending`，rollout 卡死；降 surge 或先扩容 |
| C 允许少量不可用 | 4 | 0 | 1 | 4 | 3 | `400m / 512Mi` | 够 | 不额外占容量，但发布窗口内少一个可用副本 |
| D 激进 | 4 | 2 | 1 | 6 | 3 | `600m / 768Mi` | 不够 | 峰值 6 个 Pod，节点余量不足且可用数掉到 3 |

容量账的公式只有三条，但必须逐条算，不能凭「参数看起来保守」就放行 [R-13-1]：

1. 峰值 Pod 数 = `replicas + maxSurge`（百分比时向上取整），这是调度器要同时放下的数量；
2. 最少可用 Pod 数 = `replicas − maxUnavailable`，这是发布期间服务能力的下限，要与 `PodDisruptionBudget` 的 `minAvailable` 对齐，否则 PDB 会在驱逐时反过来把 rollout 卡住 [R-13-2]；
3. `maxSurge` 与 `maxUnavailable` 不能同时为 0，否则既不允许新建也不允许销毁，更新无法推进。

场景 B 正是反模式二的数字版：参数一个字没改，只是集群余量从 `800m` 掉到 `300m`，`"maxUnavailable": 0` 就从「最稳」变成「卡死」。所以 `progressDeadlineSeconds` 必须设，它是「卡住多久判定失败」的显式上限 [R-13-1]。

**决策树**：

```
这次发布改动了数据格式 / schema 吗？        是 → 先做第 16 章 expand–contract，
        │                                      否则任何策略的回滚都是假回滚
        │ 否
有可测量的用户可感指标（错误率 / 延迟分位）吗？ 否 → 不要选金丝雀，先补 SLI（见第 20 章）
        │ 是
需要秒级整体回退且有双倍容量吗？            是 → 蓝绿（保留旧版本到观察窗口结束）
        │ 否
需要按指标决定继续还是自动回退吗？          是 → 金丝雀 / 渐进式交付（详见第 15 章）
        │ 否
→ 滚动更新（默认）：先填容量计算表，再写回滚方案，两者都通过才允许发布
```

**零停机前提**：滚动更新期间连续请求零 5xx，依赖第 8 章的探针与优雅上下线四条件。**本章只引用、不重述**，措辞以第 8 章为准（见章末备注）；验证侧用 [R-13-4][R-13-2] 支撑。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：数据 schema 不兼容时，应用层的回滚是假回滚；策略选型救不了数据，只有让新旧版本在同一 schema 上共存才保得住回滚能力。
>
> **论证**：回滚的定义要求「恢复到上一个已知良好版本」，而一个版本是否「良好」，取决于它能否正确读写当下的数据。若发布同时执行了破坏性 DDL（如 `DROP COLUMN`、改字段类型、拆分字段），旧版本启动后面对的是它从未见过的数据形状，于是「镜像退回去了、服务却没回来」。此时三种策略的差别只剩「多快发现这件事」：滚动要再滚一次，蓝绿切回去照样报错，金丝雀只让一小部分请求先报错。三者都作用在「哪个 Pod 承载流量」这一层，无法改变「数据长什么样」。可回退性因此不是发布策略的属性，而是**数据变更设计**的属性。
>
> **反例与适用前提**：这不等于「任何涉及数据库的发布都必须做四阶段迁移」。纯新增可空列、只加索引、只写不改的追加式变更，本身就是向后兼容的，旧版本无视新列即可，直接滚动更新是合理的。前提是团队能证明「旧版本在新 schema 上可服务」——这条证明由第 16 章的 expand → 双写 → 回填 → contract 四阶段及其共存验证给出，本章只声明边界、不实现迁移。跳过此步的典型代价就是 13.1 合成案例里的第二、三堵墙；自动回滚也覆盖不了这一半，见第 15 章。

## 13.3 工具选型：本章的实现只有原生 Kubernetes

第 13 章是**策略层**，不引入新的交付控制器。按 `book/decisions.md`，渐进式交付控制器（Argo Rollouts 1.x 及其 Gateway API traffic router 插件）是第 15 章的唯一示例实现，本章只把它列在矩阵里作预告 [R-13-3]；GitOps 引擎（Argo CD 2.x）属于第 14 章，负责「变更怎么进集群」，与本章「一次发布选哪种策略」不重叠（SP-04）。本章的唯一示例实现是自第 6 章沿用下来的原生 Kubernetes 清单：`Deployment` 的 `RollingUpdate` 策略，加上蓝绿路径里对 `Service` selector 的一次声明式改写。

| 工具 / 实现（主版本） | 提供什么 | 接入成本 | 与第 14 章晋升链路的衔接 | 回滚方式 | 何时不该用 |
|---|---|---|---|---|---|
| 原生 `Deployment` 滚动（Kubernetes 1.32+，示例实现） | `maxSurge` / `maxUnavailable` / `progressDeadlineSeconds` | 零，仅一个 Kustomize patch | 清单由 Git 声明、控制器同步 | `rollout undo` 或明确 SHA 回退 | 需要按流量比例分批、或需要秒级整体回退时 |
| 蓝绿：`Service` selector 切换脚本（示例实现） | 双版本并存 + 一次性切流 | 低，一份切换脚本 + 两套 Deployment 模板 | 同上，切流也是一次 Git 提交 | selector 切回旧 `version` 标签 | 没有双倍容量；有长连接 / 会话粘滞；成本敏感 |
| Argo Rollouts 1.x | 金丝雀台阶、指标分析、自动回滚 | 中，需装 CRD 与控制器 | 由第 14 章同步 Rollout 清单 | `argo rollouts abort` / 自动回滚 | 没有 SLI 与判定指标、或只想手工分批时（详见第 15 章） |
| Flagger 1.x | 与 Rollouts 同族的金丝雀自动化 | 中高，另一套 CRD 与指标接入 | 同上 | 自动回滚 | 已选 Argo Rollouts 1.x 时不该再叠一套（见第 5 章过度工程警戒线） |
| Istio 1.x（流量层，仅对比） | 细粒度流量切分 | 高，服务网格运维成本 | 与第 19 章选型相关 | 改 `VirtualService` 权重 | 只需按副本比例灰度、不愿承担网格成本时（详见第 15、19 章） |

**最小接入 diff**（相对第 6 章基线、第 10 章起的 Kustomize 5.x overlay）：

```diff
+ deploy/overlays/prod/rolling-strategy.yaml   # 显式声明 maxSurge / maxUnavailable / progressDeadlineSeconds
+ deploy/bluegreen/gateway-blue.yaml            # 旧版本 Deployment，version=git-<旧sha7>
+ deploy/bluegreen/gateway-green.yaml           # 新版本 Deployment，version=git-<新sha7>
+ deploy/bluegreen/switch.sh                    # 只改 gateway Service 的 selector
+ docs/rollback-plan.md                         # 六要素回滚方案模板
+ hack/rollback-drill.sh                        # staging 演练脚本
```

**升级 / 回滚路径**：策略参数的每次调整都是一次 PR，走第 14 章的晋升链路；回滚就是 `git revert` 这个 PR，由控制器把 `maxSurge` 等字段同步回上一版。这里刻意不让任何人用 `kubectl edit` 改 `Deployment` 的 `strategy` 字段——那会同时制造漂移（白话：集群实际状态和 Git 里写的不一致，详见第 14 章）和一笔无法复盘的发布记录。工具版本方面：本章不新增控制器，Kubernetes 适用版本 1.32+，小版本与 `kustomize` / `kubectl` 版本锁在附录 A。

## 13.4 落地配置（完整可应用文件，Kubernetes 1.32+）

> 全部字段沿用 `book/case-evolution.md` 配置契约：命名空间 `order-demo-prod` / `order-demo-staging`、Service 名 `gateway`、端口 8080、镜像 `registry.example.com/order-demo/gateway:git-<sha7>`、公共标签 `app.kubernetes.io/name=order-demo` / `app.kubernetes.io/component=gateway` / `version=git-<sha7>` / `app.kubernetes.io/managed-by=kustomize`（第 10 章起为 `kustomize`，第 14 章起改为 `argocd`）、探针 `/healthz` 与 `/readyz`、`terminationGracePeriodSeconds: 30` + `preStop` 先摘流。示例 SHA：旧版 `git-1a2b3c4`、新版 `git-5d6e7f8`，脚本会用真实短 SHA 替换。

**`deploy/overlays/prod/rolling-strategy.yaml`** —— Kustomize strategic merge patch，只改策略字段，不改镜像与标签。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway
  namespace: order-demo-prod
spec:
  replicas: 4
  progressDeadlineSeconds: 300
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  minReadySeconds: 10
  revisionHistoryLimit: 10
  template:
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: gateway
          image: registry.example.com/order-demo/gateway:git-5d6e7f8
          imagePullPolicy: IfNotPresent
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 5"]
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            initialDelaySeconds: 3
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 10
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 128Mi
```

> `revisionHistoryLimit: 10` 是 `rollout undo` 的前提：它依赖 ReplicaSet 历史 [R-13-1]。`minReadySeconds: 10` 让新 Pod 稳定 10 秒才计入 Available，避免 Ready 抖动被当成成功 [R-13-4]。

**`deploy/overlays/prod/pdb.yaml`** —— 与容量账对齐，防止 PDB 在发布期反过来卡住驱逐。

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: gateway
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
```

> `replicas: 4` + `maxUnavailable: 0` 的最少可用是 4，`minAvailable: 3` 留出一个自愿驱逐的余量，二者不冲突。若把 `minAvailable` 设成 4，节点排水时 PDB 会挡住驱逐，滚动更新与节点维护会互相顶住 [R-13-2]。

**`deploy/bluegreen/gateway-blue.yaml`** —— 旧版本，保持服务中，观察窗口结束前不删。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway-blue
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: kustomize
spec:
  replicas: 4
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
      version: git-1a2b3c4
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: gateway
        version: git-1a2b3c4
        app.kubernetes.io/managed-by: kustomize
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: gateway
          image: registry.example.com/order-demo/gateway:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 5"]
          readinessProbe:
            httpGet: { path: /readyz, port: 8080 }
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 10
            periodSeconds: 10
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
```

**`deploy/bluegreen/gateway-green.yaml`** —— 新版本，除 `version` 与 `image` 外与旧版逐字相同（保证「只换产物」）。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway-green
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
```

**`deploy/bluegreen/switch.sh`** —— 一次性切流，参数只允许两个已知 SHA，防止把流量切到不存在的版本。

```bash
#!/usr/bin/env bash
set -euo pipefail

NS=order-demo-prod
SVC=gateway
OLD=git-1a2b3c4
NEW=git-5d6e7f8
TARGET="${1:-}"

case "${TARGET}" in
  green|"${NEW}") SELECTOR="${NEW}" ;;
  blue|"${OLD}")  SELECTOR="${OLD}" ;;
  *) echo "用法: $0 green|blue（只允许切到 ${OLD} 或 ${NEW}）" >&2; exit 2 ;;
esac

# 前置：目标版本必须真的有 Ready 副本，否则拒绝切流
READY="$(kubectl -n "${NS}" get deploy \
  -l "app.kubernetes.io/component=gateway,version=${SELECTOR}" \
  -o jsonpath='{.items[*].status.readyReplicas}' | tr ' ' '\n' | awk '{s+=$1} END {print s+0}')"
[ "${READY}" -ge 4 ] || {
  echo "目标版本 ${SELECTOR} 的 Ready 副本为 ${READY}，不足 4，拒绝切流" >&2; exit 1;
}

kubectl -n "${NS}" patch svc "${SVC}" --type=merge -p \
  "{\"spec\":{\"selector\":{\"app.kubernetes.io/name\":\"order-demo\",\"app.kubernetes.io/component\":\"gateway\",\"version\":\"${SELECTOR}\"}}}"

echo "已切到 ${SELECTOR}；旧版本 Deployment 保留至观察窗口结束，切勿立即删除。"
kubectl -n "${NS}" get svc "${SVC}" -o jsonpath='{.spec.selector.version}{"\n"}'
```

> 生产环境里这个脚本不应由人直接执行：它只是把「切流」表达成一次可审查的状态变更，真正落地时应把等价的 selector 改动写进 Git，由第 14 章的控制器同步（全书公理 5，见第 3 章）。脚本放在这里是为了让 13.5 的演练可复制执行。

**`hack/rollback-drill.sh`** —— staging 演练脚本，同时演示两种回退路径。

```bash
#!/usr/bin/env bash
set -euo pipefail

NS=order-demo-staging
DEPLOY=gateway
STABLE="$(kubectl -n "${NS}" get deploy "${DEPLOY}" \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
CANDIDATE="registry.example.com/order-demo/gateway:git-0000000"
REPORT="/tmp/rollback-drill-$(date +%Y%m%d%H%M%S).log"

log() { echo "[$(date -u +%FT%TZ)] $*" | tee -a "${REPORT}"; }

log "稳定版本: ${STABLE}"

# 制造一个「新版本」并等待它就绪，让 ReplicaSet 历史里有可退的修订
kubectl -n "${NS}" set image "deployment/${DEPLOY}" gateway="${CANDIDATE}"
kubectl -n "${NS}" rollout status "deployment/${DEPLOY}" --timeout=120s || true
log "已发布候选版本: ${CANDIDATE}"

REV="$(kubectl -n "${NS}" rollout history "deployment/${DEPLOY}" \
  | tail -n2 | head -n1 | awk '{print $1}')"
log "待回退修订号: ${REV}"

# 路径 A：按历史修订回退（演练用）
START=$(date +%s)
kubectl -n "${NS}" rollout undo "deployment/${DEPLOY}" --to-revision="${REV}"
kubectl -n "${NS}" rollout status "deployment/${DEPLOY}" --timeout=120s
log "路径 A 完成，耗时 $(( $(date +%s) - START ))s"

# 路径 B：明确 SHA 回退（推荐用于明确目标产物）
kubectl -n "${NS}" set image "deployment/${DEPLOY}" gateway="${STABLE}"
kubectl -n "${NS}" rollout status "deployment/${DEPLOY}" --timeout=120s
log "路径 B 完成，目标产物: ${STABLE}"

# 验证
IMAGE="$(kubectl -n "${NS}" get deploy "${DEPLOY}" \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
[ "${IMAGE}" = "${STABLE}" ] || { log "失败：image 未回到稳定版本"; exit 1; }
kubectl -n "${NS}" port-forward "svc/${DEPLOY}" 18080:8080 >/dev/null 2>&1 &
PF=$!
trap 'kill "${PF}" 2>/dev/null || true' EXIT
for i in $(seq 1 30); do
  curl -fsS http://127.0.0.1:18080/healthz >/dev/null 2>&1 && break
  sleep 1
done
curl -fsS http://127.0.0.1:18080/healthz | tee -a "${REPORT}"
log "演练通过，报告: ${REPORT}"
```

**验证命令**（仓库根目录，需 `kubectl` / `kustomize` / `kind` / `curl`，版本见附录 A）：

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 容量账有余量 | 13.2 计算表「节点余量是否够」为「够」；峰值 Pod 数 ≤ 节点可放下的数量 |
| 零停机 | `hack/rolling-5xx-test.sh` 在滚动期间连续请求**零 5xx**；`/healthz` 与 `/readyz` 全程可用 [R-13-4] |
| 回滚演练通过 | `hack/rollback-drill.sh` 在 120s 内完成两条路径，`image` 回到稳定 SHA，`/healthz` 为 200，有报告输出 |
| 旧版本保留 | 蓝绿路径 `kubectl -n order-demo-prod get deploy` 中 `gateway-blue` 仍存在，副本数非 0 |
| PDB 不打架 | `kubectl -n order-demo-prod get pdb gateway` 的 `ALLOWED DISRUPTIONS` ≥ 1 [R-13-2] |
| 参数有上限 | `progressDeadlineSeconds: 300` 与 `revisionHistoryLimit: 10` 已生效 [R-13-1] |
| 回滚方案成文 | `docs/rollback-plan.md` 六要素齐全且附本次演练记录，否则**禁止发布**（CL-G-07） |

**回滚命令 / 步骤**。先讲清两种回退的区别，这是 H5 最核心的一条：

`kubectl rollout undo` 回退的是 **Deployment 的整个 Pod 模板的上一个修订**，不是「把镜像换回去」。若上一个修订之后还改过探针、环境变量、资源 requests 或 `preStop`，它们会被一起退回；它还依赖 ReplicaSet 历史（`revisionHistoryLimit`），历史被清理或修订号辨认不清时就会失效。第 6 章在本地 kind 里用它做演练，是为了让读者看清字段变化，不代表生产应依赖它 [R-13-1]。

**明确 SHA 回退**精确表达「恢复到上一个已知良好产物」：`git-<sha7>` 可反查唯一提交、可复现、可写进 `docs/rollback-plan.md` 的目标产物栏；而生产环境里这个动作必须回到 Git 声明（改 overlay 的 image 字段 → 提交 PR → 第 14 章控制器同步），不能由人 `kubectl set image`（全书公理 5，见第 3 章）。因此结论是：**演练用 `undo`，生产用明确 SHA + Git**。

```bash
# 路径 A：滚动更新，按历史修订回退（仅演练 / 一次性集群）
REV="$(kubectl -n order-demo-prod rollout history deployment/gateway \
  | tail -n2 | head -n1 | awk '{print $1}')"
kubectl -n order-demo-prod rollout undo deployment/gateway --to-revision="${REV}"
kubectl -n order-demo-prod rollout status deployment/gateway --timeout=120s

# 路径 B：滚动更新，明确 SHA 回退（本地 kind 演练形态）
OLD="<上一个已验证的 sha7>"
kubectl -n order-demo-prod set image deployment/gateway \
  gateway="registry.example.com/order-demo/gateway:git-${OLD}"
kubectl -n order-demo-prod rollout status deployment/gateway --timeout=120s

# 路径 C：生产唯一合法路径 —— 回到 Git，由第 14 章控制器同步
OLD="<上一个已验证的 sha7>"
(
  cd deploy/overlays/prod
  kustomize edit set image \
    "registry.example.com/order-demo/gateway=registry.example.com/order-demo/gateway:git-${OLD}"
)
git add deploy/overlays/prod && git commit -m "rollback(order-demo): gateway -> git-${OLD}"
git push origin main
# 不在此处执行任何 kubectl 写命令；由 Argo CD 2.x 同步并留下 PR 审计

# 路径 D：蓝绿回退 —— 把 gateway Service 的 selector 切回旧 version
./deploy/bluegreen/switch.sh blue

# 路径 E：金丝雀的自动回滚见第 15 章（AnalysisTemplate 判定失败即回退）
```

> 路径 D 之所以快，是因为旧版本一直在线；这也解释了反模式三为何让蓝绿优势归零。路径 A/B 只用于一次性集群，路径 C 才是生产。若牵涉 schema，以上五条路径都只完成「应用侧回退」，数据侧必须按 13.2「本书观点」与第 16 章处理。

**回滚验证**：

```bash
kubectl -n order-demo-prod get deploy gateway -o jsonpath='{..image}{"\n"}'
kubectl -n order-demo-prod get deploy gateway \
  -o jsonpath='{.status.availableReplicas}{"\n"}'
kubectl -n order-demo-prod get svc gateway -o jsonpath='{.spec.selector.version}{"\n"}'
./hack/verify.sh
kubectl -n order-demo-prod rollout history deployment/gateway
```

通过标准：`image` 为 `git-<OLD>` 且与 `docs/rollback-plan.md` 的目标产物一致；`availableReplicas` 等于 `replicas`；蓝绿路径下 Service 的 `spec.selector.version` 指向旧 SHA；连续请求恢复 200、5xx 回落到基线；`rollout history` 中本次回退产生了一条新的修订记录（而不是「什么都没发生」）。**没有在 staging 演练过回滚，就不允许进入生产发布**（CL-G-07），这是本章对公理 6 的落地。

## 回到第 1 章：H5「想回滚却发现没有回滚方案，或 schema 不兼容」

第 1 章那起「只改了一行配置」的事故里，值班同学最无力的时刻不是服务报错，而是**决定回滚之后发现没有东西可退**：命令没人写过、上一版 SHA 没记、唯一一次 `rollout undo` 还把旧版本推进了一个读不懂新表结构的境地。**回滚方案先于发布方案，是这条事故最贵的教训**。本章把这句教训拆成了可以打勾的东西：13.2 的六要素回滚方案、13.4 的 `docs/rollback-plan.md` 模板与 `hack/rollback-drill.sh` 演练脚本、13.6 的 CL-13-03 门禁，以及 13.5 里「演练用 `undo`、生产用明确 SHA + Git」那条分工。至此，应用侧的一半被补上了。
