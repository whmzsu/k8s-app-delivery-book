## 13.1 问题与反模式：想回滚，却没有回滚方案

前十二章解决了「产物是什么、怎么唯一地造出来」。从这一章起，产物要开始在生产承载真实流量——这是**发布**（让某个版本的制品在生产开始承载真实流量，并可按预案退出，正式定义见第 1 章原则、本章展开）第一次成为一章的主角。第 1 章事故里最贵的那一分钟，就发生在这一环。

**合成案例**（基于多起公开事故的合成，非真实事件）：订单服务要上线一个新版本，把订单金额字段从 `amount` 拆成 `amount_cents` 与 `currency`，发版通知里写着「出问题就回滚」。发布十分钟后 5xx 开始上升，值班同学真正动手时连撞三堵墙：第一，没人写下上一版的镜像 SHA 和回退命令，`kubectl rollout history deployment/gateway` 里最近的几个修订混着上周改探针、改环境变量的记录，`--to-revision` 该填几没人敢定；第二，硬着头皮 `kubectl rollout undo` 退回上一个修订后，旧代码读不到已经被 `ALTER TABLE DROP COLUMN` 改掉的表结构，报错比发布前更密集；第三，数据库迁移是单向的，数据已经写成了新格式，退回去也没有旧数据可读。最后的处置是「赶紧修一下再发一版」——而按本书口径，**把回滚说成「修一下再发一版」是明令禁止的误用**（见术语表）。这次故障持续了远超过「切一次流量」的时间 [R-13-5][R-13-9]。

值得单独看的是这三堵墙的性质。第一堵是**记录问题**（没人写下回退目标），第二堵是**兼容问题**（旧代码读不懂新表结构），第三堵是**数据问题**（迁移不可逆）。三堵墙里，**没有一堵是 Kubernetes 造成的**，也没有一堵能靠「换一种更聪明的部署策略」绕过去。这正是回滚这件事最反直觉的地方：**你在发布环节付出的事故时间，往往是由发布环节之外的决定造成的。**

三个反模式：

**反模式一：「先发再说，坏了就回滚」，但从未演练过回滚。** 现象是故障时找不到命令、权限不够、或者 `undo` 之后服务更糟；根因是把「回滚」当成一个随时可用的动作，而不是一份**先于发布就写好、并演练过**的方案。替代做法是发布门禁强制要求一条回滚演练记录：有明确目标产物、有命令、有时限、有验证结果、有责任人，缺一项就阻断发布 [R-13-7][R-13-9]。

**反模式二：`maxUnavailable: 0` + `maxSurge: 1` 看起来最稳，却没算节点余量。** 现象是滚动更新卡在 `Progressing=False`，新 Pod 一直 `Pending`，`Available` 副本数掉不下来也上不去；根因是「零不可用」需要额外先起一个 Pod，而集群里没有那一个人的可分配资源。替代做法是在发布前把容量账算成一张表，用数字而不是直觉回答「峰值需要几个 Pod、节点还剩多少」[R-13-1][R-13-2]。这与第 8 章 H3「新 Pod 永远不 Ready」是同一族问题的容量那一半。

**反模式三：蓝绿切流后立刻把旧版本删掉。** 现象是切流五分钟后发现问题，回退时旧 ReplicaSet 已被清理，没有回退目标；根因是把「切换完成」当成了「发布结束」。替代做法是保留旧版本到观察窗口结束，窗口长度由错误预算与业务风险决定（见第 20 章），而不是由部署脚本的清理步骤决定 [R-13-5]。

这条的诱惑力全在成本上：旧版本多跑一小时，就是多一小时的机器钱。所以总有人想把观察窗口压缩到「切完流量就清」，而**这个决定的代价不会在账单上出现，只在某次切流五分钟后才出现**。用一句更直白的话说：你省下的是可预测的小钱，押上的是不可预测的一次长故障。

还有最隐蔽的一条：**schema 不兼容时，应用层的回滚是假回滚**。上面案例里第二、三堵墙都不是 Kubernetes 的问题，而是数据格式已经不允许新旧版本共存。它无法靠选一种更聪明的部署策略解决，只能靠第 16 章的 expand–contract 迁移范式；本章在 13.2 把它作为「本书观点」显式立为边界。以上反模式的**方法论**参照公开的配置变更致全局中断、靠回滚恢复的复盘 [R-13-9]；该来源只支撑「这类失效模式确实存在」，不证明合成案例真实发生。

## 13.2 范式与决策树：容量账、回退速度与一份算数的回滚方案

本章要回答的决策问题是：**在「容量有限、必须可回退」的约束下，一次发布该选哪种策略，回滚方案怎么写才算数？**

先把本章的正式定义落到可验证的形态。**回滚**（把线上恢复到上一个已知良好版本，必须先有方案再有发布）不是一条命令，而是一份六要素文档：触发条件、目标产物（明确到 `git-<sha7>`）、执行命令、完成时限、验证方式、责任人。缺任何一项，「我们会回滚」都不算一份方案。这是全书公理 6「回滚方案先行」在本章的可执行版本 [R-13-7][R-13-8]。

这六项里，前三项是技术，后三项是组织——而**事故里真正卡住人的通常是后三项**。「多久算完」决定要不要启动对外通告，「谁批准」决定要不要在凌晨叫醒一个不在线的人，「怎么验证」决定你能不能确认退成功了而不是退成了另一个故障。**回滚失败最典型的形态不是命令报错，是命令执行完了，没人敢说已经好了。**

**策略选型矩阵**（本章主矩阵，列含「何时不该用」）：

| 策略 | 容量成本 | 回退速度 | 流量控制粒度 | 适用前提 | 何时不该用 | 回滚命令 |
|---|---|---|---|---|---|---|
| 滚动更新 RollingUpdate | 低，峰值 `replicas + maxSurge` | 慢，需再滚一次 | 无，按比例自然替换 | 新旧版本可共存、schema 兼容、有节点余量 | 需要秒级整体回退；新旧版本不能共存；节点余量不足 | `kubectl rollout undo` 或明确 SHA 回退（见 13.5） |
| 蓝绿 Blue/Green | 高，约双倍副本与资源 | 快，切一次 Service selector | 全量或零，无中间态 | 有双倍容量、无长连接粘滞、schema 兼容 | 没有双倍容量；有状态会话无法整体切换；成本敏感 | 把 `gateway` Service 的 selector 切回 `version=<旧sha7>` |
| 金丝雀 Canary | 中，少量额外副本 | 中，取决于放量台阶 | 按请求比例 / 按副本比例 | 有用户可感的指标可判定、愿意接受分批时长 | 没有 SLI 与判定指标；只想「手动分批看看」 | 见 13.5；自动回滚见第 15 章 |

> 关于第三行的术语：**渐进式交付**在这条矩阵里第一次出现，它的白话是「先给一小部分流量，指标没问题再继续」（详见第 15 章正式定义）。本章只用它标注「金丝雀这一格最终由哪一章实现」，**不拿它当推理前提**；按概念梯度，它的正式定义在第 15 章，本章不越界展开。同理，蓝绿与金丝雀的经典定义分别来自 [R-13-5][R-13-6]，本书不改写其含义，只补上容量与回滚这两列。

**容量计算表**（`api` 组件，配置契约基线：requests `cpu: 100m, memory: 128Mi`；limits `cpu: 500m, memory: 256Mi`；调度按 requests 计）。设单节点可分配余量为 `cpu: 800m, memory: 2Gi`，这是示例值，真实数值须按节点规格校准。

| 场景 | 副本数 | maxSurge | maxUnavailable | 峰值 Pod 数 | 最少可用 Pod | 峰值 requests（cpu / mem） | 节点余量是否够 | 结论 |
|---|---|---|---|---|---|---|---|---|
| A 默认滚动 | 4 | 1 | 0 | 5 | 4 | `500m / 640Mi` | 够 | 可发布，仍有 1 个 Pod 的零不可用保障 |
| B 高峰余量紧张 | 4 | 1 | 0 | 5 | 4 | `500m / 640Mi` | 余量仅 `300m`，**不够** | 新 Pod `Pending`，rollout 卡死；降 surge 或先扩容 |
| C 允许少量不可用 | 4 | 0 | 1 | 4 | 3 | `400m / 512Mi` | 够 | 不额外占容量，但发布窗口内少一个可用副本 |
| D 激进 | 4 | 2 | 1 | 6 | 3 | `600m / 768Mi` | 不够 | 峰值 6 个 Pod，节点余量不足且可用数掉到 3 |

容量账的公式只有三条，但必须逐条算，不能凭「参数看起来保守」就放行 [R-13-1]：

1. 峰值 Pod 数 = `replicas + maxSurge`（百分比时向上取整），这是调度器要同时放下的数量；
2. 最少可用 Pod 数 = `replicas − maxUnavailable`，这是发布期间服务能力的下限，要与 `PodDisruptionBudget` 的 `minAvailable` 对齐，否则 PDB 会在驱逐时反过来把 rollout 卡住 [R-13-2]；
3. `maxSurge` 与 `maxUnavailable` 不能同时为 0，否则既不允许新建也不允许销毁，更新无法推进。

场景 B 正是反模式二的数字版：参数一个字没改，只是集群余量从 `800m` 掉到 `300m`，`"maxUnavailable": 0` 就从「最稳」变成「卡死」。所以 `progressDeadlineSeconds` 必须设，它是「卡住多久判定失败」的显式上限 [R-13-1]。

**容量账的完整推导**：三条公式给出「要算什么」，这一段给出「怎么从节点数据一路算到放不放行」。以场景 A（`api`：`replicas: 4`、`maxSurge: 1`、requests `cpu: 100m, memory: 128Mi`）为例，五步推导，每步都是可复核的算术 [R-13-1]：

1. 峰值 Pod 数 = 4 + 1 = 5；
2. 峰值 requests = 5 × `100m / 128Mi` = `500m / 640Mi`；
3. 单节点可容纳数 = floor(节点可分配余量 ÷ 单 Pod requests)，按更紧的维度计：cpu 维 `800m ÷ 100m = 8`、memory 维 `2Gi ÷ 128Mi = 16`，取小 → 每节点 8 个；
4. 需要的节点数 = ceil(5 ÷ 8) = 1——**但这是均值口径**，还必须核对 13.2.1 的教训：余量是否集中在同一些节点、有没有节点带 `unschedulable` taint，有效节点要用当天的逐节点数据数出来；
5. 判定：各有效节点可容纳数**逐节点 floor 后求和** ≥ 峰值 Pod 数才放行。场景 B 里「总余量 `300m`」除以 `100m` 得 3，看似够——但三个节点分别只剩 `40m / 80m / 0`，逐节点 floor 是 0 + 0 + 0 = 0。**「余量相加再除以单 Pod requests」是容量账最常见的算错点**，floor 不可移项。

逐节点余量可以直接从集群读出来，不必手算（每节点 `Allocatable` 减去 `Allocated resources` 的 requests 即余量）：

```bash
# 逐节点列出可分配量与已分配 requests，逐节点判定：余量 ≥ 单 Pod requests
kubectl describe nodes | awk '
  /^Name:/                { node=$2 }
  /^Capacity:/            { mode="" }
  /^Allocatable:/         { mode="alloc" }
  /^Allocated resources:/ { mode="used" }
  /^  cpu:/               { if (mode=="alloc") ac=$2; else if (mode=="used") ur=$2 }
  /^  memory:/            { if (mode=="alloc") am=$2; else if (mode=="used") um=$2 }
  /^Non-terminated Pods:/ { }
  /^Events:/              { printf "%s 可分配 cpu=%s mem=%s | 已分配 requests cpu=%s mem=%s\n", node, ac, am, ur, um }
'
# 通过标准：每行输出里（allocatable − requests）在 cpu 与 memory 两个维度都 ≥ 单 Pod requests，
# 且满足条件的节点数 ≥ ceil(峰值 Pod 数 ÷ 单节点容纳数)
```

**与 `PodDisruptionBudget` 的算术自洽**是同一张账的第二层：`maxUnavailable` 管「发布允许少几个」，PDB 的 `minAvailable` 管「自愿驱逐允许少几个」，两者各自生效，但共同决定发布窗口的可用性下限，必须一起核对 [R-13-2]。三条判定：

1. **自洽不等式 `minAvailable ≤ replicas − maxUnavailable`**。13.4 的取值（4 − 0 = 4 ≥ 3）满足；若反过来 `minAvailable: 4` 且 `maxUnavailable: 1`，节点排水时 PDB 一律拒绝驱逐，滚动与节点维护互相顶住——13.4 注释警告的情形，其算术形式就是这条不等式被打破。
2. **`minAvailable` 必须严格小于 `replicas`**：取等号时任何一次驱逐都不被允许，PDB 退化成「永不允许打扰」。`replicas` 会随 HPA 变化的负载（见第 18 章）应改用百分比（如 `minAvailable: 75%`）而不是绝对值：HPA 扩到 8 副本后，绝对值 `3` 意味着允许同时消失 5 个——保护随扩容反而变弱，百分比则始终按当期副本数取整生效。
3. **发布窗口内 PDB 必须留有驱逐额度**，用下命令核对，发布开始与结束后各查一次：

```bash
kubectl -n order-demo-prod get pdb gateway
# NAME      MIN AVAILABLE   ALLOWED DISRUPTIONS   ...
# gateway   3               1
# 通过标准：ALLOWED DISRUPTIONS ≥ 1 且发布全程保持 ≥ 1；
# 出现 0 说明 PDB 把发布或排水卡死，回到本节判定 1 重算 [R-13-2]
```

**落到数字：HPA 接管时的容量与 PDB 取整例**（衔接第 18 章）。设 `api` 由 HPA 接管，`minReplicas: 4`、`maxReplicas: 8`、`maxSurge: 1`。三件事在发布前必须按 8 而不是 4 算：其一，容量按 `maxReplicas + maxSurge = 9` 个 Pod 预留，本节第 5 步的判定式从「可容纳 ≥ 5」改为「可容纳 ≥ 9」——HPA 在发布窗口扩容并不打招呼，前文观点块里「Surge Pod 与 HPA 扩容 Pod 抢余量」的冲突，落算就是 9 与 5 的差；其二，13.4 式的绝对值 `minAvailable: 3` 在 8 副本时允许 5 个 Pod 同时被驱逐，保护随扩容反而变弱，应改为 `minAvailable: 75%`，取整后 8 × 75% = 6（PDB 百分比向下取整，对可用性保守），允许驱逐 2 个——与发布期 `maxUnavailable` 保持同一数量级；其三，回退时效要按当期副本数重估：回退本身也是一次滚动，8 副本 + `maxUnavailable: 0` 的回退时长约为 4 副本的两倍，六要素方案里的「完成时限」应按 `maxReplicas` 口径写，而不是按发布时的实际副本数 [R-13-2]。

**百分比取整规则**（`maxSurge` / `maxUnavailable` 的值可以是绝对整数，也可以是百分比字符串，同一个字段只能二选一，不能混写）[R-13-1]：

| `replicas` | 声明值 | 乘积 | 取整方向 | 实际生效 |
|---|---|---|---|---|
| 4 | `maxSurge: 25%` | 4 × 25% = 1 | 向上取整 | 1 |
| 4 | `maxSurge: 10%` | 4 × 10% = 0.4 | 向上取整 | 1 |
| 4 | `maxUnavailable: 25%` | 4 × 25% = 1 | 向下取整 | 1 |
| 4 | `maxUnavailable: 10%` | 4 × 10% = 0.4 | 向下取整 | **0** |

两条推论：其一，`maxUnavailable` 向下取整意味着百分比声明在副本数较小时极易归零——上表第四行的 YAML 能通过 API 校验，行为却等价于绝对值 `0`，「峰值 Pod 数 = replicas + maxSurge」要按取整后的整数重算，容量预算不能按声明值算；其二，`maxSurge` 的取整方向永远对容量不利（宁可多占一个），做预算时一律按取整结果计 [R-13-1]。因此本章给出一条实操纪律：**`replicas` 小于 5 的工作负载直接写绝对整数**，取整规则留给大副本数的场景。

**与 HPA 同时启用时的相互作用**（HPA 的正式落地在第 18 章，本章只声明边界与后果，处理手段详见第 18 章）：

> **本书观点（本章第 5 条结论，不需要外部背书）**
>
> **主张**：滚动更新与 HPA 同时启用时，容量账的分母不再是清单里的 `replicas: 4`，而是「HPA 当期期望副本数 + `maxSurge`」。只按清单 `replicas` 核算容量、而负载实际由 HPA 接管的团队，会在第一次「扩容高峰撞上发布」时撞进 13.2.1 的卡死现场，且比无 HPA 时更难定位——HPA 扩出的 Pod 与滚动的 Surge Pod 竞争同一批节点余量，事件流互相指向对方。
>
> **论证**：HPA 计算期望副本数时会忽略未就绪的 Pod（它们不贡献指标），滚动更新期间可用 Pod 数短暂下降、分摊到每个 Ready Pod 的负载上升，HPA 随即上调期望副本；若这一步发生在节点余量已经紧张的时刻，两类 Pod 排队抢资源，双双 `Pending`，`rollout status` 与 HPA 事件互相干扰，定位成本陡增。反向也有影响：GitOps 清单里若仍写死 `replicas` 字段，会与 HPA 抢写同一个字段，制造「扩上去又被压回来」的抖动。
>
> **反例与适用前提**：这不意味着「有 HPA 就不能滚动发布」。若节点余量按 `maxReplicas + maxSurge` 预留、清单侧解决了 `replicas` 字段归属（GitOps 下删掉该字段或配置 ignoreDifferences，见第 18 章），两者可以安全共存；发布窗口内最稳的做法是把 `minReplicas` 临时抬到「预期副本 + `maxSurge`」，让容量先落位再触发发布。本条不引用外部来源，因为它是对 R-13-1 容量公式与第 18 章 HPA 机制的组合推论。

### 13.2.1 现场复盘：容量不足导致的 rollout 卡死（合成案例）

下面把反模式二从「参数表」落到「终端输出」。这是一次合成案例（非真实事件），但每一行输出都可在 staging 复现，处置路径与 13.5 的回滚命令一一对应 [R-13-1][R-13-2]。

**背景**：`api` 组件 `replicas: 4`、`maxSurge: 1`、`maxUnavailable: 0`（requests `cpu: 100m, memory: 128Mi`，与 13.2 容量表同一基线）。发布当天上午，同集群另一业务调大了一批 Pod 的 requests 并做节点排水，3 个节点的可分配余量变成：node-a 剩 `cpu: 40m`、node-b 剩 `cpu: 80m`（两者内存余量均已不足 `128Mi`）、node-c 因排水带 `unschedulable` taint。没有任何单节点还能放下一个 `api` Pod，但整体利用率不高让值班误判「余量充足」——余量紧张与否要看**单节点**，不是看集群平均。

**「余量充足」这四个字是怎么来的**（依同类事故共性还原，非原话）：

> **值班**：发布卡住了，`rollout status` 一直不结束。
> **同事**：节点资源够吗？
> **值班**：我刚看了，整个集群 CPU 才用了 40%，够得很。
> **同事**：那可能是别的原因。
> （十五分钟后）**同事**：……你看的是集群总量吧？单个节点还剩多少？
> **值班**：node-a 剩 40m。`api` 要 100m。

这段对话的关键不在最后一句，在第三句。**「整个集群 CPU 才用了 40%」是一句完全真实的话**，它来自一个每天都在用的监控面板，读数没有错，结论也没有撒谎——它只是回答了一个没人问的问题。调度器从来不看集群平均，它只回答一句：**有没有某一个节点，能完整放下这一个 Pod。**

**时间线**：

1. T+0：发布 PR 合并，镜像 `git-5d6e7f8` 由第 14 章控制器同步，Deployment 控制器把新 ReplicaSet 扩到 1 个 Pod。
2. T+2m：`rollout status` 迟迟不结束，`UP-TO-DATE` 一直是 0。
3. T+5m：`progressDeadlineSeconds: 300` 到期，Deployment 置 `Progressing=False`，事件 `ProgressDeadlineExceeded` [R-13-1]。
4. T+7m：开始定位。

**定位四步**（每步带通过判据）：

```bash
# 第 1 步：确认 rollout 是「卡住」而非「慢」
kubectl -n order-demo-prod rollout status deployment/api --timeout=30s
# 判据：输出含 exceeded its progress deadline，卡住判定成立 [R-13-1]

# 第 2 步：看 Deployment 状态——注意 READY 4/4 是「看起来正常」的假象
kubectl -n order-demo-prod get deploy api
# NAME   READY   UP-TO-DATE   AVAILABLE   AGE
# api    4/4     0            4           3d
# 判据：UP-TO-DATE=0 且 rollout 未完成 → 新 Pod 没起来，而不是旧 Pod 被误杀

# 第 3 步：找到 Pending 的 Surge Pod
kubectl -n order-demo-prod get pods -l app.kubernetes.io/component=api -o wide
# 判据：存在 AGE 小于发布时长、0/1 Running 且 STATUS 为 Pending 的新哈希 Pod

# 第 4 步：describe Pod 看 FailedScheduling 事件（定位的关键一步）
kubectl -n order-demo-prod describe pod api-7d9f6b5c4-9zq2t
```

第 4 步的 Events 段（截取）：

```text
Events:
  Type     Reason            Age                  From               Message
  ----     ------            ----                 ----               -------
  Warning  FailedScheduling  46s (x21 over 6m)    default-scheduler  0/3 nodes are available: 2 Insufficient cpu, 1 node(s) had untolerated taint {node.kubernetes.io/unschedulable: }. preemption: 0/3 nodes are available for preemption: 1 preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod..
```

判定规则：`FailedScheduling` 的 Message 在 `0/N nodes are available` 之后逐节点枚举「放不下的原因」——`Insufficient cpu` / `Insufficient memory` 对应单节点余量不足，taint 条目对应节点被排水或维护。看到它即可判定**这不是应用或探针问题**（区别于第 8 章 H3「新 Pod 永远不 Ready」：那是 Running 之后探针不过），而是调度层的容量账不过（CL-13-02 / CL-G-08 的失败形态）。注意 Message 只枚举了**失败原因覆盖**的节点：若某些节点没出现在清单里，说明其余节点其实放得下，问题多半出在反亲和或 `topologySpreadConstraints` 一类的分布约束上，排查方向随之不同。

**处置**（按优先级）：

1. **扩容节点或回收余量**（首选）：控制器是收敛式的，余量落位后 rollout 自动续跑，无需人工干预。验证：`kubectl -n order-demo-prod rollout status deployment/api --timeout=300s` 最终打印 `successfully rolled out`。
2. **无法立即扩容时**，临时把 `maxUnavailable: 0` 改为 `1`（回 Git 改 `rolling-strategy.yaml`、走 PR——生产禁止 `kubectl edit`，全书公理 5，见第 3 章）：控制器会先删除一个旧 Pod 再建新 Pod，腾出其所在节点的余量；代价是发布窗口内可用副本降为 3，与 `PodDisruptionBudget` 的 `minAvailable: 3` 恰好自洽（PDB 约束的是自愿驱逐、不影响发布本身，但两处口径必须同时核对，见 13.4）[R-13-2]。**禁止的替代做法**：把 requests 改小「骗」调度器放行——那会在真高峰期触发 OOM/限流，是用第 17 章的稳定性换发布进度。
3. **若此时必须回退**（例如新旧版本已出现兼容性问题）：回退本身也是一次滚动，同样要占用 `maxSurge` 的容量——卡死状态下 `rollout undo` 会卡在同一个 `FailedScheduling` 上。先执行处置 1 或 2 把容量腾出来，再走 13.5 的路径 C。

**复盘沉淀**：根因不是参数选错，而是「发布前的容量账」没有把**当天**的节点余量算进去——13.2 表格的余量是发布前校准的静态值，而余量随时会被邻居吃掉。落地为两条纪律：发布 PR 附当天的 `kubectl top nodes` 输出或 `kubectl describe nodes` 的 `Allocated resources` 段（即 CL-13-02 的「怎么查」）；HPA 接管的负载，余量按 `maxReplicas + maxSurge` 预留（见本节前段与第 18 章）。

**决策树**：

```
这次发布改动了数据格式 / schema 吗？        是 → 先做第 16 章 expand–contract，
        │                                      否则任何策略的回滚都是假回滚
        │ 否
有可测量的用户可感指标（错误率 / 延迟分位）吗？ 否 → 不要选金丝雀，先补 SLI（见第 20 章）
        │ 是
需要秒级整体回退且有双倍容量吗？            是 → 蓝绿（保留旧版本到观察窗口结束）
        │ 否
需要按指标决定继续还是自动回退吗？          是 → 金丝雀 / 渐进式交付（详见第 15 章）
        │ 否
→ 滚动更新（默认）：先填容量计算表，再写回滚方案，两者都通过才允许发布
```

**回退时效对照表**（三种策略 × 三类故障）。口径：从「确认回退」到「流量 100% 回到稳定版」，不含定位与决策时间；前提是六要素回滚方案已在 staging 演练过、旧版本仍然存在（蓝绿旧 Deployment 未删，或滚动路径 `revisionHistoryLimit` ≥ 10）：

| 故障类型（典型现象） | 滚动更新 | 蓝绿 | 金丝雀 |
|---|---|---|---|
| A 新版本应用缺陷：上线后 5xx 上升、延迟劣化 | 2–6 分钟：`undo` / SHA 回退要再滚一次，受 `minReadySeconds` 与剩余容量制约 [R-13-1] | 秒级–1 分钟：旧版全程在线，切一次 selector（13.5 路径 D）[R-13-5] | 秒级–2 分钟：abort 后流量权重回位，且受影响面只有台阶比例 [R-13-6] |
| B 配置 / 清单错误：探针路径、环境变量写错，新 Pod 永不 Ready | 6–12 分钟：新 Pod 要先卡满 `progressDeadlineSeconds`（300s）判定失败，回退再滚一次 | ≈0 分钟：切流前置条件（目标 Ready ≥ 4）直接拒绝，蓝版从未离开流量（见 13.4 的 `switch.sh`）[R-13-5] | 秒级：首个台阶即被 Ready / 指标拦截并自动 abort（自动回滚见第 15 章） |
| C 容量与调度故障：节点余量不足、Pending、镜像拉取失败 | **不可控**：连回退都要占 `maxSurge` 容量，`undo` 会卡在同一个 `FailedScheduling` 上（见 13.2.1） | 秒级：回退只是改 selector，不创建新 Pod，不占 Surge 容量 | 最小：只需销毁少量 canary Pod、权重回位，容量增量最小 |

三条共同前提，缺一整格失效：① schema 兼容——不兼容时三格都是假回滚（见本节「本书观点」标注块）；② 回退目标存在——蓝绿靠旧 Deployment 未删、滚动靠 `revisionHistoryLimit` 与修订号辨认（见 13.5 排错案例）；③ 回退动作在生产走 Git（13.5 路径 C），表内时效是演练环境实测口径，叠加 GitOps 同步延迟后按 +30–120 秒估算（见第 14 章）。

结论：B、C 两类故障让「蓝绿的常备双倍容量」从成本项变成**回退时效的保险**，余量常年紧张的集群尤其如此；A 类故障三种策略都能退，差别只在影响面与时长——这正是决策树里「是否需要秒级整体回退」一条的量化依据，也解释了为什么容量账不过的团队不该硬选滚动 [R-13-5][R-13-6][R-13-1][R-13-7]。

**综合决策矩阵（第二张：把「选型」从回退时效扩展到成本与规模）**。上面的回退时效对照表回答的是「故障发生时多快能退」；选型时还要回答另外三个问题——钱花在哪、规模到哪一层、数据兼容前提是否成立。成本分两列口径：**常备成本**指不出事故也要持续付出的部分，**单次发布成本**指每次发布额外付出的部分；适用规模以「同时管理的发布中工作负载」计。

| 策略 | 常备成本 | 单次发布成本 | 故障回退面（引时效表 A/B/C 行） | 适用规模 | 数据兼容前提 | 观测 / 自动化要求 |
|---|---|---|---|---|---|---|
| 滚动更新 | 零：只有策略参数与历史 ReplicaSet（受 `revisionHistoryLimit` 上限约束） | 低：峰值 `replicas + maxSurge` 的余量 + 发布窗口内的吞吐抖动 | A 可退；B 要先等 deadline；C 不可控 | 副本数 2–30 的服务均可；服务数不限 | 新旧版本可在同一 schema 上共存（硬前提，见本节「本书观点」） | 探针 + `minReadySeconds` 即可，**不需要 SLI** |
| 蓝绿 | 高：常驻双倍副本与资源，平时空闲一半 [R-13-5] | 中：切流一次提交；回退不占 Surge 容量（时效表 C 行优势的来源） | 三类故障都能秒级退 | 单服务副本 4–20；服务数少——双倍成本按服务数线性放大 | 同上 | 切流前置检查（目标 Ready ≥ replicas）即可，不需要 SLI |
| 金丝雀 | 低–中：常驻少量 canary 副本 [R-13-6] | 中：每个台阶的观察期拉长发布总时长 | A 影响面最小（仅台阶比例）；B/C 首个台阶即拦截 | 副本 ≥ 4（1 个 canary 才有统计意义）；流量可按请求计量 | 同上 | **必须有 SLI**（错误率 / 延迟分位）与指标判定；自动回滚见第 15 章 |

三条规模判据（本书观点，作为上表与决策树的取整推论，不需要外部背书）：

1. **服务数 ≥ 10 且都走蓝绿时，常备成本会超过一整套预发布环境的开销**：双倍副本按服务数线性放大，而绝大多数服务并不需要秒级整体回退。正确收敛方向是「默认滚动 + 少数关键服务蓝绿 / 金丝雀」，关键服务名单由 SLO 与错误预算决定（见第 20 章）。
2. **`replicas` ≥ 8 的工作负载优先考虑金丝雀而不是全量滚动**：滚动的一次失败以 100% 流量为代价（哪怕只持续一个 deadline 周期），金丝雀把同等缺陷的影响面压到台阶比例；副本数不足 4 时指标噪声盖过信号，退回滚动。
3. **没有 SLI 就选金丝雀，等于把回退判定交给肉眼**：时效表 A 行的「秒级–2 分钟」整格失效，退化为「手动分批看看」；此时按决策树第二问先补 SLI（见第 20 章），而不是先上金丝雀控制器。

**负载形态会让矩阵行错位**（本书观点，不需要外部背书）。两种形态要单独判：一是**长连接 / 会话粘滞**的服务（如 WebSocket 网关）——蓝绿的「切一次 selector」只对新建连接秒级生效，存量长连接不会跟着 selector 迁移，它的「秒级回退」在方案里必须改写为「新连接回退 + 存量连接排空」，时效表 A 行的蓝绿格按此打折 [R-13-5]；二是**冷启动慢**的服务（大镜像、缓存预热、JIT 预热）——`minReadySeconds` 与探针初始延迟会把每次滚动放大到分钟级，A 类故障的滚动回退格按时长线性放大，而这批服务恰恰是最该用蓝绿或金丝雀的候选：回退的稀缺性最高，滚动的代价最大。

**零停机前提**：滚动更新期间连续请求零 5xx，依赖第 8 章的探针与优雅上下线四条件。**本章只引用、不重述**，措辞以第 8 章为准（见章末备注）；验证侧用 [R-13-4][R-13-2] 支撑。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：数据 schema 不兼容时，应用层的回滚是假回滚；策略选型救不了数据，只有让新旧版本在同一 schema 上共存才保得住回滚能力。
>
> **论证**：回滚的定义要求「恢复到上一个已知良好版本」，而一个版本是否「良好」，取决于它能否正确读写当下的数据。若发布同时执行了破坏性 DDL（如 `DROP COLUMN`、改字段类型、拆分字段），旧版本启动后面对的是它从未见过的数据形状，于是「镜像退回去了、服务却没回来」。此时三种策略的差别只剩「多快发现这件事」：滚动要再滚一次，蓝绿切回去照样报错，金丝雀只让一小部分请求先报错。三者都作用在「哪个 Pod 承载流量」这一层，无法改变「数据长什么样」。可回退性因此不是发布策略的属性，而是**数据变更设计**的属性。
>
> **反例与适用前提**：这不等于「任何涉及数据库的发布都必须做四阶段迁移」。纯新增可空列、只加索引、只写不改的追加式变更，本身就是向后兼容的，旧版本无视新列即可，直接滚动更新是合理的。前提是团队能证明「旧版本在新 schema 上可服务」——这条证明由第 16 章的 expand → 双写 → 回填 → contract 四阶段及其共存验证给出，本章只声明边界、不实现迁移。跳过此步的典型代价就是 13.1 合成案例里的第二、三堵墙；自动回滚也覆盖不了这一半，见第 15 章。

### 13.2.2 rollout 卡死排查树：五种形态，各一条定位命令

13.2.1 完整复盘了「容量不足」这一种卡死形态，但现场最先要回答的问题是**这是哪一种卡死**。五种形态共用同一个入口（`rollout status` → `get deploy` 看 `UP-TO-DATE` → 列 Pod 看 STATUS），分歧点在 Pod 的 STATUS 与 Events：

```text
rollout 卡住（UP-TO-DATE 不涨，或 Progressing=False）
├─ 新 Pod STATUS = Pending
│   ├─ FailedScheduling: Insufficient cpu / Insufficient memory
│   │        → 容量不足，按 13.2.1 处置（扩容回收余量，或临时调大 maxUnavailable）
│   ├─ FailedScheduling: node(s) had untolerated taint
│   │        → 节点在排水 / 维护，等排水结束或先扩容补位
│   ├─ FailedScheduling: exceeded quota
│   │        → 命名空间 ResourceQuota 用尽，见下表第 4 行（注意此时可能根本没有 Pending Pod）
│   └─ FailedScheduling: topology / anti-affinity / spread 约束
│            → 分布约束把可放节点排空，见下表第 5 行
├─ 新 Pod STATUS = ImagePullBackOff / ErrImagePull → 镜像不可拉取，见下表第 1 行
└─ 新 Pod STATUS = Running 但一直 0/1 Ready → 探针不过，见下表第 2 行
```

| # | 形态 | 一条定位命令 | 关键判据 | 深入章节 |
|---|---|---|---|---|
| 1 | `ImagePullBackOff` / `ErrImagePull` | `kubectl -n order-demo-prod describe pod <pod> | grep -A4 "Failed to pull"` | Message 含 `not found`：tag 打错或镜像未推送，对照发布 PR 的 `git-<sha7>`；含 `denied` / `unauthorized`：仓库凭据（`imagePullSecrets`）或验签门禁拒绝 [R-13-1]，见第 24 章 | 第 3、24 章 |
| 2 | Running 但一直 0/1 Ready | `kubectl -n order-demo-prod describe pod <pod> | grep -B2 -A8 "Readiness probe failed"` | Events 出现 `Readiness probe failed: ...`，先核对探针路径与端口是否与契约一致（`/readyz`:8080），再看应用日志判断是真未就绪还是探针配置错；与第 8 章 H3「新 Pod 永远不 Ready」同族，区别只在出现在发布现场 [R-13-4] | 第 8 章 |
| 3 | Pending + `Insufficient cpu/memory` | `kubectl -n order-demo-prod describe pod <pod> | grep -A3 FailedScheduling` | `0/N nodes are available` 后逐节点枚举原因；Message 只列失败原因覆盖的节点，其余节点未出现说明它们放得下、问题多半在分布约束（13.2.1 判定规则）[R-13-1] | 本章 13.2.1 |
| 4 | 配额不足（`exceeded quota`） | `kubectl -n order-demo-prod describe rs -l app.kubernetes.io/component=gateway | tail -n 12` | **Pod 根本没被创建**，`get pods` 里看不到 Pending Pod，这是与形态 3 的关键区别；判据是 ReplicaSet 事件 `FailedCreate: pods "..." is forbidden: exceeded quota`。再用 `kubectl -n order-demo-prod describe resourcequota` 核对 `Used ≥ Hard` | 第 17 章 |
| 5 | Pending + 分布约束 | `kubectl -n order-demo-prod get pods -l app.kubernetes.io/component=gateway -o wide` | 逐节点明明有余量，FailedScheduling 却把所有节点都列进「不可放」清单；常见于反亲和要求「每节点最多一个」而节点数不足，或 `topologySpreadConstraints` 的 `maxSkew` 无解 | 第 18 章 |

两条使用纪律：其一，形态 1、2 出现时**不要动容量**——它们与新 Pod 能否被创建无关，先修镜像与探针；形态 3–5 才进入容量与调度这一层，两者处置手段完全不同，混着查会浪费一个 deadline 周期。其二，无论哪种形态，`progressDeadlineSeconds` 都会把「卡住」最终翻转成 `ProgressDeadlineExceeded` [R-13-1]——所以它不是定位手段，只是止损上限；真正决定「卡多久能发现」的是告警对 `Progressing=False` 的覆盖（见第 22 章）。

**一次误判与纠正（合成案例）**：某次发布卡住，值班看到 Pod 数没涨，凭「发布失败就是资源不够」的经验直接走变更流程申请扩容节点——但 `get pods` 里新 Pod 根本不存在，这是形态 4 的特征：`FailedCreate` 发生在 ReplicaSet 这一层，Pod 还没来得及 Pending，扩容自然无效。纠正只花了一分钟：`describe rs` 的事件里写着 `exceeded quota`，根因是当天另一业务的新 Deployment 把命名空间 `requests.cpu` 的 Hard 用满。这次误判沉淀为排查树树干的分流规则：**先确认「新 Pod 存在吗」再往下走**——存在则按形态 1–3、5 分流，不存在直接查 RS 事件与 ResourceQuota；容量动作要走变更流程，误判一次的成本远高于先看一眼 RS 事件的成本 [R-13-9]。

**`deploy/bluegreen/switch.sh`** —— 一次性切流，参数只允许两个已知 SHA，防止把流量切到不存在的版本。

```bash
#!/usr/bin/env bash
set -euo pipefail

NS=order-demo-prod
SVC=gateway
OLD=git-1a2b3c4
NEW=git-5d6e7f8
TARGET="${1:-}"

case "${TARGET}" in
  green|"${NEW}") SELECTOR="${NEW}" ;;
  blue|"${OLD}")  SELECTOR="${OLD}" ;;
  *) echo "用法: $0 green|blue（只允许切到 ${OLD} 或 ${NEW}）" >&2; exit 2 ;;
esac

# 前置：目标版本必须真的有 Ready 副本，否则拒绝切流
READY="$(kubectl -n "${NS}" get deploy \
  -l "app.kubernetes.io/component=gateway,version=${SELECTOR}" \
  -o jsonpath='{.items[*].status.readyReplicas}' | tr ' ' '\n' | awk '{s+=$1} END {print s+0}')"
[ "${READY}" -ge 4 ] || {
  echo "目标版本 ${SELECTOR} 的 Ready 副本为 ${READY}，不足 4，拒绝切流" >&2; exit 1;
}

kubectl -n "${NS}" patch svc "${SVC}" --type=merge -p \
  "{\"spec\":{\"selector\":{\"app.kubernetes.io/name\":\"order-demo\",\"app.kubernetes.io/component\":\"gateway\",\"version\":\"${SELECTOR}\"}}}"

echo "已切到 ${SELECTOR}；旧版本 Deployment 保留至观察窗口结束，切勿立即删除。"
kubectl -n "${NS}" get svc "${SVC}" -o jsonpath='{.spec.selector.version}{"\n"}'
```

> 生产环境里这个脚本不应由人直接执行：它只是把「切流」表达成一次可审查的状态变更，真正落地时应把等价的 selector 改动写进 Git，由第 14 章的控制器同步（全书公理 5，见第 3 章）。脚本放在这里是为了让 13.5 的演练可复制执行。

**`hack/rollback-drill.sh`** —— staging 演练脚本，同时演示两种回退路径。

```bash
#!/usr/bin/env bash
set -euo pipefail

NS=order-demo-staging
DEPLOY=gateway
STABLE="$(kubectl -n "${NS}" get deploy "${DEPLOY}" \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
CANDIDATE="registry.example.com/order-demo/gateway:git-0000000"
REPORT="/tmp/rollback-drill-$(date +%Y%m%d%H%M%S).log"

log() { echo "[$(date -u +%FT%TZ)] $*" | tee -a "${REPORT}"; }

log "稳定版本: ${STABLE}"

# 制造一个「新版本」并等待它就绪，让 ReplicaSet 历史里有可退的修订
kubectl -n "${NS}" set image "deployment/${DEPLOY}" gateway="${CANDIDATE}"
kubectl -n "${NS}" rollout status "deployment/${DEPLOY}" --timeout=120s || true
log "已发布候选版本: ${CANDIDATE}"

REV="$(kubectl -n "${NS}" rollout history "deployment/${DEPLOY}" \
  | tail -n2 | head -n1 | awk '{print $1}')"
log "待回退修订号: ${REV}"

# 路径 A：按历史修订回退（演练用）
START=$(date +%s)
kubectl -n "${NS}" rollout undo "deployment/${DEPLOY}" --to-revision="${REV}"
kubectl -n "${NS}" rollout status "deployment/${DEPLOY}" --timeout=120s
log "路径 A 完成，耗时 $(( $(date +%s) - START ))s"

# 路径 B：明确 SHA 回退（推荐用于明确目标产物）
kubectl -n "${NS}" set image "deployment/${DEPLOY}" gateway="${STABLE}"
kubectl -n "${NS}" rollout status "deployment/${DEPLOY}" --timeout=120s
log "路径 B 完成，目标产物: ${STABLE}"

# 验证
IMAGE="$(kubectl -n "${NS}" get deploy "${DEPLOY}" \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
[ "${IMAGE}" = "${STABLE}" ] || { log "失败：image 未回到稳定版本"; exit 1; }
kubectl -n "${NS}" port-forward "svc/${DEPLOY}" 18080:8080 >/dev/null 2>&1 &
PF=$!
trap 'kill "${PF}" 2>/dev/null || true' EXIT
for i in $(seq 1 30); do
  curl -fsS http://127.0.0.1:18080/healthz >/dev/null 2>&1 && break
  sleep 1
done
curl -fsS http://127.0.0.1:18080/healthz | tee -a "${REPORT}"
log "演练通过，报告: ${REPORT}"
```

**回滚命令 / 步骤**。先讲清两种回退的区别，这是 H5 最核心的一条：

`kubectl rollout undo` 回退的是 **Deployment 的整个 Pod 模板的上一个修订**，不是「把镜像换回去」。若上一个修订之后还改过探针、环境变量、资源 requests 或 `preStop`，它们会被一起退回；它还依赖 ReplicaSet 历史（`revisionHistoryLimit`），历史被清理或修订号辨认不清时就会失效。第 6 章在本地 kind 里用它做演练，是为了让读者看清字段变化，不代表生产应依赖它 [R-13-1]。

**明确 SHA 回退**精确表达「恢复到上一个已知良好产物」：`git-<sha7>` 可反查唯一提交、可复现、可写进 `docs/rollback-plan.md` 的目标产物栏；而生产环境里这个动作必须回到 Git 声明（改 overlay 的 image 字段 → 提交 PR → 第 14 章控制器同步），不能由人 `kubectl set image`（全书公理 5，见第 3 章）。因此结论是：**演练用 `undo`，生产用明确 SHA + Git**。

```bash
# 路径 A：滚动更新，按历史修订回退（仅演练 / 一次性集群）
REV="$(kubectl -n order-demo-prod rollout history deployment/gateway \
  | tail -n2 | head -n1 | awk '{print $1}')"
kubectl -n order-demo-prod rollout undo deployment/gateway --to-revision="${REV}"
kubectl -n order-demo-prod rollout status deployment/gateway --timeout=120s

# 路径 B：滚动更新，明确 SHA 回退（本地 kind 演练形态）
OLD="<上一个已验证的 sha7>"
kubectl -n order-demo-prod set image deployment/gateway \
  gateway="registry.example.com/order-demo/gateway:git-${OLD}"
kubectl -n order-demo-prod rollout status deployment/gateway --timeout=120s

# 路径 C：生产唯一合法路径 —— 回到 Git，由第 14 章控制器同步
OLD="<上一个已验证的 sha7>"
(
  cd deploy/overlays/prod
  kustomize edit set image \
    "registry.example.com/order-demo/gateway=registry.example.com/order-demo/gateway:git-${OLD}"
)
git add deploy/overlays/prod && git commit -m "rollback(order-demo): gateway -> git-${OLD}"
git push origin main
# 不在此处执行任何 kubectl 写命令；由 Argo CD 3.x 同步并留下 PR 审计

# 路径 D：蓝绿回退 —— 把 gateway Service 的 selector 切回旧 version
./deploy/bluegreen/switch.sh blue

# 路径 E：金丝雀的自动回滚见第 15 章（AnalysisTemplate 判定失败即回退）
```

> 路径 D 之所以快，是因为旧版本一直在线；这也解释了反模式三为何让蓝绿优势归零。路径 A/B 只用于一次性集群，路径 C 才是生产。若牵涉 schema，以上五条路径都只完成「应用侧回退」，数据侧必须按 13.2「本书观点」与第 16 章处理。

**排错案例：修订号不连续与「退错了上一版」（合成案例）**

`revisionHistoryLimit: 10` 的语义是：Deployment 控制器只保留最近 10 个历史 ReplicaSet，更早的连同其修订号一起被清理；修订号是 Pod 模板每次变更的全局递增计数，**被清理的编号不回填、不重排**，因此 `rollout history` 输出 1、5、12、13 这种不连续编号是常态而非异常 [R-13-1]。`revisionHistoryLimit` 设为 0 则只保留最新修订，`rollout undo` 将无目标可退——这正是 13.4 注释说它是 `undo` 前提的原因。

合成案例：值班同学想退「上一版」，`rollout history` 显示当前修订 13，直接 `--to-revision=12`。但 12 号是上周「调 readinessProbe 阈值」的变更（PR #490），真正的上一个发布是 10 号——修订号只与「Pod 模板变没变」有关，与「是否是一次发布」无关；探针参数随模板一起被回退 [R-13-1]，与 13.5 开头说的「`undo` 回退整个 Pod 模板」叠加成一次双重误回退。辨认修订号按三步走：

```bash
# 第 1 步：看 CHANGE-CAUSE 列，找最近一条「发布」记录（而不是「最近一个编号」）
kubectl -n order-demo-prod rollout history deployment/gateway
# REVISION  CHANGE-CAUSE
# 10        发布 gateway git-1a2b3c4（PR #482）
# 12        调整 readinessProbe failureThreshold（PR #490）
# 13        发布 gateway git-5d6e7f8（PR #495）

# 第 2 步：预览目标修订的模板，确认镜像 SHA 与容器参数再动手
kubectl -n order-demo-prod rollout history deployment/gateway --revision=10

# 第 3 步：仍不确定时，用 ReplicaSet 对照镜像与创建时间
kubectl -n order-demo-prod get rs -l app.kubernetes.io/component=gateway \
  -o custom-columns='NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image,CREATED:.metadata.creationTimestamp'
# 通过标准：目标修订对应的 ReplicaSet 镜像与 docs/rollback-plan.md 的目标产物一致
```

CHANGE-CAUSE 列来自 Pod 模板上的 `kubernetes.io/change-cause` 注解，需要发布流程主动写入（CI 在每次发布 PR 中带上，格式建议「发布 <组件> git-<sha7>（PR #编号）」）；没有它，history 只是一列裸编号，案例里的误判无从避免。配套纪律：`revisionHistoryLimit` ≥ 10（与 CL-13-04 一致）；CHANGE-CAUSE 缺失的修订视为「不可按修订号回退」，只能走明确 SHA 路径（路径 B/C）；蓝绿路径的回退目标是独立保留的旧 `Deployment`，不依赖 ReplicaSet 历史，两套口径不要混用 [R-13-1]。

**回滚 runbook：从触发到验证的完整流程**。上面给了命令与目标辨认，但一条命令不等于一次回滚。把六要素展开成可执行的 runbook，每个阶段有责任人、时限与产出，发布前整表随 `docs/rollback-plan.md` 一起评审（发布工程口径 [R-13-7][R-13-8]）：

| 阶段 | 动作 | 责任人 | 时限 | 产出 |
|---|---|---|---|---|
| T0 触发 | 对照回滚方案的「触发条件」栏确认命中（如 gateway 5xx 连续 3 分钟 > 1%） | 告警 + 发布值班 | ≤ 2 分钟 | 一条「触发条件已命中，指标值 X」的判断记录 |
| T1 审批 | 服务 owner 一句话确认「同意回退」；涉及多组件联动或数据面时升级到变更经理 | 服务 owner（审批）／发布值班（提请） | ≤ 2 分钟 | 确认留痕（值班频道 / 值班记录） |
| T2 定目标 | 目标产物以回滚方案「目标产物」栏为准（明确到 `git-<sha7>`），**不现场翻 history 挑修订号**；确实要按修订号退时，按上一节三步辨认 | 发布值班 | ≤ 1 分钟 | SHA / 修订号写入值班记录 |
| T3 执行 | 生产走路径 C（Git 提交，PR review 即 T1 的审批留痕）；蓝绿走路径 D；路径 A/B 仅限演练环境 | 发布值班 | ≤ 3 分钟（含 GitOps 同步 30–120 秒，见第 14 章） | 回滚 PR / 切流记录 |
| T4 验证 | 按「回滚验证」清单核对四判据（见下） | 发布值班 | ≤ 3 分钟 | 验证输出贴入值班记录与发布 PR |
| T5 收尾 | 观察窗口长度按第 20 章错误预算定；归因与复盘写入事故文档 | 服务 owner + SRE | 发布窗口结束前 | 复盘条目 |

生产回滚的「审批」不是增设一道人工关卡，而是把 T1 的确认与 T3 的 PR review 合并成一次 Git 操作：紧急情况下回滚 PR 带 `rollback` 标签优先合并，事后补完整复盘——这是公理 5「Git 为唯一真相」在紧急路径上的完整含义：快，但不绕过审计 [R-13-7]。

**T0 的边界：触发条件是判据，不是感觉**。指标劣化但未命中触发线（如 5xx 0.4% 未到 1%）时，正确动作是「观察 + 记录 + 缩短复查间隔」，而不是提前回退——提前回退把一次抖动升级成一次真实发布事故，还烧掉不该烧的错误预算（见第 20 章）。反向同样成立：触发条件已命中，值班却「再观察一下」，每多等一个复查间隔就多承担一个窗口的劣化。所以 13.4 模板把触发条件写成「连续 3 分钟 > 1%」这类**带持续窗口与复查间隔的可判定形式**，而不是「5xx 明显上升」这类形容词——窗口与间隔就是在 T0 阶段替值班顶住「提前退」与「拖着不退」两个方向的压力的机制 [R-13-7]。

**T4 的四个通过判据**（缺一不算回滚完成）：① `image` 为目标 SHA 且 `availableReplicas` 等于 `replicas`；② 连续 30 次 `/healthz` 全 200，5xx 比例回落到基线；③ 触发条件对应的指标停止恶化并开始回落——判据是**趋势反转**而非瞬时值，回退后旧流量排空与新副本接流有惯性延迟；④ `rollout history` 出现新修订，或蓝绿路径下 Service selector 已指回旧 SHA——「回滚发生过」必须有集群里的记录可查。

**T5 之前的退路：回滚也失败怎么办**。回滚不是流程终点，T4 验证不过时有三条退路，按代价从小到大：

| 情形 | 判据 | 退路 | 代价 |
|---|---|---|---|
| 回滚目标本身也坏 | 旧 SHA 部署完成后 `/healthz` 仍非 200，或 5xx 不回落 | 停止反复回退，转入**前向修复**：以当前集群状态为基线出 hotfix，走同一条发布链路重新过门禁 | 发布窗口延长，需要 owner 重新走 T1 审批 |
| 回滚动作被环境卡住 | 路径 C 的同步结果卡在 Pending / 配额（13.2.2 形态 3、4） | 先解决容量或配额让回滚续跑；蓝绿部署可先把 Service selector 切回旧版本（路径 D 改 selector 不占 Surge 容量，不受影响） | 回退时效超出方案承诺的 5 分钟，按超时记录复盘 |
| 回滚成功但数据已按新格式写入 | 应用侧四判据全绿，但业务数据仍是新 schema | 应用回滚不解决数据——回到 13.2「本书观点」的边界，触发第 16 章 expand–contract 的共存预案；此场景的回滚方案在设计阶段就该判废 | 最重：处置由数据面主导，不再是本章的回滚问题 |

一条禁止动作：**连续回退**。两次回滚验证都不过时，第三次必须停下来做归因，而不是再退一次——连续回退会让线上交替部署两个互不兼容的状态，比停在任一版本上更糟。这条是本书观点，由 13.1 合成案例的「第二堵墙」（回滚让服务更糟）直接推出，方法论同类失效模式见 [R-13-9]。

**runbook 本身也要演练**。上表的 T0–T5 与 `hack/rollback-drill.sh` 是两份东西：脚本验证「命令可执行」，runbook 验证「人知道在哪一步做什么」。两条纪律：其一，每季度在 staging 重演一次 runbook，T1 审批人与 T3 执行人按当时值班的真实人员来，不安排熟悉流程的老手代演——演练要暴露的正是「只有一个人会回滚」这类组织风险；其二，阶段时限以演练实测为准修订：脚本输出中路径 A/B 的耗时就是 T3 + T4 时限的实测上限，冷启动慢或副本数大的服务若实测超过时限两倍，应把方案时限放宽并注明依据（参照前文 HPA 数字例的 `maxReplicas` 口径），而不是让值班在不可能达成的时限里仓促宣布完成——那等于把 T4 验证变成走过场。

**回滚验证**：

```bash
kubectl -n order-demo-prod get deploy gateway -o jsonpath='{..image}{"\n"}'
kubectl -n order-demo-prod get deploy gateway \
  -o jsonpath='{.status.availableReplicas}{"\n"}'
kubectl -n order-demo-prod get svc gateway -o jsonpath='{.spec.selector.version}{"\n"}'
./hack/verify.sh
kubectl -n order-demo-prod rollout history deployment/gateway
```

通过标准：`image` 为 `git-<OLD>` 且与 `docs/rollback-plan.md` 的目标产物一致；`availableReplicas` 等于 `replicas`；蓝绿路径下 Service 的 `spec.selector.version` 指向旧 SHA；连续请求恢复 200、5xx 回落到基线；`rollout history` 中本次回退产生了一条新的修订记录（而不是「什么都没发生」）。**没有在 staging 演练过回滚，就不允许进入生产发布**（CL-G-07），这是本章对公理 6 的落地。

## 回到第 1 章：H5「想回滚却发现没有回滚方案，或 schema 不兼容」

第 1 章那起「只改了一行配置」的事故里，值班同学最无力的时刻不是服务报错，而是**决定回滚之后发现没有东西可退**：命令没人写过、上一版 SHA 没记、唯一一次 `rollout undo` 还把旧版本推进了一个读不懂新表结构的境地。**回滚方案先于发布方案，是这条事故最贵的教训**。本章把这句教训拆成了可以打勾的东西：13.2 的六要素回滚方案、13.4 的 `docs/rollback-plan.md` 模板与 `hack/rollback-drill.sh` 演练脚本、13.6 的 CL-13-03 门禁，以及 13.5 里「演练用 `undo`、生产用明确 SHA + Git」那条分工。至此，应用侧的一半被补上了。

补上这一半之后，回头再看那个时刻：**真正让人无力的不是「退不回去」，而是「发现自己在需要退的时候才开始准备退」。**那 33 分钟里，前几分钟用来找命令，中间用来互相确认「能不能退」，剩下的用来接受「只能往前修」。这三种消耗，在发布之前都能用一小时演练省掉。

另一半「schema 不兼容」本章不解决：13.2 的「本书观点」划给第 16 章 expand–contract；「指标不对自动退」那一半划给第 15 章。第 31 章会重演整起事故，逐条核对 H5 的收口。
