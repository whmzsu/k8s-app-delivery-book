## 1.1 事故引子：只改了一行配置（合成案例）

> **合成案例声明**：本节事故是**为教学合成的虚构案例**，非真实事件复盘，不指向任何公司或产品；它把八类失效点压到同一时刻便于读者一次数出。L3 资料只支撑「反模式方法论」与行业现状，不证明事故真实发生 [R-01-8]。

周五 14:32，值班同学接到一个普通需求：把 `PAYMENT_TIMEOUT_MS` 从 `3000` 调到 `5000`。他改了一行 ConfigMap，顺手把镜像写回 `latest`、用 `kubectl edit` 当改法、没动探针、没写回滚步骤、没确认告警手册。14:35 开始滚动更新，十五分钟后 `/orders` 稳定返回 500。

这不是产品 bug——Kubernetes 每个控制器都在按设计工作。失控的是**决策**：这次变更没有一处能回答「跑的是哪份产物、配置从哪注入、坏了退到哪、谁有权改」。下表按时间线把八个失效点钉住，每个标注**详见第 X 章**，即全书索引。

| 时刻 | 编号 | 事故中的具体现象 | 失效的不是工具，是决策 | 详见 |
|---|---|---|---|---|
| 14:33 | **H1** | `gateway` 的镜像写的是 `:latest`，昨晚一次 CI 已经把它覆盖成另一个提交；线上跑的不是发版同学以为的那份产物 | 把可变标签当成版本，产物不可追溯、回滚没有目标 | **详见第 3 章**，落地见第 6 章，门禁见第 24 章 |
| 14:34 | **H2** | 有人 `kubectl edit` 直接改了运行中的 Pod 想「先加一行环境变量」，几秒后被改回去 | 分不清「改运行状态」和「改期望状态」，不知道谁有权改 | **详见第 2 章**，深化见第 14、27 章 |
| 14:36 | **H3** | 滚动更新卡住：新 Pod 一直不 `Ready`，旧 Pod 又被摘流，可用副本掉到 0 | 没有 readiness 判据，发布停在一个永远不健康的版本上 | **详见第 8 章**，深化见第 13、15 章 |
| 14:40 | **H4** | 有人临时补了个过于激进的 liveness，探到一次慢请求就杀容器，引发 `CrashLoopBackOff` 重启级联，现场没人能第一时间定位 | 探针语义被当成「心跳」，没有速查表与止血动作 | **详见第 23 章**，根因见第 8 章，信号见第 21 章 |
| 14:45 | **H5** | 决定回滚，却发现从没演练过；且这次配置改动夹带了一次不兼容的字段变更，退回旧镜像也读不了新数据 | 没有「先于发布」的回滚方案，数据变更不可共存 | **详见第 13 章**，深化见第 16、15 章 |
| 14:50 | **H6** | 想通过轮换数据库凭据救场，却发现 `DB_PASSWORD` 明文写在和业务配置同一个 ConfigMap 里，改一处全崩，轮换还得重建 Pod | 配置与凭据混在一起，凭据边界不清 | **详见第 9 章**，环境条件见第 4 章，动态凭据见第 26 章 |
| 15:00 | **H7** | 有人为「先止血」手工 `kubectl edit` 改了生产副本数，Git 里没有对应声明，之后谁也说不清集群和仓库哪个对 | 存在手工变更通道，Git 不是唯一真相 | **详见第 14 章**，环境条件见第 4 章，处置见第 23 章 |
| 15:05 | **H8** | 告警响了，页面只有一句「5xx 偏高」，值班同学不知道该看哪个指标、敲哪条命令、找谁 | 告警不可行动，没有 runbook | **详见第 22 章**，runbook 见第 23 章，判据见第 20 章 |

八个点里**没有一个是 K8s 缺陷**：`latest`、`kubectl edit`、滚动更新、liveness、ConfigMap、告警都是官方文档写清楚的行为 [R-01-1][R-01-2]，缺的是把它们组织成「可验证、可追溯、可回退的变更」的决策。复现方式见 1.4 的清单与脚本；从第 2 章起每章补上其中一点，第 31 章用同一坐标系重做一遍。

### 1.1.1 现场还原：三段对话、三条曲线、三次错误决策

八个失效点不是同时爆发的，而是**三次决策**像三道焊点，逐个把退路焊死。把镜头拉近到那 33 分钟，能看清每一次「当时看起来最省事」的选择，如何让下一次选择更少。以下仍为**合成案例**，细节为教学需要而设计，不指向任何真实公司或个人。

**三条曲线先看走势**（合成数据，仅示意方向，不作容量依据）：

| 时刻 | `/orders` 5xx 率 | gateway 可用副本 | gateway 重启计数 | 现场判断 |
|---|---|---|---|---|
| 14:34 | 0.2% | 2 / 2 | 0 | 一切正常，滚动更新刚开始 |
| 14:36 | 6% | 1 / 2 → 0 / 2 | 0 | 新 Pod 不 Ready，旧 Pod 被摘流 |
| 14:38 | 41% | 0 / 2 | 0 | 可用副本归零，请求全部 5xx |
| 14:41 | 44% | 0 / 2 → 1 / 2 | 3 | 补了 liveness 后开始反复重启 |
| 14:52 | 47% | 2 / 2（但都为坏版本） | 11 | 升级被误判为「恢复」，实际稳定地错 |
| 15:05 | 46% | 2 / 2 | 11 | 手工改副本止血无效，告警仍只有一句「5xx 偏高」 |

三条曲线讲的是同一件事：**5xx 率上升的同时，可用副本先归零再「假性恢复」**——「2/2 全就绪」并不等于「2/2 都对」。

**三段对话**（值班 IM 记录，合成）：

> **14:32　产品**：帮忙把支付超时从 3 秒调到 5 秒，急，晚高峰前上线。
> **值班**：好，改个 ConfigMap 就行，模型里没动别的。

这一段埋下**决策一**：把「一个参数的变更」理解成「改一行值」，没有走「构建产物 → 校验 → 晋升 → 发布」的链路，也没人问「这次改的是期望状态还是运行状态」。

> **14:37　值班**：新 Pod 一直没 Ready，旧的上一个又下了，我先把镜像那行也顺手统一成 `latest` 试试。
> **同事**：`latest` 是不是不太好……算了先让它起来。

这一段埋下**决策一的下半段**：为了「让它起来」把镜像标签从带 SHA 改成 `latest`，从此**线上跑的是哪次提交再也说不清**——这正是 H1。

> **14:40　值班**：我加个 liveness，探到慢就重启，应该能自愈。
> **同事**：探针路径填 `/healthz` 对吧？超时给短点，反应快。

这一段埋下**决策二**：把 liveness 当成「心跳 / 自愈开关」，超时给得过短（1 秒）、`failureThreshold` 过小，一次依赖抖动就被判死，触发重启级联——这正是 H4。

> **15:00　值班**：先手动把副本加到 6 顶住流量。
> **主管**：行，先止血，回头再补到 Git。

这一段埋下**决策三**：用一个绕过 Git 的手工通道止血，`kubectl edit` 直接改生产副本数——这正是 H7；而「回头再补」在事故里几乎从不发生。

**三次错误决策，逐个焊死退路**：

| 决策 | 当时的话术 | 被焊死的退路 | 对应钩子 | 本书的替代做法（详见章） |
|---|---|---|---|---|
| 一：改运行对象 + 用 `latest` | 「改一行值就行」「统一下镜像标签」 | 产物不可追溯 → 回滚没有目标 | H1、H2 | 不可变镜像 + SHA 标签；变更只进 Git（第 3、6、12 章） |
| 二：把 liveness 当心跳 | 「探到慢就重启，能自愈」 | 健康信号失真 → 重启级联，现场无法定位 | H4、H3 | readiness 判可用、liveness 只判死锁、给足启动预算（第 8、23 章） |
| 三：手工改副本止血 | 「先止血，回头补 Git」 | 出现 Git 之外的真相 → 漂移无人可对账 | H7、H5 | 回滚方案先行；止血也走声明，事后必须回写（第 13、14 章） |

**复盘：如果只改一个决策**。三次决策里，**决策一是最贵的**——它同时摧毁了「产物可追溯」和「状态可对账」两块地基，使得后面每一次补救都只能凭感觉。反过来，只要一开始守住「不可变镜像 + 变更只走 Git」，决策二、三的破坏力会被大幅压缩：因为一旦 `/orders` 5xx 抬头，`git log` 能立刻指出「上一版是可回滚的 SHA」，回滚有明确目标，值班就不必去改运行时对象、也不必手工改副本。

这条复盘线，就是全书的主线：**先让每一次变更可追溯、可回退，再谈自动化与平台化**。第 3 章把这条线固化成 7 条主线公理，第 31 章用同一现场重演一遍，逐条对照 H1–H8 被哪一章的哪个范式补上。

## 1.2 问题与边界：K8s 把「部署」变简单，把「部署对不对」变难

读者多半已会 `kubectl apply`、也读得懂 YAML，团队却仍频繁在发布上出事——因为 Kubernetes 解决的与没解决的是两件事。

**Kubernetes 把「部署」变成一次声明式提交**：写一份期望状态，控制器持续比对并收敛 [R-01-1][R-01-2]。但**声明式终态不保证正确性**——控制器会忠实把写错的清单收敛成「稳定地错着」，不会替你回答「产物对不对、环境差异该不该进镜像、失败退到哪版」。官方《Best Practices》把经验分散在多页，却没有一条「一次变更的完整决策路径」[R-01-3]，这就是「API 手册」与「最佳实践」的鸿沟。

编排系统的价值也常被读矮：它不是「更方便的手工界面」，而是**把运维知识固化为可收敛的期望状态**——副本数、探活、摘流、回退目标都写成声明由控制器维持 [R-01-4]；一次构建、跨环境晋升是这套模型之上的工程纪律 [R-01-5]。

> **本书观点（本章第 1 条主张，不需要外部背书）**
>
> **主张**：一次变更沿「定义 → 校验 → 打包 → 晋升 → 发布 → 运行 → 观测 → 响应」前进；安全与可观测是**作用于每一环的横切属性**，不是流水线末尾才补的一个阶段。
>
> **论证**：把安全、观测、可回滚当作「上线后再补」，等于承认前七个环节可以没有判定标准就通过。一旦「发布」没有可用性与错误预算作判据，「观测」「响应」就只能靠人肉猜测，事故里 H8（告警无 runbook）与 H5（无回滚方案）正是后果。每环都带一道可验证护栏，单点失误会在进入下一环前被拦住。
>
> **反例与适用前提**：这不等于「每环都要上一套平台」。单服务团队把安全与观测做成几条 CI 检查 + 一份清单更合适；第 5 章「过度工程警戒线」处理这个边界。前提是**多人协作、跨环境晋升的变更**；一次性本地实验不在此列。

**本书的边界**：这是一本**决策书**，回答「什么场景选什么、为什么、踩过什么坑、怎么验证和回滚」；不是 API 手册或工具说明书合集。**不覆盖**控制面搭建、Operator 开发全流程、工具安装入门——那些由官方文档负责 [R-01-3]。目标读者是已会 `kubectl` 的平台工程师、SRE 与后端负责人。

### 1.2.1 常见误解 FAQ：六个最容易把人带沟里的说法

导论阶段先把误解摆上桌面，比读到一半被推翻便宜得多。每条按「误解 → 为什么错 → 纠正做法 → 指向章」展开；这些说法在团队里流传时往往带着「大家都这么干」的背书，值得逐条戳破。

**误解 1：「声明式 = 自动正确」**。Kubernetes 确实会持续把集群收敛到你声明的终态 [R-01-2]，但收敛的对象是**你写下的那份 YAML**——写错了，它就忠实地把集群收敛成「稳定地错着」：1.1 里那份没有 readiness 的清单会被一直维持，而不是被纠正。声明式保证「集群与清单一致」，不保证「清单是对的」；清单正确性由校验阶梯负责（第 11 章），语义正确性由探针与准入策略负责（第 8、25 章）。

**误解 2：「装了 GitOps 就是 L2」**。GitOps 的口径是「Git 声明期望状态 + 控制器持续收敛 + Git 是唯一变更入口」（1.5 白话）；只把 YAML 存进 Git、生产仍可 `kubectl edit`，不算。1.3.1 自评样例里那家「装了 Argo CD」的团队稳在 L1。判定看三道门：入口唯一性、产物一一对应、回滚演练证据——装了哪个控制器不在判据里。详见第 14 章。

**误解 3：「回滚 = 把改动改回去就行」**。回滚的定义是把线上恢复到**上一个已知良好版本**（1.5）。「改回去」三个字隐含三个前提：你知道上一个良好版本是哪个 SHA（产物可追溯，H1）；旧版本与新数据可共存（schema 兼容，H5）；这条退路最近演练过（公理 6）。事故 14:45 那次回滚失败，正是三个前提全缺。做法见第 13 章，数据侧见第 16 章。

**误解 4：「SLO 就是可用性百分比」**。一句「99.9%」不构成 SLO：没有 SLI 的测量口径、没有统计窗口、没有错误预算与冻结规则，它只是口号。1.5 的最小卡片有四个字段（`sli` / `window` / `objective` / `freeze_rule`），缺一个就没法驱动「要不要冻结发布」这类决策。反例：某团队把「可用性 99.9%」写进 OKR 就当有了 SLO，预算名义上耗尽时没人敢提冻结——因为既无窗口也无冻结规则，承诺根本无法执行。正式定义详见第 20 章；在此之前不要拿「SLO 不达标」当任何决策依据。

**误解 5：「配置打进镜像更方便」**。改一个超时参数就要重建镜像，意味着每个环境各构建一次、每次配置变更都被抬升为一次带全部发布风险的操作——同时违反公理 1（build once, promote）与公理 3（配置与镜像分离）[R-01-6]。「方便」的代价是产物不可追溯、发布面扩大、回滚颗粒度变粗：想退回旧配置，只能连镜像一起退。环境差异怎么表达见第 4 章，配置与密钥怎么分离见第 9 章。

**误解 6：「K8s 会自动帮你修好一切」**。控制循环只做一件事：把实际状态收敛到声明状态 [R-01-2]。声明缺失（没有探针、没有回滚目标、没有凭据来源）时，控制器无事可做；声明错误时，它会把错误维持住。1.1 那 33 分钟里所有控制器都在按设计工作 [R-01-1]，失控的从来都是决策层，不是集群。

## 1.3 全书总论坐标系：一主线、两横切、一演进轴、一地基

七篇不是并列目录，而是一套坐标系。把 1.1 的事故放进去，就能看出「断在哪一环、该翻哪一章」。

```
主线（一次变更的旅程）
  定义 → 校验 → 打包 → 晋升 → 发布 → 运行 → 观测 → 响应
  └─ 第 2 篇 ─┘   └─ 第 3 篇 ─┘  └ 第 4 篇 ┘  └── 第 5 篇 ──┘

横切 A：安全 · 策略 · 凭据（第 6 篇）—— 作用于主线每一环
横切 B：可观测 · 可回滚 · 可审计（第 5 篇集中展开）—— 贯穿全书

演进轴（第 7 篇）：L0 手工 → L1 自动化 → L2 GitOps → L3 自助平台

地基（第 1 篇）：心智模型 · 原则 · 环境拓扑 · 工具链地图 —— 支撑以上全部
```

> **本书观点（本章第 2 条主张，不需要外部背书）**
>
> **主张**：团队交付能力可粗分为 **L0 手工 → L1 自动化 → L2 GitOps → L3 自助平台**；工具数量不等于成熟度。
>
> **论证**：四级的区别不在「装了几个控制器」，而在「变更入口是否唯一、产物是否可追溯、回滚是否演练过」。只跑 `kubectl apply` 却把 SHA 标签、回滚演练、检查清单做扎实的团队，比装了四套控制器仍手工改生产的团队更接近 L2；行业调查里工具数量与交付稳定性并不同步增长，正是背景 [R-01-8]。
>
> **反例与适用前提**：分级是诊断工具而非考核表。20 人团队停在 L1 可能就是最优解；强行跳到 L3 反而引入 CRD 与 Operator 负债（见第 5、27 章）。自评表与改造路线见第 31 章。

### 1.3.1 L0–L3 各级的可观察行为清单与自评样例

「我们在 L2」这类自评最容易失真，因为大家评的是**愿望**而不是**当前可观察的行为**。下面把每一级拆成四列**能当场看见**的行为，自评时只勾「现在就能被第三方验证」的项，达不到就往下退一级——**宁可低估，不要高估**。

| 级别 | 变更入口（谁能改生产、怎么改） | 产物可追溯（线上跑的是哪份） | 回滚能力（坏了怎么退） | 观测与响应（怎么知道、怎么动手） |
|---|---|---|---|---|
| **L0 手工** | `kubectl edit/apply` 直连生产，多人多通道，无审批 | 用 `latest` 或人肉记忆；说不清当前 SHA | 靠「再改回去」，多数没演练过 | 靠用户报障；告警一句话、无 runbook |
| **L1 自动化** | 有 CI 构建与固定脚本，但**部署动作仍可手工触发/手工补刀** | 镜像带 SHA，但多环境可能各建各的 | 有脚本回滚，未定期演练 | 有基础监控；告警能发但对事不可行动 |
| **L2 GitOps** | 生产变更**只允许**经 Git → 控制器收敛，手工改动被检测与纠正 | `git log` 与线上 SHA 一一对应，可反查 | 回滚＝回退一个 commit，**定期演练**并留记录 | SLO + 错误预算驱动告警与冻结，每条告警指向 runbook |
| **L3 自助平台** | L2 之上，业务团队经**自助入口**发起，平台内置护栏与配额 | 同上，且跨多集群/多环境统一追溯 | 同上，且回滚/升级作为平台能力一键完成 | 平台提供黄金信号与默认 SLO 模板，护栏前置拦截 |

**四个自评判据**（逐条回答，全部为「是」才够上一级）：

1. **入口唯一性**：能否举出「最近一个月所有生产变更」的完整清单？如果不能，说明仍有 Git 之外的通道（对应公理 5）。
2. **产出一一对应**：随便挑一个线上 Pod，能否在 5 分钟内答出「它对应哪个 commit、哪次构建」？答不出说明产物不可追溯（对应公理 1、2）。
3. **回滚证据**：最近 90 天是否有**至少一次**带时限、带验证结果的回滚演练记录？没有就按「无回滚能力」处理（对应公理 6）。
4. **告警可行动**：随便挑一条 paging 告警，能否在 1 分钟内说出「看哪个指标、敲哪条命令、找谁、是否冻结发布」？答不全说明告警不可行动（对应公理 7）。

**自评样例（一家 15 人团队，合成）**：

| 判据 | 团队现状（可观察事实） | 结论 |
|---|---|---|
| 入口唯一性 | 部署走 CI，但故障时仍有人 `kubectl edit` 生产；无变更清单 | ✗ 不满足 L2 |
| 产出一一对应 | 镜像带 SHA，能反查 commit | ✓ 满足 L2 |
| 回滚证据 | 有回滚脚本，但近半年没演练过 | ✗ 按「无回滚」处理 |
| 告警可行动 | 告警能发，但无 runbook，值班靠问人 | ✗ 不满足 L2 |

四项里三否一过 → 该团队**稳在 L1，未到 L2**，尽管它「装了 Argo CD」。这就是「工具数量不等于成熟度」的典型：装了 GitOps 控制器，却还有手工通道、无演练、告警不可行动，L2 的三道门只过了一道。**改造顺序**应是先堵手工入口（第 14 章）、再补回滚演练（第 13、23 章）、最后把告警接到 runbook（第 22、23 章）——而不是再装第五个控制器。第 31 章会给出可直接填写的自评表与三档团队规模的改造 ROI 样例。

### 1.4.1 第一次跟着本书做一次变更：从 clone 到第 6 章最小闭环

1.1 可以从反面读，也可以从正面做一遍。本节给一条读者可照着敲的路径：checkout `ch06-first-loop`，在一次性 kind 集群里跑通最小闭环，然后做一次「走 Git 的小变更 + 回滚演练」。每步都给**判据**——判据不满足就停在该步排查，不要往下走。清单的完整设计动机在第 6 章展开，这里只给执行序列。

**步骤 0 · 取得现场**：

```bash
git clone <你的 order-demo 仓库地址> order-demo && cd order-demo
git checkout ch06-first-loop
git log -1 --oneline
```

判据：`git log` 输出中的短 SHA 共 7 位，记下来，后面镜像标签与 `version` 标签都要用它。本文以 `a1b2c3d` 代指你实际得到的 SHA。

**步骤 1 · 起一次性集群**（不要在共享集群上练手）：

```bash
kind create cluster --name order-demo-dev
kubectl get nodes
```

判据：节点状态为 `Ready`。

**步骤 2 · 建命名空间并应用最小闭环清单**（完整文件随 tag 提供，此处给出契约最小形态：镜像带 SHA、配置与镜像分离、非 root 运行；探针到第 8 章才加、资源基线到第 17 章才加——每章只加当章的增量）：

```yaml
# deploy/minimal/gateway.yaml —— ch06-first-loop 的最小闭环形态（Kubernetes 1.32+）
apiVersion: v1
kind: Namespace
metadata:
  name: order-demo-dev
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-demo-config
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
data:
  PAYMENT_TIMEOUT_MS: "3000"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: kubectl
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: gateway
        app.kubernetes.io/version: a1b2c3d   # 换成步骤 0 记下的 7 位短 SHA
        app.kubernetes.io/managed-by: kubectl
    spec:
      securityContext:
        runAsNonRoot: true
      containers:
        - name: gateway
          image: registry.example.com/order-demo/gateway:git-a1b2c3d   # 同上，禁用 latest
          ports:
            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: order-demo-config
---
apiVersion: v1
kind: Service
metadata:
  name: gateway
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
spec:
  selector:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
  ports:
    - name: http
      port: 8080
      targetPort: http
```

```bash
kubectl apply -f deploy/minimal/gateway.yaml
```

**步骤 3 · 验证闭环**：

```bash
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=60s
kubectl -n order-demo-dev port-forward svc/gateway 8080:8080 >/dev/null 2>&1 &
curl -fsS http://127.0.0.1:8080/healthz
kubectl -n order-demo-dev get pods -l app.kubernetes.io/component=gateway
```

判据：`curl` 返回 200；两个 Pod 均 `Running`。

**步骤 4 · 验证产物可追溯**（H1 的正面做法）：

```bash
kubectl -n order-demo-dev get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}'; echo
```

判据：输出以 `:git-a1b2c3d` 结尾且不含 `latest`，与步骤 0 的 `git log` 对得上。对照 1.1：事故现场这一步输出是 `:latest`，谁也说不清线上跑的是哪次提交。

**步骤 5 · 走一次小变更**：把 `PAYMENT_TIMEOUT_MS` 从 `3000` 改成 `5000`——只改 Git 里的清单文件，再重新 apply。注意 `envFrom` 注入的环境变量不会随 ConfigMap 更新自动生效，需要滚动重启让新值进入 Pod（这也是第 9 章引入不可变 ConfigMap 的动机伏笔）：

```bash
# 编辑 deploy/minimal/gateway.yaml：PAYMENT_TIMEOUT_MS: "3000" → "5000"
kubectl apply -f deploy/minimal/gateway.yaml
kubectl -n order-demo-dev rollout restart deployment/gateway
kubectl -n order-demo-dev rollout status deployment/gateway
```

判据：`kubectl -n order-demo-dev get cm order-demo-config -o jsonpath='{.data.PAYMENT_TIMEOUT_MS}'` 输出 `5000`；`kubectl -n order-demo-dev get pods` 显示 Pod 重建时间在最近 2 分钟内，且 `/healthz` 仍返回 200。

**步骤 6 · 演练一次回滚**（公理 6 的第一次体验）：

```bash
# 把 deploy/minimal/gateway.yaml 中的值改回 "3000"
kubectl apply -f deploy/minimal/gateway.yaml
kubectl -n order-demo-dev rollout restart deployment/gateway
kubectl -n order-demo-dev rollout status deployment/gateway
curl -fsS http://127.0.0.1:8080/healthz
```

判据：ConfigMap 值回到 `3000`，`/healthz` 仍为 200。说明：真正的回滚（第 13 章）是「回到上一个已知良好版本并恢复流量」，这里只是先建立「变更可退、退路可用」的肌肉记忆。

**步骤 7 · 对照复盘**：这次变更与 1.1 事故逐点对照——镜像带 SHA（H1 未犯）；没有 `kubectl edit`，改的是清单再 apply（H2、H7 未犯）；变更前后都有验证命令（H3 未犯）；退路先想好再动手（H5 未犯）。剩余的 H4、H6、H8 分别由第 8、9 章（探针与配置/密钥）与第 22、23 章（告警与 runbook）补上。

**何时不该照本节走**：本节的每步判据是为「多人协作、跨环境晋升」的变更准备的（与 1.2 本书观点块的适用前提一致）。单人仓库的本地 prototype、一次性验证某个字段的实验，可以直接改、直接 apply，走完即删——把七步流程套在五分钟就会销毁的环境上，是另一种过度工程。判断标准只有一条：**这份清单会不会离开你的本机**。会，就按本节顺序走；不会，怎么快怎么来。

**清理**：

```bash
kind delete cluster --name order-demo-dev
```

## 1.5 统一口径与公理体系（7 主线公理 + 2 衍生护栏）

以下为**全书唯一口径**：首次提及给一句白话并指向正式定义章；正式定义之前不得拿术语当推理前提（例如第 1 章不能拿「SLO 不达标」当不发布的理由，SLO 到第 20 章才定义）。

| 术语 | 本书白话（首次提及） | 正式定义 |
|---|---|---|
| 应用 application | 一组共同交付、共同回滚的工作负载与配置的最小单元，全书贯穿案例即 `order-demo`；不等于单个 `Deployment` 或 `Pod` | 详见第 2 章 |
| 环境 environment | 一套有独立凭据、独立配额、独立晋升入口的集群或命名空间集合，即 dev / staging / prod；命名空间不是完整隔离边界 | 详见第 4 章 |
| 晋升 promote | 把**已构建的同一制品**逐级送到不同环境，只改配置不改产物；不是「重新打包发到生产」 | 详见第 3 章 |
| 发布 release / deploy | 让某个版本的制品在生产开始承载真实流量，并可按预案退出；「推到仓库」「部署到集群」都不叫发布 | 详见第 13 章 |
| 回滚 rollback | 把线上恢复到**上一个已知良好版本**；必须先有方案再有发布，不等于「修一下再发一版」，也不等于数据回退 | 详见第 13 章 |
| 漂移 drift | 集群实际状态与 Git 声明状态不一致，多由手工变更或控制器副作用产生 | 详见第 14 章 |
| GitOps | Git 里写什么，集群就变成什么；Git 是唯一变更入口，且带持续收敛与漂移纠正（只把 YAML 存进 Git 不算） | 详见第 14 章 |
| SLO | 服务好坏的量化承诺，由 SLI 与错误预算构成，是告警与发布冻结的依据；不是监控大盘或一句可用性口号 | 详见第 20 章 |

**七条主线公理（不可协商项，第 3 章 3.2 展开）**——1.1 事故里 H1、H5、H7 的失守，都落在其中。全书另含 2 条衍生护栏（SSH 禁入生产、密钥/state/.env 不入 Git，由主线派生、同等不可协商），故**全书不可协商项共 9 条**，计数口径与 `glossary.md` 第二节、第 3 章一致：

| # | 公理 | 一句话 | 越线的可观察现象 |
|---|---|---|---|
| 1 | build once, promote | 同一制品跨环境晋升，不为每个环境重新构建 | dev 验证过的产物和 prod 跑的不是同一个 SHA |
| 2 | 不可变镜像 + git SHA 标签 | 禁用 `latest`，标签与内容一一对应 | `kubectl get deploy -o jsonpath='{..image}'` 出现 `latest` |
| 3 | 配置与镜像分离 | 环境差异只体现在配置，不体现在产物 | 改一个参数要重建镜像 [R-01-6] |
| 4 | 非 root 最小镜像 | 默认以非 root 运行 | `securityContext` 缺 `runAsNonRoot: true`、镜像以 root 启动 |
| 5 | Git 为唯一真相 | 生产变更只允许走 Git，禁止手工 `kubectl edit` 改生产 | 审计日志里出现针对生产的手工变更 [R-01-5] |
| 6 | 回滚方案先行 | 没有验证过的回滚方案，不允许发布 | staging 找不出一次带时限、带验证结果的回滚演练 |
| 7 | SLO 先行于告警 | 先有 SLO 与错误预算，再据此设计告警 | 告警阈值拍脑袋、没有冻结规则（SLO 正式定义详见第 20 章） |

> **衍生护栏（2 条，与七条主线公理同等不可协商）**：第 8 条 SSH 禁入生产（派生自公理 5 的排障侧，落地第 23 章）；第 9 条 密钥、Terraform state、`.env` 一律不入 Git（派生自公理 3 的凭据侧，落地第 4、26 章）。这 2 条不进上方主线速查表，因「越线现象」非单条变更可敲命令直接看出，但任何章节建议均不得与之冲突。

> 术语与公理的完整版见附录 E。任何章节不得给出与上表冲突的建议；确需例外，必须显式写出「例外前提 + 补偿措施 + 例外有效期」，见第 3 章的「例外机制」。

**1 页最小 SLO 卡片（引出版，口径与第 20 章一致）**：SLO 到第 20 章才正式定义，这里只给白话「服务好坏的量化承诺」与一张占位卡片；字段正式推导**详见第 20 章**，本卡片不得用作发布决策前提。

### 1.6.2 四条路径的「读完能做什么 / 跳过会缺什么」

上表只回答「从哪读到哪」，这一节回答两个更实际的问题：读完这条路径你能**当场产出什么**，以及跳过某些章**会缺哪块护栏**——缺的那块不是抽象损失，而是 1.3 对照表里一个具体钩子的防线。

| 路径 | 读完能做什么（可验证产出） | 跳过哪些章会缺什么 |
|---|---|---|
| 研发 / 后端（1–3 → 6–10 → 12–13 → 20–21） | 写出一份带 SHA 标签、配置分离、能说清回滚目标的应用定义；在 code review 里判断「这份改动会不会破坏发布」；对 gateway 可用性给出量化判据 | 跳过 4–5：不知环境边界与工具边界，容易把 dev 套路搬进 prod（公理 9 的高发区）；跳过 14–19：不懂 GitOps 收敛与运行期治理，联调生产漂移时无从下手；跳过 22–23：出事后只能靠问人（H8 重演） |
| 平台 SRE（全书，重点 4–5、14–19、22–31） | 搭起三环境晋升链与护栏，完成 1.3.1 式自评并给出团队 L 级判定与改造顺序 | 无——该路径覆盖全书；若必须压缩，最先不能砍第 14 章（Git 唯一真相，公理 5 的落地）与第 23 章（runbook 与演练，公理 6 的落地），缺这两章，其余护栏都在空转 |
| 正在救火（23 → 17 → 8 → 21） | 按速查表止血、按 runbook 处置，区分「资源不够」与「探针误杀」两类高发故障 | 跳过 12–16：止血后不知道变更该怎样规范地送进生产，下次还得出事；跳过 20：不知道何时该冻结发布，修复期间继续变更可能引发二次事故（公理 7 缺失的代价） |
| 工具速查（第 1 章 + 第 5 章 + 附录 F / G / H） | 对「选什么、不选什么、怎么退」快速给出带前提与反例的答案 | 只有索引没有案例支撑，论断记不住边界；建议至少补读每个选中工具的主责章——选 GitOps 读第 14 章、选金丝雀读第 15 章、选准入策略读第 25 章 |

**跳读的总原则**：你跳过的不是章节，是那章负责的钩子防线。跳过某章前，先在 1.3.2 地图里找到它对应的行，明确「缺的是什么护栏、这个风险现在由谁承担」；救火路径读完回补时，也按这张地图核对 H1–H8 是否都有主责章兜底。

**拿不准选哪条路径时**，用最近一次生产变更卡住的环节反推：说不清线上跑的是哪份产物 → 先补第 3、12 章（H1）；说不清坏了退到哪 → 先补第 13、16 章（H5）；说不清谁有权改、改动从哪来 → 先补第 14、26 章（H7）；出过事先说不清原因 → 先补第 8、23 章（H3、H4）。卡点最多的那条，就是你的首读路径。
