## 22.1 问题与反模式：几百条告警里，真出事那条被淹了

**合成案例**。周一 02:14，`order-demo` 的值班手机连着震了 37 次：`api` 某个容器 CPU 超 60%、某个节点磁盘剩 18%、一次滚动更新期间 readiness 短暂失败，凡此种种都来自「某个阈值被越过」。02:31，真正该叫人的那条来了——gateway 入口 5xx 在 5 分钟内吃掉了一大块错误预算。它被排在通知列表第 38 位，标题只有四个字「服务异常」，没有链接、没有首步动作。值班同学盯着它，第一反应不是止血，而是打开仓库找「这个告警当初是谁加的、超过多少算严重」。等翻到规则，故障已经持续了 25 分钟。

这就是第 1 章 H8 的原形：**告警响了，却没有 runbook，值班不知道做什么**。噪音不是「告警太多」这么简单，而是「没有任何一条告警能直接转化为动作」。告警数量与可靠性之间没有必然关系，Google SRE 体系把这条分界线写得很清楚：paging 必须基于症状、可行动、有升级路径，原因型告警只配做上下文 [R-22-4][R-22-6]。

这一晚有个残酷的算术：**37 条噪音换来 25 分钟延迟。**平均每条噪音只花掉几十秒——看一眼、判断是噪音、划掉——单次成本低到不值得抱怨。**但它们的总和，正好等于一次真故障的响应窗口。**噪音的伤害从来不体现在单条上，而体现在「真事来的那一刻，你还剩多少注意力」。

三个高频反模式：

**反模式一：每个容器 CPU 都发一条告警。** 现象是凌晨被一堆互不相干的阈值吵醒，真正的用户可感故障被淹没。根因是**把「原因」当「症状」告警**：CPU 高不等于用户受损，它只是可能的原因之一；而一个 5xx 突增，无论 CPU 是否正常，都需要有人处理。本章的替代做法是只保留由第 20 章错误预算推导的症状型告警，把资源类阈值降为 dashboard 上下文或 ticket，不进 paging [R-22-4][R-22-5]。

「多一条也无害」这个想法，是规则膨胀的唯一入口。它之所以站不住，是因为**告警的成本不在产生它的那一刻，而在它响的那一刻**——你加规则时成本为零，别人被吵醒时成本全部由他承担。**这是一种典型的「决策者与承担者分离」的配置**，所以它永远不会靠自觉收敛。

**反模式二：告警内容只有「异常」两个字。** 现象是值班得现查「怎么办」，故障时长被拉长在查资料上。根因是把告警当成「通知」，而不是「一张待执行的工单」。本章要求每条 paging 告警强制带 `runbook` 注解、`first_action` 首步动作、`dashboard` 下钻链接与 `escalate` 升级路径；四者缺一不允许合并 [R-22-6][R-22-1]。

这里要区分两个时刻的**信息需求**：告警设计时，写它的人在系统旁边、脑子清醒、知道上下文；告警触发时，读它的人刚被吵醒、可能没见过这个系统。**「服务异常」这四个字是在第一个时刻写的，却要在第二个时刻被读懂。**所以告警内容的判据不是「写得对不对」，而是「**凌晨三点、刚醒的那个人，看完知道第一步敲什么**」。

**反模式三：直接在 Alertmanager UI 改路由或加静默。** 现象是「线上路由」和仓库里的配置对不上，出事后无法回答「谁在什么时候把 paging 关了」，也无法回滚。根因是把告警规则当成运行时可调参数，而不是代码。本章用**告警即代码**：规则、路由、抑制、静默全部进 Git，走 PR 与单测，应急静默用 `amtool silence add` 且强制登记原因与到期时间 [R-22-3][R-22-1]。

这条反模式的特殊性在于：**它恰恰发生在「最需要快速动作」的时刻。**UI 点两下就能压掉噪音，走 PR 要等评审——**流程的摩擦和人的急迫，在这里方向完全相反**。所以解法不能是「禁止 UI」，只能是把应急通道也做成留痕的（`amtool` 一行命令、带 author 与到期时间），**让合规路径比绕路更快**。

> 行业侧的告警疲劳并非个别现象：公开复盘里反复出现「告警量远超人手、值班对告警麻木」的模式 [R-22-7]，年度调查也把可观测与告警治理列为高频运维课题 [R-22-8]。两条只支撑「噪音是普遍问题」这一背景，不指向任何一次具体事故；本章开头的现场是合成案例。

### 22.1.1 一次漏响应的完整时间线复盘（合成案例，延伸自本章开头场景）

把 §22.1 开头那一晚展开成完整时间线，逐段标注「噪音在哪一步被制造、在哪一步被放大、在哪一步吞掉了真告警」。这是合成案例，用于推演机制失效的链路，不指向任何真实事故；「值班麻木、复盘时发现告警量远超人手」的模式在公开 postmortem 合集中反复出现 [R-22-7]，可观测与告警治理也持续位列年度运维课题 [R-22-8]。

**T-30 天（噪音制造期）**：三个团队为「上次的告警没盯住」各自补规则——DBA 加了 24 条连接数阈值，平台加了 31 条节点资源阈值，业务加了 18 条业务量波动告警。没有人对规则总量做预算：一个月内规则从 43 条涨到 116 条，全部默认走同一个 receiver，没有 severity 区分，没有 runbook 注解。每条规则单看都「合理」，合起来是每周 600+ 条通知，且没有一条附带首步动作。

**T-7 天（麻木固化期）**：值班同学当周收到 612 条通知，事后逐条核对：需要人工动作的 3 条，且全是上班时段自己发现的，没有一条是告警先于人来。值班开始固化两个危险习惯：手机对该 receiver 设免打扰、「先静默 15 分钟再判断」。这两个习惯没有登记、没有到期时间、没有评审——本质上是绕开 Git 的运行时变更，与第 14 章「Git 唯一真相」直接冲突，却因为「只是压噪音」从未被当作变更管理。

**当晚 02:14–02:26（风暴期）**：滚动更新触发的 CPU 告警 12 条、节点磁盘 8 条、readiness 抖动 17 条，37 条通知在 12 分钟内挤进通知列表。值班按习惯执行「先静默再判断」，在 UI 里手工创建了静默，matcher 写的是 `service="gateway"`——本意是压掉网关的 CPU 阈值告警，实际把 gateway 名下一切告警（包括尚未触发的快燃尽 paging）都静默到早上 8 点，无 author、无 comment、无例外编号，事后无人能从记录里还原「谁在 02:26 关掉了 paging」。

**当晚 02:26 那三十秒**（依同类事故共性还原，非原话）：

> **值班**：（第 37 次震动）又是 gateway，肯定是这次滚动的锅。
> （打开 Alertmanager，选 matcher）
> **值班**：`service="gateway"`……就这个吧，先压到早上。
> （没有写 author，没有写 comment，点了 Create）
> **值班**：好了，能睡到六点了。

这三十秒里没有任何恶意，甚至没有任何错误判断——滚动更新确实会导致 CPU 抖，静默它确实合理。真正发生的事是：**他在极度疲惫的状态下，做了一个「覆盖面比意图大得多」的变更，而这个变更不需要任何人批准、也不会留下任何解释。**系统的宽容在这里变成了帮凶：**它允许一个凌晨两点、被吵醒 37 次的人，用三十秒关掉整条 paging 通道。**

**02:31（真告警产生，被吞）**：gateway 5xx 突增，快燃尽表达式在两个窗口同时越界，`GatewayAvailabilityFastBurnPaging` 进入 pending，2 分钟后转 firing——规则侧按设计响了。但通知在路由层被 02:26 那条过宽的静默拦下：规则 firing 了，人这一侧没响。故障从此刻起无人认领，SLI 持续下跌，燃尽率继续爬升，但所有后续通知同样落在同一条静默里。

**02:52（从用户侧倒灌发现）**：客服工单出现「下单 500」投诉，值班从工单侧反查才进入处置；03:05 认领并按记忆执行回滚。从症状出现到认领 34 分钟，是分级表 5 分钟认领时限的 6.8 倍；错误预算当晚一次性烧掉约两周份额，随后按第 20 章冻结规则暂停非必要发布。

**复盘三问**（本章后续每个机制的出处）：

1. **为什么 paging 没叫到人？** 静默过宽且无留痕——所以 §22.5 强制静默必须用 `amtool silence add` 带 `--author`、`--comment` 与到期时间，且粒度精确到 `alertname`，禁止按 `service` 整体静默 [R-22-3][R-22-6]。
2. **为什么通知到了也不知道做什么？** 告警没有 runbook、没有首步动作，值班要先翻仓库找「这条规则当初为什么加」——所以每条 paging 强制 `runbook` / `first_action` / `dashboard` / `escalate` 四注解，把处置首步直接写进告警 [R-22-6]。
3. **为什么噪音能积累到 37 条？** 规则只增不减、没有命中率复盘，三个月没人问过「这 116 条里有多少真的需要人」——所以 §22.2 的分级表与周会清退流程（命中率高线、误报率红线、清退五步）是硬机制而非建议 [R-22-4][R-22-5]。

**同月重演的合成推演**：若当时已有本章机制，同一晚收敛为——规则经周会清退到本章 5 条，02:14 的 CPU/磁盘/readiness 噪音全部落在 `info` 只落库；02:31 快燃尽 paging 是当晚唯一通知，02:33 认领（`for` 2m + 路由投递 + 人工 2m 的预算分解见 §22.4.1），03:00 前恢复，预算消耗控制在单日份额内。后续小节可以随时回到这条时间线的六个时间点，对照检查每个机制关闭的是哪个环节。

## 22.2 范式与决策树：把「该不该叫人」变成一张分级表

本章要回答的决策问题是：**什么样的告警值得把人从床上叫起来，以及噪音该在哪个环节被消掉**。

这个问题的判定标准其实只有一个，而且很朴素：**这条通知，接收者此刻能做什么？**能动作的才配 paging，说不出动作的都只是上下文。所有分级表、抑制规则、静默纪律，本质上都是在把这一句话变成可执行、可审计的机制——**因为靠自觉判断「能不能动作」，在凌晨两点最不可靠。**

答案先立一条硬边界：**只有症状型告警才能 paging**。症状＝用户当下可感的坏（SLO 燃尽、5xx 突增、延迟越界）；原因＝可能解释症状的系统量（CPU、副本数、队列长度）。原因型告警不是没用，它只能作为下钻上下文或 ticket，绝不半夜叫人 [R-22-4][R-22-6]。

**告警分级表**（阈值全部由第 20 章错误预算推导，指标名取第 21 章 `metric-naming.md`）：

| 级别 | 触发条件 | 路由目标 | 响应时限 | 何时不该 paging |
|---|---|---|---|---|
| `paging` | 快燃尽：1h 与 5m 双窗燃尽率均 ≥ 14.4；或 5xx 突增且 SLI 跌破窗口阈值 | 值班 on-call（电话/寻呼） | 5 分钟内认领 | 单个容器 CPU / 单副本重启 / 演练窗口内 |
| `ticket` | 慢燃尽：6h 燃尽率 ≥ 6；或预算耗尽触发发布冻结 | 工单队列 + 当值群 | 1 个工作日内 | 上班时段能处理、且无用户可感恶化 |
| `info`（记录） | 3d 趋势燃尽率 ≥ 1；探针抖动；配置漂移检出 | 仅落库 + 周会复盘 | 不要求即时响应 | 任何会触发人工通知的场合 |

**多窗口判据**与第 20 章逐字一致：快窗 1h/5m ≥ 14.4、慢窗 6h ≥ 6、趋势 3d ≥ 1，冻结判定 `slo:order_demo_gateway:release_freeze == 1`。之所以坚持「双窗」，是因为单一快窗会被一次采集抖动点着，单一长窗又会漏掉突发：短窗确认「正在发生」，长窗确认「不是噪声」，两者与预算同源才可复核 [R-22-1][R-22-4]。

**完整矩阵：燃尽率 × 级别 × 路由 × 响应时限（含抑制关系）**。把分级表、第 20 章窗口口径与 §22.4 的路由/抑制配置合到一张表，值班排查与周会复盘都按它对照 [R-22-3][R-22-4]：

| 行 | 燃尽率 / 状态口径 | 级别 | 路由 receiver（§22.4） | 通知节奏 | 响应时限 | 抑制关系 |
|---|---|---|---|---|---|---|
| M1 | 1h/5m 双窗燃尽率 ≥ 14.4（快燃尽） | `paging` | `paging-oncall`（电话/寻呼） | `group_wait: 10s`、`group_interval: 1m`、`repeat_interval: 30m` | 5 分钟内认领 | 抑制同 `service` 的全部 `ticket`（inhibit 规则 2）；被 M3 抑制；被演练窗口静默与登记静默抑制 |
| M2 | 6h 燃尽率 ≥ 6（慢燃尽） | `ticket` | `ticket-default`（工单 + 当值群） | `group_wait: 30s`、`group_interval: 5m`、`repeat_interval: 4h` | 1 个工作日内 | 被 M1 抑制：快燃尽正在发生时慢窗必然同向越界，重复通知没有信息量 |
| M3 | 28 天预算耗尽：`release_freeze == 1` | `ticket` | `ticket-default` | 同 M2 | 当日核对冻结清单 | 抑制同 `service` 的全部 `paging`（inhibit 规则 1）：预算已空时 paging 无法改变冻结事实，恢复动作必须走工单与第 20 章例外登记 |
| M4 | 3d 趋势燃尽率 ≥ 1；探针抖动；漂移检出 | `info` | `record-only`（不挂 notifier） | 不进通知流 | 不要求 | 无通知即无抑制必要，仅落库供周会复盘与下钻 |
| M5 | p99 延迟越界（非燃尽症状） | `info` | `record-only` | 不进通知流 | 不要求 | 若同时满足 M1，由 M1 的 paging 承载，本行只做下钻上下文 [R-22-5] |

三条判读规则：

1. **抑制方向永远从「信息量更大」指向「信息量更小」**。M3 抑制 M1 不是因为预算耗尽更紧急，而是预算已空时，再 paging 也只是在重复「预算没了」这个已知事实；M1 抑制 M2 是因为快燃尽发生时慢窗必然同时越界，两条同时响只会制造重复工单。
2. **静默优先于一切抑制**。`amtool silence add` 必须精确到 `alertname` 并带 author、comment、到期时间；第 23 章固定演练窗口由 `mute_time_intervals` 声明式覆盖，不需要每次人工静默 [R-22-3]。
3. **矩阵与配置互为镜像**。本表每一格都能在 §22.4 配置里指到具体字段（`matchers`、`inhibit_rules`、`mute_time_intervals`）；表里有而配置里没有（或反之）即视为漂移，按 §22.6 CL-22-03 处置。

**噪音治理决策树**：

```
这是一条用户可感的症状吗？              否 → 降为 ticket / info，不 paging
        │ 是
阈值由第 20 章错误预算推导了吗？         否 → 回第 20 章，禁止拍脑袋阈值
        │ 是
带 runbook / 首步动作 / 升级路径了吗？   否 → 不允许合并，先补注解
        │ 是
在抑制/静默/演练窗口内吗？              是 → 按登记放行或静默，不重复通知
        │ 否
→ 允许 paging；按分级表路由，并在周会复盘命中率
```

**命中率 / 误报率的周会复盘模板**。决策树最后一行「在周会复盘命中率」不是口号，需要固定模板与可执行的清退流程。口径与分级表同源：**命中率 = 触发后确实需要人工介入且处置有效的次数 / 总触发次数**；**误报率 = 1 − 命中率**；`paging` 单独统计，`ticket` / `info` 合并统计。这一定义与「告警必须是待执行的工单」一脉相承：不需要人动的告警，从定义上就是误报，无论表达式多精确 [R-22-6]。

周会模板（每周固定 20 分钟，逐条规则过表；缺数据的规则直接进清退候选，不允许「下周再补数」）：

```markdown
# 告警复盘周报 · 第 <N> 周（order-demo-prod）

| 规则 | 触发次数 | paging 次数 | 命中（需人动且有效） | 误报 | 命中率 | 认领中位时长 | 静默覆盖次数 | 处置 |
|---|---|---|---|---|---|---|---|---|
| GatewayAvailabilityFastBurnPaging | 2 | 2 | 2 | 0 | 100% | 3m | 1（演练窗口） | 保留 |
| <其余规则逐行> | | | | | | | | |

## 本周结论
- 清退候选：<规则名>（触发 <n> 次，命中率 <x%，连续第 <n> 周低于线）
- 阈值异议：是否需回第 20 章改预算口径（是/否，PR 链接）
- 静默核对：所有静默均有 author + comment + 到期时间（是/否）
```

清退流程五步，每步留痕在 Git：

1. **入榜**：`paging` 连续两周误报率 > 50%，或单周触发 ≥ 20 次且命中率 < 30%；`ticket` / `info` 放宽到误报率 > 80%。周会登记进周报「清退候选」，附数据行，不搞临时动议。
2. **降级优先于删除**：先把 `severity` 从 `paging` 降为 `ticket`（保留上下文价值，观察两周）；仍不达标再降为 `info`。直接删除只用于「指标本身不再有意义」的规则。
3. **PR 清退**：降级与删除都走 PR，同步更新 `observability/alert-rules-test.yaml` 的输入序列，并确认 `hack/alert-drill.sh` 的 `N/N` 断言仍然成立——规则数变了，runbook 链接断言必须同步，否则门禁会拦住这次清退 [R-22-1][R-22-3]。
4. **回看上游**：清退一条症状告警前，先确认第 20 章错误预算口径没有变化；如果是预算口径变了导致阈值失真，先改第 20 章再重新推导，禁止就地改数。
5. **回滚通道**：清退合并后两周内若漏掉真故障，`git revert` 该 PR 即可整体恢复，并在周报登记「清退事故」——这类事故说明降级决定做早了，下次改为保留降级形态而非删除。

这套流程的目的是把「规则只增不减」改成「规则有进有出」：§22.1.1 时间线里 43 → 116 条的堆积，正是因为缺少这一个每周 20 分钟的出清机制 [R-22-7]。周会产出（周报与清退 PR）与第 23 章演练记录共用同一份归档目录，复盘时能同时看到「告警说过什么」与「演练证明过什么」。

### 22.2.1 一条告警的完整设计卡：「看什么 / 做什么 / 找谁」在合并前写全

§22.1 反模式二把四注解定为合并门禁，但注解只是设计卡的**压缩产物**——注解决定值班收到通知后够不够用，设计卡决定这条规则**该不该存在**。两者不可互相替代：一张没写透的设计卡，配再全的注解也只是一条「表达精确但语义错误」的告警。本章要求每条新告警的 PR 附一张设计卡，七个字段缺一打回：

| 字段 | 要回答的问题 | 约束 | 反例 |
|---|---|---|---|
| 1 信号与来源 | 监控哪条 SLI 或记录规则，为什么是它 | 只能引用第 20 章记录规则与第 21 章 `metric-naming.md` 登记的指标名 | 在告警表达式里现场对原始指标做聚合，命名游离于登记之外 |
| 2 判定与窗口 | 什么算「坏」：哪个燃尽率窗口、越界多少 | 阈值从 14.4 / 6 / 1 口径推导，禁止另起数字 | 拍一个「> 5% 就告警」，与错误预算无关 |
| 3 误报场景 | 什么**正常**事件会触发它 | 至少列两个，并写明各自的挡法 | 一个都不列——通常说明作者没想过发版抖动与演练窗口 |
| 4 看什么 | 触发后第一张图看哪个面板 | `dashboard` 注解直达该面板，不落大盘首页 | 链接指向总览页，值班自己找图 |
| 5 做什么 | 首步动作，命令级、幂等 | `first_action` 注解；必须是演练验证过的命令 | 「检查服务状态」这种没有第一行命令的动作 |
| 6 找谁 | 5 / 15 分钟没人认领升级给谁 | `escalate` 注解落到**具体角色与联系方式** | 「通知 owner」——owner 是个标签，不是个排班 |
| 7 何时不该响 | 演练、维护、静默例外 | 由 `mute_time_intervals` 或登记静默覆盖 | 不写——第一次演练就会被一条过宽静默误伤 |

以 `GatewayAvailabilityFastBurnPaging` 为例，设计卡在 PR 里的形态：

```markdown
# 设计卡：GatewayAvailabilityFastBurnPaging
- 信号：sli:order_demo_http_bad:ratio_rate5m 与 slo:order_demo_gateway:burn_rate_1h（第 20 章记录规则）
- 判定：1h 与 5m 双窗燃尽率均 >= 14.4，for: 2m
- 误报场景：①滚动更新瞬间 5xx 毛刺——由双窗 + for 2m 挡；②第 23 章演练窗口——由 chaos-drill-window 静默挡
- 看什么：gateway-总览的 SLI 与燃尽率面板
- 做什么：kubectl -n order-demo-prod rollout undo deployment/gateway，观察 SLI 5 分钟
- 找谁：5 分钟未认领升级平台负责人寻呼；15 分钟未恢复按第 23 章启动事件响应
- 何时不该响：周三 14:00–16:00 演练窗口（mute_time_intervals）
```

评审判据只有一条：**字段 3（误报场景）写不出来就打回**。一个说不出「什么正常事件会误触发我」的告警，说明作者既没想清语义，也没跑过第 23 章演练——它上线后的第一次「响」大概率就是误报 [R-22-4][R-22-6]。

**多窗口多燃尽率的阈值来源**：分级表的 14.4 / 6 / 1 不是经验数，是「预算消耗份额」换算来的。28 天预算共 672 小时，燃尽率 r 持续越界一个窗口 w，烧掉的预算份额约为 r × w / 672 [R-22-4]：

| 窗口 | 阈值 | 持续越界烧掉的预算 | 语义 |
|---|---|---|---|
| 1h（辅以 5m 确认窗） | 14.4 | 约 2% | 一小时烧掉 2% 预算，照此速率当天烧完，必须叫人 |
| 6h | 6 | 约 5% | 半天烧掉 5%，慢性劣化，工作时段处理 |
| 3d | 1 | 约 10% | 三天烧掉 10%，趋势问题，周会复盘 |

由此「改阈值」变成「改预算消耗份额」的显式决策：想把 paging 灵敏度提高一档，等价于宣布「一小时烧 1% 也叫人」，代价是误报率上升与值班节奏的重新校准——必须回第 20 章改预算口径再重算，而不是在规则文件里直接把 14.4 改成 7 [R-22-1][R-22-4]。

### 22.2.2 误报的三种根因：降级别不是万能药

§22.2 清退流程把「降级优先于删除」定为原则，但**降级只对阈值型误报是正确的药**。清退候选入榜后，先按根因分三类，再决定处置：

| 根因 | 特征 | order-demo 例子 | 正确处置 | 错误处置 |
|---|---|---|---|---|
| 抖动型 | 单点采集毛刺让表达式短暂越界 | 一次重启让 5m 窗口瞬时顶过 14.4 后立即回落 | 输入侧平滑（双窗、`avg_over_time`）或加 `for`；`keep_firing_for` 仅在确认输出抖动后按 §22.4.1 立场补 | 调高阈值——真故障恢复期的抖动也会一起被吞掉 |
| 阈值型 | 业务节奏与预算口径不匹配 | 大促周正常流量波动让 6h 燃尽率常年在 5–7 徘徊 | 回第 20 章改预算口径或做例外登记，再重算阈值 | 就地改规则文件里的数字，破坏与第 20 章同源（CL-22-04） |
| 语义型 | 规则表达的「坏」与用户可感不对应 | 探针流量被计入 `order_demo_http_requests_total` 分母，发版期 readiness 抖动放大 bad ratio | 改表达式语义（对齐 `sli:order_demo_http_valid:rate5m` 的排除项），修好前**先静默该规则**而非降级 | 降为 info——错误语义只是变小声，每周仍以同样错误的数据污染命中率统计 |

判读口诀：**抖动改平滑、阈值回预算、语义改表达式**。语义型是三类里唯一「降级即掩盖」的：§22.1.1 时间线里 02:14 的 37 条噪音多数属于语义型——CPU 高被当成「用户受损」来告警，降成 info 并不会让它变正确，只会让错误结论以更安静的方式进周报 [R-22-5][R-22-6]。

### 22.2.3 静默的治理预算与值班体验度量

静默纪律（精确到 `alertname`、带 author 与到期时间）已在 §22.5 落成命令，但「单条静默合规」不等于「静默总量健康」。静默是规则的止痛药：一条规则长期靠静默活着，该修的是规则不是静默。两条治理线：

1. **静默预算**：按月统计 paging 告警可通知时长中被静默覆盖的比例，红线 10%。连续两月超线，周会必须把这批静默对应的规则升级为清退候选——静默在替规则还债，债务记在月报里 [R-22-3][R-22-6]。
2. **双人确认**：`paging` 级规则的静默除 author 外需第二人复核（评论栏留复核人），时长上限 4 小时，需延期重新登记。夜间临时静默次日晨会必须回看：是压掉了真故障，还是恰好挡住一次误报——两种结果都进周报。

计划内维护不走手工静默：第 23 章演练窗口用 `mute_time_intervals` 声明式覆盖并随配置走 PR；应用自身的大版本变更窗口同理，在 `alertmanager.yaml` 新增命名区间，而不是让值班每次手工 silence。判据只有一条：**这个窗口未来还会按计划重复出现吗**——会，就声明式；不会，才允许登记式静默 [R-22-3]。

治理闭环最终落到值班体验上，月度看四个数（数据源与周报同库，不另建体系）：

| 指标 | 健康基准 | 超线动作 |
|---|---|---|
| 夜间（22:00–08:00）paging 次数 / 人 / 周 | ≤ 2 | 触发「告警健康周」，只做清退不开新规则 |
| 单人周 paging 总量 | ≤ 5 | 同上，并核对演练窗口是否泄漏到真实值班 |
| 认领中位时长趋势 | ≤ 5 分钟且不逐月上升 | 查 runbook 首步动作是否仍可执行（CL-22-01） |
| 通知总量趋势（含 ticket / info 落库） | 环比不增 | 检查是否有新规则绕过清退流程入榜 |

> **本书观点（不需要外部背书）**：上表基准数字是本书建议的起点，不是外部规范——团队规模与业务节奏不同，绝对值应按本团队前三个月数据校准。但**四个数必须有人按月看**没有弹性：§22.1.1 里「612 条通知、3 条需人动」的麻木固化期，正是没有任何一个数被盯住的结果 [R-22-7]。

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：噪音治理是「分级路由 + 抑制 + 静默 + 定期复盘」四件事，不是把阈值调高。
>
> **论证**：调高阈值只是把同一批原因型告警推后触发，既没有区分症状与原因，也没有减少「值班需要逐条判断」的认知负担；真出事时，那条被推后的阈值反而可能错过最佳止血窗口。四步各自消掉不同环节的噪音：分级路由保证只有症状进 paging，抑制保证高级别告警不重复轰炸，静默保证计划内演练不制造假警，定期复盘用「命中率 / 误报率」把仍然吵的规则持续清退。这是一个闭环，不是一个数字。
>
> **反例与适用前提**：这不等于「永远不许调阈值」。当复盘发现某条症状告警的燃尽率阈值与业务节奏明显不匹配时，应当回到第 20 章改预算口径再重新推导，而不是在 Alertmanager 里就地改数。对只有一两个服务、值班与开发同组的小团队，抑制与静默可以简化为一条静默规则，但「复盘命中率」不能省——没有它，四步就退化成一次性整理。

## 22.3 工具选型：规则、路由、值班三段各归其位

| 工具 | 主版本 | 本章角色 | 何时不该用 |
|---|---|---|---|
| Prometheus 告警规则 | 3.x | 评估燃尽率与症状表达式、产出告警 | 指标还没采到（依赖第 20、21 章）时；空跑规则只会制造误报 |
| Alertmanager | 0.2x | 分级路由、分组、抑制、静默、静默到期 | 只有一位值班、不需要分组抑制时；多一跳纯增配置面 |
| amtool | 0.2x | `check-config` 校验、注入测试告警、`silence add` | 规则尚未进 Git 时；命令行改出来的状态仍会漂移 |
| 值班平台（PagerDuty / Grafana OnCall 类） | — | 升级策略、排班、认领与升级超时 | 告警量极小、一轮轮值就能覆盖时；引入排班系统收益有限 |
| 自研 webhook 转发 | — | 把告警写进内部工单/审计系统 | 只是想转发到聊天群时；用现成 receiver 即可 |

**唯一示例实现**取本书选型基线：可观测栈为 OTel Collector → Prometheus / Loki / Tempo，本章只用其中的 Prometheus 3.x 告警规则 + Alertmanager 做路由；配置打包走 Kustomize 5.x overlay，同步走 Argo CD 3.x（见第 14 章）。值班平台、自研转发、托管 SaaS 只在矩阵作对比，不写具体厂商单价，成本只给相对比例与归因口径（见第 18 章）[R-22-1][R-22-3]。

**最小接入 diff**：新增 `observability/alert-rules.yaml`、`observability/alertmanager.yaml`、`observability/alert-rules-test.yaml`、`docs/runbooks/index.md`、`hack/alert-drill.sh` 五个文件；不改应用镜像 `git-<sha7>`、不改 `order-demo-config`、不改第 21 章采集拓扑。告警规则沿用 `role: alert-rules` 标签，由第 21 章 `Prometheus` CR 的 `ruleSelector` 自动挂载 [R-22-2]。

**升级 / 回滚路径**：改阈值先改第 20 章预算口径再重算燃尽率，改路由/注解改本章文件，均走 PR + `promtool test rules` + `amtool check-config` 双门禁；升级 Alertmanager 小版本先跑 `alert-drill.sh` 验证路由不变再切。整体回滚用 `git revert` 后由 Argo CD 收敛，应急只加带到期时间的静默、不改规则（§22.5）。小版本锁在附录 A，正文只写主版本 [R-22-1][R-22-3]。

## 22.4 落地配置（完整可应用文件，Kubernetes 1.32+，Prometheus 3.x / Alertmanager 0.2x）

> 沿用配置契约：命名空间 `observability` / `order-demo-prod`，服务 `gateway` 端口 8080、`api` 8081、`db` 5432，公共标签 `app.kubernetes.io/name=order-demo`，`app.kubernetes.io/managed-by` 自第 14 章起为 `argocd`。告警表达式只引用第 20 章记录规则与第 21 章 `metric-naming.md` 登记的指标名，不另起命名。适用 K8s 版本 1.32+，组件小版本见附录 A。

**`observability/alert-rules.yaml`——多窗口燃尽率与症状告警规则（完整）**

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: order-demo-symptom-alerts
  namespace: observability
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
    role: alert-rules
spec:
  groups:
    - name: order-demo-symptom-alerts
      interval: 30s
      rules:
        - alert: GatewayAvailabilityFastBurnPaging
          expr: >-
            slo:order_demo_gateway:burn_rate_1h >= 14.4
            and avg_over_time(sli:order_demo_http_bad:ratio_rate5m[5m])
                / on() group_left() slo:order_demo_gateway:error_budget_ratio >= 14.4
          for: 2m
          labels:
            severity: paging
            service: gateway
            slo: gateway-availability
          annotations:
            summary: "gateway 错误预算快燃尽，1h 与 5m 双窗燃尽率均 >= 14.4"
            description: "用户可感 5xx 正在快速消耗 28 天错误预算，需立即止血。"
            runbook: "docs/runbooks/gateway-fast-burn.md"
            first_action: "按 runbook §1 执行 kubectl -n order-demo-prod rollout undo deployment/gateway 并观察 SLI 5 分钟。"
            dashboard: "grafana/internal.example.com/d/order-demo/gateway-总览"
            escalate: "5 分钟未认领升级至平台负责人；15 分钟未恢复按第 23 章启动事件响应。"
        - alert: GatewayAvailabilitySlowBurnTicket
          expr: 'slo:order_demo_gateway:burn_rate_6h >= 6'
          for: 15m
          labels:
            severity: ticket
            service: gateway
            slo: gateway-availability
          annotations:
            summary: "gateway 错误预算慢燃尽，6h 燃尽率 >= 6"
            description: "存在慢性劣化，需在工作时段排查，不半夜叫人。"
            runbook: "docs/runbooks/gateway-slow-burn.md"
            first_action: "按 runbook §1 拉取 6h 内按 route/status_code 分组的 SLI，定位劣化接口。"
            dashboard: "grafana/internal.example.com/d/order-demo/gateway-组件下钻"
        - alert: GatewayBudgetExhausted
          expr: 'slo:order_demo_gateway:release_freeze == 1'
          for: 5m
          labels:
            severity: ticket
            service: gateway
            slo: gateway-availability
          annotations:
            summary: "28 天错误预算耗尽，非必要发布已冻结"
            description: "按第 20 章冻结规则，功能发布/依赖升级/配置重构暂停，仅豁免回滚与安全补丁。"
            runbook: "docs/runbooks/gateway-budget-exhausted.md"
            first_action: "按 runbook §1 核对 budget-report.sh 结果与 docs/slo-contract.md 例外登记。"
            dashboard: "grafana/internal.example.com/d/order-demo/gateway-错误预算"
        - alert: GatewayLatencyP99Symptom
          expr: >-
            histogram_quantile(0.99,
              sum by (le, service) (
                rate(order_demo_http_request_duration_seconds_bucket{
                  service="gateway", route="/orders"
                }[5m])
              )) > 1.0
          for: 10m
          labels:
            severity: info
            service: gateway
            slo: gateway-availability
          annotations:
            summary: "gateway /orders p99 延迟 > 1s，仅记录不通知"
            description: "延迟症状，若同时触发快燃尽则由 paging 承载，本条只做下钻上下文。"
            runbook: "docs/runbooks/http-5xx-spike.md"
            first_action: "按 runbook §1 用 trace_id 在 Tempo 看 api → db 耗时分布。"
            dashboard: "grafana/internal.example.com/d/order-demo/gateway-排障"
        - alert: OrderDemoProbeFlapping
          expr: >-
            sum(increase(order_demo_http_requests_total{
              service="gateway", route=~"/healthz|/readyz"
            }[5m])) > 0
          for: 20m
          labels:
            severity: info
            service: gateway
          annotations:
            summary: "探针路径出现请求，仅记录"
            description: "原因型上下文，用于核对 SLI 排除项是否生效，绝不 paging。"
            runbook: "docs/runbooks/crashloop-backoff.md"
            first_action: "确认探针流量未被计入 sli:order_demo_http_valid:rate5m 分母。"
```

### 22.4.1 通知节奏：`for` / `keep_firing_for` / `group_interval` 如何决定「多快响、响几次」

规则表达式决定「该不该响」，本节的几个参数决定「什么时候响、响多少次」。两者乘起来才是值班实际体验到的通知节奏；只调表达式不调节奏，或只调节奏不改表达式，都会以不同形态复现 §22.1.1 的风暴 [R-22-1][R-22-3]。

**`for`（pending 最短持续时间，Prometheus 规则侧）**：条件首次满足后，连续保持满足满 `for` 时长才转 `firing`，期间不发任何通知。它挡的是单点抖动——一次采集毛刺、一次瞬时重启。本章取值与理由：

| 规则 | `for` | 取值理由 |
|---|---|---|
| GatewayAvailabilityFastBurnPaging | 2m | 双窗表达式已含 5m 短窗做输入侧平滑，`for` 只需再挡一次评估抖动；认领时限只有 5 分钟，`for` 每加 1 分钟都直接吃掉止血窗口，不能更长 |
| GatewayAvailabilitySlowBurnTicket | 15m | 慢性劣化不需要分钟级敏感，但要挡住小时级毛刺把 6h 窗口短暂顶过 6 |
| GatewayBudgetExhausted | 5m | `release_freeze` 是状态量而非速率量，短 `for` 防单点即可，无需平滑 |
| GatewayLatencyP99Symptom / OrderDemoProbeFlapping | 10m / 20m | `info` 级不进通知流，`for` 只影响落库时点，取宽值降低记录噪声 |

**`keep_firing_for`（Prometheus 2.42+ 引入，3.x 稳定字段）**：条件消失后继续保持 `firing` 指定时长，防止规则在阈值附近来回穿越造成「触发 → 恢复通知 → 再触发 → 再恢复通知」的循环轰炸。本书取值立场：**本章五条规则不启用它**。理由：燃尽率表达式是多窗比值，输入已被双窗平滑，输出天然不易抖动；再把 `keep_firing_for` 叠上去只会掩盖真实恢复时刻，延长值班对「已止血」的误判。它留给两类后续场景：将来若引入单窗表达式，或某条阈值贴着业务噪声带（如大促期的正常波动），必须补 `keep_firing_for: 5m`（paging）/ `15m`（ticket），并作为规则变更走 PR 评审——不允许把它当成「治抖动」的默认习惯 [R-22-1]。

**`group_wait` / `group_interval` / `repeat_interval`（Alertmanager 路由侧）**：三者管通知合并，语义必须分清 [R-22-3]：

- `group_wait`：同组**第一条**告警从 firing 到发出通知的攒批等待。paging 路由取 `10s`——认领时限只有 5 分钟，攒批几乎不可取；ticket 取 `30s`，用半分钟换掉同时爆出的同组工单合并。
- `group_interval`：同组**已有通知之后**，新增告警并入下次通知的**最短间隔**。这是最常被误解的参数：它不是「每 5 分钟重发一遍」（那是 `repeat_interval`），而是「上一条通知发出后，至少再等这么久，才把期间新增的告警合并成第二条通知」。paging 取 `1m`：故障进行中，新症状 1 分钟内必达；ticket 取 `5m`，允许一批相关工单攒着一起说。
- `repeat_interval`：未恢复时的重复提醒周期。paging 的 `30m` 是兜底而非主通道——主通道是 `escalate` 注解里的「5 分钟未认领升级、15 分钟未恢复启动事件响应」；ticket 的 `4h` 与一个工作日的响应时限对齐。

**取值的端到端校准**：这些数字不是拍出来的，用 `hack/alert-drill.sh` 量。paging 路由端到端应在 45s 内到达 receiver（评估间隔 30s + `group_wait` 10s + webhook 投递；测试告警直接注入 Alertmanager、已处于 firing，不经过规则侧 `for`），ticket 应在 90s 内；超时先查 `group_wait` 与评估间隔，再查 webhook 端。认领时限 5 分钟按预算分解为「`for` 2m + 路由投递 1m + 人工认领 2m」，任何一段变长都必须从另一段补回来，而不是悄悄放宽时限。所有节奏参数与阈值同级对待：进 Git、走 PR、`amtool check-config` 门禁，禁止在 UI 里改 [R-22-3]。

### 22.4.2 规则文件的组织与命名规范

§22.4 的两个文件能跑通五条规则，但规则会生长——没有组织规范，六个月后的 `alert-rules.yaml` 就是 §22.1.1 里那个 116 条的单体文件。本章规范四层。

**仓库布局**（每个文件在门禁中的角色）：

```text
observability/
├── alert-rules.yaml          # 告警规则（PrometheusRule CR，ruleSelector 按 role: alert-rules 挂载）
├── alert-rules-test.yaml     # 规则单测输入序列（promtool test rules 门禁）
├── alertmanager.yaml         # 路由 / 抑制 / 静默区间（挂成 Secret，amtool check-config 门禁）
docs/runbooks/                # runbook 索引与正文（CL-22-02 断链检查的对象）
hack/alert-drill.sh           # 注入测试告警的路由演练（CI 与发布后各跑一次）
```

切分原则：**一应用一 PrometheusRule**（本例 `order-demo-symptom-alerts`），单文件规则超过 10 条时按症状族拆 group 而不是拆文件——`ruleSelector` 按 `role: alert-rules` 标签挂载，文件拆多了标签管理成本先涨 [R-22-2]。

**告警命名**：PascalCase，模式 `<组件><症状><级别>`，三段各从有限集合取值——组件取配置契约（gateway / api / worker / db），症状取 runbook 索引的症状族（Availability、Latency、BudgetExhausted、ProbeFlapping），级别取 severity（FastBurnPaging / SlowBurnTicket）。由此反推三条禁令：

- **禁止把阈值写进名字**：`GatewayErrorAbove5Pct` 在阈值改成 3% 的那天开始撒谎；症状名（Availability）不会随调参失效。
- **禁止动词开头或含糊名词**：`CheckGateway`、`ServiceProblem` 不说明症状——§22.1 那条标题只有「服务异常」的告警就是这类命名的下场。
- **禁止无级别后缀的近名重复**：`GatewaySlowBurn` 与 `GatewayAvailabilitySlowBurnTicket` 同时存在时，没人知道哪条在路由表里生效；第 20 章自检 alert 的收敛处置，依据正是这条禁令。

**标签与 severity 分级**：规则侧标签只维护四个——`severity`（仅 `paging` / `ticket` / `info` 三档，与 §22.2 矩阵的 receiver 一一对应）、`service`、`slo`、`team`。`severity` 是唯一允许参与路由 `matchers` 的自定义标签，其余只做分组、抑制 `equal` 键与展示；新增第四档（`critical` / `warning` 之类）等于新增一条路由分支与一整套抑制关系，必须先改 §22.2 矩阵再改配置，禁止先加档后补矩阵。`equal: ["service"]` 是抑制规则的固定键：抑制永远限定在同一服务内——跨服务抑制会在 gateway 故障时把 api 的 ticket 一起吞掉，故障半径凭空翻倍 [R-22-3]。

**注解写法**：四个强制注解之外，`summary` 与 `description` 有一条固定分工——`summary` 是一行可读结论（手机锁屏上看到的那句，只说「发生了什么」）；`description` 必须含**数字与窗口**（「1h 与 5m 双窗燃尽率均 >= 14.4」），让值班不打开 dashboard 就能判断「现在处于哪个严重度」。两者都用模板变量引用标签值（`{{ $labels.service }}`），不硬编码服务名，规则复制到 api / worker 时注解不会说谎 [R-22-1]。

**新规则的接入路径**：以上四层收拢成一个固定的 PR 顺序，任何新告警都按同一顺序过审，评审人不必逐条重新发明检查步骤：

1. PR 描述里附 §22.2.1 设计卡全七字段，字段 3 空缺直接打回；
2. 规则本体进 `alert-rules.yaml`，命名与标签按本节禁令自查，`severity` 必须能在 §22.2 矩阵里指到一行；
3. `alert-rules-test.yaml` 补该规则的输入序列与期望样本——没有单测的表达式不允许合并 [R-22-1]；
4. runbook 文件与 `docs/runbooks/index.md` 条目同 PR 落库，`hack/alert-drill.sh` 的 `N/N` 断言自然把「规则加了、runbook 没加」挡在门外；
5. 若该规则需要新的抑制关系或维护窗口，`inhibit_rules` / `mute_time_intervals` 与 §22.2 矩阵的行**同一 PR** 同步更新——矩阵与配置互为镜像是 §22.2 判读规则 3 的硬约束。

五步走完，这条规则从出生起就有设计卡、单测、runbook 和矩阵席位；§22.2.3 的周会与月度度量则负责它的后半生。接入与退出共用同一套 PR 通道，「告警即代码」才从口号变成仓库里可 `git log` 追溯的事实。

```bash
# 3. 演练用的测试告警到期自动消失；如需立即清掉，删除静默
amtool --alertmanager.url=http://alertmanager.observability.svc.cluster.local:9093 \
  silence query --expired=false
```

> **为什么静默要带 `--author` 与 `--comment`**：静默是唯一被允许的运行时例外，它必须能被审计回溯；不带原因、不带到期时间的静默等同于在 UI 里悄悄关告警，正是 §22.1 反模式三。静默到期自动失效，不需要第二步「记得去关」[R-22-3][R-22-6]。


## 22.6 上线检查清单

检查项编号全书统一（形如 `CL-08-03`），下表只列本章专有项与必须逐条执行的安全项。

这一章的清单有一个别的章没有的量：**规则总量**。它把「有多少条告警」本身当成被检查对象，因为噪音是一种**只增不减的资源消耗**——每条规则当初都有理由，只是理由会过期，而没人负责回收。**规则不像代码那样会被重构，它只会被叠上去。**所以本章必须显式规定「清退」，否则清单本身也会变成噪音。

| 编号 | 检查项 | 怎么查 | 通过标准 | 失败处置 |
|---|---|---|---|---|
| CL-22-01 | 每条 paging 可行动 | `./hack/alert-drill.sh` 的 `N/N` 断言 + 检查 `first_action` 注解 | 100% paging 带 runbook、首步动作、dashboard、升级路径 | 禁止合并，回 22.4 补注解（见第 23 章模板） |
| CL-22-02 | runbook 链接有效 | `grep -o 'docs/runbooks/[^"]*' observability/alert-rules.yaml | while read f; do test -f "$f"; done` | 所有链接在 `docs/runbooks/index.md` 中有对应条目且文件存在 | 回 22.4 补索引，断链按 H8 视为不可行动 |
| CL-22-03 | 分级路由演练通过 | `amtool alert query` 与 `config routes test --tree` | paging/ticket/info 各自落到正确 receiver，抑制无冲突 | 回 22.4 修 `matchers` 与 `inhibit_rules`，先停 paging 再排查 |
| CL-22-04 | 规则在 Git 中且阈值同源 | `git log --oneline -- observability/` 对照第 20 章 `slo.yaml` | 14.4 / 6 / 1 与 `release_freeze` 均引用第 20 章记录规则，无硬编码第二套数字 | 回第 20 章重算预算口径，禁止就地改阈值 |
