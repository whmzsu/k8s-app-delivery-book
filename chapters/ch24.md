## 24.1 问题与护栏：护栏不是最后一道工序

先把位置说清楚。**本篇是前六篇护栏的汇总深化，不是最后才做安全。** 从第 6 章把 `automountServiceAccountToken: false` 写进最小闭环开始，检查清单里就一直挂着 `CL-S-01`（非 root）、`CL-S-02`（权限最小化）、`CL-S-03`（准入策略已生效）、`CL-S-04`（生产无手工变更通道）这几条安全项；第 9 章把密钥挪出 Git，第 11 章在 CI 拦下错误字段，第 12 章让一次构建产出唯一制品，第 14 章用 GitOps 堵住手工变更入口，第 19 章让 NetworkPolicy 默认拒绝。第六篇要做的，是把这些散落在各环的护栏收拢成一条**可验证、可阻断、可追溯**的证据链，并补上前面刻意留白的三件事：产物里到底有什么（SBOM）、有没有已知漏洞（扫描）、推到集群的到底是不是 CI 构建的那一个（签名与验签）。D-01 裁决把这三件事全部从第 6 章挪到本章，就是为了让「最小闭环」保持最小性（见第 6 章），同时让门禁有且只有一个归属（见第 12 章）。

「汇总深化」还有一层意思：安全不是发布流水线末端的一个扫描步骤，而是**同一份证据在三个位置被反复校验**。只在一处做，另外两处就能被绕过；三处都做且口径一致，才谈得上「这个产物可信」。SLSA v1.0 把构建过程的可信度分成可判定的级别，回答的是「怎么构建」[R-24-1]；SBOM 用 SPDX 这类标准格式列出镜像里的软件成分，回答的是「含什么」[R-24-5]；签名与验签回答的是「是不是那一个」[R-24-6]。三者缺一，证据链就断在某一环。

三条高频反模式，按「现象 → 根因 → 本章护栏」展开：

**反模式一：只在 CI 扫描，集群不验签。** 现象是流水线里有一排绿色对勾，但某个周五有人为了「先救一下」手工 `docker push` 了一个本地构建的镜像，再用 `kubectl set image` 指过去，集群照单全收——因为镜像从注册表到 Pod 这一跳没有任何人核对它是不是 CI 产出的那个。根因是把「出仓前检查」当成了「入集群前检查」：CI 的检查作用在构建者能控制的路径上，任何绕过这条路径的推送都不会被检查。本章护栏是把验签放到**准入阶段**（在资源真正进入集群前由 API Server 执行的校验，详见第 25 章），由 Kyverno 1.x 的 `verifyImages` 规则对所有 `registry.example.com/order-demo/*` 镜像强制校验签名，无有效签名一律拒绝 [R-24-3][R-24-4]。CI 侧签名、准入侧验签，两侧对称，缺一侧即可被绕过 [R-24-7]。

**反模式二：SBOM 生成后不归档。** 现象是流水线确实跑过 `syft`，但产物只留在当次 runner 的临时目录里；等某天爆出一个基础库漏洞，团队翻遍仓库也回答不了「受影响的是哪些版本、哪些环境在跑」。根因是把 SBOM 当成一次性构建日志，而不是**需要按制品索引长期保留的证据**。本章护栏是制品库保留策略加索引：SBOM 以 OCI 制品形式挂在镜像 digest 上，扫描报告与两份 SBOM 按 `git-<sha7>` 归档并设保留期，已晋升 `order-demo-prod` 的 digest 永久保留。NIST SP 800-190 明确把镜像内容与来源的可追溯性列为容器安全的核心控制项 [R-24-2]。

**反模式三：把「0 漏洞」当上线门槛。** 现象是扫描器一报 HIGH 就卡住发布，而 `distroless` 基础镜像里那个暂时没有修复版本的系统库永远过不了；几轮之后团队开始在流水线里堆白名单，`--ignore-unfixed` 被改成宽泛的 `--skip-files`，门禁名存实亡。根因是把「漏洞数」这个连续量当成了布尔开关，忽略了可利用性与修复窗口。本章护栏是**分级门禁**：只对「有修复版本、且严重程度为 CRITICAL/HIGH」的漏洞阻断，对无修复版本的漏洞记录并要求在修复窗口内复评，例外必须登记到期时间。公开的软件供应链与容器逃逸复盘反复印证：真正造成损失的是「不知道自己跑了什么」和「没法阻断未授权产物」，而不是「报告里还有几条 LOW」[R-24-9][R-24-2]。

> **一个作用域声明**：本章不重复第 6 章的 Dockerfile 与构建命令，也不重复第 12 章的 CI 骨架；本章只负责给「已构建的制品」加装证据与门禁。第 25 章负责策略引擎本身（安装、命名、灰度、测试），本章只给其中一条验签策略，并沿用它的命名与命名空间约定。

## 24.2 落地策略与门禁：三处校验，一条证据链

### 24.2.1 门禁分层与判据表

证据链分三层，每层的失败动作必须是「阻断」而不是「告警了事」，绕过必须留审计。这张表既是设计，也是后面检查清单的判据来源。

| 位置 | 检查项 | 工具 / 机制 | 失败动作 | 绕过审批与审计 |
|---|---|---|---|---|
| 构建（CI 内） | 产物唯一、SBOM 完整 | Syft 1.x 生成 SPDX / CycloneDX；`git-<sha7>` 标签 | SBOM 生成失败即退出，镜像不推送 | 无绕过；构建日志入 CI 审计 |
| 出仓（推送注册表前） | 漏洞分级、签名、归档 | Trivy 0.x 扫描（Grype 0.x 可作等价替换）；cosign 2.x `sign` + `attach sbom` | HIGH/CRITICAL 且可修复则退出；签名失败不推送 | 例外登记 `docs/supply-chain-exception.md`，带到期时间 |
| 入集群（准入） | 签名有效性、来源仓库 | Kyverno 1.x `order-demo-verify-image-signature` | 无签名 / 验签失败 / 非白名单仓库 → 拒绝创建 | 只能临时降级为 `Audit`，须登记例外并自动到期 |
| 归档（制品库） | 按 SHA 可检索、保留期 | Harbor 2.x 保留规则 + `crane 0.x` 检索 | 签名制品或 SBOM 缺失 → 阻断晋升 | 保留规则变更走 Git（见第 14 章） |

> **本书观点（本章第 1 条结论，不需要外部背书）**
>
> **主张**：供应链防护的重心是「可追溯与可阻断」，不是把漏洞数扫到零。
>
> **论证**：把目标定成「零漏洞」，等价于要求基础镜像永不出现任何已知问题，这在有依赖的应用里不可达；不可达的门槛会被团队用白名单绕过，最终连「有没有扫过」都失去可信度。把目标定成「每个在跑的制品都能反查到唯一提交、能列出成分、能被准入拒绝」，则每一条都能用一条命令当场证明，而且不依赖扫描器是否更新到最新漏洞库。
>
> **反例与适用前提**：这不等于「漏洞可以不修」。对有修复版本、且可远程利用的高危漏洞，本章的 CI 门禁是硬阻断；主张针对的是「无修复版本」「仅本地触发」「依赖链深处暂不可达」这类条目，做法是记录 + 修复窗口内复评，而不是永久放行。若团队处于强合规场景（如要求出具零已知漏洞证明），则需以合规口径为准，本观点只适用于以工程可验证性为优先的常规交付。

### 24.2.2 完整可应用配置（Kubernetes 1.32+，Kyverno 1.x）

以下四个文件构成最小可运行门禁；字段沿用第 6 章冻结的配置契约（命名空间 `order-demo-dev` / `order-demo-staging` / `order-demo-prod`、镜像 `registry.example.com/order-demo/<component>:git-<sha7>`、`app.kubernetes.io/name=order-demo`），小版本锁在附录 A。

**`.github/workflows/supply-chain.yml`** —— 构建、扫描、签名、归档一次做完，签名步骤按 SP-18 唯一归属本章。

```yaml
name: supply-chain
on:
  push:
    branches: [main]
permissions:
  contents: read
  packages: write
env:
  REGISTRY: registry.example.com
  IMAGE_REPO: registry.example.com/order-demo/gateway
jobs:
  build-sign-archive:
    runs-on: ubuntu-latest
    steps:
      - name: 检出源码
        uses: actions/checkout@v4
      - name: 计算短 SHA（唯一制品标识，见第 6 章）
        id: sha
        run: echo "sha7=$(git rev-parse --short=7 HEAD)" >> "$GITHUB_OUTPUT"
      - name: 登录制品库
        uses: docker/login-action@v3
        with:
          registry: registry.example.com
          username: ${{ secrets.REGISTRY_USER }}
          password: ${{ secrets.REGISTRY_PASSWORD }}
      - name: 一次构建并推送（build once，见第 3 章）
        run: |
          IMAGE_TAG="${IMAGE_REPO}:git-${{ steps.sha.outputs.sha7 }}"
          docker build -f docker/Dockerfile -t "${IMAGE_TAG}" .
          docker push "${IMAGE_TAG}"
          echo "IMAGE_TAG=${IMAGE_TAG}" >> "$GITHUB_ENV"
      - name: 生成 SBOM（Syft 1.x，两种格式都留档）
        run: |
          syft "${IMAGE_TAG}" -o spdx-json=sbom.spdx.json
          syft "${IMAGE_TAG}" -o cyclonedx-json=sbom.cdx.json
          test -s sbom.spdx.json
          test -s sbom.cdx.json
      - name: 漏洞分级门禁（Trivy 0.x，仅阻断可修复的高危项）
        run: |
          trivy image \
            --exit-code 1 \
            --severity CRITICAL,HIGH \
            --ignore-unfixed \
            --format json \
            --output trivy-report.json \
            "${IMAGE_TAG}"
      - name: cosign 2.x 签名（按 digest 签，不按可变标签签）
        env:
          COSIGN_PASSWORD: ${{ secrets.COSIGN_PASSWORD }}
        run: |
          printf '%s' "${{ secrets.COSIGN_KEY }}" > cosign.key
          DIGEST="$(docker inspect --format='{{index .RepoDigests 0}}' "${IMAGE_TAG}")"
          cosign sign --key cosign.key --tlog-upload=false "${DIGEST}"
      - name: SBOM 作为 OCI 制品挂到镜像，并按 SHA 归档报告
        run: |
          cosign attach sbom --sbom sbom.spdx.json --type spdx "${IMAGE_TAG}"
      - name: 归档 SBOM 与扫描报告（按 git-<sha7> 索引，保留 400 天）
        uses: actions/upload-artifact@v4
        with:
          name: supply-chain-git-${{ steps.sha.outputs.sha7 }}
          path: |
            sbom.spdx.json
            sbom.cdx.json
            trivy-report.json
          retention-days: 400
          if-no-files-found: error
```

> 两处刻意的设计：`cosign sign` 的对象是 `RepoDigests` 里的 `@sha256:` 摘要而不是 `git-<sha7>` 标签，因为标签是可变指针、摘要才是内容标识（见第 6 章）；`--tlog-upload=false` 让离线 kind 环境也能完成签名与验签闭环，生产可改用 keyless 模式并把签名者身份写进验签策略的 `subject` / `issuer`。`--ignore-unfixed` 是反模式三的护栏：只对有修复版本的高危项阻断 [R-24-2]。

**`policies/order-demo-verify-image-signature.yaml`** —— 准入侧验签，`Enforce` 模式。策略命名 `order-demo-*`、引擎命名空间 `kyverno`，与第 25 章完全一致。

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: order-demo-verify-image-signature
spec:
  validationFailureAction: Enforce
  background: false
  failurePolicy: Fail
  rules:
    - name: verify-order-demo-images
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - order-demo-dev
                - order-demo-staging
                - order-demo-prod
      verifyImages:
        - imageReferences:
            - "registry.example.com/order-demo/*"
          mutateDigest: true
          verifyDigest: true
          attestors:
            - count: 1
              entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      REPLACE_WITH_COSIGN_PUBLIC_KEY_BASE64
                      -----END PUBLIC KEY-----
```

> `publicKeys` 内联的是**示例占位公钥**，必须用 `hack/verify-supply-chain.sh` 生成的真实公钥替换（脚本用 `sed` 完成，手法与第 6 章替换示例 SHA 一致）；未替换直接 `apply` 会让验签恒定失败，这是刻意的 fail-closed 行为。`mutateDigest: true` 让 Kyverno 1.x 把已验签的镜像引用重写为 `@sha256:` 摘要，杜绝「验签通过后标签被覆盖」的窗口 [R-24-3]。Kyverno 1.x 的 autogen 会为 `Deployment` / `StatefulSet` / `Job` 自动派生等效规则，因此策略同样拦截写在 Deployment Pod 模板里的镜像字段。`failurePolicy: Fail` 保证 webhook 不可用时拒绝而非放行。

      "params": { "latestPushedK": 30 },

          { "decoration": "matches", "pattern": "order-demo/**" }

      },
      "tag_selectors": [

**`hack/verify-supply-chain.sh`** —— 端到端演示「签名镜像通过、未签名镜像被准入拒绝」，并把降级与恢复一并跑一遍。

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-dev
REPO=registry.example.com/order-demo/gateway
SHA7="$(git rev-parse --short=7 HEAD)"
SIGNED_TAG="${REPO}:git-${SHA7}"
UNSIGNED_TAG="${REPO}:unsigned-${SHA7}"

# 0) 前置：Kyverno 1.x 已部署在命名空间 kyverno（部署方式见第 25 章，本书不写安装教程）
kubectl -n kyverno get deploy >/dev/null 2>&1 || {
  echo "缺少 Kyverno 1.x（命名空间 kyverno），请先按第 25 章部署" >&2; exit 1; }

# 1) 生成密钥对，把策略里的示例公钥换成真实公钥
if [ ! -f cosign.key ]; then
  COSIGN_PASSWORD="" cosign generate-key-pair
fi
PUB_B64="$(grep -v -- '-----' cosign.pub | tr -d '\n')"
sed "s|REPLACE_WITH_COSIGN_PUBLIC_KEY_BASE64|${PUB_B64}|" \
  policies/order-demo-verify-image-signature.yaml > /tmp/verify-policy.yaml
kubectl apply -f /tmp/verify-policy.yaml
kubectl get clusterpolicy order-demo-verify-image-signature -o jsonpath='{.spec.validationFailureAction}{"\n"}'

# 2) 未签名镜像：复用已构建镜像换标签推送，不带任何签名
docker tag "${SIGNED_TAG}" "${UNSIGNED_TAG}"
docker push "${UNSIGNED_TAG}"

# 3) 签名镜像应通过；未签名镜像应被准入拒绝
cat >/tmp/signed-deploy.yaml <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway-signed
  namespace: ${NS}
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: gateway
        version: git-${SHA7}
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: gateway
          image: ${SIGNED_TAG}
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
EOF
kubectl apply -f /tmp/signed-deploy.yaml
kubectl -n "${NS}" rollout status deployment/gateway-signed --timeout=120s

sed "s|image: ${SIGNED_TAG}|image: ${UNSIGNED_TAG}|; s|name: gateway-signed|name: gateway-unsigned|g" \
  /tmp/signed-deploy.yaml > /tmp/unsigned-deploy.yaml
if kubectl apply -f /tmp/unsigned-deploy.yaml > /tmp/unsigned.out 2>&1; then
  echo "FAIL：未签名镜像竟然被准入放行" >&2; exit 1
fi
grep -Eqi 'blocked|denied|failed|verification' /tmp/unsigned.out
echo "OK：未签名镜像被准入拒绝"
cat /tmp/unsigned.out

# 4) 证据可检索：签名、SBOM 制品与按 SHA 归档的报告
COSIGN_PASSWORD="" cosign verify --key cosign.pub --insecure-ignore-tlog=true "${SIGNED_TAG}"
cosign download sbom "${SIGNED_TAG}" > /tmp/downloaded-sbom.json
grep -q 'spdxVersion' /tmp/downloaded-sbom.json
crane ls "${REPO}" | grep '^sha256-' | head -n 5

# 5) 降级演练：Enforce -> Audit -> Enforce，并确认两次状态
sed 's|validationFailureAction: Enforce|validationFailureAction: Audit|' \
  /tmp/verify-policy.yaml | kubectl apply -f -
kubectl get clusterpolicy order-demo-verify-image-signature -o jsonpath='{.spec.validationFailureAction}{"\n"}'
kubectl apply -f /tmp/verify-policy.yaml
kubectl get clusterpolicy order-demo-verify-image-signature -o jsonpath='{.spec.validationFailureAction}{"\n"}'

# 6) 清理演练产物
kubectl -n "${NS}" delete deployment gateway-signed --ignore-not-found
```

### 24.2.3 验证与回滚

**验证命令**（仓库根目录执行；已安装 cosign 2.x / Syft 1.x / Trivy 0.x / `crane 0.x` / kubectl / docker，版本见附录 A）：

```bash
chmod +x hack/verify-supply-chain.sh
./hack/verify-supply-chain.sh
COSIGN_PASSWORD="" cosign verify --key cosign.pub --insecure-ignore-tlog=true \
  registry.example.com/order-demo/gateway:git-<sha7>
kubectl -n order-demo-dev describe pod -l app.kubernetes.io/component=gateway | tail -n 20
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 签名镜像 | `gateway-signed` 的 `rollout status` 正常结束，Pod `Running` |
| 未签名镜像 | `kubectl apply` 返回非零，输出含 `blocked` / `denied` / `verification` 字样，`gateway-unsigned` 不存在 |
| 验签命令 | `cosign verify` 退出码 0，`cosign download sbom` 取回的 JSON 含 `spdxVersion` |
| 制品可检索 | `crane ls` 能看到 `git-<sha7>` 标签与 `sha256-*.sig` / `sha256-*.sbom` 制品 |
| 降级与恢复 | 两次读取 `validationFailureAction` 依次为 `Audit`、`Enforce` |
| 审计留痕 | 审计日志与 Kyverno 事件里能查到拒绝记录（见第 26 章） |

**回滚 / 降级命令与步骤**。降级只改变阻断强度，不删除证据链；正式回退必须回到 Git（全书公理 5，见第 3 章）：

```bash
# 应急降级：把验签从阻断改为只记审计，登记例外与到期时间
kubectl apply -f policies/order-demo-verify-image-signature-audit.yaml
kubectl get clusterpolicy order-demo-verify-image-signature \
  -o jsonpath='{.spec.validationFailureAction}{"\n"}'
# 例外登记（写入 Git，带到期时间；模板见 docs/supply-chain-exception.md）
printf '%s\n' "date=$(date -u +%F) reason=emergency-release sha=${SHA7} expires=$(date -u -d '+3 days' +%F)" \
  >> docs/supply-chain-exception.md
git add docs/supply-chain-exception.md policies/order-demo-verify-image-signature-audit.yaml
git commit -m "chore(supply-chain): temporary audit-mode exception with expiry"

# 正式回退：撤销本次门禁变更，回到上一个已知良好版本
git revert HEAD
kubectl apply -f policies/order-demo-verify-image-signature.yaml
```

**回滚验证**：

```bash
kubectl get clusterpolicy order-demo-verify-image-signature \
  -o jsonpath='{.spec.validationFailureAction}{"\n"}'
kubectl -n order-demo-dev get events --field-selector reason=PolicyViolation --sort-by=.lastTimestamp | tail -n 10
COSIGN_PASSWORD="" cosign verify --key cosign.pub --insecure-ignore-tlog=true \
  registry.example.com/order-demo/gateway:git-<sha7>
kubectl -n order-demo-dev delete pod -l app.kubernetes.io/component=gateway --wait=false
./hack/verify-supply-chain.sh
```

通过标准：`validationFailureAction` 回到 `Enforce`；降级窗口内的放行记录仍能在审计事件里查到（证据链未断）；`cosign verify` 仍为退出码 0；重跑脚本时未签名镜像再次被拒、签名镜像仍可用。**降级没有验证过恢复路径，就不允许带着例外继续发布**（母版 `CL-G-07`）。例外到期后由 `git revert` 或定期复查强制失效，不允许出现「永久 Audit」。
