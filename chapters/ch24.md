## 24.1 问题与护栏：护栏不是最后一道工序

先把位置说清楚。**本篇是前六篇护栏的汇总深化，不是最后才做安全。** 从第 6 章把 `automountServiceAccountToken: false` 写进最小闭环开始，检查清单里就一直挂着 `CL-S-01`（非 root）、`CL-S-02`（权限最小化）、`CL-S-03`（准入策略已生效）、`CL-S-04`（生产无手工变更通道）这几条安全项；第 9 章把密钥挪出 Git，第 11 章在 CI 拦下错误字段，第 12 章让一次构建产出唯一制品，第 14 章用 GitOps 堵住手工变更入口，第 19 章让 NetworkPolicy 默认拒绝。第六篇要做的，是把这些散落在各环的护栏收拢成一条**可验证、可阻断、可追溯**的证据链，并补上前面刻意留白的三件事：产物里到底有什么（SBOM）、有没有已知漏洞（扫描）、推到集群的到底是不是 CI 构建的那一个（签名与验签）。这三件事被刻意从第 6 章挪出、全部归到本章，就是为了让「最小闭环」保持最小性（见第 6 章），同时让门禁有且只有一个归属（见第 12 章）。

「汇总深化」还有一层意思：安全不是发布流水线末端的一个扫描步骤，而是**同一份证据在三个位置被反复校验**。只在一处做，另外两处就能被绕过；三处都做且口径一致，才谈得上「这个产物可信」。SLSA v1.0 把构建过程的可信度分成可判定的级别，回答的是「怎么构建」[R-24-1]；SBOM 用 SPDX 这类标准格式列出镜像里的软件成分，回答的是「含什么」[R-24-5]；签名与验签回答的是「是不是那一个」[R-24-6]。三者缺一，证据链就断在某一环。

三条高频反模式，按「现象 → 根因 → 本章护栏」展开：

**反模式一：只在 CI 扫描，集群不验签。** 现象是流水线里有一排绿色对勾，但某个周五有人为了「先救一下」手工 `docker push` 了一个本地构建的镜像，再用 `kubectl set image` 指过去，集群照单全收——因为镜像从注册表到 Pod 这一跳没有任何人核对它是不是 CI 产出的那个。根因是把「出仓前检查」当成了「入集群前检查」：CI 的检查作用在构建者能控制的路径上，任何绕过这条路径的推送都不会被检查。本章护栏是把验签放到**准入阶段**（在资源真正进入集群前由 API Server 执行的校验，详见第 25 章），由 Kyverno 1.x 的 `verifyImages` 规则对所有 `registry.example.com/order-demo/*` 镜像强制校验签名，无有效签名一律拒绝 [R-24-3][R-24-4]。CI 侧签名、准入侧验签，两侧对称，缺一侧即可被绕过 [R-24-7]。

**反模式二：SBOM 生成后不归档。** 现象是流水线确实跑过 `syft`，但产物只留在当次 runner 的临时目录里；等某天爆出一个基础库漏洞，团队翻遍仓库也回答不了「受影响的是哪些版本、哪些环境在跑」。根因是把 SBOM 当成一次性构建日志，而不是**需要按制品索引长期保留的证据**。本章护栏是制品库保留策略加索引：SBOM 以 OCI 制品形式挂在镜像 digest 上，扫描报告与两份 SBOM 按 `git-<sha7>` 归档并设保留期，已晋升 `order-demo-prod` 的 digest 永久保留。NIST SP 800-190 明确把镜像内容与来源的可追溯性列为容器安全的核心控制项 [R-24-2]。

**反模式三：把「0 漏洞」当上线门槛。** 现象是扫描器一报 HIGH 就卡住发布，而 `distroless` 基础镜像里那个暂时没有修复版本的系统库永远过不了；几轮之后团队开始在流水线里堆白名单，`--ignore-unfixed` 被改成宽泛的 `--skip-files`，门禁名存实亡。根因是把「漏洞数」这个连续量当成了布尔开关，忽略了可利用性与修复窗口。本章护栏是**分级门禁**：只对「有修复版本、且严重程度为 CRITICAL/HIGH」的漏洞阻断，对无修复版本的漏洞记录并要求在修复窗口内复评，例外必须登记到期时间。公开的供应链攻击案例目录反复印证：真正造成损失的是「不知道自己跑了什么」和「没法阻断未授权产物」，而不是「报告里还有几条 LOW」[R-24-9][R-24-2]。

### 24.1.1 翻车现场与取证：一次「手工推镜像绕过 CI」的完整复盘（合成案例）

> 本案例为**合成案例**，按合成案例约定不得冒充真实事件；方法论背景见 [R-24-9]。下列取证步骤全部可以照抄执行——门禁上线之前，这就是每次事故取证的最低动作集。

**时间线**。周五 21:40，`order-demo-prod` 的 `api` 开始返回 500，告警指向「订单金额计算异常」。值班工程师判定是当晚晋升的 `git-b7c4d21` 引入，而修复代码还在另一台开发机上、尚未 push。为了「先让业务跑起来」，他在那台机器上把未提交的调试代码一并打了进去：`docker build -f docker/Dockerfile -t registry.example.com/order-demo/api:git-9f3e2ab .`——注意这个标签**刻意模仿了 CI 的命名格式**，但 `9f3e2ab` 对应的那次提交里根本没有这行调试代码，标签与内容从这一刻起脱钩。随后 `docker push`，再执行 `kubectl -n order-demo-prod set image deploy/api api=registry.example.com/order-demo/api:git-9f3e2ab` 指过去。500 消失，大家回家。三天后用户投诉：部分订单金额被四舍五入到整数——调试代码里的临时逻辑进了生产。

**取证过程**。复盘的目标不是「谁干的」，而是依次回答四个问题：线上到底在跑什么、它是不是 CI 造的、里面含什么、还有哪些环境被波及。每一步都有一条可复制命令和一个明确发现：

```bash
# 1) 确认实际运行制品：标签不可信，摘要才可信（见第 6 章）
kubectl -n order-demo-prod get deploy api \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
# 输出 registry.example.com/order-demo/api:git-9f3e2ab@sha256:5d1f...
#    （kubelet 侧已解析为不可变摘要，取证以 @sha256: 后的值为准）

# 2) 反查 CI 构建记录：在 CI 平台按提交 9f3e2ab 检索全部流水线 run
# 发现：结果为空——没有任何一次构建产出过这个标签，标签系伪造

# 3) 签名取证
COSIGN_PASSWORD="" cosign verify --key cosign.pub \
  registry.example.com/order-demo/api:git-9f3e2ab
# 发现：退出码非 0，报 no signatures found——不是 CI 产物

# 4) 成分取证
cosign download sbom registry.example.com/order-demo/api:git-9f3e2ab
# 发现：不存在对应 SBOM 制品——镜像里含什么，无人能回答

# 5) 注册表侧审计：Harbor 操作日志按 digest 检索
# 发现：该 digest 的推送来自一台开发机 IP 的个人账号，而非 CI 机器人账号；
#      推送时间 21:47，与 CI 的合并触发窗口不符

# 6) 集群侧审计（审计日志采集与检索见第 26 章）
# 发现：审计日志里 set image 的 userAgent 与用户名直接定位到操作者与时刻，
#      与 Harbor 推送时间互相印证，时间线闭环
```

| 证据点 | 位置 | 命令 / 查询 | 结论 |
|---|---|---|---|
| 实际运行摘要 | 集群 | `kubectl get deploy -o jsonpath=…` | 伪造标签的镜像在跑，摘要是唯一可信标识 |
| 构建记录 | CI 平台 | 按提交 SHA 检索 run | 无记录 → 非 CI 产物 |
| 签名 | 制品库 | `cosign verify --key cosign.pub` | 无签名 |
| 成分 | 制品库 | `cosign download sbom` | 无 SBOM，影响面不可判定 |
| 推送来源 | Harbor 审计 | 操作日志按 digest 检索 | 开发机个人账号绕过 CI 推送 |
| 变更入口 | 集群审计 | 按 `set image` 检索（见第 26 章） | 绕过 Git 的手工生产变更（违反公理 5） |

**取证结论（四问四答）**：跑的是 `git-9f3e2ab`；不是 CI 产物（无构建记录、无签名）；成分不可知（无 SBOM，只能按最坏情况处置）；波及范围无法精确圈定——没有成分清单，就无法回答「其他版本是否含同类调试逻辑」，只能全量回滚到 `git-b7c4d21` 之前一个有完整证据链的版本。这次事故最贵的部分不是修复本身，而是**取证期间生产带着成分未知的镜像运行了三天**。

三条护栏在本案例中的落点：如果准入已装验签门禁，该镜像在第 8 步（见 24.2.1 注入点 F4）就会被当场拒绝；如果 SBOM 强制归档，第 4 步的答案就从「不可知」变成一条命令；如果生产变更只允许走 Git（公理 5），第 6 步的 `set image` 根本不会出现在审计日志里。证据链三处校验、两侧对称的设计，正是把这三条护栏从「复盘教训」变成「结构性阻断」[R-24-9][R-24-2][R-24-7]。

> **一个作用域声明**：本章不重复第 6 章的 Dockerfile 与构建命令，也不重复第 12 章的 CI 骨架；本章只负责给「已构建的制品」加装证据与门禁。第 25 章负责策略引擎本身（安装、命名、灰度、测试），本章只给其中一条验签策略，并沿用它的命名与命名空间约定。

## 24.2 落地策略与门禁：三处校验，一条证据链

### 24.2.1 门禁分层与判据表

证据链分三层，每层的失败动作必须是「阻断」而不是「告警了事」，绕过必须留审计。这张表既是设计，也是后面检查清单的判据来源。

| 位置 | 检查项 | 工具 / 机制 | 失败动作 | 绕过审批与审计 |
|---|---|---|---|---|
| 构建（CI 内） | 产物唯一、SBOM 完整 | Syft 1.x 生成 SPDX / CycloneDX；`git-<sha7>` 标签 | SBOM 生成失败即退出，镜像不推送 | 无绕过；构建日志入 CI 审计 |
| 出仓（推送注册表前） | 漏洞分级、签名、归档 | Trivy 0.x 扫描（Grype 0.x 可作等价替换）；cosign 3.x `sign` + `attach sbom` | HIGH/CRITICAL 且可修复则退出；签名失败不推送 | 例外登记 `docs/supply-chain-exception.md`，带到期时间 |
| 入集群（准入） | 签名有效性、来源仓库 | Kyverno 1.x `order-demo-verify-image-signature` | 无签名 / 验签失败 / 非白名单仓库 → 拒绝创建 | 只能临时降级为 `Audit`，须登记例外并自动到期 |
| 归档（制品库） | 按 SHA 可检索、保留期 | Harbor 2.x 保留规则 + `crane 0.x` 检索 | 签名制品或 SBOM 缺失 → 阻断晋升 | 保留规则变更走 Git（见第 14 章） |

> **本书观点（本章第 1 条结论，不需要外部背书）**
>
> **主张**：供应链防护的重心是「可追溯与可阻断」，不是把漏洞数扫到零。
>
> **论证**：把目标定成「零漏洞」，等价于要求基础镜像永不出现任何已知问题，这在有依赖的应用里不可达；不可达的门槛会被团队用白名单绕过，最终连「有没有扫过」都失去可信度。把目标定成「每个在跑的制品都能反查到唯一提交、能列出成分、能被准入拒绝」，则每一条都能用一条命令当场证明，而且不依赖扫描器是否更新到最新漏洞库。
>
> **反例与适用前提**：这不等于「漏洞可以不修」。对有修复版本、且可远程利用的高危漏洞，本章的 CI 门禁是硬阻断；主张针对的是「无修复版本」「仅本地触发」「依赖链深处暂不可达」这类条目，做法是记录 + 修复窗口内复评，而不是永久放行。若团队处于强合规场景（如要求出具零已知漏洞证明），则需以合规口径为准，本观点只适用于以工程可验证性为优先的常规交付。

**四层证据链时序与失败注入点**。把上面这张判据表沿时间轴展开，就是一次变更从提交到生产 Pod 起来的完整证据链。T1–T6 发生在集群之外（构建与出仓、归档），T7–T10 发生在准入（入集群）：

```text
开发者            CI（构建层）              制品库（出仓/归档层）        准入（入集群层）
  │ git push          │                          │                        │
  ├──────────────────>│ T1 一次构建并推送，唯一标签 :git-<sha7>（见第 12 章）
  │                   │ T2 Syft 1.x 生成两份 SBOM ——失败即退出，镜像不推送
  │                   │ T3 Trivy 0.x 分级扫描   ——可修复 HIGH 即退出
  │                   │ T4 cosign 3.x 按 @sha256: 摘要签名 ──> 制品库
  │                   │ T5 attach sbom + 按 git-<sha7> 归档报告 ──> 归档层
  │                   │                          │ T6 保留规则定时执行（3:00）
  │ 晋升 PR 合并（Git 为唯一变更入口，见第 14 章）│                        │
  │                   │                          │ T7 GitOps 同步，Pod 创建请求 ──>│
  │                   │                          │                        │ T8 verifyImages：验签 + 摘要核验
  │                   │                          │                        │ T9 mutateDigest 固定为已验摘要
  │                   │                          │                        │ T10 放行，Pod 起来
```

每层都是一次可注入的演练点。注入的目的不是制造故障，而是证明「失败动作真的是阻断，而不是降级通过」——这与第 23 章的演练思想同源，只是注入对象从运行时换成了证据链：

| 编号 | 注入层 | 注入手法 | 预期阻断行为 | 留痕位置（证据链哪一环） |
|---|---|---|---|---|
| F1 | 构建（T2） | 让 `syft` 输出空文件（`test -s` 失败） | workflow 退出非零，镜像不推送 | CI 构建日志 |
| F2 | 出仓（T3） | 挑一个含可修复 HIGH 漏洞的依赖提交 | `trivy --exit-code 1` 使流水线失败 | CI 审计 + `trivy-report.json` |
| F3 | 出仓（T4） | 同名标签推入不同 digest（标签覆盖攻击） | 签名对象是 digest，新 digest 无签名 | `cosign verify` 失败记录 |
| F4 | 入集群（T8） | 提交未签名镜像（复刻 24.1.1 翻车路径） | Kyverno 准入拒绝，Pod 不创建 | Kyverno 事件 + 审计（见第 26 章） |
| F5 | 入集群（T8） | 停掉 Kyverno webhook 制造「验签不可用」 | `failurePolicy: Fail` → 拒绝而非放行 | API Server 事件 |
| F6 | 归档（T6） | 保留规则误删已晋升 digest | 晋升前校验发现签名/SBOM 缺失 → 阻断晋升 | Harbor 操作日志 |

F4 与 F5 可以直接用 `hack/verify-supply-chain.sh` 与第 25 章的策略测试复现；F1–F3、F6 在 CI 与制品库侧演练，注入一次、留档一份。**每个注入点的预期行为都要在演练记录里写明「阻断发生在哪一层、留痕在哪一环」——留痕位置正是 24.1.1 取证时第一步要查的地方**[R-24-7][R-24-9]。

### 24.2.2 完整可应用配置（Kubernetes 1.32+，Kyverno 1.x）

以下四个文件构成最小可运行门禁；字段沿用第 6 章冻结的配置契约（命名空间 `order-demo-dev` / `order-demo-staging` / `order-demo-prod`、镜像 `registry.example.com/order-demo/<component>:git-<sha7>`、`app.kubernetes.io/name=order-demo`），小版本锁在附录 A。

**`.github/workflows/supply-chain.yml`** —— 构建、扫描、签名、归档一次做完，签名步骤唯一归属本章。

```yaml
name: supply-chain
on:
  push:
    branches: [main]
permissions:
  contents: read
  packages: write
env:
  REGISTRY: registry.example.com
  IMAGE_REPO: registry.example.com/order-demo/gateway
jobs:
  build-sign-archive:
    runs-on: ubuntu-latest
    steps:
      - name: 检出源码
        uses: actions/checkout@v4
      - name: 计算短 SHA（唯一制品标识，见第 6 章）
        id: sha
        run: echo "sha7=$(git rev-parse --short=7 HEAD)" >> "$GITHUB_OUTPUT"
      - name: 登录制品库
        uses: docker/login-action@v3
        with:
          registry: registry.example.com
          username: ${{ secrets.REGISTRY_USER }}
          password: ${{ secrets.REGISTRY_PASSWORD }}
      - name: 一次构建并推送（build once，见第 3 章）
        run: |
          IMAGE_TAG="${IMAGE_REPO}:git-${{ steps.sha.outputs.sha7 }}"
          docker build -f docker/Dockerfile -t "${IMAGE_TAG}" .
          docker push "${IMAGE_TAG}"
          echo "IMAGE_TAG=${IMAGE_TAG}" >> "$GITHUB_ENV"
      - name: 生成 SBOM（Syft 1.x，两种格式都留档）
        run: |
          syft "${IMAGE_TAG}" -o spdx-json=sbom.spdx.json
          syft "${IMAGE_TAG}" -o cyclonedx-json=sbom.cdx.json
          test -s sbom.spdx.json
          test -s sbom.cdx.json
      - name: 漏洞分级门禁（Trivy 0.x，仅阻断可修复的高危项）
        run: |
          trivy image \
            --exit-code 1 \
            --severity CRITICAL,HIGH \
            --ignore-unfixed \
            --format json \
            --output trivy-report.json \
            "${IMAGE_TAG}"
      - name: cosign 3.x 签名（按 digest 签，不按可变标签签）
        env:
          COSIGN_PASSWORD: ${{ secrets.COSIGN_PASSWORD }}
        run: |
          printf '%s' "${{ secrets.COSIGN_KEY }}" > cosign.key
          DIGEST="$(docker inspect --format='{{index .RepoDigests 0}}' "${IMAGE_TAG}")"
          cosign sign --key cosign.key --bundle signature.bundle --tlog-upload=false "${DIGEST}"
      - name: SBOM 作为 OCI 制品挂到镜像，并按 SHA 归档报告
        run: |
          cosign attach sbom --sbom sbom.spdx.json --type spdx "${IMAGE_TAG}"
      - name: 归档 SBOM 与扫描报告（按 git-<sha7> 索引，保留 400 天）
        uses: actions/upload-artifact@v4
        with:
          name: supply-chain-git-${{ steps.sha.outputs.sha7 }}
          path: |
            sbom.spdx.json
            sbom.cdx.json
            trivy-report.json
            signature.bundle
          retention-days: 400
          if-no-files-found: error
```

> 两处刻意的设计：`cosign sign` 的对象是 `RepoDigests` 里的 `@sha256:` 摘要而不是 `git-<sha7>` 标签，因为标签是可变指针、摘要才是内容标识（见第 6 章）；`--tlog-upload=false` 让离线 kind 环境也能完成签名与验签闭环，生产可改用 keyless 模式并把签名者身份写进验签策略的 `subject` / `issuer`。`--ignore-unfixed` 是反模式三的护栏：只对有修复版本的高危项阻断 [R-24-2]。
>
> `--bundle` 在 cosign 3.x 起是**必填**（2.x 时可省略）：签名材料——证书、签名、时间戳——集中落在本地 `signature.bundle` 里，所以它必须和 SBOM、扫描报告一起按 `git-<sha7>` 归档（见下一步）。空气隔离环境只凭这个文件就能离线验签，不必回连 Rekor；这条设计正是 24.2.4「何时不该用 keyless」那节的落地形态。

**`hack/verify-supply-chain.sh`** —— 端到端演示「签名镜像通过、未签名镜像被准入拒绝」，并把降级与恢复一并跑一遍。

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-dev
REPO=registry.example.com/order-demo/gateway
SHA7="$(git rev-parse --short=7 HEAD)"
SIGNED_TAG="${REPO}:git-${SHA7}"
UNSIGNED_TAG="${REPO}:unsigned-${SHA7}"

# 0) 前置：Kyverno 1.x 已部署在命名空间 kyverno（部署方式见第 25 章，本书不写安装教程）
kubectl -n kyverno get deploy >/dev/null 2>&1 || {
  echo "缺少 Kyverno 1.x（命名空间 kyverno），请先按第 25 章部署" >&2; exit 1; }

# 1) 生成密钥对，把策略里的示例公钥换成真实公钥
if [ ! -f cosign.key ]; then
  COSIGN_PASSWORD="" cosign generate-key-pair
fi
PUB_B64="$(grep -v -- '-----' cosign.pub | tr -d '\n')"
sed "s|REPLACE_WITH_COSIGN_PUBLIC_KEY_BASE64|${PUB_B64}|" \
  policies/order-demo-verify-image-signature.yaml > /tmp/verify-policy.yaml
kubectl apply -f /tmp/verify-policy.yaml
kubectl get clusterpolicy order-demo-verify-image-signature -o jsonpath='{.spec.validationFailureAction}{"\n"}'

# 2) 未签名镜像：复用已构建镜像换标签推送，不带任何签名
docker tag "${SIGNED_TAG}" "${UNSIGNED_TAG}"
docker push "${UNSIGNED_TAG}"

# 3) 签名镜像应通过；未签名镜像应被准入拒绝
cat >/tmp/signed-deploy.yaml <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway-signed
  namespace: ${NS}
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: gateway
        version: git-${SHA7}
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: gateway
          image: ${SIGNED_TAG}
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
EOF
kubectl apply -f /tmp/signed-deploy.yaml
kubectl -n "${NS}" rollout status deployment/gateway-signed --timeout=120s

sed "s|image: ${SIGNED_TAG}|image: ${UNSIGNED_TAG}|; s|name: gateway-signed|name: gateway-unsigned|g" \
  /tmp/signed-deploy.yaml > /tmp/unsigned-deploy.yaml
if kubectl apply -f /tmp/unsigned-deploy.yaml > /tmp/unsigned.out 2>&1; then
  echo "FAIL：未签名镜像竟然被准入放行" >&2; exit 1
fi
grep -Eqi 'blocked|denied|failed|verification' /tmp/unsigned.out
echo "OK：未签名镜像被准入拒绝"
cat /tmp/unsigned.out

# 4) 证据可检索：签名、SBOM 制品与按 SHA 归档的报告
COSIGN_PASSWORD="" cosign verify --key cosign.pub --insecure-ignore-tlog=true "${SIGNED_TAG}"
cosign download sbom "${SIGNED_TAG}" > /tmp/downloaded-sbom.json
grep -q 'spdxVersion' /tmp/downloaded-sbom.json
crane ls "${REPO}" | grep '^sha256-' | head -n 5

# 5) 降级演练：Enforce -> Audit -> Enforce，并确认两次状态
sed 's|validationFailureAction: Enforce|validationFailureAction: Audit|' \
  /tmp/verify-policy.yaml | kubectl apply -f -
kubectl get clusterpolicy order-demo-verify-image-signature -o jsonpath='{.spec.validationFailureAction}{"\n"}'
kubectl apply -f /tmp/verify-policy.yaml
kubectl get clusterpolicy order-demo-verify-image-signature -o jsonpath='{.spec.validationFailureAction}{"\n"}'

# 6) 清理演练产物
kubectl -n "${NS}" delete deployment gateway-signed --ignore-not-found
```

### 24.2.4 从静态密钥到 keyless 签名：迁移路径

24.2.2 的示例用静态私钥（`COSIGN_KEY`）完成签名，这是最短路径，不是终态。静态密钥有三重债务：**一是签名者身份单一且可转移**——任何拿到 `COSIGN_KEY` 的主体（人、runner、被攻陷的 CI 插件）都能签出与 CI 完全同权的签名，验签侧无法区分「CI 真的构建过」和「有人冒用密钥」；**二是轮换成本高**——换一次钥要同步更新所有环境的 Kyverno `publicKeys` 与 CI Secret，窗口期内新旧公钥并存；**三是泄露半径不可收敛**——私钥一旦进过 runner 内存或日志，只能假定已泄露 [R-24-6]。

keyless 模式把这三条逐一对消：CI 凭借 OIDC 身份令牌向 Sigstore 的 Fulcio 换取一张**绑定身份、短时效的签名证书**，用临时私钥完成签名，签名记录写入 Rekor 透明日志（append-only，可证明「何时、以何身份、为哪个 digest」签过名，事后不可抵赖、不可篡改）[R-24-6]。验签侧校验的不再是「你有没有那把钥」，而是「你的签名是否绑定了预期 issuer 与 subject、是否在透明日志里」。

对 24.2.2 workflow 的最小改造只有两处——权限声明与签名步骤：

```yaml
permissions:
  contents: read
  packages: write
  id-token: write      # 新增：允许 CI 换取 OIDC 身份令牌
```

```yaml
      - name: cosign 3.x keyless 签名（替换静态密钥步骤）
        run: |
          DIGEST="$(docker inspect --format='{{index .RepoDigests 0}}' "${IMAGE_TAG}")"
          cosign sign --yes "${DIGEST}"
          # 无 --key：走 OIDC 身份 + 临时密钥 + 透明日志上传；
          # 原步骤里的 --tlog-upload=false 一并删除
```

验签命令随之去掉 `--insecure-ignore-tlog`，改为显式校验身份：

```bash
cosign verify \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp \
    '^https://github.com/example-org/order-demo/\.github/workflows/supply-chain\.yml@refs/heads/main$' \
  registry.example.com/order-demo/gateway:git-<sha7>
```

**迁移五步，每步带验证与回退**（切换窗口内新旧两种签名并存，证据链不断）：

| 阶段 | 动作 | 验证 | 回退 |
|---|---|---|---|
| 一：双签过渡 | CI 同时执行静态签名与 keyless 签名；Kyverno `attestors` 改为 `count: 1` + 两类 `entries`（任一通过即放行，见下方配置） | 两类签名镜像都能起 Pod；未签名镜像仍被拒 | 删除 keyless `entries`，恢复纯静态 |
| 二：透明日志核验 | 验签命令不再带 `--insecure-ignore-tlog` | `cosign verify` 退出码 0，输出含 Rekor inclusion proof | 阶段内静态签名仍带 tlog 关闭参数，单独验旧镜像时临时加回 |
| 三：切入 keyless 单一信任 | `attestors` 删除 `keys` 条目，只留 `keyless` | 手工静态签名镜像被准入拒绝；keyless 镜像正常 | 恢复双 entries 配置（`kubectl apply` 旧文件） |
| 四：凭据收尾 | 删除 CI Secret `COSIGN_KEY` / `COSIGN_PASSWORD`；公钥归档到 Git 留作历史取证 | 静态私钥在 Secret 平台检索为零记录 | 无需回退（公钥仍在，历史 digest 旧签名仍可验） |
| 五：演练闭环 | 重跑 `hack/verify-supply-chain.sh`，verify 段换成上方 keyless 参数 | 未签名镜像仍被准入拒绝；签名镜像正常 | 回滚方案即阶段三的旧配置文件 |

**过渡期的 Kyverno attestors 配置**（阶段一至二生效；`count: 1` 下多个 `entries` 为「任一满足」语义 [R-24-3][R-24-6]）：

```yaml
          attestors:
            - count: 1
              entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      REPLACE_WITH_COSIGN_PUBLIC_KEY_BASE64
                      -----END PUBLIC KEY-----
                - keyless:
                    subject: "https://github.com/example-org/order-demo/.github/workflows/supply-chain.yml@refs/heads/main"
                    issuer: "https://token.actions.githubusercontent.com"
                    rekor:
                      url: "https://rekor.sigstore.dev"
```

两点边界：**离线 / 空气隔离环境无法访问 Rekor**，应保持静态密钥方案，这是 keyless 的适用前提而非能力缺陷；**keyless 的信任根是 CI 的 OIDC 身份提供方**——`COSIGN_KEY` 等静态签名凭据的盘点、轮换与最小权限归第 26 章的凭据治理统一管，本章只定义签名机制本身；构建与 CI 骨架的分工见第 12 章（：签名唯一归属本章 workflow）。

### 24.2.5 SBOM 差量分析：漏洞应急中的影响面速查

反模式二的护栏把两份 SBOM 按 `git-<sha7>` 长期归档，归档的价值在漏洞应急时兑现：**对两次构建的 SBOM 做差量，能在十分钟内回答「这次变更是否引入了受影响成分、回滚是否有效」**——这正是 24.1.1 取证里「成分不可知」的反面 [R-24-5][R-24-2]。

场景：漏洞公告指出某基础库 `libfoo` 2.14.0–2.14.3 存在可远程利用的漏洞，当前 `order-demo-prod` 在跑 `api` 的某 `git-<sha7>`。第一步先回答「回滚有没有用」：

```bash
# 取当前 prod 在跑 digest 的 SBOM（摘要从 Deployment 现场读，不抄标签）
DIGEST=$(kubectl -n order-demo-prod get deploy api \
  -o jsonpath='{.spec.template.spec.containers[0].image}' | sed 's/.*@/')
cosign download sbom "registry.example.com/order-demo/api@${DIGEST}" > sbom-now.json

# 取上一个已知良好版本的 SBOM（按 SHA 从归档取回，依赖反模式二的保留策略）
cosign download sbom registry.example.com/order-demo/api:git-b7c4d21 > sbom-prev.json

# 两次构建的成分差量：新增 / 移除了什么
jq -r '.packages[].name' sbom-now.json  | sort > now.list
jq -r '.packages[].name' sbom-prev.json | sort > prev.list
diff prev.list now.list

# 精确到版本号：受影响库在两个版本里各是什么版本
jq -r --arg n libfoo '.packages[] | select(.name==$n) | .versionInfo' \
  sbom-now.json sbom-prev.json
```

差量结果与处置的判读表：

| 差量结果 | 判读 | 处置 |
|---|---|---|
| 旧版本同样含受影响版本 | 漏洞早已存在，与本次变更无关 | **回滚无效**；走前向修复（升级依赖重新出仓）+ 按反模式三登记例外与复评窗口 |
| 仅新版本引入受影响版本 | 本次变更引入 | 按公理 6 回滚到上一良好版本；CI 升级依赖、过漏洞门禁后重新出仓 |
| 两个版本均不含 | 扫描器误报或 SBOM 生成口径差异 | 核对两份 SBOM 的格式与生成工具版本，登记误报并统一口径 |

第二步圈定影响面：对制品库里全部 `git-` 标签批量做成分核对，把「哪些镜像受影响」变成一份确定清单：

```bash
for t in $(crane ls registry.example.com/order-demo/api | grep '^git-'); do
  if cosign download sbom "registry.example.com/order-demo/api:${t}" 2>/dev/null \
     | jq -e --arg n libfoo \
         '.packages[] | select(.name==$n and (.versionInfo | test("^2\\.14\\.[0-3]$")))' >/dev/null; then
    echo "受影响: ${t}"
  fi
done
```

再把受影响标签与各环境 Deployment 的镜像标签比对（`kubectl -n order-demo-{dev,staging,prod} get deploy -o jsonpath` 逐环境核对），得到「dev / staging / prod 各受影响哪些版本」，据此排修复优先级：prod 先行，staging 复现验证，dev 修复开发。差量结论与受影响清单写入应急记录（与 `docs/supply-chain-exception.md` 同级归档），证据链在应急侧闭环。**前置依赖只有一条：上一良好版本的 SBOM 必须还取得到——这就是反模式二坚持按 SHA 长期归档的原因**[R-24-5][R-24-2]。

### 24.2.6 SBOM 的生成与消费：让证据有读者

反模式二解决的是「存不存」，这一节回答「存了之后谁在什么时刻读它、读哪一份」。归档之后没有固定消费者的 SBOM，六个月后就和构建日志一样无人问津——这是比不生成更隐蔽的浪费。

**生成侧的三个易错点**（24.2.2 的 workflow 已经规避，这里写明为什么）：

1. **扫描对象是注册表里的镜像引用，不是本地构建视图**。Syft 1.x 直接从注册表拉取 manifest 与 layer 清点成分，产出的清单与准入侧 `cosign download sbom` 取回的同源；在多阶段构建与构建缓存存在时，本地 daemon 视图可能与注册表内容不一致，用本地视图生成的 SBOM 会给证据链引入一个「归档物与运行物不同源」的暗缝。
2. **SBOM 是生成时刻的快照，绑定 digest 而非标签**。同名标签被覆盖推送（F3 场景）后，旧 SBOM 制品仍挂在旧 digest 上，恰好成为「标签是否被覆盖」的旁证——这正是把 SBOM 作为 OCI 制品挂到 digest 而不是按文件名归档的原因之一 [R-24-5]。
3. **区分镜像 SBOM 与源码 SBOM**。本章证据链口径只认镜像 SBOM（覆盖运行时全部层）；源码依赖清单（`go.sum`、`package-lock.json` 这类）属于第 12 章构建可复现性口径，两者不做互相替代。

**格式选择：为什么两种都生成**。

> **本书观点（不需要外部背书）**
>
> **主张**：SPDX JSON 做证据链主口径（`cosign attach sbom` 挂到镜像），CycloneDX JSON 做应用依赖口径（随构建归档），两份都留。
>
> **论证**：两种都是机器可读的标准格式 [R-24-5]；准入、取证、差量（24.2.5）三条主路径只依赖其中一份，选定 SPDX 做主口径后，第二条路径的存在意义是让「应用依赖视角」的消费者（如依赖升级决策）不必从系统库清单里反查。双份归档的边际成本只是每镜像几十 KB 与一行 CI 命令。
>
> **反例与适用前提**：归档容量严格受限的团队只留 SPDX 即可——三条主路径不受影响；但「两种都不留只留扫描报告」不成立，扫描报告是时点结论，SBOM 才是可重放询问的原始证据。

**存哪里、谁消费、读哪份**：

| 消费者 | 时刻 | 读哪份 | 回答什么问题 |
|---|---|---|---|
| 漏洞应急（24.2.5） | 公告发布时 | 归档的 spdx-json | 回滚有没有用、影响面多大 |
| 扫描器定期重扫 | 每周 / 漏洞库更新后 | 同一份归档 SBOM | 用统一成分视图喂扫描器，保证「重扫结果」能在归档证据里对上成分 |
| SRE 风险台账 | 季度 | prod 在跑 digest 的 SBOM | 线上到底含哪些组件与版本 |
| 合规审计 | 抽查时 | 按 `git-<sha7>` 检索 | 能否证明某时刻跑的是什么 |
| 下游交付 | 镜像交付外部使用方时 | 交付物附带 SBOM | 使用方的供应链合规要求 |

**漏洞扫描如何接到归档 SBOM**。Trivy 0.x 除了扫镜像，也能直接以 SBOM 文件为输入扫描。两种入口的差别在于成分口径：让扫描器自己扫镜像，成分视图由扫描器现场清点，可能与归档 SBOM 有出入；把归档的 spdx-json 喂给扫描器，漏洞结果与证据链口径完全同源。**定期重扫（不重新构建）一律走 SBOM 输入路径**：

```bash
trivy sbom sbom.spdx.json --severity HIGH,CRITICAL --ignore-unfixed
# 通过标准：输出漏洞条目的 PkgName 都能在 sbom.spdx.json 里 jq 到同名 packages 条目，
# 即「报告的每个漏洞都能回指到归档成分」，两条证据互相锚定
jq -r --arg p "<PkgName>" '.packages[] | select(.name==$p) | .versionInfo' sbom.spdx.json
```

**生成质量校验：把 F1 的 `test -s` 升级为成分下限校验**。24.2.1 的注入点 F1 只验证「SBOM 非空」，但 `syft` 在个别 layer 解析失败时会产出**截断但不为空**的 SBOM——它通过 `test -s`，却漏掉了基础镜像的系统库清单，门禁形同虚设。构建层校验做两件事：数量下限（`order-demo` 三个组件基于 distroless，成分不会低于两位数）与关键成分存在性：

```bash
# 数量下限：packages 少于 10 视为截断（阈值随基础镜像调整，写进 workflow 环境变量）
PKG_COUNT=$(jq '.packages | length' sbom.spdx.json)
[ "${PKG_COUNT}" -ge 10 ] || { echo "SBOM 疑似截断：仅 ${PKG_COUNT} 个成分" >&2; exit 1; }

# 关键成分存在性：基础镜像的 libc 必须在清单里（distroless 含 glibc）
jq -e '.packages[] | select(.name | test("glibc|libc6"))' sbom.spdx.json >/dev/null \
  || { echo "SBOM 缺少基础镜像关键成分，疑似截断" >&2; exit 1; }
```

通过标准：两条断言在 CI 构建层执行（并入 24.2.2 workflow 的 SBOM 步骤），失败即退出、镜像不推送——与 F1 同层的失败动作，只是判据从「非空」收紧到「下限 + 关键成分」。阈值登记在 workflow 注释里，换基础镜像时随单一示例实现登记一起评审，而不是事故后追调 [R-24-1][R-24-5]。

**保鲜判据：SBOM 何时需要重生成**。归档 SBOM 经常被问「会不会过期」，答案分两种情况。**镜像重新构建（digest 变化）→ 必然重生成**：SBOM 挂在 digest 上，新 digest 自然产生新 SBOM，不需要额外动作；同一 `git-<sha7>` 标签被重推属于 F3 攻击场景，按安全事件处理，不存在「覆盖后补生成」的合法路径。**漏洞库或扫描器升级 → 不重生成**：SBOM 描述的是成分，成分不因漏洞库更新而变化；重扫走 24.2.6 的 SBOM 输入路径，改的只是「对同一份成分清单的判定」，而不是清单本身——重生成反而会破坏「按 SHA 检索到的永远是同一份」的口径，让差量分析失去可比性。唯一需要批量重生成的例外：Syft 1.x 大版本升级导致输出格式变化时，登记一次性的批量重生成任务，新旧格式双份保留一段时间，旧镜像的差量结论在过渡期内标注生成工具版本。判据写进团队 runbook：被问「SBOM 要不要更新」时，先问「digest 变了吗」——变了走流水线，没变就不动 [R-24-5][R-24-2]。



### 24.2.7 准入验签的失败处置：五类拒绝，五条路径

验签门禁上线后，值班最先遇到的不是「怎么配」，而是「被拒了怎么判」。拒绝原因五类，处置路径完全不同，误判会把可用性事故升级成安全事件，或者反过来：

| 拒绝现象（apply 报错 / 事件） | 根因 | 处置 | 禁止动作 |
|---|---|---|---|
| `no signatures found` | 镜像未经 CI 签名（绕道推送，或 CI 签名步骤失败） | 查 CI run：失败则修流水线重跑；确需手工救场，走 24.2.3 例外登记 | 手工 `cosign sign` 救场且不登记例外 |
| `signature verification failed` / 密钥不匹配 | 策略 `publicKeys` 与 CI 密钥不同代（轮换窗口错位） | 比对公钥指纹；按 24.2.4 迁移表的回退列恢复对应阶段配置 | 往策略里追加一个「先放行」的公钥 |
| digest 不匹配（`verifyDigest` 失败） | 标签被覆盖推送（F3 场景） | 按 24.1.1 取证流程处理，按安全事件对待 | 重推一个「修复」标签掩盖现场 |
| webhook 超时 / `internal error`（`failurePolicy: Fail` 生效） | Kyverno 不可用——**可用性问题，不是安全事件** | 查 `kyverno` 命名空间 Pod 与 webhook 配置；恢复前发布自然被阻断（fail-closed 按设计生效） | 降级 `Audit` 并当作长期状态 |
| 拒绝之后出现 `imagePullBackOff` | 验签已通过，拉取失败是仓库认证 / 网络问题 | 查 `imagePullSecrets` 与网络策略 | 当作验签问题排查 Kyverno |

**一个高发误判**：准入拒绝发生在 API Server 响应里——`kubectl apply` **立即**返回非零、Pod 对象根本不存在；而 `imagePullBackOff` 说明准入已放行、Pod 已创建只是拉不动镜像。判据一条就够：apply 是「立即失败」还是「创建成功后才失败」。把后者当验签问题去查 Kyverno，会浪费整个值班窗口。

诊断命令（按顺序执行，定位到「策略侧」还是「镜像侧」）：

```bash
# 1) 策略当前状态：生效模式与失败策略是否如设计
kubectl get clusterpolicy order-demo-verify-image-signature \
  -o jsonpath='action={.spec.validationFailureAction} fail={.spec.failurePolicy}{"\n"}'
# 通过标准：action=Enforce、fail=Fail

# 2) 最近拒绝事件，拒绝原因在 message 里逐字可读
kubectl -n order-demo-prod get events --field-selector reason=PolicyViolation \
  --sort-by=.lastTimestamp | tail -n 5

# 3) 本地复现验签：区分策略问题与镜像问题
COSIGN_PASSWORD="" cosign verify --key cosign.pub --insecure-ignore-tlog=true \
  registry.example.com/order-demo/api:git-<sha7>
```

判读：本地 `cosign verify` 通过而集群拒绝 → 问题在策略侧（公钥不同代、match 范围错），回到第 1 步核对策略内容；两边都失败 → 问题在镜像侧，按 24.1.1 取证。处置终点只有三个：**重新走 CI、按 24.2.3 登记例外临时降级、回滚变更**（公理 6）。任何一条路都不包括放宽 `imageReferences` 或删减 `attestors`——那是把门禁拆掉，不是处置故障 [R-24-3][R-24-6]。

### 24.2.8 边界：何时不该签名、何时不该强制 SBOM

门禁的作用域应当等于风险的作用域。对不进生产的镜像强制全套签名与归档，换来的成本是流水线摩擦；摩擦高到一定程度，团队会复刻反模式一——找一条绕过的路。本章边界按三类场景划定：

**一、内部临时镜像：不强制签名，用标签前缀与作用域隔离。** 本地 kind 调试镜像、24.2.2 演练脚本里的 `unsigned-<sha7>` 标签，生命周期以小时计、永不承载真实流量，为它们签名只增加摩擦。护栏是**作用域收窄而非豁免**：准入策略只 match `order-demo-dev` / `order-demo-staging` / `order-demo-prod` 三个命名空间与 `registry.example.com/order-demo/*` 仓库；其余环境由第 25 章的策略体系另行约束，生产命名空间不存在任何豁免路径。两条配套纪律：临时镜像不带 `git-` 前缀——24.1.1 的伪造正是靠冒充这个前缀混过肉眼检查；临时标签不进保留策略，90 天自动清空。代价是 dev 环境存在无证据镜像；补偿是它与 prod 之间隔着「签名 + 摘要核验 + Git 晋升」三道闸。

**二、空气隔离环境：签名照做，透明日志与 keyless 让位。** keyless 依赖访问 Fulcio / Rekor，空气隔离环境不可用（24.2.4 已声明适用前提）；但**签名本身离线可做**——静态密钥的签验闭环不需要任何外联。该环境保持静态密钥方案，验签侧不要求 tlog 核验。真正的边界在信任根：空气隔离环境的信任根是「内部保管的公钥」，必须回答三问——公钥由谁生成、存在哪、丢失后按什么流程重建信任；答案写进内部凭据管理流程（凭据的盘点与轮换归第 26 章）。SBOM 在该环境照常生成（Syft 离线可用），只是归档降级为本地制品库，24.2.5 的差量分析在本地完成。

**三、第三方镜像：先问「能不能把它变成自己的」。** 上游镜像（数据库、采集器这类）不可能用你的密钥签名，验签侧对它的信任根要单选：

| 信任根选择 | 做法 | 适用前提 | 代价 |
|---|---|---|---|
| 重新构建（首选） | 以官方镜像为基础或从源码构建，产物进 `registry.example.com/order-demo/*`，吃同一套签名与 SBOM 门禁 | 有构建能力且上游许可允许 | 持续跟进上游更新的构建成本 |
| 验上游签名 | 镜像引用 pin 到 `@sha256:` 摘要 + 独立 `attestors` 条目校验上游官方签名或维护者 keyless 身份 [R-24-6] | 上游提供签名且签名者身份可枚举 | 多一套 attestors 的维护与升级跟随 |
| 仅 pin 摘要 | 引用写死 `@sha256:`，无签名校验 | 仅限 dev / staging | 无来源验证；digest 虽不可变，但「选哪个 digest」仍依赖人——注册表侧需配合不可变 tag 才能防同名重推 |

prod 只接受前两种。**SBOM 的「不该强制」主要在消费侧而非生成侧**：生成成本是一条命令，几乎总该做；不该做的是「对第三方 SBOM 承诺同等消费」——供应商提供的 SBOM 未经验证口径，不挂进本章证据链主口径、不参与 24.2.5 差量，只作参考归档。所有边界内情形与临时例外统一登记 `docs/supply-chain-exception.md` 并带到期时间（CL-24-04）；「场景豁免」与「临时例外」混进同一个无到期清单，是边界失守的第一步 [R-24-2][R-24-9][R-24-7]。

三类边界收敛成一棵可判定的树，新镜像接入时先过这一问：

```text
这个镜像会进 order-demo-dev / staging / prod 三个命名空间之一？
├─ 是（生产证据链作用域）
│    └─ 必须走 CI 签名 + SBOM + 摘要核验；第三方镜像只接受
│       「重新构建」或「验上游签名」两种信任根，无豁免路径
└─ 否（边界内）
     └─ 仓库在 registry.example.com/order-demo/* 下？
          ├─ 是 → 允许 unsigned- 前缀临时镜像；不带 git- 前缀，
          │        不进保留策略，90 天清空
          └─ 否 → 归第 25 章策略体系约束，本章不背书
```

树的价值在「变更评审时先问作用域」：任何关于「这个镜像要不要签名」的讨论，答案都由它在树上的位置决定，而不是由当场讨论的声量决定。树上没有的分支（比如「临时放开某次 prod 部署」）不是边界问题，是例外问题——按 CL-24-04 走例外登记，到期自动失效。
