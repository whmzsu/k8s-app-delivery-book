## 10.1 问题与反模式：只 review 模板，等于没 review

到第 9 章为止，`order-demo` 跑通了最小闭环、补齐了四类工作负载、配好了探针与优雅上下线、把配置与凭据彻底分开。代价是清单散成十几个文件：三份 Deployment、一份 StatefulSet、四份 Service、ConfigMap、PDB、SecretStore、ExternalSecret，还叠了第 8、9 章的增量字段。现在要发三个环境、还要把 `gateway` 交给另一个团队复用，团队很自然地做了三个动作：给每个环境复制一整份目录、在模板里加一堆 `if` 分支、把「最终提交了什么」交给 CI 自己算。**合成案例**（本书统一采用虚构合成案例，见第 1 章）：某次 PR 只改了 `values.yaml` 里一个默认值 `replicas: 3`，reviewer 看的是模板那一行的 diff，觉得毫无风险就合了；渲染后三个环境的 `gateway` 副本数同时变成 3，prod 的节点余量不够，一半 Pod `Pending`，而仓库里没有任何一份文件记录过「这次提交到底给集群送了什么」。排查时值班同学得先在本地把模板渲染出来，才能开始猜是哪一层把值改了——此时已经过去四十分钟。

这里的落差是：**清单**（manifests，描述期望状态的 YAML 声明文件，正式定义见 10.2）一旦被模板和 overlay 包起来，「你 review 的文件」和「集群收到的文件」就不再是同一个东西 [R-10-4]。模板是意图，渲染产物才是事实；只审意图、不审事实，等于把审查让给了渲染器 [R-10-8]。

这一章的题目有点反直觉：它看起来是在讲「怎么组织文件」，实际讲的是**怎么让审查重新变得有意义**。前面几章你 review 什么，集群就收到什么，两者是同一份东西。从这一章起它们分家了，而**分家这件事本身没有声音**——PR 里照样有 diff，CI 照样绿色，只是那个 diff 和集群里发生的事已经不太是同一件事了。

三个高频反模式，按「现象 → 根因 → 本章替代做法」展开：

**反模式一：overlay 继承链套了五六层。** 现象是 `prod` 的 `kustomization.yaml` 继承 `base` → `common` → `region` → `prod-base` → `prod` → `prod-canary`，某个字段最终来自哪一层没人说得清，改一处要重渲染五遍才能确认。根因是把 overlay 当成「继承」用，而 Kustomize 5.x 的 overlay 本质是**patch 叠加**，层级越多越难归因 [R-10-2]。本章的替代做法是把继承链收敛到两层（`base` + 单层 overlay），差异写在同一处 `kustomization.yaml` 里，层级上限写进检查清单（CL-10-04）[R-10-2]。

这条反模式最迷惑人的地方是它**每一层都很有道理**。「prod 当然从 staging 来」「亚太区当然和总部分开」——单独听每句话都是对的，合起来就变成了一句没人能验证的话：**这个值到底是谁定的？**层数一旦超过三层，回答这个问题的时间就开始超过重新写一份清单的时间，而团队往往还在继续加第四层。

**反模式二：values 爆炸（几百个键、大量条件分支）。** 现象是 `helm lint` 能过，但模板里 `{{ if .Values.x }}{{ if .Values.y }}` 嵌套到没人能心算渲染结果，release 升级时状态漂移 [R-10-1][R-10-7]。根因是把「对外可配置项」和「内部实现细节」都塞进 values。本章的替代做法是限制可配置项（`values.yaml` 只暴露 6 个键）、复杂 Chart 拆 Library Chart，并把「values 分层」写成检查项（CL-10-03）[R-10-1]。

**反模式三：只 review 模板 PR 不看渲染 diff。** 现象就是开头那起事故：一个默认值改动悄悄改了全部环境，而 PR 里看不出任何痕迹。根因是渲染产物没有作为一等产物进版本控制与 CI [R-10-8][R-10-10]。本章的替代做法是：把 `helm template` / `kustomize build` 的输出作为 PR 附件归档，CI 里对渲染产物跑四道关卡，任何一次提交的「最终清单」都可逐行 diff、可归因到某次 Git 提交 [R-10-3][R-10-5]。

**一次完整的翻车现场（合成案例，遵循第 1 章标注约定）**

把反模式三落到一条真实的诊断时间线上，才能看清「默认值改动悄悄改了三个环境」的代价。某周五下午，`order-demo` 对外分发的 `deploy/charts/order-demo/values.yaml` 里，两个默认值被静默改掉：`gateway.resources.requests.cpu` 从 `50m` 改成 `200m`，`replicas` 从 `2` 改成 `3`。提交者的理由是「只是默认值，没动模板逻辑」，所以 PR 的 diff 在 GitHub 上只有两行 values；reviewer 照例只看模板那一行的 diff，确认「模板结构没变」就点了 approve。三套环境（dev/staging/prod）共用同一份 `values.yaml` 作为默认基线，只有环境特异值写在 `values-dev.yaml` 等文件里——而这两个键恰好没被环境文件覆盖。于是渲染后：dev 的 gateway 从 2 副本变 3 副本、requests.cpu 翻倍；staging 同；prod 同。dev 节点余量大没出事，staging 触发资源告警，prod 因为一个 gateway Pod `Pending` 把滚动更新卡住，进而 `/healthz` 探活失败，入口开始间歇性 5xx。

值班同学接到的第一句描述是「gateway 部署异常，部分请求 5xx」。他的排查路径是：

**那两分钟的 review 里发生了什么**（依同类事故共性还原，非原话）：

> **提交者**：就改了两个默认值，模板逻辑一点没动，放心。
> **reviewer**：`replicas` 从 2 到 3……这个是为什么？
> **提交者**：哦，本地压测的时候 2 个有点吃紧，加上去了。反正现在也没人覆盖它，就是个默认值。
> **reviewer**：行吧，模板没变就好。
> （三小时后）**值班**：prod 有个 gateway 是 Pending，节点没 CPU 了。谁动了资源？

这段对话里最值得注意的不是「行吧」，而是提交者那句「**反正现在也没人覆盖它**」。他说的完全是事实，而且他真的去确认了——这恰恰是问题所在：**「没人覆盖」在 Helm 的语义里等于「三个环境全都继承」**。同一句话，在一个环境里读作「安全」，在三个环境里读作「同时生效」。而 review 的界面只显示了后者的一半。

1. `kubectl -n order-demo-prod get pods` 看到 `gateway-xxx` 处于 `Pending`，`kubectl describe pod` 报 `0/5 nodes are available: 5 Insufficient cpu`——节点 CPU 不够。但本周没有扩容，也没人申报资源调整。
2. 怀疑是最近发布带来的，但 `helm history order-demo -n order-demo-prod` 显示最近一个 release 修订只改了 `greeting` 文案；`kubectl -n order-demo-prod get deploy gateway -o yaml | grep -A2 requests` 却显示 `cpu: 200m`——release 状态和实际清单对不上，说明不是 Helm release 直接带来的，而是某次 `helm template` 渲染基线变了。
3. 拉出最近三天 Git 提交，逐条 `git show` 模板与 values，才定位到 `values.yaml` 那两行默认值改动。此时已过去约 40 分钟，staging 半瘫、prod 靠旧副本硬撑。
4. 真正的根因定位靠**渲染 diff**：对改动前后两次提交分别跑 `helm template`，归一化（见 10.4.1）后 `diff`，第一次看清「`requests.cpu` 和 `replicas` 都被默认值改了，且三环境同时中招」。此前仓库里没有任何文件记录「这次提交到底给集群送了什么」——因为渲染产物没进版本控制，PR 里只有模板/values 的 diff，没有渲染产物的 diff。

```bash
# 对改动前后两次提交分别渲染、归一化后再 diff（命令见 10.4.1）
$ diff -u \
    <(git show HEAD~1:deploy/charts/order-demo/values.yaml \
        | helm template order-demo deploy/charts/order-demo -f - | normalize) \
    <(helm template order-demo deploy/charts/order-demo \
        -f deploy/charts/order-demo/values.yaml | normalize)
-  replicas: 2            # dev/staging/prod 三环境共用同一份默认值
+  replicas: 3
-    requests:
-      cpu: 50m
+      cpu: 200m
```

这次事故把反模式三的代价钉死了：模板 diff 看不到默认值隐含的跨环境影响，而跨环境共享同一份 values 基线意味着「一个默认值改动 = 三个环境同时改动」。修复动作是回退那次 PR 的 values（等价于回到 Git 上一 tag，见 10.5 方案 B），并把「渲染产物必须作为 PR 附件、且三环境各自渲染 diff 都要过 CI」写进 CL-10-01 与 CL-10-02。背后的公理是：**清单（manifests）与渲染产物（rendered manifests）分离时，审查对象必须是后者** [R-10-4]；**差异可归因是防止「悄悄改了三个环境」的唯一抓手** [R-10-8]；**配置与产物分离要求环境差异走配置而非默认值埋雷** [R-10-10]。

**为什么默认值在 Chart 里比 overlay 更隐蔽**：Kustomize 5.x 的 overlay 把每个环境的差异**显式写在同一处 `kustomization.yaml`**（replicas、namespace、patch），改了什么一眼可见 [R-10-2]；而 Helm 4.x 的 `values.yaml` 默认值是「隐藏的全局基线」，只有被环境文件显式覆盖才会变，否则三环境 silently 继承。这正是 10.2 决策树「同源多环境用 overlay、对外分发用 Chart」的代价面：Chart 适合分发，但不适合当多环境基线的唯一真相 [R-10-1]。把多环境基线交给 overlay、把 Chart 限定为「对外分发的最小可复用单元」（只承载 `gateway`），正是本书选型基线把二者定为「同一份应用定义的两种消费方式」而非竞品的原因（见 10.3）。

本次事故的四条对冲项，沿用 §10.6 五列格式：

| 编号 | 本事故的对冲项 | 怎么查 | 通过标准 | 失败处置 |
|---|---|---|---|---|
| 事故-1 | 默认值改动须触发三环境渲染 diff | 对 PR 前后两次提交各跑 `helm template` 并归一化 diff | 任何 `replicas`/`resources` 隐含变更都出现在 PR 附件 | 回 10.4.1 归一化后逐字段比对 |
| 事故-2 | 环境文件必须显式覆盖关键键 | `yq '.replicas, .gateway.resources' values-*.yaml` | 三环境各自的 `replicas`/`requests` 显式给出 | 在 overlay 或 values-env 中补齐 |
| 事故-3 | release 状态与实际清单一致 | `helm get values order-demo -n order-demo-prod` 比对 | 与 `kubectl get deploy gateway -o yaml` 一致 | 回 10.5 方案 A 校准 |
| 事故-4 | 渲染产物进版本控制 | 查 PR 附件 / Git 内 `rendered/` 目录 | 每次提交都有可 diff 的产物基线 | 回 10.4 四道关卡补齐归档 |

> **本章是 H7 的技术前提**：第 1 章事故里「有人手工 `kubectl edit` 改了生产」这一失效点（H7），要靠 Git 唯一真相 + 漂移检测来堵；而漂移检测的前提，正是有一份**确定、可比对**的渲染产物可当基准。这份产物在本章第一次被正式定义并进 CI，GitOps 控制器怎么消费它留到第 14 章（见第 14 章）。本章无事故钩子主责，按 9.7 不硬凑「回到第 1 章」。

## 10.2 范式与决策树：patch、模板还是代码生成

本章要回答的决策问题是：**配置该用 patch、模板还是代码生成，判断依据是什么，以及渲染产物该在哪一步被审查？**

这三个选项有个不太对称的地方：**patch 出错时你能看见，模板出错时你看不见**。patch 改错了，diff 上就是那几行；模板改错了，diff 上是 values 的一行，而后果在三个环境里同时发生。所以本章真正要解决的不是「选哪个工具」，而是「**选完之后，用什么机制保证你还能看见后果**」。

先给两个术语的正式定义，后面所有判据都从它们推导。

**清单（manifests）的正式定义**：描述期望状态的 YAML/JSON 声明文件，能被 `kubectl apply` 直接接受；`kubectl run` 这类命令式操作不是清单 [R-10-4]。

**rendered manifests（渲染产物）的可验证定义**：模板渲染完、真正提交给集群的那份清单（白话，深入展开见第 14 章）。判定一份文件是不是 rendered manifests，靠三条**可验证**条件，而不是靠「看起来像最终版」：

1. **命令确定**：由一条仓库内可复现的命令产生（`helm template` 或 `kustomize build`），输出只依赖仓库内文件，不依赖集群状态、不依赖本机环境变量 [R-10-1][R-10-2]。
2. **语法封闭**：输出里不含 `{{ }}` 模板表达式、未解析的 `$()` 变量、未应用的 patch 占位，可被 `kubectl apply --dry-run=server` 直接接受 [R-10-4][R-10-5]。
3. **差异可归因**：把它存成文件后，与上一版逐行 diff，每一处差异都能指向某次 Git 提交；做不到这一点的，说明还有人工渲染或集群内渲染没被收进来 [R-10-8]。

第 3 条是本书把「渲染产物」抬到一等公民的原因：GitOps（Git 里写什么、集群就变成什么，详见第 14 章）需要一个可比对的对象，模板本身不能当这个对象 [R-10-4]。

**判据的自检表（什么产物不算 rendered manifests）**：

| 现象 | 违反哪条 | 处置 |
|---|---|---|
| 产物里出现未替换的占位（空 `""` 键或整键缺失） | 语法封闭（第 2 条） | 回 10.4.1 归一化空值，模板补默认值 |
| 渲染命令读取集群状态、`KUBECONFIG` 或环境变量 | 命令确定（第 1 条） | 渲染只允许依赖仓库内文件 |
| `helmCharts` 未锁 Chart version 与 helm 版本 | 命令确定（第 1 条） | 版本锁进附录 A（见 10.3.1 形态 B） |
| 产物只存在于 CI 临时目录 | 差异可归因（第 3 条） | 归档为 PR 附件（10.4 工作流最后一步） |
| 两个同事各自渲染结果不一致 | 命令确定（第 1 条） | 检查渲染器版本与 values 来源是否锁定 |

判定表里「保持裸清单」那一支不是弃权：它的含义是「所有抽象升级临界点都未触发」（临界点表见 10.3.1），第 6 章的裸清单同样要过上面这张自检表——判据对三种工具一视同仁，也对「无工具」一视同仁 [R-10-4]。

由「谁在用这份配置」直接得到一张判定表：

| 级 | 判据（按序自问） | 命中 → 选什么 |
|---|---|---|
| 1 | 这份配置只给同一个团队、发 2–3 个同源环境？ | **是** → Kustomize 5.x overlay（无模板 patch） |
| 2 | 需要打包、版本化、发给别的团队 / 外部用户？ | **是** → Helm 4.x Chart（模板 + 包管理 + release 状态） |
| 3 | 是大规模平台、需要类型检查 / 复用逻辑 / 多语言生成？ | **是** → Jsonnet / CDK8s 代码生成 |
| — | 三个都否 | 保持裸清单，不要引入任何模板层（第 6 章的做法） |

**模板化程度应与「谁在用这份配置」成正比**：同源多环境用 overlay，对外分发用 Chart，大规模平台才考虑代码生成 [R-10-7][R-10-9]。这正好对应本书选型基线的固定值——`Kustomize 5.x` overlay 为多环境基线，`Helm 4.x` 为对外分发 Chart，二者**不是竞品式的二选一**，而是同一份应用定义的两种消费方式 [R-10-1][R-10-2]。

| 判据 | Kustomize 5.x overlay | Helm 4.x Chart | Jsonnet / CDK8s |
|---|---|---|---|
| 本质 | 无模板 patch / overlay | 模板 + 包管理 + release 状态 | 用代码生成清单 [R-10-1][R-10-2] |
| 最适 | 同源 dev/staging/prod | 对外分发、需要版本号与依赖 | 平台团队、需要类型与逻辑复用 |
| 输出确定性 | `kustomize build` 纯函数 | `helm template` 依赖 values 与 Chart 版本 | 依赖生成器版本与语言运行时 |
| 审查对象 | 渲染后的完整清单 | 同样是渲染后的完整清单 | 同样是渲染后的完整清单 |
| 回滚单位 | 切回上一个 overlay 目录 | `helm rollback <release> <rev>` | 回退生成器版本并重渲染 |

> **双模式对照：仓库内渲染 vs 集群内渲染**（为第 14 章 GitOps 埋伏笔）
>
> rendered manifests（见 10.2 定义）还有一个被忽略的维度：**渲染这件事发生在哪里**。它直接决定第 14 章 GitOps 控制器要不要会渲染。

| 维度 | 仓库内渲染（repo-side） | 集群内渲染（cluster-side） |
|---|---|---|
| 谁在渲染 | 开发者 / CI 跑 `helm template`、`kustomize build` | 控制器（如 Argo CD / Helm Operator）在集群里渲染 |
| 产物是什么 | 静态 YAML | 控制器运行时生成 |
| 是否进 Git | 进 Git / PR 附件 | 不进 Git，Git 只存模板 / overlay |
| 下游怎么用 | GitOps 控制器直接 `apply` | 控制器自行 `apply` 运行时产物 |

- **仓库内渲染**：`helm template` / `kustomize build` 在 CI 或本地跑，渲染产物作为静态文件进 Git 或作为 PR 附件。优点是审查在合并前完成、产物可逐行 diff、可归因到某次提交（§10.2 第 3 条判据）[R-10-4][R-10-8]；缺点是要同时维护「模板」和「产物」两份真相，且产物需随模板同步刷新。
- **集群内渲染**：Git 里只存模板/overlay，由控制器在集群侧渲染后 apply。优点是单一事实源就是模板、不会产物与模板漂移；代价是审查对象变成了「渲染器本身的确定性」——Helm 版本、Kustomize 版本、values 来源都要被控制器锁定，否则「集群里到底渲染了什么」反而更难 diff。

第 14 章会展开：GitOps 选哪种模式，决定了控制器要不要内置渲染能力，以及「漂移检测」比对的是模板还是产物。本章先把产物做到「确定、可比对」，两种模式都能接 [R-10-4]。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：抽象过度比重复更贵。生成物不可读时，排障成本会转嫁给值班的人；模板化程度的天花板不是「能写多少层」，而是「凌晨三点能不能一眼看懂这份渲染产物」。
>
> **论证**：模板、overlay、代码生成解决的都是「如何批量产生清单」，它们不替你承担故障时的定位成本。每多一层抽象，就多一处「值从哪里来」的间接性：五层 overlay 里一个 `replicas` 的来源要重渲染五遍才确认，几百个 values 键的 Chart 里一个默认值改动能同时改掉三个环境。这些成本在发布顺利时是隐形的，一旦 prod 出现 `Pending`，值班同学要在「模板 → values → overlay → 渲染 → 控制器」五层里逐层排除，而他能拿到的只有一份不可读的巨型 YAML [R-10-7][R-10-9]。因此本章把「渲染产物可逐行 diff、可归因」设为硬判据，并给抽象设三条警戒线：overlay 不超过两层、values 可配置项设上限、生成物必须作为 PR 附件归档 [R-10-8]。
>
> **反例与前提**：这不等于「永远不用代码生成」。当平台团队要向几十个业务方交付带类型检查、带策略内置、带多集群变体的配置时，重复的裸清单确实更贵，CDK8s 这类方案的总成本更低——但前提是团队同时具备「生成器版本锁定 + 渲染产物归档 + 值班可读的速查文档」三样东西。另一个反例是极简场景：只有一个环境、一份清单时，任何模板层都是净负担，第 6 章刻意不选工具正是这个理由。跳过「渲染产物可审查」直接上复杂抽象的代价，汇总在第 31 章反模式速查（见第 31 章）。

## 10.3 工具选型：双骨架，且每列都要回答「何时不该用」

本章是选型章，必须覆盖互相竞争工具的官方文档：Helm 4.x 与 Kustomize 5.x 各给一条 L1 [R-10-1][R-10-2]，再加 conftest 的 L1 [R-10-3]，共三条已核验的官方来源。本书选型基线已把唯一示例实现钉死为 **Kustomize 5.x overlay 作多环境基线 + Helm 4.x 作对外分发 Chart**，其余工具只在矩阵里作对比。

先说清一个容易被读成「两头下注」的地方：**这不是把两个竞品都留着以防万一，而是让它们各干一件对方干不了的事。**Kustomize 适合当多环境基线，因为它把差异逼到明面上；Helm 适合对外分发，因为它能打版本包、能带 release 状态。反过来用就都不舒服：用 Chart 管三个环境，差异藏在默认值里（就是 10.1 那起事故）；用 overlay 分发，你没法给外部团队一个「版本号」 [R-10-1][R-10-2]。

| 工具 | 主版本 | 本质 | 最适 | 何时不该用（本章相关的一条） | 主要风险 | 回滚方式 |
|---|---|---|---|---|---|---|
| Kustomize | 5.x | 无模板 patch / overlay | 同源多环境基线 | 需要把带版本号的包发给外部团队时——它没有包管理与 release 状态 [R-10-2] | 继承链过深导致字段难归因 [R-10-2] | `git checkout <上一 tag> -- deploy/overlays/dev && kubectl apply -k deploy/overlays/dev` |
| Helm | 4.x | 模板 + 包管理 + release 状态 | 对外分发 Chart | 只有一个环境、且不需要打包时——模板与 release 状态是净开销 [R-10-1] | values 爆炸、条件分支难调试、release 状态与 Git 声明漂移 [R-10-1] | `helm rollback order-demo <rev> -n order-demo-dev` |
| Jsonnet / CDK8s | 0.x / 2.x | 代码生成清单 | 大规模平台、需类型与逻辑复用 | 团队没有「生成器版本锁定 + 产物归档」能力时——值班读不懂生成物 [R-10-9] | 生成器版本升级会让全量产物变化 | 回退生成器版本并重渲染 |
| kubeconform | 0.x | 按 schema 校验清单结构 | CI 里校验渲染产物字段/类型 | 想校验组织策略时——它只管结构不管规则 [R-10-5] | schema 版本与集群版本不匹配会误报 | 回退 workflow 到上一版规则 |
| conftest | 0.x | OPA/Rego 策略校验 | CI 里校验组织策略（非 root、标签、镜像仓库） | 想做准入拦截时——那是集群侧第 25 章的事，别把 CI 静态扫描叫准入 [R-10-3] | 规则库与集群策略不同步会出现「CI 过、准入拦」 | 回退 `policy/` 目录到上一版 |
| `helm lint` / `ct`（chart-testing） | 4.x / 3.x | Chart 结构与打包规范 | Chart 的 PR 门禁 | 只发 overlay、根本没有 Chart 时 [R-10-6] | `ct lint` 依赖集群/配置，环境不一致会 flaky | 回退 workflow 到上一版 |

**最小接入 diff**（第 6–9 章的 base 清单一个字段都不改，只做目录重组 + 一个标签值替换）：

```diff
 deploy/
   base/                      (第 6–9 章的全部清单，原样保留)
+    kustomization.yaml        # 新增：列出 resources
+  overlays/
+    dev/kustomization.yaml        # 新增：namespace + replicas
+    staging/kustomization.yaml    # 新增：namespace + replicas + GREETING patch
+    prod/kustomization.yaml       # 新增：namespace + replicas + GREETING patch
+  charts/order-demo/
+    Chart.yaml                    # 新增
+    values.yaml                   # 新增：仅 6 个可配置项
+    values-dev.yaml               # 新增
+    templates/configmap.yaml      # 新增
+    templates/deployment.yaml     # 新增：gateway 最小可复用单元
+  hack/render-diff.sh             # 新增：两条渲染路径一致性
+  .github/workflows/validate-manifests.yml  # 新增：四道关卡

# 全仓统一：managed-by 从 kubectl 改为 kustomize（第 14 章起改 argocd）
-  app.kubernetes.io/managed-by: kubectl
+  app.kubernetes.io/managed-by: kustomize
```

**升级路径**：Kustomize 5.x 的 `kustomization.yaml` 用 `apiVersion: kustomize.config.k8s.io/v1beta1`；升级前先 `kustomize build` 存一份产物基线，升级后 diff 确认无意外变更。Helm 4.x 的 Chart 用 `apiVersion: v2`；`version` 与 `appVersion` 分开锁，`appVersion` 取 `git-<sha7>`，禁用 `latest`（配置契约，见第 6 章）。**回滚路径**：overlay 侧回到 Git 上一 tag 后 `apply -k`；Helm 侧 `helm rollback` 到指定修订；生成代码侧回退生成器版本并重渲染。注意卡片里 `kubectl apply -k deploy/overlays/dev@<上一 tag>` 是简写——`kubectl` 不接受 `@` 语法，正确写法见 10.5 方案 B，这一口径与第 9 章、第 11 章保持一致。

### 10.3.1 「何时不该用」的完整边界与三种混用形态

10.3 矩阵每列只给了一条「何时不该用」，那只够做初筛；真正的翻车多发生在「两个工具单独看都对，组合方式错了」。这里把边界补成可判定清单，再给三种混用形态的取舍。

**Helm 4.x 不该用的完整情形** [R-10-1]：

- 只有一个环境、清单不足十份：模板层的编写与调试成本高于它消除的重复，第 6 章的裸清单就是正确答案；
- 当内部多环境基线用：Go template 无类型检查、默认值跨环境隐式继承（10.1 事故已演示），overlay 的显式 patch 天然更适合当基线 [R-10-2][R-10-10]；
- 消费方就是自己团队、不需要版本号与依赖解析：release 记账与打包是净开销；
- 追求渲染产物的确定性：`helm template` 输出依赖 Chart 版本与模板执行细节，确定性弱于 `kustomize build` 的纯函数性（判据见 10.2 表）。

**Kustomize 5.x 不该用的完整情形** [R-10-2]：

- 要把带版本号的包发给外部团队：它没有 Chart version、没有依赖管理、没有 release 历史，「发出去的东西是哪个版本」只能靠 Git tag 约定；
- 消费方不熟悉 YAML patch 合并语义：strategic merge 的字段合并规则有学习成本，对这类消费方，「模板 + values」的心智模型更友好；
- 需要「同一份定义渲染出结构差异极大的变体」（按开关整段生成或删除一组资源）：patch 只能改已有资源，生不出新结构，这是代码生成的领地（适用前提见 10.2 本书观点的反例）[R-10-9]。

**三种混用形态**：

**形态 A（本书采用）：并存不嵌套。** 同一份应用定义，内部走 overlay 基线、对外走 Chart，两条渲染路径互不引用，靠 `hack/render-diff.sh` 判等（10.4）。代价是要维护两套表达；换来的是审查面单一——每条路径的产物都能独立 diff、独立归因 [R-10-4][R-10-8]。

**形态 B：Kustomize 包 Helm。** `kustomization.yaml` 的 `helmCharts` 字段让 `kustomize build` 在渲染期调用 Helm 把 Chart 渲染成清单、再叠 patch：

```yaml
# deploy/overlays-helm/dev/kustomization.yaml —— 形态 B 的最小示例（对比用，非 order-demo 主骨架）
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: order-demo-dev
helmGlobals:
  chartHome: ../../charts          # 本地 Chart 所在目录
helmCharts:
  - name: order-demo
    version: 0.1.0
    releaseName: order-demo
    valuesFile: ../../charts/order-demo/values-dev.yaml
    valuesInline:
      replicas: 2
```

最正当的场景是**把社区 Chart 当 base 再 patch**（如 ingress-nginx、cert-manager 这类不由你维护的 Chart）：values 管不了的字段用 overlay patch 收口，比散落的 `--set` 可审查得多。代价有三：① 渲染依赖本机 helm 二进制、需 `--enable-helm` 开启该特性，`kubectl apply -k` 内置的 kustomize 不支持它，必须用独立 kustomize CLI；② 产物确定性依赖本机 helm 版本——锁进附录 A，否则 10.2 第 1 条「命令确定」被破坏；③ Chart 渲染出的对象带 Helm 注释与默认标签，须走 10.4.1 归一化才能与 overlay 基线比对，且 CI 四道关卡照常作用于其产物，不得因「kustomize build 通过」跳过 kubeconform / conftest [R-10-3][R-10-5]。

要改 Chart 管不到的字段时，在同一个 `kustomization.yaml` 里叠 patch（与 10.4 overlay 同语法，审查面仍是这一份文件）：

```yaml
# deploy/overlays-helm/dev/kustomization.yaml 追加（接上方 helmCharts 示例）
patches:
  - target:
      kind: Deployment
      name: gateway
    patch: |-
      - op: replace
        path: /spec/strategy/rollingUpdate/maxUnavailable
        value: 1
```

形态 B 的本地验证（CI 关卡照常作用于其产物）：

```bash
kustomize build --enable-helm deploy/overlays-helm/dev > /tmp/helmcharts-rendered.yaml
grep -c 'kind: Deployment' /tmp/helmcharts-rendered.yaml    # 期望 ≥1：Chart 渲染成功
kubeconform -strict -summary /tmp/helmcharts-rendered.yaml  # 关卡 3 照常执行
```

**形态 C：Helm 套 Kustomize**（`helm install` 接 post-renderer，或 GitOps 控制器里 helm + kustomize 叠加）。两层渲染叠加意味着归一化要剥两层差异、「值从哪里来」跨两个心智模型，10.2 本书观点的「抽象过度比重复更贵」在这里最容易应验。只允许作为迁移期的过渡形态，登记退出期限；不允许作为长期主路径。与第 14 章渲染模式的关系：形态 A 天然对应仓库内渲染；形态 B 的产物既可入 Git 也可集群内渲染，但无论哪种，「归一化逻辑」都必须随产物一起进版本控制（10.4.1）。

**混用判定表**：

| 场景 | 推荐形态 | 理由 |
|---|---|---|
| 内部三环境 + 对外分发 gateway（本书） | A | 审查面单一，render-diff 可判等 |
| 依赖社区 Chart 且要改它管不了的字段 | B | patch 收口比 `--set` 可审查，版本仍由 Chart 管理 |
| 从 Helm 全量迁到 overlay 的过渡期 | C（限期） | 迁移期兼容；须登记退出期限并到期复盘 |
| 想用「一个工具统一所有渲染」 | 都不推荐 | 双骨架的分工是刻意设计，见 10.2 决策树 |

一个常见追问：既然 Kustomize 能包 Helm（形态 B），为什么不直接用它消费自家的 gateway Chart，省掉双骨架？三个理由：① 表达仍是双份——Chart 与 overlay 都要维护，形态 B 只换掉了粘合方式，没有消除维护量；② `render-diff.sh` 的归一化要多剥一层 Helm 差异（10.4.1 的三个维度全部叠加），判等成本上升；③ `--enable-helm` 依赖使 `kubectl apply -k` 失效，第 14 章若选仓库内渲染，GitOps 控制器就得内置 helm 调用，把 10.2 第 1 条「命令确定」的锁版本范围从「一个渲染器」扩大到「两个」。形态 A 的双骨架看似重复，实则是把「内部基线」与「对外接口」的演进节奏解耦——前者跟环境走，后者跟消费方走，节奏不同就不该共享一个粘合层。

**抽象升级的临界点**：10.2 决策树回答「用哪个」，这里补「什么时候升级」。升级抽象层有触发条件，未到临界点就升级，是在为尚不存在的复用付维护成本：

| 触发信号 | 临界点 | 动作 |
|---|---|---|
| 清单复制粘贴出现在第 2 个环境 | 复制第 2 份目录**之前** | 收敛为 base + overlay（10.4） |
| 同一段 patch 在 ≥2 个 overlay 里重复 | patch 第 2 次复制时 | 升格 component 或回 base（10.4.4） |
| 第 1 个外部团队要接入 gateway | 首次对外分发请求时 | 抽最小 Chart（10.4），只暴露受控接口（10.4.3） |
| values 键频繁新增、出现嵌套 `if` | 可配置项逼近 6 上限（CL-10-03） | 拆 Library Chart（10.4.2） |
| 需要类型检查、向几十个业务方交付变体 | 平台化立项时 | 评估代码生成，适用前提见 10.2 本书观点 |

降级同样合法：当某层抽象服务的消费者消失（如外部团队下线），回退一层是减负而不是倒退——抽象层跟着「谁在用」走，这是 10.2 决策树的正读与反读。

**`hack/render-diff.sh`**

```bash
#!/usr/bin/env bash
set -euo pipefail
CHART=deploy/charts/order-demo
OVERLAY=deploy/overlays/dev
NS=order-demo-dev

helm template order-demo "${CHART}" -f "${CHART}/values-dev.yaml" -n "${NS}" > /tmp/helm.yaml
kustomize build "${OVERLAY}" > /tmp/kustomize.yaml

grep -v '^# Source:' /tmp/helm.yaml > /tmp/helm.clean.yaml

# 只取两条路径共同产出的资源，统一 JSON 序列化后逐字段比较
pick() {
  yq -o=json -I=0 'select(.kind == "Deployment" and .metadata.name == "gateway" or .kind == "ConfigMap")' "$1" \
    | jq -sS 'sort_by(.kind, .metadata.name)'
}
pick /tmp/helm.clean.yaml > /tmp/helm.json
pick /tmp/kustomize.yaml > /tmp/kustomize.json

diff -u /tmp/kustomize.json /tmp/helm.json
echo "render-equivalent: OK"
```

> 归一化是必要的：Helm 输出带 `# Source:` 注释、字段顺序与 YAML 缩进和 Kustomize 不同，逐字节 `diff` 必然失败；这里用 `yq` 转 JSON、`jq -sS` 按 `kind/metadata.name` 排序，比的是**语义等价** [R-10-1][R-10-2]。工具版本锁在附录 A。

### 10.4.1 两种渲染器的输出差异与归一化策略

`hack/render-diff.sh`（10.4）能判等的前提是：先把两条路径的输出**归一化**再比。直接 `diff` 原始输出必然失败，因为 `helm template`（Helm 4.x）与 `kustomize build`（Kustomize 5.x）在三个维度上天然不一致 [R-10-1][R-10-2]。

第一次跑这个脚本的人，通常会以为脚本写错了：**明明两边语义完全一样，diff 却红了一整页。**这不是 bug，是 YAML 这种格式的固有性质——它允许同一件事有多种写法，而 diff 只认字节。所以下面这三段不变量，本质是在教工具「什么叫一样」。

**字段顺序**。Helm 按模板文件里字段的书写顺序输出 Deployment/ConfigMap；Kustomize 在叠加 patch 后会按内部顺序重排（例如 `metadata` 与 `spec` 的相对位置、列表项的次序）。同一语义的两份 YAML，字节顺序可能完全不同，逐字节 `diff` 必报「全异」。

**注释**。Helm 每个资源前会输出 `# Source: <chart>/templates/<file>.yaml` 的源注释头，模板里的 `{{- /* ... */ }}` 也会残留；Kustomize 5.x 默认不输出 source 注释。这些注释不参与语义，但会淹没真正的差异行。脚本里用 `grep -v '^# Source:'` 先把 Helm 的注释头剥掉。

**空值处理**。Helm 对 `nil` 字段**不输出该键**；模板里 `{{ .Values.x }}` 取值为空字符串时，可能渲染出 `x: ""` 或整行消失，取决于是否用 `| quote`。Kustomize 更「原教旨」：YAML 里的 `null` 会保留为 `field: null`，空列表 `[]` 与缺省也表现不同。两者对「未设置」的表示不一致，会让 `diff` 在空值处误报。

**归一化策略（脚本已落地）**：

1. 剥注释：过滤掉所有 `# Source:` 行（以及模板残留注释）。
2. 转 JSON 再排序：`yq -o=json -I=0` 把 YAML 转成 JSON，`jq -sS` 按 `kind`/`metadata.name` 排序，使字段顺序不再影响比较。
3. 规范空值：对 `null` 与 `[]` 做统一归并（例如把 `field: null` 与缺省视为等价），避免空值误报。
4. 剥离集群侧字段：只比较「声明侧」字段；`metadata.creationTimestamp`、`status`、`resourceVersion` 这类只在集群内渲染出现的字段一律排除（见 10.2 双模式对照）。

| 维度 | `helm template` | `kustomize build` | 归一化动作 |
|---|---|---|---|
| 字段顺序 | 模板书写序 | patch 叠加后重排 | 转 JSON + `jq -sS` 排序 |
| 源注释 | 输出 `# Source:` 头 | 默认无 | `grep -v '^# Source:'` |
| 空值 `nil` | 不输出该键 | 保留 `null` / `[]` | 统一归并空值 |
| 集群字段 | 无（仓库内渲染） | 无（仓库内渲染） | 剥离 `status` / `creationTimestamp` |

归一化的目标是比**语义等价**而非字节相同：两条路径只要「同一个资源、同一组声明字段、同一组取值」就判等，这正是 §10.2 把「语法封闭」「差异可归因」作为 rendered manifests 判据的工程落地 [R-10-4][R-10-5]。注意归一化脚本本身也要进版本控制——否则「归一化逻辑变了」会制造新的不可归因，与 10.2 第 3 条判据自相矛盾。

### 10.4.3 values 的进出判据、values.schema.json 与 version/appVersion 语义

CL-10-03 只定了「可配置项 ≤ 6」的量，没定「什么键才有资格进 values」。补两条判据与一道校验，把 values 从「配置入口」收敛成「受控接口」。

**进出判据（按序问，任一「是」才允许进 values）**：

1. 会因环境不同而取值不同吗？（`namespace`、`replicas`、`greeting`）
2. 会因消费方不同而取值不同吗？（`image.repository`——别的团队要指向自己的镜像仓库）
3. 是消费方确实要覆盖、且覆盖后果能被渲染 diff 暴露的吗？

三个都是「否」，就固定在模板里。据此把键分四类：

| 类别 | 例子 | 处置 |
|---|---|---|
| 环境差异值 | `namespace`、`replicas`、`greeting` | 进 values，且每个环境文件显式覆盖（10.1 事故-2） |
| 消费方差异值 | `image.repository`、`managedBy` | 进 values，带安全默认值 |
| 契约字段 | 端口 8080、探针路径、`terminationGracePeriodSeconds: 30`、`securityContext` | 固定在模板，不进 values |
| 实现细节 | `imagePullPolicy`、`progressDeadlineSeconds`、`maxSurge` | 固定在模板 |

「契约字段不进 values」是公理 3 在打包层的对应物：「环境差异只体现在配置」的另一面是**契约不向消费方开放**——端口或探针路径一旦可配，每个消费方都拿到一个改坏契约的入口，第 8 章的探针验证与第 11 章的 CI 校验都失去统一前提 [R-10-10]。

三个「看似该进 values、实则不该」的反例：

- `probePath`：「各团队探针路径不同」是错觉——契约路径 `/healthz`、`/readyz` 全环境统一（见第 8 章），判据 1、2 均为「否」，固定在模板；
- `port`：同理；端口变更属于契约变更，走 Git 提交修改模板，不给消费方入口；
- `resources`：第 17 章会按环境定资源基线，看似环境差异值；但 10.1 事故里 `gateway.resources.requests.cpu` 被开放成 values 正是代价示范——资源基线是契约的一部分，调整它应走修改契约基线的 Git 提交，而不是给每个消费方一个可覆盖入口。

**values.schema.json（完整文件，Helm 4.x 按 JSON Schema draft-07 校验）**：schema 让「填错值」死在渲染前。`helm lint`、`helm template`、`helm install/upgrade` 都会自动执行校验，CI 关卡 1 因此无需新增 step [R-10-1]：

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "order-demo gateway chart values",
  "type": "object",
  "additionalProperties": false,
  "required": ["namespace", "replicas", "image", "greeting", "managedBy"],
  "properties": {
    "namespace": {
      "type": "string",
      "pattern": "^order-demo-(dev|staging|prod)$"
    },
    "replicas": { "type": "integer", "minimum": 2, "maximum": 10 },
    "image": {
      "type": "object",
      "additionalProperties": false,
      "required": ["repository", "tag"],
      "properties": {
        "repository": {
          "type": "string",
          "pattern": "^registry\\.example\\.com/order-demo/gateway$"
        },
        "tag": { "type": "string", "pattern": "^git-[0-9a-f]{7}$" }
      }
    },
    "greeting": { "type": "string", "minLength": 1, "maxLength": 64 },
    "managedBy": { "type": "string", "enum": ["kustomize", "argocd"] }
  }
}
```

三个设计点：

- `additionalProperties: false` 拒绝拼写错误的键——`replica: 3` 这类错键在无 schema 时会默默失效、渲染结果回退默认值，是 values 类事故的高频根因；
- `pattern: ^git-[0-9a-f]{7}$` 把公理 2（不可变镜像 + SHA 标签，禁 `latest`）下沉到渲染前拦截，谁传 `latest` 谁当场报错；
- schema 校验的是**合并后**的 values，所以 `values-dev.yaml` 这类只写覆盖键的部分文件照常工作。

校验失败的示例（合成输出，非真实截图）：

```bash
$ helm template order-demo deploy/charts/order-demo \
    -f deploy/charts/order-demo/values-dev.yaml -n order-demo-dev
Error: values don't meet the specifications of the schema(s) in the following chart(s):
order-demo:
- image.tag: Does not match pattern '^git-[0-9a-f]{7}$'
```

注意 schema 防的是「填错」，不防「合法但影响面大的值」——10.1 事故里 `replicas: 2→3` 完全合法，schema 拦不住，能拦住它的只有渲染 diff（事故-1）。两层防线各管一半，缺一不可。

**schema 拦截的一次完整现场（合成案例，遵循第 1 章标注约定）**：某外部团队接入 gateway Chart，接入脚本沿用他们自己仓库的习惯，把镜像标签写成 `tag: v2.3.1`。若无 schema，这个值会一路渲染进清单、提交到集群，然后以 `ImagePullBackOff` 的形式暴露——仓库里根本不存在 `:v2.3.1` 这个标签，值班同学要先看到 Pod 起不来、再反推「标签是谁填的」，同时它已经违反公理 2（标签必须可追溯到 git SHA）。加 schema 后，同一动作死在 CI 渲染前：PR 的关卡 1 `helm lint` 直接输出上方示例的 pattern 不匹配错误，作者当场改回 `git-<sha7>`，全程不到一分钟。价值对比很直接：无 schema 时故障暴露点在**集群**，代价是一次起不来的发布加一轮排查；有 schema 时暴露点在**提交**，代价是一条 CI 红线。把失败尽量左移，正是 10.4 四道关卡存在的意义 [R-10-1][R-10-3]。

**version 与 appVersion 分两条线锁** [R-10-1]：`appVersion` 是应用制品版本，取 `git-<sha7>`（配置契约）；`version` 是 Chart 接口自身的语义化版本，它的增量向消费方传达变更类型。注意 10.4.2 的 `check-version-increment: true` 会把任何 Chart.yaml 改动（含 appVersion）都要求 version 递增——本书口径是**接受这个约束**：镜像演进按 patch 递增，新增可配置项按 minor，破坏 values 接口按 major，版本号递增得勤一点，换取「每次变更都有单调版本可回溯」。判定表：

| 本次变更内容 | `version` | `appVersion` |
|---|---|---|
| 只发新镜像（模板与 values 接口不变） | patch +1 | 换成新 `git-<sha7>` |
| 新增 values 键 / 模板新字段 | minor +1 | 按需 |
| 删除或改语义 values 键 | major +1 | 按需 |
| 模板 bug 修复、注释调整 | patch +1 | 按需 |

反模式：把 Chart version 当「发版计数器」，每次流水线跑完自动 +1——version 失去语义化信号，消费方无法凭版本号判断要不要审视变更，`ct` 的版本递增检查也随之失去意义。

**schema 的维护边界**：schema 与 values 接口同生命周期——新增、删除或改语义 values 键的 PR 必须同步改 schema，且 schema 变更本身要过三环境渲染 diff（收紧 pattern 可能让既有环境文件当场失效）。两条禁令：不要用 schema 表达组织策略——那是 conftest 关卡 4 与第 25 章准入的事，schema 只管「这份 Chart 的接口形状」；不要往 schema 里塞环境相关规则（如「prod 副本数必须偶数」这类约束放不进单一 schema，强行放会逼出多份 schema，破坏「合并后校验」这一前提）。

### 10.4.4 component 的第三层职责：跨环境可选的能力包

10.1 反模式一治的是继承链过深，但「base + 单层 overlay」的两层上限马上会遇到新问题：某个能力两个环境要、另一个不要——写进 base 则三环境全有，写进部分 overlay 则复制多份、漂移风险回升。Kustomize 5.x 为此提供第三种构件：`Component`（`apiVersion: kustomize.config.k8s.io/v1alpha1`），一个**可被 overlay 按需挂载的能力包** [R-10-2]。三层职责分工如下：

| 层 | 职责 | 判定问题 | order-demo 中的对应 |
|---|---|---|---|
| base | 全环境必需的完整清单，无任何环境语义 | 任何环境都不能少吗？ | 10.4 的十二份文件 |
| overlay | 环境语义：namespace、replicas、环境特异 patch | 只属于这一个环境吗？ | dev / staging / prod |
| component | 跨环境可选的能力包 | ≥2 个环境要、其余不要、且不能进 base？ | `defaults-deny`（示例） |

**决策顺序（自上而下，命中即停）**：所有环境都要 → base；只有一个环境要 → 写进那个 overlay；两个以上环境要但不能进 base → component。反向判据也成立：当一个「能力」在两个以上 overlay 里出现相同的 patch，它就该升格为 component 或回 base。

以「默认拒绝网络策略」为例演示打包形态（NetworkPolicy 本体在见第 19 章正式展开，这里只讲它作为能力包怎么组织）。组件目录两个文件：

**`deploy/components/defaults-deny/kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
resources:
  - networkpolicy-default-deny.yaml
```

**`deploy/components/defaults-deny/networkpolicy-default-deny.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: order-demo-default-deny
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: kustomize
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

挂载方的形状（每个要启用该能力的 overlay 各加两行；本章的 canonical 渲染产物不变，实际挂载在第 19 章落地时执行）：

```diff
   resources:
     - ../../base
+  components:
+    - ../../components/defaults-deny
```

component 与「再套一层 overlay」的关键差别：**它不引入新的继承层级，只是资源集合的可选成员**。component 内不写 `namespace:` 字段——挂载它的 overlay 的 namespace 转换会透传进去；component 内也不做环境判断（它没有参数），环境间的取值差异仍归 overlay patch。这正是它比「common 中间层」安全的原因：挂载是显式声明，overlay 里一眼可数 [R-10-2]。

三条警戒线（并入 CL-10-04 的口径）：

- component 不嵌套 component：能力包内部再挂能力包，字段归因成本回到反模式一；
- component 数量 ≤ 5：超过说明 base 的「全集」切错了，应重新划分 base，而不是继续堆组件；
- component 内不放环境特异值：同一能力若在不同环境取值不同，取值差异写回 overlay，组件只承载共性。

**反例复盘（合成案例，遵循第 1 章标注约定）：component 被当参数化模板用。** 某团队在默认拒绝组件里塞进一段 patch，试图「按挂载者调整 `podSelector`」——发现 component 没有参数后，改成维护两个变体目录 `defaults-deny-strict/` 与 `defaults-deny-loose/`。三个月后两个变体各自演进、字段漂移，prod 的策略比 staging 宽松却无人察觉，直到做默认拒绝验证时才暴露。复盘结论回到三层职责表：环境间的**取值差异**永远归 overlay patch，组件只承载无环境语义的共性；需要给组件「传参」的那一刻，说明这个能力包切分错了，应拆回 overlay 或重新划分 base [R-10-2]。

component 与 10.4.2 的 Library Chart 是两个生态里互为对应的能力复用构件：component 复用**资源集合**，Library Chart 复用**模板片段**。当同一能力（如统一标签）要同时出现在 overlay 基线与对外 Chart 里，就得两边各写一次——这正是形态 A「并存不嵌套」的固有代价，由 `hack/render-diff.sh` 兜底判等。

验证（本章不挂载，先演练判据）：

```bash
kustomize build deploy/overlays/dev | grep -c 'kind: NetworkPolicy'
# 期望 0：dev 未挂载
kustomize build deploy/overlays/prod | grep -c 'kind: NetworkPolicy'
# 当前期望 0（未挂载）；第 19 章落地后此命令期望 ≥1，届时纳入该章检查清单
```

## 10.5 验证与回滚（回滚方案先于发布方案）

**回滚**（把线上恢复到上一个已知良好版本，详见第 13 章）在本章分两条路径：overlay 路径回退的是**一份声明**，Helm 路径回退的是**一个 release 修订**。两者都必须先演练，才允许用这套双骨架发第一个正式版本。

这里有个非常容易被忽略的陷阱：**两条路径的回滚粒度不一样**。overlay 回退一次，回去的是「整套清单当时的样子」；`helm rollback` 回退一次，回去的是「上一次 release 修订」，而 release 只记录它自己管的那部分。当同一份应用同时被这两条路径碰过，你回退其中之一，很可能只回到了半个旧世界——这和第 7 章「`rollout undo` 不退 ConfigMap」是同一个形状的错误，只是这里的「半个」更难看出来 [R-10-1][R-10-2]。

**验证命令**（仓库根目录执行，需已安装 helm 4.x / kustomize 5.x / yq / jq / kubeconform / conftest / ct / kubectl，版本见附录 A）：

```bash
chmod +x hack/render-diff.sh
./hack/render-diff.sh
helm template order-demo deploy/charts/order-demo -f deploy/charts/order-demo/values-dev.yaml \
  -n order-demo-dev > /tmp/a.yaml
kustomize build deploy/overlays/dev > /tmp/b.yaml
diff <(yq -o=json -I=0 '.' /tmp/a.yaml | jq -sS .) \
     <(yq -o=json -I=0 '.' /tmp/b.yaml | jq -sS .) || true
kustomize build deploy/overlays/dev | kubeconform -strict -summary -
kustomize build deploy/overlays/dev | conftest test - -p policy/
kubectl apply -k deploy/overlays/dev --dry-run=server
helm lint deploy/charts/order-demo
ct lint --charts deploy/charts/order-demo --validate-maintainers=false
```

**逐条通过标准**：

| 判据 | 怎么查 | 期望结果 |
|---|---|---|
| 两条渲染路径一致 | `./hack/render-diff.sh` | 退出码 0，输出 `render-equivalent: OK` |
| 渲染产物语法封闭 | `grep -n '{{' /tmp/b.yaml` | 无输出；`kubectl apply --dry-run=server` 接受 |
| `managed-by` 已改 | `kustomize build deploy/overlays/dev \| grep 'managed-by'` | 全部为 `kustomize`，无 `kubectl`、无 `Helm` |
| 四道关卡通过 | `helm lint` / `ct lint` / `kubeconform -strict` / `conftest test` | 四条全部 0 退出 |
| 继承链 ≤ 2 层 | `grep -c 'resources:' deploy/overlays/*/kustomization.yaml` | 每个 overlay 只引用 `../../base` 一次 |
| 渲染 diff 只含预期变更 | 把 `/tmp/rendered.yaml` 与上一版逐行 diff | 每处差异都能指向某个 Git 提交 |

最后一项是 10.2 定义里第 3 条「差异可归因」的验收点，也是反模式三的直接对冲 [R-10-8]。

**回滚命令 / 步骤**（先演练、后发布）：

```bash
# 方案 A：Helm 路径——回退到上一个 release 修订
helm history order-demo -n order-demo-dev
helm rollback order-demo <rev> -n order-demo-dev
helm status order-demo -n order-demo-dev

# 方案 B：overlay 路径——回到 Git 上一 tag 后重新 apply（@<tag> 是卡片简写，kubectl 不接受）
git checkout <上一 tag> -- deploy/overlays/dev/ deploy/base/
kubectl apply -k deploy/overlays/dev
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s

# 方案 C：仅渲染产物校验规则误伤（不改应用）
git checkout <上一 tag> -- .github/workflows/validate-manifests.yml policy/
kustomize build deploy/overlays/dev | kubeconform -strict -summary -
```

> **为什么方案 B 必须回到 Git**：`helm rollback` 回退的是 release 的修订状态，overlay 没有等价物；overlay 的唯一真相就是 Git 里那份 `kustomization.yaml` 与其引用的 base 清单。用 `git checkout` 取回上一 tag 再 `apply -k`，明确表达「恢复到上一份已声明的完整清单」，与全书公理 5 一致（见第 3 章）[R-10-4][R-10-8]。Helm 的 release 状态与 Argo CD 的衔接取舍在第 14 章展开（见第 14 章）；本地 kind 的演练不构成对生产手工变更的例外。

**双路径同时在线时的回滚顺序判据**：当对外 Chart 已被某团队安装、内部 overlay 基线也在跑时，回滚按「受影响流量走哪条路径」排序——受影响流量走 overlay 基线（内部三环境）→ 先方案 B，恢复声明再 apply；受影响的是已安装 release 的外部团队 → 先方案 A（`helm rollback`），并把 version / appVersion 的回退提交进 Git；只有校验规则误伤、应用本身无辜 → 方案 C。两条路径都受影响时先 B 后 A：overlay 基线承载内部主流量，恢复面最大，且方案 B 的 `git checkout` 不会碰外部团队的 release 状态。

**回滚验证**：

```bash
./hack/render-diff.sh
kubectl -n order-demo-dev get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
kubectl -n order-demo-dev get deploy gateway \
  -o jsonpath='{.metadata.labels.app\.kubernetes\.io/managed-by}{"\n"}'
./hack/verify.sh
```

通过标准：`render-diff.sh` 仍以 0 退出、镜像标签回到上一版 `git-<sha7>`、`managed-by` 为 `kustomize`、`/healthz` 仍为 200。**回滚没有验证过，就不允许带着双骨架进入第 11 章**（CL-G-07）。

### 10.5.1 Chart / overlay 的内容升级：三环境灰度闸门

10.3 的「升级路径」回答的是**工具版本**升级；更高频的是**内容升级**——新镜像（`appVersion` 变）、新可配置项（`version` 变）、base 清单演进。灰度纪律一句话：**同一份 Chart 包、同一条 base 提交，按 dev → staging → prod 过三道闸门，任何一道不过就停在那里**。这是公理 1（build once, promote）在打包层的落点：不为 prod 单独打包，三环境消费同一个 `helm package` 产出的 `.tgz` 与同一份 base 提交，差异只允许来自各自 values 文件与 overlay [R-10-10]。新镜像的 `git-<sha7>` 由第 12 章 CI 写回 Chart，本章不手工填真值（见第 12 章）。

先补齐尚未给出的两个环境 values 文件（与 `values-dev.yaml` 同构，键集一致，schema 校验同样适用）：

**`deploy/charts/order-demo/values-staging.yaml`**

```yaml
replicas: 2
greeting: "hello from configmap (staging)"
```

**`deploy/charts/order-demo/values-prod.yaml`**

```yaml
replicas: 3
greeting: "hello from configmap (prod)"
```

闸门命令序列（完整，仓库根目录执行；values.schema.json 校验由 helm 自动执行，见 10.4.3）：

```bash
# 第 0 步：打包一次，产出唯一制品（version/appVersion 按 10.4.3 判定表先在 Chart.yaml 递增）
helm package deploy/charts/order-demo
# → order-demo-0.1.1.tgz；三环境只消费这一份，不重打包

# 闸门 1 · dev：渲染 diff → dry-run → 升级 → 验证
helm template order-demo order-demo-0.1.1.tgz \
  -f deploy/charts/order-demo/values-dev.yaml -n order-demo-dev > /tmp/next-dev.yaml
diff /tmp/rendered-dev-prev.yaml /tmp/next-dev.yaml
# rendered-dev-prev.yaml 取自上一次 PR 归档的渲染产物（10.4 CI 附件）；
# 逐行确认每一处差异都能归因到本次 Git 提交 [R-10-8]
helm upgrade order-demo order-demo-0.1.1.tgz \
  -f deploy/charts/order-demo/values-dev.yaml -n order-demo-dev --dry-run
helm upgrade order-demo order-demo-0.1.1.tgz \
  -f deploy/charts/order-demo/values-dev.yaml -n order-demo-dev
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s

# 闸门 2 · staging：同一个 .tgz，换 values，不重打包
helm template order-demo order-demo-0.1.1.tgz \
  -f deploy/charts/order-demo/values-staging.yaml -n order-demo-staging > /tmp/next-staging.yaml
diff /tmp/rendered-staging-prev.yaml /tmp/next-staging.yaml
helm upgrade order-demo order-demo-0.1.1.tgz \
  -f deploy/charts/order-demo/values-staging.yaml -n order-demo-staging
helm get values order-demo -n order-demo-staging   # 核对合并结果与 values-staging.yaml 一致
kubectl -n order-demo-staging rollout status deployment/gateway --timeout=120s

# 闸门 3 · prod：dry-run 先行，真实升级必须来自 Git 里的 PR 批准（公理 5）
helm upgrade order-demo order-demo-0.1.1.tgz \
  -f deploy/charts/order-demo/values-prod.yaml -n order-demo-prod --dry-run
```

每道闸门的通过标准与失败处置：

| 闸门 | 通过标准 | 失败处置 |
|---|---|---|
| 1 · dev | 渲染 diff 每处差异可归因到本次提交；`kubeconform` / `conftest` 全绿；`rollout status` 成功 | 修 Chart 重打包，闸门 1 重跑；不进闸门 2 |
| 2 · staging | `rollout status` 成功；`helm get values` 与 `values-staging.yaml` 一致 | `helm rollback order-demo <rev> -n order-demo-staging` + `git revert`，回闸门 1 |
| 3 · prod | dry-run 的 diff 仅含预期字段；资源请求量在节点余量内（10.1 事故-1 的教训） | 不执行真实升级，回 Chart 修 values，从闸门 1 重来 |

三条纪律：

1. **prod 的真实升级必须以 Git 合并为前提**：闸门 3 的 dry-run 只是预演，正式升级由合并 PR 触发（自动化交接在第 14 章，见第 14 章）；本地手跑 `helm upgrade` 打 prod 不构成对公理 5 的例外。
2. **回退也走同一序列反向**：prod 回退用 10.5 方案 A（`helm rollback`）恢复集群，同时把 Chart version / appVersion 的回退提交进 Git——「只回集群不回 Git」会让下一次升级从错误的基线开始。
3. **灰度提速的前提是闸门自动化**：闸门 1、2 的命令序列写进 CI（10.4 工作流的下游 job），人工只保留闸门 3 的 approve；闸门全靠手跑的灰度会退化为「谁有空谁先发」。

**一次跳闸门的代价（合成案例，遵循第 1 章标注约定）**：某次安全修复要求紧急升级 gateway，团队以「时间不够」为由跳过闸门 1、2，直接对 prod 执行 `helm upgrade`。这次 Chart 的 minor 变更顺手把模板里的 `progressDeadlineSeconds` 从 120 收紧到 60，prod 节点压力下滚动更新超时，Deployment 进入 `Progressing=False`；又因为跳过了闸门，没有任何人事先渲染过 prod 的产物，没人说得清这次升级到底改了什么。`helm rollback` 恢复集群只用了两分钟，但「哪一个 Chart 版本是上一个已知良好」没有登记，版本回退多花了一小时——闸门 1 的渲染 diff 本来可以免费提供这份登记。复盘把纪律 3 升级为硬规则：**紧急路径也必须过闸门**，只是闸门 1、2 由 CI 自动执行（分钟级）；跳闸门不省时间，只省掉了安全性。

**overlay 侧的对应闸门**：overlay 没有 `.tgz`，它的「唯一制品」就是 Git 提交本身，三闸门对应逐环境晋升：

```bash
# 闸门 1 · dev：PR 内 CI 渲染 diff（10.4 工作流），合并后 apply
kubectl apply -k deploy/overlays/dev
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s

# 闸门 2 · staging：同一条 base 提交，渲染 diff 归因核对后晋升
kustomize build deploy/overlays/staging > /tmp/next-staging-kustomize.yaml
diff /tmp/rendered-staging-prev.yaml /tmp/next-staging-kustomize.yaml
# 每处差异都指向本次 Git 提交 [R-10-8]
kubectl apply -k deploy/overlays/staging
kubectl -n order-demo-staging rollout status deployment/gateway --timeout=120s

# 闸门 3 · prod：人工 PR 批准后晋升，dry-run 先行
kubectl apply -k deploy/overlays/prod --dry-run=server
kubectl apply -k deploy/overlays/prod
kubectl -n order-demo-prod rollout status deployment/gateway --timeout=120s

# 双路径一致性核对：三环境镜像标签必须完全一致（公理 1 的验收点）
for ns in order-demo-dev order-demo-staging order-demo-prod; do
  kubectl -n "$ns" get deploy gateway \
    -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
done
# 通过标准：三行输出均为同一个 registry.example.com/order-demo/gateway:git-<sha7>
```

overlay 与 Chart 两条路径的晋升单位不同——前者是 Git 提交，后者是 `.tgz` 版本号——但灰度纪律相同：闸门逐级过、失败停在原地、回退连同 Git 一起回（方案 B）。本章阶段 `kubectl apply` 仍由人按闸门执行，第 14 章起把闸门 1、2 交给 GitOps 控制器自动收敛、闸门 3 收敛为 PR 合并（见第 14 章）。

**两层灰度的正交关系**：本节的闸门是**环境级灰度**——同一制品逐环境过审；第 13、15 章的滚动更新与金丝雀是**环境内流量级灰度**——同一环境内新副本逐步接流量。两层正交、缺一不可：只做环境级灰度，prod 内部仍是全量替换，一次坏发布仍能瞬间打到全部生产 Pod；只做流量级灰度，没有逐环境审查，坏配置会带着漂亮的发布曲线直达用户。闸门序列（本节）回答「改了什么、该不该进下一个环境」，发布策略（第 13 / 15 章）回答「进了环境之后，流量怎么切」。

## 10.6 上线检查清单

检查项编号全书统一（形如 `CL-08-03`），下表只列本章专有项与必须逐条执行的安全项。

本章的清单和前几章有个区别：**它检查的不是「集群里对不对」，而是「进集群之前有没有被审过」**。`CL-10-01` 到 `CL-10-04` 全都发生在 `apply` 之前——这正是本章的立场，把判定往前压，让错误停在 PR 里，而不是停在告警里。
