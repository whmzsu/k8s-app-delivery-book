> **本章结论**：数据不是「一个版本」，是「一份历史」，你对它的每次写入都盖在上一笔之上——所以「回滚」这动作在数据面前根本不成立，第 13 章的六要素方案到这里要换成 expand–contract 与备份恢复。

## 16.1 问题与反模式：代码能回滚，数据库怎么办

**本章解释第 13 章的回滚方案为什么最难**。第 13 章把回滚定义成「把线上恢复到上一个已知良好版本」，并给了六要素方案与 `kubectl rollout undo` / 明确 SHA 两条路径；第 15 章让机器按指标自动执行它。但那两章处理的都是**无状态的工作负载**：镜像换回去，进程重启，一切恢复。一旦发布牵涉数据格式，「换回镜像」不但可能没用，还可能让情况更糟——旧版本面对的是它从未见过的一张表。

前两章给出的安全感，建立在一个没人说出口的前提上：**你要退回去的那个东西还在。**镜像在仓库里，标签没被删，所以退得回去。而数据不一样——**它不是一个版本，是一份历史**。你对它做的每一次写入都盖在上一笔之上，没有「上一版」可以回退。这也是本章要处理的那类事故为什么格外难：**它不是回滚失败，是「回滚」这个动作在数据面前根本不成立。**

**合成案例**（基于多起公开事故的合成，非真实事件）：`order-demo` 要把订单金额从 `amount` 拆成 `amount_cents` 与 `currency`。发版脚本里第一条就是 `ALTER TABLE orders DROP COLUMN amount`，新版本上线后十分钟发现有批历史订单金额算错。值班同学按第 13 章的方案 `kubectl rollout undo`：镜像退回去了，旧代码一查 `orders.amount` 就报 `column does not exist`，5xx 从局部变成全量。有人提议「把列加回来」，可数据已经被新的写路径改写过，加回空列也补不回原值。同一周，另一个团队卸载一个测试用的数据库 Operator，没检查资源上的 finalizer（删除前的清理钩子，卡住就删不掉，白话，详见第 27 章正式定义），Pod 一直卡在 `Terminating`、PVC 残留，命名空间删不掉；再往前翻，他们的备份任务每天照跑，但从没人恢复过一次，真要恢复时才发现备份存储桶的凭据早就轮换了 [R-16-1][R-16-2][R-16-10]。

三个反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：发布时直接执行破坏性 DDL（`DROP COLUMN` / 改类型 / 拆字段）。** 现象是回滚后旧版本全量报错；根因是把数据格式变更当成了「跟着代码一起发」的一个步骤，而 DDL 是**单向的**，与应用版本不在同一条可回退链上。替代做法是 expand–contract 四阶段迁移，让新旧版本在观察窗口内始终共存于同一 schema，见 16.2 [R-16-6][R-16-7]。

**反模式二：卸载 CRD / Operator 时不检查 finalizer。** 现象是对象卡在 `Terminating`、PVC 与快照残留、命名空间无法回收；根因是没等清理钩子执行完就删了控制器，或反过来手工 `patch` 掉 finalizer 导致清理逻辑被跳过。替代做法是卸载前按 `hack/uninstall-check.sh` 列出所有 `metadata.finalizers`、确认清理完成再删控制器，见 16.4；CRD 与 Operator 的机制详见第 27 章 [R-16-5]。

**反模式三：只做备份、从不恢复。** 现象是真出事时备份不可用——凭据失效、快照与 PVC 版本不匹配、恢复脚本没人跑过；根因是把「备份任务绿了」当成了「数据可恢复」。替代做法是把恢复演练当作发布的同级门禁：每季度恢复到新集群一次，出报告、有数据一致性校验 [R-16-2][R-16-8]。

这条反模式和其他所有反模式都不同：**它的证据一直是绿的。**监控显示备份成功、磁盘在涨、任务按时完成——所有信号都指向「没问题」，而这些信号测的只是「数据被复制出去了」，不是「数据能被拿回来」。**一套从没恢复过的备份，是一份内容未知的文件。**

以上反模式的**方法论**参照公开的数据一致性受损与恢复复盘 [R-16-10]；该来源只用于支撑「这类失效模式确实存在」，不用于证明上面的合成案例真实发生。

**「DROP COLUMN 之后」完整时间线（合成案例续）**。把上面的合成案例按分钟展开，可以看到三条回滚链是如何一条条失效的——16.5.1 的切流 runbook 与这张时间线一一对应：

- **T+0**：发布 PR 合并，`migrate.sh --phase contract` 在 prod 执行 `V4__contract.sql`，`DROP COLUMN amount` 提交。「旧列零写入」的校验口径有缺陷：只核对了触发器删除后的 insert/update，漏了仍在运行的 v1 Pod 已建立的连接里最后一笔写入。
- **T+10**：api v3 上线。客服反馈部分历史订单金额为 0，初判为「个别数据问题」，尚无人意识到不可逆点已越过。
- **T+15**：值班按第 13 章预案 `kubectl rollout undo deployment/api`。旧版本启动成功、readiness 通过，但第一个读订单的请求即报 `ERROR: column orders.amount does not exist`，5xx 从局部变为全量。**应用侧回滚链失效**：镜像退得回去，schema 退不回去。
- **T+22**：有人提议「把列加回来」。`ALTER TABLE orders ADD COLUMN amount NUMERIC` 确实能执行，但得到的是全表 NULL——原值随 `DROP COLUMN` 一起消失，v1 读到的全部是空金额。**「加回列」不是回滚，是把静默数据损坏伪装成恢复**。
- **T+30**：确认不可逆点已越过，宣布进入数据恢复流程：应用冻结在 v3，一切恢复动作改走「从备份恢复到新集群再切流」（16.5.1），schema 侧与应用侧不再有任何动作。
- **T+35**：盘点可用备份。`velero backup get` 显示 Schedule 每日 02:00 均为 Completed，但最近一份**被恢复验证过**的备份还是上次季度演练那份——之后的备份从未被验证（反模式三的代价在此兑现）。选定最近一份 Completed 且卷快照就绪的备份，同时接受 RPO 缺口：备份点之后写入的订单只能靠 WAL 归档重放或业务补偿找回，无法凭空恢复。
- **T+45 ～ T+95**：在备用集群执行恢复、校验与切流，逐步见 16.5.1。
- **T+120**：100% 流量落在新集群，旧集群只读封存留作取证；发布冻结直至复盘完成。

时间线里每一分钟都在验证 16.2 那句话：expand–contract 的价值在于把不可逆点推到最后，而 contract 一旦执行，三条链里只剩数据链还活着 [R-16-6][R-16-8]。

**T+20 到 T+30 之间的那十分钟**（依同类事故共性还原，非原话）：

> **值班**：回滚完了，旧版起来了，但读订单直接报 `column does not exist`。
> **开发**：那就把列加回来，`ADD COLUMN` 很快。
> **DBA**：加回来是空的。
> **开发**：空的也先加，至少不报错。
> **DBA**：不报错，但用户看到的金额是 `NULL`。这比 500 更糟。
> （沉默）
> **值班**：那现在能不能退？
> **DBA**：退什么？数据已经被写成新格式了。我们现在能做的只有一件事——从备份恢复。

这段对话里最值得记住的是 DBA 那句「**这比 500 更糟**」。整章的技术判断都可以从这句推出来：**500 是系统承认自己坏了，`NULL` 是系统认为自己好了。**前者用户会投诉、监控会红；后者安静地流进订单、报表和结算。所以本章对「不可逆点」的定义不是「数据没了」，而是「**系统开始给出看似正常的错误答案**」——那才是最难被发现、也最难补回来的那种损坏。

## 16.2 范式与决策树：expand–contract 让回滚能力活到最后一刻

先划清能力边界：**StatefulSet 提供稳定网络标识、稳定存储与有序启停，但它不提供数据库本身的备份、故障转移与升级语义**。把 PostgreSQL 放进 StatefulSet，只解决了「Pod 重建后名字和盘还在」，不解决「主库挂了谁接管」「怎么按版本升级」「怎么恢复到昨天」 [R-16-1]。本章用原生 StatefulSet 讲清迁移范式，把这些缺口显式留给第 29 章评估。

接着给本章的核心范式一句话版本：**expand–contract 的全部作用，是把「不可逆」这个动作一直往后推**——先加新结构（expand），让新旧版本都能读写，等确认没有旧版本在跑，才删旧结构（contract）。它不让你拥有「撤销」，它让你**在撤销还有效的时候拥有更多时间**。理解这一点很重要，因为后面所有阶段划分都不是流程美学，而是在回答同一个问题：**这一刻我还退得回去吗？**

**expand–contract（扩展 → 双写 → 回填 → 收缩）** 是本章的核心范式：把一次破坏性的数据格式变更，拆成四个**每一步都保住回滚能力**的阶段 [R-16-6][R-16-7]。

| 阶段 | 数据侧动作 | 应用版本 | 新旧版本能否共存 | 回滚点 | 验证方式 |
|---|---|---|---|---|---|
| ① expand（扩展） | 新增可空列 `amount_cents` / `currency`，**不删旧列** | v1 读旧写旧 | 能，旧代码无视新列 | 无需回滚，schema 向后兼容 | 新列存在、可空、旧列写入不变 |
| ② 双写 | 加数据库触发器，任何写入同时填旧列与新列；部署 v2 也写新列 | v1 / v2 混合 | 能 | 退回 v1（v1 仍读旧列，触发器继续填新列） | `hack/dual-write-check.sh` 行数与校验和一致 |
| ③ 回填 | 后台任务把历史行补齐到新列 | v2 | 能 | 同上 | 历史行新列非空率 100%、抽样金额一致 |
| ④ contract（收缩） | 观察窗口结束、旧列零写入后，v3 只读新列，再删旧列与触发器 | v3 | **不能** | **此处才失去回滚能力** | 旧列零写入持续一个完整窗口、备份已完成 |

关键在于**顺序与不可逆点的位置**：前三步都只是「加东西」，任何一步发现问题，回退方式都是把应用退回上一个版本，数据原封不动；唯一的不可逆动作 `DROP COLUMN` 被推到最后，且必须满足「观察窗口结束 + 旧列零写入 + 备份已完成」三个前置条件。这就是 16.1 里 `DROP COLUMN` 第一句执行与最后一句执行的全部差别。

**双写回填的一致性校验**不是可选项：触发器保证「新写入」双份一致，回填保证「历史数据」补齐，两者之间必须有可执行的核对——行数相等、`amount * 100 = amount_cents` 的抽样校验和相等、新列无 NULL。没有这三条，「新旧共存」只是一句假设。

**判定表**（数据格式先行：改不动数据就别谈策略）：

| 级 | 判据（按序自问） | 命中 → 去处 |
|---|---|---|
| 1 | 这次发布改动了数据格式吗？ | **否** → 回第 13 章，按容量与回退速度选策略。**是** → 进入第 2 级 |
| 2 | 是否包含破坏性 DDL（DROP / 改类型 / 拆分）？ | **是** → 禁止随发布执行，改走 expand–contract 四阶段。**否**（纯加列 / 加索引）→ 进入第 3 级 |
| 3 | ①②③ 每一步是否都验证了新旧版本可共存？ | **否** → 停在 expand，不许往下。**是** → 进入第 4 级 |
| 4 | 观察窗口结束、旧列零写入、本次备份已完成？ | **否** → 不做 contract，保留共存状态。**是** → 才允许执行 `V4__contract.sql`；此后应用侧回滚不再覆盖这一变更 |

### 16.2.1 双写触发器的并发与幂等边界

触发器方案看似一条 SQL，能安全工作的前提是先弄清它的并发语义与幂等边界：

**并发边界**。`BEFORE INSERT OR UPDATE ... FOR EACH ROW` 是行级触发器：每个事务只改写自己那一行的 `NEW` 值，两个并发事务写不同行互不影响；写同一行时由 PostgreSQL 行锁串行化，触发器在锁内执行，不存在「两个事务各写一列」的交错窗口。所以触发器**本身不引入新的并发问题**，真正的并发风险在它之外：触发器里的 `ROUND(amount * 100)` 与 v2 应用内自行实现的换算可能因浮点精度差出 1 分钱。契约因此是**换算规则只保留一份实现**——由触发器承担，v2 直接写 `amount_cents`、不再自行换算 [R-16-6]。

**幂等边界**。触发器全部用「仅当目标列为 NULL 才补写」的守卫（`IF NEW.amount_cents IS NULL ...` / `IF NEW.amount IS NULL ...`），由此得到三条性质：v1 只写旧列 → 触发器补新列；v2 只写新列 → 第二个守卫补旧列，这正是「两版本共存」的机制；回填 `UPDATE ... SET amount_cents = ...` 同样会触发本触发器，但 `NEW.amount_cents` 已非 NULL，守卫直接跳过——**回填与触发器天然无竞争**，这是幂等守卫买到的性质。边界也有两处：其一，触发器无法区分「应用没提供新列」与「应用显式写 NULL」，因此契约要求 v1 永远只写旧列、v2 永远两列都写，中间态（只写新列且期望旧列为空）在本方案里不存在；其二，守卫把「NULL = 未提供」当作前提，本例 `amount` 业务上不可为 NULL（订单必有金额）所以成立——若目标列本身可空，双写必须改为「应用统一从一条写路径进入」或改用显式标记列，这是迁移前评审必须确认的语义前提 [R-16-6][R-16-7]。

### 16.2.2 兼容窗口与收缩判定：每阶段的准入、验证与反例

16.2 的四阶段表给出了「做什么」，本节回答两个执行层问题：每个阶段停多久、凭什么进入下一阶段。

**兼容窗口的长度由业务写路径决定，不由排期决定。** 双写窗口的底线是覆盖一个完整业务周期：订单系统至少要经历一次月末对账、批处理补单或人工调账这类低频写路径，这些路径恰恰最容易绕过日常测试。经验起点是「≥7 天且覆盖一次完整备份周期」，真正的放行条件是 staging 能枚举出全部写 `orders` 的路径，并确认每条都在新列语义下验证过。回填没有独立窗口——回填期间双写照常运行（16.2.1 的幂等守卫保证两者无竞争），它的验证归入双写窗口。contract 观察窗口从 v3 只读新列开始计，长度不低于双写窗口，且必须覆盖同一类低频写路径的完整日历。

**每阶段准入判据**（全满足才进入，任何一条不满足就停在当前阶段）：

| 进入 | 准入条件 |
|---|---|
| ② 双写 | ① 完成；v1 / v2 共存测试（16.5 通过标准第一条）在 staging 全绿 |
| ③ 回填 | `hack/dual-write-check.sh` 连续 3 天输出 `missing=0`、`mismatch=0` |
| ④ contract | 回填 100% + 旧列审计计数为 0 持续一个完整窗口 + 最近备份 Completed + 演练报告在有效期内（CL-16-03） |

**「旧列零写入」必须可测量**。触发器兜底下，旧列被直写也不会报错，所以「没报错」证明不了零写入。给 V2 配一个同事件的前置审计触发器：PostgreSQL 同一事件上的 BEFORE 触发器按名字典序执行，`a_oldcol_audit` 排在 `orders_dual_write` 之前，因此它看到的是应用提交的原始行 [R-16-6]：

```sql
-- db/migrations/V2_5__oldcol_audit.sql：观察窗口期间启用，contract 前随触发器一并删除
BEGIN;
CREATE TABLE IF NOT EXISTS orders_oldcol_write_audit (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  written_at timestamptz NOT NULL DEFAULT now(),
  order_id BIGINT NOT NULL
);
CREATE OR REPLACE FUNCTION orders_oldcol_audit() RETURNS trigger AS $$
BEGIN
  IF NEW.amount IS NOT NULL AND NEW.amount_cents IS NULL THEN
    INSERT INTO orders_oldcol_write_audit(order_id) VALUES (NEW.id);
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
DROP TRIGGER IF EXISTS a_oldcol_audit ON orders;
CREATE TRIGGER a_oldcol_audit
  BEFORE INSERT OR UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION orders_oldcol_audit();
COMMIT;
```

`NEW.amount_cents` 为 NULL 而 `NEW.amount` 有值，正是 v1 的写签名（16.2.1）；v2 与回填写入都不会命中这条判据，审计表只记录「仍在直写旧列」的残留路径。窗口判定命令与通过标准：

```bash
kubectl -n order-demo-prod exec db-0 -- psql -U postgres -d orderdemo -tAc \
  "SELECT count(*) FROM orders_oldcol_write_audit WHERE written_at >= '<窗口起点>';"
# 通过标准：连续一个完整观察窗口输出 0；contract 执行前先 DROP 该触发器与审计表
```

**三个反例**（合成场景，失效模式的方法论参照公开的恢复失效复盘 [R-16-10]）：

1. **并行迁移叠加**：金额拆列进行到双写阶段时，另一条「收货地址拆表」的 expand–contract 同时启动，两个触发器都要改写同一批 `NEW` 行，重建触发器后执行顺序可能翻转，换算结果互相覆盖。判据：**同一时刻全库只允许一条进行中的数据迁移**，迁移登记（库 / 表 / 阶段 / 负责人）随发布 PR 归档；下一条迁移的 expand 必须等上一条 contract 完成。
2. **观察窗口只覆盖工作日**：窗口定为 5 个工作日，恰好漏掉月末批处理在 T+9 对历史订单回写 `amount`；contract 执行后这批写入的语义丢失，且全程没有任何报错。判据：窗口按低频写路径的日历（对账日 / 补单日 / 人工调账）圈定，不按工作日折算。
3. **用「跑了一周没出问题」代替零写入校验**：共存期不出问题只能证明「没发生」，不能证明「不会再发生」——反例 2 里那条月末写路径就在窗口之外。判据：零写入以审计表计数为准，「没报错」不进入任何准入条件。

**何时不该用 expand–contract**：纯加列、加索引等向后兼容变更不需要四阶段，一个 expand PR 直接完成，硬套只是把排期拖长四倍；百行级小表的一次性修复（单事务可完成、无并发读压力）在维护窗口内直接处理；无真实流量、可随时重建的环境（dev）走删表重建更快。四阶段的代价是时间，它买的是回滚能力——没有真实流量与真实数据的地方，这笔买卖不划算。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：用 Operator 管数据库还是买托管服务，应按团队的**故障恢复能力**决定，而不是按技术偏好。
>
> **论证**：有状态组件的成本不在「装起来」，而在「凌晨三点主库挂了，谁能在多长时间内恢复且数据不丢」。Operator（把运维知识写成控制器、让集群自己收敛，白话，详见第 27 章）把故障转移、备份、升级编码成 CRD 里的声明，看起来最「云原生」，但它同时要求团队能运维控制器本身、能处理 CRD 版本迁移、能在 Operator 出 bug 时手工接管。托管数据库把这些责任转移给服务商，代价是可控性、网络路径与成本结构变化。因此决策输入应该是四个可回答的问题：能否在 SLO 内完成恢复、是否演练过、是否有人看得懂控制器的协调循环、降级预案是否成文——而不是「我们团队喜欢用 K8s 管一切」。
>
> **反例与适用前提**：这不等于「小团队一律不许用 Operator」。若团队已有成熟的平台工程能力、且需要跨环境一致的数据库交付形态，Operator 反而是更优解；反过来，连原生 StatefulSet 的备份恢复演练都没跑通的团队，上 Operator 只是把不会的事情藏到一层抽象后面。能力边界的评估表与 CloudNativePG 1.x 的成熟度打分留到第 29 章，本章不提前给结论，也不否定 expand–contract——它替换的是「怎么管数据库实例」，不是「怎么做 schema 变更」。跳过此步的典型代价见第 29 章 Operator 评估表。

## 16.3 工具选型：本章只用原生 StatefulSet

按配置契约与用户裁决，**第 16 章先用原生 StatefulSet 讲迁移范式，CloudNativePG 1.x 是第 29 章的评估对象**，本章只在矩阵里作对比、不展开 Operator 配置[R-16-4]。备份与恢复用 Velero 1.x 为示例实现；工具主版本在此出现，小版本（含 PostgreSQL 具体版本）锁在附录 A。

| 方案（主版本） | 运维责任 | 备份恢复 | 升级路径 | 何时不该用 | 降级预案 |
|---|---|---|---|---|---|
| 原生 StatefulSet（**本章示例实现**） | 团队自担：主备、故障转移、升级、备份全要自己写 | Velero 1.x 卷快照 + 逻辑导出，需自己演练 | 改 StatefulSet 镜像 / 迁移脚本，走 PR | 团队没有 DB 故障恢复能力、要求自动故障转移时 | 保留上一版镜像与迁移脚本，回退到上一个共存阶段 |
| 数据库 Operator（CloudNativePG 1.x，仅对比，第 29 章评估） | 控制器编码了故障转移与备份 | 声明式 Backup / ScheduledBackup | CRD 版本迁移 + 控制器升级 | 没有 CRD / 控制器运维能力时（见第 5 章过度工程） | 手工接管实例，按第 29 章降级预案 |
| 托管数据库 | 服务商承担实例层，团队负责 schema 与数据 | 服务商快照 + 自己的恢复演练 | 服务商维护窗口 | 有数据不出境 / 合规约束，或成本结构不允许时 | 切回自建实例（需预先演练） |
| Velero 1.x（备份示例实现） | 备份控制器与存储桶凭据 | 定时 Schedule + 按需 Restore | 独立 PR 升级 | 只做备份、没有恢复演练计划时（反模式三） | 从上一份可用备份恢复到新集群 |

**最小接入 diff** 与升级 / 回滚路径：

```diff
+ db/migrations/V1__expand.sql        # 加可空新列
+ db/migrations/V2__dual_write.sql    # 双写触发器
+ db/migrations/V3__backfill.sql      # 历史行回填
+ db/migrations/V4__contract.sql      # 观察窗口后删旧列
+ db/migrate.sh                       # 按阶段执行 + 阶段验证
+ hack/dual-write-check.sh            # 双写一致性校验
+ hack/uninstall-check.sh             # finalizer 检查与卸载顺序
~ deploy/base/statefulset-db.yaml     # 备份卷、优雅终止、探针（diff）
+ backup/velero-schedule.yaml         # 定时备份与保留策略
+ hack/restore-drill.sh               # 恢复到新集群
+ docs/restore-drill-report.md        # 演练报告模板
```

升级路径：迁移脚本按 `V1 → V4` 顺序、每阶段单独一个 PR，每阶段先在 staging 执行并验证再进 prod；StatefulSet 镜像与 Velero 版本走独立 PR。回滚路径：**应用侧**用第 13 章的 `kubectl rollout undo` / 明确 SHA；**schema 侧只回退到上一个共存阶段**（例如从双写退回 expand，触发器可删、新列保留），**禁止直接逆向 `DROP` 或把已删的列加回来当回滚**；数据侧用 `velero restore create --from-schedule`。任何一次 schema 变更的回滚方案都必须在迁移 PR 之前写好（公理 6）[R-16-9]。

### 16.3.1 恢复时间目标与责任矩阵（衔接第 29 章）

16.2 的「本书观点」说决策输入是四个问题，本节把它变成一张可填的表。恢复时间目标（RTO）不是一个数，而是**发现 → 决策 → 恢复 → 验证切流**四段之和；同一种方案，四段的责任落在谁头上完全不同——这正是「按团队故障恢复能力选型」的可操作含义 [R-16-4][R-16-8]：

| 恢复环节 | 自建 StatefulSet（本章示例实现） | 数据库 Operator（CloudNativePG 1.x，第 29 章评估） | 托管数据库 |
|---|---|---|---|
| 故障发现 | 自己：探针 + 告警（第 22 章） | 控制器内置实例健康检查 + 自己的告警 | 服务商健康检查 + 自己的告警 |
| 故障转移决策 | 人：值班判断主库是否真挂、谁接管 | 控制器自动选新主，人复核 | 服务商自动（通常不可配置） |
| 数据恢复执行 | 自己写 runbook（16.5.1），Velero 1.x 卷快照或逻辑导出 | Operator 的 Backup / Restore CR | 服务商快照恢复，自己校验 |
| RPO 上限 | 等于自己的备份频率与 WAL 归档能力 | 通常带 WAL 归档，可达分钟级 | 服务商标称值（通常分钟级），需自己验证 |
| 恢复后验证 | 自己：16.4 的一致性校验 | 自己 + Operator 状态字段 | 自己：与自建同一套校验 |
| 典型 RTO 区间（演练过的前提下） | 小时级（1–4h，取决于集群供给速度与演练熟练度） | 十分钟到小时级 | 十分钟到小时级（受恢复点大小与工单流程影响） |
| 谁为 RTO 兑现负责 | 团队（全部四段） | 团队（发现 / 验证）+ 控制器（转移） | 服务商（转移 / 恢复）+ 团队（发现 / 验证 / 切流） |
| 演练义务 | 每季度恢复到新集群一次（本章） | 同左，另加控制器升级演练 | 同左，另加服务商快照的跨区恢复 |
| 没演练过的典型后果 | 备份凭据失效、快照与目标集群不兼容（16.4.3） | CRD 版本不兼容导致恢复 CR 无法创建 | 快照在目标区域 / 目标账号不可见 |

读这张表的方法：先在「典型 RTO 区间」写下**本团队自己的实测值**——没填过实测值的格子一律按「没演练过」处理，回 16.5.1 补演练再谈选型。自建方案的 RTO 里最长一段通常不是恢复本身，而是「决策」：值班不敢确认主库真挂、不敢开始恢复，因为每一步都没有预案；Operator 与托管服务缩短的是「转移」「恢复」两段，但「发现」「验证」两段永远在团队手里。第 29 章评估 CloudNativePG 时，逐行填的就是这张表的 Operator 列，评估结论（成熟度打分与降级预案）回填本表后再做选型裁决 [R-16-4]。

例外前提同样要成文：RPO 要求秒级且不接受任何丢失的场景，三种方案都只能靠同步复制 + WAL 归档兜底，切流 runbook 必须包含「丢失窗口内写入的补偿」一节（16.5.1 第 5 步）[R-16-1]。

### 16.3.2 迁移脚本与迁移工具：Flyway / Liquibase / golang-migrate / Atlas 对比

本章示例实现刻意用「编号 SQL 文件 + `db/migrate.sh`」而不是现成迁移工具，因为 expand–contract 的阶段间隔是**业务观察期**而非进程启动期（16.2.2）；工具不是错的，只是要按矩阵挑对使用位置 [R-16-9]：

| 工具（主版本） | 迁移定义 | 回滚 / 校验能力 | 适用 | 何时不该用 |
|---|---|---|---|---|
| Flyway 11.x | 版本化 SQL 文件（`V1__*.sql`） | 社区版无自动 undo；`validate` 校验基线一致性 | SQL 优先的团队，要在 CI 里做 schema 校验 | 需要「每条迁移自带 down」又用社区版；或想把阶段门禁塞进应用启动流程 |
| Liquibase 4.x | XML / YAML changelog，可含 rollback 段 | 逐条 rollback 定义；diff 接管存量库 | 接管无版本历史的存量库（diff 生成基线） | 团队 SQL 优先：XML 抽象让 DBA 评审看不到真实 SQL，徒增间接层 |
| golang-migrate 4.x | 成对的 up / down 纯 SQL 文件 | down 靠人工维护；有 dirty 状态标记 | Go 技术栈，迁移作为 Job 嵌进交付流水线 | 大存量库基线管理：脏状态处置粗糙，回退语义弱于 Liquibase |
| Atlas 0.x | 声明式期望 schema，diff 生成迁移 | `schema lint` 可拦破坏性变更 | 把 schema 当声明式状态管、Git 里放期望 schema | 要求逐条评审 SQL 的审计流程：生成式 diff 产物仍需人工裁决，声明式反多一步 |

**四个「不该用自动迁移」的判据**（本书观点，论证如下）：

1. **阶段间隔是观察期**：expand–contract 每阶段之间隔数天到数周，等的是审计计数归零与低频写路径覆盖（16.2.2），不是「应用重启的时机」。应用启动时自动跑迁移会把窗口压没，还让发版与改库重新耦合——这正是 16.1 反模式一的根因 [R-16-9]。
2. **多副本并发启动**：滚动更新时新旧 Pod 交叠启动，两个实例同时执行迁移会争抢表锁甚至重复执行；部分工具靠 advisory lock 防重入，但「防住了重复」不等于「阶段门禁被尊重」。
3. **不可逆动作需要人工门禁**：contract 的三重前置（16.2 表）无法表达为工具配置里的一个字段；工具能一键跑 `V4__contract.sql` 恰恰是危险所在——它把不可逆动作变成一条无感命令。
4. **GitOps 收敛口径**：第 14 章起集群状态由 Argo CD 收敛，数据库 schema 不在清单内；迁移若由应用启动触发，就产生控制器管不到的第二条变更路径，漂移的定义被悄悄扩大。

规模判据：表数个位数、迁移由单仓库单团队维护时，编号 SQL + 阶段脚本够用且可审计；多服务共享一个库、迁移历史需要跨仓库基线时，再按矩阵引入工具——引入的只是「版本排序与基线管理」，阶段门禁与不可逆动作的人工裁决无论如何不外包给工具。

> `updateStrategy: OnDelete` 是刻意的：有状态实例不靠控制器自动滚动，升级必须走迁移脚本与人工确认的顺序（16.3）。`preStop` 先让 PostgreSQL 快速停写再退出，配合 30s 宽限，避免 Pod 被强杀后数据文件需要崩溃恢复 [R-16-1]。凭据来自 ESO 注入的 `order-demo/db-credentials`，Git 里没有明文（公理 9，见第 9 章）。db 的资源取 Guaranteed 档：`requests == limits`（`cpu: 250m` / `memory: 512Mi`），保证 DB Pod 在节点压力下不被驱逐、不被 CPU 限流到抖动。迁移前的按序前置校验可用 Init Container 保证时序 [R-16-3]。

**`db/migrations/V1__expand.sql`** —— 只加、不删、不改。

```sql
BEGIN;
ALTER TABLE orders ADD COLUMN IF NOT EXISTS amount_cents BIGINT;
ALTER TABLE orders ADD COLUMN IF NOT EXISTS currency CHAR(3);
COMMIT;
```

**`db/migrations/V2__dual_write.sql`** —— 用数据库触发器实现双写：无论 v1 还是 v2 写入，新旧两列始终同时有值，因此两个版本可混合运行。

```sql
BEGIN;
CREATE OR REPLACE FUNCTION orders_dual_write() RETURNS trigger AS $$
BEGIN
  IF NEW.amount_cents IS NULL AND NEW.amount IS NOT NULL THEN
    NEW.amount_cents := ROUND(NEW.amount * 100)::BIGINT;
  END IF;
  IF NEW.currency IS NULL THEN
    NEW.currency := 'CNY';
  END IF;
  IF NEW.amount IS NULL AND NEW.amount_cents IS NOT NULL THEN
    NEW.amount := NEW.amount_cents / 100.0;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS orders_dual_write ON orders;
CREATE TRIGGER orders_dual_write
  BEFORE INSERT OR UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION orders_dual_write();
COMMIT;
```

**`db/migrations/V3__backfill.sql`** —— 回填历史行，可重复执行。

```sql
BEGIN;
UPDATE orders
   SET amount_cents = ROUND(amount * 100)::BIGINT,
       currency = 'CNY'
 WHERE amount_cents IS NULL
   AND amount IS NOT NULL;
COMMIT;
```

**`db/migrations/V4__contract.sql`** —— **最后一步**，仅在观察窗口结束、旧列零写入、备份完成后执行。

```sql
BEGIN;
DROP TRIGGER IF EXISTS orders_dual_write ON orders;
DROP FUNCTION IF EXISTS orders_dual_write();
ALTER TABLE orders DROP COLUMN IF EXISTS amount;
COMMIT;
```

**`db/migrate.sh`** —— 按阶段执行并逐阶段验证，禁止跳阶段。

```bash
#!/usr/bin/env bash
set -euo pipefail

PHASE="${1:?用法: $0 --phase <expand|dual_write|backfill|contract>}"
PHASE="${PHASE#--phase=}"
[ "${PHASE}" = "${1}" ] && PHASE="${2:-}" || true
NS=order-demo-prod
POD=db-0
PSQL=(kubectl -n "${NS}" exec "${POD}" -- psql -U postgres -d orderdemo -v ON_ERROR_STOP=1)

case "${PHASE}" in
  expand)     SQL=db/migrations/V1__expand.sql ;;
  dual_write) SQL=db/migrations/V2__dual_write.sql ;;
  backfill)   SQL=db/migrations/V3__backfill.sql ;;
  contract)   SQL=db/migrations/V4__contract.sql ;;
  *) echo "未知阶段: ${PHASE}" >&2; exit 2 ;;
esac

echo "== 阶段 ${PHASE}：先做前置校验 =="
"${PSQL[@]}" -c "SELECT count(*) AS orders FROM orders;"

if [ "${PHASE}" = "contract" ]; then
  # 三个前置条件全部满足才允许执行不可逆动作
  PENDING="$("${PSQL[@]}" -tAc \
    "SELECT count(*) FROM orders WHERE amount_cents IS NULL AND amount IS NOT NULL;")"
  [ "${PENDING}" = "0" ] || { echo "仍有 ${PENDING} 行未回填，禁止 contract" >&2; exit 1; }
  kubectl -n "${NS}" get backup -l app.kubernetes.io/name=order-demo \
    -o jsonpath='{.items[-1:].status.phase}{"\n"}' | grep -qx Completed || {
      echo "最近一次备份未完成，禁止 contract" >&2; exit 1;
    }
  echo "确认观察窗口已结束且旧列零写入（由发布 PR 的 runbook 记录负责）"
fi

echo "== 执行 ${SQL} =="
"${PSQL[@]}" -f - < "${SQL}"

echo "== 阶段验证 =="
case "${PHASE}" in
  expand|dual_write|backfill)
    "${PSQL[@]}" -c "SELECT count(*) FILTER (WHERE amount_cents IS NULL) AS missing_new FROM orders;"
    ;;
  contract)
    "${PSQL[@]}" -c "SELECT count(*) AS orders FROM orders;"
    ;;
esac
echo "阶段 ${PHASE} 完成；应用侧是否可回退到上一版本，见 16.5。"
```

### 16.4.1 大表分批回填：锁影响与批处理实现

`V3__backfill.sql` 是单事务全量 `UPDATE`，几百万行以下没问题；订单表涨到千万行后有三重代价：**长事务**持锁数小时，期间这些行上的正常业务更新（正是 v1 / v2 混跑期的流量）全部排队；WAL 一次写出导致复制延迟飙升；事务一旦中途失败，回滚成本巨大。替代做法是按主键分批、每批一个短事务，批次之间把时间让给业务流量：

**`db/backfill-batch.sh`** —— 分批回填，可重复执行（幂等：候选集只含 `amount_cents IS NULL` 的行）：

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-prod
POD=db-0
PSQL=(kubectl -n "${NS}" exec "${POD}" -- psql -U postgres -d orderdemo -v ON_ERROR_STOP=1 -tAc)
BATCH="${BATCH:-2000}"
SLEEP_S="${SLEEP_S:-0.2}"

TOTAL="$(kubectl -n "${NS}" exec "${POD}" -- psql -U postgres -d orderdemo -tAc \
  "SELECT count(*) FROM orders WHERE amount_cents IS NULL AND amount IS NOT NULL;")"
echo "待回填行数: ${TOTAL}"

LAST=0
while :; do
  LAST_ROW="$("${PSQL[@]}" "
    WITH picked AS (
      SELECT id FROM orders
       WHERE id > ${LAST}
         AND amount_cents IS NULL AND amount IS NOT NULL
       ORDER BY id
       LIMIT ${BATCH}
    )
    UPDATE orders o
       SET amount_cents = ROUND(o.amount * 100)::BIGINT,
           currency = 'CNY'
      FROM picked
     WHERE o.id = picked.id
    RETURNING o.id;" | tail -n1)"
  [ -z "${LAST_ROW}" ] && break
  LAST="${LAST_ROW}"
  echo "已回填至 id=${LAST}"
  sleep "${SLEEP_S}"
done

./hack/dual-write-check.sh
```

验证与通过标准：脚本结束后 `dual-write-check.sh` 输出 `missing=0`、`mismatch=0`；执行期间 `kubectl -n order-demo-prod exec db-0 -- psql -U postgres -d orderdemo -tAc "SELECT wait_event_type, wait_event FROM pg_stat_activity WHERE state = 'active';"` 不出现持续性的 `Lock:transactionid` 等待（业务侧锁等待应只有毫秒级偶发）。中断后重跑安全：已回填的行 `amount_cents` 非空，不会再进入候选集，也不会被二次改写。

锁影响口径：每批只持有本批行的行锁，事务毫秒级提交，长事务对 autovacuum 与复制延迟的拖累消失；`BATCH` 与 `SLEEP_S` 先在 staging 按业务写入峰值调定，随迁移 PR 附调参记录再进 prod [R-16-6]。

### 16.4.2 finalizer 卡住后的分级处置（与第 27 章卸载清单的对应）

`hack/uninstall-check.sh` 回答「删之前查什么」；本节回答「已经卡住了怎么办」。处置必须分级，跳级正是 16.1 反模式二的根因之一。finalizer 的正式定义与卸载总清单见第 27 章，本节只给有状态资源卡死时的处置序，并标出与第 27 章卸载清单的对应点 [R-16-5]。

**L0｜确认卡因，先不动手**。`kubectl -n order-demo-prod get statefulset db -o jsonpath='{.metadata.finalizers} {.metadata.deletionTimestamp}'`，再查写这个 finalizer 的控制器还在不在：`kubectl -n <operator 所在命名空间> get pods` 与 `kubectl get crd` 对照资源组名。三种常见类别：控制器还在（被误停 / CrashLoop / 拉不动镜像）、控制器已被删、finalizer 由外部系统写入（卷快照、负载均衡等）。

**L1｜控制器还在：让它完成清理，而不是替它清理**。控制器被缩到 0 副本或处于 CrashLoop，先恢复控制器运行；它跑完 reconcile 后会自己摘掉 finalizer。这一级永远优先——手工移除 finalizer 等于替控制器签署「清理已完成」，而卷、快照、外部端点可能并没有清 [R-16-5]。

**L2｜控制器已删、清理语义上已完成：手工移除 finalizer 作为最后手段**。三条前提逐一核实后才允许执行：对应外部资源已确认回收（PVC 已删、`VolumeSnapshotContent` 已清、外部端点已释放）；卸载 PR / runbook 里能对上这些资源的清单；有补偿措施与记录（残留卷逐一挂载检查后再删，patch 记录写回卸载 PR）。执行：

```bash
kubectl -n order-demo-prod patch statefulset db \
  --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'
kubectl -n order-demo-prod get statefulset,pvc   # 验证：对象已删除、无 PVC 残留
```

这是「手工 patch 生产对象」的唯一豁免场景：例外前提是控制器已不存在且清理已核实完成，补偿措施是资源清点与残留检查，有效期到卸载 PR 关闭为止——超出这个口径的 patch 一律违反公理 5。

**L3｜命名空间删不掉：逐对象排查，禁止整命名空间强删**。`kubectl get namespace order-demo-prod -o jsonpath='{.spec.finalizers}'` 若仍含 `kubernetes`，说明命名空间内有对象卡在删除流程；回到 L0 逐个找。**禁止**对挂有 PVC 的 Pod 使用 `--force --grace-period=0`：强杀只会让 kubelet 与 API Server 对卷回收状态产生分歧，留下更难清理的孤儿卷 [R-16-1][R-16-5]。

与第 27 章卸载清单的对应关系：本章 `hack/uninstall-check.sh` 的三步（列出带 finalizer 对象 → 先删实例并等清理完成 → 最后删控制器）对应第 27 章卸载清单的「资源清点」与「顺序控制」两节；本节 L1–L3 对应其「异常处置」节；第 27 章「先删实例、后删 CRD」在本章表现为「先删 StatefulSet、后删 Operator」。两章共享同一个原则：**finalizer 是清理契约，处置目标是让契约兑现或显式豁免留痕，而不是绕过它**。

### 16.4.3 排错案例：Velero 卷快照与 PVC / StorageClass 版本不兼容（合成案例）

恢复演练第一次在新集群跑就失败，是比生产事故低一档、但同样必须复盘的场景（合成案例，非真实事件）：平台组把集群存储栈从 in-tree provisioner 迁到 CSI（外置 provisioner + snapshot-controller），Velero 的 Schedule 照旧每天 Completed，季度演练在新集群执行 Restore 却卡住。

**现象**：Restore 状态 `PartiallyFailed` / `Failed`；`velero restore describe` 显示 PVC 已重建，但 Pod `db-0` 一直 `ContainerCreating`；事件里出现 `FailedMount`、`volumesnapshotcontent ... not found` 或 `no CSI driver found for storage class` [R-16-2]。

**三条典型根因与查法**：

1. **快照 API 版本不匹配**：源集群的快照由 CSI `v1beta1` 的 `VolumeSnapshotContent` 记录，目标集群的 snapshot-controller 只认 `v1`。查法：`velero backup describe <backup> --details` 看 CSI 卷快照条目是否为空；`kubectl get volumesnapshotclasses` 确认目标集群存在快照类，且其 `driver` 字段与目标 StorageClass 的 provisioner 一致。快照内容对不上时，Velero 会退化为「只恢复 PV 对象、不恢复数据」——PVC 建出来了，盘是空的。
2. **StorageClass 名或供应方变了**：备份记录里 PVC 引用 `storageClassName: standard`，新集群同名类由不同 provisioner 提供（或默认类不同），动态供给失败。查法：源 / 目标集群各执行 `kubectl get sc` 并 diff；`kubectl -n order-demo-restore get pvc` 看是否停在 `Pending` 及其事件。
3. **Velero CSI 插件与集群 CSI 版本错位**：插件支持的快照 API 版本与集群 snapshot-controller 版本不匹配，Restore 阶段直接跳过卷数据。查法：`velero plugin list` 对照 Velero 发行说明的 CSI 兼容矩阵。

**修复与预防**（按最小改动顺序）：目标集群补齐 `VolumeSnapshotClass`（`driver` 与 StorageClass provisioner 一致）后重试 Restore；若快照内容确已丢失，降级走数据面——源集群逻辑导出（`pg_dump`）、目标集群导入，这条降级路径要写进 16.5.1 的预案；预防的门禁只有一条：**升级存储栈（CSI driver / snapshot-controller / Velero 插件）之前，先在目标集群完整跑一次 16.5.1 的演练**，Schedule 每天绿不等于快照在新集群可用 [R-16-2][R-16-8]。

**判据**：演练通过时，`velero restore describe <restore>` 的卷快照恢复条目与备份一致、Pod `db-0` Ready、16.4 的一致性校验输出 `missing=0`。任何一条不满足，按上面三条根因排查，禁止带着「PartiallyFailed 但 Pod 起来了」的侥幸宣布演练通过。

### 16.4.4 备份分层、RPO/RTO 目标推导与季度演练 runbook

`backup/velero-schedule.yaml` 只是备份体系的一层。**RPO 不是拍出来的数，是备份频率的推导结果**：只有每日 02:00 卷快照时，最坏 RPO ≈ 24 小时 + 快照执行时长——16.1 时间线 T+35 的「RPO 缺口」就是这个公式的兑现。要压到分钟级，必须在快照之下补 WAL 归档：PostgreSQL 把每个 WAL 段（写满即归档，可用 `archive_timeout` 强制按分钟级切段）推到独立于快照的存储，恢复时先还原快照、再重放 WAL 到事故点前最后一个一致位。本书观点：**RPO 目标决定备份层数，每层防住一个失效面**（不需要外部背书，推导如下）——单层快照防不住快照技术栈整体失效（16.4.3 的 CSI 兼容排错正是这个失效面），逻辑导出与快照走不同技术路径，恰好互补 [R-16-2][R-16-8]：

| 层 | 内容 | 频率 / 保留 | 防住的失效面 |
|---|---|---|---|
| L0 卷快照 | Velero Schedule + CHECKPOINT 钩子 | 每日 / 7 天 | Pod / 节点 / 存储单点故障 |
| L1 WAL 归档 | 归档到独立存储桶 | 持续（分钟级切段）/ 与快照配套 | 把 RPO 从小时级压到分钟级，覆盖快照点之后的增量 |
| L2 逻辑导出 | `pg_dump` 到对象存储 | 每周 / 30 天 | 快照技术栈整体失效（16.4.3 的降级路径） |
| L3 恢复演练 | 季度恢复到新集群 | 每季度 + contract 前追加 | 「备份不可用」本身（反模式三） |

**RTO 目标要把 16.3.1 的四段拆成可考核的数**：发现 ≤5 分钟（告警，见第 22 章）、决策 ≤15 分钟（按 runbook 判据确认主库真挂 / 不可逆点已越过）、恢复 ≤60 分钟（演练实测，集群供给速度是主要变量）、验证切流 ≤30 分钟（16.5.1 第 3–4 步）；合计上限 2 小时。每次演练把各段实测值回填 16.3.1 责任矩阵，哪一段超标就加固哪一段，而不是笼统宣布一个「RTO 4 小时」。

**季度演练的组织 runbook**（`hack/restore-drill.sh` 只是其中一步）：

1. **演练前**：选定备份并核对 `ttl` 未过期；核对备份桶凭据的有效期——16.1 反模式三的翻车点就是凭据轮换后从没用备份桶做过真实读取；演练集群就绪且与生产同形。
2. **执行**：`./hack/restore-drill.sh <演练 context> <backup 名>`。
3. **校验**：除脚本的行数与新列校验外，追加完整一致性清单——行数相同只证明「量」一致，还要证明恢复点位置与数据「质」一致 [R-16-8]：

```bash
# 序列名以实际库为准，本例为 orders_id_seq；源库与恢复库各执行一次，除 seq_lag 外逐项相等
kubectl --context <演练 context> -n order-demo-restore exec db-0 -- \
  psql -U postgres -d orderdemo -tAc "
SELECT 'row_count', count(*) FROM orders
UNION ALL SELECT 'max_id', max(id) FROM orders
UNION ALL SELECT 'seq_lag', (SELECT last_value FROM orders_id_seq) - (SELECT coalesce(max(id),0) FROM orders)
UNION ALL SELECT 'amount_checksum', coalesce(sum(hashtext(id::text || ':' || coalesce(amount_cents::text,''))),0) FROM orders;"
# 通过标准：row_count / max_id / amount_checksum 与源库执行同一条 SQL 的结果一致；
# seq_lag ≥ 0（序列不落后于 max(id)，否则恢复库新写入会主键冲突）
```

4. **报告与闭环**：报告归档发布 PR；演练发现的每个问题（凭据失效、快照类缺失、脚本缺步骤）建 issue 限期修复，下次演练逐条复核——演练的价值在闭环，不在「跑过一次」。

## 16.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（仓库根目录，需 `kubectl` / `velero` / `psql` / `python3`，版本见附录 A）：

```bash
chmod +x db/migrate.sh hack/dual-write-check.sh hack/uninstall-check.sh hack/restore-drill.sh
./db/migrate.sh --phase expand
./db/migrate.sh --phase dual_write
./hack/dual-write-check.sh
./db/migrate.sh --phase backfill
./hack/dual-write-check.sh
# 新旧版本同时读写订单表（v1 写旧列、v2 写新列，触发器保证两列一致）
kubectl -n order-demo-prod exec db-0 -- psql -U postgres -d orderdemo \
  -c "INSERT INTO orders(amount) VALUES (12.34); SELECT amount, amount_cents, currency FROM orders ORDER BY id DESC LIMIT 1;"
# 备份恢复演练
velero backup get
./hack/restore-drill.sh kind-order-demo-drill "$(velero backup get -o json | python3 -c 'import sys,json; print(json.load(sys.stdin)["items"][0]["metadata"]["name"])')"
./hack/uninstall-check.sh
./hack/verify.sh
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 四阶段可共存 | ①②③ 各阶段执行后，v1 与 v2 版本同时读写订单表均成功，无 `column does not exist` |
| 双写一致性 | `hack/dual-write-check.sh` 输出 `missing=0`、`mismatch=0` [R-16-6] |
| contract 前置 | `V4` 执行前「未回填行 = 0」「最近备份 Completed」「旧列零写入」三条全满足，否则脚本拒绝执行 |
| 恢复演练通过 | `hack/restore-drill.sh` 在演练集群恢复出相同行数、新列无缺失，且生成 `docs/restore-drill-report.md` [R-16-2][R-16-8] |
| finalizer 无残留 | `hack/uninstall-check.sh` 列出的带 finalizer 对象为空（或已按清单完成清理），无 `Terminating` 卡住 [R-16-5] |
| 应用回归 | `verify.sh` 的 `/healthz` 为 200；旧版本启动后读写正常 |

**回滚命令 / 步骤**。三条链要分开处理，这是本章与第 13 章最大的不同：

```bash
# 链 1：应用侧回滚（与第 13 章相同）
REV="$(kubectl -n order-demo-prod rollout history deployment/api | tail -n2 | head -n1 | awk '{print $1}')"
kubectl -n order-demo-prod rollout undo deployment/api --to-revision="${REV}"
kubectl -n order-demo-prod rollout status deployment/api --timeout=120s

# 链 2：schema 侧 —— 只回退到「上一个共存阶段」，禁止逆向 DROP
# 双写阶段出问题：删触发器、保留新列，应用退回 v1（v1 仍读旧列）
kubectl -n order-demo-prod exec db-0 -- psql -U postgres -d orderdemo -v ON_ERROR_STOP=1 \
  -c "DROP TRIGGER IF EXISTS orders_dual_write ON orders; DROP FUNCTION IF EXISTS orders_dual_write();"
# 已到 contract：不可逆，唯一回退是把数据从备份恢复到新集群再切流

# 链 3：数据侧 —— 从备份恢复（生产唯一合法路径仍须回到 Git，见第 14 章）
velero restore create --from-schedule order-demo-db --wait
# 或恢复到演练/新集群做验证：./hack/restore-drill.sh <context> <backup>

# 生产真相源：把 StatefulSet 与迁移脚本的回退写成 PR，由第 14 章控制器同步
git revert <迁移 PR 的 merge commit>
git push origin main
argocd app sync order-demo-prod
```

> **为什么 schema 不能「逆向回滚」**：`DROP COLUMN` 之后把列加回来，得到的是空列，原值已经丢了；把 `amount_cents` 改回 `amount` 同理。所以前三阶段的回退动作是「停用触发器 / 停在新列仍在的共存态」，而不是「执行反向 SQL」。这也是 16.2 把不可逆点推到最后的原因。任何一次迁移 PR 合并之前，回滚方案（三条链各写一遍）必须已附在 PR 上，否则禁止发布（CL-G-07）。

**回滚验证**：

```bash
kubectl -n order-demo-prod exec db-0 -- psql -U postgres -d orderdemo \
  -c "SELECT count(*) FROM orders; SELECT amount, amount_cents FROM orders ORDER BY id DESC LIMIT 3;"
kubectl -n order-demo-prod rollout status deployment/api --timeout=120s
argocd app diff order-demo-prod
./hack/verify.sh
velero restore get
```

通过标准：旧版本启动后读写订单表正常、两列数据仍一致（说明仍处共存态）、`argocd app diff` 为空、`/healthz` 为 200、恢复任务为 `Completed`。**没有在 staging 演练过「从双写退回 expand」与一次备份恢复，就不允许执行任何迁移 PR**（CL-G-07、CL-G-09）。

### 16.5.1 不可逆点已越过：从备份恢复到新集群并切流（16.1 时间线 T+45 起的 runbook）

前置条件：发布已冻结；备份点已选定（最近一份 Completed 且满足 16.4.3 判据的备份）；备用集群已就绪、形态与生产一致且演练过恢复。全程遵循公理 5：恢复期间的清单变更一律走 Git，本 runbook 中唯一的「手工」动作是执行 velero / kubectl 命令本身，命令输出与结论都贴回事故 PR [R-16-2][R-16-8]。

```bash
# 1) 在备用集群恢复（仅 db 组件；命名空间同名，便于 Argo CD 直接复用同一份 Git 声明）
velero --kubecontext <备用集群 context> restore create db-incident-restore \
  --from-backup <backup 名> \
  --include-resources pvc,pods,services,statefulsets,secrets,configmaps \
  --namespace-mappings order-demo-prod:order-demo-prod \
  --wait
velero --kubecontext <备用集群 context> restore get
# 通过标准：restore phase=Completed；16.4.3 三条判据全过

# 2) 数据一致性校验（与 hack/restore-drill.sh 同一套判据）
kubectl --context <备用集群 context> -n order-demo-prod wait \
  --for=condition=Ready pod/db-0 --timeout=300s
kubectl --context <备用集群 context> -n order-demo-prod exec db-0 -- \
  psql -U postgres -d orderdemo -tAc \
  "SELECT count(*) FROM orders; SELECT count(*) FROM orders WHERE amount_cents IS NULL;"
# 通过标准：新列缺失 = 0；行数与备份点核对，差额即 RPO 窗口内的写入量
```

**第 3 步｜应用切流**：在 Git 中把 api / gateway / worker 的发布目标切到备用集群（复用第 30 章双集群发布的黄金路径），Argo CD 3.x 同步、健康检查通过后再放流量。db 连接目标不变——同名 Service `db`、端口 5432，应用清单零改动；这是恢复环境必须与生产保持同形的原因。

**第 4 步｜流量切换**：Gateway / DNS 按第 15 章的权重机制小比例试流（5% → 50% → 100%），每档观察 `/readyz` 成功率与订单写入速率，异常即停在该档回退权重。

**第 5 步｜RPO 缺口补偿**：对「备份点之后、事故点之前」的写入按来源分三类处置——有 WAL 归档的重放到事故前最后一条；有上游消息队列的重放消息；两者都没有的出清单交业务侧人工补录。补偿完成前，受影响订单的查询路径挂「数据恢复中」的降级说明。

**第 6 步｜旧集群封存**：原 prod 命名空间改为只读（摘除写权限而非删除），PVC 与快照全部保留至复盘结束——既是取证需要，也是「新集群恢复被证伪」时的最后退路。

**第 7 步｜回写 Git**：恢复期间的一切变更（切流、补偿脚本、只读化）合并为一个事故 PR 归档；用 16.4 的演练报告模板追加「真实 RTO 四段耗时」与「RPO 缺口清单」两列，形成本次事故的恢复记录 [R-16-9]。

通过标准：100% 流量由新集群承载且 `/healthz` 为 200、`argocd app diff` 为空、RPO 缺口清单逐条闭环、恢复报告归档。整段流程要兑现 16.3.1 责任矩阵中自建方案的 RTO 承诺：**决策与执行分离、每步有判据、全程走 Git**。
