## 12.1 问题与反模式：为什么「CI 跑绿了」不等于「生产跑的是这个包」

前十一章，`order-demo` 的清单都是人在本地 `kubectl apply` 出来的，构建也靠 `hack/kind-up.sh` 里的一句 `docker build`。到了这一章，构建要搬进持续集成（CI）流水线，这是第一次「机器替人做决定」。很多团队搬完之后会松一口气：每次 push 都绿，镜像自动进仓库，看起来交付已经自动化了。直到某次生产故障复盘，才会撞上三个无法回答的问题：**这次上线的产物是哪一个 commit 构建的、staging 验过的和 prod 跑的是不是同一份、要退回上一版该把哪个引用改回去**。

**合成案例**（基于多起公开事故的合成，非真实事件）：一个订单服务把 dev / staging / prod 各配了一条流水线，三条流水线各自执行 `docker build`，标签都用同一个 `git-<sha7>`。某次只改了一行文档的提交被推上去，三条流水线几乎同时启动；其中 prod 那条因为缓存未命中，拉到了当天刚更新的基础镜像层。三份镜像 digest 各不相同，标签却完全一致。当晚订单接口报错，值班同学按标签回滚，拉回来的仍是当天 digest 里的新基础镜像，故障没有消失。复盘时发现，谁也拿不出「staging 验过的那个 digest 到底叫什么」——因为流水线从来没有把 digest 当成一等产物记录下来 [R-12-1][R-12-5]。

这不是运气差。**把「同一份产物」寄托在「同一套构建命令」上，本身就是把可复现交给了概率**：基础镜像、依赖缓存、时间戳、并行任务，任何一个变量都会让「同一条命令」产出不同的字节。Kubernetes 只保证按镜像字段去拉取，不保证这个字段指向你以为的那次构建 [R-12-4]。

三个高频反模式：

**反模式一：每个环境跑一遍 build。** 现象是 staging 验证通过、prod 行为不同，或者同一个 `git-<sha7>` 在三个仓库指向不同层；根因是把「环境配置差异」和「制品差异」混为一谈，违反了 build once / promote（全书公理 1，见第 3 章）。本章的替代做法是把构建收敛成流水线里唯一一个 job，产出一个带 digest 的制品引用，后续所有阶段与环境只传递这个引用，晋升动作不调用任何构建命令 [R-12-1][R-12-6]。

**反模式二：第三方 Action 用 `@v1` 而不是提交 SHA 锁定。** 现象是流水线某天突然行为变化、`set -e` 失效，或构建产物里多了预期外的文件；根因是 tag 只是可变指针，上游移动 tag 或被篡改时，你的流水线会在无提交、无评审的情况下换掉执行代码，而 CI 又恰好握着推送镜像和读取机密的权限 [R-12-2]。本章的替代做法是把每个 `uses:` 锁到 40 位 commit SHA，升级由自动化依赖更新 PR 显式发起、可 review、可回滚。

**反模式三：把生产凭据塞进 CI 变量并到处打日志。** 现象是构建日志里出现明文口令、`env` 调试输出把凭据带进了归档，或一个被入侵的第三方 Action 直接读走长期密钥；根因是把机密当作普通环境变量，且给流水线发了长期、过宽的权限 [R-12-7][R-12-8]。本章的替代做法是权限默认最小、机密脱敏、用 OIDC 短期凭据换取推送令牌（OIDC 与动态凭据的完整配置见第 26 章），凭据永不进入镜像层与仓库。

还有一类更隐蔽的信号污染：**flaky 测试**。「重跑一下就好」如果被写进流水线重试策略，绿灯就不再代表代码正确，整条流水线的判定价值被稀释；本章把它作为「本书观点」在 12.2 单独论证，因为它没有外部规范可引，是本书对工程判断的主张。以上反模式的**方法论**参照公开的 CI 供应链与凭据外泄复盘 [R-12-9]，该来源只用于支撑「这类失效模式确实存在」，不用于证明上面这个合成案例真实发生。

## 12.2 范式与决策树：一次构建的四个可证明判据

本章要回答的决策问题只有一句：**流水线怎样保证「一次构建、多处晋升」，而不在每个环境悄悄重做一遍？** 这里的「晋升」（把已构建的同一制品逐级送到不同环境，只改配置不改产物，正式定义见第 3 章）是全书公理 1 的动词形式，第 3 章给的是原则，本章给的是机器可执行的证据。

**一次构建**（build once）不是一句口号，而是四个能用命令当场证明的结果：

| 判据 | 可证明的形式 | 为什么必须是它 |
|---|---|---|
| 唯一制品 | 一个 commit 只触发一次 build job，产出一个 `sha256:` digest | digest 才是内容标识，标签是可变指针 [R-12-5] |
| 唯一标签 | 镜像标签为 `git-<sha7>`，可反查到唯一源码提交 | 禁用 `latest`，故障复盘才有确定目标（见第 6 章） |
| 环境等价 | dev / staging / prod 的 `image` 字段**完全相同**，只有配置不同 | 环境差异只能在配置里，不能在产物里 [R-12-7] |
| 引用晋升 | 晋升动作只改写制品引用，不调用任何构建命令 | 一调用 build，前三条立刻失效 [R-12-1] |

由这四个判据得到一棵决策树。它的用途不是「设计流水线」，而是**在合并任何一条流水线改动之前，判断这次改动会不会破坏一次构建**：

```
这次变更改动了源码 / Dockerfile 吗？          是 → 走 build job，产出唯一 digest，记录到制品清单
        │ 否
只改了配置 / 文档 / 工作流文件吗？            是 → 不重建镜像，只更新配置清单（见第 9、14 章）
        │ 否
build job 是否只在 push 到主干时触发一次？    否 → 收敛触发条件，禁止每个环境各跑一遍
        │ 是
promote 脚本里是否出现 docker build / buildx？ 是 → 删掉，改为 set image 引用（12.4）
        │ 是/否
uses: 是否全部锁定到 40 位 SHA？             否 → 执行 hack/pin-actions.sh 并提交（12.4）
        │ 是
流水线的 job 顺序是否为 lint → 单测 → 集成 → 构建 → 校验 → 推送？
                                            否 → 按下方阶段表重排，越晚发现的错误越贵 [R-12-6]
        │ 是
→ 一次构建成立，产物可进入第 13 章的发布策略选择
```

**流水线阶段表**（fail fast 的具体落点，接第 11 章的四层校验，不重复实现）：

| 阶段 | 输入 | 输出 | 失败即停条件 |
|---|---|---|---|
| lint | 源码 | 静态检查结果 | 格式 / 静态检查非零退出 |
| 单测 | 源码 + 依赖 | 测试报告 | 任一用例失败，**不重跑** |
| 集成测试 | 本地 kind 集群 | 可访问的最小闭环 | 第 11 章 kubeconform / conftest / kuttl 任一关失败 |
| 校验 | 渲染产物 | 制品清单（含 digest） | 清单缺 `sha256:` 或含 `latest` |
| 构建 | 通过校验的源码 | 唯一镜像 + digest | 同一个 `git-<sha7>` 已有不同 digest → 阻断 |
| 推送 | 唯一镜像 | 仓库中的不可变制品 | 推送凭据非 OIDC 短期令牌 → 阻断 [R-12-2] |

注意顺序里「校验在构建之前」：第 11 章的四层校验是对**清单**的校验，把错误字段拦在产出制品之前，代价最低；构建与推送排在最后，是因为它们最贵且一旦做成不可变制品就无法「改一下」 [R-12-6]。**回滚**（把线上恢复到上一个已知良好版本，详见第 13 章）在本章只以「制品引用可回退」的形态出现，不作为推理前提。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：flaky 测试要么修、要么删，不允许用「失败自动重跑」长期留在流水线里。
>
> **论证**：流水线的价值是把「这段代码能不能发布」压缩成一个可信的布尔信号。自动重跑等于把 `flaky || !flaky` 折叠成「绿」，于是绿灯不再蕴含「代码正确」，只蕴含「跑够了次数」。更贵的代价在下游：一旦团队习惯了「红灯先重跑」，真正的回归缺陷也会被当成抖动放过，第 13 章之后的回滚演练、第 15 章的指标判定都会继承一个被污染的信号底座。修复的方向是把不确定性从判定环节里移除——外部依赖用可重放的 fixture 或本地容器替代，时序问题用显式等待替代 `sleep`，确实无法消除的抖动源移出阻断门禁。
>
> **反例与适用前提**：这不等于「所有偶发失败都必须当天删用例」。对尚未定位的外部依赖抖动，允许临时把该用例从阻断门禁移到独立观测，但必须写清责任人、有效期与恢复条件，到期不修即删除。前提是团队有权限改测试代码；若测试来自上游不可控套件，则应把整套测试降级为「参考信号」并在发布门禁里显式声明豁免，而不是偷偷加重试。跳过此步的典型代价见第 31 章反模式速查。

**制品引用流转图**：一次构建产出的引用，在后续章节里被谁消费、以什么形态流转。全链路唯一的不变量是 **digest**；`git-<sha7>` 标签只是人读的索引，每个环节真正的操作对象都是 digest [R-12-1][R-12-5]。

```
源码 push 到 main
   │  build job（唯一一次，12.4 build.yml）
   ▼
【第 12 章 · 构建】制品诞生
   registry.example.com/order-demo/gateway:git-<sha7>@sha256:<digest>
   digest 写入 artifacts.txt 与运行摘要 —— 这是它第一次被记录
   │  制品引用（overlay 的 image 字段）
   ▼
【第 14 章 · 晋升】promote-artifact.sh 只改写引用，Git PR 合并，控制器同步到 staging / prod
   同一个 digest 承载流量；任何环境都不出现第二次 build
   │  同一 digest 进入发布编排
   ▼
【第 13 章 · 发布 / 回滚】发布策略承载该引用；回滚 = 把引用指回上一个已知良好的 digest
   引用回退而非重建，正是 12.5 方案 A 在第 13 章的完整展开
   │  不可变制品 + digest 证据链
   ▼
【第 24 章 · 签名验签】cosign 按 digest 签名，准入控制器按 digest 验签
   未签名 / digest 对不上的引用在集群门口被拒绝
```

| 环节 | 章 | 拿到什么 | 对制品引用做什么 | 红线 |
|---|---|---|---|---|
| 构建 | 第 12 章（本章） | 源码 commit | 产出 `:git-<sha7>` + digest，写入 artifacts.txt | 晋升脚本里出现 build 命令（判据 4 失效） |
| 晋升 | 第 14 章 | Git 里的 overlay | 只改写 `image` 引用，控制器同步 | 晋升触发二次构建（违反 build once） |
| 发布 / 回滚 | 第 13 章 | 同一 digest | 发布策略承载引用；回滚指回上一 digest | 未验证回滚方案就发布（公理 6） |
| 签名验签 | 第 24 章 | digest | 按 digest 签名、按 digest 验签门禁 | 按 tag 验签（tag 可变，签名失去对象） |

两个次序说明：其一，生命周期主线是 12→14→13，而第 13 章的回滚方案按公理 6 **先于**发布存在，所以流转图里回滚能力在晋升时就已就绪；其二，第 24 章的签名之所以必须按 digest 而非 tag，是因为 tag 在链路上任何一点都可能被覆盖——这正是 12.5.1 定位演练要现场演示的情形。

## 12.3 工具选型：CI 平台不是重点，制品边界才是

按本书选型基线，本章唯一示例实现取卡片配置清单里的 GitHub Actions，其余平台只在矩阵里作对比 [R-12-3]；工具主版本在此出现，小版本统一锁在附录 A。需要先说清一个边界：**CI 平台不负责「变更怎么进集群」**，那是 GitOps 引擎的事（Git 里写什么、集群就变成什么，白话见第 14 章）。本章只负责把源码变成一份带 SHA 的不可变制品，并把它交给仓库；越过这条边界，在 CI 里直接 `kubectl apply -f` 生产集群，就是第 14 章要堵住的手工变更入口。

| 工具（主版本） | 最适 | 不选 / 迁移成本 | 与 GitOps 的衔接 | 回滚方式 | 何时不该用 |
|---|---|---|---|---|---|
| GitHub Actions（示例实现） | 仓库已在 GitHub、想要最短接入路径 | 从其他平台迁入需重写工作流语法，中等 | 产出制品引用写入 Git，由第 14 章控制器拉取 | `git revert` 工作流文件；制品引用回退 | 仓库不在 GitHub，或有数据不出境 / 强制自托管要求 |
| GitLab CI/CD 1.x | 已用 GitLab 全家桶、要内置容器仓库 | 与 GitHub 生态不通用，中等 | 同上，产物以 CI job artifact 或仓库提交传递 | 回滚 `.gitlab-ci.yml` 提交 | 团队已重度依赖 GitHub Actions 且不愿维护 Runner |
| Tekton Pipelines 0.x | 需要 K8s 原生、跨集群复用的流水线 CRD | 需运维控制器与 `Task`/`Pipeline` 资源，高 | 天然在集群内，容易越界直接改集群 | 回滚 `PipelineRun` 定义 | 只要跑几条脚本、没有 K8s 原生流水线运维能力时（过度工程，见第 5 章） |
| Dagger 0.x | 本地与 CI 需要完全一致的构建图 | 需引入 SDK 与引擎，中高 | 只管构建，不碰集群，边界最干净 | 回滚构建脚本提交 | CI 平台已够用、没有「本地跑不过、CI 却过了」的痛点时 |

**最小接入 diff**（相对「没有流水线」的仓库，只新增两个文件与一个脚本）：

```diff
+ .github/workflows/build.yml      # 唯一一次构建 + OIDC 推送
+ .github/workflows/validate.yml   # 接入第 11 章四层校验，作为 build 的前置依赖
+ hack/promote-artifact.sh         # 按 SHA 改写引用，不重建
+ docs/gitops-preview.md           # 1 页预告，标明本章不越界改集群
```

**升级 / 回滚路径**：升级第三方 Action 时，由依赖更新机器人发起一个只改 SHA 的 PR，走与业务代码同样的评审；回滚就是 `git revert` 这个 PR。构建工具链（Go、BuildKit）的版本锁在附录 A，升级同样以 PR 形式发生，绝不由 runner 自动拉「最新」。任何一次升级导致 digest 变化，都必须重新走一遍 12.5 的验证命令，因为「同 SHA 不同 digest」正是一次构建要消灭的情形 [R-12-1][R-12-5]。若平台需要整体替换，回滚路径是保留旧工作流文件一个观察窗口，而不是原地删掉——理由与第 13 章「蓝绿切流后保留旧版本」相同。

一条容易被忽略的过度工程警戒线：上表四个平台里，Tekton 0.x 与 Dagger 0.x 都不是本章示例，因为 `order-demo` 只有四个组件、一条主干，引入 K8s 原生流水线或构建图 SDK 的维护成本大于收益（见第 5 章工具选型方法论）。

**四平台迁移成本量化表**。选型矩阵回答「选哪个」，这张表回答「换一次要付多少」。口径：以「GitHub Actions → GitHub Actions」为 1× 基线，只计工作流语法重写、机密与变量、Runner 与网络、缓存与制品四类工作，不计业务代码；成本给相对比例与归因，不涉及任何单价 [R-12-2][R-12-3]。

| 迁移方向 | 工作流语法重写 | 机密与变量迁移 | Runner / 网络适配 | 缓存与制品仓库 | 相对总成本 | 主要归因 |
|---|---|---|---|---|---|---|
| GitHub Actions → GitHub Actions（基线） | 无 | 无 | 无 | 无 | 1× | — |
| GitLab CI/CD → GitHub Actions | 高：`.gitlab-ci.yml` 的 stage/rules 改为 jobs / needs / `if`，语义需逐条对译 | 中：CI/CD Variables 换成 Secrets，作用域（group / project / protected）需重挂 | 低：托管 runner 直接可用 | 中：内置 Container Registry 里的历史镜像需迁移或改推 | 约 2× | YAML 方言完全不同，规则求值顺序不等价 [R-12-2][R-12-3] |
| GitHub Actions → GitLab CI/CD | 高：同上反向 | 中：同上反向 | 中：需自建并运维 Runner（见下方自托管注意事项） | 中：同上反向 | 约 2× | 反向迁移；GitHub 的环境保护规则要在 GitLab 侧用 protected environments 重做 |
| Tekton 0.x → GitHub Actions | 中：`Task` 步骤展开为脚本，参数 / `Workspace` / 结果传递改为文件约定 | 中：集群内凭据改为仓库 Secrets | 低 | 高：PVC 工作区缓存改为 Actions cache，键策略重设计 | 约 2.5× | 声明式 CRD 展开为命令式脚本，工作区与结果语义变化最大 [R-12-3] |
| GitHub Actions → Tekton 0.x | 高：同上反向 | 低：凭据进 `Secret` 后由 `Workspace` 挂载 | 高：先要运维控制器与执行集群本身 | 高：同上反向 | 约 3× | 除重写外，还要从零建立集群内流水线的运维基线 |
| Dagger 0.x ↔ 任一托管平台 | 中：构建逻辑沉到脚本里，平台侧只留一个入口步骤 | 低：机密由 Dagger 引擎按需注入 | 低 | 低 | 约 1.5×–2× | 构建图与平台语法各翻译一次；迁移后「本地跑不过、CI 却过了」是否真的消失需重新验证 |

两条结论：其一，成本大头不在 YAML 语法而在**语义不等价**——规则求值顺序、机密作用域、缓存键设计，这些差异不会在迁移当天暴露，而是在第一个行为不一致的构建里暴露，所以任何迁移 PR 都必须重跑 12.5 的全部验证命令，特别是 12.5.1 的 digest 一致性对照；其二，这张表同时解释了为什么不建议频繁换平台：对一条主干、四个组件的项目，1×–3× 的一次性成本加上验证重跑，远大于换平台能带来的收益 [R-12-6]。

**自托管 Runner 的安全注意事项**（GitHub Actions 与 GitLab CI/CD 都提供这一选项，风险同构）。托管 runner 与自托管 runner 的本质区别是：前者每个 job 用完即焚，后者是**长期存活、握有内网凭据的主机**——一旦流水线执行了不可信代码（被篡改的第三方 Action、恶意 PR 的脚本），它就从「构建机」变成「内网跳板」[R-12-2][R-12-8]。最低要求六条：

1. **Ephemeral 化**：每个 job 用一次性容器或 VM 承载，注册令牌一次性下发、job 结束即注销销毁；禁止常驻 runner 复用工作目录——工作目录残留是上一条 job 泄漏给下一条 job 的最短路径。
2. **fork PR 不自动执行**：来自 fork 的 PR 默认不在自托管 runner 上触发，须维护者显式 approve 后才运行；`pull_request_target` 误用导致凭据外泄是公开复盘里的高频根因 [R-12-9]。
3. **不落长期凭据**：推送令牌走 12.4.1 的 OIDC 短期令牌；runner 主机不写入 `.docker/config.json` 长期凭据、不挂载生产 kubeconfig、不持有云厂商长期密钥。
4. **网络分段**：runner 只允许访问镜像仓库、依赖代理与测试数据库，用安全组或 NetworkPolicy 显式拒绝到生产网段的路由；验证方法是 `crane digest` 可通而 `kubectl -n order-demo-prod get pod` 不可通。
5. **主机最小化与定期重建**：非 root 运行、镜像只含构建必需工具、按固定周期重建——重建先走镜像构建与验证，与第 4 章「环境可重建」是同一逻辑。
6. **不混信任级别**：同一 runner 池不跨信任级别的仓库共用；`order-demo` 若自托管，runner 池只服务本仓库。

这六条与 12.6 的 `CL-S-02` 同源：自托管不是权限放宽的理由，反而是把「凭据最小化」从工作流层面下沉到主机层面的理由。

## 12.4 落地配置（完整可应用文件）

> 全部字段沿用配置契约：镜像 `registry.example.com/order-demo/<component>:git-<sha7>`、命名空间 `order-demo-dev` / `order-demo-staging` / `order-demo-prod`、公共标签 `app.kubernetes.io/*`、`version=git-<sha7>`。本章新增的是 CI 与晋升脚本，**不改动任何已冻结字段**。适用的 Kubernetes 版本为 1.32+（清单校验环节对接第 11 章的 kind 版本矩阵），工具小版本见附录 A。

**`.github/workflows/build.yml`** —— 唯一一次构建。全文只用了一个第三方 Action，并锁定到 40 位 commit SHA；其余步骤一律用 runner 自带命令，把供应链面压到最小。

```yaml
name: build-once

on:
  push:
    branches: ["main"]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

concurrency:
  group: build-${{ github.sha }}
  cancel-in-progress: false

env:
  REGISTRY: registry.example.com
  COMPONENT: gateway
  GO_VERSION: "1.23"

jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      # 锁定到上游 v4.2.2 的 commit SHA；升级由 hack/pin-actions.sh 显式发起
      - name: Checkout
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
        with:
          fetch-depth: 0
          persist-credentials: false

      - name: Derive immutable tag
        id: meta
        run: |
          SHA7="$(git rev-parse --short=7 "${GITHUB_SHA}")"
          echo "sha7=${SHA7}" >> "${GITHUB_OUTPUT}"
          echo "IMAGE=${REGISTRY}/order-demo/${COMPONENT}:git-${SHA7}" >> "${GITHUB_OUTPUT}"
          echo "tag=git-${SHA7}" >> "${GITHUB_OUTPUT}"

      - name: Setup Go
        run: |
          # runner 镜像已预装 Go 工具链（小版本见附录 A），只校验版本、不联网下载
          go version | grep -q "go${GO_VERSION}" || {
            echo "Go 工具链版本与附录 A 不一致，阻断构建"; exit 1;
          }

      - name: Lint
        run: |
          /usr/local/go/bin/go vet ./...
          test -z "$(gofmt -l cmd/)" || { echo "gofmt 未通过"; exit 1; }

      - name: Unit tests (no retry)
        run: /usr/local/go/bin/go test ./... -count=1 -timeout=120s

      - name: Integration validation (第 11 章四层校验)
        run: |
          ./hack/ci-validate.sh "${{ steps.meta.outputs.tag }}"

      - name: Build once
        run: |
          docker buildx build \
            --file docker/Dockerfile \
            --tag "${{ steps.meta.outputs.IMAGE }}" \
            --label "org.opencontainers.image.revision=${GITHUB_SHA}" \
            --provenance=false \
            --load .

      - name: Record digest
        id: digest
        run: |
          DIGEST="$(docker image inspect "${{ steps.meta.outputs.IMAGE }}" \
            --format '{{index .RepoDigests 0}}')"
          test -n "${DIGEST}" || { echo "未取得 digest，阻断"; exit 1; }
          echo "digest=${DIGEST}" >> "${GITHUB_OUTPUT}"
          printf '%s  %s\n' "${{ steps.meta.outputs.IMAGE }}" "${DIGEST}" \
            > artifacts.txt

      - name: OIDC short-lived registry token
        id: oidc
        run: |
          TOKEN="$(curl -fsS -H "Authorization: bearer ${ACTIONS_ID_TOKEN_REQUEST_TOKEN}" \
            "${ACTIONS_ID_TOKEN_REQUEST_URL}&audience=registry.example.com" \
            | python3 -c 'import sys,json; print(json.load(sys.stdin)["value"])')"
          echo "::add-mask::${TOKEN}"
          echo "token=${TOKEN}" >> "${GITHUB_OUTPUT}"

      - name: Push immutable artifact
        run: |
          echo "${{ steps.oidc.outputs.token }}" \
            | docker login "${REGISTRY}" -u oidc --password-stdin
          docker push "${{ steps.meta.outputs.IMAGE }}"
          docker logout "${REGISTRY}"

      - name: Publish artifact reference
        run: |
          {
            echo "### 本次唯一制品"
            echo ""
            echo '```'
            cat artifacts.txt
            echo '```'
          } >> "${GITHUB_STEP_SUMMARY}"
```

> 两处刻意设计：其一，`permissions` 只给 `contents: read` 与 `id-token: write`，不写 `packages: write` 之类的长期写权限，推送靠 OIDC 短期令牌完成，凭据脱敏由 `::add-mask::` 保证 [R-12-2][R-12-8]。其二，`Unit tests` 用 `-count=1` 明确禁用重试，把 12.2 的「本书观点」落到一行可 grep 的命令上。制品引用通过 `$GITHUB_STEP_SUMMARY` 写进运行摘要，因此全文只有一个第三方 Action；CL-12-02 会检查所有 `uses:` 是否锁定到 40 位 SHA。

**`hack/pin-actions.sh`** —— 把工作流里的 Action 从可变 tag 改写成 commit SHA，升级与回滚都走这个脚本产生的 PR。命令不内联任何第三方 URL，靠 `gh api` 解析。

```bash
#!/usr/bin/env bash
set -euo pipefail

WORKFLOWS=(".github/workflows/build.yml" ".github/workflows/validate.yml")
# repo:tag 对照表；新增 Action 时在这里登记，而不是在工作流里写 @vX
PINS=(
  "actions/checkout:v4.2.2"
)

resolve_sha() {
  local repo="$1" tag="$2" refsha objsha
  refsha="$(gh api "repos/${repo}/git/ref/tags/${tag}" --jq '.object.sha')"
  # 附注标签需要再解一层，拿到真正指向的 commit
  objsha="$(gh api "repos/${repo}/git/tags/${refsha}" --jq '.object.sha' 2>/dev/null || true)"
  if [ -n "${objsha}" ]; then
    echo "${objsha}"
  else
    echo "${refsha}"
  fi
}

for pin in "${PINS[@]}"; do
  repo="${pin%%:*}"; tag="${pin##*:}"
  sha="$(resolve_sha "${repo}" "${tag}")"
  case "${sha}" in
    ????????????????????????????????????????) ;;
    *) echo "解析 ${repo}@${tag} 未得到 40 位 SHA: ${sha}" >&2; exit 1 ;;
  esac
  for f in "${WORKFLOWS[@]}"; do
    sed -i -E \
      "s|uses: ${repo}@[^ #]+( *#.*)?|uses: ${repo}@${sha} # ${tag}|" \
      "${f}"
  done
  echo "pinned ${repo}@${tag} -> ${sha}"
done

echo "请检查 git diff 后提交，本脚本不会自动 commit。"
```

**`hack/promote-artifact.sh`** —— 按 SHA 晋升制品引用。全文没有 `docker build` / `buildx`，这是「不重建」最直接的证据。

```bash
#!/usr/bin/env bash
set -euo pipefail

usage() {
  echo "用法: $0 --from <env> --to <env> --sha <sha7>" >&2
  exit 2
}

FROM=""; TO=""; SHA=""
while [ "$#" -gt 0 ]; do
  case "$1" in
    --from) FROM="$2"; shift 2 ;;
    --to)   TO="$2";   shift 2 ;;
    --sha)  SHA="$2";  shift 2 ;;
    *) usage ;;
  esac
done

for v in "${FROM}" "${TO}" "${SHA}"; do
  [ -n "${v}" ] || usage
done
case "${TO}" in
  dev|staging|prod) ;;
  *) echo "未知目标环境: ${TO}" >&2; exit 2 ;;
esac
case "${SHA}" in
  ???????) ;;
  *) echo "SHA 必须是 7 位短 SHA: ${SHA}" >&2; exit 2 ;;
esac

COMPONENT="gateway"
REPO="registry.example.com/order-demo/${COMPONENT}"
IMAGE="${REPO}:git-${SHA}"
OVERLAY="deploy/overlays/${TO}"

# 前置一：制品必须已存在，且这一步绝不调用任何构建命令
command -v crane >/dev/null 2>&1 || { echo "缺少 crane，见附录 A" >&2; exit 1; }
DIGEST="$(crane digest "${IMAGE}")"
[ -n "${DIGEST}" ] || { echo "镜像不存在，禁止晋升: ${IMAGE}" >&2; exit 1; }
echo "制品引用: ${IMAGE}@${DIGEST}  (from=${FROM}, to=${TO}, 不重新构建)"

# 前置二：源环境与目标环境当前指向同一制品，避免把「配置差异」误当「产物升级」
FROM_TAG="$(kustomize build "deploy/overlays/${FROM}" \
  | grep -oE "image: ${REPO}:git-[0-9a-f]{7}" | head -n1 | awk -F: '{print $NF}')"
[ "${FROM_TAG}" = "git-${SHA}" ] || {
  echo "源环境 ${FROM} 当前为 ${FROM_TAG}，与待晋升 SHA 不一致" >&2; exit 1;
}

# 只改 image 的 tag，配置差异继续保留在各自 overlay 中
(
  cd "${OVERLAY}"
  kustomize edit set image "${REPO}=${IMAGE}"
)
kustomize build "${OVERLAY}" > "/tmp/rendered-${TO}.yaml"
grep -q "image: ${IMAGE}" "/tmp/rendered-${TO}.yaml"
! grep -qE 'image:.*:latest' "/tmp/rendered-${TO}.yaml"

git add "${OVERLAY}"
git commit -m "promote(order-demo): ${COMPONENT} git-${SHA} -> ${TO} [skip ci]"
echo "OK: ${TO} 已指向 ${IMAGE}，请推送后由第 14 章的控制器同步到集群。"
```

> `[skip ci]` 不是偷懒，而是关键：晋升只改引用，如果因此又触发一次流水线，就同时违反「一次构建」和「引用不重建」两条判据。第 14 章会由 GitOps 控制器消费这次提交，CI 与 CD 在这里明确分工。

### 12.4.1 OIDC 短期令牌：仓库侧信任配置与 `id-token: write` 的边界

`build.yml` 里那两行 `id-token: write` 与 `audience=registry.example.com` 背后是一条完整的信任链。值得拆开讲透，因为配错方向时失败是**静默的**：仓库可能继续接受旧口令，你以为 OIDC 已生效，实际推送走的是另一条长期凭据路径——日志里看不出差别，审计时才发现 [R-12-2]。

**信任链三要素**。镜像仓库作为资源方，回答三个问题才能把令牌换成权限：

| 要素 | `order-demo` 的值 | 配错会发生什么 |
|---|---|---|
| issuer（谁签发的） | GitHub Actions 的 OIDC 签发方 URL（job 运行时由 `ACTIONS_ID_TOKEN_REQUEST_URL` 对应签发方给出） | issuer 写错 → 仓库拒绝全部令牌，推送永远 401，流水线在推送步停住 |
| audience（给谁用的） | `registry.example.com`（请求令牌时在查询参数里指定） | 复用默认 audience → 该令牌可被其他同样信任 issuer 的服务接受，攻击面扩大 [R-12-8] |
| subject 绑定（谁有权拿） | `repo:<org>/order-demo:ref:refs/heads/main`（限定仓库 + 主干分支 + 工作流文件路径三元组） | 绑定过宽（如整个 org）→ 任何能改任意工作流的人都能自取推送权限 [R-12-2] |

仓库侧的信任策略由这三要素构成，内容为：**登记 issuer URL 与 audience；声明只接受匹配三元组的 subject；subject 到权限的映射限定为 `order-demo/*` 仓库命名空间内的 push 与 pull；令牌有效期以签发方 `exp` 声明为准（分钟级），job 结束即作废**。各支持 OIDC 的镜像仓库字段名不同、语义一致，具体字段以你的仓库实现为准——把这份语义清单拿去逐字段核对，比抄任何一份厂商示例更不容易配错。

**验证命令**（在 job 内或本地复现，验证的是令牌内容而非假设）：

```bash
# 取 ID token 并解开 payload，逐项核对 iss / aud / repository / ref
TOKEN="$(curl -fsS -H "Authorization: bearer ${ACTIONS_ID_TOKEN_REQUEST_TOKEN}" \
  "${ACTIONS_ID_TOKEN_REQUEST_URL}&audience=registry.example.com" \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["value"])')"
python3 - "$TOKEN" <<'PY'
import sys, base64, json
payload = sys.argv[1].split(".")[1]
payload += "=" * (-len(payload) % 4)
claims = json.loads(base64.urlsafe_b64decode(payload))
assert "token.actions." in claims["iss"], claims["iss"]  # iss 应为 GitHub Actions 的 OIDC 签发方
assert "registry.example.com" in str(claims["aud"]), claims["aud"]
assert claims["repository"] == "your-org/order-demo", claims["repository"]
assert claims["ref"] == "refs/heads/main", claims["ref"]
print("OIDC claims 校验通过:", claims["sub"])
PY
```

通过标准：输出 `OIDC claims 校验通过`，且打印出的 `sub` 与仓库侧信任策略绑定的 subject **逐字符一致**；任一断言失败都说明信任链错位，先修绑定再谈推送。这个脚本应作为一次性 job 收进流水线，在首次接入镜像仓库时跑一遍并留存输出。

**`id-token: write` 的边界**。这个权限比它看起来窄得多，也宽得多：

- **窄**：它只允许工作流向签发方请求 ID token，本身不授予仓库、包或集群的任何写权限。删掉这一行，`build.yml` 里所有推送逻辑立刻失效。
- **宽**：真实的授权边界不在 GitHub 侧，而在**仓库侧信任策略 subject 绑定的粒度**——绑定越宽，能自取推送令牌的人越多。攻击者不需要拿到任何机密，只需要能改一个工作流文件，就能自己写一步「取令牌 + 推镜像」[R-12-2]。
- **收缩边界的三个动作**：subject 绑到「仓库 + 分支 + 工作流文件路径」三元组；推送 audience 单独设值、不复用默认值；镜像仓库侧对 `order-demo/*` 命名空间再挂一层推送白名单。三者叠起来之后，即使工作流被篡改，篡改者也推不出一个能通过第 24 章验签门禁的镜像。

**与第 26 章的分工**。OIDC 在本书出现两次，语义不同，不要混配：

| | 本章（12.4.1） | 第 26 章 |
|---|---|---|
| 方向 | CI runner → 镜像仓库 | 集群内工作负载 → 密钥后端 / 云 API |
| 凭据形态 | 流水线 job 的 ID token | 工作负载 Service Account 的身份令牌 |
| 信任主体 | 镜像仓库的 OIDC 信任策略 | 密钥后端 / 云端的 workload identity 绑定 |
| 生命周期 | 单个 job 结束即失效 | Pod 生命周期内随凭据轮换 |
| 本章是否落地 | 是（`build.yml` 推送步） | 否，完整配置与 RBAC 最小化在第 26 章 |

两边如果共享同一个 audience，审计日志将无法区分「谁在什么时候推了镜像」与「谁在什么时候读了密钥」——这也是 audience 按用途拆分的另一个原因。本章不配集群侧 workload identity，第 26 章不重复讲推送令牌，互为分工 [R-12-8]。

### 12.4.2 流水线的完整设计：每一步的门禁与产物

12.2 的阶段表回答的是「顺序为什么这样排」；本节把每一步补齐两列——**门禁**（失败即停的可执行判据）与**产物**（这一步必须留下的可审计证据）。判定一条步骤是否该存在的标准只有一条：它的产物要么是下一阶段的输入，要么是复盘时的证据，两者都不是的步骤没有存在价值 [R-12-6]。

| 阶段 | 门禁（失败即停） | 产物 | 产物被谁消费 |
|---|---|---|---|
| lint | `go vet` / `gofmt` 非零退出 | 无（退出码即结果） | 无下游，纯门禁 |
| 单测 | `-count=1` 任一用例失败，不重跑 | 测试报告 artifact（按固定窗口保留） | 复盘证据、质量趋势 |
| 集成测试 | 第 11 章四层任一关失败 | 渲染产物 `rendered-*.yaml` | 第 10、14 章 review 渲染产物而非模板 |
| 校验 | 制品清单缺 `sha256:` 或含 `latest` | 制品清单（含 digest） | 推送与晋升的引用来源 |
| 构建 | 同一 `git-<sha7>` 已有不同 digest → 阻断；基础镜像按 digest 显式固定 | 镜像 + digest + `artifacts.txt` + revision 标签 | 推送、晋升（第 14 章）、签名（第 24 章） |
| 扫描 | HIGH/CRITICAL 且上游有修复版 → 阻断 | 扫描报告 artifact | 复盘证据；第 24 章准入对照的构建期来源 |
| 推送 | 推送凭据非 OIDC 短期令牌 → 阻断；推送后 `crane digest` 复核与本地记录一致 | 仓库中的不可变制品 + 运行摘要里的制品引用 | 第 14 章晋升的唯一输入 |
| 签名（接口） | 未签名引用不得进入 prod（实现与验签门禁见第 24 章） | 按 digest 的签名对象 | 第 24 章准入验签 |

三处设计说明。

**扫描卡在推送之前**。一旦推送，扫描就拦不住任何东西了：制品已经是仓库里的不可变对象，晋升与部署会把漏洞带进每个环境。这与 12.2「校验在构建之前」是同一条 fail-fast 逻辑——越晚发现的错误越贵 [R-12-6]。`build.yml` 接入最小扫描步（不用第三方 Action，用官方 trivy 镜像执行；镜像版本与 digest 锁定值记入附录 A，纪律与 Action 锁 SHA 相同）：

```diff
       - name: Build once
         run: |
           docker buildx build \
             --file docker/Dockerfile \
             --tag "${{ steps.meta.outputs.IMAGE }}" \
             --label "org.opencontainers.image.revision=${GITHUB_SHA}" \
             --provenance=false \
             --load .

+      - name: Vulnerability scan (gate before push)
+        run: |
+          docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
+            aquasec/trivy:0.58 image \
+            --exit-code 1 \
+            --severity HIGH,CRITICAL \
+            --ignore-unfixed \
+            "${{ steps.meta.outputs.IMAGE }}"

       - name: Record digest
```

两个参数都有决策含义：`--ignore-unfixed` 把「上游根本没有修复版」的历史 CVE 与「可修复但没修」区分开——前者会让流水线永久红、逼团队把门禁整个关掉，后者才是门禁真正要拦的；豁免走 `.trivyignore` 进 Git、经 PR 评审，禁止用 CI 变量偷偷豁免（与公理 5「变更只走 Git」同源）。

**签名是接口而不是本章实现**。签名的对象是 digest 而不是 tag [R-12-5]，且签名动作必须在推送之后——签名要把签名对象作为仓库附注写回 registry，此时制品才在仓库里有可挂签名的位置。本章流水线的职责边界是「产出待签名的 digest 清单」；cosign 的密钥形态、验签门禁与准入策略在第 24 章完整落地（本章不重复）。若止步于本章，12.4.1 收缩的信任边界仍留一个洞：任何能通过仓库认证的主体都能推一个「内容合法但不是流水线产出」的镜像，第 24 章的验签门禁正是补这个洞。

**每一步的产物都要有留存约定**。测试报告与扫描报告按固定窗口保留为 job artifact，渲染产物按环境命名——复盘 12.5.1 那类「同标签不同 digest」时，第一件事就是打开对应 SHA 的运行页核对 `artifacts.txt`；产物没有留存约定，证据链在事发前就断了 [R-12-1]。

### 12.4.3 构建速度与缓存：快和稳是同一个决策

缓存不是性能装饰。12.1 合成案例里 digest 分歧的根源之一就是「两条流水线的缓存状态不同」；反过来，构建慢到让团队觉得麻烦，就会自己发明「每个环境再构建一遍」的旁路。所以「快」和「稳」必须放进同一组决策。

| 缓存对象 | 机制 | 失效条件 | 何时不该用 |
|---|---|---|---|
| 层缓存 | BuildKit 按指令与内容逐层复用 | 前置层任一字节变化，其后全部失效 | 没有可信缓存来源时不要乱配 `--cache-from`（缓存投毒路径，见下） |
| 依赖缓存 | `--mount=type=cache` 挂载 module / build 缓存目录 | 内容寻址，依赖清单不变即命中 | 单机、构建分钟级以内时收益甚微 |
| 远程缓存 | `--cache-from/--cache-to type=registry`，`mode=max` 连中间层一起推 | 缓存 ref 被覆盖即失效 | 构建 1–2 分钟就完成的仓库：额外的推送/拉取可能比省下的还多 |
| 多架构构建 | `buildx --platform` 多目标 | 目标平台基础镜像或交叉编译工具变化 | 集群节点只有 amd64 时，arm64 产物纯属浪费（节点池见第 18 章） |

两个落地配置。其一，Dockerfile 用缓存挂载承接依赖缓存，`COPY go.mod go.sum` 放在源码之前，保证源码改动时依赖层仍命中：

```dockerfile
# syntax=docker/dockerfile:1.7
FROM golang:1.27 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go mod download
COPY cmd/ cmd/
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -o /out/gateway ./cmd/gateway
```

其二，`build.yml` 的 Build once 步接 registry 远程缓存，让下一条流水线（含不同 runner 实例）能复用中间层：

```diff
           docker buildx build \
+            --cache-from type=registry,ref=${REGISTRY}/order-demo/${COMPONENT}:buildcache \
+            --cache-to type=registry,ref=${REGISTRY}/order-demo/${COMPONENT}:buildcache,mode=max \
             --file docker/Dockerfile \
             --tag "${{ steps.meta.outputs.IMAGE }}" \
```

`buildcache` 是可变标签，但它**不是制品引用**：任何 overlay、任何 Deployment 都不得引用它，读写权只属于流水线，与 `git-<sha7>` 制品标签分属两种语义。缓存标签的可变性与公理 2 不冲突——公理 2 约束的是部署引用，缓存只影响构建输入。

三条边界必须写清：

**缓存救不了「重构建等价」**。缓存只让同一条流水线更快，不保证两条缓存状态不同的流水线产出相同字节。消灭 12.5.1 那类分歧的根本手段是**基础镜像按 digest 固定**（`FROM` 写成 `镜像:版本@sha256:…`，升级走显式 PR），而不是指望缓存状态恰好一致 [R-12-4]。

**远程缓存是信任边界**。`--cache-from` 等于「把别人产出的中间层当自己的构建输入」：缓存 ref 可被任何有推送权的人覆盖，恶意层可借缓存进入你的镜像而源码干净。缓存 ref 必须与本制品同仓库同命名空间，并纳入 12.4.1 的推送白名单；接受社区 `cache-from` 之前，先回答「谁的中间层我愿意信任」。

**多架构在 `order-demo` 是可选项**。QEMU 仿真构建慢数倍且更难排障，本章示例保持单架构 `--load`。何时开：集群出现 arm64 节点池且需要真实调度 arm64 负载（第 18 章）时再开，并优先用交叉编译（`GOARCH` + `COPY --from=$TARGETPLATFORM`）替代纯仿真。

### 12.4.4 密钥分层、环境隔离与 fork PR 的凭据边界

12.4.1 讲透了「CI → 仓库」这一条信任链；本节补全 CI 侧密钥的另外两个边界：**密钥放哪一层**，以及**不可信代码（fork PR）能碰到哪一层**。

**密钥三层分级**，判据是「谁能读到它、泄漏后影响多大」：

| 层 | 形态 | 谁能读 | 放什么 |
|---|---|---|---|
| 仓库级 Secrets | 静态存储 | 本仓库任意分支的工作流 | 只放价值最低的凭据（依赖代理只读令牌） |
| 环境级 Secrets | 静态存储 + 保护规则（必选审批人、限定分支） | 通过环境保护规则的 job | 环境专属凭据（演练集群只读 kubeconfig） |
| OIDC 动态凭据 | 不存储、job 级生命周期 | subject 绑定匹配的 job | 推送令牌（12.4.1） |

原则只有一句：**能换成 OIDC 的全部换掉，静态存储的每一把都要能回答「它为什么不能不存」**——静态密钥的价值随存储数量线性贬值，审计面随数量线性增大 [R-12-8]。需要把某个 job 提权时，用环境而不是加 Secrets：

```yaml
jobs:
  build:
    runs-on: ubuntu-24.04
    environment: ci-build   # 仓库设置里绑定 required reviewers + 限 main 分支
```

保护规则本身在仓库设置页配置，本节只约束工作流语法；「环境 + 审批」的思想在第 26 章会落到集群侧 RBAC。

**fork PR 的凭据边界**。两种 PR 触发方式的语义差异是本节的根源：

| | `pull_request` | `pull_request_target` |
|---|---|---|
| 工作流定义取自 | PR 的 merge commit | 基分支 |
| Secrets | fork PR 不可读 | 可读 |
| `id-token` | fork PR 不签发 | 可签发 |
| 结论 | fork PR 只能跑无凭据校验 | 任何一步 checkout PR head 并执行其中脚本，攻击者代码即获得全部凭据 [R-12-2][R-12-9] |

`pull_request_target` 本身不是漏洞——工作流定义来自基分支，贡献者改不了它；出事的是典型误用：「想给贡献者的代码跑点特权步骤，于是在 `pull_request_target` 里 checkout PR head 再执行其中脚本」。这时攻击者的脚本运行在持有 Secrets 与 OIDC 签发权的上下文里，`::add-mask::` 与最小 `permissions` 都救不回来 [R-12-9]。`order-demo` 的规则固化成两句话：`validate.yml` 只用 `pull_request`（当前已是），fork PR 的校验永远无凭据；需要凭据的步骤拆成两段——先无凭据跑完校验，维护者 approve 后再在带环境保护规则的 job 里执行，两段之间只传递数据（制品引用、报告文件），不传递凭据。

**runner 自带的最后一道**：`GITHUB_TOKEN` 每个 job 自动签发、job 结束作废，权限由 `permissions` 块收缩（12.4 已做到最小）；checkout 的 `persist-credentials: false` 防止仓库令牌残留在 `.git/config` 被后续步骤读到。这两处零成本默认值，是「不写长期凭据」在工作流语法层的最后落点 [R-12-2]。

## 12.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（仓库根目录执行；需 `git` / `docker` / `crane` / `kustomize` / `kubectl` / `kind`，版本见附录 A）：

```bash
chmod +x hack/promote-artifact.sh hack/pin-actions.sh
./hack/pin-actions.sh && git diff -- .github/workflows/
git commit --allow-empty -m "test ci" && git push origin main
# 等 build-once 结束后，记录流水线产出的 sha7 与 digest
SHA7="$(git rev-parse --short=7 HEAD)"
crane digest "registry.example.com/order-demo/gateway:git-${SHA7}"
# 晋升到 staging，确认没有第二次构建
./hack/promote-artifact.sh --from dev --to staging --sha "${SHA7}"
git log -3 --oneline
kustomize build deploy/overlays/staging | grep 'image:'
./hack/verify.sh
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 唯一制品 | `crane digest` 返回一个 `sha256:`，且一次 push 只产生一条 `build-once` 运行记录 |
| 标签可追溯 | image 为 `registry.example.com/order-demo/gateway:git-<sha7>`，与 `git rev-parse --short=7 HEAD` 一致，无 `latest` |
| 环境等价 | dev / staging / prod 的 `image` 字段**完全相同**；`kustomize build` 的 diff 只含配置差异 |
| 未二次构建 | `git log` 里晋升提交含 `[skip ci]`，晋升后没有新的 `build-once` 运行 |
| 凭据安全 | 构建日志无明文口令，工作流 `permissions` 无长期写权限（CL-S-02） |
| 回归可用 | `hack/verify.sh` 的 `/healthz` 返回 200，根路径 `version` 与镜像标签一致 |

**回滚命令 / 步骤**（先演练、后发布）。本章的回滚对象是**制品引用**，不是集群里的 Pod：把目标环境的 `image` 指回上一个已知良好的 SHA，且这个动作同样必须回到 Git，不能在生产上 `kubectl set image`（全书公理 5，见第 3 章）。

```bash
PREV="<上一个已验证的 sha7>"
# 方案 A（推荐，生产唯一合法路径）：用同一个晋升脚本回退引用，不重建
./hack/promote-artifact.sh --from dev --to staging --sha "${PREV}"
git push origin main
# 由第 14 章的控制器同步；此处不执行任何 kubectl 写命令

# 方案 B（仅本地 kind 演练）：直接把 image 指回已知良好的 SHA
kubectl -n order-demo-dev set image deployment/gateway \
  gateway="registry.example.com/order-demo/gateway:git-${PREV}"
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s
```

> **为什么方案 A 更可靠**：`kubectl set image` 改的是集群里的一次性事实，Git 没变，下一次控制器同步会把它改回去（第 14 章）；而回退引用改的是真相源，所有环境、审计与后续发布都基于同一个声明。方案 B 只用于让读者在本地看清字段变化，对象是一次性 kind 集群，不构成对公理 5 的例外。若整个工作流改动导致构建行为异常，兜底是 `git revert <工作流 commit>`，再重跑验证命令——这与第 6 章「方案 B 精确表达意图」是同一条逻辑。

**回滚验证**：

```bash
kustomize build deploy/overlays/staging | grep 'image:'
# 期望为 git-<PREV>，且与 dev 当前引用一致
crane digest "registry.example.com/order-demo/gateway:git-${PREV}"
./hack/verify.sh
kubectl -n order-demo-dev get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

通过标准：目标环境 `image` 回到 `git-<PREV>`；`crane digest` 返回的 digest 与该 SHA 首次构建时记录的 `artifacts.txt` 一致（证明「退回的是同一份产物」，而不是同名的新层）；`/healthz` 仍为 200。**没有在 staging 演练过引用回退，就不允许进入第 13 章的发布策略选择**（CL-G-07）。

### 12.5.1 定位演练：基础镜像更新导致 staging / prod 同标签不同 digest

12.1 的合成案例停在「谁也拿不出 staging 验过的 digest」。这一节把那个夜晚的定位过程完整走一遍——它是上面验证命令的实战形态，也是 `CL-12-01` 与通用项 `CL-G-02` 的失败处置现场。**再次声明：合成案例，非真实事件，下列 digest 均为演练构造** [R-12-9]。

背景回顾（合成）：基础镜像 `docker.io/library/alpine` 当天发布新层；`order-demo` 曾遗留一条 prod 专用流水线，缓存未命中导致它拉到新基础镜像并二次构建，**用同一个 `git-a1b2c3d` 标签覆盖推送**。staging 上验证的是旧 digest，prod 跑的是新 digest，标签完全一致。

**第 0 步：冻结现场，只取证据，不做任何写操作**：

```bash
# 取三个环境当前声明的镜像引用（只读）
for ns in order-demo-dev order-demo-staging order-demo-prod; do
  kubectl -n "${ns}" get deploy api \
    -o jsonpath="{.spec.template.spec.containers[0].image}{'\n'}"
done
```

三行输出都是 `registry.example.com/order-demo/api:git-a1b2c3d`——标签一致。**到此为止不能下任何结论**：标签一致只说明三个环境「想跑」同一份，digest 才说明是不是「真的」同一份 [R-12-5]。

**第 1 步：取各环境实际运行中的 digest**。集群侧的真相藏在 Pod 的 `imageID` 里，它记录的是控制平面实际拉取的那份内容的 digest：

```bash
for ns in order-demo-dev order-demo-staging order-demo-prod; do
  kubectl -n "${ns}" get pod -l component=api \
    -o jsonpath="{${ns}:}{.items[0].status.containerStatuses[0].imageID}{'\n'}"
done
```

**第 2 步：取仓库当前的 digest 作基准**：

```bash
crane digest registry.example.com/order-demo/api:git-a1b2c3d
```

**第 3 步：对照表**（合成数据，`…` 表示省略的中间位）：

| 对照点 | 取证命令 | 结果（合成数据） | 判定 |
|---|---|---|---|
| dev 实际运行 digest | 第 1 步命令（dev） | `sha256:1111…` | 与构建记录一致 |
| staging 实际运行 digest | 第 1 步命令（staging） | `sha256:1111…` | 与 dev 一致 → staging 验过的就是这份 |
| prod 实际运行 digest | 第 1 步命令（prod） | `sha256:2222…` | **与 staging 不同** → 「环境等价」判据被破坏 |
| 仓库当前 digest | 第 2 步 `crane digest` | `sha256:2222…` | 等于 prod 那份 → prod 的构建**后推**并覆盖了 tag |
| 首次构建记录（CI 运行摘要 / `artifacts.txt`） | 打开本次 SHA 的 build-once 运行页 | `sha256:1111…` | 与仓库不符 → 存在用同一标签的**第二次推送** |

**第 4 步：判定链**。dev、staging、首次构建记录三方一致，可以排除「构建本身不可复现」；分歧集中在 prod 与仓库侧，指向**第二条流水线在 prod 环境重跑了一次 build 并覆盖推送**——正是 12.1 反模式一的实物形态，而非基础镜像更新本身的错（基础镜像更新只是让两条流水线的产物可区分了）。

**第 5 步：止血**。回退引用走 Git，不碰集群（公理 5；命令即 12.5 方案 A，`promote-artifact.sh` 本就支持 `--to prod`）：

```bash
PREV="<上一次已验证的 sha7，取自 12.5 的回滚演练记录>"
./hack/promote-artifact.sh --from dev --to prod --sha "${PREV}"
git push origin main
# 由第 14 章的控制器同步；rollout 完成后复核 digest 归位
kubectl -n order-demo-prod get pod -l component=api \
  -o jsonpath='{.items[0].status.containerStatuses[0].imageID}{"\n"}'
```

通过标准：prod 的 `imageID` 回到首次构建记录中的 `sha256:1111…`，故障现象消失。若回退后故障仍在，说明根因不在制品而在配置或数据面，按第 23 章的 runbook 另起排查，不要继续在镜像上打转。

**第 6 步：根因消除**（止损之后必须做完，否则下一次推送还会覆盖）：

1. 删掉 prod 那条独立流水线，触发条件收敛为 12.4 的 `on.push.branches: ["main"]`（`CL-12-01` 的失败处置）。
2. 在镜像仓库侧开启「同标签不可变推送」禁令，让第二次同名推送在仓库层直接失败——把「靠纪律」变成「靠门禁」，与不可变镜像口径一致（见第 3、6 章）。
3. 把本节对照表存入事故记录：今后任何「staging 是好的、prod 不对」类故障，第一张表就是它。

**沉淀**。这次演练固化成一条可 grep 的纪律：**任何发布比对都从 `imageID` 与 `crane digest` 出发，不从标签出发**。digest 是内容标识、标签是可变指针 [R-12-5]；SLSA 对制品来源与完整性的要求，落到值班现场就是这张五行对照表 [R-12-1]。
