## 29.1 问题与反模式：90% 的人不需要自己写，那现成的怎么挑

第 27 章的结论是「多数团队不写 Operator」，第 28 章把少数要写的人带过深水区。现在轮到大多数人会遇到的决策：**现成的 Operator 值不值得引入，怎么评估「靠不靠谱」，以及它挂了业务会不会跟着挂？**

**合成案例**（教学合成，非真实事件）：一个团队按「功能最全、star 最多」挑了数据库 Operator 装上。半年后集群升级，CRD 从 `v1alpha1` 跳到 `v1beta1` 却无转换路径，存量实例读不出来；卸载时 CR 挂着 finalizer 卡在 `Terminating`、PVC 残留。控制器告警、升级、备份演练更从装上起无人负责，直到它静默挂掉、主库故障才发现故障转移没触发 [R-29-1][R-29-4][R-29-7][R-29-12]。

三个反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：只看功能 / star 就引入。** 现象是升级时存量对象无处可去；根因是漏掉升级路径、活跃度、卸载残留这些半年后才显形的维度。替代做法是把它们写进评估表逐项打分，升级路径没结论就不许引入 [R-29-1][R-29-8][R-29-12]。

**反模式二：没做卸载演练。** 现象是 finalizer 卡住、PVC 残留；根因是把「装」当成可逆的，从没验证过「退」。本章把它变成可执行脚本与上线门禁 [R-29-4][R-29-12]。

**反模式三：把 Operator 当「装了就有人管」。** 现象是控制器自身告警与升级无人负责，它挂了业务静默降级；根因是没把它当「会挂、要升级、要有 runbook 的服务」。替代做法是纳入平台运维清单：健康告警、升级复评、备份演练、降级预案四项齐备 [R-29-7][R-29-8]。

以上反模式的**方法论**参照公开 Operator 升级事故复盘 [R-29-12]；该来源只支撑「这类失效模式确实存在」，不证明合成案例真实发生。

## 29.2 范式与决策树：先回答「它挂了，业务会不会挂」

**成熟度评估的六个维度**（本章判据表的骨架）：维护活跃度、升级策略、备份、可观测、降级预案、社区治理。它们各自对应一个「半年后才会显形」的问题，而不是装完当天能看见的功能 [R-29-8]：

| 维度 | 要回答的问题 | 可验证的证据 |
|---|---|---|
| 维护活跃度 | 近几个周期有没有 release、issue 有没有人回 | 发行说明、提交历史、issue 响应 |
| 升级策略 | CRD 版本怎么迁、控制器与实例谁先升 | 官方升级文档里的版本兼容矩阵 |
| 备份 | 能不能恢复到**新集群**，而不只是「任务绿了」 | 声明式 Backup / ScheduledBackup + 恢复演练报告（见第 16 章） |
| 可观测 | 控制器自己有没有指标与告警 | 指标端点 + 平台方补的告警规则（见第 22 章） |
| 降级预案 | 控制器不可用时业务能撑多久、谁接管 | 停用控制器演练记录 + 分级动作表 |
| 社区治理 | 有没有明确维护者、贡献流程与项目成熟度 | 治理文件与项目分级（沙箱 / 孵化 / 毕业）[R-29-8] |

**「Operator 挂了业务会不会挂」必须先回答**。多数现成 Operator 把**数据面**（Pod、Service、PVC）与**控制面**（控制器）解耦：控制器停掉后实例继续运行，业务不立刻 500；但故障转移、备份、升级、漂移纠正全部停摆——**业务没挂，恢复能力归零** [R-29-1][R-29-10]。可验证动作：把控制器缩到 0，看实例是否继续服务、主库故障是否无人接管（29.5）。这决定降级预案的分级。

**决策树**（判断一个现成 Operator 能不能进试点）：

```
有没有一个现成 Operator 覆盖这个领域？                  否 → 回第 27 章五选一，不引入 CRD
        │ 是
八个评估维度是否全部有结论（含「不通过」）？            否 → 停在评估，禁止装
        │ 是
加权得分是否达到通过线？                                否 → 换候选或自建，不许「先装上再说」
        │ 是
升级路径 / 备份恢复 / 卸载残留三项是否各演练过一次？     否 → 补演练，否则不许进 staging [R-29-4]
        │ 是
「停用控制器」演练是否证明了业务影响面？                否 → 补降级预案，否则不许进 prod
        │ 是
控制器自身告警、升级复评、责任人是否写进平台运维清单？   否 → 回 29.1 反模式三
        │ 是
→ 允许进入受限试点；生产替换仍走第 14 章 GitOps 晋升链
```

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：评估现成 Operator，必须回答「**它挂了业务会不会挂**」，并把答案写成分级降级预案；引入与否按**故障恢复能力**决定，不按功能清单或技术偏好。
>
> **论证**：Operator 的价值不在「装起来」，而在「主库挂了，谁能恢复且数据不丢」。数据面与控制面解耦让「控制器挂了业务不立刻挂」成为常态，反而最危险——监控一片绿，恢复能力却归零。所以评估表把「备份能否恢复到新集群」「卸载是否无残留」「停用控制器后谁接管」与功能放在同等甚至更高权重。L1 只支撑架构解耦这一事实 [R-29-1][R-29-10]。
>
> **反例与适用前提**：这不等于「所有 Operator 都要配人工接管」。证书轮换这类**不影响在线流量**的，预案只需「暂停签发、告警、等修复」；数据库这类**恢复能力关系数据不丢**的，才需分级接管与备份兜底。前提是具备第 16 章恢复能力；连 `StatefulSet` 恢复都没跑通的团队，引入 Operator 只是把不会的事藏到抽象后面 [R-29-5]。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：自建 / 采购 / 托管的取舍按「谁承担故障恢复与升级」，不按「喜不喜欢用 K8s 管一切」。
>
> **论证**：三者差异不在功能表，而在责任归属：自建换来自主权，但要自己背控制器升级、CRD 迁移与值班；采购把部分责任转给供应商，代价是锁定与成本；托管把实例层责任整体转出，代价是可控性。决策输入应是四个可回答的问题——SLO 内能否恢复、是否演练过、是否有人懂协调循环、预案是否成文——而非技术审美。
>
> **反例与适用前提**：这不等于「小团队一律不许自建」。有成熟平台能力、需跨环境一致交付的团队自建反而最可控；20 人团队若无专人维护 CRD，托管几乎总是更优。前提是**存在多人协作、跨环境晋升的变更**；一次性本地实验不在此列。

## 29.3 工具选型：成熟度评估表与横向对照

按 `book/decisions.md`，**PostgreSQL 是全书有状态示例；第 16 章先用原生 `StatefulSet` 讲迁移范式，CloudNativePG 1.x 是第 29 章的评估对象**。本章不把 `order-demo-prod` 的 `db` 切到 Operator、不推翻 `case-evolution.md` 的配置契约（SP-03/16）；评估结论只决定「值不值得进入受限试点」。工具主版本在此出现，小版本锁附录 A。

**Operator 成熟度评估表**（评估项 / 权重 / 通过标准 / 何时不该用 / 回滚方式；加权规则：通过计满分、条件通过计半分、不通过计 0 分，总分 ≥ 80% 才允许进入试点）：

| 评估项 | 权重 | 通过标准 | 何时不该用 | 回滚方式 |
|---|---|---|---|---|
| 维护活跃度 | 5 | 有持续 release、issue 有响应、维护者可数 | 近几个周期无 release、issue 无人回 | 不引入；已引入则换候选 |
| 升级策略（CRD 版本迁移） | 5 | 有版本兼容矩阵、转换 webhook 路径、控制器与实例升级顺序 | 只有单版本 CRD、升级要手工改存量对象时 | 按第 28 章 28.2 五步逆序回退 |
| 备份恢复 | 5 | 声明式 Backup / ScheduledBackup，且能恢复到**新集群** | 备份只能原地覆盖、无恢复演练时 [R-29-4] | Velero 1.x 恢复到新集群兜底（见第 16 章） |
| 卸载残留 | 4 | 先删 CR 实例 → finalizer 清空 → PVC 按保留策略处置 → 删 CRD | 从未演练过卸载、finalizer 文档缺失时 | 按 29.4 脚本逐项检查后回退 |
| 自身可观测 | 4 | 暴露控制器指标，平台方补告警与 runbook [R-29-7] | 控制器无指标、告警无 runbook 时 | 补告警规则，或退回自建 |
| 降级预案 | 5 | 「停用控制器」演练已跑，分级动作与责任人成文 | 答不出「它挂了业务会不会挂」时 | 按 `docs/operator-degradation-plan.md` 执行 |

**Strimzi / cert-manager 简要对照**（都只作对照，不是本章评估对象）[R-29-2][R-29-3]：

| 工具（主版本） | 管什么 | 相对 CloudNativePG 1.x 的差异 | 何时不该用 |
|---|---|---|---|

**`docs/operator-degradation-plan.md`**（降级预案模板，完整成文）：

```markdown
# Operator 降级预案（CloudNativePG 1.x 受限试点）

## 1. 触发条件
- 控制器连续 10 分钟无成功 reconcile（告警 OperatorNoSuccessfulReconcile）。
- 升级后 CRD 版本不兼容、控制器 CrashLoopBackOff。
- 控制器镜像验签失败（第 24 章供应链门禁）。

## 2. 影响面判断（先回答「业务会不会挂」）
- 已收敛的 Postgres 实例继续服务：数据面不依赖控制器常驻。
- 停摆的能力：故障转移、备份、升级、漂移纠正、新实例创建。
- 结论：SLO 内可维持在线读写，但恢复能力归零；按第 20 章错误预算冻结非必要发布。

## 3. 分级动作
| 级别 | 现象 | 动作 | 时限 | 责任人 |
|---|---|---|---|---|
| L0 观察 | 控制器告警但实例健康 | 保留流量、修复控制器；禁止升级 / 备份 / 扩缩容操作 | 30 分钟 | 平台值班 |
| L1 降级 | 控制器不可用 > 10 分钟 | 控制器副本缩到 0 冻结误动作；业务维持只读或现状；人工接管故障转移 | 15 分钟 | 平台 + DBA |
| L2 接管 | 主库故障且控制器无法转移 | 按第 16 章备份恢复到新集群 / 手工提升备库，再切流 | 按恢复点目标 | DBA |

## 4. 回滚路径
- 控制器版本回退：helm rollback <release> <rev>，或 git revert 升级 PR + argocd app sync --prune。
- CRD 版本逆向：按第 28 章 28.2 五步逆序。
- 业务侧兜底：Velero 1.x 从最近一次 Completed 备份恢复到新集群（见第 16 章）。

## 5. 演练与复评
- 每季度一次「停用控制器」演练；每次控制器升级前追加一次。
- 演练报告归档到发布 PR，未演练过的降级预案不算预案。
```
