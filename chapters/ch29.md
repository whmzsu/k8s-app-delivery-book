> **本章结论**：挑现成 Operator 时 star 多、功能全是真的，但选的时候只看一个维度，半年后就要为「无转换路径的 CRD 升级」和「静默挂掉的控制器」买单——评估它靠不靠谱比装上它难得多。

## 29.1 问题与反模式：90% 的人不需要自己写，那现成的怎么挑

第 27 章的结论是「多数团队不写 Operator」，第 28 章把少数要写的人带过深水区。现在轮到大多数人会遇到的决策：**现成的 Operator 值不值得引入，怎么评估「靠不靠谱」，以及它挂了业务会不会跟着挂？** 这一章的读者面比上两章加起来还宽——「挑现成的」才是九成团队的真实路径。

**合成案例**（教学合成，非真实事件）：一个团队按「功能最全、star 最多」挑了数据库 Operator 装上。半年后集群升级，CRD 从 `v1alpha1` 跳到 `v1beta1` 却无转换路径，存量实例读不出来；卸载时 CR 挂着 finalizer 卡在 `Terminating`、PVC 残留。控制器告警、升级、备份演练更从装上起无人负责，直到它静默挂掉、主库故障才发现故障转移没触发 [R-29-1][R-29-4][R-29-7][R-29-12]。这个选择在装上的那天完全合理：它 star 多是真的，功能全也是真的——半年后的问题不是选错了一个项目，是选的时候只看了一个维度。

**评估会上的那两分钟**（合成案例，按共性还原，非真实对话）

> **平台组**：八项里「升级策略」和「卸载残留」我们还没演练，先装上再说？
> **同事**：装上之后再演练不一样吗。
> **主管**：数据先别动，只装控制器，不接管生产库。
> **平台组**：对，只装控制器。
> **同事**：那升级和卸载演练排进这个迭代？
> **主管**：先看装完效果，下个迭代再排。
> （「下个迭代再排」这句话在半年后依然成立，因为它的前提——「先看装完效果」——从来没有被满足过。）

这两分钟里没有一句是错的：先装再看效果是正常节奏，不接管生产库是正确的克制，连「下个迭代」也是当时最诚实的估计。缺的是有人把「演练」写成一个有截止日期的条目——**没有日期的待办，会在每一次会议上被重新排到「下个迭代」**。

三个反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：只看功能 / star 就引入。** 现象是升级时存量对象无处可去；根因是漏掉升级路径、活跃度、卸载残留这些半年后才显形的维度。「半年后才显形」不等于「半年后才重要」——它只说明你有一个很长的窗口，可以不在任何一次会上提它。替代做法是把它们写进评估表逐项打分，升级路径没结论就不许引入 [R-29-1][R-29-8][R-29-12]。

**反模式二：没做卸载演练。** 现象是 finalizer 卡住、PVC 残留；根因是把「装」当成可逆的，从没验证过「退」。本章把它变成可执行脚本与上线门禁 [R-29-4][R-29-12]。

**反模式三：把 Operator 当「装了就有人管」。** 现象是控制器自身告警与升级无人负责，它挂了业务静默降级；根因是没把它当「会挂、要升级、要有 runbook 的服务」。替代做法是纳入平台运维清单：健康告警、升级复评、备份演练、降级预案四项齐备 [R-29-7][R-29-8]。

以上反模式的**方法论**参照公开复盘索引中控制器升级类案例 [R-29-12]；该来源只支撑「这类失效模式确实存在」，不证明合成案例真实发生。

## 29.2 范式与决策树：先回答「它挂了，业务会不会挂」

**成熟度评估的六个维度**（本章判据表的骨架）：维护活跃度、升级策略、备份、可观测、降级预案、社区治理。它们各自对应一个「半年后才会显形」的问题，而不是装完当天能看见的功能 [R-29-8]：

| 维度 | 要回答的问题 | 可验证的证据 |
|---|---|---|
| 维护活跃度 | 近几个周期有没有 release、issue 有没有人回 | 发行说明、提交历史、issue 响应 |
| 升级策略 | CRD 版本怎么迁、控制器与实例谁先升 | 官方升级文档里的版本兼容矩阵 |
| 备份 | 能不能恢复到**新集群**，而不只是「任务绿了」 | 声明式 Backup / ScheduledBackup + 恢复演练报告（见第 16 章） |
| 可观测 | 控制器自己有没有指标与告警 | 指标端点 + 平台方补的告警规则（见第 22 章） |
| 降级预案 | 控制器不可用时业务能撑多久、谁接管 | 停用控制器演练记录 + 分级动作表 |
| 社区治理 | 有没有明确维护者、贡献流程与项目成熟度 | 治理文件与项目分级（沙箱 / 孵化 / 毕业）[R-29-8] |

**「Operator 挂了业务会不会挂」必须先回答**。多数现成 Operator 把**数据面**（Pod、Service、PVC）与**控制面**（控制器）解耦：控制器停掉后实例继续运行，业务不立刻 500；但故障转移、备份、升级、漂移纠正全部停摆——**业务没挂，恢复能力归零** [R-29-1][R-29-10]。这句话值得念两遍：监控上是绿的，业务上是好的，唯一消失的东西叫「出了事还有人能救」。可验证动作：把控制器缩到 0，看实例是否继续服务、主库故障是否无人接管（29.5）。这决定降级预案的分级。

**数据面 / 控制面停摆清单 × 接管 runbook 对照**（L1 降级时值班按此表逐行核对「这一行现在谁在管」；runbook 与第 23 章的 6 份 runbook 共用同一索引，此处只写要点，完整步骤以 runbook 正文为准）：

| 停摆的能力 | 数据面现象 | 接管人 | 接管 runbook 要点 |
|---|---|---|---|
| 故障转移 | 主库故障后备库不提升，`db` Service（5432）持续失败 | DBA | 确认副本到达一致位点 → 手工提升备库 → 验证 5432 可写、`/readyz` 通过 → 通知平台组恢复控制器后核对新主拓扑 |
| 备份 | 无新备份点，RPO 随停摆时间劣化 | DBA | 按第 16 章手工执行一次备份并校验可恢复；期间禁止任何不可逆数据变更（CL-G-09） |
| 升级 | 控制器与实例小版本漂移扩大 | 平台值班 | 冻结升级窗口（按第 20 章错误预算口径），恢复控制器后按 29.5 演练流程补升 |
| 漂移纠正 | 手工 `kubectl edit` 的改动不再被收敛，漂移持续累积 | 平台值班 | 立即停止手工变更（公理 5）；恢复控制器后用 `argocd app diff` 清点漂移并回 Git |
| 新实例创建 / 扩缩容 | 无法加副本，损毁实例无法自动重建 | DBA | 扩容需求挂起；损毁实例按第 16 章恢复到新集群再切流，不原地修 |
| 凭据轮换生效 | ESO 注入新 Secret 后实例侧无人衔接，继续用旧凭据 | 平台组 | 轮换延后到控制器恢复；恢复后核对新凭据已生效、旧凭据已禁用 |

这张对照表不是「控制器挂了怎么办」的全部答案，而是**降级预案 L1 的核对清单**：值班逐行确认接管人是否就位，任何一行「无人接管」都意味着预案有洞，回 `docs/operator-degradation-plan.md` 补齐后再重新演练——没有对照过这张表的降级预案，等于没写。数据面与控制面解耦的事实由 [R-29-1] 支撑；「按故障恢复能力取舍、用错误预算约束停摆期变更」的口径见 [R-29-10]。

**接管 runbook（完整版）**。上面对照表回答「谁接管」，这里回答「怎么接管、何时恢复 Operator」。runbook 分两条线，按停摆的是哪一面选择；所有命令先在演练集群验证过再写入预案，写进预案后按第 23 章 runbook 索引共用同一维护流程 [R-29-1][R-29-4]。

**runbook A：控制面停摆、数据面健康**（触发：`CnpgOperatorNoSuccessfulReconcile` 告警，实例继续服务）。目标不是马上修好控制器，而是先封住「半死控制器下发误动作」这条最危险的路：

1. **冻结（5 分钟内）**：`kubectl -n cnpg-system scale deploy cnpg-controller-manager --replicas=0` 把控制器缩到 0；同时按第 20 章错误预算口径冻结升级、备份策略变更与扩缩容操作 [R-29-10]。
2. **判定数据面（10 分钟内）**：`kubectl -n order-demo-eval get cluster,pod` 确认实例 Running、`./hack/verify.sh` 为 200；并记录当前主库快照 `kubectl -n order-demo-eval get cluster order-demo-eval-db -o jsonpath='{.status.currentPrimary}'`——这一行是恢复后核对的基准。
3. **修复与恢复时机**：恢复 Operator 的时机不是「能启动就行」，而是三个条件同时满足——根因已定位（升级 PR 可 revert、镜像验签通过、RBAC 未被误改）；reconcile 成功至少一次（`CnpgOperatorReconcileErrors` 告警消除）；同版本控制器在演练集群读当前 CR 无报错。满足后 `scale --replicas=1` 恢复，并核对 `.status.currentPrimary` 与第 2 步快照一致；**不一致时立即再缩到 0**——控制器可能在恢复瞬间误判拓扑，此时以快照中的实际主库为准，升级为 runbook B 处置。若 30 分钟内三条件无法满足，按降级预案维持 L1 并让 DBA 进入接管待命。

**runbook B：数据面停摆（主库故障且控制器不可用）**（触发：主库 Pod 崩溃、`db` 5432 持续失败、且控制器已停摆导致自动故障转移不会发生）。这是 L2 接管线，每一步都要能贴进告警回复里：

1. **确认现状**：`kubectl -n order-demo-eval get pods -l cnpg.io/cluster=order-demo-eval-db -o wide` 区分主备；应用 `/readyz` 失败且备库未被提升，确认进入人工接管。
2. **选提升候选（比 LSN，不比猜测）**：对每个候选备库执行 `kubectl exec <备库pod> -c postgres -- psql -U postgres -tAc "SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();"`，取 receive 最大者为候选；候选与次优库的 LSN 差距超过 RPO 容忍度时，先按第 16 章评估丢失窗口并通报数据 owner，再决定是否提升 [R-29-4]。
3. **手工提升**：`kubectl exec <候选pod> -c postgres -- psql -U postgres -c "SELECT pg_promote();"`，验证 `kubectl exec <候选pod> -c postgres -- psql -U postgres -tAc "SELECT pg_is_in_recovery();"` 返回 `f`。
4. **重新接流量**：控制器停摆时没有控制器替你改服务指向——手工给新主打角色标签 `kubectl -n order-demo-eval label pod <新主pod> cnpg.io/instanceRole=primary --overwrite`，并把旧主 Pod 改标 `replica` 或直接隔离；确认 `-rw` 服务 Endpoints 指向新主：`kubectl -n order-demo-eval get endpoints order-demo-eval-db-rw`。通过标准：Endpoints 指向新主、`verify.sh` 恢复 200（订单写路径即写探活）、`db` 5432 持续可达。
5. **恢复 Operator 的时机：数据面稳定之后立刻恢复，而不是等彻底收尾**——提升完成后新主没有自动备份、没有漂移纠正，暴露时间越长风险越大。恢复顺序：先过 runbook A 第 3 步三条件 → 恢复 1 副本 → 观察 reconcile 是否把拓扑收敛到与手工结果一致（`.status.currentPrimary` 应指向新主；若控制器试图把旧主重新提升，立即缩到 0，以手工提升结果为准移除旧主的抢占条件）→ 恢复后第一时间手工触发一次备份并校验可恢复 [R-29-4] → 最后用 `argocd app diff` 清点停摆期间的漂移并回 Git（公理 5，见第 3 章）[R-29-11]。

两条 runbook 的演练要求与卸载演练同级：没在演练集群各跑过一次（含「恢复后拓扑不一致」分支），降级预案不算可执行。

**逐级放行判据**（判断一个现成 Operator 能不能进试点；六级逐级放行，任一级不通过即停，不跳级）：

| 级 | 判据 | 不通过 → 去处 |
|---|---|---|
| 1 | 有没有一个现成 Operator 覆盖这个领域？ | 回第 27 章五选一，不引入 CRD |
| 2 | 八个评估维度是否全部有结论（含「不通过」）？ | 停在评估，禁止装 |
| 3 | 加权得分是否达到通过线？ | 换候选或自建，不许「先装上再说」 |
| 4 | 升级路径 / 备份恢复 / 卸载残留三项是否各演练过一次？ | 补演练，否则不许进 staging [R-29-4] |
| 5 | 「停用控制器」演练是否证明了业务影响面？ | 补降级预案，否则不许进 prod |
| 6 | 控制器自身告警、升级复评、责任人是否写进平台运维清单？ | 回 29.1 反模式三 |
| **全部** | 六级全部通过 | 允许进入受限试点；生产替换仍走第 14 章 GitOps 晋升链 |

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：评估现成 Operator，必须回答「**它挂了业务会不会挂**」，并把答案写成分级降级预案；引入与否按**故障恢复能力**决定，不按功能清单或技术偏好。
>
> **论证**：Operator 的价值不在「装起来」，而在「主库挂了，谁能恢复且数据不丢」。数据面与控制面解耦让「控制器挂了业务不立刻挂」成为常态，反而最危险——监控一片绿，恢复能力却归零。所以评估表把「备份能否恢复到新集群」「卸载是否无残留」「停用控制器后谁接管」与功能放在同等甚至更高权重。L1 只支撑架构解耦这一事实 [R-29-1][R-29-10]。
>
> **反例与适用前提**：这不等于「所有 Operator 都要配人工接管」。证书轮换这类**不影响在线流量**的，预案只需「暂停签发、告警、等修复」；数据库这类**恢复能力关系数据不丢**的，才需分级接管与备份兜底。前提是具备第 16 章恢复能力；连 `StatefulSet` 恢复都没跑通的团队，引入 Operator 只是把不会的事藏到抽象后面 [R-29-5]。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：自建 / 采购 / 托管的取舍按「谁承担故障恢复与升级」，不按「喜不喜欢用 K8s 管一切」。
>
> **论证**：三者差异不在功能表，而在责任归属：自建换来自主权，但要自己背控制器升级、CRD 迁移与值班；采购把部分责任转给供应商，代价是锁定与成本；托管把实例层责任整体转出，代价是可控性。决策输入应是四个可回答的问题——SLO 内能否恢复、是否演练过、是否有人懂协调循环、预案是否成文——而非技术审美。
>
> **反例与适用前提**：这不等于「小团队一律不许自建」。有成熟平台能力、需跨环境一致交付的团队自建反而最可控；20 人团队若无专人维护 CRD，托管几乎总是更优。前提是**存在多人协作、跨环境晋升的变更**；一次性本地实验不在此列。

## 29.3 工具选型：成熟度评估表与横向对照

按本书选型基线，**PostgreSQL 是全书有状态示例；第 16 章先用原生 `StatefulSet` 讲迁移范式，CloudNativePG 1.x 是第 29 章的评估对象**。本章不把 `order-demo-prod` 的 `db` 切到 Operator、不推翻 配置契约（16）；评估结论只决定「值不值得进入受限试点」。工具主版本在此出现，小版本锁附录 A。

**Operator 成熟度评估表**（评估项 / 权重 / 通过标准 / 何时不该用 / 回滚方式；加权规则：通过计满分、条件通过计半分、不通过计 0 分，总分 ≥ 80% 才允许进入试点）：

| 评估项 | 权重 | 通过标准 | 何时不该用 | 回滚方式 |
|---|---|---|---|---|
| 维护活跃度 | 5 | 有持续 release、issue 有响应、维护者可数 | 近几个周期无 release、issue 无人回 | 不引入；已引入则换候选 |
| 升级策略（CRD 版本迁移） | 5 | 有版本兼容矩阵、转换 webhook 路径、控制器与实例升级顺序 | 只有单版本 CRD、升级要手工改存量对象时 | 按第 28 章 28.2 五步逆序回退 |
| 备份恢复 | 5 | 声明式 Backup / ScheduledBackup，且能恢复到**新集群** | 备份只能原地覆盖、无恢复演练时 [R-29-4] | Velero 1.x 恢复到新集群兜底（见第 16 章） |
| 卸载残留 | 4 | 先删 CR 实例 → finalizer 清空 → PVC 按保留策略处置 → 删 CRD | 从未演练过卸载、finalizer 文档缺失时 | 按 29.4 脚本逐项检查后回退 |
| 自身可观测 | 4 | 暴露控制器指标，平台方补告警与 runbook [R-29-7] | 控制器无指标、告警无 runbook 时 | 补告警规则，或退回自建 |
| 降级预案 | 5 | 「停用控制器」演练已跑，分级动作与责任人成文 | 答不出「它挂了业务会不会挂」时 | 按 `docs/operator-degradation-plan.md` 执行 |
| 社区治理 | 3 | 有治理文件、贡献流程、明确项目成熟度 [R-29-8] | 单人维护、无治理结构、项目停更时 | 换候选 |
| 云厂绑定 | 3 | 存储 / 网络用可移植抽象，不锁死单一云厂 | 强绑定某云厂专有能力且无退出路径时 | 保留数据导出路径再退出 |

**评估怎么打分：从候选圈定到加权结论的完整流程**（把上表从「一张表」变成「一条可填写的评估流程」，五步走完才算填完）：

第 0 步 · 候选圈定：从 Artifact Hub 按领域筛出 1–2 个候选 [R-29-6]，超出评估带宽就砍掉；候选先过四条否决项（见 29.4 评估表「否决项」），命中任意一条直接出局，不进入打分——否决项是底线，加权分是底线之上的精细比较，两者不可互相抵扣。

第 1 步 · 证据收集：每个评估项固定一个证据源，收集不到证据就计 0 分，不凭印象折中。活跃度看发行说明与提交历史；升级策略看官方版本兼容矩阵；备份看恢复演练报告而非「任务绿了」的截图 [R-29-4]；可观测看指标端点与告警规则；降级预案看演练记录；治理看治理文件与 CNCF 分级 [R-29-8]；云厂绑定看存储与网络抽象层。证据超过一个季度未更新视为过期，按无证据处理。这条规则看起来苛刻，它挡住的却是最常见的一种打分：凭印象给个高分，然后在半年后的某个凌晨一次性结算。

第 2 步 · 单项打分：三档判据，逐条对照后落分，不允许出现「大概算通过」。「大概算通过」是这张表里最贵的一个词——它把一次没做完的判断，变成了一条写在案上的事实。三档如下：

| 得分档 | 判据（三条同时满足才是满分） |
|---|---|
| 满分 | 证据齐备、演练过至少一次、责任人有名有姓 |
| 半分 | 证据齐备但未演练过，或演练过但责任人挂空（如本章「自身可观测」项） |
| 0 分 | 无证据、证据过期、或命中该项「何时不该用」 |

第 3 步 · 加权与通过线：权重设计原则是**恢复能力相关项最高**（备份、降级、升级策略各 5），**退出与观测居中**（卸载残留、自身可观测各 4），**治理与绑定最低**（社区治理、云厂绑定各 3），满分合计 34 分。通过线 ≥ 80% 即 ≥ 28 分（34 × 0.8 = 27.2，向上取整）。示例：本章 CloudNativePG 结论为 7 项满分 30 分 + 1 项半分 2 分 = 32 分，约 94%。通过线设 80% 而非 60% 的理由：评估表是引入前的最后一道门，60% 意味着允许两项核心能力缺失，而按 29.3 末尾的代价复盘，缺失项往往半年后才显形 [R-29-12]。

第 4 步 · 结论落档：评估单归档到 `docs/operator-assessment.md`（29.4 给出完整归档版），结论只有三种——通过 / 有条件通过 / 不通过。「有条件通过」必须同时写明条件项与关闭期限并挂在引入 PR 上；未注明期限的条件不允许随版本晋升进入 prod。

第 5 步 · 复评触发：控制器大版本升级前全表复评；每季度复评维护活跃度与社区治理两项（这两项随时间衰减最快）；发生一次与该 Operator 相关的事故后强制全表复评。复评结论与首次结论的差异要写成 diff 说明，不许只改分数。

**加权结论**：8 项中 7 项通过、1 项条件通过，总分超过 80% → **有条件通过：允许受限试点，不直接替换生产 `db`**；条件项（自身告警）关闭前不得晋升 prod。每项都有证据栏或待办栏，没有「凭感觉」的空格，这正是「能完成评估表」的验收形态。

**各评估项「不通过」的代价复盘**（合成复盘：按 29.1 的失效模式逐项推演「这一项不通过，半年后会付出什么」；方法论参照公开复盘索引中控制器升级类案例 [R-29-12]，不冒充真实事件）。复盘的作用是把「不通过计 0 分」从形式规则变成真实风险定价——权重低的项（社区治理 3、云厂绑定 3）不通过同样可能半年后吃掉整个周末，只是表现为「换候选容易」而不是「故障大」。这两项的区别也可以用一句话记住：一项让事故更大，另一项让选择更少。八项逐条推演：

1. **维护活跃度不通过**：半年后上游不再发 release，你遇到的问题在 issue 区无人回应，只能自己 fork 改控制器——这相当于被迫做了一次第 28 章的「自建 Operator」，却没有当初自建的决心与人力。代价：隐患修复周期从「上游补丁」变成「你们自己的迭代节奏」。复盘结论：此项不通过时不允许「先装上、等人回复」，必须直接换候选。
2. **升级策略不通过**：CRD 只有单一版本、或升级要手工改存量对象，意味着每次控制器升级都是一次高危变更；29.5 的 CRD 版本演练永远跑不通，升级 PR 无法回滚（公理 6，见第 3 章）。代价：要么永远停在旧版本吃安全漏洞，要么被迫一次性大改存量 CR。复盘结论：升级路径没结论正是 29.1 合成案例的原发故障，直接否决。
3. **备份恢复不通过**：「备份任务绿了」但从未恢复到新集群，等于没有备份（见第 16 章）；主库一旦损坏，RPO 从「上一个备份点」变成「未知」。代价：数据丢失风险，且事故后才发现备份文件根本不可用。复盘结论：此项是「数据不丢」的底线，不通过时即便其他七项满分也不引入，只能退回第 16 章自建 + Velero 1.x 恢复演练兜底 [R-29-4]。
4. **卸载残留不通过**：finalizer 卡住、PVC 残留、CRD 删不掉，半年后想做架构调整时发现「装得起、卸不掉」，旧 Operator 变成集群里的永久债务。代价：退出成本远高于当初的引入收益，且残留组件可能干扰无关命名空间。复盘结论：29.4 卸载演练脚本跑不出退出码 0，就不许进 staging。
5. **自身可观测不通过**：控制器挂了没人知道，恢复能力静默归零——这正是 29.2 强调的最危险状态。代价：直到主库故障无人接管才报警，MTTR 从「分钟级」劣化到「小时级」。复盘结论：控制器指标必须接入第 22 章告警体系并带 runbook [R-29-7]；条件项不关闭不得晋升 prod。
6. **降级预案不通过**：答不出「它挂了业务会不会挂」，值班时只能现场发明流程。代价：控制器故障演变为业务故障的概率大幅上升，且每人处置不一致。复盘结论：降级预案五栏（分级动作、时限、责任人、回滚路径、退出顺序）不齐就不许进 prod；冻结口径按第 20 章错误预算执行 [R-29-10]。
7. **社区治理不通过**：单人维护、无治理结构的项目，核心维护者一旦失联整个项目停更；与前一项「维护活跃度」的差别在于它不可观测——活跃度是「现在」，治理是「将来」。代价：想换候选时发现生态里没有同量级替代品。复盘结论：按 CNCF 成熟度分级（沙箱 / 孵化 / 毕业）核对治理文件后再打分 [R-29-8]。
8. **云厂绑定不通过**：存储、网络或身份认证锁死单一云厂专有能力，跨云迁移或成本谈判时数据导出路径不可行。代价：退出前必须先自建一套导出工具，迁移窗口以月计。复盘结论：引入前确认「数据导出」是现成路径而非口头承诺——只有一行数据的导出演示不算数。

**Strimzi / cert-manager 评估卡**（沿用同一张八项评估表快速预打分。目的有两个：等真要引入 Kafka 或证书签发时不必从零起步；反过来检验评估表是否只对数据库场景有效。两者都只作对照，不是本章正式评估对象）[R-29-2][R-29-3]：

**Strimzi 0.x 评估卡（预打分，未做正式评估）**：

- 升级策略：CRD 数量多（Kafka / KafkaTopic / KafkaUser 等多 CR 协同），控制器、实例镜像与 Kafka 协议版本三方耦合，升级路径在全部候选里最重 [R-29-2]。预判：条件通过。
- 降级预案：数据面（broker 继续收发消息）不依赖控制器，但分区再平衡、Topic / User 变更全部停摆，预案复杂度高于数据库类 Operator。预判：条件通过。
- 卸载残留：Topic CR 的删除会级联删真实 Topic，卸载顺序写错等于删生产数据——这一项必须先演练再谈引入。它的分数不取决于文档写得多好，取决于有没有人真的在演练集群上删过一次。
- 何时不该用：无专职 Kafka 运维、或已用托管消息服务（与上方对照表口径一致）。
- 预判结论：八项中「升级策略」「降级预案」大概率只拿半分；无专职运维的团队不引入，回第 5 章工具清单写明「不上什么」。

**cert-manager 1.x 评估卡（预打分，未做正式评估）**：

- 降级预案最轻：已签发证书继续有效，不影响在线流量；预案只需「暂停签发 + 告警 + 等修复」[R-29-3]。预判：通过。
- 升级策略：证书签发链的兼容矩阵必须引入前核对——cert-manager 历史上经历过 CRD 版本迁移，存量 Certificate 对象的升级路径要按其官方升级文档写进评估表，这是「升级策略」项的必答题而非加分题 [R-29-3]。预判：条件通过（未演练前）。
- 卸载残留：webhook 组件若有残留会拦住所有新 Pod 的准入，影响面超出自身命名空间。本书观点：卸载演练必须覆盖「删控制器后新建 Pod 是否正常」这一步；适用前提是集群内还有其他 admission webhook。
- 自身可观测：控制器有指标，按第 22 章接入告警规则即可 [R-29-7]。预判：通过。
- 预判结论：数据库类与证书类 Operator 的权重分布应当不同——「降级预案」「备份」两项对 cert-manager 可降权，「升级策略」「卸载残留」反而必须满分。这印证 29.2 本书观点：评估按故障恢复能力取舍，不按功能清单。

**自建 vs 采购 vs 托管对比**（责任归属口径，不写具体云厂单价）：

| 形态 | 谁承担实例恢复 | 谁承担控制器升级 | 可移植性 | 何时不该用 | 相对成本档位 |
|---|---|---|---|---|---|
| 自建（原生 `StatefulSet`，第 7/16 章） | 团队 | 不适用（无控制器） | 最高 | 要求自动故障转移、团队无 DB 恢复能力时 [R-29-5] | 低（人力高） |
| 自建 + 现成 Operator（本章评估） | 控制器 + 团队兜底 | 团队 | 高 | 无 CRD / 控制器运维能力时（见第 5 章警戒线） | 中 |
| 采购商业发行版 | 供应商 + 团队 | 供应商 | 中 | 预算不允许、或数据不出境有合规约束时 | 中高 |
| 托管数据库 | 服务商 | 服务商 | 低 | 有合规 / 网络 / 成本结构约束时 | 高（按用量） |

**成本 / 控制力 / 维护负担三维判定**（把上面的责任归属表落成三个可回答的问题；成本只给相对比例与归因口径，不写具体单价 [R-29-5][R-29-9]）：

- **成本：看隐性成本归因，不看账单**。显性成本排序大致是托管 > 采购 > 自建 + Operator ≈ 原生 `StatefulSet`，但真正的差距在隐性成本——值班人力、演练工时、升级窗口。原生 `StatefulSet` 显性最低，却把每次故障转移变成人工事件（第 16 章范式），成本以「事故工时」形式到账；托管显性最高，却把 DBA 值班工时整体移出团队。归因口径：季度复盘把「与数据库相关的 on-call 工时 × 频次」与形态溢价做对比——账单高但工时归零可能是划算的，账单为零但每次主库故障烧掉一个周末不是。
- **控制力：用「SLO 缺口」度量，不用偏好度量**。自建最高（版本节奏、参数、拓扑自己定）；Operator 形态交出协调循环但保留数据主权（PVC、备份目标、实例镜像仍可声明，这正是本章评估表的检查面）；托管交出最深——升级窗口、参数白名单、维护窗口都归服务商。可判定检验：列出团队 SLO 承诺过、且当前形态做不到的能力清单，每缺一条扣一层控制力；SLO 没承诺的能力（如跨区自动切换）不纳入比较，避免为用不上的控制力付费。
- **维护负担：用固定人力当量度量**。自建 + Operator 最重（控制器升级、CRD 迁移、指标补齐、值班全在团队，即本章评估表复评的全部对象）；原生 `StatefulSet` 次之（无 CRD 迁移但无自动化）；托管最轻（剩下自查告警与成本核对）。可判定检验：该形态要求团队投入多少固定工时？答案折算 ≥ 0.5 FTE 且 headcount 不动时，维护负担超标——评估表五步流程（本节上文）的复评触发本身就是这份工时的一部分，引入前要把它算进去。

三个维度的临界点合成一张判定表：

| 判定输入（满足其一即倾向该列） | 倾向形态 |
|---|---|
| 数据库相关固定投入 < 0.5 FTE 且无季度演练记录 | 托管 |
| ≥ 2 人能读懂 reconcile、季度演练有记录、要求跨环境一致交付 | 自建 + 现成 Operator（先过本章评估表）|
| SLO 要求自动故障转移，但数据不可出私有网络 | 自建 + Operator 或商业发行版（合规约束优先于成本）|
| 数据库只是边界服务、无 DBA、SLO 宽松 | 原生 `StatefulSet` + 第 16 章备份演练兜底 |

反例与适用前提：这张表不否定「先托管、后迁出」的路径——早期用托管换交付速度，数据量与团队成熟后再迁回 Operator，是常见且合理的次序；前提是迁移路径（导出格式、版本兼容、停摆窗口）在**引入托管当天**就验证过一次，而不是决定迁出前才试——否则等于把退出成本推迟到最不方便的时刻 [R-29-9]。另一点前提：四个形态可以共存（如核心库自建 + Operator、边界服务托管），判定表按「这一个数据库」逐个套用，不做全有全无的架构站队。
