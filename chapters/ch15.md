## 15.1 问题与反模式：能自动进集群了，为什么还是全量炸

先把因果摆正（D-02）：**第 14 章解决「变更怎么进集群」，是底座；本章解决「流量怎么灰度」，是发布策略的工具实现**。第 13 章把滚动 / 蓝绿 / 金丝雀的选型与回滚方案写成了清单，第 14 章让 Git 成为唯一变更入口；到这里，一次合并 PR 已经能自动把清单同步进 prod。但「自动同步」默认仍是**一次性全量**：新版本一进集群，立刻承载 100% 真实流量。自动化的速度把「本来能靠人观察一下拦住」的窗口也压没了。

**合成案例**（基于多起公开事故的合成，非真实事件）：团队上了 GitOps 之后很兴奋，把发布也「自动化」了：合并 PR 即全量。某次 `gateway` 的新版本里，一个只在特定请求头下触发的分支会返回 500，影响大约 5% 的请求。因为没有分批，这 5% 立刻摊到全部用户身上，值班同学发现时错误预算已经烧掉一大半。团队随后补了个「金丝雀」：起一个新 Pod 当 canary，用 CPU 与内存做放量判据——结果这个 bug 完全不影响资源使用，指标一路漂亮，于是脚本放心地全量放开。第三次他们加了「自动回滚」，阈值照抄官方示例写成「错误率 > 50% 才回滚」，而真实的 5% 错误率从来触发不了它；改成 1% 后又因指标抖动反复回滚，发布永远停在 25% 完成不了 [R-15-4][R-15-8][R-15-12]。

三次失败对应三个反模式：

**反模式一：用 CPU / 内存做放量判据。** 现象是版本有 bug 但资源指标全绿，全量放出去才暴露；根因是把「机器忙不忙」当成了「用户好不好」。替代做法是判定指标必须来自用户可感信号——错误率与延迟分位——而不是资源利用率 [R-15-4][R-15-8]。

**反模式二：自动回滚没设人工门禁与冷却窗口。** 现象是阈值抖动引发反复回滚、发布永远完不成，或者反过来阈值太松形同虚设；根因是把 Analysis 的窗口、失败阈值、冷却时间当成可以照抄的示例值。替代做法是按业务风险设定阈值并加确认步骤与冷却窗口，见 15.2 的阈值设定表 [R-15-5]。

**反模式三：小团队上 Rollouts + Flagger + Kargo 全套。** 现象是维护三套 CRD、两套指标接入、一条晋升编排，收益却只是「5% 试一下」；根因是工具数量超过了团队的故障恢复能力。替代做法是引用第 5 章的过度工程警戒线：先上最小可用的一层（原生按副本比例分批），确有精确流量比例需求再加流量插件。

以上反模式的**方法论**参照公开渐进式交付 / 自动回滚事故复盘 [R-15-12]；该来源只支撑「这类失效模式确实存在」，不用于证明上面的合成案例真实发生。

## 15.2 范式与决策树：渐进式交付的正式定义

本章是 **渐进式交付的正式定义章**（第 13 章首次提及已给白话与「详见第 15 章」，本章不再当预告用）。给一个可测量、可验证的定义：

> **渐进式交付 = 按流量或请求比例逐步放量 + 用指标判定继续或自动回滚。三者缺一，就只是「手动分批」** [R-15-1][R-15-8]。

| 要素 | 可验证判据 | 缺了会怎样 |
|---|---|---|
| 流量分批 | `HTTPRoute` 的 `backendRefs.weight` 或 Rollout 的 `setWeight` 台阶可查；退化方案下按副本比例近似 | 一次全量，没有观察窗口 |
| 指标判定 | `AnalysisTemplate` 的查询引用错误率 / P99 延迟等用户可感信号 | 「新 Pod 没崩」不等于「用户没受影响」 |
| 自动回滚 | 判定失败时 Rollout 自动 `abort` 并把权重退回稳定版，无需人工敲命令 | 半夜等指标被人看见，回滚方案又变成「看一眼再决定」 |

**指标口径的三句白话**（正式定义在第 20 章，本章只借用概念、不拿它们当推理前提）：SLI 是「可直接测量的好坏比例，如成功请求数 / 总请求数」；SLO 是「服务好坏的量化承诺」；错误预算是「一个窗口内允许不可用的额度」。三者详见第 20 章。本章只要求一件事：**判定信号必须是用户可感的**，即请求成败与延迟，而非 CPU、内存这类业务无感指标 [R-15-4][R-15-10]。按概念梯度，本章不写「SLO 不达标所以不发布」这类以 SLO 为前提的推导。

**AnalysisTemplate 阈值设定表**（窗口 / 失败阈值 / 冷却 / 人工门禁，示例值须按业务风险校准，见一致性备注）：

| 指标 | 查询窗口 | 失败阈值 | 判定次数 | 冷却窗口 | 人工门禁 |
|---|---|---|---|---|---|
| 5xx 错误率 | 5m | `> 1%` | 连续 2 次失败即 abort（`failureLimit: 1`） | 10m | 5% → 25% 自动；25% → 50% 需确认 |
| P99 延迟 | 5m | `> 800ms` | 连续 2 次 | 10m | 50% → 100% 需确认 |
| 成功率 | 10m | `< 99%` | 连续 3 次 | 10m | 每个台阶结束各一次 |

表中三列的取舍逻辑：窗口太短会被毛刺误伤、太长会让坏版本多服务一阵；失败阈值必须落在「比正常波动高、比真实事故低」的窄带里；`failureLimit` 与冷却窗口共同防止阈值抖动引发反复回滚 [R-15-5][R-15-11]。这些值不是从工具文档里抄来的，必须来自本服务第 20 章的 SLI 基线与第 22 章的告警口径。

**决策树**：

```
是否有可查询的用户可感指标（错误率 / 延迟分位）？
        否 → 不要开自动判定，退回按副本比例手动分批；先补第 21 章可观测栈
        │ 是
需要精确按请求比例（如精确 5%）或按 header 定向切流吗？
        是 → Gateway API + Envoy Gateway traffic router 插件路径（15.4）
        否 → 按副本比例金丝雀退化方案（不依赖流量插件，15.4）
        │
阈值、冷却、人工门禁是否按业务风险设定并演练过自动回滚？
        否 → 禁止开启自动回滚，只保留指标观测
        │ 是
→ 渐进式交付成立；发布由指标决定是否继续
```

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：特性开关控制「功能对谁可见」，渐进式交付控制「哪个版本承载流量」；两者可配合，但不可互相替代 [R-15-9]。
>
> **论证**：特性开关作用在**代码路径**上——同一个二进制里，用配置决定某段逻辑是否执行；渐进式交付作用在**版本与流量**上——两个不同的制品，用权重决定请求落到哪个。把开关当发布策略用，会得到「所有 Pod 都跑着新二进制、只是功能关着」的状态：新版本里那些不经过开关的代码（依赖升级、序列化改动、连接池参数）已经全量生效，一旦出问题，关开关救不了你，只能回滚版本。反过来，用金丝雀去做「只给 VIP 用户开放某功能」也是错配，那是按身份路由，属于开关或网关策略的活。两者配合的正确形态是：先用渐进式交付把新版本安全地放到 100% 流量，再用特性开关按人群逐个打开功能。
>
> **反例与适用前提**：这不等于「上了 Rollouts 就不许用开关」。功能 Flag 与发布灰度本就是两层，前提是团队能说清「这次变更的风险来自版本还是来自功能」；若风险只在功能逻辑且新旧二进制完全等价，单独用开关是合理的。跳过此步的典型代价是「以为有灰度、其实二进制已全量」，反例见把开关当发布策略的做法。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：Analysis 的窗口、失败阈值与人工门禁必须按业务风险设定；照抄示例值会让自动回滚形同虚设或频繁误触发。
>
> **论证**：自动回滚把「继续放量」的决策权从人交给了机器，而机器只看你给的阈值。阈值太松（如错误率 > 50%），等于把发布退化成全量；阈值太紧又没冷却，一个采集毛刺就能让发布在 25% 反复 abort，团队很快会把自动回滚关掉——这比没配更糟，因为它消耗了大家对自动化的信任。阈值因此是一个**业务参数**，不是工具参数：它必须由本服务正常的错误率波动、SLO 余量、以及一次事故可接受的影响面共同推导，并在 staging 用故障注入演练过一次。
>
> **反例与适用前提**：这不等于「每个服务都要从零调一套阈值」。同一业务域、同一 SLI 口径的服务可以共用基线模板，但上线前仍要用该服务一周的真实分布校验。前提是第 21 章的指标确实按统一命名规范产出、第 22 章的告警不会与 Analysis 相互打架（SP-06）；指标名对不上时，示例查询会直接查空值，自动回滚静默失效。跳过此步的典型代价见第 22 章告警噪音治理。

## 15.3 工具选型：唯一示例 + 一条不依赖插件的退化路径

按 `book/decisions.md` 的 U-05 与配置契约：**Argo Rollouts 1.x 及其 Gateway API traffic router 插件为渐进式交付的唯一示例实现**；流量层固定 **Gateway API 1.x + Envoy Gateway 1.x**（`GatewayClass: eg`、`Gateway` 名 `order-demo-gw`、`HTTPRoute` 名 `gateway-route`），**Istio 1.x 仅在选型矩阵作对比**。并且按 U-05 硬要求，必须同时给出**不依赖流量插件的「按副本比例金丝雀」退化方案**——插件属快速演进组件，没有退化路径，示例会随插件版本失效。

> 术语铺垫：`Rollout`、`AnalysisTemplate`、`HTTPRoute` 都是 CRD（给 K8s 增加一种自定义资源类型，白话，详见第 27 章正式定义）。本章只使用它们，不解释 CRD 机制本身。

| 工具 / 实现（主版本） | 流量层依赖 | 指标接入 | 与第 14 章晋升链路的衔接 | 回滚方式 | 何时不该用 |
|---|---|---|---|---|---|
| Argo Rollouts 1.x + Gateway API traffic router 插件（**示例实现**） | Gateway API 1.x + Envoy Gateway 1.x | `AnalysisTemplate` 查 Prometheus | 清单由 GitOps 控制器同步，`setWeight` 台阶在清单里声明 | 判定失败自动 abort；手动 `abort` + `undo` | 没有用户可感指标；或不想引入 Rollout CRD 时 |
| Argo Rollouts 1.x「按副本比例金丝雀」（**退化方案**） | 无，靠 Service 随机负载均衡 | 同上 | 同上 | 同上 | 需要精确 5% 或按 header/cookie 定向切流时 |
| Flagger 1.x（仅对比） | 支持 Gateway API / mesh | 自带指标模板 | 需另一套 CRD 与控制器 | 自动回滚 | 已选 Argo Rollouts 1.x 时不该再叠一套（第 5 章） |
| 原生 `Deployment` + 手工分批 | 无 | 人看大盘 | 两个 Deployment 由 Git 声明 | 手工改回副本数 | 想要「指标不对自动退」时；只是手动分批，不算渐进式交付 |
| Istio 1.x（流量层，仅对比） | 服务网格 | 需接 mesh 指标 | 与第 19 章选型相关 | 改 `VirtualService` 权重 | 只需按副本比例灰度、不愿承担网格运维成本时（SP-15） |

Flagger 1.x 与 Istio 1.x 仅作为互相竞争的实现在矩阵里出现，不进入本书示例链路 [R-15-3][R-15-7]。

**按副本比例金丝雀为什么是必要的退化方案**：精确 5% 依赖 Gateway API 插件改写 `HTTPRoute` 权重；插件一升级、CRD 一变体，示例就可能跑不通。退化方案完全不碰 `trafficRouting`，只让 canary 与 stable 的副本数成比例，由 Service 的轮询近似分流——4 个副本里放 1 个 canary，约等于 25% 流量，不精确，但足以在「先让一小部分请求试一下」这件事上保住能力。判断标准很直白：**需要精确百分比或按身份路由，才值得上流量插件；否则退化方案更稳**。

**最小接入 diff** 与升级 / 回滚路径：

```diff
+ deploy/rollouts/rollout-canary.yaml              # 5%→25%→50%→100% + Analysis + 自动回滚
+ deploy/rollouts/rollout-replica-canary.yaml      # 退化方案：按副本比例，无 trafficRouting
+ deploy/rollouts/analysis-template.yaml           # 错误率 / P99 延迟
+ deploy/rollouts/traffic.yaml                     # Gateway / HTTPRoute / 两个 Service
+ hack/inject-error-rate.sh                        # 故障注入，演练自动回滚
~ deploy/overlays/prod/                            # gateway 工作负载由 Deployment 改为 Rollout
```

升级 Rollouts 控制器或 Gateway API 插件版本走独立 PR，先 staging 观察一次完整发布再升 prod；回滚是 `git revert` 该 PR 并由第 14 章控制器同步。Rollout 清单本身不放任何镜像 `latest`，仍用 `git-<sha7>`；工具小版本锁在附录 A。

## 15.4 落地配置（完整可应用文件，Kubernetes 1.32+ / Argo Rollouts 1.x / Gateway API 1.x）

> 全部字段沿用 `book/case-evolution.md` 配置契约：命名空间 `order-demo-prod`、镜像 `registry.example.com/order-demo/gateway:git-<sha7>`、Service 名 `gateway` 端口 8080、公共标签 `app.kubernetes.io/name=order-demo` / `app.kubernetes.io/component=gateway` / `version=git-<sha7>` / `app.kubernetes.io/managed-by=argocd`（第 14 章起）、探针 `/healthz` 与 `/readyz`、`terminationGracePeriodSeconds: 30` + `preStop` 先摘流、资源基线 requests `cpu: 100m, memory: 128Mi` / limits `cpu: 500m, memory: 256Mi`。流量入口固定值：`GatewayClass: eg`、`Gateway: order-demo-gw`、`HTTPRoute: gateway-route`。示例 SHA：稳定版 `git-1a2b3c4`、候选版 `git-5d6e7f8`。

**`deploy/rollouts/traffic.yaml`** —— 流量层唯一实现。`HTTPRoute` 的两个 backend 权重由 Rollouts 插件改写 [R-15-2][R-15-6]。

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: order-demo-gw
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  gatewayClassName: eg
  listeners:
    - name: http
      protocol: HTTP
      port: 8080
      allowedRoutes:
        namespaces:
          from: Same
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: gateway-route
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  parentRefs:
    - name: order-demo-gw
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: gateway-stable
          port: 8080
          weight: 100
        - name: gateway-canary
          port: 8080
          weight: 0
---
apiVersion: v1
kind: Service
metadata:
  name: gateway-stable
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
  ports:
    - name: http
      port: 8080
      targetPort: http
      protocol: TCP
---
apiVersion: v1
kind: Service
metadata:
  name: gateway-canary
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
  ports:
    - name: http
      port: 8080
      targetPort: http
      protocol: TCP
```

> `gateway-stable` / `gateway-canary` 的 selector 不带 `version`，由 Rollouts 通过 `rollouts-pod-template-hash` 自动注入到 ReplicaSet 层区分；这是 Rollout 与两个 Service 协作的常规形态。配置契约冻结的 Service 名 `gateway` 保留为对外入口（见第 19 章），这两个 Service 是灰度内部使用的附加资源，不改动 `gateway` 的端口与标签约定。

**`deploy/rollouts/analysis-template.yaml`** —— 指标驱动判定。两个指标都来自用户可感信号，不是 CPU / 内存 [R-15-1][R-15-4][R-15-5]。

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: gateway-sli
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  args:
    - name: canary-service
      value: gateway-canary
  metrics:
    - name: error-rate
      interval: 1m
      count: 5
      successCondition: "result[0] <= 0.01"
      failureLimit: 1
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            sum(rate(http_requests_total{service="{{args.canary-service}}",code=~"5.."}[5m]))
            /
            sum(rate(http_requests_total{service="{{args.canary-service}}"}[5m]))
    - name: p99-latency
      interval: 1m
      count: 5
      successCondition: "result[0] <= 0.8"
      failureLimit: 1
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            histogram_quantile(
              0.99,
              sum(rate(http_request_duration_seconds_bucket{
                service="{{args.canary-service}}"
              }[5m])) by (le)
            )
```

> `successCondition` 里的 `0.01`（1% 错误率）与 `0.8`（800ms P99）即 15.2 阈值表的值；`failureLimit: 1` 配合 `count: 5` 表示「连续两次采集不达标即判定失败」，冷却由 Rollout 台阶间的 `pause` 承担。指标名必须与第 21 章命名规范一致，否则查询会静默返回空值使自动回滚失效（见一致性备注）[R-15-4]。

**`deploy/rollouts/rollout-canary.yaml`** —— 5% → 25% → 50% → 100%，每级接 Analysis，判定失败自动回退。

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: gateway
  namespace: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: gateway
    app.kubernetes.io/managed-by: argocd
spec:
  replicas: 4
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: gateway
  template:
    metadata:
      labels:
```

**`hack/inject-error-rate.sh`** —— 注入错误率，演练自动回滚。`INJECT_ERROR_RATE` 是本章演练镜像内置的 chaos 开关，只在演练时通过环境变量注入，不属于配置契约冻结字段，也不进生产清单。

```bash
#!/usr/bin/env bash
set -euo pipefail

NS=order-demo-prod
ROLLOUT=gateway
REPORT="/tmp/canary-drill-$(date +%Y%m%d%H%M%S).log"
log() { echo "[$(date -u +%FT%TZ)] $*" | tee -a "${REPORT}"; }

log "注入前状态"
kubectl argo rollouts -n "${NS}" get rollout "${ROLLOUT}" | tee -a "${REPORT}"

# 给 canary Pod 模板注入 20% 错误率（仅演练镜像支持该开关）
kubectl -n "${NS}" patch rollout "${ROLLOUT}" --type=json -p \
  '[{"op":"add","path":"/spec/template/spec/containers/0/env","value":[{"name":"INJECT_ERROR_RATE","value":"0.20"}]}]'
log "已注入 INJECT_ERROR_RATE=0.20，等待 Analysis 判定失败并自动回退"

for i in $(seq 1 60); do
  PHASE="$(kubectl -n "${NS}" get rollout "${ROLLOUT}" -o jsonpath='{.status.phase}')"
  WEIGHT="$(kubectl -n "${NS}" get httproute gateway-route \
    -o jsonpath='{.spec.rules[0].backendRefs[1].weight}')"
  log "phase=${PHASE} canaryWeight=${WEIGHT}"
  if [ "${PHASE}" = "Degraded" ] || [ "${WEIGHT}" = "0" ]; then
    log "检测到自动回退，报告: ${REPORT}"
    exit 0
  fi
  sleep 5
done

log "失败：300s 内未观察到自动回退"; exit 1
```

## 15.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（仓库根目录，需 `kubectl` + `kubectl-argo-rollouts` 插件、`argocd`、Prometheus 可达，版本见附录 A）：

```bash
chmod +x hack/inject-error-rate.sh
# 合并一个只改 image SHA 的 PR，由第 14 章控制器同步 Rollout 清单
git log -1 --oneline
kubectl argo rollouts -n order-demo-prod get rollout gateway --watch &
WATCH=$!
sleep 10
kill "${WATCH}" 2>/dev/null || true
# 观察先停在 5%
kubectl -n order-demo-prod get httproute gateway-route \
  -o jsonpath='{.spec.rules[0].backendRefs[1].weight}{"\n"}'
# 注入错误率触发自动回退
./hack/inject-error-rate.sh
kubectl argo rollouts -n order-demo-prod get rollout gateway
./hack/verify.sh
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| 先停在 5% | `HTTPRoute` 的 canary `weight` 稳定在 5，未直接跳到 100 [R-15-2] |
| 指标来自用户可感信号 | `AnalysisTemplate` 查询的是错误率与 P99 延迟，无 CPU / 内存指标 [R-15-4] |
| 阈值有依据 | 15.2 阈值表的值来自本服务基线，`failureLimit` 与冷却窗口已设 [R-15-5] |
| 自动回退 | 注入 20% 错误率后，Analysis 判定失败，Rollout 自动 `abort`，canary `weight` 回到 0，**无人工介入** |
| 人工门禁生效 | 25% → 50% 与 50% → 100% 台阶停在 `pause: {}`，需显式 `promote` 才继续 |
| 退化方案可用 | 不启用插件、改用 `rollout-replica-canary.yaml` 时，按副本比例分批且 Analysis 仍触发自动回退 |
| 回归可用 | `verify.sh` 的 `/healthz` 为 200，流量 100% 落在稳定版 |

**回滚命令 / 步骤**。自动回滚由 Rollout 自己执行，这是本章与第 13 章最大的差别：判定与执行都在集群内闭环，不等人。但**回滚方案仍须先于发布方案**——上面的 `hack/inject-error-rate.sh` 演练记录必须附在发布 PR 上，没演练过就不允许开自动回滚（CL-G-07）。

```bash
# 路径 A：自动回滚（常态）——由 Analysis 判定失败触发，无需命令
# 以上演练已覆盖

# 路径 B：手动兜底（自动判定未及时生效时）
kubectl argo rollouts -n order-demo-prod abort gateway
kubectl argo rollouts -n order-demo-prod undo gateway
kubectl argo rollouts -n order-demo-prod status gateway --watch=false

# 路径 C：回到 Git，让真相源与集群一致（生产唯一合法路径，见第 14 章）
OLD="<上一个已验证的 sha7>"
git revert <本次晋升 PR 的 merge commit>
git push origin main
argocd app sync order-demo-prod
./hack/render.sh prod "${OLD}"
```

> 路径 B 只改集群当下状态，路径 C 才改真相源；用了 B 必须补 C，否则第 14 章的漂移检测会把它当成一次手工变更。另有一条硬边界：**自动回滚只覆盖版本，不覆盖数据 schema**。若本次发布牵涉数据格式，15.2 的指标再漂亮也救不了「旧版本读不懂新表」，那一半按第 13 章「本书观点」交给第 16 章的 expand–contract（SP-03）。

**回滚验证**：

```bash
kubectl argo rollouts -n order-demo-prod get rollout gateway
kubectl -n order-demo-prod get httproute gateway-route \
  -o jsonpath='{.spec.rules[0].backendRefs[1].weight}{"\n"}'
kubectl -n order-demo-prod get rollout gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
argocd app diff order-demo-prod
./hack/verify.sh
```

通过标准：Rollout 为 `Healthy` / 稳定版，canary `weight` 为 0、`image` 回到 `git-<上一个 sha7>`，`argocd app diff` 为空（Git 与集群一致），`/healthz` 为 200，连续请求无 5xx。**没有在 staging 演练过自动回滚，就不允许在生产开启 Analysis 自动判定**（CL-G-07）。
