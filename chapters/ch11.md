## 11.1 问题与反模式：改一行 YAML，为什么非要走完整发布

第 10 章把 `order-demo` 组织成了 overlay 与 Chart 双骨架，并让渲染产物进了 PR 附件。但读者很快会撞上一个很实际的摩擦：为了确认「改一个 `replicas` 到底对不对」，仍然要开 PR、等四道关卡、合并、再走一遍发布，才能从集群上看到结果。**合成案例**（本书统一采用虚构合成案例，见第 1 章）：某团队嫌这个回路太长，给本地装了热更新工具，把工作目录直接指向了共享的 staging 集群；某次 `replicas: "three"`（把整数写成了字符串）被热推送上去，`kubectl apply` 在 staging 直接报 schema 错误，而同一时刻别人正在 staging 做验收，两个人互相以为是对方改坏了配置。更麻烦的是，团队只在单一 K8s 版本上验证过清单，集群升级到新版本后，一批字段被判定为移除/改名，书里的示例和仓库里的清单同时失效，却没有任何机制提前报警 [R-11-6][R-11-11]。

这里的落差是：**验证被放在了发布之后**。第 2 章的心智模型说控制循环会持续收敛，但收敛的是「写进集群的声明」，不是「声明本身对不对」[R-11-9]。声明对不对必须在提交之前判定，且判定方式不能随集群版本升级而失效 [R-11-1][R-11-6]。

三个高频反模式，按「现象 → 根因 → 本章替代做法」展开：

**反模式一：只在单一 K8s 版本上验证。** 现象是集群一升级，示例与清单同时失效，且失效点散落在多个 API 版本里 [R-11-6]。根因是把「本地能 apply」当成了「各版本都能 apply」，没有把版本偏差当成一个可测维度 [R-11-11]。本章的替代做法是 CI 里跑 kind 版本矩阵（1.32 / 1.33 / 1.34），每个版本起一个一次性集群做冒烟，让「书中示例与全书配置过时」在 PR 阶段就暴露 [R-11-1][R-11-6]。

**反模式二：热更新工具直接把本地文件推到共享集群。** 现象是绕过 Git 与渲染产物审查，别人的验收被本地改动打断，且审计里查不到这次变更从哪来 [R-11-8]。根因是把「缩短反馈」和「绕过审查」绑在了一起。本章的替代做法是：Tilt 0.x / Skaffold 2.x 只允许指向个人/临时命名空间，护栏由脚本在启动前校验 `KUBECONFIG`；共享环境与生产一律不接受开发回路写入 [R-11-3][R-11-9]。

**反模式三：声明式测试写成一堆 `sleep`。** 现象是测试又慢又 flaky，等待时间全靠拍脑袋，版本矩阵上一半 job 随机红。根因是用「睡够时间」代替「断言终态」。本章的替代做法是用 kuttl 的断言与超时：`00-assert.yaml` 声明 `readyReplicas: 2`，由 kuttl 轮询到满足或超时，而不是 `sleep 60` 后碰运气 [R-11-5][R-11-10]。

> **与前两章的分工**：第 10 章把 kubeconform / conftest 定位为**发布前的渲染审查关卡**，本章定位为**本地与多版本验证环**，工具名重复但定位不重复（见第 10 章）；第 12 章的流水线阶段会接住本章的四层校验，不得重复也不得遗漏（见第 12 章）；第 25 章才把 `conftest` 的规则库升级成集群侧准入策略，本章的 CI 静态校验**不得叫「准入」**（见第 25 章）[R-11-7]。

### 11.1.1 复盘：升级后字段被移除的多版本定位过程（兼论附录 A 版本矩阵维护法）

反模式一在 11.1 只给了结论：单版本验证会在集群升级后集体失效。这里补一次**可复现的定位过程**，说明「字段被移除」到底是怎么被多版本矩阵抓出来的，以及为什么必须靠附录 A 把版本号锁死。

**现场**。某团队把 `order-demo` 的 overlay 跑在 1.32 上，CI 的四层校验全绿。集群从 1.32 滚动升级到 1.33 后，运维在 staging 用 `kubectl apply -k` 推送同一份清单，第 1 层 kubeconform 在本地却仍报通过——因为本地 kubeconform 还用着 1.32 的 schema 缓存。真正的失效点在 `batch/v1 Job`（worker 的离线关单任务）上：团队误把 `spec.activeDeadlineSeconds` 写进了 1.33 已不再推荐的旧字段路径；另一个点是 `PodDisruptionBudget` 的 `apiVersion: policy/v1beta1` 在 1.33 被正式移除，清单里残留了一个该版本的 PDB。两个字段在 1.32 上能 apply，在 1.33 上一 apply 就报 `no matches for kind "PodDisruptionBudget" in version "policy/v1beta1"`。

**用版本矩阵定位**。如果只在 1.32 上验证，这两个问题永远不会暴露。我们依赖 11.4 的 `matrix.k8s: ["1.32","1.33","1.34"]`：在 1.33 那个 job 上，`kubectl apply --dry-run=server` 第一次红，报错明确指向 `policy/v1beta1` 与 PDB 这一对象；`kubeconform -strict` 在 1.33 的 schema 下也立刻标出 `activeDeadlineSeconds` 已不在 `batch/v1 Job` 的 schema 里。定位过程因此能画出一条最短路径：**先按 `matrix.k8s` 定位到「红」发生在哪个版本（这里是 1.33），再 diff 该版本报错涉及的 apiVersion / 字段，最后在附录 A 确认该字段在此版本的归属状态**，而不是逐文件肉眼排查 [R-11-6][R-11-1]。`fail-fast: false` 让三个版本都跑完，正是为了把「偏差落在哪一版」这个事实固化下来，而不是在第一个红的版本上草草回退 [R-11-6]。

**附录 A 版本矩阵维护法**。版本矩阵不是写死在 `hack/kind-matrix.yaml` 就完事。维护职责有三：
1. **节点镜像小版本锁附录 A**：`kindest/node:v1.32.0` 这类 tag 必须逐版本登记进附录 A 的「kind 发布对照表」，CI 不允许用浮动 tag；升级 kind 时，先改附录 A 再改 `node_images`，保证「书里写的版本号」和「CI 真正拉的镜像」一致（这正是 `validate.sh` 开头一致性断言要兜住的事）[R-11-1]。
2. **字段归属随版本更新**：每升级一个 Kubernetes 小版本，去官方版本偏差策略核对一次被移除 / 改名的 apiVersion 与字段，把结论登记进附录 A 的「字段 × 版本」矩阵；本书示例里凡涉及 `policy/v1`、`batch/v1`、`apps/v1` 的清单，都以附录 A 该行的「最低可用版本」为下限 [R-11-6]。
3. **三版本窗口滚动**：当集群普遍升级到 1.34 / 1.35 时，矩阵下限从 1.32 上移，旧版本移出矩阵——但移出前必须在附录 A 标注「该版本于何次升级后退役」，并保留至少一个发布周期的双版本重叠，避免一次把书中示例全量改写 [R-11-11]。

这套维护法的本质是：把「某字段在哪一版失效」从一次性的排障经验，沉淀成附录 A 里可查、可复用、可审计的矩阵；它和 11.4 的 `kind-matrix.yaml` 形成「单一数据源（YAML）+ 权威记录（附录 A）」的双保险，缺一不可 [R-11-6][R-11-1]。

## 11.2 范式与决策树：四层校验，把判定压到提交之前

本章要回答的决策问题是：**怎样把「这份清单到底对不对」的验证，压缩到提交之前，并且不会随 K8s 版本升级而失效？**

答案是把验证拆成四层，每层有明确的检查对象、运行位置与失败定位方式 [R-11-2][R-11-4][R-11-5]：

| 层 | 工具（主版本） | 检查什么 | 在哪跑 | 失败如何定位 |
|---|---|---|---|---|
| 1 语法 / 结构 | kubeconform 0.x | 渲染产物的字段、类型、apiVersion 是否符合 schema | 本地 + CI static job | 报错直接给出资源、字段路径与期望类型 [R-11-4] |
| 2 组织策略 | conftest 0.x | 非 root、标签、镜像仓库白名单等组织规则 | 本地 + CI static job | 输出命中的 Rego 规则名与资源 [R-11-2] |
| 3 声明式行为测试 | kuttl 0.x（备选 chainsaw 0.x） | 应用部署后是否真的收敛到期望终态 | 一次性 kind 集群 | 断言超时给出期望值与实际值 diff [R-11-5][R-11-10] |
| 4 真实集群冒烟 | kind 0.x 版本矩阵（k3d 5.x 仅作本地对比） | 各 K8s 版本下能否 apply、能否 `curl` 通 | CI matrix job | 按 `matrix.k8s` 定位到具体版本 [R-11-1][R-11-6] |

四层的顺序不可交换：先做不需要集群的 1、2 层（秒级反馈），再做需要集群的 3、4 层（分钟级反馈），让最便宜的检查先拦住最常见的错误 [R-11-8][R-11-9]。这也解释了为什么「提交一个错误字段被 CI 拦下」是本章的核心演示——`replicas: "three"` 这种类型错误应该在**第 1 层**就被 kubeconform 拦住，根本不该走到起集群那一步 [R-11-4]。

**一棵可判定的验证决策树**：

```
kustomize build 能否产出渲染产物？            否 → 第 10 章 render-diff（见第 10 章）
        │ 是
第 1 层 kubeconform -strict 通过？            否 → 字段/类型/schema 错误，按报错改清单
        │ 是
第 2 层 conftest 通过？                       否 → 组织策略违规，按规则名改清单
        │ 是
第 3 层 kuttl 断言终态通过？                 否 → 行为未收敛，查探针/副本数（见第 8 章）
        │ 是
第 4 层 1.32 / 1.33 / 1.34 三个 job 全绿？    否 → 版本偏差，按 matrix.k8s 定位并锁附录 A
        │ 是
→ 四层齐备，可以带着这份清单进入第 12 章流水线
```

「CI 里跑多版本 K8s 矩阵是防止书中示例与全书配置过时的机制，不是可选项」——这是本章第 2 条结论，依据是 Kubernetes 的版本与版本偏差策略：API 会按版本移除，单版本验证无法覆盖一个版本窗口 [R-11-6][R-11-11]。第 3 条结论是「本地热更新回路的价值在于缩短反馈，但绝不能成为绕过渲染产物审查的路径」[R-11-8][R-11-10]。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：临时预览环境必须由 PR 自动生成、随 PR 关闭自动销毁；生命周期不绑定 PR 的预览环境，一定会变成成本黑洞。
>
> **论证**：预览环境的价值在于「让 reviewer 在合并前看到一个真实跑起来的版本」，因此它的生命周期天然应该与 PR 一致：PR 在，环境在；PR 合了或关了，环境就没有存在理由。一旦允许「手工创建、手工保留」，就会出现没人认领的常驻集群：命名空间里跑着三个星期前的镜像，节点与存储持续计费，却没有任何一次变更与之对应。更糟的是，这些残留环境往往还挂着共享凭据与开放入口，成为审计与安全的盲区 [R-11-8][R-11-9]。把销毁动作绑到 PR 关闭事件上，是唯一能让「环境数量」随「活跃变更数量」自动收敛的机制；成本归因时也只有这样才能把费用精确归到某次变更（口径见第 18 章）。
>
> **反例与前提**：这不等于「所有环境都该短命」。第 4 章定义的 dev / staging / prod 是长期环境，有独立凭据、独立配额与独立晋升入口（见第 4 章），它们不随 PR 销毁。另一个反例是需要跨 PR 复现的性能基线环境：那种环境应当被显式登记为「长期资产」并纳入成本台账，而不是以「预览环境」的名义悄悄常驻。跳过生命周期绑定的典型代价见第 18 章成本归因与第 26 章租户隔离。

### 11.2.1 成本对照：四层校验 × 反馈时长 × 失败定位

11.2 的四层表回答了「查什么、在哪查」，但没回答「每层花多少时间、失败了好不好定位」。把成本摊开，才能理解为什么顺序是 1→2→3→4 不可交换 [R-11-8][R-11-9]。

| 层 | 工具 | 触发位置 | 反馈时长（典型） | 失败定位成本 | 失败定位方式 |
|---|---|---|---|---|---|
| 1 语法/结构 | kubeconform | 本地 `--static` 或 CI static job | 秒级（<5s） | 极低 | 报错含资源名、字段路径、期望类型 [R-11-4] |
| 2 组织策略 | conftest | 同上 | 秒级（<10s） | 低 | 命中 Rego 规则名 + 资源 [R-11-2] |
| 3 声明式行为 | kuttl | 一次性 kind 集群 | 分钟级（30–120s） | 中 | 断言超时打印期望/实际 diff [R-11-5] |
| 4 真实集群冒烟 | kind 版本矩阵 | CI matrix job ×3 | 分钟～十分钟级 | 高（但可分区） | 按 `matrix.k8s` 定位到具体版本 [R-11-1][R-11-6] |

成本的三条结论：
1. **最便宜的检查先拦最常见的错误**：`replicas: "three"` 这类类型错误应在第 1 层秒级拦下，根本不该走到起集群；让便宜层前置，等价于把「开发者的等待」压缩到最小 [R-11-9]。
2. **失败定位成本随层递增，但每层都有可读输出**：没有一层是「一句校验失败」——即便最贵的第 4 层，也能凭 `matrix.k8s` 定位到是 1.33 而非 1.32 红，避免「全红但不知哪版」的黑盒 [R-11-6]。
3. **第 4 层的「高成本」靠「只跑一次必要矩阵」摊薄**：`fail-fast: false` 让三版本并行、随 job 销毁（见 11.4），单次 PR 的边际成本固定，不会随仓库变大线性增长 [R-11-1]。

> 这张对照图与 11.2 决策树互为表里：决策树决定「顺序」，本图决定「为什么这个顺序省钱」；两者共同支撑「四层齐备才能进第 12 章流水线」的结论 [R-11-8]。

## 11.3 工具选型：验证工具分层表，含「何时不该用」

本章唯一示例实现按 `book/decisions.md` 的单一示例原则收敛：本地集群用 kind 0.x（第 6 章已用），四层校验工具按上表固定；k3d 5.x、chainsaw 0.x、Telepresence 2.x 只在矩阵里作对比，不给第二套实现 [R-11-1][R-11-7]。

| 层 / 工具 | 主版本 | 检查什么 | 在哪跑 | 何时不该用（本章相关的一条） | 失败如何定位 |
|---|---|---|---|---|---|
| kubeconform | 0.x | schema / 字段类型 | 本地 + CI | 想校验组织策略时——它只管结构不管规则，交给 conftest [R-11-4] | 报错含资源名与字段路径 |
| conftest | 0.x | 组织策略（Rego） | 本地 + CI | 想做集群准入拦截时——那是第 25 章的事，别把静态扫描叫准入 [R-11-2][R-11-7] | 输出命中的规则名 |
| kuttl | 0.x | 声明式终态断言 | 一次性 kind | 只想校验语法时——起集群是浪费 [R-11-5] | 断言超时打印期望/实际值 |
| chainsaw | 0.x | 同上，另一种断言语法 | 一次性 kind | 团队已统一 kuttl 时——两套断言语法是净负担 [R-11-10] | 同 kuttl |
| kind | 0.x | 多版本真实集群 | CI matrix | 只想做本地快速预览时——用开发回路工具即可 [R-11-1] | 按 `matrix.k8s` 定位 |
| k3d | 5.x | 本地多集群（k3s 底座） | 仅本地 | 需要严格对齐上游 K8s 行为时——k3s 与上游有差异，版本矩阵以 kind 为准 [R-11-1] | 查集群名与节点镜像 |
| Tilt / Skaffold / Telepresence | 0.x / 2.x / 2.x | **仅开发回路**：热更新、端口转发、远程替换 | 个人/临时命名空间 | **绝不指向共享或生产集群**，也绝不替代渲染产物审查 [R-11-3][R-11-8] | 查 `KUBECONFIG` 与命名空间白名单 |
| Kyverno CLI | 1.x | 策略离线校验 | 本地 + CI | 想同时做准入时——集群侧策略库在第 25 章，本章只做离线 [R-11-7] | 输出命中的策略名 |

**最小接入 diff**（本章只加校验，不改第 6–10 章任何应用清单）：

```diff
+ hack/kind-matrix.yaml                 # 新增：1.32/1.33/1.34 版本矩阵数据源
+ hack/validate.sh                      # 新增：四层校验入口（--static / --cluster）
+ hack/dev-loop.yaml                    # 新增：本地开发回路护栏声明（非 K8s 对象）
+ hack/dev-loop.sh                      # 新增：启动前校验 KUBECONFIG 与命名空间
+ tests/kuttl/kuttl-test.yaml           # 新增：TestSuite
+ tests/kuttl/gateway-ready/00-install.yaml
+ tests/kuttl/gateway-ready/00-assert.yaml
+ .github/workflows/validate.yml        # 新增：四层校验 + 版本矩阵 job
   deploy/**                            (第 6–10 章，零改动)
   .github/workflows/validate-manifests.yml  (第 10 章，零改动)
```

> 「零改动」是本章的验收点：`git diff ch10-helm..ch11-validate -- deploy/` 应当为空。本章只加校验，不改应用——这也是 11.5 回滚方案能保持极简的原因。

**升级路径**：新增一条策略规则时，先在 `policy/` 里以 `warn` 级别跑一个 PR 周期，观察误伤率后再升为 `deny`；K8s 版本矩阵新增一个版本时，先加进 `hack/kind-matrix.yaml` 并让 `hack/validate.sh` 断言 workflow 的 `matrix.k8s` 与之逐项一致，再合入。**回滚路径**：本章只加校验不改应用；若新规则误伤，回退 `validate.yml` / `validate-manifests.yml` 到上一版并标注误伤原因；应用侧若因误判被拦，按 11.5 方案 B 回到 Git 上一 tag 重新 `apply -k`。生产变更必须回到 Git（全书公理 5，见第 3 章）。

### 11.3.1 kuttl 与 chainsaw 断言语法对照及 flaky 测试治理

11.3 选型矩阵把 chainsaw 0.x 列在 kuttl 旁边、并标注「团队已统一 kuttl 时，两套断言语法是净负担」。这里把两种断言语法摆在一起，并给出 flaky 治理的落地方法，方便读者选定后不再摇摆 [R-11-5][R-11-10]。

**kuttl 的断言**：以「期望资源的最终状态文件」表达，文件名 `00-assert.yaml`，kuttl 轮询直到实际状态匹配或超时。上例 `tests/kuttl/gateway-ready/00-assert.yaml` 直接写 `status.readyReplicas: 2`，写法就是普通 K8s 资源清单里只保留「想断言的字段」，缺失字段不参与比较。优点是直观、与 `kubectl get -o yaml` 同源；缺点是不能表达「跨资源关系」或「数值比较」（例如「副本数 ≥ 2」只能写成等于 2）[R-11-5]。

**chainsaw 的断言**：把断言内联进 `TestStep` 的 `assert:` 段，用 `resource`（按对象比对）或 `jsonPath`（用表达式比较）两种形式。例如：

```yaml
apiVersion: chainsaw.kyverno.io/v1alpha1
kind: Test
metadata:
  name: gateway-ready
spec:
  steps:
    - try:
        - apply:
            file: tests/chainsaw/gateway.yaml
    - assert:
        - resource:
            apiVersion: apps/v1
            kind: Deployment
            metadata:
              name: gateway
              namespace: order-demo-dev
            status:
              readyReplicas: 2
        - jsonPath:
            # 数值比较：副本数落在期望值
            resource: deployment/gateway
            namespace: order-demo-dev
            path: status.readyReplicas
            value: 2
```

chainsaw 额外支持 `script`（跑一段命令判断退出码）与 `pod` 日志抓取，适合「验证一个 Job 跑完且日志含某关键字」这类 kuttl 表达起来别扭的场景 [R-11-10]。

**决策**：只选一套。kuttl 心智负担小、与 `kubectl` 同构，是本书示例；chainsaw 表达力强但要引入 Kyverno 生态约定（本书第 25 章才用 Kyverno）。两者并存只会增加 reviewer 的认知成本与 CI 维护面 [R-11-7]。

**flaky 治理**。声明式测试也会有 flaky，但根因几乎不是「机器慢」，而是误用等待：
- **用 `sleep` 代替断言**（反模式三）：一律改为 `00-assert.yaml` 终态轮询；kuttl 的 `timeout` 控制上限，超时即失败而非碰运气 [R-11-5]。
- **断言字段过早**：在 `readyReplicas` 之前去断言 `image` 或 `labels` 没问题，但断言 `readyReplicas: 2` 时若探针配错（第 8 章），Pod 永远不 ready，应让测试**稳定失败**暴露问题，而不是加 `sleep` 掩盖 [R-11-10]。
- **并发打同一命名空间**：`kuttl-test.yaml` 里 `parallel` 调到 >1 会让多个 TestStep 抢 `order-demo-dev`，制造偶发冲突；本书示例固定 `parallel: 1`，用「每个用例独立命名空间」替代提速 [R-11-5]。
- **版本矩阵上的随机红**：把第 4 层（kind 版本矩阵）与第 3 层（kuttl 行为测试）拆成独立 job，让 flaky 只污染「真实集群」那一层，静态两层保持秒级稳定，避免一次 kind 拉镜像超时连累结构校验 [R-11-1]。

flaky 治理的底线：**测试要么稳定通过，要么稳定失败，不存在「偶尔绿」是可接受的状态**；出现 flaky 先查断言与并发，不要调大 `timeout` 或加 `sleep` 来压制 [R-11-9]。

**`hack/validate.sh`**（四层校验入口，可复制执行）

```bash
#!/usr/bin/env bash
set -euo pipefail
MODE="${1:---static}"
NS=order-demo-dev
RENDER=/tmp/rendered.yaml

# 矩阵一致性断言：workflow 的 matrix.k8s 必须与数据源逐项一致
MATRIX=$(yq -r '.kubernetes_versions | join(",")' hack/kind-matrix.yaml)
WORKFLOW=$(grep -A6 'matrix:' .github/workflows/validate.yml \
  | grep -oE '"1\.[0-9]+"' | tr -d '"' | paste -sd, -)
if [ "${MATRIX}" != "${WORKFLOW}" ]; then
  echo "FAIL: kind-matrix.yaml (${MATRIX}) 与 workflow matrix (${WORKFLOW}) 不一致" >&2
  exit 1
fi

kustomize build deploy/overlays/dev > "${RENDER}"

echo "== 第 1 层 · 语法/结构（kubeconform）=="
kubeconform -strict -summary "${RENDER}"

echo "== 第 2 层 · 组织策略（conftest）=="
conftest test "${RENDER}" -p policy/

if [ "${MODE}" = "--static" ]; then
  echo "static layers OK"
  exit 0
fi

echo "== 第 3 层 · 声明式行为测试（kuttl）=="
kubectl kuttl test --config tests/kuttl/kuttl-test.yaml

echo "== 第 4 层 · 真实集群冒烟 =="
kubectl apply -k deploy/overlays/dev
kubectl -n "${NS}" rollout status deployment/gateway --timeout=120s
kubectl -n "${NS}" port-forward svc/gateway 8080:8080 >/dev/null 2>&1 &
PF=$!
trap 'kill "${PF}" 2>/dev/null || true' EXIT
for i in $(seq 1 30); do
  curl -fsS http://127.0.0.1:8080/healthz >/dev/null 2>&1 && break
  sleep 1
done
curl -fsS http://127.0.0.1:8080/healthz
echo "cluster smoke OK (k8s ${K8S_VERSION:-local})"
```

> `--static` 只跑不需要集群的两层，本地改一行 YAML 的反馈是秒级；`--cluster` 由 CI matrix job 调用，跑完四层 [R-11-2][R-11-4][R-11-5]。脚本开头的矩阵一致性断言，保证「书里写的版本号」和「CI 真正跑的版本号」不会各说各话 [R-11-6]。

**`hack/dev-loop.sh`**（启动前护栏，可复制执行）

```bash

set -euo pipefail
CTX="$(kubectl config current-context)"
NS="$(yq -r '.allowed_namespace' hack/dev-loop.yaml)"

case "${CTX}" in
  kind-*) ;;

esac
```

**`.github/workflows/validate.yml`**（四层校验 + 版本矩阵）

```yaml
name: validate
on:
  pull_request:
    paths:
      - "deploy/**"
      - "policy/**"
      - "tests/kuttl/**"
      - "hack/**"
jobs:
  static:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 第 1–2 层 · 结构与策略（秒级反馈）
        run: ./hack/validate.sh --static
  cluster-matrix:
    runs-on: ubuntu-latest
    needs: static
    strategy:
      fail-fast: false
      matrix:
        k8s: ["1.32", "1.33", "1.34"]
    steps:
      - uses: actions/checkout@v4
      - name: 起对应版本的一次性 kind 集群
        run: |
          IMAGE=$(yq -r ".node_images.\"${{ matrix.k8s }}\"" hack/kind-matrix.yaml)
          kind create cluster --name "order-demo-${{ matrix.k8s }}" --image "${IMAGE}"
      - name: 第 3–4 层 · 行为测试与真实集群冒烟
        env:
          K8S_VERSION: ${{ matrix.k8s }}
        run: ./hack/validate.sh --cluster
      - name: 随 job 结束销毁集群
        if: always()
        run: kind delete cluster --name "order-demo-${{ matrix.k8s }}"
```

> `fail-fast: false` 是刻意的：三个版本必须都跑完，才能知道偏差落在哪个版本 [R-11-6]；`if: always()` 保证集群随 job 销毁，正是 11.2 本书观点「生命周期不绑定就会变成本黑洞」在验证环自身的落地 [R-11-1]。`matrix.k8s` 与 `hack/kind-matrix.yaml` 的一致性由 `validate.sh` 开头断言。**注意**：`kubeconform` / `conftest` 在这里是**多版本验证环的静态两层**，与第 10 章 `.github/workflows/validate-manifests.yml` 里「发布前渲染审查」的同名关卡分工不同、不重复定位（见第 10 章）[R-11-2][R-11-4]。

**演示：提交一个错误字段被 CI 拦下**（可复制执行）

```bash

git checkout -b demo/bad-replicas

# 2. 开 PR 后，static job 的第 1 层 kubeconform -strict 会失败，报错要点：
#    rendered.yaml - Deployment gateway is invalid: problem validating schema
#      spec.replicas: Invalid type. Expected: integer, given: string
#    （具体措辞随 kubeconform 版本变化，但一定包含资源名 gateway、字段 spec.replicas
#      与「Expected: integer」；见 references/ch11.yaml 的 R-11-4 支撑说明）

# 3. 本地复现同一条拦截（不必等 CI）
./hack/validate.sh --static || echo "已按预期被第 1 层拦下"

# 4. 修复并把 PR 转绿

```

> 这个演示是本章的验收动作：**错误字段在第 1 层（不需要集群）就被拦下**，既没有走到起 kind 集群，也没有绕过渲染产物审查 [R-11-4][R-11-9]。报错里带资源名、字段路径与期望类型，因此是可读、可定位的，不是一句「校验失败」[R-11-8]。

### 11.4.1 预览环境随 PR 自动创建/销毁的 workflow 与成本归因示例

11.2 的本书观点断言「预览环境生命周期必须绑定 PR」。这里给出可直接落地的 workflow，并演示成本如何归因到某次变更 [R-11-8][R-11-9]。

**workflow**（`.github/workflows/preview-env.yml`）：PR 打开/推送时按 PR 号起一个临时命名空间 `order-demo-preview-<pr>`，关闭或合并时销毁。它复用 `deploy/overlays/dev` 的渲染产物，仅替换命名空间与 `managed-by` 标签，不引入任何新配置契约值。

```yaml
name: preview-env
on:
  pull_request:
    types: [opened, synchronize, reopened, closed]
jobs:
  provision:
    if: github.event.action != 'closed'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 起临时 kind 集群并创建预览命名空间
        run: |
          kind create cluster --name "preview-${{ github.event.number }}"
          kubectl create namespace "order-demo-preview-${{ github.event.number }}"
      - name: 用 dev overlay 渲染到预览命名空间
        run: |
          kubectl kustomize "deploy/overlays/dev" \
            | sed "s/order-demo-dev/order-demo-preview-${{ github.event.number }}/g" \
            | kubectl apply -n "order-demo-preview-${{ github.event.number }}" -f -
      - name: 跑第 3 层行为断言验证预览可用
        run: kubectl kuttl test --config tests/kuttl/kuttl-test.yaml
  teardown:
    if: github.event.action == 'closed'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 随 PR 关闭销毁预览集群
        run: kind delete cluster --name "preview-${{ github.event.number }}"
```

护栏与 11.4 一致：预览命名空间不挂生产凭据，Secret 仍由 ESO 从 `order-demo/db-credentials` 注入（路径含 `/`，绝不作为对象名），且仅包含 dev 级只读数据 [R-11-1][R-11-9]。

**成本归因示例**（只给相对比例与归因口径，不写单价，见 glossary 成本约定）。假设一次变更的预览环境消耗 = 1 个临时 kind 集群 × PR 存活时长。归因口径：

| 维度 | 取值 | 归属 |
|---|---|---|
| 成本对象 | `preview-<pr-number>` 集群 | 该 PR 对应的那次变更 |
| 计量 | 集群节点数 × 存活小时数 | 计入「变更评审」成本池，不计入 dev/staging/prod 长期环境 |
| 销毁触发 | `pull_request: closed` | 合并或放弃即停止计费，无残留 |

由于销毁绑在 `closed` 事件，环境数量随活跃 PR 数量自动收敛：10 个在审 PR = 10 个临时集群，全部合/关后归零，不会出现「三个星期前的镜像还在计费」的常驻黑洞 [R-11-8][R-11-9]。这正是 11.2 本书观点的工程闭环：把「环境数量」与「活跃变更数量」用事件绑定锁死，成本归因才有干净的对账边界。

## 11.5 验证与回滚（回滚方案先于发布方案）

**回滚**（把线上恢复到上一个已知良好版本，详见第 13 章）在本章最轻：本章只加校验、不改应用，所以「回滚」主要指的是**校验规则本身**，应用侧只需保留一条回到 Git 的路径。

**验证命令**（仓库根目录执行，需已安装 kind 0.x / kubectl / kustomize 5.x / kubeconform 0.x / conftest 0.x / kuttl 0.x / yq / curl，版本见附录 A）：

```bash
chmod +x hack/validate.sh hack/dev-loop.sh
./hack/validate.sh --static
kubectl apply -k deploy/overlays/dev --dry-run=server
./hack/dev-loop.sh --help >/dev/null 2>&1 || true   # 仅检查脚本语法，不启动 Tilt
K8S_VERSION=1.32 ./hack/validate.sh --cluster
K8S_VERSION=1.33 ./hack/validate.sh --cluster
K8S_VERSION=1.34 ./hack/validate.sh --cluster
git diff --stat ch10-helm..HEAD -- deploy/          # 应为空：本章零改动应用清单
```

**逐条通过标准**：

| 判据 | 怎么查 | 期望结果 |
|---|---|---|
| 四层校验齐备 | `./hack/validate.sh --static` 与 `--cluster` 的日志 | 依次出现第 1/2/3/4 层，全部 0 退出 |
| 版本矩阵 ≥ 3 个版本 | `.github/workflows/validate.yml` 的 `matrix.k8s` 与 `hack/kind-matrix.yaml` | 均为 `1.32 / 1.33 / 1.34`，且一致性断言通过 |
| 错误字段能被拦 | `./hack/validate.sh --static` 在 `replicas: "three"` 下 | 非零退出，报错含 `gateway`、`spec.replicas`、`Expected: integer` |
| 开发回路不指向共享生产 | `hack/dev-loop.sh` 在非 `kind-*` 上下文下 | 直接 `FAIL`，不启动 Tilt |
| 应用清单零改动 | `git diff --stat ch10-helm..HEAD -- deploy/` | 无输出 |
| 集群随 job 销毁 | workflow 的 `if: always()` 步骤 | 三个版本集群在 job 结束后均 `kind delete` |

最后两项容易被跳过：它们证明本章的验证环没有偷偷改应用、也没有留下常驻集群 [R-11-1][R-11-8]。

**回滚命令 / 步骤**（先演练、后发布）：

```bash
# 方案 A：新规则误伤（本章最常见的回滚原因）——只回退校验，不动应用
git checkout <上一 tag> -- .github/workflows/validate.yml \
                           .github/workflows/validate-manifests.yml \
                           policy/ hack/validate.sh
echo "误伤原因：<在此写明被误伤的资源与规则名，供统稿复查>"
./hack/validate.sh --static

# 方案 B：应用侧若因误判被拦，回到 Git 上一 tag 重新声明
git checkout <上一 tag> -- deploy/overlays/dev/ deploy/base/
kubectl apply -k deploy/overlays/dev
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s

# 方案 C：版本矩阵某个 job 持续失败，先降级为两版本并登记
yq -i '.kubernetes_versions = ["1.32", "1.33"]' hack/kind-matrix.yaml
# 同步修改 .github/workflows/validate.yml 的 matrix.k8s，再跑一致性断言
./hack/validate.sh --static
```

> **为什么方案 B 用 `git checkout` 而不是 `@<上一 tag>`**：卡片里 `kubectl apply -k deploy/overlays/dev@<上一 tag>` 是简写，`kubectl` 不接受 `@` 语法；正确表达是回到 Git 上一 tag 取出声明再 `apply -k`，与全书公理 5 一致（见第 3 章），也与第 9 章「一致性备注」⑤、第 10 章「一致性备注」⑤ 口径一致 [R-11-9]。方案 A 里「回退校验规则 + 标注误伤原因」是本章特有动作：校验本身是代码，误伤必须留痕，否则下一次升级会重蹈覆辙。
