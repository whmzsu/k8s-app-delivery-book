## 28.1 问题与反模式：控制器写起来容易，写对很难

**合成案例**（教学合成，非真实事件）：一个平台组通过第 27 章决策树，确认「证书轮换编排」确实需要自定义控制器，于是动手写。第一版把「调用外部 CA 签发证书」直接放在 reconcile 函数里同步等待，CA 一旦慢，worker 被占满，其他 CR 全部饿死；为了「记住签到第几步」，又把流程中间态写进 `status`，控制器一次重启后从半路继续，签出两张重复证书；最要命的是，控制器自己没有告警，某天它 OOM 后被静默重启，`status` 停在旧值，业务以为「一切正常」，直到证书过期才集体报错 [R-28-2][R-28-4][R-28-6][R-28-8]。注意这个故事里没有一行是「明显写错」的代码——三处都是很自然的实现选择，写完当时都能跑通。

**写第一版时的那次评审**（合成案例，按共性还原，非真实对话）

> **开发**：我把签到第几步写进 `status`，控制器重启就能从半路继续。
> **同事**：那 `status` 里存的就不是观测结果了。
> **开发**：解耦一下，加个 `status.phase` 区分。
> **同事**：重启之后 `phase` 跟真实情况对不上怎么办？
> **开发**：`phase` 是我们自己写的，不会对不上。
> （`status` 由控制器自己写，所以它永远「自己觉得对」——这正是它不能用来记过程的原因。）

这段对话的关键不在谁对谁错，在最后那句：**一个由自己写、自己读的字段，永远无法用来校验自己**。所谓「从半路继续」，实际是从一个没人验证过的断点继续。

三个反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：reconcile 里同步调用外部慢 API。** 现象是 worker 被占满、其他对象饿死、队列堆积；根因是把协调循环当成「一次把事情做完的过程」，而它其实是「反复被触发、随时可被打断的一段短逻辑」。这两者的区别可以用一句话验出来：这段逻辑被打断之后，能不能从零重来？本章的替代做法是**异步化 + 重入队列**：循环里只发起动作、记观测结果、用 `RequeueAfter` 把等待交还给队列，绝不阻塞等外部结果 [R-28-2][R-28-7]。

**反模式二：把中间状态写进 `status`。** 现象是控制器重启后流程走偏、产生重复副作用；根因是违反了第 27 章的语义——`status` 只表达**观测结果**，不是「下一步该做什么」的持久化存储。一旦循环必须依赖上一轮留下的中间态才能算对，就不再幂等、不再可重入。替代做法是让每一步都能从当前实际状态重新推导出来 [R-28-4][R-28-7]。

**反模式三：Operator 自身没有告警。** 现象是它挂了业务静默降级，值班看板一片绿；根因是把控制器当「基础设施」而不是「一个会挂的服务」。基础设施假设自己不会挂，服务假设自己随时会挂——对这两者的要求正好相反：前者要没人管也能跑，后者要有人看着才敢跑。替代做法是给控制器本身配健康指标与告警：reconcile 错误率、队列深度、最近一次成功协调时间，三条缺一不可，且每条都指向 runbook [R-28-6][R-28-8]。这与第 22 章「面向症状的告警」是同一套纪律，只是对象换成了控制器。

> 本章的前提是第 27 章已给出 CRD / Operator / finalizer / 协调循环的正式定义，这里不再复述定义，只把它们变成可测的工程约束。

## 28.2 范式与决策树：幂等是可测的，不是口头承诺

**本章要回答的决策问题**：控制器写起来容易，怎么让它幂等、可测、可观测、可升级？四个词都能落成一条可执行的判据。

**幂等的形式化判据**（本章最核心的一条）：给定同一份 `spec` 与同一 `generation`，连续触发 reconcile N 次，下游副作用（创建的对象数、发出的事件数、外部调用次数）恒为 1；且收敛后 `status.observedGeneration == metadata.generation` [R-28-2][R-28-4]。这条判据之所以可测，是因为它不依赖「我觉得代码没写错」，而依赖重复触发同一事件后数副作用——28.4 的 envtest 用例就是把它写成断言。「我觉得没写错」永远说服得了评审会，数副作用只有一种结果。

**reconcile 五步骨架**：① 读（Get 当前 CR，NotFound 直接返回）→ ② 比（判断删除路径、判断是否已收敛）→ ③ 做（确保下游对象存在，先 Get 再 Create）→ ④ 记（只把观测结果写进 `status`）→ ⑤ 必要时 `RequeueAfter` 重入。短循环原则贯穿始终：任何一步都不阻塞等待外部结果，慢动作一律「发起 + 记状态 + 定时重入」[R-28-2]。五步里最容易写歪的是 ④，因为它看起来只是「顺手记一下」——而这一笔写下的内容，决定了下一轮还能不能从零推导。

**envtest** 的价值在此：它起一个本地 API Server + etcd，加载真实 CRD，让 reconcile 在**不连生产集群**的前提下跑起来 [R-28-1]。于是「重复触发不产生重复副作用」可以在 CI 里每次提交都验，而不是靠上线后观察。这正是第 11 章「从本地到集群的验证环」在控制器层的形态。

**CRD 版本迁移范式**（第 27 章负债清单第 ① 项在这里落地）：`v1alpha1 → v1beta1 → v1` 不是改个字符串，而是一条有顺序的升级链 [R-28-5]：

```
1) 新版本已加入 served、storage 仍指向旧版本，转换 webhook 已部署且健康
2) 观察一个发布窗口，确认新旧版本对象都能读写
3) 把 storage 切到新版本（此时 etcd 里存量对象由转换 webhook 按需转换）
4) 确认无旧版本写入后，把旧版本 served 置 false
5) 清理旧版本 schema 与转换 webhook（降级时按 4→3→2→1 逆向执行）
```

把 storage 切换放在「转换 webhook 已就绪」之后，是这条链唯一的硬约束；反过来做，存量对象会在读出来时被拒绝，等于一次不可回退的数据事故 [R-28-5]。

**OLM 的边界**：Operator Lifecycle Manager 用订阅、升级通道与 CSV 管理 Operator 自身的安装与升级，把「控制器版本」也变成声明式对象 [R-28-3]。但它同时引入一套 CRD 与依赖解析器，**何时不该用**：只有一个集群、只有一个自研 Operator、且已用第 14 章 Argo CD 3.x 管住清单时，再叠一层 OLM 就是第 5 章警戒线里「同一问题域两个控制器」。本章把控制器清单走 Git PR，不引入 OLM。

**reconcile 反模式清单**（每条都对应一个可测症状）：

| 反模式 | 可测症状 | 本章替代做法 |
|---|---|---|
| 循环内同步慢调用 | 队列深度持续 > 50，reconcile P99 飙升 | 异步化 + `RequeueAfter` [R-28-7] |
| `status` 当存储 | 重启后副作用重复、流程错乱 | `status` 只写可重新观测的结果 [R-28-4] |
| 无幂等、无去重 | 同一 CR 触发 N 次创建 N 个下游对象 | `observedGeneration` 短路 + 先 Get 再 Create |
| 忽略 `deletionTimestamp` | 对象卡 `Terminating`、finalizer 永不清理 | 删除路径先清理再移除 finalizer（第 27 章） |
| 事件风暴 | `workqueue_adds_total` 异常放大 | `Owns()` 精确订阅、避免无条件 requeue |

**Operator 自身可观测指标表**（告警规则见 28.4）[R-28-6]：

| 指标 | 含义 | 健康阈值 | 对应告警 |
|---|---|---|---|
| `controller_runtime_reconcile_total` | 协调总次数（按 result 分） | 10m 内 `result="success"` 非 0 | `OperatorNoSuccessfulReconcile` |
| `controller_runtime_reconcile_errors_total` | 协调错误数 | rate 5m 为 0 | `OperatorReconcileErrors` |
| `workqueue_depth` | 待处理队列深度 | 稳态 < 50 | `OperatorQueueDepthHigh` |
| `controller_runtime_reconcile_time_seconds` | 单次协调耗时 | P99 < 1s（短循环） | 观察项，不单独告警 |

**放行表**（判断一个控制器能不能进 staging）。下面的每一问都对应一条已经写好的命令或断言，所以它不是评审提纲，是一组开关：

| 级 | 判据（逐级放行） | 不通过 → 去处 |
|---|---|---|
| 1 | `make test`（envtest）通过、幂等断言为 1？ | 停在开发环境，禁止合并 |
| 2 | `status` 是否只含观测字段、`observedGeneration` 对齐？ | 回 28.2 语义修正 |
| 3 | 控制器 SA 是否最小权限、无 `cluster-admin`？ | 回 28.4 `role.yaml`（CL-S-02） |
| 4 | 三条健康告警已加载且各带 runbook？ | 补 28.4 告警规则 |
| 5 | CRD 版本迁移路径 + 升级 / 回滚演练已跑过？ | 先补演练（CL-G-07） |
| — | 五条全过 | 允许进 staging；prod 仍走第 14 章 GitOps 晋升链 |

### 28.2.1 Operator 自身 SLO 与错误预算（衔接第 20 章）

28.2 的指标表回答「控制器现在好不好」，却没有回答更关键的一句：**坏到什么程度，就该冻结控制器自己的发布**。第 20 章把 SLO 定义成 SLI + 目标 + 窗口，并规定对外错误预算只在旅程入口记一次账；控制器是平台内部组件，没有自己的外部用户旅程，因此它只能拥有**诊断 SLO**——用于冻结自己的升级节奏，不参与业务冻结（第 20 章「记账点唯一」）。换句话说，这个 SLO 的唯一权力是「停」，不是「罚」。

两条 SLI 必须能从 28.4 已埋的指标直接算出来，不新造采集链路：

| SLI | 分子 / 分母 | 为什么这样取 | 目标（28d 滚动） |
|---|---|---|---|
| 协调成功率 | `result="success"` /（`success` + `error`） | `requeue` 与 `requeue_after` 是正常节流，计入分母会让稳态成功率永远低于目标——这是口径错误，不是控制器劣化 | 99.5% |
| 及时收敛率 | `order_demo_operator_convergence_seconds` 中 `le="60"` 的桶 / 总观测数 | 使用者可感的是「改了 CR 多久生效」，不是「协调了几次」 | 99.0% |

预算换算（28 天 = 40,320 分钟）：

| SLI | 目标 | 错误预算 | 等价额度 | 耗尽意味着 |
|---|---|---|---|---|
| 协调成功率 | 99.5% | 0.5% | 约 201 分钟（3h22m）的坏协调额度 | 已无法稳定收敛，此刻升级只会放大故障 |
| 及时收敛率 | 99.0% | 1.0% | 约 403 分钟（6h43m）的超时额度 | 生效时延在劣化，先查慢调用与队列，不要发版 |

燃尽阈值直接沿用第 20 章的 14.4 / 6 / 1 三档，不另立数字（同源）：14.4 对应「1 小时花掉 2% 预算」、6 对应「6 小时花掉 5%」、1 对应 3 天慢性劣化。推导过程与第 20 章逐字相同，改一个数就必须两边同改，否则会出现「业务侧说没超、平台侧已经冻结」的错位。

```yaml
# observability/operator-slo.yaml（Prometheus 3.x 记录规则；与 28.4 的 operator-alerts.yaml 同一个 PR）
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: order-demo-operator-slo
  namespace: observability
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  groups:
    - name: operator-slo
      interval: 30s
      rules:
        # SLI-1：分母刻意排除 requeue / requeue_after，否则正常节流会被算成「坏协调」
        - record: sli:order_demo_operator:reconcile_success_ratio_5m
          expr: |
            sum(rate(controller_runtime_reconcile_total{job="order-demo-operator",result="success"}[5m]))
            /
            sum(rate(controller_runtime_reconcile_total{job="order-demo-operator",result=~"success|error"}[5m]))
        - record: slo:order_demo_operator:error_budget_ratio
          expr: "1 - 0.995"
        - record: slo:order_demo_operator:burn_rate_1h
          expr: |
            (1 - avg_over_time(sli:order_demo_operator:reconcile_success_ratio_5m[1h]))
            / scalar(slo:order_demo_operator:error_budget_ratio)
        - record: slo:order_demo_operator:burn_rate_6h
          expr: |
            (1 - avg_over_time(sli:order_demo_operator:reconcile_success_ratio_5m[6h]))
            / scalar(slo:order_demo_operator:error_budget_ratio)
        - record: slo:order_demo_operator:burn_rate_3d
          expr: |
            (1 - avg_over_time(sli:order_demo_operator:reconcile_success_ratio_5m[3d]))
            / scalar(slo:order_demo_operator:error_budget_ratio)
        # SLI-2：及时收敛率，直方图桶由 28.4 controller 的 convergenceSeconds 观测器上报
        - record: sli:order_demo_operator:converge_within_60s_ratio_5m
          expr: |
            sum(rate(order_demo_operator_convergence_seconds_bucket{job="order-demo-operator",le="60"}[5m]))
            /
            sum(rate(order_demo_operator_convergence_seconds_count{job="order-demo-operator"}[5m]))
        - record: slo:order_demo_operator:release_freeze
          expr: |
            (1 - avg_over_time(sli:order_demo_operator:reconcile_success_ratio_5m[28d]))
            >= scalar(slo:order_demo_operator:error_budget_ratio)
```

> 三处必须同源：`operator-slo.yaml` 的 `objective`（0.995）、`metrics.go` 的桶边界（`le="60"`）、以及第 20 章冻结表里「非必要发布」的定义。改任何一处，都要在 PR 描述里写明另外两处为何不用改——这就是「同源」在控制器上的具体形态：三个文件、一条算式，任何一处单独漂移都会让冻结判定失去依据。

**冻结范围**：`slo:order_demo_operator:release_freeze == 1` 时，冻结**控制器镜像升级**与**CRD storage 轮转**两项；不冻结 `order-demo` 业务发布（那是第 20 章 `gateway` 预算的职责，两本账不能混）。**豁免**：修故障的回滚、安全补丁、为恢复收敛而做的止血变更——豁免不等于放行，须按第 20 章口径登记例外编号与到期时间。**解除条件**：滚动窗口滚出坏事件后剩余预算 > 0，且连续 3 个快窗口无燃尽告警。

为什么 CRD 迁移必须被同一条预算挡住：storage 轮转是本章唯一的**不可逆点**（详见 28.5.1），而控制器正在劣化时做不可逆操作，等于在余量最低的时刻做风险最高的事。反过来，控制器镜像回滚是可逆的，预算耗尽时它反而是允许的动作——这条不对称是整套 SLO 的落点。

> 一条护栏：不要把这套 SLO 写进对外 SLA，也不要让它冻结业务发布。控制器抖一下冻结整条业务线，是第 20 章反例里「诊断口径挂了冻结阈值」的典型翻版。

> **本书观点（本章的定位说明，不需要外部背书）**
>
> **主张**：本章是**平台团队可选阅读**，绝大多数读者应跳过它直接去第 29 章；它不承担「要不要用 Operator」的决策，只服务「决策树已命中第 ⑤ 项」之后的少数人。
>
> **论证**：全书抽象层级在这里骤升（9.1 问题 7）——从「改一份清单」跳到「用 Go 写一个会常驻、会挂、要升级的控制器」。若把它放进主线必经路径，90% 读者会为一套自己根本不会写的东西付出理解成本，甚至误以为「上 K8s 就得会写 Operator」。第 27 章的结论恰恰相反：多数人需要的是会评估现成 Operator（第 29 章）。把深水区标成可选、并给出明确的跳过路径，是按阅读概率组织内容，而不是降低标准。
>
> **反例与适用前提**：这不等于「工程内容可以潦草」。对确实要写控制器的平台团队，本章四条边界（幂等、可测、可观测、可升级）每一条都是上线门禁，缺一条就会在故障时放大故障——28.1 合成案例里三个反模式正是反证。前提是**团队已有专人承担第 27 章那份九项负债清单**；没有这个前提，读本章反而会诱导过度工程。跳过本章的读者不会损失主线连贯性：第 29、30、31 章都不依赖本章的 Go 代码。

## 28.3 工具选型：脚手架、运行时与生命周期管理

按第 1 章 1.4 的版本基线，扩展脚手架为 **Kubebuilder 4.x**，协调循环库为 **controller-runtime 0.x**，集成测试为 **envtest**（K8s 版本矩阵对齐第 11 章，小版本锁附录 A）；Prometheus 3.x 用于控制器自身告警。下表每列都含「何时不该用」[R-28-1][R-28-2][R-28-9]。

| 脚手架 / 工具（主版本） | 生成物 | 维护成本 | 何时不该用 | 升级 / 退出路径 |
|---|---|---|---|---|
| **Kubebuilder 4.x（本章示例实现）** | PROJECT、API 类型、controller 骨架、RBAC markers、Makefile、CRD bases | 中：随 Kubebuilder 大版本重脚手架一次 | 只需要一两个字段校验、没有领域模型时（回第 27 章第 ④ 项）[R-28-9] | 独立 PR 升 Kubebuilder；`go.mod` 锁 controller-runtime 版本 |

```go
package controller

import (
	"context"
	"fmt"
	"time"

	corev1 "k8s.io/api/core/v1"
	apierrors "k8s.io/apimachinery/pkg/api/errors"
	metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
	"k8s.io/apimachinery/pkg/runtime"
	ctrl "sigs.k8s.io/controller-runtime"
	"sigs.k8s.io/controller-runtime/pkg/client"
	"sigs.k8s.io/controller-runtime/pkg/controller/controllerutil"
	"sigs.k8s.io/controller-runtime/pkg/log"

	opsv1alpha1 "order-demo/operator/api/v1alpha1"
)

const cleanupFinalizer = "ops.example.com/cleanup"

type MaintenanceWindowReconciler struct {
	client.Client
	Scheme *runtime.Scheme
}

// +kubebuilder:rbac:groups=ops.example.com,resources=maintenancewindows,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=ops.example.com,resources=maintenancewindows/status,verbs=get;update;patch
// +kubebuilder:rbac:groups=ops.example.com,resources=maintenancewindows/finalizers,verbs=update
// +kubebuilder:rbac:groups="",resources=configmaps,verbs=get;list;watch;create;update;patch;delete

func (r *MaintenanceWindowReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	logger := log.FromContext(ctx)

	// ① 读：NotFound 不是错误，是对象已删
	var mw opsv1alpha1.MaintenanceWindow
	if err := r.Get(ctx, req.NamespacedName, &mw); err != nil {
		return ctrl.Result{}, client.IgnoreNotFound(err)
	}

	// ② 比之一：删除路径 —— 先清理、再移除 finalizer，绝不跳过（第 27 章）
	if !mw.DeletionTimestamp.IsZero() {
		if controllerutil.ContainsFinalizer(&mw, cleanupFinalizer) {
			if err := r.cleanup(ctx, &mw); err != nil {
				return ctrl.Result{}, err
			}
			controllerutil.RemoveFinalizer(&mw, cleanupFinalizer)
			if err := r.Update(ctx, &mw); err != nil {
				return ctrl.Result{}, err
			}
		}
		return ctrl.Result{}, nil
	}

	// ② 比之二：幂等短路 —— 已收敛且 generation 未变，零副作用直接返回
	if mw.Status.ObservedGeneration == mw.Generation && mw.Status.Phase == opsv1alpha1.PhaseApplied {
		return ctrl.Result{}, nil
	}

	// ③ 做之一：确保 finalizer 存在（只加一次，随后重入）
	if !controllerutil.ContainsFinalizer(&mw, cleanupFinalizer) {
		controllerutil.AddFinalizer(&mw, cleanupFinalizer)
		if err := r.Update(ctx, &mw); err != nil {
			return ctrl.Result{}, err
		}
		return ctrl.Result{Requeue: true}, nil
	}

	// ③ 做之二：先 Get 再 Create，重复事件不会重复创建下游对象
	cmName := fmt.Sprintf("%s-window", mw.Name)
	cm := &corev1.ConfigMap{}
	err := r.Get(ctx, client.ObjectKey{Namespace: mw.Namespace, Name: cmName}, cm)
	if apierrors.IsNotFound(err) {
		cm = &corev1.ConfigMap{
			ObjectMeta: metav1.ObjectMeta{
				Name:      cmName,
				Namespace: mw.Namespace,
				Labels: map[string]string{
					"app.kubernetes.io/name":       "order-demo",
					"app.kubernetes.io/managed-by": "operator",
				},
			},
			Data: map[string]string{"replicas": fmt.Sprintf("%d", mw.Spec.Replicas)},
		}
		if err := controllerutil.SetControllerReference(&mw, cm, r.Scheme); err != nil {
			return ctrl.Result{}, err
		}
		if err := r.Create(ctx, cm); err != nil {
			return ctrl.Result{}, err
		}
		logger.Info("created downstream ConfigMap", "name", cmName)
	} else if err != nil {
		return ctrl.Result{}, err
	}

	// ④ 记：status 只写观测结果
	mw.Status.ObservedGeneration = mw.Generation
	mw.Status.AppliedReplicas = mw.Spec.Replicas
	mw.Status.Phase = opsv1alpha1.PhaseApplied
	if err := r.Status().Update(ctx, &mw); err != nil {
		return ctrl.Result{RequeueAfter: 5 * time.Second}, err
	}

	// ⑤ 慢动作不在此阻塞：定时重入，保持短循环
	return ctrl.Result{RequeueAfter: 60 * time.Second}, nil
}

func (r *MaintenanceWindowReconciler) cleanup(ctx context.Context, mw *opsv1alpha1.MaintenanceWindow) error {
	cm := &corev1.ConfigMap{}
	cmName := fmt.Sprintf("%s-window", mw.Name)
	err := r.Get(ctx, client.ObjectKey{Namespace: mw.Namespace, Name: cmName}, cm)
	if apierrors.IsNotFound(err) {
		return nil
	}
	if err != nil {
		return err
	}
	return r.Delete(ctx, cm)
}

func (r *MaintenanceWindowReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&opsv1alpha1.MaintenanceWindow{}).
		Owns(&corev1.ConfigMap{}). // 精确订阅，避免事件风暴
		Complete(r)
}
```

```go
var convergenceSeconds = prometheus.NewHistogram(

		Help:    "CR 从 generation 变更到 observedGeneration 对齐的耗时（秒）",
		Buckets: []float64{1, 5, 15, 30, 60, 120, 300},
	},
)

func init() {
	metrics.Registry.MustRegister(convergenceSeconds)
}

// 进程内记录「对象 + generation 首次被看到」的时刻。重启后丢一次样本，
// 代价是这个收敛窗口内少一例观测；相比为它新增 status 字段（第 27 章：status 只放观测结果），前者便宜得多。
var convergenceSeen = struct {
	sync.Mutex
	m map[string]time.Time
}{m: map[string]time.Time{}}

func firstSeenAt(uid types.UID, generation int64) time.Time {
	key := fmt.Sprintf("%s/%d", uid, generation)
	convergenceSeen.Lock()
	defer convergenceSeen.Unlock()
	if t, ok := convergenceSeen.m[key]; ok {
		return t
	}
	convergenceSeen.m[key] = time.Now()
	return convergenceSeen.m[key]
}

func forgetSeen(uid types.UID, generation int64) {
	convergenceSeen.Lock()
	defer convergenceSeen.Unlock()
	delete(convergenceSeen.m, fmt.Sprintf("%s/%d", uid, generation))
}
```

```go
import (
	"context"
	"path/filepath"
	"testing"

	corev1 "k8s.io/api/core/v1"

func TestReconcileIdempotent(t *testing.T) {
	env := &envtest.Environment{
		CRDDirectoryPaths:     []string{filepath.Join("..", "..", "config", "crd", "bases")},
		ErrorIfCRDPathMissing: true,
	}
	cfg, err := env.Start()
	if err != nil {
		t.Fatalf("启动 envtest 失败（KUBEBUILDER_ASSETS 是否已设置）: %v", err)
	}
	defer func() { _ = env.Stop() }()

	scheme := runtime.NewScheme()
	if err := corev1.AddToScheme(scheme); err != nil {
		t.Fatal(err)
	}
	if err := opsv1alpha1.AddToScheme(scheme); err != nil {
		t.Fatal(err)
	}
	c, err := client.New(cfg, client.Options{Scheme: scheme})
	if err != nil {
		t.Fatal(err)
	}

	ns := "default"
	mw := &opsv1alpha1.MaintenanceWindow{
		ObjectMeta: metav1.ObjectMeta{Name: "idem-sample", Namespace: ns},
		Spec:       opsv1alpha1.MaintenanceWindowSpec{Replicas: 3, Reason: "幂等测试"},
	}
	if err := c.Create(context.Background(), mw); err != nil {
		t.Fatal(err)
	}

	r := &MaintenanceWindowReconciler{Client: c, Scheme: scheme}
	req := types.NamespacedName{Name: mw.Name, Namespace: ns}

	// 连续触发同一事件三次：模拟 Informer 重复投递
	for i := 0; i < 3; i++ {
		if _, err := r.Reconcile(context.Background(), req); err != nil {
			t.Fatalf("第 %d 次 reconcile 出错: %v", i+1, err)
		}
	}

	// 断言 1：下游 ConfigMap 恰好一个，副作用不重复
	var cms corev1.ConfigMapList

		t.Fatal(err)

	created := 0

		if cm.Name == "idem-sample-window" {
			created++
		}
	}

		t.Fatalf("幂等失败：期望 1 个下游 ConfigMap，实际 %d 个", created)
	}

	// 断言 2：status 只表达观测结果且与 generation 对齐

		t.Fatal(err)

		t.Fatalf("phase=%s，期望 Applied", got.Status.Phase)

	if len(got.Finalizers) != 1 || got.Finalizers[0] != cleanupFinalizer {
		t.Fatalf("finalizer 异常: %v", got.Finalizers)
	}
```

```bash

d = json.load(sys.stdin)
for item in d["items"]:
    fs = item.get("metadata", {}).get("finalizers", [])
    if fs:
        print(item["kind"], item["metadata"]["name"], fs)
'

# 2) 降级控制器：二选一
# 路径 A：Helm 安装时按历史修订回退
helm rollback order-demo-operator <上一 rev> --namespace order-demo-system
# 路径 B：声明式回退（生产唯一合法路径仍须回到 Git，公理 5，见第 3 章）

  -o jsonpath='{.spec.versions[*].name}{"\n"}'
```

> **为什么 CRD 版本要逆序回退**：升级时「转换 webhook 就绪 → 切 storage → 关旧 served」；回滚必须先把 `storage` 切回旧版本、恢复旧版本 `served: true`，最后才下线转换 webhook，否则存量对象读出来会被新 schema 拒绝 [R-28-5]。这也是公理 6「回滚方案先于发布方案」在控制器层的形态：升级 PR 合并之前，上面三步命令就必须写在 PR 描述里。

**回滚验证**：

```bash
make -C operator test
kubectl get maintenancewindow -A --ignore-not-found=true
kubectl get configmap -n default -l app.kubernetes.io/managed-by=operator || true
kubectl -n order-demo-system get deploy order-demo-operator -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
./hack/verify.sh
```

通过标准：CR 实例无残留、finalizer 列表为空、控制器镜像回到上一版、`make test` 仍通过、业务 `verify.sh` 的 `/healthz` 为 200（控制器降级不影响 `order-demo` 业务）。**升级/回滚演练没在 staging 跑过，就不允许把控制器镜像晋升到 prod**（CL-G-07）。

### 28.5.1 三链并行时序：控制器升级 / 降级 / CRD 版本迁移

控制器升级、控制器降级、CRD 版本迁移这三件事，工程上常常被塞进同一个 PR，理由是「反正都要动控制器」。「反正都要动」是一句关于成本的实话，也是一句关于风险的口误——它把三次可以分别回退的改动，合成了一次回不去的改动。结果是一旦出问题，没人分得清是镜像有问题、还是 API 版本有问题——两类故障的信号完全重叠：都表现为 CR 不收敛、都报 `OperatorNoSuccessfulReconcile`。

正确的拆法是：**三条链并行推进，但只有三个同步点，且只有一处不可逆**。三链在每个时间窗各做什么、同步点卡在哪，见下表（T0–T5 是时间窗，不是工时）：



| 阶段 | 升级链 | CRD 链 | 降级链（含演练） | 同步约束 | 失败即回到 |
|---|---|---|---|---|---|
| T0 | 用 `git-<sha7>` 构建 operator 镜像（禁浮动的 `latest` 标签） | 写 `v1beta1` 类型与 `ConvertTo` / `ConvertFrom` | 写三链回滚脚本并 dry-run | 三者完全并行 | — |
| T1 | envtest 四组全绿（28.5.2） | 生成证书、部署 webhook、注入 `caBundle` | 注入「摘掉 webhook」故障并恢复 | 可并行；webhook 必须先于任何 storage 变更就绪 | T0 |
| T2 | staging 灰度（只跑演练 CR） | 两版本都 served、storage 仍在 `v1alpha1` | 跑 `crd-rotation-drill.sh` 第 1–2 步（只验双写） | **同步点 1**：控制器必须能读两个版本 | T1 |
| T3 | prod 10% → 50% | storage 切到 `v1beta1` + 重写存量 | 跑第 3–5 步，核对 `storedVersions`；同时演练镜像回滚 | storage 轮转可与 prod 灰度并行，但必须在同一窗口内**先**验证完 | T2（storage 回滚见下） |
| T4 | prod 100%，旧镜像保留一个窗口 | `v1alpha1` 置 `served: false` | 验证旧版本读写返回 4xx，业务不受影响 | **同步点 2**：控制器全量后，才允许关旧 served | T3 |
| T5 | 清理旧镜像 tag 引用 | 撤转换 webhook、删旧 schema | 归档演练记录与 `storedVersions` 快照 | **同步点 3**：webhook 下线后不再有跨版本读 | T4 |

**为什么「并行」不等于「随便排」**——控制器版本与 CRD 服务版本之间存在硬兼容矩阵，排错时第一时间查这张表：

| 控制器 scheme | 两版本都 served | 仅 `v1alpha1` served | 仅 `v1beta1` served |
|---|---|---|---|
| 只认 `v1alpha1` | 正常（全走旧版本，转换对客户端透明） | 正常 | **崩溃**：`no matches for kind "MaintenanceWindow"` |
| 双版本（本章要求） | 正常 | 正常 | 正常（自动走新版本） |
| 只认 `v1beta1` | 正常 | **崩溃** | 正常 |

矩阵的含义很直接：`served: false` 是一次**对客户端的破坏性变更**，破坏面取决于还有谁在用旧版本。所以「关旧版本」永远排在最后，且必须先用 28.5.2 那种「双版本 scheme」把控制器升上去——这就是同步点 2 存在的原因。

**只读代码回滚救不了的那一步**：控制器镜像坏了，`git revert` + `argocd app sync` 十分钟就能回去；`storage` 一旦切换并重写存量，etcd 里的对象已经按新版本落盘，把 CRD 的 `storage` 改回旧版本**不会**自动把数据翻译回去——必须先恢复旧版本 `served: true`，再改 `storage`，再逐对象重写（28.5.3 的 R 段）。这就是三条链里唯一的不可逆点，也是 28.2.1 里「CRD 轮转必须被错误预算挡住」的原因。本章最想让你带走的一句就是它：**镜像可以回退，数据不能倒带**。

**故障注入清单**（演练链的验收项，每项都要有「期望观察 → 期望动作」）：

| 注入 | 期望观察 | 期望动作 | 是否触及不可逆点 |
|---|---|---|---|
| 删掉 webhook Service 的 endpoints | 旧版本读写 500，新版本同版本读写正常 | 恢复 Deployment；storage 未切则无损 | 否 |
| 控制器镜像 CrashLoop | 5 分钟内 `OperatorNoSuccessfulReconcile` 触发 | `git revert` 上一 PR，镜像回退 | 否 |
| 断开 `finalizers/update` 权限 | CR 卡 `Terminating`，错误率上升 | 恢复 ClusterRole，一次协调后清空 | 否 |
| storage 切换后立刻杀 webhook | 仅旧版本客户端报错，新版本不受影响 | 先把 storage 切回旧版本并重写，再修 webhook | **是**，需双签 |

最后一行值得单独记一句：切完 storage 后，**同版本读不需要转换**，所以 webhook 挂掉的影响面会从「所有对象」缩小到「仍用旧版本的客户端」。这也是为什么顺序是「先切 storage、后关 served」而不是反过来——反过来的话，webhook 一挂就是全站读失败 [R-28-5]。

### 28.5.2 测试矩阵：删除路径 / finalizer 卡住 / 事件风暴

上面那一个 `TestReconcileIdempotent` 只能证明「同一事件重复投递不产生重复副作用」。它证不了三件事：对象被删时清理是否真的发生、清理失败时会不会伪装成成功、稳态下控制器会不会自己把自己叫醒。这三类失败在真实事故里比「重复创建」更常见，也更难在 review 时看出来——28.1 的反模式一与反模式三都栽在这里。

矩阵按失败后果分组，每组一个 `Test` 函数，失败信息直接指向根因：

| 组 | 用例 | 触发方式 | 断言（失败即红） | 防的是哪个反模式 |
|---|---|---|---|---|
| **A 删除路径** | A1 正常删除 | Create → 2 次 reconcile → Delete → 1 次 reconcile | 下游 `ConfigMap` 与 CR 均 `NotFound`，删除瞬间 `deletionTimestamp` 非零 | 忽略 `deletionTimestamp` |
| | A2 删除后重复触发 | 对已删对象再 reconcile | 返回 `nil`，不 panic、不报错 | 把 `NotFound` 当错误 |
| | A3 下游已被人手工删 | 删 `ConfigMap` → 删 CR → reconcile | `cleanup` 容忍 `NotFound`，finalizer 正常移除 | `cleanup` 不幂等 |
| | A4 无 finalizer 的历史对象 | Create 后立即 Delete（未及 reconcile） | reconcile 返回 `nil`，对象直接消失 | 旧版本遗留对象把控制器打挂 |
| **B finalizer 卡住** | B1 清理失败 | 注入 `Delete` 故障后删 CR | 错误上抛、finalizer 保留、对象不消失、下游仍在 | 吞掉错误做「假清理」 |
| | B2 故障恢复 | 关掉注入后再 reconcile | 同一对象被清干净，`deletionTimestamp` 消失 | 清理逻辑不可重入 |
| | B3 权限不足 | staging 去掉 `finalizers/update` 后重跑 B1 | 返回 `Forbidden` 且 finalizer 保留，告警触发 | 权限过宽掩盖失败 |
| **C 事件风暴** | C1 稳态无自激 | 收敛后静置 3s | 额外协调 ≤ 1 次 | 无条件 `Requeue` / `RequeueAfter: 0` |
| | C2 下游单次变更 | 手工改 `ConfigMap` 的 `data` | 触发 ≤ 3 次后收敛，不再增长 | `Owns()` 写成全类型 `Watches` |
| | C3 批量创建 | 一次建 20 个 CR | 总协调 ≤ 120 次（每对象 ≤ 6） | 全表重放、队列放大 |
| | C4 队列深度 | staging 观察 `workqueue_depth` | 稳态 < 50，峰值 5 分钟内回落 | 循环内同步慢调用 |

B3 与 C4 必须在真集群（staging）跑：**envtest 用管理员证书起 API Server，不做 RBAC 鉴权，也导不出 Prometheus 指标**，把它们塞进 envtest 只会得到永远通过的空断言。

```go
import (
	"context"
	"fmt"
	"sync/atomic"
	"testing"
	"time"

	corev1 "k8s.io/api/core/v1"
	metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"

type countingReconciler struct {
	inner *MaintenanceWindowReconciler
	n     *atomic.Int64
}

func (c *countingReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	c.n.Add(1)
	return c.inner.Reconcile(ctx, req)
}

func waitApplied(t *testing.T, c client.Client, req types.NamespacedName) {
	t.Helper()
	deadline := time.Now().Add(30 * time.Second)
	for time.Now().Before(deadline) {
		var got opsv1alpha1.MaintenanceWindow
		if err := c.Get(context.Background(), req, &got); err == nil &&
			got.Status.ObservedGeneration == got.Generation &&
			got.Status.Phase == opsv1alpha1.PhaseApplied {
			return
		}
		time.Sleep(100 * time.Millisecond)
	}
	t.Fatalf("%s 未在 30s 内收敛", req.Name)
}

func TestReconcileEventStorm(t *testing.T) {
	f := newEnvFixture(t)
	defer f.stop()
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	var n atomic.Int64
	mgr, err := ctrl.NewManager(f.cfg, ctrl.Options{
		Scheme:  f.scheme,
		Metrics: server.Options{BindAddress: "0"}, // 关掉指标端口，避免与并行测试抢 8080
	})
	if err != nil {
		t.Fatal(err)
	}
	if err := ctrl.NewControllerManagedBy(mgr).
		For(&opsv1alpha1.MaintenanceWindow{}).
		Owns(&corev1.ConfigMap{}).
		Complete(&countingReconciler{
			inner: &MaintenanceWindowReconciler{Client: mgr.GetClient(), Scheme: mgr.GetScheme()},
			n:     &n,
		}); err != nil {
		t.Fatal(err)
	}
	go func() {
		if err := mgr.Start(ctx); err != nil {
			t.Logf("manager 退出: %v", err)
		}
	}()
	if !mgr.GetCache().WaitForCacheSync(ctx) {
		t.Fatal("cache 未同步")
	}

	// C1：收敛后静置，status 更新不得再引发链式协调
	mw := newMW("storm-sample")
	if err := f.c.Create(ctx, mw); err != nil {
		t.Fatal(err)
	}
	req := types.NamespacedName{Name: mw.Name, Namespace: mw.Namespace}
	waitApplied(t, f.c, req)
	base := n.Load()
	time.Sleep(3 * time.Second)
	if extra := n.Load() - base; extra > 1 {
		t.Fatalf("稳态 3s 内额外协调 %d 次，疑似自激循环", extra)
	}

	// C2：改下游对象只应触发少量协调（Owns 精确订阅）
	var cm corev1.ConfigMap
	if err := f.c.Get(ctx, types.NamespacedName{Name: "storm-sample-window", Namespace: "default"}, &cm); err != nil {
		t.Fatal(err)
	}
	before := n.Load()
	cm.Data["replicas"] = "5"
	if err := f.c.Update(ctx, &cm); err != nil {
		t.Fatal(err)
	}
	time.Sleep(2 * time.Second)
	if extra := n.Load() - before; extra > 3 {
		t.Fatalf("单次下游变更触发 %d 次协调", extra)
	}

	// C3：批量创建时协调次数应与对象数线性，而不是平方
	const bulk = 20
	for i := 0; i < bulk; i++ {
		item := newMW(fmt.Sprintf("storm-%02d", i))
		if err := f.c.Create(ctx, item); err != nil {
			t.Fatal(err)
		}
	}
	for i := 0; i < bulk; i++ {
		waitApplied(t, f.c, types.NamespacedName{Name: fmt.Sprintf("storm-%02d", i), Namespace: "default"})
	}
	if total := n.Load(); total > int64(bulk*6)+base {
		t.Fatalf("批量 %d 个 CR 共协调 %d 次，超出上限 %d，疑似事件风暴", bulk, total, int64(bulk*6)+base)
	}
}
```

> C 组必须带 `-race`：计数器是 `atomic.Int64`，若改成普通 `int`，`-race` 会立刻报数据竞争——这本身就是 CI 里最便宜的一条防线。另外 `Metrics: server.Options{BindAddress: "0"}` 不能省，否则三个测试并行时会抢 `:8080` 直接起不来。

**怎么跑**（分组跑，禁止吃测试缓存）：

```bash
cd operator
go test ./internal/controller/ -count=1 -race -run 'TestReconcileIdempotent'      -v
go test ./internal/controller/ -count=1 -race -run 'TestReconcileDeletionPath'    -v
go test ./internal/controller/ -count=1 -race -run 'TestReconcileFinalizerStuck'  -v
go test ./internal/controller/ -count=1 -race -run 'TestReconcileEventStorm'      -v
make test   # CI 门禁：四组全量 + manifests/generate 一致性
```

> 四组各起一个 envtest 实例，彼此不共享状态，也刻意不合并成一个大 `TestLifecycle`：A 组验证「删除是否真的发生」，B 组验证「失败是否被承认」，C 组验证「没有事件时是否安静」。合并后只会得到一句「清理有问题」，而定不出是顺序写反、错误被吞，还是订阅过宽——三种修法完全不同。

**矩阵的自维护成本**：11 个用例里没有一个是「为了覆盖率好看」加的，每一条都对应一种真实故障形态——清理被跳过、错误被吞、控制器自激。反过来，用例也会腐化：envtest 二进制随 K8s 小版本升级时，删除行为与默认的字段管理语义都可能变，表现为「昨天还绿、今天红灯」。所以矩阵必须跟 `ENVTEST_K8S_VERSION` 一起升级：先用旧版本跑一遍留基线，再升二进制对比结果；红灯若集中在 A 组，几乎总是环境差异而不是代码回归。这套纪律与第 11 章「验证环要锁版本」同源 [R-28-1]。

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| A 组 | A1–A4 全 PASS；A1 中下游与 CR 的 `NotFound` 必须**同时**成立，只满足一个说明清理与删除顺序写反了 [R-28-4] |
| B 组 | B1 必须有非空 `err` 且 finalizer 保留；B2 后对象 `NotFound`。B1 若「无错误 + finalizer 仍在」也判失败——那说明错误被吞了 [R-28-2] |
| C 组 | C1 额外协调 ≤ 1、C2 ≤ 3、C3 ≤ 120；任一项超限即视为 `Owns()` 订阅或短路条件写错 [R-28-7] |
| 竞态 | `-race` 无任何 `DATA RACE` 输出 |
| 时长 | 四组在 CI 上合计 < 5 分钟（每组一个 envtest 实例约 5–8s 启动），超时说明用例里写了 `time.Sleep` 轮询而非条件等待 |

### 28.5.3 转换 webhook：`v1alpha1 → v1beta1` 双写与 storage 轮转演练

28.2 给的五步顺序只是一个骨架，真正会出事的是「双写」这三个字被误读。先把口径钉死：**CRD 的双写不是两份数据**。两个版本都 `served: true` 时，客户端可以按任一版本读写，但 etcd 里每个对象只有一份，按 `storage: true` 的那个版本落盘；跨版本读写由转换 webhook 在 API Server 侧做翻译 [R-28-5]。所以「双写期」的真实含义是「两个版本都能写，但只有一份数据，且转换必须是双射」——任何一次有损转换，都会在切 storage 的那一刻变成不可逆的数据丢失。

本例的字段变化刻意选成**有损风险**最大的一种：`v1beta1` 新增 `spec.suspend`（暂停窗口），`v1alpha1` 根本没有这个字段。

**`operator/api/v1beta1/maintenancewindow_types.go`**（Hub 版本，即 storage 版本）：

```go
package v1beta1

import (
	metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
	"k8s.io/apimachinery/pkg/runtime"
	"k8s.io/apimachinery/pkg/runtime/schema"
)

var (
	GroupVersion  = schema.GroupVersion{Group: "ops.example.com", Version: "v1beta1"}
	SchemeBuilder = runtime.NewSchemeBuilder(addKnownTypes)
	AddToScheme   = SchemeBuilder.AddToScheme
)

// v1alpha1 没有 suspend 字段，降级视图靠这条注解保住它，否则一次 round-trip 就丢配置
const PreserveSuspendAnnotation = "ops.example.com/converted-suspend"

type MaintenanceWindowSpec struct {
	Replicas int32  `json:"replicas"`
	Reason   string `json:"reason,omitempty"`
	Suspend  bool   `json:"suspend,omitempty"`
}

type MaintenanceWindowStatus struct {
	ObservedGeneration int64        `json:"observedGeneration,omitempty"`
	AppliedReplicas    int32        `json:"appliedReplicas,omitempty"`
	Phase              string       `json:"phase,omitempty"`
	LastTransitionTime metav1.Time `json:"lastTransitionTime,omitempty"`
}

// +kubebuilder:object:root=true
// +kubebuilder:subresource:status
// +kubebuilder:storageversion
type MaintenanceWindow struct {
	metav1.TypeMeta   `json:",inline"`
	metav1.ObjectMeta `json:"metadata,omitempty"`
	Spec              MaintenanceWindowSpec   `json:"spec,omitempty"`
	Status            MaintenanceWindowStatus `json:"status,omitempty"`
}

// +kubebuilder:object:root=true
type MaintenanceWindowList struct {
	metav1.TypeMeta `json:",inline"`
	metav1.ListMeta `json:"metadata,omitempty"`
	Items           []MaintenanceWindow `json:"items"`
}

// Hub 声明 v1beta1 是转换中心版本；controller-runtime 0.x 的 webhook server
// 会在 /convert 上自动服务所有实现了 ConvertTo / ConvertFrom 的类型 [R-28-2]
func (*MaintenanceWindow) Hub() {}

func addKnownTypes(scheme *runtime.Scheme) error {
	scheme.AddKnownTypes(GroupVersion, &MaintenanceWindow{}, &MaintenanceWindowList{})
	metav1.AddToGroupVersion(scheme, GroupVersion)
	return nil
}
```

**`operator/api/v1alpha1/maintenancewindow_conversion.go`**（两个方向都写在旧版本包里，避免包循环）：

```go
package v1alpha1

import (
	"sigs.k8s.io/controller-runtime/pkg/conversion"

	opsv1beta1 "order-demo/operator/api/v1beta1"
)

// 旧 → 新：补齐默认值，而不是「尽量不报错」
func (src *MaintenanceWindow) ConvertTo(dstRaw conversion.Hub) error {
	dst := dstRaw.(*opsv1beta1.MaintenanceWindow)
	dst.ObjectMeta = src.ObjectMeta
	dst.Spec.Replicas = src.Spec.Replicas
	dst.Spec.Reason = src.Spec.Reason
	dst.Spec.Suspend = src.Annotations[opsv1beta1.PreserveSuspendAnnotation] == "true"
	dst.Status.ObservedGeneration = src.Status.ObservedGeneration
	dst.Status.AppliedReplicas = src.Status.AppliedReplicas
	dst.Status.Phase = string(src.Status.Phase)
	return nil
}

// 新 → 旧：v1alpha1 装不下的字段必须落到注解，不允许静默丢弃
func (dst *MaintenanceWindow) ConvertFrom(srcRaw conversion.Hub) error {
	src := srcRaw.(*opsv1beta1.MaintenanceWindow)
	dst.ObjectMeta = src.ObjectMeta
	if src.Spec.Suspend {
		if dst.Annotations == nil {
			dst.Annotations = map[string]string{}
		}
		dst.Annotations[opsv1beta1.PreserveSuspendAnnotation] = "true"
	}
	dst.Spec.Replicas = src.Spec.Replicas
	dst.Spec.Reason = src.Spec.Reason
	dst.Status.ObservedGeneration = src.Status.ObservedGeneration
	dst.Status.AppliedReplicas = src.Status.AppliedReplicas
	dst.Status.Phase = Phase(src.Status.Phase)
	return nil
}
```

> 为什么注解必须存在 **storage 版本**里：注解随 `ObjectMeta` 落盘，切 storage 后它就在 etcd 的那一份对象上；降级视图读出来时还能还原 `suspend: true`。若只是「在 ConvertFrom 里写注解、ConvertTo 里不读」，第一次 round-trip 就丢，而这正是版本迁移最常见的隐性数据事故 [R-28-5]。

**`hack/gen-webhook-certs.sh`**（不引入 cert-manager：本章的栈里没有它，多一个组件就多一条要维护的信任链）：

```bash
#!/usr/bin/env bash
# 生成转换 webhook 的自签 CA 与服务端证书，并把 CA 注入 CRD 的 caBundle
set -euo pipefail
NS=order-demo-system
SVC=order-demo-operator-webhook
DIR=certs
CRD=maintenancewindows.ops.example.com

mkdir -p "$DIR"
openssl genrsa -out "$DIR/ca.key" 2048
openssl req -x509 -new -nodes -key "$DIR/ca.key" -days 3650 \
  -subj "/CN=order-demo-operator-webhook-ca" -out "$DIR/ca.crt"

cat > "$DIR/server.cnf" <<EOF
[req]
req_extensions = v3_req
distinguished_name = dn
prompt = no
[dn]
CN = $SVC.$NS.svc
[v3_req]
subjectAltName = @alt
extendedKeyUsage = serverAuth
keyUsage = digitalSignature, keyEncipherment
[alt]
DNS.1 = $SVC
DNS.2 = $SVC.$NS
DNS.3 = $SVC.$NS.svc
DNS.4 = $SVC.$NS.svc.cluster.local
EOF

openssl genrsa -out "$DIR/tls.key" 2048
openssl req -new -key "$DIR/tls.key" -out "$DIR/tls.csr" -config "$DIR/server.cnf"
openssl x509 -req -in "$DIR/tls.csr" -CA "$DIR/ca.crt" -CAkey "$DIR/ca.key" \
  -CAcreateserial -days 365 -extensions v3_req -extfile "$DIR/server.cnf" -out "$DIR/tls.crt"

kubectl -n "$NS" create secret tls conversion-webhook-certs \
  --cert="$DIR/tls.crt" --key="$DIR/tls.key" --dry-run=client -o yaml | kubectl apply -f -

# GNU base64；macOS 用: CA_BUNDLE=$(base64 -i "$DIR/ca.crt" | tr -d '\n')
CA_BUNDLE=$(base64 -w0 < "$DIR/ca.crt")
kubectl patch crd "$CRD" --type=merge \
  -p "{\"spec\":{\"conversion\":{\"webhook\":{\"clientConfig\":{\"caBundle\":\"${CA_BUNDLE}\"}}}}}"

kubectl get crd "$CRD" -o jsonpath='{.spec.conversion.webhook.clientConfig.caBundle}' | head -c 24
echo "  <- caBundle 前 24 字符，非空即注入成功"
```

`caBundle` 没注入时的报错是 `x509: certificate signed by unknown authority`，而很多人会先去查证书 SAN 是否正确——顺序反了：**先查 caBundle 是否为空，再查 SAN**。

**`hack/crd-rotation-drill.sh`**（演练脚本：双写 → 切 storage → 重写 → 关旧版本 → 逆序回滚）：

```bash
#!/usr/bin/env bash
# v1alpha1 → v1beta1 双写与 storage 轮转演练；只在演练集群执行，prod 必须走 Git PR（公理 5）
set -euo pipefail
CRD=maintenancewindows.ops.example.com
NS=default
API_OLD=ops.example.com/v1alpha1
API_NEW=ops.example.com/v1beta1

step() { printf '\n=== %s ===\n' "$*"; }
fail() { printf 'FAIL: %s\n' "$*" >&2; exit 1; }
raw()  { kubectl get --raw "/apis/$1/namespaces/$NS/maintenancewindows/$2"; }

step "0 前置：webhook 必须健康，否则任何 storage 变更都会把对象读坏"

[ "$(kubectl get crd "$CRD" -o jsonpath='{.spec.conversion.strategy}')" = "Webhook" ] \
  || fail "conversion.strategy 不是 Webhook"
kubectl get crd "$CRD" -o json | jq -e '.spec.versions[0].name=="v1alpha1" and .spec.versions[1].name=="v1beta1"' >/dev/null \
  || fail "版本顺序与脚本假设不符，先按实际索引改下面的 json patch"

step "1 双写验证一：旧版本创建，两个版本互为视图"
kubectl apply -f operator/config/samples/ops_v1alpha1_maintenancewindow.yaml
old_spec=$(raw "$API_OLD" idem-sample | jq -S '.spec')
new_spec=$(raw "$API_NEW" idem-sample | jq -S '.spec')
diff <(echo "$old_spec") <(echo "$new_spec") || fail "round-trip 后 spec 不一致"

step "2 双写验证二：新字段在降级视图里不许丢"
kubectl apply -f - <<'EOF'
apiVersion: ops.example.com/v1beta1

  name: drill-suspend
  namespace: default

  replicas: 2

  suspend: true
EOF
raw "$API_OLD" drill-suspend | jq -e '.metadata.annotations["ops.example.com/converted-suspend"]=="true"' >/dev/null \
  || fail "降级视图未通过注解保留 suspend"
raw "$API_NEW" drill-suspend | jq -e '.spec.suspend==true' >/dev/null \
  || fail "round-trip 丢了 suspend（ConvertTo 未读注解）"

step "3 切 storage：一次 patch 同时改两个版本，绝不分成两次"
kubectl patch crd "$CRD" --type=json -p '[
  {"op":"replace","path":"/spec/versions/0/storage","value":false},
  {"op":"replace","path":"/spec/versions/1/storage","value":true}
]'

step "4 重写存量对象，让 etcd 真正落到 v1beta1（不重写，storedVersions 永远有两个）"
for ns in $(kubectl get "$CRD" -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"\n"}{end}' | sort -u); do
  for name in $(kubectl -n "$ns" get "$CRD" -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
    kubectl -n "$ns" get "$CRD" "$name" -o json \
      | jq 'del(.metadata.managedFields) | .apiVersion="ops.example.com/v1beta1"' \
      | kubectl replace -f - >/dev/null
  done
done

step "5 验证 storedVersions 只剩 v1beta1"
stored=$(kubectl get crd "$CRD" -o jsonpath='{.status.storedVersions}')
echo "storedVersions=$stored"
case "$stored" in *v1alpha1*) fail "仍有对象以 v1alpha1 落盘，补跑第 4 步" ;; esac

step "6 关旧版本 served（此刻 v1alpha1 读写 4xx，属预期）"
kubectl patch crd "$CRD" --type=json -p '[{"op":"replace","path":"/spec/versions/0/served","value":false}]'
if kubectl get --raw "/apis/$API_OLD/namespaces/$NS/maintenancewindows/drill-suspend" >/dev/null 2>&1; then
  fail "旧版本仍可读，served 未生效"
fi
raw "$API_NEW" drill-suspend | jq -r '.spec.suspend' | grep -qx true || fail "关闭 served 后新版本读数异常"

step "R 回滚：先恢复 served，再切回 storage，最后再重写一遍"
kubectl patch crd "$CRD" --type=json -p '[{"op":"replace","path":"/spec/versions/0/served","value":true}]'
kubectl patch crd "$CRD" --type=json -p '[
  {"op":"replace","path":"/spec/versions/0/storage","value":true},
  {"op":"replace","path":"/spec/versions/1/storage","value":false}
]'
for name in $(kubectl -n "$NS" get "$CRD" -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  kubectl -n "$NS" get "$CRD" "$name" -o json \
    | jq 'del(.metadata.managedFields) | .apiVersion="ops.example.com/v1alpha1"' \
    | kubectl replace -f - >/dev/null
done
echo "回滚完成，storedVersions=$(kubectl get crd "$CRD" -o jsonpath='{.status.storedVersions}')"
```

**演练频率与窗口**：每次改 CRD schema 前必跑一次；此后每季度空跑一次（无 schema 变更也跑），目的是确认脚本本身没有随 CRD 一起腐化——脚本和 CRD 同步漂移，是这类演练最常见的失效方式。窗口选业务低峰，跑完把 `storedVersions` 快照与脚本输出一起存进演练记录，它就是下一次「这个集群能不能升 K8s」的直接证据。

**卡住时的判定表**（30 秒内定位，不要从证书开始猜）：

| 现象 | 真实原因 | 处置 |
|---|---|---|
| 读写都报 `x509: certificate signed by unknown authority` | `caBundle` 为空或与 Secret 里的证书不配对 | 重跑 `gen-webhook-certs.sh`；`caBundle` 必与 `ca.crt` 同源 |
| `failed calling webhook: no endpoints available for service` | Service selector 与 Pod 标签不一致，或 webhook Pod 未 Ready | `kubectl -n order-demo-system get endpointslice -l kubernetes.io/service-name=order-demo-operator-webhook` |
| `conversion webhook ... failed: unable to convert` | 类型未注册到 scheme，或 `ConvertTo` 里对 nil 注解直接索引 | 查 manager 启动日志里的 `conversion` 注册行；`ConvertFrom` 先 `if dst.Annotations == nil` |
| 切完 storage 后旧客户端读出来缺字段 | `ConvertFrom` 静默丢字段，未落注解 | 立即按 R 段回滚 storage，补转换逻辑后重跑 1–2 步 |
| `storedVersions` 一直是两个 | 只改了 CRD，没重写存量对象 | 补跑第 4 步；**不要**直接删 `storedVersions` 里的条目 |

> 最后一条是硬约束：`status.storedVersions` 里留着两个版本，下一次 K8s 升级校验会拒绝，届时你面对的是「升不了集群」而不是「迁移失败」。这也是为什么演练脚本把「重写存量」写成独立一步，而不是切完 storage 就算完 [R-28-5]。
