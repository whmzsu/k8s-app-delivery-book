## 23.1 现场：从「先查根因」到「先止血」

**合成案例**。周四 21:07，一次把 `api` 的 liveness 探针超时从 3s 调成 1s 的配置变更被同步到生产。GC 停顿一超过 1s，kubelet 就判定容器不健康并重启；重启中的实例从 Service 摘流，存活实例瞬时多扛了全部流量，响应变慢，又更容易触发下一次误杀。于是 Pod 进入 `CrashLoopBackOff`，重启级联开始。值班看到的是「一堆 Pod 在重启、5xx 往上走」，第一反应是打开日志查「为什么这个版本会崩」——查根因。21:40，有人终于提议「先退回上一版吧」，但没人能立刻说清「上一版探针配置是哪份、敲哪条命令、退了之后怎么确认好了」。等回滚执行完，故障已经持续 33 分钟。

这正是第 1 章 H4 的形态：**liveness 误杀引发重启级联，现场无人能定位**。探针语义与误用边界在第 8 章 [R-23-4]，级联的信号基础在第 21 章，而本章要补的是「真出事时，第一步做什么」。事故处置的优先级不是「查清再修」，而是**先恢复服务、再保全现场、最后查根因**：先把流量恢复到用户可用的状态，再冻结现场保留日志与指标供复盘，根因分析放到服务恢复之后 [R-23-6][R-23-7]。

三个高频反模式：

**反模式一：出事先查根因、迟迟不回滚。** 现象是故障时长被「找原因」拉长，用户一直在受损。根因是把「理解」误当成「恢复」的前置条件。本章的替代做法是止血优先：只要判定是变更引入的，第 13 章的回滚命令就是第一动作，查根因留到复盘 [R-23-9]。

**反模式二：runbook 只写「联系某某」。** 现象是半夜找不到人、找到了也不知道敲什么。根因是把处置知识存在人脑里，而不是存在可执行的命令与判断标准里。本章要求每份 runbook 含**症状、定位命令、止血动作、验证方法、升级路径**五项，命令与通过标准前置，「联系人」只出现在最后一项 [R-23-3][R-23-6]。

**反模式三：复盘追责。** 现象是下次没人愿意上报小故障，组织失去早期信号。根因是把复盘当成责任认定。本章用无责复盘：只写可观测证据与系统/流程改进项，产出的每一项都要有负责人、截止日期与验收方式 [R-23-6][R-23-8]。公开复盘里反复出现的「处置时间被信息搜集拖长」「复盘后改进项无人跟踪」，正是这两条反模式的方法论背景 [R-23-8]。

> 本章不教「系统够不够抗揍」，只教「救火流程能不能被复现」。演练的价值在于验证 runbook 与回滚路径——**没写过的 runbook，一定会在演练中暴露缺口** [R-23-6][R-23-8]。

````markdown
# Runbook · Pod Pending

## 症状
`kubectl -n order-demo-prod get pods` 中 Pod 持续 Pending 超过 5 分钟，可用副本数不足。

## 定位命令
```bash
kubectl -n order-demo-prod get pods -l app.kubernetes.io/component=api -o wide
kubectl -n order-demo-prod describe pod <pod> | grep -A8 Events
kubectl -n order-demo-prod get events --sort-by=.lastTimestamp | tail -20
kubectl -n order-demo-prod describe node <node> | grep -A6 Allocated
```

## 止血动作
1. 事件含 `Insufficient cpu/memory`：降副本回上一版 `kubectl -n order-demo-prod scale deploy/api --replicas=<上一版>`，再按第 18 章补容量。
2. 事件含 `untolerated taint` 或亲和冲突：回第 18 章核对拓扑，不在现场改生产调度字段。
3. 事件含 `unbound PVC`：查 `kubectl -n order-demo-prod get pvc`，转第 16 章，禁止删 db 的 PVC。

## 验证方法
`kubectl -n order-demo-prod rollout status deploy/api --timeout=120s` 正常结束；`./hack/verify.sh` 通过；`/readyz` 返回 200。

## 升级路径
15 分钟未恢复 → 按第 22 章 paging 升级平台负责人；涉及 db 的转第 16 章数据边界，不自行重建 StatefulSet。
````

````markdown
# Runbook · CrashLoopBackOff（含 liveness 误杀识别）

## 症状
Pod 反复重启、`CrashLoopBackOff`；常伴 5xx 抬升与实例数下降。这是第 1 章 H4 的落地识别点。

## 定位命令
```bash
kubectl -n order-demo-prod get pods -l app.kubernetes.io/component=api
kubectl -n order-demo-prod logs <pod> --previous | tail -50
kubectl -n order-demo-prod describe pod <pod> | grep -A3 'Liveness probe failed'
kubectl -n order-demo-prod describe pod <pod> | grep -A3 'Readiness probe failed'
```
判据：出现 `Liveness probe failed` 且进程日志无崩溃栈 → 判为 liveness 误杀（探针语义见第 8 章），不是代码崩溃。

## 止血动作
1. 误杀：`kubectl -n order-demo-prod rollout undo deployment/api` 退回上一版探针配置；随后 `argocd app sync order-demo`（第 14 章）。
2. 真崩溃：同样先 `rollout undo deployment/api` 止血，再按第 21 章 `trace_id` 下钻崩溃请求。
3. 禁止把 `failureThreshold` 调大当作止血，那只会让误杀更难被发现。

## 验证方法
`kubectl -n order-demo-prod rollout status deploy/api --timeout=120s` 正常结束；5 分钟内无新增 `Liveness probe failed`；`./hack/verify.sh` 通过。

## 升级路径
误杀持续或回滚失败 → 第 22 章 paging；探针基线复核转第 8 章，信号下钻转第 21 章。
````

````markdown
# Runbook · OOMKilled

## 症状
Pod 状态 `OOMKilled` 或被反复重启，`lastState.terminated.reason` 为 `OOMKilled`。

## 定位命令
```bash
kubectl -n order-demo-prod get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\n"}'
kubectl -n order-demo-prod top pod -l app.kubernetes.io/component=api
kubectl -n order-demo-prod get deploy api -o jsonpath='{.spec.template.spec.containers[0].resources}{"\n"}'
```
通过标准：limits 与第 17 章基线一致（`cpu: 500m, memory: 256Mi`）；超出则说明是容量问题而非代码泄漏。

## 止血动作
1. 先 `kubectl -n order-demo-prod rollout undo deployment/api` 回到上一版产物（第 13 章）。
2. 确属容量不足：由 Git 提交新 limits，走 PR 与第 14 章同步，禁止现场 `kubectl set resources` 改生产。
3. 疑似内存泄漏：保留 heap/日志现场，按第 21 章 `trace_id` 采样，交复盘（23.6）。

## 验证方法
`rollout status` 正常结束；5 分钟内无新增 `OOMKilled`；`./hack/verify.sh` 通过；`kubectl top pod` 内存低于新 limits。

## 升级路径
回滚后仍 OOM → 第 22 章 paging；容量基线转第 17 章，配额与 HPA 转第 18 章。
````

````markdown
# Runbook · 证书过期

## 症状
入口 TLS 握手失败，客户端报证书过期；gateway 侧 5xx 或连不上。

## 定位命令
```bash
kubectl -n order-demo-prod get certificate
kubectl -n order-demo-prod get secret <tls-secret> -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -enddate
kubectl -n order-demo-prod describe certificate <cert-name> | grep -A6 Events
```
通过标准：`Not After` 晚于当前时间；`renewBefore` 已配置（见第 19 章）。

## 止血动作
1. 触发重签：`kubectl -n order-demo-prod delete secret <tls-secret>`，由 cert-manager 1.x 依据 `Certificate` 重建。
2. 同步核对 `GatewayClass: eg` / `order-demo-gw` / `gateway-route` 的证书引用（第 19 章）。
3. 重签期间如入口完全不可用，按第 13 章回滚到上一版入口配置，不手工自签临时证书。

## 验证方法
`openssl x509 -noout -enddate` 显示新有效期；`curl` 入口返回 200；`./hack/verify.sh` 通过。

## 升级路径
重签失败或 `Certificate` 未 Ready → 第 22 章 paging；证书策略与 `renewBefore` 转第 19 章。
````

## 23.4 混沌工程与回滚演练：验证的是 runbook，不是「抗揍」

演练工具固定 **Chaos Mesh 2.x** 为唯一示例实现，**Litmus 3.x 仅在对比中出现**（`decisions.md`）。

| 维度 | Chaos Mesh 2.x（本书示例） | Litmus 3.x（仅对比） |
|---|---|---|
| 实验定义 | Kubernetes 原生 CRD（PodChaos / StressChaos / NetworkChaos） | ChaosExperiment / ChaosEngine CRD + hub 工作流 |
| 适用场景 | 已用 K8s 原生清单、想把实验与 `argocd`/Kustomize 一起管 | 需要中心化实验市场与较多预置场景 |
| 何时不该用 | 无 K8s 权限、或只想做一次性手工杀 Pod | 团队已全量用原生 CRD、不想再引入一套控制器 |

**爆炸半径上限（本书硬性约定）**：演练只在 `order-demo-staging`，`mode: one`（单 Pod）、`duration: 2m`、`selector` 限定 `app.kubernetes.io/name=order-demo` 与单个 `component`，且只在第 22 章 `chaos-drill-window` 的静默窗口内执行；生产 `order-demo-prod` 永不注入 [R-23-1]。任何实验都先有对应 runbook，没有 runbook 的症状不演练。

```bash
NS=order-demo-staging
PREV="$(kubectl -n "${NS}" get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"

kubectl -n "${NS}" set image deployment/gateway \
  gateway=registry.example.com/order-demo/gateway:git-0000000
kubectl -n "${NS}" rollout status deployment/gateway --timeout=60s || true

kubectl -n "${NS}" set image deployment/gateway gateway="${PREV}"
kubectl -n "${NS}" rollout status deployment/gateway --timeout=120s
./hack/verify.sh

[ "$(kubectl -n "${NS}" get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}')" = "${PREV}" ] \
  && echo "PASS: rollback drill restored ${PREV}"
```

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：回滚演练应纳入常规发布门禁，而不是一年一次的演习。
>
> **论证**：回滚方案的价值在于「出事那一刻能被执行」，而这项能力会随人员流动、控制器升级、配置结构变化而衰减。一年一次演习只能证明演习当天可用；把它挂到每次发布的门禁上（沿用第 3 章公理 6 与第 13 章方案先行），才能让「回滚命令、时限、验证结果」始终与当前产物同步。演练脚本 `rollback-drill.sh` 之所以写成可执行、带断言的命令，就是为了能进 CI 而不是靠人记。
>
> **反例与适用前提**：这不等于「每次发布都在生产演练回滚」。演练对象是 `order-demo-staging`，生产只验证「回滚方案存在且已演练过」这一证据（CL-G-07）。若团队已在第 15 章用金丝雀 + 指标自动回滚，自动回滚路径本身也要纳入同一门禁，不能用「有自动回滚」替代演练。对变更极少的内部系统，可放宽到按季度演练，但「无演练记录即禁止发布」这条不能松。

## 23.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（在仓库根目录执行，需 `kubectl`、`argocd`、`curl`、`jq`、`git`，小版本见附录 A）：

```bash
./hack/chaos-drill.sh
./hack/rollback-drill.sh
for f in chaos/experiments/*.yaml; do grep -q '^kind: .*Chaos' "$f" || { echo "FAIL: $f"; exit 1; }; done
for f in docs/runbooks/*.md; do grep -q '## 升级路径' "$f" || { echo "FAIL: $f"; exit 1; }; done
./hack/verify.sh
```

**逐条通过标准**：

| 判据 | 期望结果 |
|---|---|
| 注入后按 runbook 恢复 | `chaos-drill.sh` 打印 `PASS`，`rollout status` 在时限内正常结束 |
| 6 份 runbook 可执行 | 每份都含「症状/定位命令/止血动作/验证方法/升级路径」五项，定位命令均可复制执行 |
| 演练报告 | `chaos-drill.sh` 输出含注入对象清单与清理结果，`chaos-testing` 下无残留实验 CR |
| 复盘产出改进项 | `postmortem-template.md` 的第六节至少一条 `ACT-` 项，含负责人、截止、验收方式 |
| 回滚演练纳入门禁 | `rollback-drill.sh` 打印 `PASS: rollback drill restored git-<sha7>` |
| 应用侧不受影响 | `./hack/verify.sh` 的 `/healthz` 为 200，镜像标签仍为 `git-<sha7>` |

**回滚命令 / 步骤**（先演练、后发布；生产变更回到 Git，见第 3 章）：

```bash
# 1. 演练侧：删除注入对象，恢复静默窗口外的正常状态
kubectl -n chaos-testing delete -f chaos/experiments/ --ignore-not-found
kubectl -n chaos-testing get podchaos,stresschaos,networkchaos

# 2. 真实止血：变更引入的故障一律用第 13 章回滚命令，不现场调参
kubectl -n order-demo-prod rollout undo deployment/gateway
kubectl -n order-demo-prod rollout status deployment/gateway --timeout=120s

# 3. 配置漂移：由 Git 唯一真相收敛（第 14 章），禁止 kubectl edit
argocd app diff order-demo
argocd app sync order-demo

# 4. 声明回滚：演练规则/ runbook 的变更走 git revert
BAD="$(git log --oneline -5 -- chaos/ docs/runbooks/ | head -1 | awk '{print $1}')"
git revert "${BAD}"
argocd app sync order-demo-observability
```

> 第 1 步清注入对象、第 2 步止血、第 3 步纠漂移、第 4 步回退声明，四步顺序不能倒：先保住用户，再收敛状态，最后查根因 [R-23-6][R-23-7]。真实止血用第 13 章命令，数据边界见第 16 章，本章不重复给出数据回滚方案。

**回滚验证**：

```bash
./hack/verify.sh
kubectl -n order-demo-prod get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
kubectl -n order-demo-prod get pods -l app.kubernetes.io/component=gateway
argocd app diff order-demo
```

通过标准：`/healthz` 200、镜像回到已知良好 `git-<sha7>`、无 `CrashLoopBackOff` / `Pending` 残留、`argocd app diff` 无输出、故障注入对象已清理。**回滚没有验证过，不允许进入发布门禁**（CL-G-07、CL-G-12）。
