## 31.1 回到起点：用同一套坐标系重演那起事故

第 1 章 1.1 的周五 14:32，一次「只改了一行配置」让 `/orders` 稳定返回 500。那不是产品 bug——Kubernetes 的每个控制器都在按设计工作，失控的是决策 [R-31-2]。全书用三十章补上了那些缺失的决策，现在用**第 1 章的同一套坐标系**把同一变更再做一遍，看它会不会还出事。

> **合成案例声明**：本章重演的仍是第 1 章那起**教学合成的虚构事故**，非真实事件复盘；L3 资料只支撑「反模式方法论」与行业现状，不证明事故真实发生 [R-31-7]。

```
主线（一次变更的旅程）
  定义 → 校验 → 打包 → 晋升 → 发布 → 运行 → 观测 → 响应
  └─ 第 2 篇 ─┘   └─ 第 3 篇 ─┘  └ 第 4 篇 ┘  └── 第 5 篇 ──┘

横切 A：安全 · 策略 · 凭据（第 6 篇）—— 作用于主线每一环
横切 B：可观测 · 可回滚 · 可审计（第 5 篇集中展开）—— 贯穿全书

演进轴（第 7 篇）：L0 手工 → L1 自动化 → L2 GitOps → L3 自助平台

地基（第 1 篇）：心智模型 · 原则 · 环境拓扑 · 工具链地图 —— 支撑以上全部
```

**同一变更、两种结局**（时间线逐点对照第 1 章 1.1）[R-31-5][R-31-6]：

| 时刻 | 第 1 章的现象 | 第 31 章按范式重做的结果 | 补上的环节 |
|---|---|---|---|

| 14:34 | `kubectl edit` 改 Pod，几秒被改回 | 变更只从 Git PR 进，改运行状态本就不被允许 | 地基 / 晋升（H2、H7） |
| 14:36 | 新 Pod 永远不 `Ready`，可用副本掉到 0 | `readinessProbe` + `maxUnavailable: 0` + PDB，滚动期间始终有可用副本 | 定义 / 发布（H3） |
| 14:40 | 激进 liveness 误杀，重启级联无人定位 | 三类探针语义分明，误杀由第 23 章速查表与 runbook 止血 | 定义 / 响应（H4） |
| 14:45 | 想回滚却发现没方案、schema 不兼容 | 回滚方案先于发布写好，数据变更走 expand–contract | 发布（H5） |

| 15:05 | 告警只有「5xx 偏高」，值班不知做什么 | 每条告警带 runbook 链接，按 SLO / 错误预算分级路由 | 观测 / 响应（H8） |
| 结果 | `/orders` 稳定 500 | `/healthz` 连续 30 次 200，零故障完成 | 首尾闭环 |

**监控曲线：把两次现场放进同一张面板**（文字描述指标走势；指标口径与第 20、21 章一致：SLI 用成功请求数 / 总请求数，不用 CPU 使用率充当 SLI）[R-31-5]：

- **事故现场（`ch01-incident`）**：请求成功率在 14:32 前稳定 100%；14:33 变更落地，曲线开始缓慢下行；14:36 滚动更新摘流，可用副本从 4 掉到 0，成功率跌至 0% 并贴地；14:40 激进 liveness 误杀，Pod 重启计数呈阶梯上升（1→2→4→8，每轮叠加退避），成功率在 0–40% 之间剧烈锯齿；14:50 与 15:00 的两轮手工「救援」（改 Pod、改副本数）各制造一次新的向下尖刺；15:05 之后曲线长期横盘在 0% 附近——因为回滚目标已经不可知（H1 与 H5 叠加）。本周错误预算在 33 分钟内耗尽：按第 20 章冻结规则此刻应冻结发布，但变更入口都不唯一，冻结无从谈起。
- **事故现场的可用副本曲线**：4 → 0 →（手工扩回 4，与 Git 声明不一致）→ 因镜像不可用再次掉 0。整条曲线没有任何一段能被一份声明解释——这正是漂移在监控上的长相。
- **事故现场的 p99 延迟**：从约 80ms 抬升到超时上限，与成功率锯齿同相位；是故障而非容量问题，但当时没有任何一张图能把这两个信号连起来，值班只能靠猜。
- **重演现场（`ch31-replay`）**：成功率是一条水平直线，30 次探测全 200；可用副本走出 4→5→4→5→4 的规则台阶（`maxSurge: 1` + `maxUnavailable: 0` + PDB `minAvailable: 3`，摘流与新 Pod 就绪在时间上错开）；重启计数全程为 0；p99 稳定在约 80ms；`kubectl -n order-demo-prod rollout status deployment/gateway` 在两分钟内完成。两条曲线放在一张面板上，结论无需解释：左边每次抖动都对应一个缺失的决策，右边每一格都能由清单字段推出来。

**两次现场的指标对照**（取曲线上的关键采样点）：

| 指标 | 事故现场（14:36 / 14:40 / 15:05） | 重演现场（对应时刻） |
|---|---|---|
| 成功率 SLI | 0% / 0–40% 锯齿 / 贴地 0% | 100% / 100% / 100% |
| 可用副本 | 0 / 0 / 0（手工改过 4 又掉 0） | ≥3（PDB 下限）/ ≥3 / 4 |
| Pod 重启计数 | 2 / 8（级联中）/ >8 | 0 / 0 / 0 |
| p99 延迟 | 超时上限 / 随锯齿抖动 / 超时 | 约 80ms / 约 80ms / 约 80ms |
| 审计手工写记录 | 2 次（改 Pod、改副本数） | 0 次 |

**三次正确决策的现场**（重演时间线里真正起作用的三处）：

- **决策现场一（14:36，readiness 门，H3）**：新 Pod 起来后 `/readyz` 返回非 200，Endpoints 不收录它，旧 Pod 继续承载流量；`kubectl get events` 里只有 `Readiness probe failed`，成功率曲线上没有任何新事件。发布「停在安全的半路」等待人工确认，而不是「把永远不健康的版本放进生产」。对照第 1 章 14:36：同样是发布卡住，一次是事故，一次是护栏在正确地拦截——差别在判定标准，不在工具 [R-31-5]。
- **决策现场二（14:45，回滚现场，H5）**：重演里这次变更根本不需要回滚，但回滚方案在发布之前已经写好并在 staging 演练过：`git revert <本次变更 PR>` + `argocd app sync --prune order-demo-prod`，演练记录带时限与验证结果。假使曲线拐头，值班面对的动作是「翻出演练记录、执行、观察曲线回到基线」，而不是「开会讨论怎么退」。公理 6（回滚方案先行）在这个现场的形态是：回滚是一段已验证的自动化，不是临场发挥。
- **决策现场三（15:00，漂移现场，H2 / H7）**：重演现场仍有同事习惯性地想手工改副本数——`kubectl edit` 被 RBAC 拒绝（第 26 章）；即使权限放开，声明副本数也会被 `selfHeal` 在一个同步周期内收敛回去 [R-31-2]。审计窗口里零手工写记录，「谁改的」这个问题在发生之前就已消解。监控曲线上，这一分钟与前后任何一分钟没有任何区别——**正确决策的现场，往往表现为什么都没发生**。

三次现场的共同点：每个决策都有事前写好的判据（探针语义、演练记录、声明副本数）与事后可查的记录（events、演练表、审计日志）；第 1 章的现场则处处是临场决定。把这条曲线与 31.2 的 H1–H8 逐点对照：曲线左侧的每一次抖动，都对应一个本可以被事前判据拦住的钩子。

行业调查里「采用工具数量」与「交付稳定性」并不同步增长 [R-31-6]；这张表说明的正是第 1 章 1.3 那条主张：把安全与可观测当横切属性贯穿每一环，八处决策缺口就会在进入下一环前被各自拦住，而不是攒到周五下午一起爆发 [R-31-5]。

## 31.2 逐条收口：H1–H8 分别被哪一章的哪个范式补上

下表**与 `book/hooks.md` 第一节完全一致**：主责章、该章要写的一句话、深化 / 落地章三处不改写；第四列把范式变成一条能当场执行的验证动作。

| 钩子 | 主责章 | 补上的范式（hooks.md 原句） | 可验证动作 |
|---|---|---|---|
| H1 | 第 3 章 七条原则 | 不可变镜像 + SHA 标签让产物可追溯，事故第一步就失守（落地 6、12、24） | `kubectl get deploy -o jsonpath='{..image}'` 全为 `git-<sha7>`，无 `latest` |
| H2 | 第 2 章 心智模型 | 声明式终态与控制循环解释了「手改无效」（深化 14、27） | `kubectl edit` 改副本数后在一个同步周期内被改回 |
| H3 | 第 8 章 探针与优雅上下线 | readiness 判错会让发布停在一个永远不健康的版本上（深化 13、15） | 滚动更新期间连续请求零 5xx，新 Pod 全部 `Ready` |
| H4 | 第 23 章 故障处置与演练 | CrashLoopBackOff 速查表让误杀可被快速识别与止血（根因 8、信号 21） | 注入一次 liveness 误杀后按 runbook 在时限内止血 |
| H5 | 第 13 章 部署策略选型 | 回滚方案先于发布方案，是这条事故最贵的教训（深化 16、15） | staging 存有一次带命令、时限、验证结果的回滚演练记录 |
| H6 | 第 9 章 配置与密钥 | 配置与密钥分离、外部注入，轮换不必重建镜像（深化 4、26） | 轮换 `order-demo/db-credentials` 后服务仍 200、Pod 无需重建 |
| H7 | 第 14 章 GitOps 引擎与晋升 | Git 唯一真相 + 漂移检测与自愈，堵住手工变更入口（深化 4、23） | `argocd app diff` 为空，审计窗口内零 `kubectl edit` |
| H8 | 第 22 章 面向症状的告警 | 每条告警必须可操作并指向 runbook（深化 23、20） | 逐条检查告警 100% 带 runbook 链接 |

逐条展开（钩子编号 → 主责章 → 补上的范式 → 可验证动作）：

- **H1 → 第 3 章**：七条原则把「不可变镜像 + `git-<sha7>`」定为不可协商项，理由是标签只是可变指针、摘要才是内容标识；第 6 章把它落成清单字段，第 12 章由 CI 统一打标签，第 24 章用签名验签做门禁。验证动作是读 image 字段并与 `git rev-parse --short=7 HEAD` 对照，两者一致 [R-31-5]。
- **H2 → 第 2 章**：控制循环的心智模型说明「改运行状态」与「改期望状态」是两回事，`kubectl edit` 会被控制器收敛回去；第 14 章给出漂移纠正的工程形态，第 27 章把协调循环正式定义。验证动作是手工改一个字段、观察它被改回 [R-31-2]。
- **H3 → 第 8 章**：`readinessProbe` 决定 Pod 何时接流量，`maxUnavailable: 0` 与 PDB 保证容量账；第 13 章算容量、第 15 章按指标判定继续放量。验证动作是滚动期间连续请求零 5xx。
- **H4 → 第 23 章**：CrashLoopBackOff 速查表把「liveness 误杀」变成可识别症状与止血动作；根因在第 8 章的探针语义，信号来自第 21 章可观测栈。验证动作是按 runbook 在时限内完成一次注入演练。
- **H5 → 第 13 章**：「没有验证过的回滚方案，不允许发布」把回滚从事故后的补救前移成发布前的门禁；第 16 章补数据侧 expand–contract，第 15 章让机器按指标自动执行。验证动作是 staging 的一次演练记录。
- **H6 → 第 9 章**：配置与镜像分离、凭据由 ESO 注入且 Git 里只有引用，轮换后端值即可；第 4 章给每环境独立凭据，第 26 章给动态凭据与审计。验证动作是轮换凭据后服务不中断 [R-31-5]。
- **H7 → 第 14 章**：GitOps 三要素（Git 声明 + 控制器持续收敛 + 漂移纠正）收回人的集群写权限，PR 即变更；第 4 章定仓库拓扑，第 23 章给漂移处置 runbook。验证动作是 `app diff` 为空 + 审计零手工记录 [R-31-5]。
- **H8 → 第 22 章**：告警面向症状、可行动、带 runbook，阈值由第 20 章的 SLO 与错误预算推导；第 23 章提供 runbook 模板。验证动作是逐条检查 runbook 链接。

> **首尾闭环（本书观点，不需要外部背书）**
>
> **主张**：同一变更按本书范式重做，H1–H8 每个失效点都能指出被哪一章的哪个范式补上；从 1.1 的 500 到零故障，缺的从来不是工具，是决策。
>
> **论证**：八个失效点落在「定义、地基、发布、响应、回滚、凭据、漂移、告警」八个不同决策位置，没有两个能靠同一工具顺带解决。这正是「一主线 + 两横切 + 一演进轴 + 地基篇」坐标系的用处：定位「烂在哪一环」，而非笼统「再上一套平台」。31.3 重演脚本把八条验证写成可执行断言，闭环靠命令输出。
>
> **反例与适用前提**：这不等于「做完 31 章才不会出事」。团队可以停在 L1 甚至 L0，只要补上 H1 / H5 / H7 三条最贵的决策，就能挡住多数同类事故（见 31.6 ROI 排序）。前提是**多人协作、跨环境晋升的变更**；一次性本地实验不在此列。把本章读成「工具清单」是误读：第 5、27 章警戒线恰恰反对那样做。

## 31.3 重演脚本、零故障验证与回滚

**`deploy/replay/order-demo-replay.yaml`**（重演基线：与 `ch01-incident` 同版本基线、语法合法且**语义正确**，Kubernetes 1.32+ 可直接 `apply`）：

```yaml

  labels:
    app.kubernetes.io/name: order-demo

  namespace: order-demo-prod
```

> 第 1 章事故清单里 `DB_PASSWORD` 明文写在同一个 ConfigMap（H6）；这里只剩业务配置，凭据由 ESO 注入键名 `order-demo/db-credentials`、不入 Git。`ConfigMap` 改名为 `order-demo-config-v2` 而非原地改 `3000 → 5000`，是第 9 章「immutable + 新对象」的落地：同一变更，改法不同。

**`hack/replay-incident.sh`**（重演 1.1 的同一变更，完整可执行）[R-31-7]：

```bash
#!/usr/bin/env bash
set -euo pipefail
# 用 ch31-replay 重演 1.1 的同一变更：把 PAYMENT_TIMEOUT_MS 从 3000 调到 5000。
# 与 ch01-incident 同版本基线；本脚本在一次性 kind 集群执行，零故障完成。
CLUSTER=order-demo-replay
NS=order-demo-prod
REPORT="/tmp/replay-incident-$(date +%Y%m%d%H%M%S).log"
```

### 31.4.1 30 条反模式的可观察症状与定位命令

31.4 的表回答「有哪些、烂在哪一环」；本表回答「怎么当场认出来、用什么命令确认」。症状列是监控面板或用户侧能直接看到的现象，命令列给出最小定位命令（可直接复制；环境对比类命令在 `order-demo-dev` / `order-demo-staging` / `order-demo-prod` 之间比对；通过标准是命令输出能**证实或排除**该反模式）[R-31-1]：

| 编号 | 反模式 | 可观察症状 | 定位命令 | 对应章 |
|---|---|---|---|---|
| AP-01 | `latest` 标签覆盖产物 | Pod 实际镜像与发版记录不符；仓库同标签推送历史被覆盖 | `kubectl -n order-demo-prod get deploy gateway -o jsonpath='{.spec.template.spec.containers[0].image}'`，与 `git rev-parse --short=7 HEAD` 对照 | 3、6、12 |

| AP-10 | 提交前无离线校验 / 版本矩阵 | CI 绿灯但 apply 时才报 schema 错误 | `kubeconform -strict deploy/replay/ && conftest test deploy/replay/` | 11 |

| AP-22 | HPA 无稳定窗口、反复抖动 | 副本数锯齿；HPA 事件频繁扩缩 | `kubectl -n order-demo-prod describe hpa api`（看 Events 与稳定窗口配置） | 18 |

### 31.4.2 30 条反模式的止血优先级与改错代价

31.4 回答「有哪些」，31.4.1 回答「怎么认出来」；本节回答「先改哪条、哪些可以后置、改错顺序的代价是什么」。排序用三问：这条反模式会不会在**下一次发版或下一次攻击**时直接制造事故？修复动作半途停下会不会比不改更糟？修复依赖哪些前置项？按答案分三档，风险口径取自 SRE 的风险排序方法 [R-31-4]，归档口径沿用 31.4 [R-31-1]：

| 档位 | 反模式 | 共同特征 | 可后置条件 |
|---|---|---|---|
| 立即止血 | AP-01、05、06、16、20、30 | 直接制造或放大事故，或让回滚失效——不修，同类事故必然复发且更难退 | 无；任何情况下都不后置 |
| 尽快（两周～一个月） | AP-02、07、08、11、12、15、17、18、19、21、23、27、28、29 | 单点修复即消除一类隐患，彼此不依赖，可并行排期 | 仅当对应环节从未复现、且已有护栏兜底时，可延后一个季度 |
| 可后置（季度级） | AP-03、04、09、10、13、14、22、24、25、26 | 结构性改进，依赖前两档落地（如渲染产物 review 依赖 SHA 标签与唯一变更入口） | 写进季度复评；出现一次真实症状即升级为「尽快」 |

立即止血档与 31.6 路线图的前 2 项、H1 / H5 高度重合——第 1 章 1.1 的八个失效点本来就是最高频的反模式，这不是巧合。改错顺序有两种代价。**顺序颠倒**：先做可后置项——上了 Argo CD 2.x、甚至写了 Operator，而 `latest` 标签与回滚方案原样不动——投入越大，两份真相（AP-15）越牢固，复盘时连「真相源是什么」都指认不清 [R-31-6]。**半途而废**：止血项比后置项更怕改一半——加了 `readinessProbe` 却不算容量账（滑向 AP-17），`selfHeal` 开了却不收回人的写权限（正是 AP-15）。所以每条止血项的完成判据一律取 31.4.1 的定位命令输出翻转：命令从「证实中招」变成「证实排除」，才算改完；这也与公开 postmortem 的方法论一致——止血以可验证的恢复证据收尾，不以「已安排」收尾 [R-31-7]。

## 31.5 成熟度模型与八环节自评表

**L0 手工 → L1 自动化 → L2 GitOps → L3 自助平台** 的跃迁，不是工具叠加，而是**变更入口、验证与回滚能力**的升级：L0 靠人敲命令，L1 把重复动作交给脚本与 CI，L2 把 Git 变成唯一入口并持续收敛，L3 把「默认就对」做成自助黄金路径。第 1 章 1.3 已立过这条主张，本章把它变成可填写的表 [R-31-3][R-31-4][R-31-6]。

### 31.5.2 自评表的填法、读法与优先级推导

31.5 的表回答「在哪一级」，31.5.1 回答「短板回哪章」；本节补三个操作问题：怎么填、怎么读、填完之后优先级怎么排。

**填法三步**：第一步，每个环节先跑 31.4.1 的定位命令，把输出粘进「实证」列——实证必须是命令输出或演练记录，一句「大概齐 L2」不是实证；第二步，对级时若一条实证同时能解释两个级别，取低者（例如 CI 已统一产出 SHA 标签、但仍允许手工改生产，定义环节只能记 L1）；第三步，拿不准的格子写「L1–L2（缺：××判据）」并注明缺哪条命令，禁止发明 L1.5 这类分级口径里不存在的档位 [R-31-3]。

**读法**：「八行最低者定团队级」这条规则已写进 `docs/maturity-selfcheck.md`，本节补一个更容易被漏掉的新信息：**读第二低的环节**——它决定修复会不会被拖住。例：晋升已到 L2（Argo CD 2.x + `selfHeal`）而观测仍是 L0，那么「漂移被自愈收敛」这件事没有任何指标能证实，晋升的 L2 是账面级别；此时下一项改造不是继续升晋升环节，而是把观测抬到 L1，否则后续所有验收判据本身不可信 [R-31-4]。

**优先级推导**：把三张表交叉——31.4.2 的止血档 × 31.5 自评结果 × 31.5.1 地图：止血档反模式落在自评最低环节的，是本季度第一项；落在第二低环节的，是第二项；两者都不沾的止血项按 31.6 的 ROI 序插入。评审会只需要回答三个问题：改哪条（AP 编号）、哪个环节（自评行）、哪条命令验收（31.4.1 输出翻转）。三档团队规模的填法差异见 31.6.1，本节不重复；季度与事故后的复评节奏沿用 `docs/maturity-selfcheck.md` 既有约定。

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：改造顺序应按 ROI 排序——**先把回滚与产物追溯做对，再谈渐进式交付与平台化**。
>
> **论证**：前 2 项成本最低、收益最高，且是后面所有能力的前提：没有可追溯的产物，回滚就没有目标；没有验证过的回滚，渐进式交付的「自动回退」退不到确定版本；没有唯一变更入口，平台化只是把手工通道包装得更好看。第 7、8 项收益随规模才显现，提前做的典型代价是「先上全套工具」——装了 Argo CD 2.x、Kyverno 1.x、Crossplane 却仍允许手工改生产，H1 / H5 / H7 一条没补 [R-31-6]。
>

### 31.6.2 从 L0 到 L3 的分阶段路线图：目标、动作、验收与卡点

31.6 定「先做什么」，31.6.1 定「每档做到哪停」，本节补第三个维度：**每次跃迁怎么走完**。三个阶段各给目标、关键动作、验收判据与常见卡点；团队规模档位沿用第 5 章，平台化内容衔接第 27–30 章 [R-31-3]。

| 跃迁阶段 | 目标 | 关键动作 | 验收判据 | 常见卡点与解法 |
|---|---|---|---|---|
| L0 → L1 | 把人的重复动作交给脚本与 CI，产物可追溯、回滚可执行 | SHA 标签进 CI（第 12 章）；一切 apply 来自仓库文件；三类探针 + preStop（第 8 章）；staging 首次回滚演练（第 13 章） | 推 commit 产出带 SHA 镜像；滚动更新零 5xx；一条带时限与验证结果的演练记录 | 清单化后每环境一份、脚本爆炸——用 overlay 收敛，见第 10 章；「回滚演练以后再补」是 L0 团队最贵的口头承诺（AP-16） |
| L1 → L2 | Git 成为唯一变更入口并持续收敛 | 定仓库拓扑（第 4 章）；GitOps 引擎 + `selfHeal`（第 14 章）；渲染产物进 PR review（第 10 章）；校验关卡前置（第 11 章）；SLO 与错误预算成文并接发布冻结（第 20 章） | `argocd app diff` 为空；审计窗口零手工写记录；错误预算耗尽时发布真的被冻结过一次 | 半吊子 GitOps：引擎在跑、手工通道没关＝AP-15，比停在 L1 更糟——收写权限要配套第 26 章的流程与沟通；SLO 写成口号即 AP-25 |
| L2 → L3 | 把前六项护栏做成自助黄金路径 | 黄金路径模板：新服务默认带探针、资源基线、策略与 SLO 卡片；扩展评估走第 27 章决策树；多集群发布按第 30 章；Operator 仅在第 28 章判据通过后写 | 新服务从模板到生产零手工 YAML；一次变更发两集群；自定义控制器数量为零（AP-14） | 平台代持护栏而业务团队仍留手工通道（AP-15 的平台版）；黄金路径做成第二套审批流程、研发绕道直连——黄金路径必须比绕道**更省事**，否则 L3 只是账面 [R-31-6] |

进入下一阶段的判据是上一阶段验收全绿——这正是 31.6 模板里「前一项未完成不启动后一项」在阶段粒度上的形态。三个阶段有一处不对称值得点破：L0→L1 的卡点几乎全是技术债，L1→L2 起卡点过半是流程与人心（收写权限的抵触、错误预算冻结要真敢执行），到 L2→L3 则几乎全是组织问题——平台团队与业务团队的激励若不一致，护栏就会被当作负担绕开，这与「工具数量不等于成熟度」是同一件事的两种说法 [R-31-6]。
