## 31.1 回到起点：用同一套坐标系重演那起事故

第 1 章 1.1 的周五 14:32，一次「只改了一行配置」让 `/orders` 稳定返回 500。那不是产品 bug——Kubernetes 的每个控制器都在按设计工作，失控的是决策 [R-31-2]。全书用三十章补上了那些缺失的决策，现在用**第 1 章的同一套坐标系**把同一变更再做一遍，看它会不会还出事。

> **合成案例声明**：本章重演的仍是第 1 章那起**教学合成的虚构事故**，非真实事件复盘；L3 资料只支撑「反模式方法论」与行业现状，不证明事故真实发生 [R-31-7]。

```
主线（一次变更的旅程）
  定义 → 校验 → 打包 → 晋升 → 发布 → 运行 → 观测 → 响应
  └─ 第 2 篇 ─┘   └─ 第 3 篇 ─┘  └ 第 4 篇 ┘  └── 第 5 篇 ──┘

横切 A：安全 · 策略 · 凭据（第 6 篇）—— 作用于主线每一环
横切 B：可观测 · 可回滚 · 可审计（第 5 篇集中展开）—— 贯穿全书

演进轴（第 7 篇）：L0 手工 → L1 自动化 → L2 GitOps → L3 自助平台

地基（第 1 篇）：心智模型 · 原则 · 环境拓扑 · 工具链地图 —— 支撑以上全部
```

**同一变更、两种结局**（时间线逐点对照第 1 章 1.1）[R-31-5][R-31-6]：

| 时刻 | 第 1 章的现象 | 第 31 章按范式重做的结果 | 补上的环节 |
|---|---|---|---|
| 14:33 | 镜像写 `:latest`，昨晚被 CI 覆盖 | 镜像是 `git-<sha7>`，标签与提交一一对应 | 定义（H1） |
| 14:34 | `kubectl edit` 改 Pod，几秒被改回 | 变更只从 Git PR 进，改运行状态本就不被允许 | 地基 / 晋升（H2、H7） |
| 14:36 | 新 Pod 永远不 `Ready`，可用副本掉到 0 | `readinessProbe` + `maxUnavailable: 0` + PDB，滚动期间始终有可用副本 | 定义 / 发布（H3） |
| 14:40 | 激进 liveness 误杀，重启级联无人定位 | 三类探针语义分明，误杀由第 23 章速查表与 runbook 止血 | 定义 / 响应（H4） |
| 14:45 | 想回滚却发现没方案、schema 不兼容 | 回滚方案先于发布写好，数据变更走 expand–contract | 发布（H5） |
| 14:50 | 凭据与业务配置混在一个 ConfigMap | 业务配置进 immutable ConfigMap，凭据由 ESO 注入、不入 Git | 定义（H6） |
| 15:00 | 手工改生产副本数，Git 与集群两份真相 | `selfHeal` 把漂移改回，审计窗口零手工写记录 | 晋升（H7） |
| 15:05 | 告警只有「5xx 偏高」，值班不知做什么 | 每条告警带 runbook 链接，按 SLO / 错误预算分级路由 | 观测 / 响应（H8） |
| 结果 | `/orders` 稳定 500 | `/healthz` 连续 30 次 200，零故障完成 | 首尾闭环 |

行业调查里「采用工具数量」与「交付稳定性」并不同步增长 [R-31-6]；这张表说明的正是第 1 章 1.3 那条主张：把安全与可观测当横切属性贯穿每一环，八处决策缺口就会在进入下一环前被各自拦住，而不是攒到周五下午一起爆发 [R-31-5]。

## 31.2 逐条收口：H1–H8 分别被哪一章的哪个范式补上

下表**与 `book/hooks.md` 第一节完全一致**：主责章、该章要写的一句话、深化 / 落地章三处不改写；第四列把范式变成一条能当场执行的验证动作。

| 钩子 | 主责章 | 补上的范式（hooks.md 原句） | 可验证动作 |
|---|---|---|---|
| H1 | 第 3 章 七条原则 | 不可变镜像 + SHA 标签让产物可追溯，事故第一步就失守（落地 6、12、24） | `kubectl get deploy -o jsonpath='{..image}'` 全为 `git-<sha7>`，无 `latest` |
| H2 | 第 2 章 心智模型 | 声明式终态与控制循环解释了「手改无效」（深化 14、27） | `kubectl edit` 改副本数后在一个同步周期内被改回 |
| H3 | 第 8 章 探针与优雅上下线 | readiness 判错会让发布停在一个永远不健康的版本上（深化 13、15） | 滚动更新期间连续请求零 5xx，新 Pod 全部 `Ready` |
| H4 | 第 23 章 故障处置与演练 | CrashLoopBackOff 速查表让误杀可被快速识别与止血（根因 8、信号 21） | 注入一次 liveness 误杀后按 runbook 在时限内止血 |
| H5 | 第 13 章 部署策略选型 | 回滚方案先于发布方案，是这条事故最贵的教训（深化 16、15） | staging 存有一次带命令、时限、验证结果的回滚演练记录 |
| H6 | 第 9 章 配置与密钥 | 配置与密钥分离、外部注入，轮换不必重建镜像（深化 4、26） | 轮换 `order-demo/db-credentials` 后服务仍 200、Pod 无需重建 |
| H7 | 第 14 章 GitOps 引擎与晋升 | Git 唯一真相 + 漂移检测与自愈，堵住手工变更入口（深化 4、23） | `argocd app diff` 为空，审计窗口内零 `kubectl edit` |
| H8 | 第 22 章 面向症状的告警 | 每条告警必须可操作并指向 runbook（深化 23、20） | 逐条检查告警 100% 带 runbook 链接 |

逐条展开（钩子编号 → 主责章 → 补上的范式 → 可验证动作）：

- **H1 → 第 3 章**：七条原则把「不可变镜像 + `git-<sha7>`」定为不可协商项，理由是标签只是可变指针、摘要才是内容标识；第 6 章把它落成清单字段，第 12 章由 CI 统一打标签，第 24 章用签名验签做门禁。验证动作是读 image 字段并与 `git rev-parse --short=7 HEAD` 对照，两者一致 [R-31-5]。
- **H2 → 第 2 章**：控制循环的心智模型说明「改运行状态」与「改期望状态」是两回事，`kubectl edit` 会被控制器收敛回去；第 14 章给出漂移纠正的工程形态，第 27 章把协调循环正式定义。验证动作是手工改一个字段、观察它被改回 [R-31-2]。
- **H3 → 第 8 章**：`readinessProbe` 决定 Pod 何时接流量，`maxUnavailable: 0` 与 PDB 保证容量账；第 13 章算容量、第 15 章按指标判定继续放量。验证动作是滚动期间连续请求零 5xx。
- **H4 → 第 23 章**：CrashLoopBackOff 速查表把「liveness 误杀」变成可识别症状与止血动作；根因在第 8 章的探针语义，信号来自第 21 章可观测栈。验证动作是按 runbook 在时限内完成一次注入演练。
- **H5 → 第 13 章**：「没有验证过的回滚方案，不允许发布」把回滚从事故后的补救前移成发布前的门禁；第 16 章补数据侧 expand–contract，第 15 章让机器按指标自动执行。验证动作是 staging 的一次演练记录。
- **H6 → 第 9 章**：配置与镜像分离、凭据由 ESO 注入且 Git 里只有引用，轮换后端值即可；第 4 章给每环境独立凭据，第 26 章给动态凭据与审计。验证动作是轮换凭据后服务不中断 [R-31-5]。
- **H7 → 第 14 章**：GitOps 三要素（Git 声明 + 控制器持续收敛 + 漂移纠正）收回人的集群写权限，PR 即变更；第 4 章定仓库拓扑，第 23 章给漂移处置 runbook。验证动作是 `app diff` 为空 + 审计零手工记录 [R-31-5]。
- **H8 → 第 22 章**：告警面向症状、可行动、带 runbook，阈值由第 20 章的 SLO 与错误预算推导；第 23 章提供 runbook 模板。验证动作是逐条检查 runbook 链接。

> **首尾闭环（本书观点，不需要外部背书）**
>
> **主张**：同一变更按本书范式重做，H1–H8 每个失效点都能指出被哪一章的哪个范式补上；从 1.1 的 500 到零故障，缺的从来不是工具，是决策。
>
> **论证**：八个失效点落在「定义、地基、发布、响应、回滚、凭据、漂移、告警」八个不同决策位置，没有两个能靠同一工具顺带解决。这正是「一主线 + 两横切 + 一演进轴 + 地基篇」坐标系的用处：定位「烂在哪一环」，而非笼统「再上一套平台」。31.3 重演脚本把八条验证写成可执行断言，闭环靠命令输出。
>
> **反例与适用前提**：这不等于「做完 31 章才不会出事」。团队可以停在 L1 甚至 L0，只要补上 H1 / H5 / H7 三条最贵的决策，就能挡住多数同类事故（见 31.6 ROI 排序）。前提是**多人协作、跨环境晋升的变更**；一次性本地实验不在此列。把本章读成「工具清单」是误读：第 5、27 章警戒线恰恰反对那样做。

## 31.3 重演脚本、零故障验证与回滚

**`deploy/replay/order-demo-replay.yaml`**（重演基线：与 `ch01-incident` 同版本基线、语法合法且**语义正确**，Kubernetes 1.32+ 可直接 `apply`）：

```yaml

# 与第 1 章事故清单的差别：git-<sha7> 镜像、三类探针、非 root、凭据不入 Git、

apiVersion: v1
kind: Namespace

  name: order-demo-prod
  labels:
    app.kubernetes.io/name: order-demo

kind: ConfigMap

  name: order-demo-config-v2
```

**`hack/replay-incident.sh`**（重演 1.1 的同一变更，完整可执行）[R-31-7]：

```bash
#!/usr/bin/env bash
set -euo pipefail
# 用 ch31-replay 重演 1.1 的同一变更：把 PAYMENT_TIMEOUT_MS 从 3000 调到 5000。
# 与 ch01-incident 同版本基线；本脚本在一次性 kind 集群执行，零故障完成。
CLUSTER=order-demo-replay
NS=order-demo-prod
REPORT="/tmp/replay-incident-$(date +%Y%m%d%H%M%S).log"

log() { echo "[$(date -u +%FT%TZ)] $*" | tee -a "${REPORT}"; }

if ! kind get clusters | grep -qx "${CLUSTER}"; then
  kind create cluster --name "${CLUSTER}"
fi

echo "== 0) 回滚方案先于发布方案（H5） =="
log "回滚命令：git revert <本次变更 PR> && argocd app sync --prune order-demo-prod"
log "回滚演练：在 staging 执行一次 git revert + app sync（见 31.3 回滚段）"

echo "== 1) 只改一行配置，产物不变（H1 / 公理 1、3） =="
kubectl apply --dry-run=server -f deploy/replay/order-demo-replay.yaml

echo "== 2) 应用正确形态基线 =="
kubectl apply -f deploy/replay/order-demo-replay.yaml
kubectl -n "${NS}" rollout status deployment/gateway --timeout=120s

echo "== 3) H1：产物可追溯，无 latest =="
IMG="$(kubectl -n "${NS}" get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
log "image=${IMG}"
case "${IMG}" in *:latest) log "失败：出现 latest"; exit 1 ;; esac

echo "== 4) H3 / H4：滚动更新期间连续请求零 5xx =="
kubectl -n "${NS}" port-forward svc/gateway 8080:8080 >/dev/null 2>&1 &
PF=$!
trap 'kill "${PF}" 2>/dev/null || true' EXIT
for i in $(seq 1 30); do
  curl -fsS http://127.0.0.1:8080/healthz >/dev/null 2>&1 && break
  sleep 1
done
FAIL=0
for i in $(seq 1 30); do
  CODE="$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8080/healthz || true)"
  [ "${CODE}" = "200" ] || FAIL=$((FAIL + 1))
done
log "30 次连续请求失败数=${FAIL}"
[ "${FAIL}" = "0" ] || { log "失败：出现非 200"; exit 1; }

echo "== 5) H2 / H7：Git 唯一真相、无漂移 =="
log "生产变更入口：Git PR；argocd app diff 应为空"
if command -v argocd >/dev/null 2>&1; then
  DIFF="$(argocd app diff order-demo-prod || true)"
  [ -z "${DIFF}" ] || log "注意：检测到漂移 ${DIFF}"
else
  log "argocd 未安装，漂移检查由第 14 章 CI 门禁承担"
fi

echo "== 6) H6：配置与密钥分离，凭据不入 Git =="
kubectl -n "${NS}" get configmap order-demo-config-v2 \
  -o jsonpath='{.data.PAYMENT_TIMEOUT_MS}{"\n"}'
if git grep -n 'DB_PASSWORD' -- deploy/ gitops/ | grep -q .; then
  log "失败：仓库出现明文凭据"; exit 1
fi
log "凭据由 ESO 注入键名 order-demo/db-credentials，Git 中只有引用"

echo "== 7) H8：告警带 runbook =="
log "逐条告警 100% 带 runbook_url（第 22 章 CL-G-11）"

echo "== 8) 首尾闭环：H1–H8 逐条收口 =="
echo "H1 [产物] 不可变镜像 + SHA 标签 …… 主责第 3 章，落地 6/12/24"
echo "H2 [终态] 声明式终态与控制循环 …… 主责第 2 章，深化 14/27"
echo "H3 [发布] readiness 判据 …… 主责第 8 章，深化 13/15"
echo "H4 [处置] CrashLoopBackOff 速查表 …… 主责第 23 章，根因 8 / 信号 21"
echo "H5 [回滚] 回滚方案先于发布 …… 主责第 13 章，深化 16/15"
echo "H6 [凭据] 配置与密钥分离 …… 主责第 9 章，深化 4/26"
echo "H7 [漂移] Git 唯一真相 + 自愈 …… 主责第 14 章，深化 4/23"
echo "H8 [响应] 每条告警可行动并指向 runbook …… 主责第 22 章，深化 23/20"

echo
echo "== 对照 ch01-incident 的 500，本次 /healthz 连续 30 次 200，零故障完成 =="
log "重演通过，报告: ${REPORT}"
```

## 31.5 成熟度模型与八环节自评表

**L0 手工 → L1 自动化 → L2 GitOps → L3 自助平台** 的跃迁，不是工具叠加，而是**变更入口、验证与回滚能力**的升级：L0 靠人敲命令，L1 把重复动作交给脚本与 CI，L2 把 Git 变成唯一入口并持续收敛，L3 把「默认就对」做成自助黄金路径。第 1 章 1.3 已立过这条主张，本章把它变成可填写的表 [R-31-3][R-31-4][R-31-6]。

| 环节 | L0 手工 | L1 自动化 | L2 GitOps | L3 自助平台 | 本团队自评（填写） |
|---|---|---|---|---|---|
| 定义 | 手改清单、`latest` | SHA 标签 + 不可变镜像 | 声明进 Git、渲染产物可 diff | 模板产出即带护栏 | ______ |
| 校验 | 上线才发现问题 | CI 校验 + 本地验证环 | 校验关卡进流水线、阻断合并 | 平台默认校验，研发无感 | ______ |
| 打包 | 每环境各改一份 | overlay / values 同源 | 仓库内渲染、PR diff 最终清单 | 黄金路径自动生成 | ______ |
| 晋升 | 手工 `kubectl apply` | 脚本推送多环境 | PR 晋升、控制器持续收敛 | 一次变更发多集群 | ______ |
| 发布 | 直接全量替换 | 滚动更新 + 回滚演练 | 回滚方案先于发布、可审计 | 渐进式交付自动判定 | ______ |

## 31.6 按 ROI 排序的改造路线图

**按 ROI 排序的改造路线图**（成本 / 收益只给相对档位与归因口径，不写具体单价）[R-31-3][R-31-4]：

| 序 | 改造动作 | 解决哪个失效点 | 相对成本 | 相对收益 | 前置 | 可验证动作 | 对应章 |
|---|---|---|---|---|---|---|---|
| 1 | SHA 标签 + 不可变镜像 | H1 | 低 | 极高 | 无 | `kubectl get deploy -o jsonpath='{..image}'` 无 `latest` | 3、6、12 |
| 2 | 回滚方案先行 + 演练 | H5 | 低 | 极高 | 1 | staging 一次带时限、带验证结果的回滚演练 | 13 |
| 3 | 探针与优雅上下线 | H3、H4 | 低 | 高 | 1 | 滚动更新期间连续请求零 5xx | 8 |
| 4 | 配置与密钥分离 + 外部注入 | H6 | 中 | 高 | 1 | 轮换凭据无需重建镜像、服务仍 200 | 9、26 |
| 5 | Git 唯一真相 + 漂移纠正 | H7、H2 | 中 | 高 | 1、2 | 手工 `kubectl edit` 被自愈改回、`app diff` 为空 | 2、14 |
| 6 | SLO / 错误预算 + 告警 runbook | H8 | 中 | 高 | 5 | 每条告警 100% 带 runbook 链接 | 20、22、23 |
| 7 | 渐进式交付 | — | 中高 | 中 | 1–6 | 5% 流量、注入错误率后自动回退 | 15 |
| 8 | 平台化 / 黄金路径 / 多集群 | — | 高 | 中（随规模增长） | 1–7 | 一次变更发两集群、模板自带护栏 | 30 |

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：改造顺序应按 ROI 排序——**先把回滚与产物追溯做对，再谈渐进式交付与平台化**。
>
> **论证**：前 2 项成本最低、收益最高，且是后面所有能力的前提：没有可追溯的产物，回滚就没有目标；没有验证过的回滚，渐进式交付的「自动回退」退不到确定版本；没有唯一变更入口，平台化只是把手工通道包装得更好看。第 7、8 项收益随规模才显现，提前做的典型代价是「先上全套工具」——装了 Argo CD 2.x、Kyverno 1.x、Crossplane 却仍允许手工改生产，H1 / H5 / H7 一条没补 [R-31-6]。
>
> **反例与适用前提**：这不等于「第 7、8 项永远不做」。团队规模、跨环境晋升数量、值班容量到第 5 章 L2/L3 档时，平台化收益会超过成本；那时再做，且仍要带着前 6 项护栏。前提是**存在多人协作、跨环境晋升的变更**；一次性本地实验跳过全部路线图即可。排序是诊断工具，不是硬性工序表。
