## 5.1 问题与反模式：在还没见过任何工具之前，怎么不被「工具堆叠」拖走

Helm、Kustomize、Argo CD、Flux、Crossplane、Kargo……读者打开任何一个云原生工具列表，第一反应往往是「到底该上哪几个」。这一章刻意**不教任何工具怎么装**（那是官方文档的事），只解决一件事：在还没见过任何工具之前，先建立一套不会把团队拖进「工具堆叠」的选型方法。

行业调查里「采用工具数量」与「交付稳定性」并不同步增长 [R-05-10]；CNCF Landscape 把工具分成若干层，恰恰说明每层解决的是**不同的问题域** [R-05-1]。工具堆叠的根因从来不是「工具不好」，而是「按工具名做决策」。

三个高频反模式（现象 → 根因 → 本章替代做法）：

**反模式一：按工具名设章、按热度选型。** 现象是「同一个问题域装了两个互相打架的控制器」（例如同时上 Argo CD 2.x 与 Flux 2.x 持续收敛同一份清单），漂移时谁改的都查不清。根因是把「工具」当成决策起点，而没有先问「我要解决哪个问题域」。本章的替代做法是先定七层问题域（5.2），再在每一层里选**至多一个**工具。

**反模式二：一上来引入 CRD。** 现象是「集群里多了一种自定义资源，升级、备份、卸载残留全变成团队的长期负债」。这里先把两个词用白话讲清楚：**CRD** 是「给 K8s 加一种新资源类型」，**Operator** 是「把运维知识写成控制器，让集群自己收敛」——两者的正式定义与「什么时候真的需要」都**详见第 27 章**，本章只在警戒线上白话提及，绝不拿它们当推理前提。本章的替代做法是把「引入 CRD」列为需要单独书面论证的选项，20 人团队默认不上（SP-11，展开归第 27、29 章）。

**反模式三：版本不锁定。** 现象是「某个 minor 升级让全书示例一夜失效」。根因是把工具版本当成可以随时跟进的滚动值。本章的替代做法是主版本写进决策、小版本锁进附录 A，并用 CI 多版本矩阵兜底（第 11 章落地）。

### 5.1.1 逐层「上错工具」的代价复盘（合成案例，逐段标注）

工具堆叠的可怕之处，不在「装上的那一刻」，而在「想退出来的那一天」。下面按七层地图（5.2）逐层复盘一个**合成案例**：每个案例都标注「合成案例」，不冒充真实事故，但代价量级来自真实的运维账本 [R-05-1]。请把它当成「如果当初按热度选型，会怎样」的推演。

**第 1 层 · 源码与 CI：两条流水线互相打架。**
（合成案例）某 15 人团队先用了仓库自带的 GitHub Actions 做 CI，半年后又听人说 Tekton 更「云原生」，于是把核心构建迁到 Tekton，旧流水线却没下线。结果是：一个 PR 同时触发两套构建，两边产物标签不同；有一次 Tekton 因配额被限流失败、GitHub Actions 成功，开发者以为过测合并，生产却跑的是失败那次构建的镜像。定位耗时一整天，根因是「同一次提交有两个真相源」。代价不是 Tekton 不好，而是没有先回答「这次要解决哪一层的问题」就叠工具 [R-05-10]。替代做法：CI 只保留一条主干，迁移是把流量整体切走，而非并存。

**第 2 层 · 构建与制品：每个环境各构建一次。**
（合成案例）团队早期没有「一次构建、跨环境晋升」的纪律，dev 在笔记本上 `docker build`、staging 在 CI 里构建、prod 在发布机上再构建一次，三次用的基础镜像小版本还不一样。一次 prod 报 `NullPointerException`，dev 复现不出——最后发现 prod 的基础镜像多打了一个补丁包，而该包在 dev 的基础镜像里不存在。代价：故障定位从「分钟级」变成「跨三天、跨三套环境比对」，且彻底违反「同一制品跨环境晋升」的公理 1。替代做法：构建只发生一次，产出带 `git-<sha7>` 的不可变制品，环境差异只通过配置体现（见公理 3）。

**第 3 层 · 配置与打包：dev 手写 YAML、prod 用 Helm。**
（合成案例）某团队 dev 环境图省事直接 `kubectl apply` 手写 YAML，生产环境却用 Helm 4.x 管理同一套逻辑。一次扩容要把副本数从 3 调到 5，开发者改了 dev 的 YAML，忘了 Helm 的 `values.yaml` 也要改，导致 staging 通过、prod 发布后副本数仍是 3，流量高峰直接被打满。代价是「同一份意图，两套实现，必有一处遗漏」[R-05-3][R-05-4]。替代做法：全环境用同一套同源清单（Kustomize 5.x overlay 或 Helm 4.x），差异只通过 overlay / values 表达，杜绝「手写 vs 模板」双轨。

**第 4 层 · 交付与 GitOps：Argo CD 与 Flux 同收敛。**
（合成案例）一个 40 人团队先上了 Argo CD 2.x，后来又有人把 Flux 2.x 接进同一份 Git 仓库「做对比」。某天 Argo CD 把清单收敛成 3 副本，Flux 因为自己缓存的 Generation 落后，又把它改回 2 副本，两个控制器你改我改，生产副本数在 2 和 3 之间反复横跳，监控曲线呈锯齿状抖动。定位「谁在动我的集群」花了大半天，最后只能把 Flux 整个停掉。代价不在工具本身，而在「同一问题域两个控制器，谁收敛了这份清单不可判定」[R-05-5]。替代做法：每问题域至多一个工具，收敛入口唯一（公理 5 的 Git 唯一真相侧）。

**第 5 层 · 扩展与运行时：20 人团队上 Crossplane。**
（合成案例）团队想「用代码管理云资源」，在 20 人、无平台组的状态下引入 Crossplane，把数据库、存储桶都抽象成 CRD。一次 Crossplane 小版本升级后，某个 Provider 的 CRD 字段变更，旧 `CompositeResourceDefinition` 卡在删除中、新资源无法创建，而团队里没人知道怎么清理残留类型。代价：一次本应 10 分钟的升级，演变成两天「猜残留 + 手工删 etcd 对象」的事故，且没有人能在值班时独立处理 [R-05-7]。替代做法：20 人团队默认不上 CRD 类扩展，基础设施用 Terraform 1.x 等成熟路径（见第 30 章），把「谁负责升级、怎么备份、怎么卸载」写进 ADR 再决定。

**第 6 层 · 观测与韧性：没 SLO 就上大盘。**
（合成案例）团队在还没有 SLO 卡片、告警没有 runbook 的情况下，先搭了一整套 Prometheus 3.x + 一堆大盘。结果告警规则照搬网上的「CPU > 80% 就报警」，而该服务本就周期性跑批、CPU 常驻高位，于是每天凌晨误报，值班被叫醒七八次，最后大家把告警静音，真出事反而没人看。代价是「告警疲劳」——比没有监控更危险，因为掩盖了真实信号 [R-05-1]。替代做法：先有 SLO 与错误预算（见第 20 章），再据其设计告警与 runbook（见第 22 章），观测栈是结果不是起点。

**第 7 层 · 策略与平台：10 人团队硬上 Kyverno 策略库。**
（合成案例）某 10 人团队听说「准入策略能防误配」，上了一套 Kyverno 1.x 加十几条自写策略，但无人专职维护。一次 K8s 升级后，一条 `validate` 策略的语法被废弃，所有新清单在准入时被拒，整个发布通道堵死，而唯一懂策略的人正在休假。代价是「策略把自己变成了单点故障」[R-05-6]。替代做法：无专人维护策略库的团队，先靠 CI 静态校验（见第 11 章）拦住明显错误，待有平台组再上 Kyverno（见第 25 章），且策略必须先在 `audit` 模式跑稳再转 `enforce`。

**复盘共性**：七层案例的代价全都落在「退出 / 维护」而非「引入」。工具上车的成本是一次性的、可见的；工具退出的成本是长期的、隐形的——这正是 5.3「过度工程警戒线」与 ADR「退出路径」栏要买下的可逆性。下一节（5.2）用七层地图把「该不该上」变成可判定的决策，而不是凭热度。

> 与第 1 章的分工（大纲第 5 章注）：第 1 章讲「问题域与篇的关系、这本书怎么读」，本章讲「工具怎么选」。不重复，也不在没见过任何工具时展开某个工具的实现——具体工具留到后续各自首次出现的章节。

## 5.2 范式与决策树：七层地图（1 页）

**工具链可分七层，每层解决一个独立问题域** [R-05-1]。这张表就是本章的「1 页地图」：先按问题域对号入座，再决定这一层要不要放工具。工具带主版本，小版本只锁在附录 A；对托管型 SaaS 没有固定主版本的，如实标注。

| 层 | 问题域 | 代表工具（主版本） | 主要章节 | 本层「何时不该用」 |
|---|---|---|---|---|
| 1 源码与 CI | 从提交触发校验与构建 | GitHub Actions / GitLab CI（托管，无固定主版本）、Tekton、Dagger | 12 | 单仓库单人提交、手工构建已够时 |
| 2 构建与制品 | 产出唯一不可变制品 | BuildKit、Kaniko、Harbor、cosign | 6、24 | 还没有「一次构建」纪律时 |
| 3 配置与打包 | 组织同源清单 / 参数化分发 | Kustomize 5.x、Helm 4.x、kubeconform、conftest | 10–11 | 只有一份清单、只有一个环境时（Kustomize 5.x / Helm 4.x 都先不上）[R-05-3][R-05-4] |
| 4 交付与 GitOps | 把声明持续收敛进集群 | Argo CD 2.x、Flux 2.x、Argo Rollouts 1.x | 14–15 | 还没有判断清单对错的标准之前 [R-05-5] |
| 5 扩展与运行时 | 扩展 K8s / 流量 / 密钥 | Gateway API 1.x、External Secrets 0.x、KEDA 2.x；CRD / Operator（详见第 27 章） | 18–19、27–29 | 需求只是「跑一个 HTTP 服务」时 |
| 6 观测与韧性 | 指标 / 日志 / 链路 / 演练 | OTel Collector 0.x、Prometheus 3.x、Loki 3.x、Chaos Mesh | 21–23 | 还没有 SLO 卡片、告警无 runbook 时（见第 20、22 章） |
| 7 策略与平台 | 准入、权限、IaC、自助平台 | Kyverno 1.x、Crossplane、Cluster API 1.x、Terraform 1.x、Backstage | 25–26、30 | 20 人团队、无专人维护策略与 CRD 时 [R-05-6][R-05-7] |

**项目成熟度分级**决定「能不能上」而不只是「想不想上」：CNCF 的项目分级（沙箱 / 孵化 / 毕业）是选型时的客观输入，越靠近生产核心的层越应该选成熟度高的项目 [R-05-2]。

**工具选型决策树**（问题域 → 候选 → 不选的理由 → 退出成本）：

```
这次要解决的问题落在七层里的哪一层？       不知道 → 别选工具，先回 5.2 地图定位
        │ 知道
这一层已经有工具在跑了？                   是 → 先问「为什么要换」，不要叠第二个
        │ 否
候选里有没有「何时不该用」命中当前团队？     是 → 这一层留空，写书面理由
        │ 否
能写出退出路径与替换成本吗？                 否 → 不选（等于把决策外包给供应商）
        │ 是
→ 写入 ADR：问题域 / 候选 / 不选理由 / 退出路径 / 版本（5.4）
```

> **本书观点（本章第 1 条主张，不需要外部背书）**
>
> **主张**：20 人团队不必同时上 Argo CD 2.x + Flux 2.x + Kargo 1.x + Crossplane；**工具数量不等于成熟度，每引入一个 CRD 都是长期运维负债**。
>
> **论证**：第 4 层（交付）里 Argo CD 2.x 与 Flux 2.x 解决的是同一个问题域，装两个只会让「谁收敛了这份清单」变得不可判定；Kargo 1.x 的晋升编排、Crossplane 的基础设施抽象，各自都要求有人长期维护升级路径、备份与卸载残留。团队规模没到需要这些能力的量级时，收益是想象出来的，成本是确定的。这与第 1 章 1.3 的 L0–L3 演进轴一致：成熟度看的是「变更入口是否唯一、产物是否可追溯、回滚是否演练过」，不是装了几个控制器。
>
> **反例与适用前提**：这不等于「小团队永远不能用 CRD」。当团队已有专门的平台组、且某个现成 Operator 明显降低运维负担时，引入是合理的（评估表见第 29 章）。前提是**存在需要多人协作、跨环境晋升的变更**；一次性本地实验不在此列。成熟度自评的反例速查见第 31 章。

### 5.2.1 版本锁定与 CI 多版本矩阵的最小实现（衔接第 11 章）

5.2 反模式三点出「版本不锁定」会让全书示例一夜失效；本节给最小可落地的锁法与兜底矩阵，并衔接第 11 章的校验流水线（kubeconform / conftest / kuttl + kind 版本矩阵，可验证动作 `git checkout ch11-validate`）。

**第一步：主版本进 ADR，小版本锁附录 A。** 在 5.4 的 ADR 模板里，「版本锁定」栏写主版本（如 `Kustomize 5.x`），具体小版本（如 `5.4.3`）落到附录 A 的「工具小版本锁定表」，由统稿随 K8s 大版本统一 bump，避免散落在各章 YAML 里各自为政。

**第二步：CI 多版本矩阵兜底。** 即使小版本锁死，集群侧的 K8s 大版本仍可能漂移。用 CI 矩阵在多个 K8s 版本上跑同一份渲染产物，提前暴露「某字段在新版本被废弃」这类问题。下面是最小实现（GitHub Actions，托管 CI 无固定主版本，按 5.2 第 1 层如实标注）：

```yaml
# .github/workflows/validate-matrix.yaml
# 适用：GitHub Actions（托管，无固定主版本）；K8s 版本见 matrix
name: validate-matrix
on: [pull_request]
jobs:
  k8s-matrix:
    runs-on: ubuntu-24.04   # 固定 runner 版本，契合本章「版本锁定」主题
    strategy:
      fail-fast: false
      matrix:
        k8s: ["1.28.0", "1.29.0", "1.30.0"]   # 随附录 A 大版本档同步
    steps:
      - uses: actions/checkout@v4
      - name: 起 kind 集群（版本来自 matrix）
        uses: helm/kind-action@v1
        with:
          node_image: "kindest/node:${{ matrix.k8s }}"
      - name: 渲染产物（Kustomize 5.x overlay）
        run: kustomize build overlays/prod > rendered.yaml
      - name: kubeconform 校验（第 11 章落地）
        run: kubeconform -strict -summary rendered.yaml
      - name: conftest 策略校验（第 11 章落地）
        run: conftest test rendered.yaml --policy policy/
```

**通过标准**：三个 K8s 版本下 `kubeconform` 与 `conftest` 均通过，PR 才允许合并；任一版本失败即阻断，错误信息指向具体被废弃的字段。

**与第 11 章的衔接**：本节的矩阵只负责「跨版本跑通」，真正的字段契约校验（kubeconform 的 CRD schema、conftest 的自定义规则、kuttl 的端到端冒烟）由第 11 章完整展开；本章只把「版本矩阵」这层壳搭好，避免重复实现。CI 里被拦下的错误字段，正是 5.1.1 里「小版本升级让示例失效」代价的前置消解。

**最小锁版检查（四列）。**

| 编号 | 检查项 | 怎么查 | 通过标准 | 失败处置 |
|---|---|---|---|---|
| CL-05-11 | 主版本已锁 | `grep -n '版本锁定' docs/adr/*.md` | 每个已选工具主版本明确 | 回 5.4 补锁版栏 |
| CL-05-12 | 矩阵覆盖多版本 | 查 `validate-matrix.yaml` 的 `matrix.k8s` | 含 ≥2 个在维护的大版本 | 补版本，回第 11 章对齐 |

这一步把「版本不锁定」的反模式直接转成可执行的 CI 门禁：锁死小版本、矩阵兜底大版本，工具升级不再是无声的雷。

### 5.2.2 七层决策表：每层默认选什么、什么时候留空、何时该换、换的代价

5.2 的地图回答「这一层解决什么问题」，5.3 的替换成本表回答「单个工具怎么退」；两者之间还缺一块：**按层看，默认选什么、什么时候该换、换了之后要付多少迁移成本**。下表以 10–50 人团队为默认档（更小规模先按 5.3.1 频率判据留空，更大规模只增层不换层）：

| 层 | 默认选什么 | 什么情况下留空 | 何时该换 | 换的迁移成本 |
|---|---|---|---|---|
| 1 源码与 CI | 仓库自带 CI（GitHub Actions / GitLab CI） | 单仓库且每周变更 ≤ 10 次 | 构建排队时间超过构建时长一半、需要自托管构建环境时换 Tekton 类 | 低：流水线即 YAML，逐 job 平移，产物标签契约不变 |
| 2 构建与制品 | BuildKit + 镜像仓库 | 尚无「一次构建」纪律（先立纪律再选工具） | 构建环境无 Docker daemon 时换 Kaniko | 低：换构建器不动产物契约（`git-<sha7>` 标签不变） |
| 3 配置与打包 | Kustomize 5.x overlay | 只有一份清单、一个环境 [R-05-3][R-05-4] | 需对外分发 Chart、或 values 参数超过 50 个时换 Helm 4.x | 中：模板化是重写不是平移，先归档渲染产物再迁 |
| 4 交付与 GitOps | Argo CD 2.x | 无判断清单对错的标准之前 [R-05-5] | Application 数过百管理不动 → ApplicationSet；仅当团队已深度使用 Flux 且无 UI 需求才考虑 Flux 2.x | 中高：停 sync → 导出 Application → 平移，切换期禁止手工改集群 |
| 5 扩展与运行时 | Gateway API + External Secrets（按需） | 需求只是跑一个 HTTP 服务 | Ingress 表达不了流量切分、密钥必须定期轮换时 | 中：CRD 类迁移按 5.5 顺序（先删实例再删类型） |
| 6 观测与韧性 | 托管观测起步 | 无 SLO 卡片前不上告警栈 | 数据量超托管配额、需长周期指标时自建 Prometheus 3.x（配 Thanos） | 中：指标历史可选迁，告警规则是 YAML 可平移 |
| 7 策略与平台 | Kyverno 1.x（有专人时） | 无专人维护策略库 [R-05-6] | 需要 Rego 生态与跨集群策略时换 Gatekeeper | 中：策略语义重写，先 `audit` 双跑再切 `enforce` |

**「何时该换」只有三条触发判据**：① 当前工具确实解决不了新需求（「有更好玩的」不算）；② 项目成熟度降级或官方 EOL [R-05-2]；③ 团队规模 / 变更频率跨过 5.3.1 的档位。换的纪律只有一条：**新旧工具不得并存收敛同一份清单**——5.1.1 第 1、4 层的合成案例已经演示过双真相源的代价 [R-05-10]。迁移期间旧工具只读、新工具只写，切换完成后按 ADR 退出路径卸载旧工具，才算换完；换层比换层内工具更慎重，因为跨层迁移意味着问题域本身变了，要重新过一遍 5.2 的决策树。

## 5.3 工具选型：最小可行组合、警戒线与退出路径

**按团队规模的最小可行组合表**（建议工具数为相对档位，成本只给归因口径，不写具体云厂单价）：

| 团队规模 | 建议工具数 | 必选层 | 可留空的层（须有书面理由） | 过度工程警戒线 |
|---|---|---|---|---|
| < 10 人 | 2–3 | 第 3 层 Kustomize 5.x、第 4 层 Argo CD 2.x | 第 5、6、7 层（用托管观测 / 暂不上策略与 CRD） | 出现第二个交付控制器即越线 |
| 10–50 人 | 4–5 | 加第 1、6 层（CI 校验、基础观测） | 第 5 层扩展、第 7 层平台工程 | 同一问题域装两个互相打架的控制器即越线 |
| 50–200 人 | 6–7 | 加第 7 层 Kyverno 1.x 策略、第 4 层渐进式交付 | 自研 Operator（详见第 27 章） | 没有专人维护却引入多个 CRD 即越线 |
| 平台团队 | 按七层按需 | 全部七层 | 无，但每层仍要写「明确不上什么」 | CRD 数量无上限、无人负责升级即越线 |

**过度工程警戒线**（命中任意一条，先停手再论证）：① 同一问题域装了第二个控制器；② 20 人团队里出现「Argo CD 2.x + Flux 2.x + Kargo 1.x + Crossplane」这类组合 [R-05-10]；③ 引入 CRD 却答不出「谁负责升级、怎么备份、怎么卸载」；④ 版本未锁定，某个 minor 升级会让示例失效 [R-05-2]；⑤ 没有退出路径就上线。

**自建 / 托管 / 云厂托管的取舍**按「**谁负责升级与故障**」而非功能清单来定：自建换来自主权，但要自己背升级、备份、值班；托管把运维转移出去，代价是锁定与可移植性 [R-05-8][R-05-9]。一个 10 人团队把第 6 层观测托管出去，通常比自建 Prometheus 3.x + Thanos 更划算；这不是功能比较，是责任归属比较。

**工具替换成本表**（每个候选必须回答「何时不该用」与「怎么退」）：

| 工具 | 替换成本 | 退出路径 | 何时不该用 |
|---|---|---|---|
| Kustomize 5.x | 低 | 保留渲染产物，换生成器即可 | 需要复杂条件逻辑、对外打包分发时 [R-05-4] |
| Helm 4.x | 中 | `helm uninstall <release>` + 渲染产物归档 | 只改几个字段、不愿维护模板时 [R-05-3] |
| Argo CD 2.x | 中高 | 先停 sync → 导出 Application → 再卸载 | 还没有判断清单对错的标准之前 [R-05-5] |
| Kyverno 1.x | 中 | 策略先置 audit → 删策略 → 卸载 | 无专人维护策略库时 [R-05-6] |
| CRD / Operator 类 | 高 | 先删 CR 实例 → 再删 CRD → 确认无残留类型（详见第 29 章） | 20 人团队、无平台组时（详见第 27 章）[R-05-7] |

> **本书观点（本章第 2 条主张，不需要外部背书）**
>
> **主张**：选型必须**同时给出「何时不该用」与退出路径**；没有退出路径的工具，等于把决策外包给供应商。
>
> **论证**：所有工具都会遇到版本不兼容、社区转向、团队规模变化的一天。若引入时没记录「替换成本」与「卸载顺序」，退出就会变成一次没人敢做的高风险操作，工具也就从「选择」变成「既成事实」。把「何时不该用」和「退出路径」写进 ADR（5.4），是把决策的可逆性显式买下来。
>
> **反例与适用前提**：这不等于「每个工具都要提前写好卸载脚本」。对 Kustomize 5.x 这类低成本工具，一句「保留渲染产物即可」就够；对 CRD 类高成本工具才需要完整卸载顺序（详见第 29 章）。前提是**工具会长期运行在生产链路上**；一次性本地实验无需 ADR。

**唯一示例实现**按 `book/decisions.md` 固定值：GitOps 用 Argo CD 2.x（Flux 2.x 仅作对比）、配置打包以 Kustomize 5.x overlay 为多环境基线（Helm 4.x 为对外分发 Chart）、流量层用 Gateway API + Envoy Gateway、准入用 Kyverno 1.x、密钥用 External Secrets Operator。本章的最小可行组合表与这些固定值逐项对齐，后续第 10、14、19、25 章的选型矩阵只深化、不推翻（SP-21）。

### 5.3.1 团队规模分档的量化判据

5.3 的最小可行组合表用「< 10 人 / 10–50 人 / 50–200 人 / 平台团队」分档，但「人多人少」若只凭感觉，分档就会失真。本节给每档补三个可量化判据：**人数**、**变更频率（每周有效变更数）**、**值班容量（可独立处理发布与回滚的人力）**。三者共同决定「这个工具团队养不养得起」，而不是看它多诱人。

| 规模档 | 人数判据 | 变更频率判据（每周有效变更） | 值班容量判据 | 对应的工具数上限 |
|---|---|---|---|---|
| < 10 人 | 研发 ≤ 10，无专职平台 | ≤ 10 次 | 1 人轮值，且此人能独立完成「发布 + 回滚」 | 2–3 |
| 10–50 人 | 研发 11–50，可能有 1 名平台兼职 | 10–40 次 | 2–3 人轮值，任一班次至少 1 人能处理回滚 | 4–5 |
| 50–200 人 | 研发 51–200，有 3+ 人平台组 | 40–150 次 | 专职 on-call 小组，7×24 有 ≥2 人可响应 | 6–7 |
| 平台团队 | 独立平台组 ≥ 5 人 | 按租户计，跨多团队 | 分层 on-call（平台 + 应用），有明确升级链路 | 七层按需 |

**判据怎么用（决策规则）。**
- *人数* 决定「有没有人维护」。一条 Kyverno 1.x 策略库（第 7 层）至少需要 1 名专职维护者；若平台组为 0，则按 5.3 警戒线「无专人维护却引入 CRD 即越线」[R-05-6] 直接判为「留空」。
- *变更频率* 决定「值不值得自动化」。每周 ≤ 10 次变更时，人工 `kubectl` + 一份 `docs/toolmap.md` 往往比上一整套 GitOps 更划算；频率跨过 40 次，Argo CD 2.x 这类持续收敛工具才真正摊薄成本 [R-05-5]。
- *值班容量* 决定「出事能不能兜住」。引入任何需要 on-call 响应故障的工具前，先问「这个班次里有没有人能独立回滚它」。若答案是「只有 XX 会」，那它就是单点故障，按 5.4.1 状态机应标「风险」而非「已采纳」。

**反模式：用人数掩盖频率。** 一个 5 人团队若服务的是高频交易类业务（每周变更 50+），人数档虽落在「< 10 人」，但频率与值班压力已逼近 10–50 档——此时应以**频率与值班容量为准**上调工具数，而非死守人数档。分档是起点不是枷锁：三者中任一越档，就按最严苛的那一档定工具上限。

**量化后的最小判定（四列）。**

| 编号 | 检查项 | 怎么查 | 通过标准 | 失败处置 |
|---|---|---|---|---|
| CL-05-09 | 分档判据已填 | `docs/toolmap.md` 头部加三行判据 | 人数 / 频率 / 值班三栏都有数 | 回本节补量化判据 |
| CL-05-10 | 工具数不越档 | 数已选工具 vs 上表上限 | 已选数 ≤ 上限 | 回 5.3 撤一项或论证上调 |

这三条量化判据与 5.3 的「建议工具数」互为校验：人数给下限直觉，频率与值班给上限硬约束。下一节用 ADR 把「为什么是这个档」写进决策记录。

### 5.3.2 团队规模与项目成熟度的匹配：5 人 / 20 人 / 100 人三个画像

5.3.1 给了分档判据，本节把三个典型规模落成具体画像——「该用什么、不该用什么、成熟度怎么卡」。成熟度约束只有两条：**生产核心链路（第 1–4 层）只用毕业或孵化项目** [R-05-2]；沙箱项目只允许进非生产的实验命名空间，且必须带到期复评（复用 5.4.1 的复评机制）。每跨一档规模，最多新增一个层的工具，不一次补齐。

| 画像 | 该用什么 | 不该用什么 | 说明 |
|---|---|---|---|
| 5 人（运维兼职 1 人，每周变更 ≤ 10 次） | Kustomize 5.x + 仓库自带 CI + 托管观测；第 4 层按 5.3.1 频率判据留空并写书面理由，频率跨档后才上 Argo CD 2.x | 任何 CRD / Operator（详见第 27 章）、Kyverno 策略库、第二个交付控制器 | 人少时最大的风险不是工具不够，而是工具没人养 [R-05-6] |
| 20 人（1 名平台兼职，每周变更 10–40 次） | Kustomize 5.x overlay 多环境 + Argo CD 2.x + 5.2.1 的 CI 版本矩阵；观测从托管转自建 Prometheus 3.x | Crossplane、Kargo 1.x、自研 Operator、Backstage | 这正是 5.2 本书观点第 1 条的量级：Argo CD 2.x + Flux 2.x + Kargo 1.x + Crossplane 的组合对 20 人是净负债 [R-05-10] |
| 100 人（平台组 3+ 人，7×24 on-call） | 补齐第 1、3、4、6、7 层：CI 校验矩阵 + Kyverno 1.x 先 `audit` 跑稳再转 `enforce` + 渐进式交付（见第 15 章） | 非业务控制器超过 5.3.3 的计数上限、无责任人的 CRD、沙箱项目进生产链路 | 规模到了之后，缺的通常是策略与渐进交付，不是再加一个 GitOps 控制器 [R-05-5] |

三个画像之间不是阶梯必经——5 人团队可以直接跳过第 4 层，20 人团队也可能因频率偏低而延后第 6 层。但**从 20 人走向 100 人时最常见的错误，是按 100 人的清单一次补齐**：每季度最多新增一层，每新增一个工具先过 5.4.1 的 ADR 评审，把「补工具」的节奏放进决策流程而不是采购流程。

### 5.3.3 复杂度警戒线的可数判据：几个控制器、几个 CRD 算过度

5.3 的五条警戒线是定性判断（「命中即停手」），但复盘时经常吵起来：「这算不算第二个控制器？」本节把「过度」变成可数的数。

**控制器计数**——统计非 `kube-system`、非业务命名空间里以 Deployment 形态运行的平台控制器：

```bash
# 列出平台控制器（示例：业务命名空间前缀为 order-demo-）
kubectl get deploy -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\n"}{end}' \
  | grep -v '^kube-system' | grep -v '^order-demo-'
# 通过标准：输出里每一行都能在 docs/toolmap.md 的某一层找到对应 ADR
```

计数上限按规模档：10 人以下 ≤ 2、10–50 人 ≤ 5、50–200 人 ≤ 10；超出即触发书面论证，答不出「谁负责升级」的按 5.3 警戒线 ③ 启动退出。

**CRD 计数**——把「装了几个 CRD」算清楚：

```bash
kubectl get crd --no-headers | wc -l   # 减去当前 K8s 版本自带数量即为引入量
```

判据：未上第 5、7 层扩展时应约为 0；Gateway API、External Secrets 这类**现成**的 CRD 按需 ≤ 3 组；**自研** CRD（不是现成 Operator 附带的）在 20 人团队里出现第 1 个，即触发第 27 章的书面论证 [R-05-7]。CRD 的可怕在卸载残留（5.5 已给删除顺序），数量本身就是长期负债的直接度量 [R-05-2]。

**一次计数的复盘示范**（合成案例）：某 20 人团队数出 7 个平台控制器——Argo CD、ESO、Cert-Manager、Prometheus Operator、一个聊天机器人、一个废弃的 CI Runner、一个来历不明的自动扩缩器。对照 10–50 人档上限 5，超了 2 个：CI Runner 是历史残留、自动扩缩器无人认领，两者按「无 ADR 先退」处理，退出后 5 个全部能对上 ADR，恰好达线。这个动作每季度做一次，花 10 分钟；不做，控制器就会像冰箱角落一样只进不出。

**过度工程的日常信号**（不靠数数就能察觉）：① 升级一个工具需要排期、写预案且无人敢执行；② 新同事问「为什么用 X」，没人答得上来；③ 同一个效果存在两条实现路径（5.1.1 第 1、3 层的双真相源）；④ on-call 手册里出现「这个组件出问题先问某某」。

**退路三步**：冻结引入（新工具申请一律缓批）→ 按业务依赖度从低到高逐个退出（先退无 ADR 或无责任人的）→ 退出后把本节计数阈值写进 CI 门禁（第 11 章），防止回潮。

### 5.4.1 ADR 评审、废弃与到期复评机制

5.4 给了 ADR 模板，但模板不保证决策「活」着。一个只写不评审、只采纳不废弃的 ADR 库，最终会和它描述的工具一样变成负债。本节把 ADR 的生命周期补齐：评审怎么过、什么时候该废弃、到期怎么复评。

**评审流程（四步，可逆优先）。**
1. *提议*：任何人在 `docs/adr/` 下新建 `NNNN-tool-choice.md`，填全 5.4 模板，状态置「提议」。
2. *评审*：由工具所属层的责任人牵头，拉一次不超过 30 分钟的评审，逐条核对「何时不该用」「退出路径」两栏是否填全、是否命中 5.3 过度工程警戒线。
3. *裁决*：结论写入状态栏——「已采纳」或「已否决」；否决的 ADR 保留但不进入工具地图，避免重复讨论。
4. *归档*：已采纳的 ADR 编号进 `docs/toolmap.md` 对应层；工具带着主版本进入链路，小版本锁进附录 A。

评审不是走形式：若「退出路径」写不清，按 5.5 通过标准「退出路径没在 ADR 里写清，就不允许把工具带进第 10 章」（CL-G-03），直接打回。

**状态机。** 每份 ADR 处于且仅处于一种状态：

| 状态 | 含义 | 进入条件 | 退出动作 |
|---|---|---|---|
| 提议 | 待评审 | 新建模板 | 评审后转「已采纳 / 已否决」 |
| 已采纳 | 工具在链路中 | 评审通过 | 复评不达标转「已废弃 / 已过期」 |
| 已否决 | 记录在案不采用 | 评审驳回 | 不再讨论，可作未来参考 |
| 已废弃 | 曾采纳，现已退出 | 命中废弃条件 | 执行退出路径，更新工具地图 |
| 已过期 | 复评超期未处理 | 复评周期到点未复评 | 工具标黄，限期补复评 |

**废弃条件（命中任意一条即启动退出）。**
① 工具官方宣布 EOL 或停止维护，且社区无继任；② 团队规模 / 变更频率跨过 5.3.1 量化档位，原选型前提失效；③ 出现更优候选，且当前工具能按 ADR「退出路径」无损退出；④ 连续两次复评未通过「仍解决原问题域且无更低价替代」的判定；⑤ 命中 5.3 过度工程警戒线且无书面补偿。废弃不是失败，是把「当初的正确」诚实更新为「现在的正确」。

**到期复评机制。** ADR 不是一次性判决，它有有效期：
- *复评周期*：主版本工具每 **K8s 大版本** 复评一次（如 1.28→1.29），纯托管 SaaS 至少每 **季度** 一次。
- *触发即评*：出现上述废弃条件任意一条，立即触发一次临时复评，不等周期。
- *复评动作*：更新「版本锁定」栏、核对退出成本档位是否变化、在 ADR 末尾追加一条 `复评：YYYY-MM-DD 结论` 记录。
- *超期处置*：复评到点未处理，状态自动转「已过期」，工具在地图中标黄，限期两周内补评，否则按废弃处理。

| 复评触发项 | 周期 / 触发 | 责任人 | 产出 |
|---|---|---|---|
| 主版本工具 | 每 K8s 大版本 | 层责任人 | 追加复评记录 + 版本栏 |
| 托管 SaaS | 每季度 | 层责任人 | 追加复评记录 |
| 废弃条件命中 | 立即 | 任意发现人 | 启动退出或留书面补偿 |
| 超期未评 | 自动 | 平台 | 状态转「已过期」 |

**最小评审检查清单（四列）。**

| 编号 | 检查项 | 怎么查 | 通过标准 | 失败处置 |
|---|---|---|---|---|
| CL-05-06 | ADR 状态合法 | `grep -n '状态' docs/adr/*.md` | 每份处于五态之一，无空白 | 补状态，回评审流程 |
| CL-05-07 | 复评记录连续 | 查 ADR 末尾 `复评：` 行 | 最近一次不晚于周期 | 限期两周内补复评 |
| CL-05-08 | 废弃已执行退出 | `kubectl get crd \| grep` 工具类型 | 已退出的工具无残留类型 | 回 5.5 卸载顺序 |

这条机制把「工具上错」的代价前置到决策阶段：评审拦一次，比事后退出省十天。

## 5.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（桌面推演，不产生集群变更）：

```bash
# 1) 每个 ADR 的「何时不该用」「退出路径」两栏必须填全
for f in docs/adr/*.md; do
  grep -q '何时不该用' "$f" || echo "MISSING 何时不该用: $f"
  grep -q '退出路径' "$f" || echo "MISSING 退出路径: $f"
done

# 2) 七层中被主动留空的层有书面理由
grep -n '留空理由\|明确不上什么' docs/toolmap.md

# 3) 无重复问题域的工具：同一层不应出现两个交付控制器
grep -n 'Argo CD\|Flux' docs/toolmap.md
```

**通过标准**：

| 判据 | 期望结果 |
|---|---|
| ADR 两栏 | 每个 `docs/adr/*.md` 都含「何时不该用」与「退出路径」，无 `MISSING` 输出 |
| 留空有理由 | `docs/toolmap.md` 里被留空的层都写了理由，「明确不上什么」至少 3 条 |
| 无重复问题域 | 第 4 层只出现一个交付控制器（Argo CD 2.x），没有第二个持续收敛工具 [R-05-5] |
| 版本已锁定 | 每个已选工具带主版本，小版本指向附录 A [R-05-2] |

**回滚命令 / 步骤**（本章不产生集群变更；工具退出按 ADR 的卸载顺序执行）。下列 CRD / CR 名为示例，按 ADR 里的实际值替换：

```bash
CRD="example-tool.widgets.io"
CR_KIND="Widget"

# 1) 先列出并删除所有 CR 实例（顺序不能反）
kubectl get "${CR_KIND}" -A || true
kubectl delete "${CR_KIND}" --all -A --ignore-not-found || true

# 2) 再删 CRD
kubectl delete crd "${CRD}" --ignore-not-found || true

# 3) 确认无残留类型（清理钩子卡住等卸载残留的处置详见第 29 章）
kubectl get crd | grep "${CRD}" || true
```

> **顺序不能反**：先删 CRD 会让 CR 实例变成孤儿、卡在删除中（卸载残留的深入展开详见第 29 章）。退出路径的完整性由 5.4 的 ADR「退出路径」栏保证；本章不展开具体清理钩子的语义，避免在概念梯度里提前定义它。

**回滚验证**：

```bash
kubectl get crd | grep "${CRD}" || true
kubectl api-resources | grep -i widget || true
```

通过标准：`kubectl get crd` 中已无该工具注册的类型、`api-resources` 中无对应资源、`docs/adr/` 中该 ADR 状态改为「已废弃」。**退出路径没在 ADR 里写清，就不允许把工具带进第 10 章**（CL-G-03）。
