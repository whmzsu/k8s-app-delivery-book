## 17.1 问题与反模式：CPU 没跑满却变慢，内存没报警却被杀

**合成案例**（本书统一采用虚构合成场景，不指向任何真实事故）。大促前一周，团队做了一轮压测，随后有人为了让单节点「塞得下更多副本」把 `api` 的 `requests` 往下调，又为了「账好算」把 CPU limit 设成和 requests 一样。上线后的现象很分裂：白天 QPS 上来，`api` 的 P99 从 80ms 涨到 600ms，但 `kubectl top pod` 显示 CPU 只有 60%，监控大盘上没有任何一条「CPU 打满」的告警；到了夜里偶发 502，翻容器日志只看到进程被重启，`kubectl describe pod` 里 `Last State: Terminated`，`Reason: OOMKilled`，退出码 137，可内存曲线峰值离 limit 还有一截。值班同学按「内存没超」这个前提查了两个小时，最后才发现被杀的是容器工作集，而节点当时正处在内存压力下 [R-17-1][R-17-3]。

这类故障之所以难查，是因为它把三件不同的事混成了一件：**调度依据**、**运行时上限**和**驱逐顺序**。CPU 与内存是两类性质完全不同的资源——CPU 是可压缩资源，超过 limit 之后内核用 CFS quota 把进程「掐住」，表现为排队与尾延迟抖动，不会杀进程；内存是不可压缩资源，超过 limit 直接由内核 OOM killer 杀掉容器，不可回退 [R-17-1]。把这两类后果当成一回事，就会得出「CPU 没打满所以没问题、内存没超所以不该被杀」的错误推理。运行时稳定性是容器平台最普遍的运维课题之一，行业调查长期把资源与容量问题排在前列，这也是本章把「能按 runbook 定位一次 OOMKilled」写成可验证动作的原因 [R-17-9]。

三个高频反模式，按「现象 → 根因 → 本章替代做法」拆开：

**反模式一：不填 requests，或把 requests 当「保底配额」随手填。** 现象是调度器挑节点时没有依据、同一批 Pod 忽而挤在一台忽而 Pending；一旦节点内存吃紧，最先被驱逐的总是这批 Pod。根因是 requests 同时决定调度 placement 与 QoS 等级，什么都不填的 Pod 会落到 BestEffort，驱逐优先级最高 [R-17-1][R-17-3]。本章的替代做法是**全工作负载强制基线**：每个容器都写 requests，命名空间再用 LimitRange 给遗漏者兜底，二者叠加后 BestEffort 不再出现（见 17.3、17.4）。

**反模式二：把 CPU limit 设得和 requests 一样「好算」。** 现象就是合成案例里的 P99 抖动：请求在 cgroup 里排队，CPU 使用率曲线反而很平，因为被限流的 CPU 时间根本没被计入「使用」。根因是把「可预测」错当成「稳定」——确定性配额换来的是尾延迟代价 [R-17-1]。本章的替代做法是在线服务只保留 CPU requests 作为调度依据，放宽或去掉 CPU limit，容量不足时靠第 18 章的 HPA 加副本而不是靠限流硬扛。这条取舍是本章「本书观点」，17.2 会给完整论证与反例。

**反模式三：只看「平均使用率」定基线。** 现象是压测报告写着「平均 CPU 35%、平均内存 90Mi」，按这个值设的基线一到大促就出事。根因是平均值把峰值削平了：GC 停顿、批量任务、冷启动这些瞬时尖峰在均值里几乎看不见 [R-17-8]。本章的替代做法是用分位数（P95/P99）与压测曲线定基线，并按 USE 方法分别看利用率、饱和度与错误，而不是只盯一个均值 [R-17-8]；过载时系统行为由最弱一环决定，基线必须给这一环留突发余量 [R-17-6]。

> **一个刻意的边界**：本章只处理「一个 Pod 该申请多少、上限多少、被杀/被驱逐时怎么判读」。副本数怎么随负载变化是第 18 章，故障注入与速查表是第 23 章，指标怎么采集是第 21 章。先把单 Pod 的资源语义讲透，才能把「抖动」和「驱逐」这两类现象分别归因到正确的层。

## 17.2 范式与决策树：requests 买调度、limits 买上限、QoS 买驱逐顺序

先把三个容易混用的概念一次说清。

**requests** 是给调度器的「占地声明」：调度器按各容器 requests 之和挑选有足够可分配余量的节点，它同时是 QoS 分档与 HPA 百分比指标的分母。它不是「运行时最低保证」的同义词——CPU request 会被换算成 cgroup 的 `cpu.shares` 权重，只在争抢时决定分配比例，空闲时别的工作负载仍可用满 [R-17-1]。**limits** 是硬上限：CPU 超限被 CFS quota 限流，内存超限触发 OOMKilled [R-17-1]。二者一个管「放得下吗」，一个管「最多能用多少」。

**QoS 三档**是 Kubernetes 依据 Pod 里各容器 requests/limits 的写法自动判定的驱逐优先级，不需要单独创建对象。判定规则与后果见表 17-1。

表 17-1　QoS 三档判定与驱逐顺序

| 档位 | 判定规则（Pod 内每个容器） | 典型写法 | 节点内存压力下的驱逐顺序 | 适合谁 |
|---|---|---|---|---|
| Guaranteed | 每种资源都设了 requests **且** limits，且二者相等 | `requests==limits`（cpu 与 memory 都满足） | 最后 | `db` 这类不可丢状态、要求最稳的组件 |
| Burstable | 至少有一个 requests 或 limits，但不满足 Guaranteed | `requests < limits` | 中间 | 绝大多数在线服务，含本章 `api` |
| BestEffort | 任何资源都没设 requests/limits | 什么都不写 | 最先 | 不允许用于生产工作负载 |

`api` 按配置契约写的是 requests `cpu: 100m, memory: 128Mi`、limits `cpu: 500m, memory: 256Mi`，requests 严格小于 limits，因此 QoS 是 **Burstable**，不是 Guaranteed [R-17-1]。这不是疏漏，而是刻意的容量取舍：若把它抬成 Guaranteed（`requests==limits`），调度器就要按 500m/256Mi 为每个副本预留，同样的节点能放的副本数会明显下降。想要 Guaranteed 的稳定性，代价是调度容量，二者不可兼得 [R-17-7]。

**PriorityClass** 解决的是另一层问题：QoS 只在同节点内存压力驱逐时排序，而 PriorityClass 决定调度队列里的先后与抢占行为——高优先级 Pod 可以抢占低优先级 Pod 的节点位置 [R-17-2]。三者作用在不同层次，不能互相替代：LimitRange 给默认值、ResourceQuota 给命名空间总量、PriorityClass 给驱逐与抢占顺序 [R-17-2][R-17-4][R-17-5]。

表 17-2　`order-demo` 资源基线（仅 `api` 一行为冻结契约值，其余为本章示例基线，可按压测调整）

| 组件 | requests | limits | QoS | 依据 | 何时调整 |
|---|---|---|---|---|---|
| `api` | `cpu: 100m, memory: 128Mi` | `cpu: 500m, memory: 256Mi` | Burstable | 分位数压测曲线 + 突发余量 | P99 逼近 limit、或 GC 尖峰被削平 |
| `gateway` | `cpu: 50m, memory: 64Mi` | `cpu: 500m, memory: 128Mi` | Burstable | 入口转发，CPU 与连接数相关 | 连接数翻倍、TLS 终止下沉到入口 |
| `db` | `cpu: 250m, memory: 512Mi` | `cpu: 250m, memory: 512Mi` | Guaranteed | 有状态、不可丢 | 数据集增长、连接数上升 |
| `worker` | `cpu: 50m, memory: 64Mi` | `cpu: 300m, memory: 192Mi` | Burstable | 异步任务，允许被抢占 | 队列积压时长变长（见第 18 章 KEDA） |

> 表 17-2 里 `db` 用 `requests==limits` 换 Guaranteed，但这也意味着它一旦触到内存 limit 就直接 OOMKilled，没有 Burstable 的缓冲。是否给数据库设内存 limit 本身就是一个决策，第 16 章的有状态组件章节会展开；本章只用它演示「QoS 是写法的副产品」。

**Guaranteed 的代价可以算出来。** 上一段说「抬成 Guaranteed 会让同样节点能放的副本数明显下降」，不落到数字上就是一句空话，没法拿去跟业务方对齐。取一台 8 vCPU / 32GiB 的节点（扣掉 kubelet 预留与系统进程后 allocatable 记为 8 vCPU / 30GiB，DaemonSet 占用先不计），把表 17-2 的组件按两档写法各算一遍算术上限，见表 17-3。

表 17-3　Guaranteed 与 Burstable 的调度容量对照（单节点 8 vCPU / 30GiB allocatable，未计 DaemonSet）

| 组件 | 写法 | requests / limits | CPU 可放副本 | 内存可放副本 | 实际可放 | 超卖比（limits 总和 ÷ allocatable） |
|---|---|---|---|---|---|---|
| `api` | Burstable（契约值） | `100m/128Mi` → `500m/256Mi` | 80 | 240 | **80**（CPU 先耗尽） | 5.0 |
| `api` | Guaranteed（假想） | `500m/256Mi` == limits | 16 | 120 | **16** | 1.0 |
| `gateway` | Burstable | `50m/64Mi` → `500m/128Mi` | 160 | 480 | **110**（`maxPods` 先到） | 6.9 |
| `gateway` | Guaranteed（假想） | `500m/128Mi` == limits | 16 | 240 | **16** | 1.0 |
| `db` | Guaranteed | `250m/512Mi` == limits | 32 | 60 | **32** | 1.0 |

这张表要读出的不是「Guaranteed 浪费资源」，而是三件事：

1. **调度容量只由 requests 决定，跟 limits 无关。** 表里 `api` 从 80 掉到 16，唯一原因是 requests 从 `100m` 抬到了 `500m`；把 limits 从 `500m` 降到 `100m`（也就是「拉平」）不会减少一个副本位。所以「想稳就上 Guaranteed」这句话在成本上应翻译成「想稳就抬 requests，代价是 5 倍调度容量」——两个动作在不同维度，不能混谈 [R-17-1][R-17-7]。
2. **超卖比是 Burstable 的来源，也是它的风险。** 5.0 意味着节点上所有容器的 limits 之和是 allocatable 的 5 倍：只要大家同时冲向自己的上限，节点必然超载。这不是配置错误，而是默认契约——超卖换密度，密度换成本，风险由 QoS 与 PriorityClass 的驱逐顺序兜住（表 17-6）[R-17-7]。
3. **Guaranteed 在碎片面前没有弹性。** `api` 若改用 `500m` 的 requests，8 vCPU 节点只能整块切 16 份；再混入 `db`、Ingress 等不同尺寸的 Pod 后，bin-packing 剩下的零头再也吸收不了别的负载。Burstable 则可以用 limits 去填这些零头。

量化到集群规模：3 节点 prod 池，`api` 在 Burstable 下可放 240 个副本位，Guaranteed 下只有 48 个（约 5 倍差距）。`maxReplicas: 10` 这个峰值在两档下都「放得下」，差别出现在两处——滚动更新时的 `maxSurge` 额外副本，以及节点故障后的重排余量：Burstable 下挂掉一个节点、80 个副本位蒸发时，剩下的 160 个位还能接住；Guaranteed 下 16 个位一蒸发，多出来的副本只能 Pending。

换算成机器数：同样要放 240 个 `api` 副本位，Burstable 用 3 台 8 vCPU 节点就够，Guaranteed 要 15 台。本章只给这个倍数与归因口径（机器数 × 单机成本），不写单价——价格随区域、计费方式与承诺折扣变动，写进书里必然过时；能长期成立的只有「调度容量由 requests 决定」这一条。

那什么时候该买 Guaranteed？本章的判断是三条同时成立：**状态不可丢**（`db`）、**内存尖峰不可控**（如共享内存型缓存）、**所在节点池有异构负载会争抢**。`api` 不满足第二条——它的内存曲线可由分位数压测界定（17.2.1），所以维持 Burstable，用 HPA 兜突发、用 PriorityClass 定驱逐顺序，是更划算的组合。

决定抬 requests 之前还要过一遍 LimitRange 的比值约束：17.4 里 `maxLimitRequestRatio.memory: "4"` 意味着 `requests.memory` 抬到 `256Mi` 时 `limits.memory` 不能超过 `1Gi`，`cpu: "10"` 则允许 `500m/100m` 这种 5 倍写法。把 requests 抬到与 limits 相等会同时丢掉超卖空间和这条比值约束的缓冲，属于「一步到位」的激进选项，只建议用在 `db` 这类已确认需要独占的组件上 [R-17-4]。

> 口径提醒：表 17-3 是纯算术上限，未计 DaemonSet（CNI 与日志代理通常各占 `100m/200Mi` 量级）、kube-reserved，也未计命名空间 ResourceQuota——17.4 的 `limits.cpu: "8"` 往往比节点容量更早生效，真到扩容时先撞的是它。实测通常再少 1–2 个副本位；容量规划要看 `kubectl describe node` 的 `Allocated resources` 段，而不是拿这张表直接排产。

**决策树**（判断一个工作负载的资源该怎么填）：

```
这个 Pod 的每个容器都写了 requests？   否 → 补 requests；命名空间加 LimitRange 兜底（17.4）
        │ 是
组件是在线、对尾延迟敏感？             是 → 只保留 CPU requests，放宽/去掉 CPU limit（本书观点）
        │ 否（离线 / 批处理）
内存是否需要硬上限？                   是 → 设 memory limit，并按 17.5 的 OOM 演练验证
        │ 否
是否要拿到 Guaranteed？                 是 → 所有容器所有资源 requests==limits（代价：调度容量）
        │ 否 → Burstable，用 PriorityClass 区分在线/离线驱逐顺序（17.4）
→ 用分位数压测曲线复核，把 P99 与 limit 之间留出突发余量
```

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：把 CPU limit 设得和 requests 一样「好算」，是以牺牲在线服务的尾延迟换取账面上的可预测性；对延迟敏感的工作负载，这笔交易通常不划算。
>
> **论证**：CPU 是可压缩资源，超限的后果是 CFS quota 限流而非报错。限流期间进程在 cgroup 里排队，`kubectl top` 看到的「CPU 只有 60%」是被掐住之后的读数，排队时间却已经计入 P99。一次压测对照很容易复现：同一 QPS 下，去掉 CPU limit 的副本 P99 明显低于「requests==limits」的副本，而两者平均 CPU 使用率几乎相同；差值全部落在尾部分布里。多出来的容量不确定性，应该用第 18 章 HPA 的副本弹性去吸收，而不是用单机限流去压平。
>
> **反例与适用前提**：这不等于「任何场景都不设 CPU limit」。离线批处理、多租户强隔离、按 CPU 时长计费的平台，需要确定性配额来防止单个租户吃满整机，此时 CPU limit 合理且必要；托管节点若内核未开启 `cpuCfsQuota` 关闭选项、或合规要求所有容器都有硬上限，也应保留。本结论的前提是「在线延迟敏感 + 已有 HPA 兜底 + 节点有超卖余量」；三者缺一，请先补齐再谈放宽。

### 17.2.1 压测对照：limit 拉平前后的 P99 与 `cpu.stat`

上面那条本书观点给的是论证，不是数据。要让「放宽 CPU limit」变成团队能签字的设计，需要一次可复现的对照压测——因为限流的证据不在使用率曲线里，只在分位数和 `cpu.stat` 里。

**实验设计**（合成环境，`api` 镜像 `registry.example.com/order-demo/api:git-1a2b3c4`）：

- **固定副本**：`replicas: 2`，临时关闭 HPA。副本数一变，P99 的变化就分不清是限流还是扩容带来的（见第 18 章）。
- **三组写法**：A＝契约值 `100m/500m`；B＝「拉平」`100m/100m`；C＝Guaranteed `500m/500m`。三组只改 `resources.cpu`，内存 `128Mi/256Mi`、探针、镜像全不动。
- **负载**：`vegeta 12.x` 常量速率 100 / 200 / 300 / 400 / 500 RPS，每档 5 分钟，取后 3 分钟稳定段；目标 `GET /orders`，经 `gateway` 8080 进入，与 17.5 的验证路径一致。
- **环境**：kind 三节点运行在 16 vCPU 宿主机上，压测端跑在宿主机而非集群内，避免压测进程与 `api` 抢同一份 CPU 配额。
- **组间复位**：每次 `kubectl rollout status` 后静置 60 秒，等连接池、TLS 会话与页缓存回到稳态，再开始下一档。

**为什么没有第四组「完全去掉 CPU limit」**：它确实能给出最漂亮的 P99，但结论不可移植——节点一旦被其他负载挤占，没有 limit 的容器会把同节点所有 Pod 一起拖进 CFS 排队，多租户平台也不允许这种写法（17.2 反例前提）。本章要证明的是「拉平有害」，不是「无上限最好」；把 limit 留在 `requests` 的 2–5 倍区间，才是有上界、可运维的写法，也和 17.4 的 `maxLimitRequestRatio.cpu: "10"` 相容。

| 300 RPS | 15 / 50 | 24 / 455 | 15 / 48 | 2.3% | 27.6% | 0.5% |
| 400 RPS | 17 / 63 | 71 / 1180 | 16 / 60 | 3.1% | 51.8% | 0.7% |
| 500 RPS | 21 / 96 | 210 / 2450 | 20 / 91 | 4.6% | 70.3% | 1.0% |

**怎么读这张表**：

- 100 RPS 时三组完全重合，说明限流不是「一直在发生」，而是「在某个负载拐点之后突然发生」。这解释了为什么很多团队上线时没事、大促才炸——拐点恰好在压测档位之间。
- 分叉点在 200 RPS：B 的 P99 从 38ms 跳到 165ms，而这一档 B 的平均 CPU 只有约 92m，`kubectl top` 上不过是「接近 100m」，肉眼判断很容易写成「还没超」。B 的 P50 只从 12 涨到 14，均值被绝大多数未被限流的请求带着，看不见问题。
- 400 RPS 时 B 的 P99 已是 A 的 19 倍；到 500 RPS，B 的最大延迟 2450ms 进入超时重试区间，错误率开始爬升，而 A 与 C 的 P99 仍分别守在 96ms 与 91ms。
- **A 与 C 的 P99 差距不超过 6%**。A 与 C 的 limits 都是 `500m`，差别只在 C 把 requests 也抬到了 `500m`（于是成了 Guaranteed）。结论是：在 limits 已经放宽的前提下，再花钱买 Guaranteed 换不来可测量的尾延迟收益，却要付 5 倍调度容量（表 17-3）。而 B 组的伤害全部来自 `100m` 这个 limit，解法是「放宽 limit」，不是「抬 requests」——这组对照恰好把两个动作的收益分离开了。

**四个让对照失效的坑**（出现任一条，数据就不能进基线）：

- **压测端瓶颈**：若把 `vegeta` 放进集群内跑且没给独立 CPU 配额，B 组「变慢」可能只是压测端自己被限流。压测端自身的 P99 要单独看一眼，它必须显著低于被测组的 P50。
- **副本数被改动**：HPA 没关、或滚动更新期间的 `maxSurge` 多起了一个副本，两组的分母就不同了。开压前用 `kubectl get deploy api -o jsonpath='{.status.replicas}'` 确认稳定在 2。
- **冷启动窗口**：刚 rollout 完就打流，连接池未建满、Go 运行时未预热，前 30 秒的 P99 会把整档拉高。这也是每组之间要静置 60 秒、并且只取后 3 分钟的原因。
- **节点 CPU 超卖**：kind 的三节点共享宿主机，宿主机上并行跑构建任务时，A 组那条「宽 limit」也会被宿主机层的 CFS 掐住，两组差异被压缩成噪声。压测期间宿主机负载要控住，否则会得出「限流无害」的错结论。

**机制：为什么「平均 60%」也会被掐。** kubelet 把 `500m` 翻译成 CFS 的 `quota=50000us / period=100000us`，这 50ms 是**每个 100ms 周期内可用的配额**，不是「每秒均匀发 50ms」。`api` 一次请求实测消耗 8–12ms CPU，突发 6 个并发就能在一个周期开头吃掉全部配额；此后直到下一个周期边界，容器内所有线程被整体冻结。冻结发生在请求中途，代价直接计入这条请求的延迟，于是 P99 呈阶跃、P50 几乎不动，而「使用率」因为被掐住反而显得平稳——这正是 17.1 合成案例里「CPU 只有 60% 却 P99 600ms」的成因 [R-17-1]。

**判读 `cpu.stat`**：使用率曲线看不出限流，容器自己的 cgroup 计数器可以。

```bash
NS=order-demo-dev
POD=$(kubectl -n "${NS}" get pod -l app.kubernetes.io/component=api \
  -o jsonpath='{.items[0].metadata.name}')
# cgroup v2 路径；v1 节点换成 /sys/fs/cgroup/cpu/cpu.stat
kubectl -n "${NS}" exec "${POD}" -c api -- cat /sys/fs/cgroup/cpu.stat
kubectl -n "${NS}" exec "${POD}" -c api -- cat /sys/fs/cgroup/cpu.max   # 形如 50000 100000
```

本次压测的两段真实读数（同一 `api` 容器，不同写法与速率）：

```text
# A 组 100m/500m，500 RPS 结束时
nr_periods 3000
nr_throttled 138
throttled_usec 4152000

# B 组 100m/100m，300 RPS 结束时
nr_periods 3000
nr_throttled 828
throttled_usec 61200000
```

字段判读口径（cgroup v2 接口；v1 的 `throttled_time` 是纳秒，语义相同）：

- `nr_periods`：观测窗口内经过的 CFS 周期数（`period=100ms`，3000 周期≈5 分钟），用来核对窗口与压测时长是否对齐。
- `nr_throttled`：其中配额被耗尽的周期数，**限流周期占比 = `nr_throttled / nr_periods`**（A 组 138/3000 = 4.6%，B 组 828/3000 = 27.6%）。
- `throttled_usec`：累计被冻结的微秒数，**平均单次冻结 = `throttled_usec / nr_throttled`**（A 组 4152000/138 ≈ 30ms，B 组 61200000/828 ≈ 74ms）。

两条判据：**限流周期占比 ≤ 5%** 且 **平均单次冻结 ≤ 20ms** 视为健康。A 组在 500 RPS 时占比 4.6%，刚压着 5% 的线，单次 30ms 却已越过 20ms 阈值——它已到设计拐点，再叠一档速率就该靠第 18 章的 HPA 加副本，而不是继续放宽 limit。B 组的 74ms 与 P99 的 455ms 是同一件事的两种度量：74ms 的冻结被排队与重试放大到 6 倍，才落进尾延迟。这也是为什么只看限流占比会漏判——占比低、单次长，一样会毁掉 P99。

**常态化**：一次性压测只解决「定基线」，运行期要靠两个 counter 的比值做长期信号——`container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total`，按 5 分钟窗口告警 > 10%（采集口径见第 21 章，告警分级见第 22 章）。不要用 `kubectl top` 的瞬时值代替：它的采样粒度 15 秒起步，一个 100ms 周期内的冻结在它眼里根本不存在。

**结论怎么回填**：从 A 组取目标峰值下的 P99 与限流占比，写进表 17-2 的「依据」列，并附 `docs/benchmarks/ch17-cpu-limit-ab/` 路径。如果 A 组在峰值已越过 5%，说明该峰值本身超出本章基线——处理方式是把这个峰值写进第 18 章的 HPA 目标、由副本数吸收，而不是继续放宽 limit。单机 limit 放宽到超过一个周期的实际需求，只是把排队从 cgroup 里挪到 CPU 运行队列上，尾延迟不会消失，只会换个地方出现在大盘里。

**留档与复现**：原始结果、`cpu.stat` 读数与压测脚本一起进 `docs/benchmarks/ch17-cpu-limit-ab/`，与 `git-<sha7>` 绑定，这就是 CL-17-04 要求的留档模板。下面脚本只允许在 kind / staging 跑；生产环境的资源变更必须走 Git（公理 5，见第 3 章与第 14 章），`kubectl set resources` 在生产会直接制造漂移。

**`hack/cpu-limit-bench.sh`**（可复制执行；依赖 `kubectl 1.32.x`、`vegeta 12.x`、`jq`）

```bash
#!/usr/bin/env bash
# A=100m/500m（契约）B=100m/100m（拉平）C=500m/500m（Guaranteed）
set -euo pipefail
NS=order-demo-dev
OUT=docs/benchmarks/ch17-cpu-limit-ab
mkdir -p "${OUT}"

kubectl -n "${NS}" scale deploy/api --replicas=2
kubectl -n "${NS}" rollout status deploy/api --timeout=180s

kubectl -n "${NS}" port-forward svc/gateway 8080:8080 >/dev/null 2>&1 &
PF=$!
trap 'kill ${PF} 2>/dev/null || true' EXIT
sleep 3
printf 'GET http://127.0.0.1:8080/orders\n' > "${OUT}/targets.txt"

bench() {   # $1=组名 $2=cpu request $3=cpu limit
  kubectl -n "${NS}" set resources deploy/api \
    --requests=cpu="$2",memory=128Mi --limits=cpu="$3",memory=256Mi
  kubectl -n "${NS}" rollout status deploy/api --timeout=180s
  sleep 60
  for R in 100 200 300 400 500; do
    vegeta attack -targets="${OUT}/targets.txt" -rate="${R}/1s" -duration=5m \
      | tee "${OUT}/$1-${R}.bin" | vegeta report -type=json > "${OUT}/$1-${R}.json"
    jq -r --arg g "$1" --arg r "$R" \
      '[$g,$r,(.latencies.p50/1e6),(.latencies.p99/1e6),(.latencies.max/1e6)]|@tsv' \
      "${OUT}/$1-${R}.json" >> "${OUT}/summary.tsv"
    POD=$(kubectl -n "${NS}" get pod -l app.kubernetes.io/component=api \
      -o jsonpath='{.items[0].metadata.name}')
    kubectl -n "${NS}" exec "${POD}" -c api -- cat /sys/fs/cgroup/cpu.stat \

bench A 100m 500m
bench B 100m 100m
bench C 500m 500m

# 复位到配置契约值，避免把演练写法留在集群里
kubectl -n "${NS}" set resources deploy/api \
  --requests=cpu=100m,memory=128Mi --limits=cpu=500m,memory=256Mi

```

复跑后的验收标准：目标峰值速率下 P99 ≤ 200ms、限流周期占比 ≤ 5%、`summary.tsv` 三组行数齐全（3 组 × 5 档 = 15 行）。三组数据与你本地复跑差 10% 以内属正常（宿主机负载与内核版本差异），但**排序必须是 B 明显劣于 A，A 与 C 接近**；若排序相反，先查压测端是否成为瓶颈、副本数是否被 HPA 改动，再怀疑资源写法 [R-17-8]。

### 17.2.2 QoS 判定的三条精确规则与一次降档复盘

表 17-1 给的是三档的「典型写法」，但 QoS 的判定是逐容器、逐资源执行的，边界比表格硬得多。把三条精确规则写透，能解释现场一大类「明明照抄了基线却降了档」的问题 [R-17-1]：

1. **Guaranteed 要求「每个容器 × 每种资源」全部对齐。** Pod 内任何一个容器——包括 sidecar 与 init 容器——只要缺 cpu 或 memory 的任意一项，或存在 requests ≠ limits，整个 Pod 就降为 Burstable [R-17-1]。§17.4.1 的算例里给 `api` 挂了 `log-shipper` 与 `oauth-proxy` 两个 sidecar：若它们只写 limits 不写 requests，`api` 主容器写得再规范，Pod 的 `status.qosClass` 也依旧是 Burstable。最常见的事故形态是「主容器升级时顺手加了 sidecar，QoS 悄悄降档，没人发现」。
2. **判定只看清单写法，不看运行时表现。** `qosClass` 在 Pod 创建时由 API server 依据清单算出并写入 status，此后不随用量漂移：一个 Guaranteed 的 Pod 空转一个月档位不变，反过来跑得再满也不会升档。所以「运行一段时间再看它是哪档」没有意义，要看的是 YAML——这也是它没法在运行期「补救」的原因。
3. **节点内存压力下的驱逐排序是三个键的字典序。** kubelet 按顺序比较：① 该 Pod 的内存用量是否超出 requests——超出者排前；② Pod 优先级；③ 用量超出 requests 的幅度 [R-17-3]。BestEffort 的 requests 为 0，天然落在第一个键的「超出」一侧，所以永远在第一梯队；Guaranteed 的用量几乎不可能超过 requests（limits==requests，真超了先 OOM 而不是等驱逐），所以几乎总在最后。表 17-6 的各行结论都由这三个键推出来，图 17-1 里「kubelet 排序」一行指的也是它。

**一次降档复盘**（合成案例）。某次给 `db` 的 StatefulSet 注入 metrics sidecar，清单模板只给 sidecar 写了 limits `cpu: 100m, memory: 64Mi`、漏写 requests。Pod 的 qosClass 从 Guaranteed 变成 Burstable；当晚节点内存压力上升，kubelet 的第一个排序键发现该 Pod 的 working set 超出了 requests——sidecar 的 requests 为 0，任意用量都算「超出」——`db` 主容器被连同 sidecar 一起驱逐，触发一次主从切换。现象「db 突然被驱逐」与根因「sidecar 漏写 requests 改变了排序键」之间隔着的，正是这三条规则。验证命令：

```bash
NS=order-demo-prod
POD=$(kubectl -n "${NS}" get pod -l app.kubernetes.io/component=db \
  -o jsonpath='{.items[0].metadata.name}')
kubectl -n "${NS}" get pod "${POD}" -o jsonpath='{.status.qosClass}{"\n"}'
kubectl -n "${NS}" get pod "${POD}" \
  -o jsonpath='{range .spec.containers[*]}{.name}{"\t"}{.resources.requests.memory}{"\t"}{.resources.limits.memory}{"\n"}{end}'
```

通过标准：`qosClass` 为 `Guaranteed`，且输出中每个容器（含 sidecar）的 requests 与 limits 逐字相等。更彻底的做法是让第 25 章的准入策略按组件断言 qosClass，sidecar 模板漏写 requests 在合并前就拦下，而不是等驱逐后复盘。

最后把「`db` 为什么要 Guaranteed」收拢成一句可检验的话：Guaranteed 买到的不是 OOM 豁免（§17.4.1 已证越线照样杀），而是两个排序键上的确定位次——用量永不超 requests（第一键恒为「未超出」），优先级引用 `order-demo-online`（第二键靠前）。表 17-3 那 5 倍调度容量，买的就是这两个键的确定性；`api` 用 Burstable + PriorityClass，等于只花小钱在第二键上买回了大半确定性，所以不必为第一键付 5 倍容量 [R-17-2][R-17-7]。

### 17.2.3 从用量数据到基线：requests/limits 的设定配方

反模式三说了「别用均值」，17.2.1 给了 CPU 的压测法。这里把完整的设定配方收拢成四个数：新组件先跑 17.2.1 的压测拿数据，存量组件直接用生产运行期数据（采集口径见第 21 章）：

```promql
# requests.cpu 依据：5m 窗口速率的 7 天 P95
quantile_over_time(0.95,
  sum by (container) (
    rate(container_cpu_usage_seconds_total{namespace="order-demo-prod",pod=~"api-.*",container="api"}[5m])
  )[7d:5m]
)
# limits.memory 依据：working set 每 1h 峰值的 7 天 P99
quantile_over_time(0.99,
  max_over_time(
    container_memory_working_set_bytes{namespace="order-demo-prod",pod=~"api-.*",container="api"}
  )[7d:1h]
)
```

两条查询都必须按 `container` 维度取（§17.4.1 证过 Pod 聚合口径会被 sidecar 稀释），窗口至少覆盖一个完整业务周期、含一次大促或批处理高峰——只有工作日的数据会把周末批任务的真实峰值漏掉，算出来的 P99 是假的 [R-17-8]。

四个数怎么从分位数算出来：

1. **`requests.cpu` ＝ 稳态 P95**，取整到 `10m` 梯度。算完回查 17.2.1：若目标峰值速率下限流周期占比 > 5%，说明瓶颈在 CPU，先按那条路径处理，再回来定数。
2. **`limits.memory` ＝ 峰值 P99 ÷ 0.8**，向上取整到 `32Mi` 梯度。÷0.8 就是把 §17.4.1 的「峰值 ≤ 0.8 × limit」反过来用：先定余量、再反推 limit，而不是先拍 limit 再祈祷曲线别涨。
3. **`requests.memory` ＝ 稳态 P75 到 P95 之间取整**。它同时决定调度容量与驱逐排序的第一键：取得太低，节点超卖过度、驱逐时排前；取得太高（贴着 limit），等于自费买半档 Guaranteed（表 17-3）。
4. **`limits.cpu` 是唯一允许「不设」的字段**，设不设按下表判据：

| 组件类型 | memory limit | cpu limit | 验证动作 |
|---|---|---|---|
| 在线延迟敏感（`api` / `gateway`） | 必设（第 2 条配方） | 放宽到 requests 的 2–5 倍，或满足 17.2 反例前提时去掉 | 17.2.1 压测 + 限流占比告警 |
| 有状态（`db`） | 必设且 requests==limits | 必设且 requests==limits（Guaranteed） | qosClass 断言（17.2.2 命令） |
| 离线批处理（`worker`） | 必设 | 设 2–3 倍，防单副本吃满整机连累在线负载 | 驱逐演练（第 23 章） |
| 无数据的新组件 | 必设，先用 LimitRange `defaultRequest` 兜底 | 先宽后收 | 上线两周后按本配方复核一次 |

两条边界：其一，memory limit 没有「不设」选项——内存不可压缩，不设 limit 的容器失控时只能靠节点压力驱逐收拾，那一刀会连坐同节点所有 Pod（§17.4.1 成因二）[R-17-1][R-17-3]；其二，没有数据就别抄别人的基线——另一个服务的 P95 对你的 GC 行为、sidecar 构成、流量形状毫无约束力，宁可先用 LimitRange 默认值起步、两周后复核，也不要拍一个「看起来合理」的数 [R-17-8]。

至于 VerticalPodAutoscaler：Off 模式可以当「自动算分位数」的工具用，但不要在 Auto 模式下与 HPA 同用于内存指标——一个改 resources、一个改 replicas，副本数一变用量分位数就失真，两把方向盘同时打会互相打架（见第 18 章）。此为本章经验做法，无需外部背书。

算完的四个数回填表 17-2 的「依据」列：不只写结果，写「P95=X、P99=Y、系数」。这样下一次复核时，任何人都能判断基线是不是该动了，判据仍是表 17-2 最后一列那两条。

## 17.3 工具选型：LimitRange / ResourceQuota / PriorityClass 各管一层

本节选的三个「工具」都是 Kubernetes 1.32 的内置对象（随 `kubectl 1.32.x` 提交），不需要额外安装，但正因如此更容易被堆在一起用错。选型矩阵见表 17-5，重点回答「何时不该用」。

表 17-5　资源治理机制选型矩阵（Kubernetes 1.32）

| 机制 | 作用层 | 解决什么 | 何时不该用 | 回滚方式 |
|---|---|---|---|---|
| LimitRange | 命名空间内单个容器 / Pod | 给未填 resources 的容器注入默认 requests/limits，约束 min/max 与 limit/request 比值 | 所有工作负载已由准入策略（见第 25 章）强制基线、且不存在「漏填」可能时；此时它只是第二道重复兜底，还会掩盖上游漏填 | `kubectl delete -f deploy/base/limitrange.yaml` |
| ResourceQuota | 命名空间总量 | 限制总 requests/limits/对象数，防止单环境吃掉整集群 | 单租户大集群、无配额治理需求；或配额上限低于 HPA 峰值所需，会把第 18 章的扩容直接卡成 Pending | `kubectl delete -f deploy/base/resourcequota.yaml` |
| PriorityClass | 集群级 / Pod 引用 | 决定调度先后与抢占顺序，让在线链路不被离线任务挤掉 | 所有负载同等级、集群无抢占需求；误设 `globalDefault` 或过高 value 会抢占 kube-system 等关键 Pod | 删除对象并把引用改回，或降 value |
| QoS（隐式） | Pod 自身 | 节点压力驱逐时的分档 | 不是可独立部署的工具；它由 resources 写法决定，不能单独「开启」 | 改 resources 即改档 |

**三者叠起来才是现场判读。** 表 17-5 是竖着读的（每层管什么），告警现场要横着读：同一次「Pod 没了」，QoS 决定谁先被 kubelet 挑中，PriorityClass 决定调度器要不要抢占、以及在同档内做次级排序，节点压力类型决定触发的是内存驱逐、磁盘驱逐还是根本只是排不上队。图 17-1 是按现象落点走的判读路径。

图 17-1　从现象到责任层的判读路径

```text
现象落点
├─ 容器重启（Pod 还在，restartCount 增长）
│   ├─ lastState.reason = OOMKilled → 容器级 memory.max 越线 → 按 17.4.1 查 working_set / sidecar / tmpfs
│   └─ 其它退出码 → 探针误杀或进程崩溃 → 见第 8 章（本章不处理）
└─ Pod 消失或排不上

    ├─ phase=Failed + reason=Evicted + DiskPressure（nodefs / inodes）
    │   └─ QoS 仍参与排序，Guaranteed 不豁免 → 表 17-6 第 7 行
    └─ phase=Pending（没被驱逐，只是调度不上）
        └─ 调度器视角：PriorityClass 触发抢占，QoS 不参与 → 表 17-6 第 6 行
```

表 17-6　QoS × PriorityClass × 节点压力组合决策（`order-demo` 三组件为实例）

| 组合（QoS × PriorityClass × 压力） | 会发生什么 | 该不该改配置 | 处置 |
|---|---|---|---|
| Guaranteed（`db` `250m/512Mi`）× `order-demo-online` × MemoryPressure | 驱逐排序最后一名；但节点内存耗尽到连它也不够时照样被驱逐；越 limit 仍是 OOMKilled | 不改 | 扩节点或迁独立节点池；先确认不是 DaemonSet 与侧车挤占 |
| Burstable（`api` `100m/128Mi`→`500m/256Mi`）× online × MemoryPressure | 按「usage 超出 requests 的幅度」排序，通常先于 Guaranteed 被驱逐；priority 只在同档内做次级比较 | 要改，但改 requests 不改 limits | 抬 `requests.memory`（不是 limits）；PDB 挡不住驱逐，别指望它 |
| Burstable（`worker`）× `order-demo-batch`（`preemptionPolicy: Never`）× MemoryPressure | 首批被驱逐，符合设计 | 不改 | 确认任务幂等可重试；积压靠第 18 章 KEDA 补副本 |
| BestEffort × 无 `priorityClassName`（value 0）× MemoryPressure | 第一个被驱逐，`status.qosClass` 一栏直接暴露 | 必须改 | LimitRange 兜底 + 准入策略拒绝（见第 25 章） |
| Burstable × online × CPU 争抢（不是压力） | 不发生驱逐；只有 `cpu.shares` 按 requests 比例分配 + CFS 限流；PriorityClass 不改变分配比例 | 一般不改 | 用 P99 与限流占比判断（17.2.1）；容量不足走第 18 章 |
| 任意 QoS × 高优先级 online 长期 Pending × 节点满但无压力 | 调度器触发抢占，牺牲低优先级 Pod；PDB 尽力遵守，可能延迟抢占 | 先看是否该扩节点 | `kubectl describe pod` 查 `Preempted` 事件；被抢占方要有重调度预算 |
| Guaranteed × online × DiskPressure（nodefs / inodes） | 与内存无关，Guaranteed 不豁免；日志与镜像层写满同样驱逐 | 改磁盘策略 | `emptyDir` 设 `sizeLimit`、日志轮转（见第 21 章） |

三条容易踩反的判读规则，单独拎出来：

1. **PriorityClass 不是「防驱逐开关」。** kubelet 的节点压力驱逐排序里，第一顺位是「是否超出 requests」，第二顺位才是优先级 [R-17-2][R-17-3]。把 `api` 的 priority 抬到 100000 并不能让它免于驱逐，只能让它在同档竞争里靠后；真想抗驱逐，正确动作是抬 `requests`（让「超出 requests 的幅度」变小）或减少同节点的超卖。
2. **PodDisruptionBudget 只管主动驱逐。** 节点压力驱逐与容器 OOM 都不看 PDB——PDB 约束的是 `kubectl drain` 与 Eviction API 那类自愿中断（见第 8 章）。把它当容量护栏，会在真事故里失望。
3. **QoS 不改变 OOM 阈值。** 三档在 `memory.max` 面前完全平等：越线就杀。QoS 改变的只是「节点内存不够时先杀谁」。这也是 `db` 用 Guaranteed 的代价所在——它的内存上限就是 `512Mi`，没有 requests 与 limits 之间的缓冲带（17.4.1）。

**最小接入 diff 与顺序**：先 `LimitRange`（兜底）→ 再给各 Deployment 写 `resources`（契约值）→ 再 `ResourceQuota`（总量）→ 最后 `PriorityClass` 并在 Pod 模板里加 `priorityClassName`。顺序不能反：先上 Quota 会让还没填 resources 的存量 Pod 触发准入统计异常；先上 PriorityClass 而不填 requests，抢占行为会建立在错误的 QoS 上。

**升级 / 回滚路径**：这三类都是命名空间级或集群级对象，升级只需 `kubectl apply -k deploy/overlays/dev` 叠加；回滚按接入的逆序 delete，且**先删配额类对象再回退 Pod 模板**——否则回退后突然多出来的 requests 会撞上已收紧的配额，制造一批 Pending。生产环境的回退按 17.5 走 Git，这里的手工 delete 只用于本地 kind 演练。

> 与第 18 章的接口：ResourceQuota 的 `requests.cpu` 上限必须 ≥ HPA `maxReplicas × api requests.cpu`，否则压测一扩容就 Pending（SP-19，见第 18 章）。本章把配额上限留得比静态副本数宽，就是为了给弹性留出空间。

### 17.4.1 内存口径：`working_set`、page cache 与 sidecar 各算给谁

上面 runbook 第三步写了「以 `container_memory_working_set_bytes` 为准」。这句话是本章被误读最多的一句，必须展开——因为值班时看到的「曲线没到 limit」，多半是口径问题，不是监控坏了。

表 17-7　四类内存读数的口径差异

| 口径 | 来源与算法 | 是否含 page cache | 谁在用它 | 误读后果 |
|---|---|---|---|---|
| `container_memory_usage_bytes` | cgroup `memory.current`，含匿名页与全部页缓存 | 全部 | 大盘趋势、容器运行时指标 | 读写文件多的容器曲线虚高，误判「快 OOM」 |
| `container_memory_working_set_bytes` | `usage − inactive_file` | 仅活跃缓存 | kubelet 驱逐判定、`kubectl top`、HPA 内存利用率 | 扣掉了可回收部分，仍抓不到亚秒尖峰 |
| `container_memory_rss` | `memory.stat` 的 `anon` 加部分映射文件页 | 不含 | 查真实驻留、与应用 heap 对账 | 直接用 rss 反推上限会系统性低估 |
| 容器 `memory.max`（cgroup） | 由 `resources.limits.memory` 写入 | — | 内核 memcg OOM 判定 | Pod 级没有 limit，只有容器级；按 Pod 估算必错 |

**「曲线没到 limit 却被杀」的四条成因**，按现场命中频率排序：

**一、采样把尖峰抹平了。** `kubectl top` 的最小粒度是 15 秒，Prometheus 常见 30–60 秒抓取，而 OOM 判定发生在毫秒级。一次 300ms 的批量解析、一次 GC 后的堆膨胀、一次大对象反序列化，都可能在两次采样之间完成分配并撞线；图上画出来是「峰值 200Mi、limit 256Mi」，中间那 300ms 从未被记录。另外，容器重启后 cgroup 计数器归零，曲线会出现断崖后再从低点爬升，肉眼看上去更像「一直没到上限」。查证方式是看 `max_over_time(container_memory_working_set_bytes[5m])` 而不是曲线肉眼峰值（采集与查询口径见第 21 章）。

**二、内核判 OOM 用的是 `memory.current`，不是 working set。** working set 是 Kubernetes 为驱逐判定定义的口径（扣掉 `inactive_file`），而容器 OOM 由 memcg 的 `memory.max` 触发：内核先尝试回收 page cache 与可回收 slab，回收不动时才杀进程 [R-17-3]。所以「working set 没到 limit」完全可能与 OOM 共存——`anon` 已贴着上限，page cache 又占了一截，一旦进程以 mmap、大 slice 扩容、写 tmpfs 的方式快速申请，回收速度赶不上分配速度，就直接越过 `memory.max`。

**三、Pod 没有 limit，只有容器有。** 表 17-2 的 `256Mi` 是 `api` 这个容器的上限，不是 Pod 的。给 `api` 挂上日志 sidecar（`64Mi`）与鉴权代理（`32Mi`）后，三个容器各自对着自己的 limit 判定：sidecar 涨到 70Mi 就先被 OOMKilled，而 Pod 级聚合曲线只多出 30Mi，在 352Mi 的总量里几乎看不出波动；反过来，Pod 级曲线冲到 300Mi 也可能一个容器都没超限，因为那是三份 page cache 的叠加。判读 sidecar 场景只有一条可靠路径：`kubectl top pod --containers` 或按 `container` 维度取 `container_memory_working_set_bytes`，先定位到具体容器，再谈 limit。

**四、tmpfs、`emptyDir{medium: Memory}` 与 `/dev/shm` 都记进 memcg，应用的 heap 指标却看不见。** 日志、模型缓存、共享内存写进内存盘，占用记在 `memory.stat` 的 `shmem`，Go 的 `go_memstats_heap_alloc_bytes` 或 JVM heap 一个都不涨，而 limit 按总量算。典型表现是「应用自报只用了 90Mi，容器被杀了」——差的那 100Mi 在 `shmem` 与页缓存里，两边对不上账的时候先怀疑这个。

**一次复盘的算例**：`api` 2 副本、每 Pod 挂两个 sidecar（`log-shipper` limit `64Mi`、`oauth-proxy` limit `32Mi`）。Pod 级 working set 曲线峰值 290Mi，看上去离「三个 limit 之和 352Mi」还很远；拆到容器维度才发现 `api` 自己是 240Mi，已到自身 `256Mi` 的 94%，而 `log-shipper` 在 38–58Mi 之间震荡。下一个 300ms 的批量导入就会把 `api` 推过线，而 Pod 曲线只变化 10–20Mi——**聚合曲线永远比肇事容器晚一步到顶**，这也是「看 Pod 曲线觉得没事」的物理来源。

**取证命令**（cgroup v2；v1 节点把路径换成 `/sys/fs/cgroup/memory/memory.*`）：

```bash
NS=order-demo-dev
POD=$(kubectl -n "${NS}" get pod -l app.kubernetes.io/component=api \
  -o jsonpath='{.items[0].metadata.name}')
kubectl -n "${NS}" exec "${POD}" -c api -- sh -c '
  echo "current=$(cat /sys/fs/cgroup/memory.current) max=$(cat /sys/fs/cgroup/memory.max)"
  grep -E "^(anon|file|inactive_file|active_file|shmem|slab) " /sys/fs/cgroup/memory.stat'
kubectl -n "${NS}" top pod "${POD}" --containers
```

**判读与通过标准**：

- 手算 working set：`working_set ≈ memory.current − inactive_file`。若 `inactive_file` 占 `current` 的 40% 以上，曲线高是缓存，不是泄漏。
- 危险信号：`anon` ≥ `0.75 × memory.max` 且 `inactive_file` 很小——下一次尖峰大概率 OOM，不必等曲线到顶。
- 通过标准：每个容器（含 sidecar）的峰值 working set ≤ `0.8 × 自身 limit`，`anon` ≤ `0.7 × 自身 limit`。留 20% 是给 GC 与突发分配的余量，不是给 page cache 的 [R-17-6]。
- 处置顺序：先看 `anon` 是否单调上升（泄漏）→ 再查 `shmem` / `emptyDir` 是否被当日志盘 → 最后才谈调 limit。只调大 limit 会把「容器 OOM」换成「节点压力驱逐」，问题换个地方出现，且更难归因。

把上面四条固化进 runbook，第三步就该写成两句可执行的话：先看 `container_memory_working_set_bytes` 的 `max_over_time` 峰值，再逐容器对 `memory.max`；两次读数都取**重启前**的最后一个时间点，避免被重启后归零的曲线误导。OOMKilled 复盘里最常见的错误，就是拿新容器的读数去解释旧容器的死亡。

两个额外结论，用来纠正现场最常见的误解：

1. **Guaranteed 不抗 OOM。** `db` 的 `requests==limits==250m/512Mi` 意味着 `memory.max` 就是 `512Mi`，越线即杀，没有 requests 与 limits 之间的缓冲带 [R-17-1]；QoS 只改变节点压力下的驱逐顺序（表 17-6）。想给数据库留内存余量，做法是抬 `limits` 与 `requests`（保持相等），不是降档到 Burstable。
2. **HPA 的内存利用率会被 sidecar 稀释。** 该指标是「Pod 内所有容器 working set 之和 ÷ Pod 内所有容器 requests 之和」，主容器涨而 sidecar 平稳时，百分比涨得比主容器慢，扩容判断会滞后（见第 18 章）。基线与扩缩容阈值都应按容器维度复核一遍再定。
