## 17.1 问题与反模式：CPU 没跑满却变慢，内存没报警却被杀

**合成案例**（本书统一采用虚构合成场景，不指向任何真实事故）。大促前一周，团队做了一轮压测，随后有人为了让单节点「塞得下更多副本」把 `api` 的 `requests` 往下调，又为了「账好算」把 CPU limit 设成和 requests 一样。上线后的现象很分裂：白天 QPS 上来，`api` 的 P99 从 80ms 涨到 600ms，但 `kubectl top pod` 显示 CPU 只有 60%，监控大盘上没有任何一条「CPU 打满」的告警；到了夜里偶发 502，翻容器日志只看到进程被重启，`kubectl describe pod` 里 `Last State: Terminated`，`Reason: OOMKilled`，退出码 137，可内存曲线峰值离 limit 还有一截。值班同学按「内存没超」这个前提查了两个小时，最后才发现被杀的是容器工作集，而节点当时正处在内存压力下 [R-17-1][R-17-3]。

这类故障之所以难查，是因为它把三件不同的事混成了一件：**调度依据**、**运行时上限**和**驱逐顺序**。CPU 与内存是两类性质完全不同的资源——CPU 是可压缩资源，超过 limit 之后内核用 CFS quota 把进程「掐住」，表现为排队与尾延迟抖动，不会杀进程；内存是不可压缩资源，超过 limit 直接由内核 OOM killer 杀掉容器，不可回退 [R-17-1]。把这两类后果当成一回事，就会得出「CPU 没打满所以没问题、内存没超所以不该被杀」的错误推理。运行时稳定性是容器平台最普遍的运维课题之一，行业调查长期把资源与容量问题排在前列，这也是本章把「能按 runbook 定位一次 OOMKilled」写成可验证动作的原因 [R-17-9]。

三个高频反模式，按「现象 → 根因 → 本章替代做法」拆开：

**反模式一：不填 requests，或把 requests 当「保底配额」随手填。** 现象是调度器挑节点时没有依据、同一批 Pod 忽而挤在一台忽而 Pending；一旦节点内存吃紧，最先被驱逐的总是这批 Pod。根因是 requests 同时决定调度 placement 与 QoS 等级，什么都不填的 Pod 会落到 BestEffort，驱逐优先级最高 [R-17-1][R-17-3]。本章的替代做法是**全工作负载强制基线**：每个容器都写 requests，命名空间再用 LimitRange 给遗漏者兜底，二者叠加后 BestEffort 不再出现（见 17.3、17.4）。

**反模式二：把 CPU limit 设得和 requests 一样「好算」。** 现象就是合成案例里的 P99 抖动：请求在 cgroup 里排队，CPU 使用率曲线反而很平，因为被限流的 CPU 时间根本没被计入「使用」。根因是把「可预测」错当成「稳定」——确定性配额换来的是尾延迟代价 [R-17-1]。本章的替代做法是在线服务只保留 CPU requests 作为调度依据，放宽或去掉 CPU limit，容量不足时靠第 18 章的 HPA 加副本而不是靠限流硬扛。这条取舍是本章「本书观点」，17.2 会给完整论证与反例。

**反模式三：只看「平均使用率」定基线。** 现象是压测报告写着「平均 CPU 35%、平均内存 90Mi」，按这个值设的基线一到大促就出事。根因是平均值把峰值削平了：GC 停顿、批量任务、冷启动这些瞬时尖峰在均值里几乎看不见 [R-17-8]。本章的替代做法是用分位数（P95/P99）与压测曲线定基线，并按 USE 方法分别看利用率、饱和度与错误，而不是只盯一个均值 [R-17-8]；过载时系统行为由最弱一环决定，基线必须给这一环留突发余量 [R-17-6]。

> **一个刻意的边界**：本章只处理「一个 Pod 该申请多少、上限多少、被杀/被驱逐时怎么判读」。副本数怎么随负载变化是第 18 章，故障注入与速查表是第 23 章，指标怎么采集是第 21 章。先把单 Pod 的资源语义讲透，才能把「抖动」和「驱逐」这两类现象分别归因到正确的层。

## 17.2 范式与决策树：requests 买调度、limits 买上限、QoS 买驱逐顺序

先把三个容易混用的概念一次说清。

**requests** 是给调度器的「占地声明」：调度器按各容器 requests 之和挑选有足够可分配余量的节点，它同时是 QoS 分档与 HPA 百分比指标的分母。它不是「运行时最低保证」的同义词——CPU request 会被换算成 cgroup 的 `cpu.shares` 权重，只在争抢时决定分配比例，空闲时别的工作负载仍可用满 [R-17-1]。**limits** 是硬上限：CPU 超限被 CFS quota 限流，内存超限触发 OOMKilled [R-17-1]。二者一个管「放得下吗」，一个管「最多能用多少」。

**QoS 三档**是 Kubernetes 依据 Pod 里各容器 requests/limits 的写法自动判定的驱逐优先级，不需要单独创建对象。判定规则与后果见表 17-1。

表 17-1　QoS 三档判定与驱逐顺序

| 档位 | 判定规则（Pod 内每个容器） | 典型写法 | 节点内存压力下的驱逐顺序 | 适合谁 |
|---|---|---|---|---|
| Guaranteed | 每种资源都设了 requests **且** limits，且二者相等 | `requests==limits`（cpu 与 memory 都满足） | 最后 | `db` 这类不可丢状态、要求最稳的组件 |
| Burstable | 至少有一个 requests 或 limits，但不满足 Guaranteed | `requests < limits` | 中间 | 绝大多数在线服务，含本章 `api` |
| BestEffort | 任何资源都没设 requests/limits | 什么都不写 | 最先 | 不允许用于生产工作负载 |

`api` 按配置契约写的是 requests `cpu: 100m, memory: 128Mi`、limits `cpu: 500m, memory: 256Mi`，requests 严格小于 limits，因此 QoS 是 **Burstable**，不是 Guaranteed [R-17-1]。这不是疏漏，而是刻意的容量取舍：若把它抬成 Guaranteed（`requests==limits`），调度器就要按 500m/256Mi 为每个副本预留，同样的节点能放的副本数会明显下降。想要 Guaranteed 的稳定性，代价是调度容量，二者不可兼得 [R-17-7]。

**PriorityClass** 解决的是另一层问题：QoS 只在同节点内存压力驱逐时排序，而 PriorityClass 决定调度队列里的先后与抢占行为——高优先级 Pod 可以抢占低优先级 Pod 的节点位置 [R-17-2]。三者作用在不同层次，不能互相替代：LimitRange 给默认值、ResourceQuota 给命名空间总量、PriorityClass 给驱逐与抢占顺序 [R-17-2][R-17-4][R-17-5]。

表 17-2　`order-demo` 资源基线（仅 `api` 一行为冻结契约值，其余为本章示例基线，可按压测调整）

| 组件 | requests | limits | QoS | 依据 | 何时调整 |
|---|---|---|---|---|---|
| `api` | `cpu: 100m, memory: 128Mi` | `cpu: 500m, memory: 256Mi` | Burstable | 分位数压测曲线 + 突发余量 | P99 逼近 limit、或 GC 尖峰被削平 |
| `gateway` | `cpu: 50m, memory: 64Mi` | `cpu: 500m, memory: 128Mi` | Burstable | 入口转发，CPU 与连接数相关 | 连接数翻倍、TLS 终止下沉到入口 |
| `db` | `cpu: 250m, memory: 512Mi` | `cpu: 250m, memory: 512Mi` | Guaranteed | 有状态、不可丢 | 数据集增长、连接数上升 |
| `worker` | `cpu: 50m, memory: 64Mi` | `cpu: 300m, memory: 192Mi` | Burstable | 异步任务，允许被抢占 | 队列积压时长变长（见第 18 章 KEDA） |

> 表 17-2 里 `db` 用 `requests==limits` 换 Guaranteed，但这也意味着它一旦触到内存 limit 就直接 OOMKilled，没有 Burstable 的缓冲。是否给数据库设内存 limit 本身就是一个决策，第 16 章的有状态组件章节会展开；本章只用它演示「QoS 是写法的副产品」。

**决策树**（判断一个工作负载的资源该怎么填）：

```
这个 Pod 的每个容器都写了 requests？   否 → 补 requests；命名空间加 LimitRange 兜底（17.4）
        │ 是
组件是在线、对尾延迟敏感？             是 → 只保留 CPU requests，放宽/去掉 CPU limit（本书观点）
        │ 否（离线 / 批处理）
内存是否需要硬上限？                   是 → 设 memory limit，并按 17.5 的 OOM 演练验证
        │ 否
是否要拿到 Guaranteed？                 是 → 所有容器所有资源 requests==limits（代价：调度容量）
        │ 否 → Burstable，用 PriorityClass 区分在线/离线驱逐顺序（17.4）
→ 用分位数压测曲线复核，把 P99 与 limit 之间留出突发余量
```

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：把 CPU limit 设得和 requests 一样「好算」，是以牺牲在线服务的尾延迟换取账面上的可预测性；对延迟敏感的工作负载，这笔交易通常不划算。
>
> **论证**：CPU 是可压缩资源，超限的后果是 CFS quota 限流而非报错。限流期间进程在 cgroup 里排队，`kubectl top` 看到的「CPU 只有 60%」是被掐住之后的读数，排队时间却已经计入 P99。一次压测对照很容易复现：同一 QPS 下，去掉 CPU limit 的副本 P99 明显低于「requests==limits」的副本，而两者平均 CPU 使用率几乎相同；差值全部落在尾部分布里。多出来的容量不确定性，应该用第 18 章 HPA 的副本弹性去吸收，而不是用单机限流去压平。
>
> **反例与适用前提**：这不等于「任何场景都不设 CPU limit」。离线批处理、多租户强隔离、按 CPU 时长计费的平台，需要确定性配额来防止单个租户吃满整机，此时 CPU limit 合理且必要；托管节点若内核未开启 `cpuCfsQuota` 关闭选项、或合规要求所有容器都有硬上限，也应保留。本结论的前提是「在线延迟敏感 + 已有 HPA 兜底 + 节点有超卖余量」；三者缺一，请先补齐再谈放宽。

## 17.3 工具选型：LimitRange / ResourceQuota / PriorityClass 各管一层

本节选的三个「工具」都是 Kubernetes 1.32 的内置对象（随 `kubectl 1.32.x` 提交），不需要额外安装，但正因如此更容易被堆在一起用错。选型矩阵见表 17-3，重点回答「何时不该用」。

表 17-3　资源治理机制选型矩阵（Kubernetes 1.32）

| 机制 | 作用层 | 解决什么 | 何时不该用 | 回滚方式 |
|---|---|---|---|---|
| LimitRange | 命名空间内单个容器 / Pod | 给未填 resources 的容器注入默认 requests/limits，约束 min/max 与 limit/request 比值 | 所有工作负载已由准入策略（见第 25 章）强制基线、且不存在「漏填」可能时；此时它只是第二道重复兜底，还会掩盖上游漏填 | `kubectl delete -f deploy/base/limitrange.yaml` |
| ResourceQuota | 命名空间总量 | 限制总 requests/limits/对象数，防止单环境吃掉整集群 | 单租户大集群、无配额治理需求；或配额上限低于 HPA 峰值所需，会把第 18 章的扩容直接卡成 Pending | `kubectl delete -f deploy/base/resourcequota.yaml` |
| PriorityClass | 集群级 / Pod 引用 | 决定调度先后与抢占顺序，让在线链路不被离线任务挤掉 | 所有负载同等级、集群无抢占需求；误设 `globalDefault` 或过高 value 会抢占 kube-system 等关键 Pod | 删除对象并把引用改回，或降 value |
| QoS（隐式） | Pod 自身 | 节点压力驱逐时的分档 | 不是可独立部署的工具；它由 resources 写法决定，不能单独「开启」 | 改 resources 即改档 |

**最小接入 diff 与顺序**：先 `LimitRange`（兜底）→ 再给各 Deployment 写 `resources`（契约值）→ 再 `ResourceQuota`（总量）→ 最后 `PriorityClass` 并在 Pod 模板里加 `priorityClassName`。顺序不能反：先上 Quota 会让还没填 resources 的存量 Pod 触发准入统计异常；先上 PriorityClass 而不填 requests，抢占行为会建立在错误的 QoS 上。

**升级 / 回滚路径**：这三类都是命名空间级或集群级对象，升级只需 `kubectl apply -k deploy/overlays/dev` 叠加；回滚按接入的逆序 delete，且**先删配额类对象再回退 Pod 模板**——否则回退后突然多出来的 requests 会撞上已收紧的配额，制造一批 Pending。生产环境的回退按 17.5 走 Git，这里的手工 delete 只用于本地 kind 演练。

> 与第 18 章的接口：ResourceQuota 的 `requests.cpu` 上限必须 ≥ HPA `maxReplicas × api requests.cpu`，否则压测一扩容就 Pending（SP-19，见第 18 章）。本章把配额上限留得比静态副本数宽，就是为了给弹性留出空间。

## 17.4 落地配置（完整可应用文件，Kubernetes 1.32+）

> 全部字段沿用 `book/case-evolution.md` 的配置契约：命名空间 `order-demo-dev`、镜像 `registry.example.com/order-demo/<component>:git-<sha7>`、公共标签、`api` 端口 8081、探针路径、`terminationGracePeriodSeconds: 30`。`git-1a2b3c4` 是示例 SHA，发布脚本用真实短 SHA 替换它。`app.kubernetes.io/managed-by` 按第 14 章起约定为 `argocd`。

**`deploy/base/deployment-api.yaml`**（`apiVersion: apps/v1`，Kubernetes 1.32+）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: api
    app.kubernetes.io/managed-by: argocd
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: api
        version: git-1a2b3c4
        app.kubernetes.io/managed-by: argocd
    spec:
      priorityClassName: order-demo-online
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: api
          image: registry.example.com/order-demo/api:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8081
              protocol: TCP
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
          startupProbe:
            httpGet:
              path: /startup
              port: http
            failureThreshold: 30
            periodSeconds: 2
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            periodSeconds: 5
            failureThreshold: 2
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 5"]
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
```

> `preStop` 的 `sleep 5` 依赖运行时镜像含 `/bin/sh`（按第 8 章的工具层镜像给出）；它的作用是在 readiness 摘流之后为端点收敛留出窗口（见第 8 章）。`startupProbe` 仅 `api` 有，符合契约。注意 `resources` 与 `priorityClassName` 是本章新增字段，其余字段与第 6–11 章一致，没有另起命名空间、标签或端口 [R-17-1][R-17-2]。

**`deploy/base/limitrange.yaml`**（`apiVersion: v1`，Kubernetes 1.32+）

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: order-demo-defaults
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  limits:
    - type: Container
      default:
        cpu: 200m
        memory: 256Mi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      min:
        cpu: 50m
        memory: 64Mi
      max:
        cpu: "2"
        memory: 1Gi
      maxLimitRequestRatio:
        cpu: "10"
        memory: "4"
```

> `defaultRequest` 与 `api` 的 requests 完全一致，是为了让「漏填」的容器自动对齐基线而不是另立一套 [R-17-4]。`maxLimitRequestRatio.memory: "4"` 允许 `limits/requests` 到 4 倍，`api` 的 256Mi/128Mi=2、演练 Pod 的 64Mi/32Mi=2 都在范围内。

**`deploy/base/resourcequota.yaml`**（`apiVersion: v1`，Kubernetes 1.32+）

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: order-demo-quota
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 4Gi
    limits.cpu: "8"
    limits.memory: 8Gi
    pods: "40"
    count/deployments.apps: "10"
```

> `requests.cpu: "4"` = 4000m，按 `api` 单副本 100m 计算可容纳约 40 个副本，明显宽于 HPA `maxReplicas: 10` 的峰值需求（见第 18 章），不会把扩容卡成 Pending [R-17-5]。

**`deploy/base/priorityclass.yaml`**（`apiVersion: scheduling.k8s.io/v1`，Kubernetes 1.32+）

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: order-demo-online
  labels:
    app.kubernetes.io/name: order-demo
value: 100000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "在线链路 gateway / api / db，驱逐顺序最后，可抢占离线负载"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: order-demo-batch
  labels:
    app.kubernetes.io/name: order-demo
value: 10000
globalDefault: false
preemptionPolicy: Never
description: "离线任务 worker，不抢占在线负载，允许被抢占"
```

> `globalDefault: false` 是刻意的：任何没写 `priorityClassName` 的 Pod 保持默认优先级 0，不会被悄悄抬到在线档 [R-17-2]。`order-demo-batch` 用 `preemptionPolicy: Never`，保证 worker 不会反向抢占 `api`。

**`docs/runbooks/oomkilled.md`**（配套 runbook，内容完整）

```markdown
# Runbook：OOMKilled 定位

适用：容器被重启 / 退出码 137 / 事件出现 OOMKilled。
前置：kubectl 已指向目标集群，命名空间 order-demo-{env}。

## 一、先分清两种「被杀」
- 容器内 OOM：cgroup memory limit 触顶，内核杀容器内进程；事件 Reason=OOMKilled，退出码 137。
- 节点压力驱逐：节点内存/磁盘不足，kubelet 驱逐整个 Pod；事件 Reason=Evicted，Pod phase=Failed。
两者命令不同、处置不同，先看事件 Reason 再动手。

## 二、三步定位
1. 看状态与上次终止原因：
   kubectl -n order-demo-dev describe pod <pod> | sed -n '/Last State/,+8p'
   kubectl -n order-demo-dev get pod <pod> -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}{"\n"}'
2. 看事件时间线（区分 OOMKilled / Evicted / 探针误杀）：
   kubectl -n order-demo-dev get events --sort-by=.lastTimestamp | grep <pod>
3. 看 limit 与实际工作集口径：
   kubectl -n order-demo-dev get pod <pod> -o jsonpath='{range .spec.containers[*]}{.name}{"\t"}{.resources.limits.memory}{"\n"}{end}'
   kubectl -n order-demo-dev top pod <pod> --containers
   注意：limit 是容器级，Pod 内 sidecar、临时卷、page cache 都会计入工作集；
   「曲线峰值没到 limit」不等于没超限，要以 container_memory_working_set_bytes 为准（见第 21 章）。

## 三、处置
- 单次偶发：确认是冷启动/批量任务尖峰 → 按 17.2 用分位数重设基线，留突发余量。
- 持续发生：不要只调大 limit；先查泄漏，再决定是否扩容或改缓存策略。
- 节点级 Evicted：查 PriorityClass 与 QoS，确认是否 BestEffort 被优先驱逐。
```

**`hack/oom-drill.sh`**（触发并定位一次 OOMKilled，可复制执行）

```bash
#!/usr/bin/env bash
set -euo pipefail
NS=order-demo-dev

# 用一个独立演练 Pod 触发内存超限，不改动 api 的冻结基线
kubectl -n "${NS}" apply -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: oom-drill
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: oom-drill
spec:
  restartPolicy: Never
  containers:
    - name: allocator
      image: python:3.12-slim
      command: ["python", "-c"]
      args:
        - |
          import time
          blocks = []
          while True:
              blocks.append(bytearray(16 * 1024 * 1024))
              time.sleep(0.2)
      resources:
        requests:
          cpu: 50m
          memory: 32Mi
        limits:
          cpu: 200m
          memory: 64Mi
YAML

# 轮询等待 OOMKilled（restartPolicy=Never，终止原因落在 state 或 lastState）
for i in $(seq 1 60); do
  REASON=$(kubectl -n "${NS}" get pod oom-drill \
    -o jsonpath='{.status.containerStatuses[0].state.terminated.reason}{.status.containerStatuses[0].lastState.terminated.reason}' 2>/dev/null || true)
  if [ "${REASON}" = "OOMKilled" ]; then
    echo "OOMKilled 已触发（第 ${i} 次轮询）"
    break
  fi
  sleep 2
done

echo "== describe 关键段 =="
kubectl -n "${NS}" describe pod oom-drill | sed -n '/Last State/,+8p'
echo "== 事件时间线 =="
kubectl -n "${NS}" get events --field-selector involvedObject.name=oom-drill --sort-by=.lastTimestamp
echo "== 按 runbook 三步定位完成；清理演练对象 =="
kubectl -n "${NS}" delete pod oom-drill --wait=false
```
