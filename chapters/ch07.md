## 7.1 问题与反模式：四个组件，为什么不能都塞进 Deployment

第 6 章留下的 `order-demo` 只有一个 `gateway`：一个 Deployment、一个 Service、一个 ConfigMap，在 kind 里能 `curl` 通 `/healthz`，也能退回上一版。这是一个被刻意削到最小的闭环。真实应用不会停在这么舒服的状态——按 `book/case-evolution.md` 的组成表，`order-demo` 还有订单读写的 `api`、跑超时关单与通知的 `worker`、以及 PostgreSQL `db`。**合成案例**（本书统一采用虚构合成案例，见第 1 章）：某团队把这四个进程按最省事的方式全部写进同一个 Deployment 的四个容器里，理由是「反正都在一个 Pod 里，互相用 localhost 调用最方便」。上线一周后出了三件事：节点 drains 时这个「巨无霸 Pod」整体被重建，`gateway` 连带不可用；`db` 重启后数据目录回到初始状态，因为它写的是容器内临时层；`worker` 的异步任务在滚动更新时反复被 SIGTERM 打断，关单任务丢了一半。

这三件事的根因是同一个：**把「工作负载类型」当成了一个不需要决策的默认值**。工作负载（workload，承载应用进程的 K8s 资源，正式定义见本节下文）决定了控制器如何收敛、Pod 如何被标识、终止时发生什么、以及数据能不能留下来。第 6 章的 Deployment 只回答了「无状态、可随时替换」这一种情形；把有状态进程、一次性任务、节点级代理都套进这一种，等于把四类完全不同的运维语义压成一个 [R-07-3][R-07-1]。集群不会拒绝这样一份清单（描述期望状态的 YAML 声明文件，详见第 10 章），它只会忠实地按你写的语义运行，然后在故障时把代价一次性还回来。

三个高频反模式，按「现象 → 根因 → 本章替代做法」展开：

**反模式一：直接创建裸 Pod。** 现象是 `kubectl run` 出来的进程看着正常，节点故障或手动删除后再也不会回来，也没有滚动更新、没有副本数收敛。根因是裸 Pod 没有控制器，谁都不负责比对实际状态与期望状态——控制循环（controllers，持续比对并收敛的控制器，见第 2 章）根本没有挂在这个对象上 [R-07-3]。本章的替代做法是：任何进集群的进程都必须经由工作负载控制器创建，四类组件分别落到 Deployment 或 StatefulSet，禁止用裸 Pod 承载生产进程 [R-07-3]。

**反模式二：无状态服务也用 StatefulSet「为了名字稳定」。** 现象是 `gateway` 被写成 StatefulSet 后扩容明显变慢、升级要按顺序逐个来、删除后还残留一串 PVC 没人认领。根因是把「稳定网络标识」和「稳定访问入口」混为一谈：StatefulSet 提供的是每个副本固定的序号、固定的 DNS 名与有序启停，这是为有状态副本设计的，代价是滚动更新按序串行、PVC 默认不随对象删除 [R-07-1]；而调用方需要的「一个固定名字」由 Service 的虚拟 IP 与 DNS 提供，与副本有没有序号无关 [R-07-4]。本章的替代做法是：无状态组件一律用 Deployment + Service，`gateway`/`api`/`worker` 三个都这样落位，只有 `db` 用 StatefulSet 拿稳定标识。

### 7.1.1 真实复盘：把 gateway 误写成 StatefulSet 的 PVC 残留定位与清理 runbook

下面是一则脱敏后的产线复盘，它把反模式二从「道理上不对」推进到「出事时怎么定位、怎么收拾」。注意本章主叙事统一用合成案例，而此处是真实工程中反复出现的事故形态，仅对团队与业务名做脱敏。

**背景。** 某团队把对外网关 `gw` 用 `StatefulSet` 部署，副本 3。理由是「客户端要做 IP 白名单与长连接亲和，需要 `gw-0`/`gw-1`/`gw-2` 这种固定名字」。三个月后做资源降本，先把副本缩到 1，再把整个 `StatefulSet` 删除来清理环境。删除时用了 `kubectl delete sts gw`，没有显式回收 PVC。几天后同集群重新部署新版本 `gw` 时，存储侧磁盘容量告警、节点进入 `DiskPressure`，新 `StatefulSet` 的 Pod 卡在 `Pending`——调度器报「节点无足够可分配磁盘」。

**第一步：从告警定位到「孤儿 PVC」。** 收到 `DiskPressure` 后，先确认是哪类资源膨胀：

```bash
kubectl -n order-demo-prod get nodes \
  -o custom-columns=NAME:.metadata.name,ALLOC:.status.allocatable.ephemeral-storage,CAP:.status.capacity.ephemeral-storage
kubectl -n order-demo-prod get pvc -o wide | sort -k1
```

输出里出现 `data-gw-0`、`data-gw-1`、`data-gw-2` 等十余个 `Bound` 状态的 PVC，但同命名空间下 `kubectl get pod -l app=gw` 为空——这些 PVC 没有任何 Pod 引用，是孤儿。

**第二步：确认 StatefulSet 已删、PVC 不在级联删除范围。**

```bash
kubectl -n order-demo-prod get sts                 # 无 gw，确认已删
kubectl -n order-demo-prod get pod -l app=gw       # 空，确认无引用者
kubectl -n order-demo-prod describe pvc data-gw-0  # 看 Events 与 Used By
```

`describe` 的 `Used By` 为空、`Events` 无挂载记录，说明 PVC 与任何工作负载都已解耦。根因在此：StatefulSet 的 `volumeClaimTemplates` 创建的 PVC **不属于其级联删除范围**。Kubernetes 默认 `kubectl delete sts` 走 `cascade=background`，只删 Pod 与控制器对象，PVC 因「怕误删数据」被刻意保留。这正是反模式二最隐蔽的代价——比串行升级慢更难被第一时间发现 [R-07-1]。

**为什么这类残留容易被忽略。** StatefulSet 的 PVC 命名规则 `data-<sts>-<ordinal>` 与 Pod 同名，删除 Pod 时人眼容易误以为 PVC 一并没了；加上存储侧 `Retain` 策略下 PV 不会自动回收，时间一长就成了「看不见的债」。很多团队直到节点 `DiskPressure` 才回头翻账。

**第三步：回到 Git 与审计，判定「固定身份」是否真被用到。** 翻 `git log` 与客户端配置，发现白名单实际指向 `Service` 的 `ClusterIP`（`gw.order-demo-prod.svc`），长连接亲和也由 `Service` 的会话保持完成。`gw-0` 这种序号 DNS 从未被任何调用方解析。结论：此处 StatefulSet 提供的稳定身份是**无用开销**，用 `Deployment` + `Service` 即可满足全部需求 [R-07-4]。

**清理 runbook（四列，先评估再删除，绝不裸删生产数据）。**

| 步骤 | 动作 | 怎么查 | 通过标准 / 失败处置 |
|---|---|---|---|
| 1 评估 | 确认 PVC 无引用 Pod | `kubectl get pod -l app=gw` 为空 | 空则继续；非空先排查谁在挂载 |
| 2 备份 | 即便要删也先导出/快照 | 存储侧快照或 `kubectl -n order-demo-prod exec gw-0 -- pg_dump` 类命令（依组件） | 备份可读回放后再删；无备份严禁进入下一步 |
| 3 回收 | 逐个删 PVC | `kubectl -n order-demo-prod delete pvc data-gw-0 data-gw-1 data-gw-2` | 每个删后 `get pvc` 确认消失；若卡 `Terminating`，查 finalizer（见第 16 章） |
| 4 释放 PV | 若 StorageClass 回收策略为 `Retain`，PVC 删后 PV 仍占后端 | `kubectl get pv` 看状态 `Released`；`kubectl delete pv <name>` | PV 状态变 `Deleted`、云盘计费停止；`Delete` 策略则可跳过 |
| 5 校验 | 节点压力是否解除 | `kubectl get nodes` 无 `DiskPressure` | 告警清除、新 `StatefulSet`/`Deployment` 正常 `Pending→Running` |

**防止再犯的三道防线。** 其一，把 `gw` 重写为 `Deployment` + `Service`，删掉 `volumeClaimTemplates`；其二，给无状态组件单独建一个回收策略为 `Delete` 的 `StorageClass`，避免 `Retain` 残留；其三，在第 25 章的准入策略里禁止「无 `volumeClaimTemplates` 却用 `StatefulSet`」的写法，从提交源头拦截。

这则复盘的核心一句话：**无状态服务用 StatefulSet 只为「名字稳定」，不仅升级慢，还会把清理负担悄悄转嫁给 PVC。** 判定标准永远是可证伪的——调用方是否真的解析了 `gw-0` 这种序号 DNS？若只用 `Service` 虚拟 IP，StatefulSet 的稳定身份就是负债 [R-07-1][R-07-4][R-07-3]。

**反模式三：把日志采集 sidecar 写成常驻主容器且不做退出协调。** 现象是任务型 Pod 永远停在 `Running` 或 `NotReady`，永远到不了 `Completed`，因为主容器跑完退出了，日志 sidecar 还在常驻 [R-07-6]。根因是老写法里 sidecar 与主容器是平级的 `containers`，K8s 不会替它们协调生命周期。本章的替代做法是用原生 sidecar（KEP-753，把带 `restartPolicy: Always` 的容器放进 `initContainers`，由 kubelet 保证主容器退出后它也退出）或干脆把日志采集提到 DaemonSet（每节点一个实例，见 7.2 决策树）[R-07-6][R-07-7]。

> **本章的取舍边界**：本章只给工作负载定型，不写探针（第 8 章）、不写 ConfigMap 的 `immutable`（第 9 章）、不写 `requests`/`limits`（第 17 章）、不写 Chart/overlay（第 10 章）。第 6 章已冻结的字段一个都不动，本章全部是**新增文件**。这样任何一次失败都能定位到「是哪一层加固引入的」，而不是在几十个字段里猜。

## 7.2 范式与决策树：先问四个问题，再选控制器

**工作负载（workload）的可验证定义**：一组由控制器管理的 Pod，控制器依据你声明的 `replicas`、更新策略与 Pod 模板持续收敛；判定「某进程属于哪类工作负载」的标准不是它叫什么名字，而是三个可观察行为——**副本被删除后是否自动重建、Pod 是否有稳定且可预期的标识、终止时是否有确定的顺序与数据保留语义** [R-07-3][R-07-1]。凡是不满足「自动重建」的（裸 Pod）不用于生产；凡是同时要求「稳定标识 + 有序启停 + 每副本独立存储」的，才落到 StatefulSet。

本章要回答的决策问题只有一句：**面对一个组件，凭什么选 Deployment 而不是 StatefulSet、Job 或 DaemonSet？** 把这句话拆成一棵可判定、可用命令验证的决策树：

```
这个组件需要「每个节点恰好一个实例」吗？        是 → DaemonSet（节点级代理/采集）
        │ 否
这个进程「跑完就该结束」吗？                    是 → Job（一次性）/ CronJob（周期）
        │ 否
这个组件需要「稳定身份 / 稳定网络标识 / 有序启停 / 每副本独立存储」吗？
                                                是 → StatefulSet（db）
        │ 否
→ Deployment（无状态、可随时丢弃、靠 Service 拿稳定入口）
```

四个问题都是**可证伪**的：问「每节点一个」时看的是有没有 `daemonSet` 语义；问「跑完即结束」时看的是进程有没有自然退出点；问「稳定身份」时看的是 `db-0` 这种序号和 headless Service 是否真的被用到；最后一个分支靠 Service 的 selector 验证，而不是靠感觉 [R-07-4][R-07-7]。把 `order-demo` 四个组件代入：

| 组件 | 决策路径落点 | 判据（可用命令证明） | 端口 / 存储 |
|---|---|---|---|
| `gateway` | Deployment | 无序号、删 Pod 后 Service 仍返回 200 | 8080 / 无状态 |
| `api` | Deployment | 同上；额外挂 initContainer 与原生 sidecar | 8081 / 无状态 |
| `worker` | Deployment | 无监听端口、被删后自动重建并续跑队列 | 无端口 / 无状态 |
| `db` | StatefulSet | `db-0` 稳定标识 + `db` headless Service + 独立 PVC | 5432 / `volumeClaimTemplates` |

四条结论由此定型：

1. **有状态身份、稳定网络标识与有序启停才需要 StatefulSet；普通无状态服务用 Deployment，裸 Pod 不用于生产。** 依据是 StatefulSet 的序号、稳定 DNS 与按序更新语义，以及 Service 提供的固定入口 [R-07-1][R-07-4][R-07-3]。
2. **原生 sidecar（KEP-753）解决了「主容器退出后 sidecar 不退出」的老问题；initContainer 只用于启动前的一次性准备。** 二者边界必须钉死：一次性准备用不带 `restartPolicy: Always` 的 initContainer，常驻但需随主容器退出的辅助进程用原生 sidecar [R-07-2][R-07-6]。
3. **进程应无状态、可随时丢弃，把状态外置；这是工作负载可自由选型的前提。** 只有进程自身不持有不可重建的状态，副本才能被任意替换、伸缩、回滚，配置与产物分离才成立 [R-07-8][R-07-9]；编排系统把「可丢弃的进程」作为基本假设，见 Borg 系列论文的抽象 [R-07-11]。
4. **「用 StatefulSet 跑数据库」只是可选项之一，托管数据库往往更省事；是否自己管要按运维能力而非技术偏好决定。** 这是本书观点，见下方独立标注块。

三种「Pod 内协作机制」的分工也必须一次说清，否则第 8 章的 preStop 与第 23 章的 CrashLoop 速查表会共用错术语：

| 机制 | 写在清单哪里 | 解决什么 | 不该用来做什么 |
|---|---|---|---|
| initContainer | `spec.template.spec.initContainers`（默认 `restartPolicy: Never` 语义） | 启动前一次性准备：等依赖就绪、建表、拉配置 | 常驻服务、需要随业务长期运行的东西 [R-07-2] |
| 原生 sidecar | `spec.template.spec.initContainers` + `restartPolicy: Always` | 与主容器同生命周期的辅助进程，主退它退 | 需要独立伸缩的组件（那应该是独立工作负载）[R-07-6] |
| 生命周期钩子 | `lifecycle.preStop` / `postStart` | 终止前摘流排空、启动后注册 | 替代 readiness 判断（那是第 8 章的事）[R-07-7] |

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：`db` 用 StatefulSet 只是为了让读者看见「稳定标识、有序启停、每副本独立存储」这三件事长什么样；生产环境是否自己管数据库，应由团队的备份恢复、故障切换与版本升级能力决定，而不是由「我们已经会写 StatefulSet」决定。
>
> **论证**：StatefulSet 只解决编排层的身份与顺序，不解决数据层的备份、PITR、主从切换、major 版本升级与 schema 兼容。把这些责任接进团队，等于接下一条完整的运维链路；本章给出的 `db` 是**教学用最小形态**——单副本、无备份、无高可用，只用来演示 `db-0` 与 headless Service 的可验证行为。判断依据应当是可量化的能力项（能否在规定时间内完成一次备份恢复到新集群、能否在不丢数据的前提下做版本升级），这些恰恰是第 16 章与第 29 章的评估对象；Operator（把运维知识写成控制器让集群自己收敛，详见第 27 章）与托管服务只是把这份责任转移到不同载体上 [R-07-5]。
>
> **反例与前提**：若团队已有成熟的托管数据库服务与 SLA，且应用不需要感知底层拓扑，那么自建 StatefulSet 几乎总是更贵的选择，第 16 章的 expand–contract 与第 29 章的成熟度评估表给出降级预案。反过来，若出于数据主权、离线环境或教学目的必须自建，则本章形态是合法的起点，但必须显式接受「例外前提：本地一次性 kind、无真实数据；补偿措施：第 9 章起凭据由 ESO 注入、第 16 章补备份、CL-S-01/CL-S-02 仍生效；例外有效期：仅 `ch07-workloads` 与 `ch08-probes` 两个 tag」这一限制。跳过能力评估直接上自建，典型代价见第 29 章。

### 7.2.1 稳定标识三件套：StatefulSet 到底给了什么、没给什么

7.1.1 的复盘回答了「出事怎么收拾」，这里把机制的另一半补全：StatefulSet 的「稳定标识」不是一句口号，而是三件套，每一件都可用命令验证；三者缺一，稳定标识就不成立，也就不该用 StatefulSet。

**第一件：序号身份。** Pod 名固定为 `<StatefulSet 名>-<序号>`，`hostname` 与 Pod 名一致；`db-0` 被删后，控制器重建的新 Pod 仍叫 `db-0`，且重新挂回同一个 PVC `data-db-0`。身份跟着序号走，不跟容器实例走——这是「重建后身份不漂移」的机制来源 [R-07-1]。验证：

```bash
kubectl -n order-demo-dev get pod db-0 \
  -o jsonpath='{.metadata.name}{"\t"}{.spec.hostname}{"\t"}{.spec.nodeName}{"\n"}'
# 期望：db-0    db-0    <某节点>；删掉重建后再执行一次，前两列不变
```

**第二件：稳定 DNS。** 序号身份要被调用方用到，必须能被解析，这由 `serviceName: db` 指向的 headless Service 完成：`clusterIP: None` 让集群 DNS 直接为每个副本发布记录——`db-0.db.order-demo-dev.svc.cluster.local` 精确指向 `db-0`，`db-1.db…` 指向 `db-1`；而解析无序号前缀的 `db.db.order-demo-dev.svc.cluster.local`（headless Service 本名）返回的是全部就绪副本的地址列表 [R-07-1][R-07-4]。注意分寸：普通 ClusterIP Service 的 DNS 返回虚拟 IP，天然由 kube-proxy 均衡；headless 本名返回的地址列表不保证均衡，由调用方自行选择。**只有「调用方需要点名某个具体副本」时，序号 DNS 才是刚需**——主库直连 `db-0`、按分片连 `db-N` 属于这类；「只是想有个固定名字调服务」属于 Service 的职责范围，判定方法见 7.1.1 第三步。

**第三件：稳定存储。** `volumeClaimTemplates` 按 `<模板名>-<StatefulSet 名>-<序号>` 的规则创建 PVC，`db-0` 对应 `data-db-0`。这条命名规则是三件套里最容易被低估的：它把「身份—存储」绑定，使缩容、升级、重建都不挪数据；同时也正是 7.1.1 里 PVC 残留的成因——绑定太稳，以至于控制器删除时不敢替你回收 [R-07-1]。另外它**不可原地修改**：改容量请求、换 StorageClass 对已存在的 PVC 无效，要换只能重建，这正是 7.4.3 单独讲存储卷生命周期的原因。

三件套齐了，「无状态别用 StatefulSet」的判据就不再是感觉，而是三个可证伪的问题：

| 问题 | 验证方式 | 任一为「是」→ | 三问全否 → |
|---|---|---|---|
| 调用方是否点名具体副本（序号 DNS） | 翻调用方配置与 DNS 查询日志，是否解析过 `db-0.db…` | StatefulSet | Deployment + Service |
| 副本是否需要各自独立的持久存储身份 | 是否每个副本要读写**不同的**数据集 | StatefulSet + `volumeClaimTemplates` | Deployment（共享卷用 PVC，见第 16 章） |
| 启停/升级是否依赖序号顺序 | 主从拓扑、故障切换是否按序号语义工作 | StatefulSet（配 `podManagementPolicy`，见 7.4.1） | Deployment + 滚动更新 |

三问全否却仍写 StatefulSet，代价清单是：升级按序串行、慢于 Deployment 的并行滚动；缩容留下无人认领的 PVC（7.1.1 的全部代价）；扩容必须逐个等就绪。反过来，**三问有一问为「是」**，也不能拿 Deployment 凑合——用「每个副本一份手写 YAML」模拟稳定身份，会把身份做进配置而不是控制器，扩缩容时立刻崩坏。这就是 7.2 决策树第三问的完整判据 [R-07-1][R-07-3]。

> **本书观点（稳定标识的边界，不需要外部背书）**
>
> **主张**：StatefulSet 只提供身份与顺序，不提供「有状态的正确性」——主从复制、选主、脑裂防护都是数据层组件自己实现的，编排层无法替你补上。
>
> **论证**：三件套全部作用在 Pod/PVC/DNS 这层对象上；`db-0` 与 `db-1` 之间是否存在复制关系、谁可写，取决于镜像内进程自己的配置。把「用了 StatefulSet」当成「数据库就高可用了」，是把编排语义与数据语义混为一谈；本书的高可用形态在第 16 章以复制与备份展开，Operator 形态的评估对象见第 27、29 章 [R-07-5]。
>
> **反例与适用前提**：本章的单副本教学 `db` 没有任何高可用，但它仍是合法的 StatefulSet——可见「用 StatefulSet」与「高可用」互不蕴含。适用前提：仅讨论 Kubernetes 内置工作负载；自定义控制器的语义边界见第 27 章。

### 7.4.1 `podManagementPolicy` 与 `partition` 分批升级演练

`statefulset-db.yaml` 里写了 `podManagementPolicy: OrderedReady` 与 `updateStrategy.rollingUpdate.partition: 0`。这两行决定了「Pod 怎么起、怎么升」，是 StatefulSet 区别于 Deployment 的核心语义，必须把差异讲透。

**`podManagementPolicy` 两种取值。**
- `OrderedReady`（默认）：启动/扩缩容时严格按序号 `0→1→2` 串行，前一个 `Running` 且 `Ready` 后，下一个才被创建；终止时反向 `2→1→0`。好处是依赖顺序的组件（如主从）天然有序；坏处是缩容/升级慢，一个卡住后面全等着 [R-07-1]。
- `Parallel`：所有序号同时启动/终止，不互相等待。适合各副本互相独立、不需要顺序的 StatefulSet（如独立分片）。注意：`Parallel` 只影响「管理顺序」，不影响 `updateStrategy` 的升级分批逻辑。

**与 Deployment 的本质区别。** Deployment 的 `maxSurge`/`maxUnavailable` 控制「同时有几个新/旧副本」，与「序号」无关；StatefulSet 没有这两个字段，它用 `podManagementPolicy` 管启停顺序、用 `partition` 管升级分批。两者正交：启停顺序管「谁先起来」，`partition` 管「哪些序号进升级窗口」。

**`partition` 分批升级演练**（教学用 `db` 是单副本，这里扩到 3 副本说明机制）。设 `replicas: 3`、`partition: 0`：

```yaml
spec:
  replicas: 3
  podManagementPolicy: OrderedReady
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0
```

升级时，只有**序号 ≥ partition** 的副本进入新版。把 `partition` 设为 2，则 `db-0`、`db-1` 保持旧版不动，`db-2` 先升；观察无误再调到 1，让 `db-1` 升；最后调到 0 全部升完。这是「金丝雀但带序号」的原语，不依赖额外控制器 [R-07-1]。

演练命令（用真实 SHA 替换示例值；`db` 教学镜像本地 kind 可用，生产凭据见第 9 章）：

```bash
# 1) 先把 db 扩到 3 副本并确认有序就绪
kubectl -n order-demo-dev scale sts/db --replicas=3
kubectl -n order-demo-dev rollout status statefulset/db --timeout=120s
kubectl -n order-demo-dev get pod -l app.kubernetes.io/component=db -o name

# 2) 改镜像，但先卡在 partition=2，只让 db-2 进新版
kubectl -n order-demo-dev patch sts/db --type=merge \
  -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'
kubectl -n order-demo-dev set image sts/db \
  db=registry.example.com/order-demo/db:git-9f8e7d6

# 3) 观察只有 db-2 进入新版
kubectl -n order-demo-dev get pod -l app.kubernetes.io/component=db \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[0].image}{"\n"}{end}'

# 4) 批次放行：依次 1 → 0
kubectl -n order-demo-dev patch sts/db --type=merge \
  -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":1}}}}'
kubectl -n order-demo-dev rollout status statefulset/db --timeout=120s
kubectl -n order-demo-dev patch sts/db --type=merge \
  -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'
kubectl -n order-demo-dev rollout status statefulset/db --timeout=120s
```

**回滚要点。** `partition` 只控制升级窗口，回滚仍走 `kubectl -n order-demo-dev rollout undo statefulset/db`；但若要把「工作负载类型从 StatefulSet 改回 Deployment」这类结构性回退，必须回到 Git 上一 tag 重新 apply（见 7.5 方案 B），这与公理 5 一致 [R-07-3][R-07-9]。

**选择建议（判据表）。**

| 场景 | `podManagementPolicy` | 原因 |
|---|---|---|
| 主从数据库、强顺序依赖 | `OrderedReady` | 保证从库在重建/升级时按序，避免脑裂 |
| 独立分片、彼此无依赖 | `Parallel` | 启动快，不互等 |
| 需要分批升级（金丝雀式） | 任意 + `partition` | `partition` 才是分批开关 |

注意：`podManagementPolicy: Parallel` 不会改变「PVC 与序号绑定」的事实——`db-2` 升完级仍挂载 `data-db-2`，数据不因升级而挪窝 [R-07-1]。

**`hack/ch07-apply.sh`**

```bash
#!/usr/bin/env bash
set -euo pipefail
```

### 7.4.2 Job/CronJob 与 `ttlSecondsAfterFinished` 完整示例

决策树里「跑完即结束」的分支落到 `Job` / `CronJob`。`order-demo` 的 `worker` 是常驻 Deployment（消费队列），但还有一类**周期性、可丢弃**的任务——例如每日凌晨对历史订单做对账、导出离线报表——它们不适合常驻，用 `CronJob` 更合适：到点跑、跑完退出、不留进程。

完整可应用示例（`apiVersion: batch/v1`，Kubernetes 1.32+）：

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: order-reconcile
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: reconcile
    app.kubernetes.io/managed-by: kubectl
spec:
  schedule: "17 2 * * *"            # 每日 02:17（避整点）
  concurrencyPolicy: Forbid         # 上次没跑完则跳过本次，避免堆叠
  startingDeadlineSeconds: 300      # 错过窗口 5 分钟内仍尝试
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      ttlSecondsAfterFinished: 3600   # 完成后 1 小时自动回收 Job 对象
      backoffLimit: 3
      template:
        metadata:
          labels:
            app.kubernetes.io/name: order-demo
            app.kubernetes.io/component: reconcile
            version: git-1a2b3c4
            app.kubernetes.io/managed-by: kubectl
        spec:
          restartPolicy: Never          # Job 容器退出即终态，由 backoffLimit 管重试
          automountServiceAccountToken: false
          securityContext:
            runAsNonRoot: true
            seccompProfile:
              type: RuntimeDefault
          containers:
            - name: reconcile
              image: registry.example.com/order-demo/api:git-1a2b3c4
              imagePullPolicy: IfNotPresent
              command: ["/api", "--reconcile"]
              env:
                - name: APP_VERSION
                  value: git-1a2b3c4
              # 凭据由第 9 章的 ESO 注入，对象名 order-demo-db-credentials，绝不入 Git
              envFrom:
                - secretRef:
                    name: order-demo-db-credentials
              securityContext:
                allowPrivilegeEscalation: false
                readOnlyRootFilesystem: true
                capabilities:
                  drop: ["ALL"]
```

**关键字段解释。** `ttlSecondsAfterFinished: 3600` 让 Job 在 `Completed`/`Failed` 达到终态 1 小时后被控制器自动删除——否则 Job 与 Pod 会永久留在集群里，日积月累撑爆 `etcd`。这是 `CronJob` / `Job` 区别于 Deployment 的回收方式：Deployment 靠 `replicas` 常驻，Job 靠 `ttlSecondsAfterFinished` 自杀 [R-07-7]。`restartPolicy: Never` 是 Job 的硬性要求之一（另可选 `OnFailure`），与 Deployment 的 `Always` 相反——因为 Job 的「完成」就是进程自然退出，`kubelet` 不应拉起它 [R-07-7]。`concurrencyPolicy: Forbid` 防止对账任务重叠写同一批数据。

**一次性 Job 的写法**：把上面 `CronJob` 换成 `kind: Job`，其余 `jobTemplate.spec` 内容移到 `spec` 下即可，`ttlSecondsAfterFinished` 同样生效，适合手动触发的迁移/修复任务。

**验证与回滚。**

```bash
# 立即触发一次（不等职时），从 CronJob 派生一个一次性 Job
kubectl -n order-demo-dev create job order-reconcile-manual \
  --from=cronjob/order-reconcile
kubectl -n order-demo-dev wait --for=condition=complete job/order-reconcile-manual --timeout=120s
kubectl -n order-demo-dev get job   # 1 小时后 ttl 生效，记录消失
# 回滚：Job 失败由 backoffLimit 重试；要强制重跑先删旧 Job 再建
kubectl -n order-demo-dev delete job order-reconcile-manual
```

通过标准：`wait` 返回 `complete`，`get pods` 里该 Pod 为 `Completed`；1 小时后 `get job` 不再列出（或被 `successfulJobsHistoryLimit` 收敛到 3 条）。这与第 7 章「可丢弃进程」的基调一致：任务型工作负载的干净退出与自动回收，是它能被自由选型的前提 [R-07-3][R-07-11]。

### 7.4.3 存储卷生命周期：动态供应、回收策略、扩容与快照

7.4 的 `statefulset-db.yaml` 里 `volumeClaimTemplates` 没写 `storageClassName`，这条 PVC 是怎么变成一块真实磁盘的？——动态供应链条：控制器按模板创建 PVC → PVC 未指定 `storageClassName` 时落到集群**默认 StorageClass**（带 `storageclass.kubernetes.io/is-default-class: "true"` 注解的那个）→ StorageClass 指定的 CSI 驱动创建 PV → PVC 与 PV 绑定为 `Bound` → Pod 调度后挂载 [R-07-1]。链条里最常断的一环是「集群没有默认 StorageClass」：此时 PVC 永远停在 `Pending`，`describe pvc` 只有一句 waiting for a volume to be created。定位命令与通过标准：

```bash
kubectl get storageclass
# 通过标准：目标类带 (default) 标记；没有默认类则 PVC 会一直 Pending，不会自行恢复
```

处置不是「随手指定一个类」，而是按数据性质选回收策略与能力（判据见本节末的本书观点块）。

**回收策略：`reclaimPolicy` 决定「删 PVC 之后发生什么」。** `Delete`：PV 与后端存储一并回收，干净但删了就真没了；`Retain`：PV 进入 `Released`，数据留在后端，等人工处置。注意两层策略要分开看：PVC 被删除时触发的是 StorageClass 的 `reclaimPolicy`；而删除 StatefulSet 时 `volumeClaimTemplates` 创建的 PVC 根本不在级联删除范围（7.1.1 的根因）——所以「`Retain` 兜底」与「Sts 删除不删 PVC」是两条独立的防线，一条顶替不了另一条 [R-07-1]。

**扩容：先看 StorageClass 的 `allowVolumeExpansion`。** 只有该字段为 `true` 的类，其 PVC 才允许把 `spec.resources.requests.storage` 调大；**只能增大、不能缩小**，缩小需要新建卷迁移数据；在线扩容（文件系统 resize）多数 CSI 驱动已支持，但依赖驱动实现。教学环境的现实：kind 默认的 local-path 供应器不支持扩容，本章的 `1Gi` 在本地只能观察字段语义；扩容完整演练属于第 16 章的范畴。

一个完整可应用的 StorageClass 示例（`apiVersion: storage.k8s.io/v1`；`provisioner` 按集群实际 CSI 驱动填写，kind 本地无法直接应用，生产接入与选型见第 16 章）：

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: order-demo-data
provisioner: csi.example.com            # 按集群实际 CSI 驱动填写
reclaimPolicy: Retain                   # 数据库类资产：删 PVC 后 PV 保留待人工处置
volumeBindingMode: WaitForFirstConsumer # 等 Pod 调度定型后再供应卷，避免拓扑不匹配
allowVolumeExpansion: true              # 允许 PVC 只增不减地扩容
```

对应地，在 `statefulset-db.yaml` 的 `volumeClaimTemplates` 里加 `storageClassName: order-demo-data` 即可落到这个类；但方向要钉死：**模板对已存在的 `data-db-0` 无效**，要换类只能按 7.5 方案 B 的结构性回退重建 [R-07-1]。

**快照：升级前的回滚物料。** VolumeSnapshot 是独立 API（`snapshot.storage.k8s.io/v1`，依赖集群安装 external-snapshotter 及其 CRD），对指定 PVC 打点：

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: order-demo-snapclass
driver: csi.example.com                # 与上面 StorageClass 同一驱动
deletionPolicy: Retain                 # 删快照对象时保留底层快照，防误删
---
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: db-data-pre-upgrade
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: db
spec:
  volumeSnapshotClassName: order-demo-snapclass
  source:
    persistentVolumeClaimName: data-db-0
```

验证与用途：`kubectl -n order-demo-dev get volumesnapshot db-data-pre-upgrade` 的 `READYTOUSE` 为 `true` 即可，把它登记进第 16 章的备份台账。

> **本书观点（存储生命周期判据，不需要外部背书）**
>
> **主张**：`reclaimPolicy` 与 `allowVolumeExpansion` 的选型按「数据资产性质」而非「磁盘价格」决定——可重建数据选 `Delete` + 可扩容类，数据库类资产选 `Retain` + 显式回收义务。
>
> **论证**：`Retain` 的代价不是磁盘占用而是流程负债，每次清理都要走 7.1.1 那样的 runbook；`Delete` 的代价是不可恢复。两者对资产性质的敏感度完全不同。扩容选型同理：`allowVolumeExpansion` 只能在创建 StorageClass 时决定，事后补开不改变已创建 PVC 的可用性，应在接入 CSI 时一次性审清。
>
> **反例与适用前提**：缓存类数据用 `Retain`，孤儿卷会按 7.1.1 的形态静默积累；数据库数据用 `Delete`，误删 PVC 即直接丢库——第 16 章的备份恢复演练专门对照这种失败。适用前提：本节只覆盖动态供应（CSI）路径；静态供应（手工建 PV）与跨集群恢复见第 16 章。

> **本书观点（快照的定位，不需要外部背书）**
>
> **主张**：快照是「回滚物料」，不是「备份」。给 `db` 升级前打快照，目的是让 7.4.5 的回滚有一个存储层的退路，使公理 6「回滚方案先行」对有状态负载可执行。
>
> **论证**：快照通常与源卷同处一个存储域：源卷所在存储系统的误删、区域级故障、逻辑损坏经复制传播时，快照同样受损；快照的保留期也常短于事故追溯窗口。真正独立于源存储的备份（物理复制、WAL 归档、恢复到新集群演练）是第 16 章的主题。
>
> **反例与适用前提**：把「每天打快照」当备份完备性的团队，在源卷被误删时快照一并丢失，这类代价在第 16 章有专门对照。适用前提：快照只承担「升级/变更窗口内的短程回退」，不承担长期保留。

### 7.4.4 Job/CronJob 并发与重试语义的完整判据

7.4.2 给了能跑的 CronJob，但 `completions`/`parallelism`/`backoffLimit`/`activeDeadlineSeconds` 四个字段的语义边界没展开——它们决定「跑几次、同时跑几个、失败怎么算、多久必须停」，错一处就是夜里反复失败或任务堆叠。逐条钉死 [R-07-7]：

| 字段 | 管什么 | 什么时候偏离默认值 | 常见误判 |
|---|---|---|---|
| `completions` | 累计成功次数；缺省 1（成功一次 Job 即 `Complete`） | 批量分片处理（按订单段对账）设为段数，配合索引区分输入 | 误以为它管「同时跑几个」——那是 `parallelism` |
| `parallelism` | 同时运行的 Pod 上限 | 控制打下游的力度（如 db 连接池容量） | 设得比剩余 `completions` 大没有意义，会被裁剪 |
| `backoffLimit` | 允许的失败次数上限，超出即标 `Failed` 并停止重试 | 幂等任务可给大；非幂等给小并配 `activeDeadlineSeconds` 兜底 | `restartPolicy: OnFailure` 时同一 Pod 内的重启不计入，只有 Pod 重建才计——失败计数与重启计数不是一回事 |
| `activeDeadlineSeconds` | 整个 Job 的墙钟上限，到点杀 Pod 并标 `Failed` | 卡死保护：宁可失败报警，不可无限挂着 | 到点即终态、**不再重试**，与 `backoffLimit` 是两个独立的失败出口；不存在「到点后按 backoffLimit 重来」 |
| `concurrencyPolicy` | 上一轮没跑完时新触发的处理：`Allow` 并行 / `Forbid` 跳过本轮 / `Replace` 杀旧起新 | 写型任务（对账、结算）一律 `Forbid`；「最新值覆盖」型（刷新缓存、物化视图）可用 `Replace` | `Forbid` + `startingDeadlineSeconds` 组合：被跳过的触发超出窗口后不再补跑，监控上表现为「静默少跑」而不是报错 |

**合成案例：每晚必失败的 `DeadlineExceeded`。** 某团队给对账 Job 设了 `activeDeadlineSeconds: 600`，历史上对账只需几分钟；某月数据量增长后单轮跑到 12 分钟，于是每晚 Job 被 deadline 杀掉标 `Failed`，`backoffLimit: 3` 一次都没用上——没有新的重试，deadline 触发即终态。值班连续一周把告警当偶发，直到 `describe job` 里 conditions 的 reason 稳定为 `DeadlineExceeded` 才改判。纠正动作分两步：先用下面的命令确认失败出口；再把「慢而能完成」与「卡死」区分开——前者调大 deadline 或改为分片（`completions` + `parallelism` 按订单段切），后者才需要 deadline 兜底。

```bash
kubectl -n order-demo-dev describe job order-reconcile-manual | grep -A3 Conditions
# 判定：reason=DeadlineExceeded → 走 deadline 语义（不再重试），查耗时为什么增长；
#       reason=BackoffLimitExceeded → 已按 backoffLimit 重试完仍失败，查容器日志
```

`ttlSecondsAfterFinished` 再钉一句定位语义：它删的是**对象**（Job 及其 Pod 记录），不影响任何已写数据；设 `0` 表示终态即删——排障现场会随告警一起消失，本书建议至少保留一个告警处置周期（7.4.2 取 1 小时）。CronJob 侧还有一层 `successfulJobsHistoryLimit`/`failedJobsHistoryLimit` 管历史记录条数，与 ttl 是两套回收（历史列表 vs 单个 Job 自删），叠着用不冲突 [R-07-7]。

### 7.4.5 有状态负载的升级与回滚：OnDelete、partition 回滚与存储兼容前提

7.4.1 讲了 `partition` 灰度，这里补齐升级策略的第三个取值，与「回滚到旧版」在有状态负载上的特殊约束。

**`OnDelete`：升级的第三种策略。** `updateStrategy.type` 除了 `RollingUpdate` 还有 `OnDelete`：改了 Pod 模板后控制器**什么都不做**，等你手动删 Pod 才按新模板重建，节奏完全由人控制。适用场景：major 版本升级、需要人工逐个确认副本健康的有状态组件。代价也明确：模板与实际状态会漂移——`sts` 的 YAML 里写着新镜像、Pod 里跑的还是旧镜像，排障时若不看这个差异会误判「已经升级了」。漂移检测命令与通过标准：

```bash
kubectl -n order-demo-dev get sts db \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
kubectl -n order-demo-dev get pod db-0 \
  -o jsonpath='{.spec.containers[0].image}{"\n"}'
# 通过标准：两行一致；用 OnDelete 期间允许不一致，但必须登记在案并限期收敛
```

```bash
# OnDelete 演练：改策略 → set image → 手动逐个触发
kubectl -n order-demo-dev patch sts/db --type=merge \
  -p '{"spec":{"updateStrategy":{"type":"OnDelete"}}}'
kubectl -n order-demo-dev set image sts/db \
  db=registry.example.com/order-demo/db:git-9f8e7d6
kubectl -n order-demo-dev delete pod db-0   # 单副本教学形态；多副本按 2→1→0 反向逐个
kubectl -n order-demo-dev get pod db-0 -o jsonpath='{.spec.containers[0].image}{"\n"}'
```

`delete pod db-0` 触发重建后，新 Pod 仍叫 `db-0` 并重新挂回 `data-db-0`——存储不随升级挪窝，这正是 7.2.1 第三件套的机制在升级场景的表现 [R-07-1]。

**partition 的回滚语义与存储兼容前提。** `rollout undo statefulset/db` 把模板退回上一修订，回滚同样受 `partition` 约束：序号低于 partition 的副本不参与，因此**回滚也要分批**，把 partition 从 2 放到 0 的节奏与升级对称。但镜像回退只是回滚的一半。对有状态负载，公理 6「回滚方案先行」要求三件套同时成立：

1. **镜像可回退**：旧镜像在仓库中存在且可拉取（不可变镜像 + SHA 标签保证，见第 3 章）；
2. **数据向后兼容**：新版本写入的数据格式不能让旧版本读不回来。PostgreSQL 的 major 版本升级会改数据目录布局，旧二进制直接挂新目录无法启动——这正是第 16 章 expand–contract 范式存在的原因：schema 变更始终「可加不可删、可空不可非空」，让旧代码在新 schema 上仍能跑；
3. **存储层有退路**：7.4.3 的升级前快照（或第 16 章的备份）在手，才有「数据也退回去」的选项。

三条缺任何一条，「回滚」就退化成名义上的动作。还要钉死一个术语边界（口径与第 13 章一致）：**回滚是恢复到上一个已知良好版本的镜像与配置；「把数据也退回去」不是回滚，是恢复**，必须走第 16 章的备份恢复流程并按 runbook 执行，不能靠 `rollout undo` 顺带完成 [R-07-9]。若团队评估自己撑不起这三件套，把有状态负载交给 Operator 或托管服务（责任转移的论证见 7.2 本书观点块）就是更诚实的选项 [R-07-5]。

最后一项是本章最容易被跳过的一项：它证明新增三个组件没有动到已经跑通的最小闭环，SP-01 在命令层面成立 [R-07-3]。

**回滚命令 / 步骤**（先演练、后发布）：

```bash
# 方案 A：控制器内的参数回退（镜像、副本数等 Pod 模板字段）
PREV=$(kubectl -n order-demo-dev get deploy worker \
  -o jsonpath='{.spec.template.spec.containers[0].image}')
kubectl -n order-demo-dev set image deployment/worker \
  worker=registry.example.com/order-demo/worker:git-0000000
kubectl -n order-demo-dev rollout status deployment/worker --timeout=60s || true
kubectl -n order-demo-dev rollout undo deployment/worker
kubectl -n order-demo-dev rollout status deployment/worker --timeout=120s
kubectl -n order-demo-dev set image deployment/worker worker="${PREV}"
kubectl -n order-demo-dev rollout status deployment/worker --timeout=120s

# 方案 B：结构性回退——把工作负载类型/新增文件整体退回上一 tag
git diff --stat ch06-first-loop..HEAD -- deploy/base/     # 先确认只新增、未改动第 6 章文件
git checkout ch06-first-loop -- deploy/base/
kubectl -n order-demo-dev delete sts db --cascade=orphan
kubectl -n order-demo-dev delete pvc data-db-0           # 显式回收，验证 PVC 残留风险
kubectl -n order-demo-dev apply -f deploy/base/deployment.yaml
kubectl -n order-demo-dev apply -f deploy/base/service.yaml
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s
```

> **为什么方案 B 必须回到 Git**：`rollout undo` 只能回退同一个控制器的 Pod 模板修订，无法把 StatefulSet「变回」Deployment，也无法撤销新增的 Service 与 PVC。结构性回退的唯一正确表达是「恢复到上一份已声明的完整清单」——这与全书公理 5 一致：生产变更必须回到 Git，不得靠一串 `kubectl delete` 拼出目标状态 [R-07-3][R-07-9]。本章对象是本地一次性 kind，用 `git checkout` 到文件是为了让读者看清「回退的是哪一份声明」，从第 10 章起同一意图写作 `kubectl apply -k deploy/overlays/dev@<上一 tag>`（见第 10 章），从第 14 章起由 GitOps 控制器自动完成（见第 14 章）。

**回滚验证**：

