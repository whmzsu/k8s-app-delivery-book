## 7.1 问题与反模式：四个组件，为什么不能都塞进 Deployment

第 6 章留下的 `order-demo` 只有一个 `gateway`：一个 Deployment、一个 Service、一个 ConfigMap，在 kind 里能 `curl` 通 `/healthz`，也能退回上一版。这是一个被刻意削到最小的闭环。真实应用不会停在这么舒服的状态——按 `book/case-evolution.md` 的组成表，`order-demo` 还有订单读写的 `api`、跑超时关单与通知的 `worker`、以及 PostgreSQL `db`。**合成案例**（本书统一采用虚构合成案例，见第 1 章）：某团队把这四个进程按最省事的方式全部写进同一个 Deployment 的四个容器里，理由是「反正都在一个 Pod 里，互相用 localhost 调用最方便」。上线一周后出了三件事：节点 drains 时这个「巨无霸 Pod」整体被重建，`gateway` 连带不可用；`db` 重启后数据目录回到初始状态，因为它写的是容器内临时层；`worker` 的异步任务在滚动更新时反复被 SIGTERM 打断，关单任务丢了一半。

这三件事的根因是同一个：**把「工作负载类型」当成了一个不需要决策的默认值**。工作负载（workload，承载应用进程的 K8s 资源，正式定义见本节下文）决定了控制器如何收敛、Pod 如何被标识、终止时发生什么、以及数据能不能留下来。第 6 章的 Deployment 只回答了「无状态、可随时替换」这一种情形；把有状态进程、一次性任务、节点级代理都套进这一种，等于把四类完全不同的运维语义压成一个 [R-07-3][R-07-1]。集群不会拒绝这样一份清单（描述期望状态的 YAML 声明文件，详见第 10 章），它只会忠实地按你写的语义运行，然后在故障时把代价一次性还回来。

三个高频反模式，按「现象 → 根因 → 本章替代做法」展开：

**反模式一：直接创建裸 Pod。** 现象是 `kubectl run` 出来的进程看着正常，节点故障或手动删除后再也不会回来，也没有滚动更新、没有副本数收敛。根因是裸 Pod 没有控制器，谁都不负责比对实际状态与期望状态——控制循环（controllers，持续比对并收敛的控制器，见第 2 章）根本没有挂在这个对象上 [R-07-3]。本章的替代做法是：任何进集群的进程都必须经由工作负载控制器创建，四类组件分别落到 Deployment 或 StatefulSet，禁止用裸 Pod 承载生产进程 [R-07-3]。

**反模式二：无状态服务也用 StatefulSet「为了名字稳定」。** 现象是 `gateway` 被写成 StatefulSet 后扩容明显变慢、升级要按顺序逐个来、删除后还残留一串 PVC 没人认领。根因是把「稳定网络标识」和「稳定访问入口」混为一谈：StatefulSet 提供的是每个副本固定的序号、固定的 DNS 名与有序启停，这是为有状态副本设计的，代价是滚动更新按序串行、PVC 默认不随对象删除 [R-07-1]；而调用方需要的「一个固定名字」由 Service 的虚拟 IP 与 DNS 提供，与副本有没有序号无关 [R-07-4]。本章的替代做法是：无状态组件一律用 Deployment + Service，`gateway`/`api`/`worker` 三个都这样落位，只有 `db` 用 StatefulSet 拿稳定标识。

**反模式三：把日志采集 sidecar 写成常驻主容器且不做退出协调。** 现象是任务型 Pod 永远停在 `Running` 或 `NotReady`，永远到不了 `Completed`，因为主容器跑完退出了，日志 sidecar 还在常驻 [R-07-6]。根因是老写法里 sidecar 与主容器是平级的 `containers`，K8s 不会替它们协调生命周期。本章的替代做法是用原生 sidecar（KEP-753，把带 `restartPolicy: Always` 的容器放进 `initContainers`，由 kubelet 保证主容器退出后它也退出）或干脆把日志采集提到 DaemonSet（每节点一个实例，见 7.2 决策树）[R-07-6][R-07-7]。

> **本章的取舍边界**：本章只给工作负载定型，不写探针（第 8 章）、不写 ConfigMap 的 `immutable`（第 9 章）、不写 `requests`/`limits`（第 17 章）、不写 Chart/overlay（第 10 章）。第 6 章已冻结的字段一个都不动，本章全部是**新增文件**。这样任何一次失败都能定位到「是哪一层加固引入的」，而不是在几十个字段里猜。

## 7.2 范式与决策树：先问四个问题，再选控制器

**工作负载（workload）的可验证定义**：一组由控制器管理的 Pod，控制器依据你声明的 `replicas`、更新策略与 Pod 模板持续收敛；判定「某进程属于哪类工作负载」的标准不是它叫什么名字，而是三个可观察行为——**副本被删除后是否自动重建、Pod 是否有稳定且可预期的标识、终止时是否有确定的顺序与数据保留语义** [R-07-3][R-07-1]。凡是不满足「自动重建」的（裸 Pod）不用于生产；凡是同时要求「稳定标识 + 有序启停 + 每副本独立存储」的，才落到 StatefulSet。

本章要回答的决策问题只有一句：**面对一个组件，凭什么选 Deployment 而不是 StatefulSet、Job 或 DaemonSet？** 把这句话拆成一棵可判定、可用命令验证的决策树：

```
这个组件需要「每个节点恰好一个实例」吗？        是 → DaemonSet（节点级代理/采集）
        │ 否
这个进程「跑完就该结束」吗？                    是 → Job（一次性）/ CronJob（周期）
        │ 否
这个组件需要「稳定身份 / 稳定网络标识 / 有序启停 / 每副本独立存储」吗？
                                                是 → StatefulSet（db）
        │ 否
→ Deployment（无状态、可随时丢弃、靠 Service 拿稳定入口）
```

四个问题都是**可证伪**的：问「每节点一个」时看的是有没有 `daemonSet` 语义；问「跑完即结束」时看的是进程有没有自然退出点；问「稳定身份」时看的是 `db-0` 这种序号和 headless Service 是否真的被用到；最后一个分支靠 Service 的 selector 验证，而不是靠感觉 [R-07-4][R-07-7]。把 `order-demo` 四个组件代入：

| 组件 | 决策路径落点 | 判据（可用命令证明） | 端口 / 存储 |
|---|---|---|---|
| `gateway` | Deployment | 无序号、删 Pod 后 Service 仍返回 200 | 8080 / 无状态 |
| `api` | Deployment | 同上；额外挂 initContainer 与原生 sidecar | 8081 / 无状态 |
| `worker` | Deployment | 无监听端口、被删后自动重建并续跑队列 | 无端口 / 无状态 |
| `db` | StatefulSet | `db-0` 稳定标识 + `db` headless Service + 独立 PVC | 5432 / `volumeClaimTemplates` |

四条结论由此定型：

1. **有状态身份、稳定网络标识与有序启停才需要 StatefulSet；普通无状态服务用 Deployment，裸 Pod 不用于生产。** 依据是 StatefulSet 的序号、稳定 DNS 与按序更新语义，以及 Service 提供的固定入口 [R-07-1][R-07-4][R-07-3]。
2. **原生 sidecar（KEP-753）解决了「主容器退出后 sidecar 不退出」的老问题；initContainer 只用于启动前的一次性准备。** 二者边界必须钉死：一次性准备用不带 `restartPolicy: Always` 的 initContainer，常驻但需随主容器退出的辅助进程用原生 sidecar [R-07-2][R-07-6]。
3. **进程应无状态、可随时丢弃，把状态外置；这是工作负载可自由选型的前提。** 只有进程自身不持有不可重建的状态，副本才能被任意替换、伸缩、回滚，配置与产物分离才成立 [R-07-8][R-07-9]；编排系统把「可丢弃的进程」作为基本假设，见 Borg 系列论文的抽象 [R-07-11]。
4. **「用 StatefulSet 跑数据库」只是可选项之一，托管数据库往往更省事；是否自己管要按运维能力而非技术偏好决定。** 这是本书观点，见下方独立标注块。

三种「Pod 内协作机制」的分工也必须一次说清，否则第 8 章的 preStop 与第 23 章的 CrashLoop 速查表会共用错术语：

| 机制 | 写在清单哪里 | 解决什么 | 不该用来做什么 |
|---|---|---|---|
| initContainer | `spec.template.spec.initContainers`（默认 `restartPolicy: Never` 语义） | 启动前一次性准备：等依赖就绪、建表、拉配置 | 常驻服务、需要随业务长期运行的东西 [R-07-2] |
| 原生 sidecar | `spec.template.spec.initContainers` + `restartPolicy: Always` | 与主容器同生命周期的辅助进程，主退它退 | 需要独立伸缩的组件（那应该是独立工作负载）[R-07-6] |
| 生命周期钩子 | `lifecycle.preStop` / `postStart` | 终止前摘流排空、启动后注册 | 替代 readiness 判断（那是第 8 章的事）[R-07-7] |

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：`db` 用 StatefulSet 只是为了让读者看见「稳定标识、有序启停、每副本独立存储」这三件事长什么样；生产环境是否自己管数据库，应由团队的备份恢复、故障切换与版本升级能力决定，而不是由「我们已经会写 StatefulSet」决定。
>
> **论证**：StatefulSet 只解决编排层的身份与顺序，不解决数据层的备份、PITR、主从切换、major 版本升级与 schema 兼容。把这些责任接进团队，等于接下一条完整的运维链路；本章给出的 `db` 是**教学用最小形态**——单副本、无备份、无高可用，只用来演示 `db-0` 与 headless Service 的可验证行为。判断依据应当是可量化的能力项（能否在规定时间内完成一次备份恢复到新集群、能否在不丢数据的前提下做版本升级），这些恰恰是第 16 章与第 29 章的评估对象；Operator（把运维知识写成控制器让集群自己收敛，详见第 27 章）与托管服务只是把这份责任转移到不同载体上 [R-07-5]。
>
> **反例与前提**：若团队已有成熟的托管数据库服务与 SLA，且应用不需要感知底层拓扑，那么自建 StatefulSet 几乎总是更贵的选择，第 16 章的 expand–contract 与第 29 章的成熟度评估表给出降级预案。反过来，若出于数据主权、离线环境或教学目的必须自建，则本章形态是合法的起点，但必须显式接受「例外前提：本地一次性 kind、无真实数据；补偿措施：第 9 章起凭据由 ESO 注入、第 16 章补备份、CL-S-01/CL-S-02 仍生效；例外有效期：仅 `ch07-workloads` 与 `ch08-probes` 两个 tag」这一限制。跳过能力评估直接上自建，典型代价见第 29 章。

## 7.3 工具选型：本章的「工具」是 K8s 内置控制器

第 7 章没有外部工具要装，选型对象是 Kubernetes 内置的工作负载控制器与 Pod 内协作机制。这正是第 6 章「先不引入模板与交付工具」的延续：先把原生语义用对，第 10 章再用 Helm 3.x / Kustomize 5.x 把这些清单组织起来，才不会把类型选错藏进模板里 [R-07-10]。所有条目都按 `book/decisions.md` 的单一示例实现原则收敛——`db` 用原生 StatefulSet（教学最小形态），其余工具只在下表作对比，不另给第二套实现。

| 控制器 / 机制 | 最适 | 何时不该用（本章相关的一条） | 主要风险 | 回滚方式 |
|---|---|---|---|---|
| Deployment（apps/v1） | 无状态、可随时替换的长驻进程 | 需要每副本固定标识或独立存储时——那该用 StatefulSet | 误当 StatefulSet 用会丢数据；误当 Job 用完不成语义 | `kubectl -n order-demo-dev rollout undo deployment/<name>` |
| StatefulSet（apps/v1） | `db`：稳定序号、headless DNS、独立 PVC | 无状态服务「为了名字稳定」——用 Service 即可 [R-07-4] | 串行升级慢、PVC 残留、缩容需手工清理 | `kubectl -n order-demo-dev rollout undo statefulset/db` |
| DaemonSet（apps/v1） | 每节点一个的日志/指标采集 | 业务进程——不需要也不应该绑节点 | 节点加入即调度，易吃掉业务资源 | `kubectl -n order-demo-dev rollout undo daemonset/<name>` |
| Job / CronJob（batch/v1） | 跑完即结束的一次性/周期任务 | 长驻服务——没有自然退出点 | sidecar 未协调会导致永不 `Completed` [R-07-6] | 删除并重建 Job（`ttlSecondsAfterFinished` 回收） |
| initContainer | 启动前一次性准备（建表/等依赖） | 常驻辅助进程 | 失败会阻塞整个 Pod 启动 [R-07-2] | 改回上一版 Pod 模板 |
| 原生 sidecar（KEP-753） | 需随主容器退出的常驻辅助进程 | 需独立伸缩的组件 | 最低 K8s 版本要求（锁附录 A）[R-07-6] | 改回上一版 Pod 模板 |
| 裸 Pod（v1） | 仅本地排障临时刻 | **生产进程一律不用** | 无控制器、不重建、无滚动更新 [R-07-3] | 无回滚语义，只能删除 |

**最小接入 diff**（关键：对第 6 章零改动，只新增文件）：

```diff
 deploy/base/
   namespace.yaml                (第 6 章，未改动)
   configmap.yaml                (第 6 章，未改动)
   deployment.yaml               (第 6 章 gateway，未改动)
   service.yaml                  (第 6 章 gateway，未改动)
+  deployment-worker.yaml        # 新增：worker，无监听端口
+  deployment-api.yaml           # 新增：api 8081 + initContainer + 原生 sidecar
+  service-api.yaml              # 新增：ClusterIP api 8081
+  service-db-headless.yaml      # 新增：headless db 5432，供 StatefulSet 用
+  statefulset-db.yaml           # 新增：db，PostgreSQL 5432 + volumeClaimTemplates
 hack/
   kind-up.sh                    (第 6 章，未改动)
   verify.sh                     (第 6 章，未改动)
+  ch07-apply.sh                 # 新增：SHA 替换 + apply + rollout status
```

「零改动」不是修辞：第 6 章的 `namespace.yaml`、`configmap.yaml`、`deployment.yaml`、`service.yaml` 在本章的 `git diff ch06-first-loop..ch07-workloads` 里应当一条都不出现，这是 SP-01 的验收点。**升级路径**：Deployment 靠 `strategy.rollingUpdate`（沿用第 6 章 `maxSurge: 1`、`maxUnavailable: 0`）；StatefulSet 靠 `updateStrategy.rollingUpdate.partition` 做分批，先升 `db` 的非数据面参数再动镜像。**回滚路径**：控制器内的镜像/参数回退用 `rollout undo`；但「把工作负载类型从 StatefulSet 改回 Deployment」这类结构性回退，`rollout undo` 无能为力，必须回到 Git 的上一 tag 重新 apply 整份清单——这一动作在本章用 `git checkout` 表达，从第 10 章起会收敛成 `kubectl apply -k deploy/overlays/dev@<上一 tag>`（见第 10 章）。这与全书公理 5「Git 为唯一真相」一致，不构成例外。

## 7.4 落地配置（完整可应用文件，Kubernetes 1.32+）

> 全部字段沿用第 6 章配置契约：命名空间 `order-demo-dev`、镜像 `registry.example.com/order-demo/<component>:git-<sha7>`、公共标签 `app.kubernetes.io/*`、`version=git-<sha7>`、`app.kubernetes.io/managed-by: kubectl`、Service 端口 `gateway` 8080 / `api` 8081 / `db` 5432。`git-1a2b3c4` 为示例 SHA，脚本用真实短 SHA 替换。探针在第 8 章补，本章不写；`requests`/`limits` 在第 17 章统一给，本章不写。原生 sidecar 依赖 KEP-753，对应最低 K8s 版本锁在附录 A，本章按 1.32+ 书写。

**`deploy/base/deployment-worker.yaml`**（`apiVersion: apps/v1`）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: worker
    app.kubernetes.io/managed-by: kubectl
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: worker
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: worker
        version: git-1a2b3c4
        app.kubernetes.io/managed-by: kubectl
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: worker
          image: registry.example.com/order-demo/worker:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          env:
            - name: APP_VERSION
              value: git-1a2b3c4
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
```

> `worker` 故意不写 `ports`：它没有监听端口，只从队列取任务。把「无监听端口」写进清单本身，就是一条可验证的工作负载判据 [R-07-3]。

**`deploy/base/deployment-api.yaml`**（`apiVersion: apps/v1`；含 initContainer 与原生 sidecar）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: api
    app.kubernetes.io/managed-by: kubectl
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: api
        version: git-1a2b3c4
        app.kubernetes.io/managed-by: kubectl
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      initContainers:
        # 一次性准备：只做启动前建表，跑完即退出（不带 restartPolicy: Always）
        - name: init-schema
          image: registry.example.com/order-demo/api:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          command: ["/api", "--migrate"]
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
        # 原生 sidecar（KEP-753）：restartPolicy: Always 表示随主容器同生命周期，主退它退
        - name: log-forwarder
          image: registry.example.com/order-demo/api:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          restartPolicy: Always
          command: ["/api", "--log-forward"]
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
      containers:
        - name: api
          image: registry.example.com/order-demo/api:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8081
              protocol: TCP
          env:
            - name: APP_VERSION
              value: git-1a2b3c4
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
```

> 两个 `initContainers` 复用了 `api` 镜像的不同入口参数，这是教学简化：真实项目的日志 sidecar 会是专用镜像，但**机制不变**——`init-schema` 没有 `restartPolicy: Always`，跑完退出；`log-forwarder` 带 `restartPolicy: Always`，由 kubelet 按原生 sidecar 语义管理 [R-07-2][R-07-6]。`api` 的探针要等第 8 章才补，且按配置契约只有 `api` 会有 `/startup`。

**`deploy/base/statefulset-db.yaml`**（`apiVersion: apps/v1`）

```yaml

metadata:
  name: db
  namespace: order-demo-dev
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/component: db
    app.kubernetes.io/managed-by: kubectl
spec:

    rollingUpdate:
      partition: 0

    matchLabels:
      app.kubernetes.io/name: order-demo
      app.kubernetes.io/component: db

    metadata:
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/component: db
        version: git-1a2b3c4
        app.kubernetes.io/managed-by: kubectl
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: db
          image: registry.example.com/order-demo/db:git-1a2b3c4
          imagePullPolicy: IfNotPresent
          ports:
            - name: postgres
              containerPort: 5432
              protocol: TCP
          env:
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true

```

> `volumeClaimTemplates` 给每个副本独立 PVC，`db-0` 拿到 `data-db-0`；这正是反模式二里「PVC 残留」的由来——删 StatefulSet 不会自动删 PVC，回收要显式做（见 7.5）。本章不写任何数据库口令：凭据从属于第 9 章的 `order-demo/db-credentials`，由 ESO 注入，绝不入 Git；教学镜像在本地 kind 内使用内建默认值，生产形态见第 16、29 章（见本书观点块的例外边界）。


## 7.5 验证与回滚（回滚方案先于发布方案）

**回滚**（把线上恢复到上一个已知良好版本，详见第 13 章）在本章第一次涉及「结构性回退」：镜像参数回退与工作负载类型回退是两条不同的路径，必须先各演练一次，才允许带着这四个组件进入第 8 章。

**验证命令**（仓库根目录执行，需已安装 kind / kubectl / docker / curl，版本见附录 A）：

```bash
chmod +x hack/ch07-apply.sh
./hack/ch07-apply.sh
kubectl -n order-demo-dev get deploy,sts,pod -o wide
kubectl -n order-demo-dev get svc -o wide
kubectl -n order-demo-dev get pvc
kubectl -n order-demo-dev get pod db-0 -o jsonpath='{.metadata.name}{"\t"}{.spec.hostname}{"\n"}'
kubectl -n order-demo-dev rollout history deployment/worker
./hack/verify.sh
```

**逐条通过标准**：

| 判据 | 怎么查 | 期望结果 |
|---|---|---|
| 四类工作负载各出现一次 | `kubectl -n order-demo-dev get deploy,sts` | `gateway`/`api`/`worker` 为 Deployment，`db` 为 StatefulSet |
| 无裸 Pod | `kubectl -n order-demo-dev get pods` | 每个 Pod 的 `ownerReferences` 都指向控制器，无独立创建者 |
| `db` 有稳定标识 | `kubectl -n order-demo-dev get pod db-0` | 存在 `db-0`，且 headless Service `db` 的 DNS 能解析到它 |
| 独立存储 | `kubectl -n order-demo-dev get pvc` | 出现 `data-db-0`，状态 `Bound` |
| initContainer / sidecar 语义正确 | `kubectl -n order-demo-dev get pod -l app.kubernetes.io/component=api -o jsonpath='{..initContainerStatuses}'` | `init-schema` 为 `Terminated/Completed`，`log-forwarder` 为 `Running` 且带 `restartPolicy: Always` |
| 第 6 章闭环未被破坏 | `./hack/verify.sh` | `gateway/healthz` 仍返回 200，根路径 `version` 与 SHA 一致 |

最后一项是本章最容易被跳过的一项：它证明新增三个组件没有动到已经跑通的最小闭环，SP-01 在命令层面成立 [R-07-3]。

**回滚命令 / 步骤**（先演练、后发布）：

```bash
# 方案 A：控制器内的参数回退（镜像、副本数等 Pod 模板字段）
PREV=$(kubectl -n order-demo-dev get deploy worker \
  -o jsonpath='{.spec.template.spec.containers[0].image}')
kubectl -n order-demo-dev set image deployment/worker \
  worker=registry.example.com/order-demo/worker:git-0000000
kubectl -n order-demo-dev rollout status deployment/worker --timeout=60s || true
kubectl -n order-demo-dev rollout undo deployment/worker
kubectl -n order-demo-dev rollout status deployment/worker --timeout=120s
kubectl -n order-demo-dev set image deployment/worker worker="${PREV}"
kubectl -n order-demo-dev rollout status deployment/worker --timeout=120s

# 方案 B：结构性回退——把工作负载类型/新增文件整体退回上一 tag
git diff --stat ch06-first-loop..HEAD -- deploy/base/     # 先确认只新增、未改动第 6 章文件
git checkout ch06-first-loop -- deploy/base/
kubectl -n order-demo-dev delete sts db --cascade=orphan
kubectl -n order-demo-dev delete pvc data-db-0           # 显式回收，验证 PVC 残留风险
kubectl -n order-demo-dev apply -f deploy/base/deployment.yaml
kubectl -n order-demo-dev apply -f deploy/base/service.yaml
kubectl -n order-demo-dev rollout status deployment/gateway --timeout=120s
```

> **为什么方案 B 必须回到 Git**：`rollout undo` 只能回退同一个控制器的 Pod 模板修订，无法把 StatefulSet「变回」Deployment，也无法撤销新增的 Service 与 PVC。结构性回退的唯一正确表达是「恢复到上一份已声明的完整清单」——这与全书公理 5 一致：生产变更必须回到 Git，不得靠一串 `kubectl delete` 拼出目标状态 [R-07-3][R-07-9]。本章对象是本地一次性 kind，用 `git checkout` 到文件是为了让读者看清「回退的是哪一份声明」，从第 10 章起同一意图写作 `kubectl apply -k deploy/overlays/dev@<上一 tag>`（见第 10 章），从第 14 章起由 GitOps 控制器自动完成（见第 14 章）。

**回滚验证**：

```bash
./hack/verify.sh
kubectl -n order-demo-dev get deploy,sts,pod -o wide
kubectl -n order-demo-dev get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

通过标准：`gateway/healthz` 为 200 且根路径 `version` 与镜像标签一致；`get deploy,sts` 只剩第 6 章的 `gateway`；`data-db-0` PVC 已不存在。**回滚没有验证过，就不允许进入第 8 章**（CL-G-07）。
