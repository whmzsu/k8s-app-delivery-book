## 30.1 问题与反模式：集群从 1 个变 5 个，前面的做法怎么不失控

第 4 章把边界划在三套命名空间，第 14 章用 Argo CD 2.x 让「一次 PR 同步一个集群」成立。团队与集群数量涨上来之后，这两个前提都会被撑破：五个团队、五个集群、五套流水线，前面所有关于「唯一真相」的纪律会在复制粘贴里悄悄失效。

**合成案例**（教学合成，非真实事件）：某团队从单集群扩到五套。做法一是**为每个团队复制一套集群与流水线**，半年后五套集群的 K8s 版本差了两个 minor、Kyverno 1.x 策略库各改各的，一次通用漏洞修复要在五个地方分别发版；做法二是平台方**把一切包办并强制审批**，研发新建一个服务要排三天队，于是有人偷偷把 `kubectl apply` 塞进自己的 CI，旁路就此滋生；做法三是**`terraform apply` 在本地随手跑、state 落在笔记本**，某次误操作把 cluster-b 的节点池缩到 0，而 Git 里没有任何对应声明，复盘时谁也说不清集群当时该是什么样 [R-30-1][R-30-3][R-30-8][R-30-12]。

三个反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：为每个团队复制一套集群与流水线。** 现象是升级与策略各自漂移、同一修复发五遍；根因是把「多团队」直接等价于「多套独立实现」，没有区分「故障域要隔离」与「实现要统一」。替代做法是用 Cluster API 1.x / Terraform 1.x **集中供应**集群、以标准化模板生成，差异只留在「故障域 / 合规 / 租户」三个维度 [R-30-1][R-30-12]。

**反模式二：平台方把一切包办并强制审批。** 现象是研发排队、旁路滋生、护栏形同虚设；根因是把「平台工程」理解成审批关卡，而不是给研发铺一条**默认就对**的路。替代做法是「黄金路径」：模板产出的骨架自带非 root、SHA 标签、探针、资源基线、最小权限，研发填几个参数即可自助创建，平台只守护栏不守工单 [R-30-8][R-30-9]。

**反模式三：`terraform apply` 本地随手跑、state 在笔记本。** 现象是状态不一致、无审计、误操作无法回退；根因是把 state 当普通文件，而它其实是「基础设施的唯一真相」，且常含凭据明文。替代做法是**远端加密 state + PR 里的 plan/diff 审查 + 锁**，本地只 `plan` 不 `apply` [R-30-3][R-30-12]。

以上反模式的**方法论**参照 CNCF 公开案例 [R-30-12]；该来源只支撑「这类失效模式确实存在」，不证明合成案例真实发生。

## 30.2 范式与决策树：边界、顺序与一条有护栏的自助路径

**第一条判据沿用第 4 章（SP-12）**：命名空间不是安全边界；**需要凭据、配额、故障域的硬隔离时，应分集群乃至独立账号** [R-30-1]。第 4 章当时只取「三套命名空间」这一最低成本档，本章不推翻它，只是把「什么时候升级到多集群」用同一把尺子量清楚：变的不是判断标准，是团队规模与合规要求。

**集群边界划分表**（按故障域 / 合规 / 租户隔离，不按团队名切）：

| 划分依据 | 单集群多命名空间 | 多集群（本章） | 独立账号 / 订阅 |
|---|---|---|---|
| 故障域 | 共享控制面，控制面故障全受影响 | 每集群独立控制面 | 完全独立 |
| 凭据 / 合规 | 需额外 RBAC 与独立 Secret | 每集群独立凭据 | 独立审计与账单 |
| 租户隔离 | 弱（仅组织 / 配额） | 中（集群级） | 最强 |
| 相对成本档位 | 最低 | 中 | 最高 |
| 何时不该用 | 需要硬故障域或合规审计时 | 单团队单服务、预算有限时 | 不需要跨账号审计时 |

对 `order-demo` 本书取两档：`cluster-a` 为 canary 故障域、`cluster-b` 为 production 故障域，二者 K8s 版本保持同一 minor，凭据独立注入，用同一份模块供应 [R-30-1]。

**双集群升级顺序**（按 Kubernetes 版本偏差策略，控制面与节点偏差不得跨越一个 minor）[R-30-6]：

| 顺序 | 动作 | 前置条件 | 观察点 |
|---|---|---|---|
| 1 | 升级管理集群（承载 Cluster API 1.x / Argo CD 2.x 的那个） | 版本偏差策略允许 | 控制器自身健康（见第 28 章指标表） |
| 2 | 升 `cluster-a`（canary）控制面 → 节点 | 管理集群已稳定一个同步周期 | 业务 `verify.sh` 200、无 CrashLoopBackOff |
| 3 | 观察一个完整发布窗口 | cluster-a 无版本相关告警 | 错误预算未异常消耗（见第 20 章） |
| 4 | 升 `cluster-b`（production）控制面 → 节点 | 上一步通过 | 同上 |
| 5 | 收尾：清理旧版本资源 | 两集群版本一致 | `kubectl get nodes` 版本齐平 |

降级 / 回滚按 **4→3→2→1 逆向**执行：先回退生产集群、再回退 canary，控制面先于节点；绝不先动管理集群，否则两工作集群同时失去供应与交付能力 [R-30-6]。

**一次变更同时发到两集群的范式**：沿用第 14 章的晋升模型（SP-04），把 ApplicationSet 的 List 生成器从「三环境」扩成「两集群」——**一份渲染产物、一个 PR、两个 Application、按 `tier` 顺序同步**。关键在「一次变更入口」而非「两次发布」：SHA 只在 `gitops/rendered/prod/all.yaml` 里改一次，两个 destination 由同一 `ApplicationSet` 生成，因此不会出现「cluster-a 是 git-1a2b3c4、cluster-b 还是上一版」的分裂 [R-30-5]。同步顺序用 `tier` 标签表达：canary 先健康，production 再跟上；这与第 15 章渐进式交付是同一思想，只是粒度从「流量比例」换成了「集群集合」。

**黄金路径的判据**：平台工程的产出是「默认就对的模板」，不是审批关卡。可验证形态是——用 Backstage 模板新建一个服务，产出骨架**自带**全部护栏，无需人工补 [R-30-4][R-30-7][R-30-8][R-30-9]：

| 护栏 | 模板必须自带 | 对应章 |
|---|---|---|
| 不可变镜像 + SHA 标签 | `image: ...:git-<sha7>`，无 `latest` | 3、6、12 |
| 非 root 最小镜像 | `runAsNonRoot: true`、`seccompProfile` | 6、25 |
| 探针与优雅终止 | `/healthz` / `/readyz`、`preStop`、30s 宽限 | 8 |
| 资源基线 | requests / limits 对齐 api 基线 | 17 |
| 最小权限 | 无 `cluster-admin`、不挂载多余 SA token | 26 |
| 准入默认拒绝 | `NetworkPolicy` 默认拒绝 | 19、25 |
| 变更入口 | 产出即 Git 仓库，走第 14 章 PR | 14 |

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：平台工程的产出是**黄金路径**而非审批关卡；抽象应当**给自由但不给 root**——把安全、可观测、可回滚做成模板默认值，研发只填业务参数。
>
> **论证**：审批关卡把「做对」的成本压到每次变更，研发排队越久，越有动力绕开平台自建旁路（30.1 反模式二）。黄金路径把成本前移到「生成骨架」那一次：护栏是模板里的字段，不是评审会上的口头要求，于是「默认就对」且可被 CI 校验。这也延续了第 1 章的横切观——安全不是流水线末尾的一个阶段，而是作用于每一环的属性；平台只是把横切属性固化进模板。判断标准不是「平台管了多少」，而是「不用平台能不能做错」：能，说明护栏没进模板。
>
> **反例与适用前提**：这不等于「完全放开、不设任何门禁」。涉及生产凭据、跨集群写权限、集群级资源的操作仍要 CODEOWNERS 审批（见第 14 章）；护栏式抽象管的是「高频、低风险、模式化」的创建动作。前提是团队规模已到需要自助（第 5 章警戒线里的 L3 档）、且平台方能维护模板与策略库；20 人团队用几条 CI 检查 + 一份清单更合适。跳过此步的典型代价是「平台变成工单系统」。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：**state 必须远端加密存储并做 plan/diff 审查**；把它当普通文件处理，是多集群事故的高频来源。生产 `terraform apply` 只允许发生在 CI 的受控流水线里，本地只 `plan`。
>
> **论证**：state 是基础设施的唯一真相，既记录「现在该是什么样」，也可能含凭据明文。本地随手 `apply` 会在不产生 commit 的情况下改变集群，此后任何发布、回滚、复盘都失去确定基线——这与第 14 章「Git 唯一真相」是同一条纪律在基础设施层的投影，也是公理 5、9 的衍生护栏（见第 3、4 章）。远端加密 + 状态锁 + PR 里的 plan/diff 审查，把「谁在何时把 state 改成了什么」变成可审计、可 `git revert` 的记录。L1 只支撑 state 的语义与后端配置，主张部分不引用外部背书 [R-30-3][R-30-11]。
>
> **反例与适用前提**：这不等于「任何 Terraform 操作都不能在本地跑」。本地一次性实验集群、明确不涉及共享 state 的沙箱可以 `apply`；前提是 state 不指向任何共享后端、且对象是一次性环境。常态下任何指向生产 state 的本地 `apply` 都被禁止。

**决策树**（判断当前该停在单集群还是升级）：

```
是否需要凭据 / 配额 / 故障域的硬隔离，或有合规审计要求？  否 → 停在第 4 章三套命名空间
        │ 是
是否有平台组能维护标准化模板与策略库？                    否 → 先补平台能力，不复制集群
        │ 是
多个集群是否由同一份 IaC 模块供应、同一 GitOps 入口发布？   否 → 集中供应 + 一份 ApplicationSet，停
        │ 是
一次变更能否在两个集群产生同一 SHA 且可一起回退？          否 → 回 30.4 检查双集群生成器
        │ 是
state 是否远端加密、plan 是否进 PR、升级顺序是否成文？      否 → 补护栏，不许升级生产集群
        │ 是
→ 多集群拓扑成立；黄金路径按 30.4 模板开放自助
```

### 30.2.1 升级五步 × 观察指标 × 回滚触发条件

决策树回答「能不能升级」，下面回答「升的时候看到什么数就停手」。30.2 开头的五步表只写了「观察什么方向」，没写阈值，执行时会退化成「节点起来了、没告警，继续下一步」——这正是 30.1 反模式一里五套集群各自漂移的起点：**漂移不是一次做错的，是五次「看起来没问题」累积的**。把五步铺成带窗口、带阈值、带回滚动作的时序，升级才从「手艺」变成「流程」[R-30-6]。

| 步 | 动作与观察窗口 | 观察指标（阈值，本章经验值，须按集群规模校准） | 通过判据 | 回滚触发（任一命中即停） | 回滚动作 |
|---|---|---|---|---|---|
| 1 | 管理集群：控制面 → 节点，窗口 30m | Argo CD 2.x 与 Cluster API 1.x 控制器 `Ready` 副本数；apiserver 请求 P99 `< 1s`；`etcd_disk_wal_fsync_duration_seconds` P99 `< 25ms`；`apiserver_requested_deprecated_apis` 无新增 | 控制器全 `Ready`、下一轮同步无错误、两个工作集群仍 `Synced` | 控制器 CrashLoop；P99 连续 10m 超阈；两工作集群接连 `Unknown` | 停止后续步骤；控制面**不支持降级**，只能从 etcd 快照重建或换新控制面后重试 |
| 2 | `cluster-a`（canary）控制面 → 节点，窗口 60m | `kubectl get --raw='/readyz?verbose'` 全 ok；`kube-system` 下 DaemonSet 的 `numberReady` 等于 `desiredNumberScheduled`；`Pending` Pod `= 0`；`NotReady` 节点 `= 0` | 上述四项持续 15m 达标，`kubectl get nodes` 版本一致 | 任一节点 `NotReady` 超 5m；DaemonSet 就绪数缺 1 以上；准入 webhook 拒绝率突增 | 节点回退到上一版镜像并 `cordon` 该节点；控制面同上，不做降级 |
| 3 | 观察窗口：至少覆盖一次业务高峰（`>= 1` 个第 20 章 SLI 窗口） | `gateway` 5xx `<= 1%`（`5m` 窗口、连续 2 次采集，与第 15 章 `AnalysisTemplate` 同口径）；P99 `<= 800ms`；`CrashLoopBackOff = 0`；错误预算日消耗 `<= 50%` | 四项全达标，且 `hack/multicluster-verify.sh` 在 cluster-a 侧通过 | 5xx 或延迟连续 2 次触阈；预算日消耗 `> 50%`；出现版本相关告警（第 22 章） | 停在此步，**不升生产**；应用侧 `git revert` 回上一版 SHA，集群侧保持 canary 版本 |
| 4 | `cluster-b`（production）控制面 → 节点，窗口 60m + 一个业务高峰 | 同步 2、步 3，另加 `argocd app diff` 两集群为空、两个 Application 同 SHA | 两集群同版本、同 SHA、均 `Healthy`，业务 `verify.sh` 的 `/healthz` 返回 200 | 同步 2、步 3；或两集群出现版本 / SHA 不一致 | 应用侧一次 `git revert` 修两集群（30.5 链 1）；集群侧按 4→3→2→1 逆向（30.2） |
| 5 | 收尾：清理旧版本资源与弃用 API，窗口 1 周 | `kubectl get nodes` 版本齐平；`apiserver_requested_deprecated_apis` 归零；`terraform -chdir=infra plan` 无漂移 | `plan` 空 diff、弃用 API 计数为 0 | 清理后 `plan` 出现非预期 diff | `git revert` 清理 PR，恢复被删对象的声明 |

三点必须写进升级 PR 描述，否则 CL-30-02 判不合格：

1. **控制面不可降级**。Kubernetes 不支持控制面版本回退，步 1、步 2 的「回滚」只能写成「停止推进 + 从 etcd 快照重建控制面」，步 4 之后才有「退回上一版节点」这种常规动作。把「回滚 = 降级」写进方案，等于给值班同学一个做不到的指令 [R-30-6]。
2. **观察窗口按业务高峰定，不按小时数定**。凌晨升级、两小时后看「没有告警」就推进，等于用最低负载时段给最高负载时段背书；窗口必须覆盖至少一个第 20 章的 SLI 窗口。
3. **阈值只有一处**。步 3、步 4 的 5xx 与延迟必须与第 15 章 `AnalysisTemplate`、第 22 章告警用同一组数，否则「升级时 1% 算正常、发布时 1% 算故障」，同一份数据两套结论。

### 30.2.2 hub–spoke 拓扑与集群注册：凭证怎么进 hub、新集群怎么被发现

30.4 的 `ApplicationSet` 把两个 destination 的 `server` 写死在 List 生成器里。两个集群时这是最诚实的写法——显式、可审计、review 一眼看全；集群数涨到三五个之后它暴露两个问题：每接一个新集群都要改一次 ApplicationSet（改的还是平台仓库，研发重新排队），而且「Argo CD 怎么拿到 spoke 的凭证」完全没有约定。后者恰是公理 9（密钥不入 Git，见第 3、4 章）在多集群最容易破的口子：最常见的事故不是凭证泄露，而是有人图省事把 kubeconfig 直接提交进 GitOps 仓库。

本书拓扑固定为 hub–spoke：**hub = 管理集群**（30.3 边界结论表里承载 Argo CD 2.x 与 Cluster API 1.x 的那个），**spoke = cluster-a / cluster-b 等工作集群**。hub 只跑控制面组件与 ApplicationSet 声明；spoke 上不装任何 Argo CD 组件、不持有 hub 的任何凭据。信任方向只有一条：hub → spoke。这条约束的价值在事件响应时兑现——一个 spoke 被攻破时拿不到 hub，重建一个 spoke 也不牵连交付控制面 [R-30-5]。

**注册三件套的归属**。清单、凭证、发现规则三者生命周期不同，不能捆在同一个地方：

| 关注点 | 归属 | 做法 | 为什么 |
|---|---|---|---|
| 哪些集群存在 | Git：`docs/cluster-inventory.md`（30.3.1 阶段 0 产物） | 每集群一行：名称、tier、版本、owner、注册日期 | 无敏感信息，变更走 PR 可审计 |
| hub 如何连 spoke | apply 到 hub `argocd` 命名空间的 Secret | 由注册流水线注入，内容取自供应模块输出（30.3.2 第 5 步） | kubeconfig 含集群级凭据，属公理 9 禁入 Git |
| ApplicationSet 如何发现集群 | Git：生成器 selector | cluster 生成器按 label 选集群 | 发现规则需要 review，凭证不需要 |

清单与凭证分离的关键是**生命周期不同**：清单变更走 PR（评审 + 审计），凭证轮换是运维动作（流水线日志 + 轮换窗口），两者节奏不该互相绑架。轮换频率写进 `docs/toolmap.md`；轮换只重跑注册流水线，不动任何 Git 声明——反过来，改清单也绝不触碰凭证。

```yaml
# 由注册流水线 apply 到 hub 的 argocd 命名空间，不进 Git（公理 9）。
# Terraform 1.x 模块输出 spoke kubeconfig，流水线注入后打 label 供生成器发现 [R-30-1][R-30-5]。
apiVersion: v1
kind: Secret
metadata:
  name: cluster-cluster-b
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
    order-demo.io/tier: production        # cluster 生成器与 RollingSync 分组都依赖此 label
type: Opaque
stringData:
  name: cluster-b
  server: "https://cluster-b.example.com:6443"
  config: |
    {
      "bearerToken": "<注册流水线注入的最小权限 SA 短期 token>",
      "tlsClientConfig": {
        "insecure": false,
        "caData": "<base64 编码的 CA 证书>"
      }
    }
```

三个字段是这套注册的安全底线，逐一说明取舍：

1. `bearerToken` 用**专用最小权限 ServiceAccount** 的短期 token——只授予该集群 AppProject `destinations` 白名单内命名空间的写权限（第 26 章），绝不用集群管理员 kubeconfig。spoke 侧这个 SA 的 RBAC 由 30.3.2 供应流程第 3 步一并创建，与应用命名空间同生命周期。
2. `insecure: false` 是硬性要求。关掉 CA 校验等于把「谁在跟 hub 说话」交给网络里任何一个响应者，中间人可以从这里改写整个 spoke 的声明状态。
3. `secret-type: cluster` 与 tier label 缺一不可：前者让 `argocd cluster list` 与生成器认它，后者是 30.4.1 `RollingSync` 分组的数据来源——**label 打错，生产 Application 会排进 canary 组**。这是注册环节唯一能造成错序事故的误操作，因此 label 由流水线按清单写入而非人手打。

把 30.4 的 List 生成器换成语义等价、随集群注册自动扩展的 cluster 生成器：

```yaml
  # 与 30.4 的 List 生成器二选一；切换判据见下文，切换时模板语法须一并评估
  generators:
    - clusters:
        selector:
          matchLabels:
            order-demo.io/managed-by-gitops: "true"
```

> **选 List 还是 cluster 生成器**：判据不是「哪个高级」，而是「谁有权决定新集群加入发布拓扑」。List 生成器把决定权锁在平台仓库 PR 里，三个以内集群时更显式、更可审计，本书双集群示例因此选它；cluster 生成器把决定权交给注册时打的 label，新集群注册即生成 Application，适合集群数多且持续增长的 L3 档团队。切换有两个连带动作，必须在**同一个 PR** 完成：cluster 生成器的模板参数随模板语法（`goTemplate` 开关）而变，30.4.1 已声明本书沿用 `{{var}}` 语法且「两处模板写法必须一致」，因此切换生成器必然牵动 30.4 与 30.4.1 两份清单同步改写；同时 `AppProject.destinations` 白名单（第 14 章）要预先加入新集群 server，否则生成的 Application 全部被拒。忘记第二条的失败形态是「注册很顺利、发布全被拒」——排查时先看 AppProject 事件，再查生成器 [R-30-5]。

**hub 不可用时的降级判据**要先写清楚，否则值班同学会把 hub 当生产组件过度投入，或反过来当普通组件漏备份。hub–spoke 的生存属性是：hub 宕机时，spoke 上已在运行的版本继续承载流量，应用侧零影响；失去的只有三件事——漂移纠正（`selfHeal` 与巡检都住在 hub）、新版本晋升、跨集群同步顺序。因此管理集群的可用性档位**低于** `cluster-b`，但备份要求不低：ApplicationSet、AppProject 与集群注册 Secret 都住在 hub 的 etcd 里，hub 重建时若只有 etcd 快照而没有声明来源，「哪些集群该注册、哪些白名单该有」就会变成第二重事故。本书口径是三层各自可重建：ApplicationSet / AppProject / 应用清单在 Git（随 Git 恢复）；集群 Secret 由注册流水线幂等重放（30.3.2 第 5 步）；hub 自身 etcd 定期快照（备份范式见第 16 章）。三层齐备，hub 就不是单点故障，只是单点降级；降级期间的处置口径写进 `docs/toolmap.md`——恢复 hub 优先于任何发布，降级期间两集群的任何手工修复都必须在 hub 恢复后补等价 PR（公理 5）[R-30-5]。

| 工具（主版本） | 管什么 | 谁来用 | 何时不该用 | 与 GitOps 的衔接 | 回滚方式 |

### 30.3.1 五套漂移集群 → 统一供应：一条可复制的迁移时间线

30.1 的反模式一说起来容易，做起来要回答一个更硬的问题：**已经漂了的五套集群，怎么在不叫停业务的前提下收敛成一份模板**。下面是本章给出的迁移范式，每阶段带可判定的退出判据与停手点；它是方法论而非某家公司的项目记录（合成叙事，版本与周期为教学取值）[R-30-1][R-30-3]。

起点（第 0 周盘点出的真实形态）：五套集群跑在 `1.26`–`1.30` 五个 minor 上，最旧与最新差 4 个 minor，早已超出「控制面与节点不跨一个 minor」的窗口；Kyverno 1.x 策略库分叉成三份；集群供应手段有三种形态（两套 Terraform、一套 `kubeadm` 脚本、两套云控制台点出来的）；三份 state 分别躺在两台笔记本和一个共享目录里。

| 阶段 | 周期 | 动作 | 产出 | 退出判据 | 停手点（不满足不进下一阶段） |
|---|---|---|---|---|---|
| 0 止血 | 第 1 周 | CI 加一条 job：非 `infra/` 模板路径创建集群一律拒绝；每集群登记 owner | `docs/cluster-inventory.md`：版本、插件、CRD、策略差异、责任人 | 五套集群的差异可逐行追到人 | 盘点没做完就动手迁，等于把未知搬进新模板 |
| 1 抽模块 | 第 2–3 周 | 以版本最新的那套为参照实现，抽 `modules/workload-cluster`，入参只留 `name` / `tier` / `k8s_version` / `failure_domain` | 参照集群 `terraform plan` 空 diff | 参照集群 `plan` 为空；`k8s_version` 在模块里只有一处默认值 | 模块里出现「按集群名 if/else」，说明还在复制而不是收敛 |
| 2 接管 state | 第 3–4 周 | `terraform import` 逐资源接管，state 落到 `infra/backend.tf` 的远端加密 bucket | 每集群一份 plan 报告，差异逐条标注「纳入声明」或「改回现状」 | 全部集群 `plan` 为空，或仅剩已登记的豁免项 | state 迁移后**立即轮换**曾出现在旧 state 里的凭据（公理 9，见第 4、26 章） |
| 3 逐集群收敛 | 第 5–12 周 | 一次只迁一套，先非生产后生产；每套一个 PR，附版本偏差与回滚点 | 每套集群纳入统一模块并跑通一次升级演练 | 目标集群 `plan` 空 diff + 工作负载全绿 + 演练通过 | 同周不做业务功能变更、不做版本升级，三件事不许并行 |
| 4 统一节奏 | 第 13–16 周 | 五套集群进入同一 minor，管理集群先行，按 30.2.1 的窗口与阈值推进 | 版本齐平、策略库单一来源 | `kubectl get nodes` 五套齐平、`apiserver_requested_deprecated_apis` 归零 | 任一套卡在阶段 4，其余全部停下等它，不允许「先让生产跟上」 |
| 5 守栏 | 第 17 周起 | 新集群只能由模板创建；每周 `terraform plan` 巡检结果进频道 | 漂移告警常态化 | 连续四周 `plan` 无意外 diff | 巡检一旦靠人记得跑，就等于没有 |

三条迁移红线比时间表本身更重要：

- **迁移期不追新版本**。阶段 1–3 只做「声明化」，不做版本跳跃；版本统一放到阶段 4，用已经验证过的 30.2.1 时序。把「收敛」和「升级」混进一个 PR，出问题时无法判断是模板写错了还是新版本坏了 [R-30-6]。
- **每个集群保留可回退的 IaC tag**。阶段 3 的每个 PR 都是一个可 `git revert` 的点；没有这个点，模板化本身就是一次不可逆操作 [R-30-11]。
- **该重建就不要硬收敛**。若某套集群超过一半资源无法 `import` 或声明化（早期靠控制台点出来的集群常见），重建比收敛便宜；重建按 30.2 的顺序走——先在 canary 故障域建新的，业务验证后再换生产，绝不同时重建两套 [R-30-1]。

这条路径与第 14 章「Git 唯一真相」是同一件事在基础设施层的投影：阶段 0 到阶段 2 的本质，是把「集群现在长什么样」从人的记忆搬进 `plan` 的输出里。收敛完成后再回看 30.1 的反模式一，「五套集群」本身并不违规——违规的是**五套实现**。

### 30.3.2 供应全流程五步与「何时不该自管控制面」

30.3.1 讲了存量漂移集群怎么收敛，30.4 给了 `clusters.tf` 声明，中间还缺一段：从「什么都没有」到「两集群可发布」的完整链路；以及一个更根本的判据——这条链路什么时候**根本不该走**。

**完整供应流程**（每步有可判定产出，失败即停，不带病进下一步）：

| 步 | 动作 | 工具与输入 | 可判定产出 | 停手条件 |
|---|---|---|---|---|
| 1 | 供应管理集群本体、网络、IAM、state 后端 | Terraform 1.x，`apply` 只在 CI | `kubectl get nodes` 管理集群全 `Ready` | state 锁冲突；本地 `apply` 被审计捕获（30.2 本书观点） |
| 2 | 初始化 Cluster API 1.x 提供者 | `clusterctl init` | `capi-system` 等提供者命名空间 Pod 全 `Running` | CRD 安装或 webhook 起不来，立即回退该 PR |
| 3 | 从模块渲染 Cluster / MachineDeployment | `modules/workload-cluster`（30.4 `clusters.tf` 引用） | `clusterctl describe cluster cluster-a` 控制面与 worker 全 `Ready` | Machine 卡 `Provisioning` 超 30m，先查 provider 凭据与配额 |
| 4 | 配 MachineHealthCheck 并演练自愈 | 同模块 | 注入一个 `NotReady` 节点，15m 内被自动替换 | 自愈演练没通过不算交付完成——多集群的自愈是复利，单集群演练是学费 |
| 5 | 注册进 hub 并打 tier label | 注册流水线（30.2.2 Secret） | `argocd cluster list` 两集群 `Successful`，生成器发现两集群 | 凭据注入失败重试 3 次即转人工，禁止把 kubeconfig 落盘重试 |

分工口径一句话：**Terraform 1.x 管「集群外」的一切**（网络、IAM、state 后端、管理集群本体），**Cluster API 1.x 管「集群本体」**（控制面版本、节点池、Machine 生命周期）；唯一交界是第 5 步的 kubeconfig 输出。这条边界写进 `docs/toolmap.md`，同时越过边界持有两边工具权限的那类账号，是最该被 RBAC 审计盯住的（第 26 章）[R-30-1][R-30-3]。

**「何时不该自管控制面」判据表**。Cluster API 的价值随集群数量与同构程度增长，单集群时它是纯负债——把云商已经管好的控制面升级、备份、etcd 运维全部接回自己手里 [R-30-1][R-30-10]：

| 判据 | 自管（Cluster API 1.x）占优 | 托管控制面占优 |
|---|---|---|
| 集群数量与增长 | ≥ 3 且持续新增，同构复制是主诉求 | 1–2 个、长期稳定 |
| 控制面运维责任 | 平台组有带宽执行 30.2.1 的 runbook | 想把控制面升级、etcd 运维交给云商 |
| 版本与配置自由度 | 需要特定 minor 或 apiserver 配置 | 接受云商支持列表 |
| 部署形态 | 边缘、本地机房、多云 | 云商 region 内 |
| 合规审计 | 要求控制面自管、可自证 | 接受云商合规证明 |

四个「不该用托管」的典型情形，命中任一条才回到自管：**升级窗口不可协商**——云商控制面升级窗口与发布窗口长期冲突且无法约定；**版本断供**——业务依赖的版本或特性门控不在云商支持列表；**部署位置**——边缘或私有环境没有托管形态；**合规要求自管**——审计要求控制面可自证而非引用云商证明。反例同样成立（合成案例）：一个单集群团队引入 Cluster API，随后被双重卡住——provider 版本落后于目标 K8s minor 时升不了集群，升 provider 又牵动管理集群，最终版本比同园区用托管控制面的团队落后两个 minor。本书观点：**先托管、后自管**是默认顺序，「不该用托管」的判据逐条命中才升级到自管，而不是反过来 [R-30-1][R-30-10]。

```yaml
        server: "{{server}}"
        namespace: "{{namespace}}"
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
          allowEmpty: false
        syncOptions:
          - CreateNamespace=false
          - PruneLast=true
          - ApplyOutOfSyncOnly=true
        retry:
          limit: 5
          backoff:
            duration: 5s
            factor: 2
            maxDuration: 3m
      ignoreDifferences:
        - group: apps
          kind: Deployment
          jsonPointers:
            - /spec/replicas
      revisionHistoryLimit: 10
```

> 两个 Application 共用同一 `source.path`，因此一次 SHA 变更 PR 会同时收敛到两个 `destination.server`；`order-demo.io/tier` 标签供 30.2 的升级顺序与同步排序使用。`ignoreDifferences` 只排除 HPA 拥有的 `/spec/replicas`，与第 14 章 applicationset 口径一致 [R-30-5]。两个集群都必须在第 14 章 `AppProject` 的 `destinations` 白名单内，否则会被拒绝写入。

### 30.4.1 Progressive Syncs：按 `tier` 排序与失败自动停摆

上面那份 `ApplicationSet` 解决了「一份产物、两个 destination」，却没解决「谁先谁后」：两个 Application 各自带 `syncPolicy.automated`，由 Argo CD 2.x 的应用控制器**独立、并发**同步，canary 还在拉镜像时 production 可能已经全量换完。于是「一次变更」退化成「两次同时发布」，出事时也分不清是产物的问题还是生产集群自身的问题 [R-30-5]。

ApplicationSet 的 `strategy` 提供 `RollingSync`：把 Application 按标签分组为有序 step，前一组**全部 `Healthy`** 才推进下一组；前一组有不健康成员时，后续 step 停摆不再推进。这与第 15 章的渐进式交付是同一思想在两个尺度上的应用——第 15 章管「一个集群内的流量比例」，这里管「一组集群的推进顺序」，判定信号从业务指标换成了 Application 健康度。

两个前置条件不写进文档，配了也不生效：

1. `argocd-cmd-params-cm` 打开 `applicationsetcontroller.enable.progressive.syncs: "true"`，控制器需重启。
2. 被策略管理的 Application **不能**带 `syncPolicy.automated`——控制器会跳过 automated 的 Application。代价是这些 Application 失去 `selfHeal`：手工 `kubectl edit` 造成的漂移不再被自动纠正，须由第 14 章的漂移巡检（定时 `argocd app diff`）发现并告警。**这是用「顺序可控」换「自愈」，不是白拿的**，取舍必须写进 `docs/toolmap.md`。

采用本节策略时，30.4 示例里的 `syncPolicy.automated` 段应**整体删除**，不要两份清单同时存在——同一个 ApplicationSet 名只留一份定义，否则 `kubectl apply` 的结果取决于最后写入的那份。

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: order-demo-multicluster
  namespace: argocd
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  goTemplate: false          # 沿用 30.4 的 {{var}} 语法，两处模板写法必须一致
  generators:
    - list:
        elements:
          - env: prod
            namespace: order-demo-prod
            cluster: cluster-a
            tier: canary
            server: "https://cluster-a.example.com:6443"
          - env: prod
            namespace: order-demo-prod
            cluster: cluster-b
            tier: production
            server: "https://cluster-b.example.com:6443"
  strategy:
    type: RollingSync
    rollingSync:
      steps:
        - matchExpressions:
            - key: order-demo.io/tier
              operator: In
              values:
                - canary
        - matchExpressions:
            - key: order-demo.io/tier
              operator: In
              values:
                - production
  template:
    metadata:
      name: "order-demo-{{env}}-{{cluster}}"
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/managed-by: argocd
        order-demo.io/tier: "{{tier}}"
    spec:
      project: order-demo
      source:
        repoURL: "https://git.example.com/order-demo/gitops.git"
        targetRevision: main
        path: "gitops/rendered/{{env}}"
      destination:
        server: "{{server}}"
        namespace: "{{namespace}}"
      syncPolicy:
        # 关键：不写 automated。Progressive Syncs 由 ApplicationSet 控制器决定何时同步，
        # automated 的 Application 会被跳过；代价是失去 selfHeal，由第 14 章漂移巡检补位。
        syncOptions:
          - CreateNamespace=false
          - PruneLast=true
          - ApplyOutOfSyncOnly=true
        retry:
          limit: 5
          backoff:
            duration: 5s
            factor: 2
            maxDuration: 3m
      ignoreDifferences:
        - group: apps
          kind: Deployment
          jsonPointers:
            - /spec/replicas
```

**「故障自动停摆」停在哪、谁负责恢复**，是这套配置最容易被误解的地方：`RollingSync` 只保证「不继续往前推」，**没有任何自动回滚**。canary 变成 `Degraded` 时，production 的 step 不会被触发，集群停在「新版本只在 canary」的状态，直到有人处理。这与第 15 章 Rollout 的 `Analysis` 判定失败后自动 `abort` 是两回事：第 15 章的自动回滚发生在**集群内**，这里的停摆发生在**集群之间**，后者必须由一条流水线或一位值班同学接上，否则只是「卡住」。

```bash
# 1) 特性开关是否真的生效（输出 true 才有意义）
kubectl -n argocd get cm argocd-cmd-params-cm \
  -o jsonpath='{.data.applicationsetcontroller\.enable\.progressive\.syncs}{"\n"}'

# 2) 当前停在哪一步：canary 先动，production 在它 Healthy 之前应保持旧 SHA
argocd app list -l order-demo.io/tier=canary -o wide
argocd app list -l order-demo.io/tier=production -o wide

# 3) 停摆现场取证：ApplicationSet 状态与最近的同步操作
kubectl -n argocd describe applicationset order-demo-multicluster | tail -20
argocd app get order-demo-prod-cluster-a --show-operation

# 4) 处置：canary 坏 → 修产物或回滚，绝不「先让生产跟上」
git revert <晋升 PR 的 merge commit> && git push origin main
argocd app sync --prune order-demo-prod-cluster-a
```

通过标准：canary 的 `Synced` / `Healthy` 时间早于 production，两者最终 `image` 字段相同；向 canary 注入故障（口径见第 23 章）后，production **保持**上一版 SHA 且无同步操作记录。若两个 Application 几乎同时开始同步，先查第 1 条命令——九成是特性开关没开或 `automated` 还留着。

两层门禁都得有，缺一层就漏一类事故：`RollingSync` 的「Healthy」只表示**资源就绪**（Deployment 副本够了、Pod 没崩），不表示**用户没受影响**；所以 canary 集群内部仍必须跑第 15 章的 `AnalysisTemplate`，把 5xx 与延迟判进去。否则第一道门禁放行的是「Pod 起来了」，不是「业务没坏」——这正是第 15 章「三者缺一，就只是手动分批」在多集群尺度上的重述。

### 30.4.2 黄金路径的治理：模板怎么演进、怎么不僵化

30.4 的骨架解决「新建服务默认就对」，没有回答两个必然随时间出现的问题：skeleton 本身怎么演进；一年前用旧骨架创建的存量服务怎么不掉队。模板僵化的失败形态是：黄金路径变成「生成那一刻的快照」——平台模板持续迭代，存量服务永远停在旧护栏上；多集群环境下更糟，同一服务在两集群可能连骨架版本都不一致，30.1 反模式一「五套集群各自漂移」在服务维度重演。判僵化的尺子就是 30.2 那一把：**「不用平台能不能做错」对存量服务是否仍然成立**——护栏只对新建服务生效，说明护栏只活在模板里，没进策略 [R-30-4][R-30-8][R-30-9]。

四个治理机制，缺一个就留一个僵化入口：

| 机制 | 解决什么 | 做法 | 何时不该用 |
|---|---|---|---|
| skeleton 版本化 | 演进不破坏存量 | `skeleton/v1/`、`skeleton/v2/` 并存，模板参数 `skeleton_version` 默认最新；v2 的每次变更走 PR 并跑 30.4 骨架校验 | 服务数 < 10 时一套 skeleton 直接改，版本化是过早抽象 |
| 策略层兜底 | 存量服务不被淘汰出最低护栏 | Kyverno 1.x 策略面向集群内**所有** Deployment，不区分由哪个骨架生成（第 25 章） | 策略兜底不能替代骨架：策略管「不许更差」，骨架管「默认就好」，互不替代 |
| 采纳度巡检 | 让僵化可见、可量化 | 每周 job 渲染「最新骨架」与「每服务现状」的 diff，产出采纳度报告进平台频道，只报告不自动改写 | 报告没人看就停掉并找回读者，而不是继续发送 |
| 弃用流程 | 旧骨架有明确终点 | v1 标记弃用日期，弃用期 ≥ 一个季度，到期后**收紧策略**使 v1 骨架过不了准入，倒逼迁移 | 没有「到期收紧」的弃用只是改名，等于没有弃用 |

两条红线与 30.3.1 的迁移红线对称。其一，**平台改模板与业务改代码不并行**：模板大版本升级窗口内不叠加策略收紧，出问题时才分得清是骨架坏了还是策略误伤——这是「收敛与升级不混进一个 PR」在平台层的重述 [R-30-11]。其二，**不要做「自动重写存量服务为新骨架」的工具**：诱惑是把治理变成大规模自动化变更，但 diff 工具一旦误判——存量服务对骨架做过合理定制是常态——一次重写就毁掉一批服务。采纳度报告给可见性、策略收紧给截止日期：迁移节奏归服务 owner，最低护栏归平台，两边各拿各的责任 [R-30-10]。

```bash

kustomize build gitops/rendered/prod \
  | kyverno apply platform/policies/ --detailed-results
# 通过标准：弃用骨架缺失的每个护栏字段各命中一条 deny；非弃用骨架服务全部 pass。
# deny 数为 0 说明「到期收紧」没配，弃用流程是空的。
```

治理节奏收口在 `docs/toolmap.md`：skeleton 当前版本、各版本存量服务数、下次策略收紧日期，三行常驻——平台组换人之后，这三行就是黄金路径「还活着」的全部证据。

还有一个 30.4 模板本身没有回答的衔接问题：**模板产出的新仓库如何进入本节的多集群发布拓扑**。Backstage 的 `publish` 步骤只创建了仓库，若接线靠「事后有人手工把它加进 ApplicationSet」，黄金路径就绕过了 30.4.1 的顺序控制——新服务可能直接全量进两集群。本书口径：模板的 `publish` 之后追加一个平台流水线步骤，按 `catalog-info.yaml` 里的 owner 与 tier 申报，把新服务登记进对应 AppProject 的 `destinations` 白名单与多集群 ApplicationSet 的生成范围，登记动作本身是一个可 review 的 PR；在登记 PR 合并之前，新仓库的清单不会被任何集群同步。这样「自助创建」与「受控接入」各走各的门：创建零排队，接入走评审——黄金路径不会因为速度快而变成旁路 [R-30-4][R-30-5]。

## 30.5 验证与回滚（回滚方案先于发布方案）

**验证命令**（仓库根目录，需 `argocd` / `kubectl` / `terraform` / `kustomize` / `kubeconform`，版本见附录 A）：

```bash
chmod +x hack/multicluster-verify.sh

# 1) 一次变更：只改渲染产物里的 image tag（沿用第 14 章 hack/render.sh）
./hack/render.sh prod 1a2b3c4

argocd app list -o wide

# 3) IaC 侧：state 远端、plan 无漂移
terraform -chdir=infra init
terraform -chdir=infra plan

# 4) 黄金路径：用模板新建一个服务，检查骨架自带护栏
cat platform/golden-path/template.yaml

```

|---|---|
| 两集群同步成功 | `argocd app list` 出现 `...-cluster-a` 与 `...-cluster-b` 两份 Application，均为 `Synced` / `Healthy` [R-30-5] |
| 产物一致 | `hack/multicluster-verify.sh` 显示两集群 `image` 字段完全相同、无 `latest`（CL-G-02） |
| 零漂移 | 两集群 `argocd app diff` 均为空，`terraform plan` 无变更 [R-30-3] |
| state 远端加密 | `git ls-files '*.tfstate'` 无命中，`infra/backend.tf` 含 `encrypt = true` 与状态锁 [R-30-3] |
| 升级顺序成文 | 30.2 五步顺序与逆向顺序已写进集群升级 PR 描述（CL-30-02） |
| 黄金路径自带护栏 | 模板骨架含 30.2 护栏表七项，CI 校验通过，无 `cluster-admin` [R-30-4][R-30-7] |
| 回滚方案 | 双集群 `git revert` 演练已在 staging 跑过（CL-G-07） |

**回滚命令 / 步骤**。应用侧与集群供应侧分开，且**一次 `git revert` 同时修两集群**——这正是「同一真相源」的红利 [R-30-5][R-30-11]：

```bash
# 链 1：应用变更回滚（一次 revert 同时作用于两个 Application）
git revert <晋升 PR 的 merge commit>
git push origin main
argocd app sync --prune order-demo-prod-cluster-a
argocd app sync --prune order-demo-prod-cluster-b
argocd app wait order-demo-prod-cluster-a --health --timeout 120s
argocd app wait order-demo-prod-cluster-b --health --timeout 120s

# 链 2：集群供应侧回退 IaC 版本，按 30.2 顺序逆向执行
#   逆向 = 先生产集群 b → 再 canary 集群 a → 最后管理集群；控制面先于节点
git revert <集群升级 PR 的 merge commit>
terraform -chdir=infra plan
terraform -chdir=infra apply

# 链 3：若只回退某一个集群的发布（不回退 Git 真相源），
#   仅允许作为有有效期、有责任人的冻结窗口，且窗口结束必须补等价 PR（见第 14 章）
```

> **为什么不同时 `apply` 到两个集群却说「一次变更」**：变更入口（Git PR）只有一个，同步顺序由 `tier` 控制；这与「两个入口、两份清单」有本质区别。生产变更必须回到 Git（全书公理 5，见第 3 章），任何 `kubectl --context cluster-b set image` 都会被第 14 章的 `selfHeal` 纠正并写进审计。

**回滚验证**：

```bash
./hack/multicluster-verify.sh
kubectl --context cluster-a -n order-demo-prod get deploy gateway -o jsonpath='{..image}{"\n"}'
kubectl --context cluster-b -n order-demo-prod get deploy gateway -o jsonpath='{..image}{"\n"}'
argocd app diff order-demo-prod-cluster-a
argocd app diff order-demo-prod-cluster-b
terraform -chdir=infra plan
./hack/verify.sh
```

通过标准：两集群 `image` 都回到上一版 `git-<sha7>`、两集群 `app diff` 为空、`terraform plan` 无漂移、业务 `verify.sh` 的 `/healthz` 为 200。**双集群 `git revert` 回退没在 staging 演练过，就不允许把多集群拓扑带进生产**（CL-G-07）。
