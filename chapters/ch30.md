## 30.1 问题与反模式：集群从 1 个变 5 个，前面的做法怎么不失控

第 4 章把边界划在三套命名空间，第 14 章用 Argo CD 2.x 让「一次 PR 同步一个集群」成立。团队与集群数量涨上来之后，这两个前提都会被撑破：五个团队、五个集群、五套流水线，前面所有关于「唯一真相」的纪律会在复制粘贴里悄悄失效。

**合成案例**（教学合成，非真实事件）：某团队从单集群扩到五套。做法一是**为每个团队复制一套集群与流水线**，半年后五套集群的 K8s 版本差了两个 minor、Kyverno 1.x 策略库各改各的，一次通用漏洞修复要在五个地方分别发版；做法二是平台方**把一切包办并强制审批**，研发新建一个服务要排三天队，于是有人偷偷把 `kubectl apply` 塞进自己的 CI，旁路就此滋生；做法三是**`terraform apply` 在本地随手跑、state 落在笔记本**，某次误操作把 cluster-b 的节点池缩到 0，而 Git 里没有任何对应声明，复盘时谁也说不清集群当时该是什么样 [R-30-1][R-30-3][R-30-8][R-30-12]。

三个反模式，按「现象 → 根因 → 本章替代做法」：

**反模式一：为每个团队复制一套集群与流水线。** 现象是升级与策略各自漂移、同一修复发五遍；根因是把「多团队」直接等价于「多套独立实现」，没有区分「故障域要隔离」与「实现要统一」。替代做法是用 Cluster API 1.x / Terraform 1.x **集中供应**集群、以标准化模板生成，差异只留在「故障域 / 合规 / 租户」三个维度 [R-30-1][R-30-12]。

**反模式二：平台方把一切包办并强制审批。** 现象是研发排队、旁路滋生、护栏形同虚设；根因是把「平台工程」理解成审批关卡，而不是给研发铺一条**默认就对**的路。替代做法是「黄金路径」：模板产出的骨架自带非 root、SHA 标签、探针、资源基线、最小权限，研发填几个参数即可自助创建，平台只守护栏不守工单 [R-30-8][R-30-9]。

**反模式三：`terraform apply` 本地随手跑、state 在笔记本。** 现象是状态不一致、无审计、误操作无法回退；根因是把 state 当普通文件，而它其实是「基础设施的唯一真相」，且常含凭据明文。替代做法是**远端加密 state + PR 里的 plan/diff 审查 + 锁**，本地只 `plan` 不 `apply` [R-30-3][R-30-12]。

以上反模式的**方法论**参照 CNCF 公开案例 [R-30-12]；该来源只支撑「这类失效模式确实存在」，不证明合成案例真实发生。

## 30.2 范式与决策树：边界、顺序与一条有护栏的自助路径

**第一条判据沿用第 4 章（SP-12）**：命名空间不是安全边界；**需要凭据、配额、故障域的硬隔离时，应分集群乃至独立账号** [R-30-1]。第 4 章当时只取「三套命名空间」这一最低成本档，本章不推翻它，只是把「什么时候升级到多集群」用同一把尺子量清楚：变的不是判断标准，是团队规模与合规要求。

**集群边界划分表**（按故障域 / 合规 / 租户隔离，不按团队名切）：

| 划分依据 | 单集群多命名空间 | 多集群（本章） | 独立账号 / 订阅 |
|---|---|---|---|
| 故障域 | 共享控制面，控制面故障全受影响 | 每集群独立控制面 | 完全独立 |
| 凭据 / 合规 | 需额外 RBAC 与独立 Secret | 每集群独立凭据 | 独立审计与账单 |
| 租户隔离 | 弱（仅组织 / 配额） | 中（集群级） | 最强 |
| 相对成本档位 | 最低 | 中 | 最高 |
| 何时不该用 | 需要硬故障域或合规审计时 | 单团队单服务、预算有限时 | 不需要跨账号审计时 |

对 `order-demo` 本书取两档：`cluster-a` 为 canary 故障域、`cluster-b` 为 production 故障域，二者 K8s 版本保持同一 minor，凭据独立注入，用同一份模块供应 [R-30-1]。

**双集群升级顺序**（按 Kubernetes 版本偏差策略，控制面与节点偏差不得跨越一个 minor）[R-30-6]：

| 顺序 | 动作 | 前置条件 | 观察点 |
|---|---|---|---|
| 1 | 升级管理集群（承载 Cluster API 1.x / Argo CD 2.x 的那个） | 版本偏差策略允许 | 控制器自身健康（见第 28 章指标表） |
| 2 | 升 `cluster-a`（canary）控制面 → 节点 | 管理集群已稳定一个同步周期 | 业务 `verify.sh` 200、无 CrashLoopBackOff |
| 3 | 观察一个完整发布窗口 | cluster-a 无版本相关告警 | 错误预算未异常消耗（见第 20 章） |
| 4 | 升 `cluster-b`（production）控制面 → 节点 | 上一步通过 | 同上 |
| 5 | 收尾：清理旧版本资源 | 两集群版本一致 | `kubectl get nodes` 版本齐平 |

降级 / 回滚按 **4→3→2→1 逆向**执行：先回退生产集群、再回退 canary，控制面先于节点；绝不先动管理集群，否则两工作集群同时失去供应与交付能力 [R-30-6]。

**一次变更同时发到两集群的范式**：沿用第 14 章的晋升模型（SP-04），把 ApplicationSet 的 List 生成器从「三环境」扩成「两集群」——**一份渲染产物、一个 PR、两个 Application、按 `tier` 顺序同步**。关键在「一次变更入口」而非「两次发布」：SHA 只在 `gitops/rendered/prod/all.yaml` 里改一次，两个 destination 由同一 `ApplicationSet` 生成，因此不会出现「cluster-a 是 git-1a2b3c4、cluster-b 还是上一版」的分裂 [R-30-5]。同步顺序用 `tier` 标签表达：canary 先健康，production 再跟上；这与第 15 章渐进式交付是同一思想，只是粒度从「流量比例」换成了「集群集合」。

**黄金路径的判据**：平台工程的产出是「默认就对的模板」，不是审批关卡。可验证形态是——用 Backstage 模板新建一个服务，产出骨架**自带**全部护栏，无需人工补 [R-30-4][R-30-7][R-30-8][R-30-9]：

| 护栏 | 模板必须自带 | 对应章 |
|---|---|---|
| 不可变镜像 + SHA 标签 | `image: ...:git-<sha7>`，无 `latest` | 3、6、12 |
| 非 root 最小镜像 | `runAsNonRoot: true`、`seccompProfile` | 6、25 |
| 探针与优雅终止 | `/healthz` / `/readyz`、`preStop`、30s 宽限 | 8 |
| 资源基线 | requests / limits 对齐 api 基线 | 17 |
| 最小权限 | 无 `cluster-admin`、不挂载多余 SA token | 26 |
| 准入默认拒绝 | `NetworkPolicy` 默认拒绝 | 19、25 |
| 变更入口 | 产出即 Git 仓库，走第 14 章 PR | 14 |

> **本书观点（本章第 3 条结论，不需要外部背书）**
>
> **主张**：平台工程的产出是**黄金路径**而非审批关卡；抽象应当**给自由但不给 root**——把安全、可观测、可回滚做成模板默认值，研发只填业务参数。
>
> **论证**：审批关卡把「做对」的成本压到每次变更，研发排队越久，越有动力绕开平台自建旁路（30.1 反模式二）。黄金路径把成本前移到「生成骨架」那一次：护栏是模板里的字段，不是评审会上的口头要求，于是「默认就对」且可被 CI 校验。这也延续了第 1 章的横切观——安全不是流水线末尾的一个阶段，而是作用于每一环的属性；平台只是把横切属性固化进模板。判断标准不是「平台管了多少」，而是「不用平台能不能做错」：能，说明护栏没进模板。
>
> **反例与适用前提**：这不等于「完全放开、不设任何门禁」。涉及生产凭据、跨集群写权限、集群级资源的操作仍要 CODEOWNERS 审批（见第 14 章）；护栏式抽象管的是「高频、低风险、模式化」的创建动作。前提是团队规模已到需要自助（第 5 章警戒线里的 L3 档）、且平台方能维护模板与策略库；20 人团队用几条 CI 检查 + 一份清单更合适。跳过此步的典型代价是「平台变成工单系统」。

> **本书观点（本章第 4 条结论，不需要外部背书）**
>
> **主张**：**state 必须远端加密存储并做 plan/diff 审查**；把它当普通文件处理，是多集群事故的高频来源。生产 `terraform apply` 只允许发生在 CI 的受控流水线里，本地只 `plan`。
>
> **论证**：state 是基础设施的唯一真相，既记录「现在该是什么样」，也可能含凭据明文。本地随手 `apply` 会在不产生 commit 的情况下改变集群，此后任何发布、回滚、复盘都失去确定基线——这与第 14 章「Git 唯一真相」是同一条纪律在基础设施层的投影，也是公理 5、9 的衍生护栏（见第 3、4 章）。远端加密 + 状态锁 + PR 里的 plan/diff 审查，把「谁在何时把 state 改成了什么」变成可审计、可 `git revert` 的记录。L1 只支撑 state 的语义与后端配置，主张部分不引用外部背书 [R-30-3][R-30-11]。
>
> **反例与适用前提**：这不等于「任何 Terraform 操作都不能在本地跑」。本地一次性实验集群、明确不涉及共享 state 的沙箱可以 `apply`；前提是 state 不指向任何共享后端、且对象是一次性环境。常态下任何指向生产 state 的本地 `apply` 都被禁止。

**决策树**（判断当前该停在单集群还是升级）：

```
是否需要凭据 / 配额 / 故障域的硬隔离，或有合规审计要求？  否 → 停在第 4 章三套命名空间
        │ 是
是否有平台组能维护标准化模板与策略库？                    否 → 先补平台能力，不复制集群
        │ 是
多个集群是否由同一份 IaC 模块供应、同一 GitOps 入口发布？   否 → 集中供应 + 一份 ApplicationSet，停
        │ 是
一次变更能否在两个集群产生同一 SHA 且可一起回退？          否 → 回 30.4 检查双集群生成器
        │ 是
state 是否远端加密、plan 是否进 PR、升级顺序是否成文？      否 → 补护栏，不许升级生产集群
        │ 是
→ 多集群拓扑成立；黄金路径按 30.4 模板开放自助
```

## 30.3 工具选型：IaC / 平台工具分工表

按 `book/decisions.md` 与第 4 章固定值：**集群供应沿用 Terraform 1.x（state）+ Cluster API 1.x（集群声明）**，GitOps 引擎仍是 Argo CD 2.x、配置打包仍是 Kustomize 5.x overlay、策略仍是 Kyverno 1.x、流量层仍是 Gateway API + Envoy Gateway、密钥仍是 ESO。Crossplane / Backstage / Score 只在分工表里作对比或作为平台层组件，**不另起一套集群供应实现**（D-08）。工具首次出现带主版本，小版本锁附录 A。

| 工具（主版本） | 管什么 | 谁来用 | 何时不该用 | 与 GitOps 的衔接 | 回滚方式 |
|---|---|---|---|---|---|
| **Cluster API 1.x（本章示例实现之一）** | 集群生命周期声明（控制面 / 节点 / 版本） | 平台方 | 单集群实验、无需声明式供应时 [R-30-1] | 清单进 `infra/`，由第 14 章控制器同步 | IaC 版本回退 + 按 30.2 顺序逆向 |
| **Terraform 1.x（本章示例实现之一）** | 基础设施与远端 state、plan/diff | 平台方 | 集群完全托管、无需自管基础设施时 [R-30-3] | `plan` 输出进 PR，`apply` 只走 CI | `git revert` + `terraform apply` 回退 |
| Crossplane 1.x（仅对比） | 把云资源抽象成 K8s CR | 平台方 | 已用 Terraform 1.x 管住基础设施、不愿再引入一批 CRD 时 [R-30-2] | 可与 Argo CD 2.x 收敛同一批 CR | 删 XRD / Composition → 清 CR |
| **Backstage（本章示例实现之一）** | 开发者门户与黄金路径模板 [R-30-4] | 研发自助 | 团队 < 10 人、创建动作低频时 | 模板产出即 Git 仓库，走 PR | 停用模板 → 归档已建仓库 |
| Score（本章示例实现之一） | 平台无关的工作负载规范 [R-30-7] | 研发 | 已深度绑定单一平台清单、无需可移植描述时 | 由 Score 实现翻译成 K8s 清单再进 Git | 回退到上一版 Score 文件 |
| Argo CD 2.x（唯一 GitOps 实现） | 多集群持续收敛 [R-30-5] | 平台方 | 还没有判断清单对错的标准之前（第 5 章） | ApplicationSet 一次生成两集群 Application | `git revert` + `app sync --prune` |

**集群边界划分结论表**（把 30.2 判据落到 `order-demo`）：

| 集群 | 角色 | 故障域 | 凭据边界 | 升级顺序 | 何时不该用 |
|---|---|---|---|---|---|
| 管理集群 | 承载 Cluster API 1.x / Argo CD 2.x | 独立 | 平台专用 | 第 1 位 | 与工作负载混部时 |
| `cluster-a` | canary | `region-a` | 独立注入 | 第 2 位 | 不需要灰度升级顺序时 |
| `cluster-b` | production | `region-b` | 独立注入 | 第 4 位 | 与 canary 共享故障域时 |

**最小接入 diff**：

```diff
+ infra/backend.tf                          # 远端加密 state + 状态锁（沿用第 4 章同一 bucket）
+ infra/clusters.tf                         # 双集群声明，同一模块、同一 K8s 版本
+ gitops/applicationset-multicluster.yaml   # 一次变更生成两集群 Application
+ platform/golden-path/template.yaml        # Backstage 黄金路径模板
+ platform/golden-path/score.yaml           # Score 工作负载规范
+ hack/multicluster-verify.sh               # 双集群一致性验证
~ docs/toolmap.md                           # 第 7 层补多集群与平台组件、责任人
~ gitops/appproject.yaml                    # destinations 增加两集群 server（第 14 章边界延伸）
```

**升级 / 回滚路径**：集群供应侧按 30.2 五步顺序、每步一个 PR，先 `terraform plan` 进 PR 审查再 `apply`；应用侧一次 SHA 变更 PR 同时生成两集群 Application，回滚一次 `git revert` 同时修两边。控制器与策略版本升级同样先 canary 集群、观察一个窗口、再 production 集群 [R-30-11]。

## 30.4 落地配置（完整可应用文件，Kubernetes 1.32+ / Argo CD 2.x / Terraform 1.x）

> 应用侧字段沿用 `book/case-evolution.md` 契约：命名空间 `order-demo-prod`、镜像 `registry.example.com/order-demo/gateway:git-<sha7>`、Service `gateway` 端口 8080、`app.kubernetes.io/managed-by: argocd`（第 14 章起）、公共标签与探针路径不变。`server` / `repoURL` / `repoUrl` 均为示例占位地址，非引用来源链接。

**`infra/backend.tf`**（Terraform 1.x 远端加密 state + 状态锁）[R-30-3]：

```hcl
# 与第 4 章 gitops/bootstrap/backend.tf 指向同一远端加密 bucket，
# key 区分「集群供应」与「bootstrap」，不新建第二套 state 后端。
terraform {
  backend "s3" {
    bucket         = "order-demo-tfstate"
    key            = "order-demo/multicluster.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "order-demo-tfstate-lock"
  }
}
```

**`infra/clusters.tf`**（双集群声明，同一模块、同一 K8s 版本）[R-30-1]：

```hcl
terraform {
  required_version = ">= 1.5, < 2.0"
}

# 两个工作负载集群的差异只有故障域与 tier；版本、模块、策略保持一致，
# 避免 30.1 反模式一里「五套集群各自漂移」。provider 与模块实现锁附录 A。
module "cluster_a" {
  source         = "./modules/workload-cluster"
  name           = "cluster-a"
  tier           = "canary"
  k8s_version    = "1.32.0"
  failure_domain = "region-a"
}

module "cluster_b" {
  source         = "./modules/workload-cluster"
  name           = "cluster-b"
  tier           = "production"
  k8s_version    = "1.32.0"
  failure_domain = "region-b"
}

output "cluster_endpoints" {
  value = {
    cluster-a = module.cluster_a.endpoint
    cluster-b = module.cluster_b.endpoint
  }
}
```

**`gitops/applicationset-multicluster.yaml`**（Argo CD 2.x，核心：一次变更发到两集群）[R-30-5]：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: order-demo-multicluster
  namespace: argocd
  labels:
    app.kubernetes.io/name: order-demo
    app.kubernetes.io/managed-by: argocd
spec:
  generators:
    - list:
        elements:
          - env: prod
            namespace: order-demo-prod
            cluster: cluster-a
            tier: canary
            server: "https://cluster-a.example.com:6443"
          - env: prod
            namespace: order-demo-prod
            cluster: cluster-b
            tier: production
            server: "https://cluster-b.example.com:6443"
  template:
    metadata:
      name: "order-demo-{{env}}-{{cluster}}"
      labels:
        app.kubernetes.io/name: order-demo
        app.kubernetes.io/managed-by: argocd
        order-demo.io/tier: "{{tier}}"
    spec:
      project: order-demo
      source:
        repoURL: "https://git.example.com/order-demo/gitops.git"
        targetRevision: main
        path: "gitops/rendered/{{env}}"
        directory:
          recurse: false
      destination:
        server: "{{server}}"
        namespace: "{{namespace}}"
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
          allowEmpty: false
        syncOptions:
          - CreateNamespace=false
          - PruneLast=true
          - ApplyOutOfSyncOnly=true
        retry:
          limit: 5
          backoff:
            duration: 5s
            factor: 2
            maxDuration: 3m
      ignoreDifferences:
        - group: apps
          kind: Deployment
          jsonPointers:
            - /spec/replicas
      revisionHistoryLimit: 10
```

> 两个 Application 共用同一 `source.path`，因此一次 SHA 变更 PR 会同时收敛到两个 `destination.server`；`order-demo.io/tier` 标签供 30.2 的升级顺序与同步排序使用。`ignoreDifferences` 只排除 HPA 拥有的 `/spec/replicas`，与第 14 章 applicationset 口径一致 [R-30-5]。两个集群都必须在第 14 章 `AppProject` 的 `destinations` 白名单内，否则会被拒绝写入。

**`hack/multicluster-verify.sh`**（双集群一致性验证，完整可执行）：

```bash
#!/usr/bin/env bash
set -euo pipefail
# 验证：一次变更、两集群同一 SHA、零漂移、state 远端加密。
APP_A=order-demo-prod-cluster-a
APP_B=order-demo-prod-cluster-b
CTX_A=cluster-a
CTX_B=cluster-b
NS=order-demo-prod

echo "== 1) 两个 Application 由同一 ApplicationSet 生成 =="
argocd app list -o wide | grep -E "${APP_A}|${APP_B}"

echo "== 2) 两集群 image 字段必须相同 =="
IMG_A="$(kubectl --context "${CTX_A}" -n "${NS}" get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
IMG_B="$(kubectl --context "${CTX_B}" -n "${NS}" get deploy gateway \
  -o jsonpath='{.spec.template.spec.containers[0].image}')"
echo "cluster-a: ${IMG_A}"
echo "cluster-b: ${IMG_B}"
[ "${IMG_A}" = "${IMG_B}" ] || { echo "两集群产物不一致" >&2; exit 1; }
! grep -qE ':latest' <<<"${IMG_A}"

echo "== 3) 两集群均 Healthy，且 app diff 为空 =="
for APP in "${APP_A}" "${APP_B}"; do
  argocd app wait "${APP}" --health --timeout 120s
  DIFF="$(argocd app diff "${APP}")"
  [ -z "${DIFF}" ] || { echo "${APP} 存在漂移: ${DIFF}" >&2; exit 1; }
done

echo "== 4) state 无本地副本、远端加密、plan 无漂移 =="
if git ls-files '*.tfstate' | grep -q .; then
  echo "state 文件入 Git，禁止" >&2; exit 1
fi
grep -q 'encrypt = true' infra/backend.tf
terraform -chdir=infra plan -detailed-exitcode >/dev/null
echo "terraform plan 无漂移"

echo "双集群验证通过：一次变更、两集群同一 SHA、零漂移。"
```

**回滚命令 / 步骤**。应用侧与集群供应侧分开，且**一次 `git revert` 同时修两集群**——这正是「同一真相源」的红利 [R-30-5][R-30-11]：

```bash
# 链 1：应用变更回滚（一次 revert 同时作用于两个 Application）
git revert <晋升 PR 的 merge commit>
git push origin main
argocd app sync --prune order-demo-prod-cluster-a
argocd app sync --prune order-demo-prod-cluster-b
argocd app wait order-demo-prod-cluster-a --health --timeout 120s
argocd app wait order-demo-prod-cluster-b --health --timeout 120s

# 链 2：集群供应侧回退 IaC 版本，按 30.2 顺序逆向执行
#   逆向 = 先生产集群 b → 再 canary 集群 a → 最后管理集群；控制面先于节点
git revert <集群升级 PR 的 merge commit>
terraform -chdir=infra plan
terraform -chdir=infra apply

# 链 3：若只回退某一个集群的发布（不回退 Git 真相源），
#   仅允许作为有有效期、有责任人的冻结窗口，且窗口结束必须补等价 PR（见第 14 章）
```

> **为什么不同时 `apply` 到两个集群却说「一次变更」**：变更入口（Git PR）只有一个，同步顺序由 `tier` 控制；这与「两个入口、两份清单」有本质区别。生产变更必须回到 Git（全书公理 5，见第 3 章），任何 `kubectl --context cluster-b set image` 都会被第 14 章的 `selfHeal` 纠正并写进审计。

**回滚验证**：

```bash
./hack/multicluster-verify.sh
kubectl --context cluster-a -n order-demo-prod get deploy gateway -o jsonpath='{..image}{"\n"}'
kubectl --context cluster-b -n order-demo-prod get deploy gateway -o jsonpath='{..image}{"\n"}'
argocd app diff order-demo-prod-cluster-a
argocd app diff order-demo-prod-cluster-b
terraform -chdir=infra plan
./hack/verify.sh
```

通过标准：两集群 `image` 都回到上一版 `git-<sha7>`、两集群 `app diff` 为空、`terraform plan` 无漂移、业务 `verify.sh` 的 `/healthz` 为 200。**双集群 `git revert` 回退没在 staging 演练过，就不允许把多集群拓扑带进生产**（CL-G-07）。
