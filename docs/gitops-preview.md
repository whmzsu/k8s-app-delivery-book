# 下一站：变更怎么进集群

本章的流水线止步于「把带 SHA 的制品推进仓库、把引用写进 Git」。它**不**执行
`kubectl apply` 到 staging 或 prod，也不读取生产 kubeconfig。原因是：一旦 CI
能直接改集群，集群里就同时存在「Git 写的」和「CI 写的」两个真相来源，配置被
人手工改过、集群和 Git 对不上的现象（漂移，白话：集群实际状态和 Git 里写的
不一致，详见第 14 章）就无法收敛。

从第 14 章起，由控制器持续比对 Git 声明与集群实际状态并自动收敛：合并一个
只改镜像 SHA 的 PR，集群自己同步；有人在 prod 上手改副本数，会被改回去。
本章产出的 `git-<sha7>` 制品引用，正是这条链路上的输入。

因此本仓库的两条硬规则：
1. 生产变更只允许走 Git PR，CI 不持有生产写权限（见第 3 章公理 5）。
2. 应急止血也必须先提交 PR，再让控制器同步，而不是 `kubectl edit`（见第 14 章）。
