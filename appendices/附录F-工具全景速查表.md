## F.8 按团队规模的最小可行组合（第 5 章的「过度工程警戒线」）

| 团队规模 | 建议的最小工具集 | 明确「先不上」的 |
|---|---|---|
| ≤ 10 人 / 单集群 | Git + 一次构建 + Kustomize overlay + 手工 PR 审核 + Prometheus/日志托管 + 基本告警与 runbook | GitOps 控制器、渐进式交付、Operator、服务网格、平台门户 |
| 10–50 人 / 多环境 | 上面 + Argo CD + kind 版本矩阵 CI + Kyverno + OTel + SLO/错误预算 + 回滚演练 | 自研 Operator、双 GitOps 引擎、多集群容灾编排 |
| 50–200 人 / 多集群 | 上面 + 渐进式交付 + 外部密钥管理 + 多集群发布 + 内部平台黄金路径 | 同时维护 Argo CD + Flux + Kargo + Crossplane 全套（除非有专职平台团队） |
| 平台团队 | 上面 + 按第 27 章决策树评估是否自研控制器 | 在「能用现成 Operator」时自研（见第 29 章评估表） |

> **本书观点**：工具数量不是成熟度。判断标准只有一条——**这一层工具是否消掉了一个已经发生过、且能被验证的事故失效点**。按 ROI 排序的改造路线见第 31 章。
