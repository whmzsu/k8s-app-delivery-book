# 附录 H　全书坐标系速查卡

> 第 1 章 1.3 提出，第 31 章用同一张图做首尾闭环。可单独打印，读书时放在手边；每章章首的「坐标标签」就是这张卡的坐标。

## H.1 一主线 + 两横切 + 一演进轴 + 地基篇

```
                    【地基篇 1–5】原则 / 边界 / 工具方法论（不占主线环节，撑住整条链）
                                  │
  定义 → 校验 → 打包 → 晋升 → 发布 → 运行 → 观测 → 响应      ← 一主线：一次变更的旅程
   6–9   11     10     14     13/15   17–19   20–21   22–23
                                  │
   ┌──────────── 横切 A：安全 · 策略 · 凭据（6 篇 24–26 汇总深化）────────────┐
   └──────────── 横切 B：可观测 · 可回滚 · 可审计（5 篇 20–23 汇总深化）─────┘
                                  │
   L0 手工 → L1 自动化 → L2 GitOps / 渐进式 → L3 平台化      ← 一演进轴
```

**为什么第 5、6 篇不按流水线顺序排**：它们是横切面，作用于主线的每一个环节，而不是链路上的某一段。把安全放到第 24–26 章是「汇总深化」，不是「最后才做安全」——每章检查清单固定含 2–3 条 `CL-S-xx` 安全项就是证据。

## H.2 篇—章—环节映射

| 篇 | 章 | 在坐标系中的位置 | 学完你能……（能力进阶线） |
|---|---|---|---|
| 一 原则与地基 | 1–5 | 地基 + 全书索引 | 判断一次变更应该走哪条链路、哪些工具先别上 |
| 二 定义与打包 | 6–11 | 主线·定义 / 打包 / 校验 | 从一份 Dockerfile 出发，把应用跑通并逐层加固到可校验 |
| 三 部署与发布 | 12–16 | 主线·晋升 / 发布 | 让一次变更可重复、可晋升、可灰度、可回滚（含数据侧） |
| 四 运行时治理 | 17–19 | 主线·运行 | 让应用在高负载、节点故障与网络约束下仍稳定 |
| 五 观测与可靠性 | 20–23 | 主线·观测 / 响应 + 横切 B | 用 SLO 决定能不能发、用告警与 runbook 把故障压到最短 |
| 六 安全与供应链 | 24–26 | 横切 A 汇总深化 | 在前五篇的每个环节补上可验证的护栏，而不是最后补安全 |
| 七 扩展与平台化 | 27–31 | 演进轴 L3 | 判断要不要扩展 K8s API，并把能力沉淀成黄金路径 |

## H.3 成熟度阶梯

| 级别 | 特征 | 典型失效点 | 对应章 |
|---|---|---|---|
| L0 手工 | 手工 apply、凭经验排障、`latest` | 产物不可追溯、配置改了不生效 | 1–3 |
| L1 自动化 | SHA 标签、CI、清单校验、探针与回滚演练 | 多环境不一致、回滚没练过 | 6–13 |
| L2 GitOps / 渐进式 | Git 唯一真相、持续收敛、指标驱动放量、SLO 冻结 | 漂移、自愈误伤、告警无 runbook | 14–23 |
| L3 平台化 | 护栏内建、黄金路径、多集群、自助交付 | 抽象过度、Operator 无人维护 | 27–31 |

## H.4 章首坐标标签怎么读

格式：`位置：<主线环节/地基/横切/演进轴> ｜ 横切：<A/B/无> ｜ 成熟度 <L0–L3>`

- **横切 A**＝安全、策略、凭据；**横切 B**＝可观测、可回滚、可审计
- 示例：`位置：主线 · 发布 ｜ 横切：B 可回滚 ｜ 成熟度 L1`（第 13 章）
- 每章开头还有固定块「此刻 `order-demo` 长什么样 / 本章可验证动作 / 复现 tag」，来自附录 D

## H.5 事故钩子 → 关键章对照（第 1 章埋，第 31 章收）

| 钩子 | 失效点 | 主责章 | 补上的范式 |
|---|---|---|---|
| H1 | `latest` 被覆盖，线上不是以为的产物 | 3 | 不可变镜像 + git SHA 标签 |
| H2 | 改了配置不生效或被改回去 | 2 | 声明式终态与控制循环 |
| H3 | 滚动更新卡住，新 Pod 永不 Ready | 8 | readiness 语义、startupProbe、preStop、PDB |
| H4 | liveness 误杀引发重启级联，无人能定位 | 23 | CrashLoop 速查表与 runbook |
| H5 | 想回滚却没有方案或 schema 不兼容 | 13 | 回滚方案先行 + expand–contract（16） |
| H6 | 密钥轮换踩坑，配置与凭据混在一起 | 9 | 配置/密钥分离 + 外部注入 |
| H7 | 手工 `kubectl edit` 造成配置漂移 | 14 | Git 唯一真相 + 漂移检测与自愈 |
| H8 | 告警响了却没有 runbook | 22 | 每条告警必须可操作并指向 runbook |

> 只有这 8 个主责章写「回到第 1 章」；其余章不硬凑（9.7）。第 31 章用同一张坐标系重演整起事故，逐条对照 H1–H8。

## H.7 统一章节模板（七段）

`N.1 问题与反模式` → `N.2 范式与决策树` → `N.3 工具选型` → `N.4 落地配置` → `N.5 验证与回滚` → `N.6 上线检查清单` → `N.7 依据与延伸阅读`（之后按需写「回到第 1 章」）。横切章 24–26 精简为三段 + 依据段；专题章 1、23、31 按叙事组织。第 7 段的 `[R-XX-N]` 角标与附录 I 一一对应；「本书观点」独立标注，不混进背书列表。
