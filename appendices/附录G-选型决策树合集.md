## G.2 七张最常用的决策树（速查）

### G.2.1 工作负载（见第 7 章）

```
需要每个节点都跑一份（日志/网络/代理）？ → DaemonSet
需要稳定网络标识与有序启停、持久卷？     → StatefulSet（先评估现成 Operator，见第 29 章）
跑到完成就退出 / 按计划周期执行？          → Job / CronJob
以上都不是，且可随时被替换？               → Deployment（默认）
都不是却想直接写 Pod？                     → 停：裸 Pod 不受控制器收敛，见第 2、6 章
```

### G.2.2 探针（见第 8 章）

```
启动明显慢于常规？            → 先加 startupProbe，屏蔽启动期的 liveness
失败时「重启有帮助」吗？       → 是：liveness；否：不要配 liveness
失败时「不该接流量」吗？       → 是：readiness（摘 EndpointSlice，不重启）
依赖 DB/下游吗？              → 不要在 liveness 里查下游，否则级联重启
滚动更新要求零 5xx？          → 还要 preStop + 终止宽限 + PDB + maxUnavailable:0
```

### G.2.3 配置打包（见第 10 章）

```
同源清单、只是各环境字段不同？      → Kustomize overlay
要对外分发、参数多、需要 release？  → Helm
需要大规模程序化复用与抽象？        → CDK8s / Jsonnet（先确认有人维护 SDK）
只是改几个字段？                    → 别引模板，直接改清单
无论选哪个：必须 review 渲染产物，不能只 review 模板
```

### G.2.4 部署策略（见第 13 章）

```
schema 新旧版本能共存？          → 否：先做 expand–contract（见第 16 章），不要谈策略
节点余量够 maxSurge 吗？        → 否：先算容量账（CL-G-08）
要求秒级切换且能承担双倍容量？   → 蓝绿
要求用指标自动判定继续/回退？    → 金丝雀 / 渐进式交付（见第 15 章）
只需最稳妥、回滚代价最低？      → 滚动 + maxUnavailable:0
无论选哪个：先写并演练回滚方案（CL-G-07）
```

### G.2.5 变更入口（见第 14 章）

```
只是本地实验？                → 手工 apply 可以，但别进生产
需要可审计但不需要自动收敛？   → CI 推送 + PR 审核
需要漂移纠正与自愈？           → GitOps（Git 唯一真相）
有人还在手工改生产？           → 先收权限与审计（见第 26 章），否则自愈会被反复绕过
```

### G.2.6 SLO 与告警（见第 20、22 章）

```
指标业务可感吗？              → 否：不能做 SLI（CPU 不是 SLI）
能算出好请求 / 总请求吗？      → 是：定义 SLI；设定窗口与目标
预算快耗尽了吗？              → 是：冻结非必要发布（CL-G-10）
告警触发后值班知道做什么吗？   → 否：这条告警不该存在，先补 runbook
```

### G.2.7 要不要写 Operator（见第 27 章，全书最贵的一个决策）

```
原生资源能表达吗？             → 是：停
配置打包 / overlay 能表达吗？   → 是：停
CI 里的脚本能定时做完吗？      → 是：停
准入策略 / Webhook 能校验吗？   → 是：停
以上都不行，且有长期运行的领域状态？→ 先找现成 Operator（见第 29 章评估表）
仍没有，且有专职维护者 + CRD 版本迁移 + 降级预案？→ 才考虑自研（见第 28 章）
```

## G.3 使用说明

1. 每张决策树的**第一行判定是前提，不是选项**：前提不满足就不要往下比工具。
2. 选型结论必须同时给出「何时不该用」与「回滚方式」，否则视为未完成（第 5 章方法论）。
3. 全书只允许一个示例实现（附录 F 的 ★ 列）；矩阵里的其他工具用于说明取舍，不复刻配置。
4. 决策结果要落进对应章的检查清单，并在附录 B 的发布三段式执行卡里能查到。
