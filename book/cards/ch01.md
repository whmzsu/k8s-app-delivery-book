## 读者视角

- **读者带着什么问题来**：我会 `kubectl apply`，也读得懂 YAML，为什么团队还是频繁在发布上出事？这本书和官方文档差在哪？
- **学完你能……**：拿到一张坐标系，能指出自己团队的一次变更会在哪个环节失控、对应翻哪一章，并判断团队处在 L0–L3 哪一级。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：事故现场最小复现环境（`ch01-incident`）；`curl gateway/orders` 返回 500，读者能在输出里数出 8 个失效点。

## 一句话核心问题

**为什么「会用 kubectl」和「能把应用可靠地交付好」之间，还差一整套决策体系？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | K8s 把「部署」变成一次声明式提交，却没有替你回答「提交的对不对、坏了怎么退」；声明式终态本身不保证正确性 | L1 | Kubernetes Concepts Overview；Kubernetes Declarative Management |
| 2 | 编排系统的价值在于把运维知识固化为可收敛的期望状态，而不是提供一套更方便的手工操作界面 | L2 | Borg, Omega, and Kubernetes（Burns 等，ACM Queue 2016）；CNCF Cloud Native Definition |
| 3 | 一次变更沿「定义 → 校验 → 打包 → 晋升 → 发布 → 运行 → 观测 → 响应」前进，安全与可观测是作用于每一环的横切属性，不是流水线末尾的一个阶段 | **本书观点** | 不设背书；论证见 1.3 的篇—章—环节映射表，反例见「先上线再补监控」的常见做法 |
| 4 | 团队交付能力可粗分为 L0 手工 → L1 自动化 → L2 GitOps → L3 自助平台；工具数量不等于成熟度 | **本书观点** | 不设背书；论证与反例见 1.3 演进轴与第 5 章「过度工程警戒线」 |

## 验证与回滚

- **验证命令**：`./hack/reproduce-incident.sh`，随后 `curl -i http://localhost:8080/orders`
- **通过标准**：返回 500，且日志/事件里能定位到 H1–H8 各自对应的现象
- **回滚命令 / 步骤**：`kind delete cluster --name order-demo-incident && git checkout ch01-incident`（环境一次性，无状态需保留）
- **回滚验证**：重新执行脚本能稳定复现同一事故，保证第 31 章的重演可对照
