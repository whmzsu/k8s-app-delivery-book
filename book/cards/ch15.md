## 读者视角

- **读者带着什么问题来**：变更已经能自动进集群了，怎么做到「只放 5% 流量、指标不对自动退」？
- **学完你能……**：配好 Rollout + AnalysisTemplate，让一次发布由指标决定是否继续，并说清它和特性开关的边界。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：金丝雀 5% 流量，注入错误率后自动回退（`ch15-canary`）。

> 开头须点明：第 14 章解决变更怎么进集群，本章解决流量怎么灰度。

## 一句话核心问题

**用哪些指标、什么阈值，才敢让机器自动决定「继续放量还是回滚」？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 渐进式交付 = 流量分批 + 指标判定 + 自动回滚；三者缺一就只是「手动分批」 | L1 | Argo Rollouts 官方文档（Rollout / AnalysisTemplate）；Flagger 官方文档 |
| 2 | 判定指标必须来自 SLO 相关的用户可感信号（错误率、延迟分位），而不是 CPU 这类资源指标 | L2 | Danilo Sato《CanaryRelease》（已核验）；Google SRE Workbook《Canarying Releases》（候选待核验） |
| 3 | 特性开关控制「功能对谁可见」，渐进式交付控制「哪个版本承载流量」；两者可配合但不可互相替代 | **本书观点** | 不设背书；论证见「边界」小节，反例见把开关当发布策略的做法 |
| 4 | Analysis 的窗口、失败阈值与人工门禁要按业务风险设定；照抄示例值会让自动回滚形同虚设或频繁误触发 | **本书观点** | 不设背书；论证见「阈值设定表」，反例见第 22 章告警噪音治理 |

## 反模式（3 条）

1. 用 CPU / 内存做放量判据 → 版本有 bug 但资源正常，全量放出去 → 改用错误率与延迟分位
2. 自动回滚没设人工门禁 → 阈值抖动导致反复回滚、发布永远完不成 → 加确认步骤与冷却窗口
3. 小团队上 Rollouts + Flagger + Kargo 全套 → 维护成本超过收益 → 引用第 5 章过度工程警戒线

## 选型矩阵

**Argo Rollouts / Flagger / 原生 Deployment + 手工分批**：流量层依赖 / 指标接入 / **何时不该用** / 与第 14 章晋升链路的衔接 / 回滚方式。另含**AnalysisTemplate 阈值设定表**（指标、窗口、失败阈值、冷却、人工门禁）。

## 验证与回滚

- **验证命令**：合并新版本 PR；`kubectl -n order-demo-prod argo rollouts get rollout gateway --watch`；`./hack/inject-error-rate.sh`
- **通过标准**：先停在 5%；注入错误率后判定失败并自动回退到上一版；无人工介入
- **回滚命令 / 步骤**：自动回滚由 Rollout 执行；手动兜底 `kubectl -n order-demo-prod argo rollouts abort gateway && kubectl argo rollouts undo gateway`
- **回滚验证**：流量 100% 回到稳定版，`verify.sh` 与 `healthz` 通过
