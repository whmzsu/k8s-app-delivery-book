## 一句话核心问题

**怎样把故障处置从「靠老手记忆」变成可复现、可演练、可复盘的流程？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | runbook 必须包含症状、定位命令、止血动作、验证方法、升级路径五项，缺一不可 | L1 | Chaos Mesh / Litmus 官方文档（演练侧）；Kubernetes 故障排查相关官方文档（症状侧） |
| 2 | 事故处置的优先级是「先恢复服务、再保全现场、最后查根因」；复盘应无责且产出可跟踪的改进项 | L2 | Google SRE Book《Managing Incidents》《Postmortem Culture》（SRE Book 入口已核验）；SRE Workbook《Incident Response》（候选待核验） |
| 3 | 演练的价值在于验证 runbook 与回滚路径，不是验证系统「够不够抗揍」；没写过的 runbook 一定会在演练中暴露缺口 | L2 | Google SRE Book《Managing Incidents》；公开 postmortem（如 GitLab 2017 数据库事故，L3 候选待核验） |
| 4 | 回滚演练应纳入常规发布门禁，而不是一年一次的演习 | **本书观点** | 不设背书；论证与第 13 章回滚方案门禁呼应 |

## 反模式（3 条）

1. 出事先查根因、迟迟不回滚 → 故障时长被拉长 → 止血优先
2. runbook 只写「联系某某」 → 半夜找不到人 → 命令与判断标准前置
3. 复盘追责 → 下次没人愿意上报 → 无责复盘 + 改进项跟踪

## 选型矩阵

本章为专题章，不做工具横比。含**「症状 → 定位 → 处置」速查表**（7 类症状：Pending / CrashLoopBackOff / OOMKilled / 5xx 突增 / 证书过期 / 配置漂移 / CRD 卡 finalizer）、**runbook 模板**与**复盘模板**。可选列 Chaos Mesh / Litmus 的适用场景，但不强制矩阵。
