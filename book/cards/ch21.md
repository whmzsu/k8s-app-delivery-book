## 读者视角

- **读者带着什么问题来**：指标、日志、链路各装一套，出事时还是串不起来，问题出在哪？

## 一句话核心问题

**三大信号该怎么采集、存储与关联，才能既查得动又不被 cardinality 拖垮？**

## 反模式（3 条）

1. 把用户 ID 写进指标 label → cardinality 爆炸、Prometheus OOM → label 白名单与采集前聚合
2. 只采指标不采链路 → 跨服务问题只能靠猜 → trace_id 贯通日志与指标
3. 全量日志不采样 → 成本失控且检索变慢 → 错误与慢请求全采、正常请求按比例采样

## 验证与回滚

- **验证命令**：`curl http://localhost:8080/orders` 后按 `trace_id` 在日志/链路/指标中检索；`promtool check metrics`
- **通过标准**：同一请求在三类信号中可关联；cardinality 在阈值内；命名符合规范表
- **回滚命令 / 步骤**：`kubectl apply -k observability@<上一 tag>`；采集端应急可降采样：`kubectl -n observability rollout undo deploy/otel-collector`
- **回滚验证**：应用侧 `verify.sh` 不受影响，采集链路恢复
