## 读者视角

- **读者带着什么问题来**：配置改了要不要重建镜像？数据库密码放哪，轮换时会不会把服务搞挂？
- **学完你能……**：把配置与凭据彻底分开，用外部密钥注入完成一次不停机轮换，并留下审计痕迹。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：`order-demo-config` 设 `immutable: true`，密钥改由 ESO/CSI 注入；轮换密钥无需重建镜像（`ch09-secrets`）。

## 一句话核心问题

**哪些东西该进 ConfigMap，哪些必须走外部密钥系统，以及轮换怎样才不引发事故？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | ConfigMap 存非敏感配置，Secret 只是 base64 编码而非加密；不可变 ConfigMap 强制「改配置就换对象」，避免原地修改导致Pod 与声明不一致 | L1 | Kubernetes ConfigMap / Immutable ConfigMaps；Kubernetes Secrets |
| 2 | 生产密钥应由外部系统托管并经 ESO / CSI Driver 注入；密钥、`state`、`.env` 一律不入 Git | L1 | Kubernetes Secrets；External Secrets 官方文档；NIST SP 800-190 |
| 3 | 容器化应用的凭据处理应覆盖全生命周期：分发、轮换、吊销、审计，只做「加密存储」远远不够 | L2 | CNCF Security Whitepaper v2（正式链接待补）；SOPS 项目文档（按 10.6 映射列 L2，待核验） |
| 4 | 轮换的正确姿势是「双凭据共存 → 切流 → 作废旧凭据」，而不是原地覆盖同一个键 | **本书观点** | 不设背书；论证见轮换 runbook，反例引第 1 章 H6 事故 |

## 反模式（3 条）

1. 把 `Secret` 提交进 Git「反正只是测试环境」→ 凭据泄露且历史里洗不掉 → 外部托管 + 仓库扫描
2. 原地改同名 ConfigMap → 部分 Pod 读到新值、部分读旧值 → 用带版本后缀的不可变对象
3. 轮换时直接覆盖密钥 → 新旧 Pod 凭据不一致，瞬时全量认证失败 → 双凭据共存

## 验证与回滚

- **验证命令**：`kubectl -n order-demo-dev exec deploy/api -- env | grep DB_`；`./hack/verify.sh`；`grep -R "password" deploy/`（应无明文）
- **通过标准**：轮换期间连续请求无 5xx；仓库无凭据明文；审计日志能查到读取记录
- **回滚命令 / 步骤**：`kubectl -n order-demo-dev apply -f deploy/base/externalsecret.yaml@<上一版>`，或把 `SecretStore` 指回旧版本凭据；再 `kubectl -n order-demo-dev rollout restart deploy/api`
- **回滚验证**：api 能重新连上 db，`healthz` 为 200
