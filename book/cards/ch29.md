## 读者视角

- **读者带着什么问题来**：90% 的人不需要自己写 Operator，那现成的怎么挑？它挂了业务会不会跟着挂？
- **学完你能……**：用成熟度评估表挑一个现成 Operator，写出降级预案，并说明升级与卸载的风险点。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：CloudNativePG 成熟度评估；完成评估表并写出降级预案（`ch29-cnp`）。

## 一句话核心问题

**现成 Operator 值不值得引入，怎么评估它「靠不靠谱」以及它挂了怎么办？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 选型要看 CRD 版本升级路径、备份恢复、卸载残留、社区活跃度、是否锁死云厂，而不是只看 star 数 | L1 | CloudNativePG / Strimzi / cert-manager / external-dns / Velero 官方文档；Artifact Hub |
| 2 | 项目成熟度有可依据的分级标准；社区活跃度与治理结构决定长期可维护性 | L2 | CNCF 项目成熟度标准；Thoughtworks Technology Radar（候选待核验） |
| 3 | 必须回答「Operator 挂了业务会不会挂」：多数情况下 CR 已收敛的实例继续运行，但故障转移与升级会停摆 | **本书观点**+ L1 支撑 | 支撑：各 Operator 架构文档；主张部分显式标注，给降级预案与反例 |
| 4 | 自建 / 采购 / 托管的取舍按故障恢复能力，不按技术偏好 | **本书观点** | 不设背书；与第 16 章能力边界表呼应 |

## 反模式（3 条）

1. 只看功能清单就引入 → 升级时 CRD 版本不兼容 → 升级路径先行
2. 没做卸载演练 → finalizer 卡住、PVC 残留 → 卸载清单与检查命令
3. 把 Operator 当「装了就有人管」 → 它自身的告警与升级无人负责 → 纳入平台运维清单

## 选型矩阵

**Operator 成熟度评估表**：评估项（升级路径 / 备份恢复 / 卸载残留 / 社区活跃度 / 云厂绑定 / 自身可观测 / 降级预案）/ 权重 / 通过标准 / **何时不该用** / 回滚方式。另含**自建 vs 采购 vs 托管对比**。

## 验证与回滚

- **验证命令**：`./hack/operator-uninstall-drill.sh`；`kubectl get crd,finalizers`；停用控制器后观察业务实例是否继续服务
- **通过标准**：评估表全部有结论；卸载无残留；降级预案可执行
- **回滚命令 / 步骤**：`kubectl delete -f <CR 实例>` → 检查 finalizer → 回退 Operator 版本；业务侧按第 16 章备份恢复兜底
- **回滚验证**：CRD 无残留、业务 `verify.sh` 通过
