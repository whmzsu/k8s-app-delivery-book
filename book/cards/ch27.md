## 一句话核心问题

**什么时候真的需要扩展 K8s API，以及什么时候不该写 Operator？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | CRD 让你定义新资源类型，Operator = CRD + 协调循环；status 表达观测结果，spec 表达期望，二者不可混用 | L1 | Kubernetes Custom Resources；Operator Pattern；API Conventions |
| 2 | 协调循环必须幂等、可重入、能容忍重复事件；finalizer 用于删除前清理，卡住会导致对象无法删除 | L1 | Kubernetes API Conventions；finalizer / 删除语义文档；CRD 版本迁移与转换 webhook 文档 |
| 3 | 「什么时候不该写」比「怎么写」更重要：Helm Chart / CronJob / Admission Webhook / 外部脚本往往就够了 | L2 | CoreOS《Introducing Operators》(2016，候选待核验)；CNCF Operator 相关白皮书（候选待核验） |
| 4 | 每引入一个 CRD 都是长期负债：版本迁移、备份恢复、卸载残留、升级兼容都要有人负责 | **本书观点** | 不设背书；论证见「负债清单」，与第 5 章警戒线呼应 |

## 反模式（3 条）

1. 把一次性脚本包装成 Operator → 多一套控制器要运维 → 五选一决策树
2. reconcile 里做长耗时阻塞、把 status 当数据库 → 事件堆积、状态失真 → 幂等与短循环
3. 只定义 v1alpha1 从不规划版本迁移 → 升级时转换 webhook 仓促上阵 → 版本迁移路径先行
