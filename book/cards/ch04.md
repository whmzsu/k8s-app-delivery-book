## 读者视角

- **读者带着什么问题来**：dev、staging、prod 到底该分集群还是分命名空间？仓库目录怎么摆才不会 3 个月后失控？
- **学完你能……**：画出本团队的环境边界与仓库骨架，做到三环境只改配置、不改产物，且凭据完全隔离。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：新增 `order-demo-dev` / `staging` / `prod` 三套 overlay，`helm template` 与 overlay 渲染结果仅配置不同、镜像相同（`ch04-env`）。

## 一句话核心问题

**环境与仓库的边界怎么划，才能让「晋升」真的只是改配置，而不是重新做一遍？**

## 结论（3 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 命名空间不是安全边界；需要凭据、配额、故障域隔离时应分集群，命名空间只做组织与配额划分 | L1 | Kubernetes Namespaces / Multi-tenancy；ResourceQuota |
| 2 | 每环境独立凭据，state、`.env`、密钥一律不入 Git；集群自身用 IaC 声明式供应并走 GitOps bootstrap | L1 | Kubernetes Secrets；Kustomize 官方文档；Terraform State 文档 |
| 3 | 目录结构应先服务「晋升时只改一处」，再服务「看着整齐」；同源清单的多环境差异用 overlay，参数化分发才用 values | L2 | Thoughtworks Technology Radar（目录策略，候选待核验）；CNCF TAG App Delivery 材料（候选待核验） |

## 反模式（2 条）

1. 三个环境共用一套凭据「方便联调」→ 一次泄露全线失守 → 每环境独立凭据 + 审计
2. 把 `terraform.tfstate` 或 `.env` 提交进仓库 → 凭据与基础设施状态泄露 → 远端加密存储 + plan/diff 审查

## 选型矩阵

**环境隔离方式选型**：命名空间 / 同集群多租户 / 独立集群 / 独立账号，列维度含「隔离强度、成本、凭据边界、故障域、何时不该用、回滚方式」。另含**仓库目录规范表**（`deploy/base`、`overlays/`、`charts/`、`gitops/`、`policies/`）。

## 验证与回滚

- **验证命令**：`./hack/render-diff.sh`；`grep -R "password\|token" deploy/ gitops/`（应无命中）
- **通过标准**：三环境 image 字段完全一致；差异仅为白名单内的配置项；仓库无凭据明文
- **回滚命令 / 步骤**：`git revert <commit> && kubectl apply -k deploy/overlays/<env>`；IaC 侧用 `terraform apply` 回到上一版 state
- **回滚验证**：重新执行 `render-diff.sh`，三环境回到上一版配置
