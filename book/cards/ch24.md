## 读者视角

- **读者带着什么问题来**：镜像从哪来、依赖有没有漏洞、推到仓库的到底是不是 CI 构建的那一个，怎么证明？
- **学完你能……**：为 `order-demo` 装上 SBOM、扫描与验签门禁，让未签名镜像进不了集群。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：SBOM / 扫描 / cosign 验签门禁；未签名镜像被准入拒绝（`ch24-supply`）。

## 一句话核心问题

**「这个产物可信」需要哪几道可验证的门禁，分别挡住什么？**

## 结论（3 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | SLSA 构建级别、SBOM（SPDX / CycloneDX）、cosign/Notation 签名与准入验签，分别解决「怎么构建」「含什么」「是不是那一个」 | L1 | SLSA 规范；Sigstore/cosign 文档；SPDX / CycloneDX 规范；NIST SP 800-190 |
| 2 | 门禁应同时在 CI（出仓前）与准入（入集群前）生效，只做一侧可被绕过 | L1 | Kubernetes Admission Controllers；Kyverno / Gatekeeper 验签文档（与第 25 章共用） |
| 3 | 供应链防护的重心是「可追溯与可阻断」，不是把漏洞数扫到零 | L2 | CNCF Cloud Native Security Whitepaper v2（正式链接待补）；CNCF 供应链最佳实践白皮书（候选待核验） |

## 反模式（3 条）

1. 只在 CI 扫描、集群不验签 → 手工推一个镜像就能绕过 → 准入侧验签
2. SBOM 生成后不归档 → 出事时无法回答「受影响的是哪些版本」 → 制品库保留策略 + 索引
3. 把「0 漏洞」当上线门槛 → 基础镜像永远过不了、团队开始加白名单糊弄 → 按可利用性与修复窗口分级

## 验证与回滚

- **验证命令**：`./hack/verify-supply-chain.sh`；`cosign verify <image>`；`kubectl -n order-demo-dev describe pod`（查看验签事件）
- **通过标准**：签名镜像通过、未签名镜像被拒；SBOM 可按 SHA 检索
- **回滚命令 / 步骤**：应急时把策略临时置为 `audit` 模式（`kubectl apply -f policies/verify-image-signature.yaml` 的 warn 版本），并登记例外与到期时间；正式回退走 `git revert`
- **回滚验证**：验签事件出现在审计日志，应用 `verify.sh` 通过
