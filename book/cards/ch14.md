## 读者视角

- **读者带着什么问题来**：配置被人手工改过、集群和 Git 对不上，怎么让「Git 里写什么就跑什么」真正成立？
- **学完你能……**：搭出 dev → staging → prod 的声明式晋升链路，让手工改动被自动纠正，并能一键回退任意环境。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：三环境 GitOps 晋升；合并 PR 后集群自动同步，手工改动被纠正（`ch14-gitops`）。

## 一句话核心问题

**变更应该通过什么入口进入集群，以及如何在多环境之间只晋升「同一个制品」？**

> 本章解决「变更怎么进集群」，是底座；第 15 章解决「流量怎么灰度」，是发布策略的工具实现。因果不倒置（D-02）。

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | GitOps 的四个原则（声明式、版本化且不可变、自动拉取、持续收敛）缺一不可；只把 YAML 放进 Git 不算 GitOps | L1 | OpenGitOps Principles；Argo CD Declarative Setup；Flux 官方文档 |
| 2 | ApplicationSet 生成多集群/多环境应用；rendered manifests 模式与集群内渲染模式各有取舍，关键是渲染产物可 review | L1 | Argo CD ApplicationSet / Sync Options / 渲染插件文档；Flux Kustomization 文档 |
| 3 | 漂移检测与自愈是 GitOps 的价值，也是风险源：自愈会把紧急手工止血一起改回去 | L2 | Weaveworks 关于 GitOps 的论述（候选待核验）；CNCF App Delivery TAG 材料（候选待核验） |
| 4 | 生产变更只允许走 Git（PR 即变更），应急止血必须走「先提交 PR、后同步」而非 `kubectl edit`；这是本书不可协商项 | **本书观点** | 不设背书；论证见「应急变更流程」，反例见第 1 章 H7 |

## 反模式（3 条）

1. Argo CD 与手工 `kubectl edit` 并存 → 漂移反复出现，无人知道真相在哪 → 收回写权限 + 审计
2. 密钥直接提交进 GitOps 仓库 → 泄露 → SOPS / Sealed Secrets / ESO 三选一，与第 9 章一致
3. 开自愈却没设排除项 → 紧急扩容被自愈改回去 → 定义自愈白名单与冻结窗口

## 选型矩阵

**Argo CD 3.x vs Flux 2.x**：架构 / 渲染模式 / 多集群 / 密钥方案 / **何时不该用** / 升级与回滚。另含**晋升链路表**（PR 类型、审批、diff 范围、同步策略、回滚方式）与**密钥方案对照**（须与第 9 章选定方案一致）。

## 验证与回滚

- **验证命令**：合并一个只改镜像 SHA 的 PR；`kubectl -n order-demo-dev edit deploy gateway --replicas=9`（观察被纠正）；`argocd app diff order-demo-dev`
- **通过标准**：PR 合并后自动同步；手工改动在同步周期内被纠正；三环境 image 相同、配置不同
- **回滚命令 / 步骤**：`git revert <PR commit> && argocd app sync order-demo-prod`；或 `argocd app rollback order-demo-prod <history-id>`；Kargo 路径回退到上一 Stage
- **回滚验证**：`argocd app diff` 为空，`verify.sh` 通过
