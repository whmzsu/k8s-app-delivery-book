## 一句话核心问题

**面对一个组件，凭什么选 Deployment 而不是 StatefulSet、Job 或 DaemonSet？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 有状态身份、稳定网络标识与有序启停才需要 StatefulSet；普通无状态服务用 Deployment，裸 Pod 不用于生产 | L1 | Kubernetes Workloads / StatefulSets / Jobs / DaemonSet；Pod Lifecycle |
| 2 | 原生 sidecar（KEP-753）解决了「主容器退出后 sidecar 不退出」的老问题；initContainer 只用于启动前的一次性准备 | L1 | KEP-753 Sidecar Containers；Init Containers；Pod Lifecycle |
| 3 | 进程应无状态、可随时丢弃，把状态外置；这是工作负载可自由选型的前提 | L2 | 12-Factor App《VI. Processes》（候选待核验）；Borg 论文（EuroSys 2015，候选待核验） |
| 4 | 「用 StatefulSet 跑数据库」只是可选项之一，托管数据库往往更省事；是否自己管要按运维能力而非技术偏好决定 | **本书观点** | 不设背书；论证见第 16 章，反例见第 29 章 Operator 成熟度评估 |

## 反模式（3 条）

1. 直接创建裸 Pod → 节点故障后不会重建，也没有滚动更新 → 一律经由工作负载控制器
2. 无状态服务也用 StatefulSet「为了名字稳定」→ 扩容慢、升级复杂、PVC 残留 → 用 Service 提供稳定入口
3. 把日志采集 sidecar 写成常驻主容器且无退出协调 → 任务型 Pod 永远 Completed 不了 → 原生 sidecar 或 DaemonSet

## 选型矩阵

**工作负载决策树**：是否需要每节点一个实例 → DaemonSet；是否跑完即结束 → Job/CronJob；是否需要稳定身份与有序启停 → StatefulSet；否则 → Deployment。矩阵列含「最适 / 不选 / 主要风险 / 回滚方式」。

## 验证与回滚

- **验证命令**：`kubectl -n order-demo-dev get deploy,sts,pod -o wide`；`kubectl -n order-demo-dev rollout status sts/db`
