## 读者视角

- **读者带着什么问题来**：命名空间隔离到底能挡住什么？服务账号怎么给权限才不越界，人还能不能 SSH 上生产？
- **学完你能……**：给 `order-demo` 配最小 RBAC 与 Workload Identity，说清命名空间隔离的失效场景，并把审计留痕接上。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：SA 最小化、审计、租户隔离；越权请求被 RBAC 拒绝并留审计（`ch26-rbac`）。

## 一句话核心问题

**多租户集群里，隔离的边界在哪，权限与凭据该怎么发、怎么收？**

## 结论（3 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | RBAC 最小权限：按 ServiceAccount 绑定 Role，默认关闭 `automountServiceAccountToken`，禁用 cluster-admin 泛用 | L1 | Kubernetes RBAC；ServiceAccount；Auditing；CIS Kubernetes Benchmark |
| 2 | 命名空间只做组织与配额隔离，不是安全边界；跨租户需独立集群/账号或额外策略层 | L1 | Kubernetes Multi-tenancy；Network Policies（第 19 章交叉） |
| 3 | 机器身份优先用 Workload Identity / IRSA，动态凭据优于长期静态密钥；容器化环境的凭据风险覆盖分发、轮换、吊销全周期 | L1 + L2 | NIST SP 800-190；CNCF Cloud Native Security Whitepaper v2（正式链接待补）；云厂 Workload Identity 文档 |
| 4 | **SSH 禁入生产**：排障走可观测与 runbook，不登机器；这是全书公理之一 | **本书观点** | 不设背书；论证见「为什么禁 SSH」，反例见第 23 章现场处置 |

## 反模式（3 条）

1. 给所有 Pod 默认挂载 SA token → 任一应用被攻破即可调 API → 默认关闭、按需开启
2. 把命名空间当安全边界 → 同集群内横向移动 → 明确失效场景与补偿措施
3. 长期 Access Key 写进配置 → 轮换困难、泄露难发现 → 动态凭据 + 审计

## 验证与回滚

- **验证命令**：`kubectl -n order-demo-dev auth can-i --as=system:serviceaccount:order-demo-dev:api get secrets`（应 no）；`kubectl -n order-demo-dev get sa api -o yaml`；查询审计日志
- **通过标准**：越权被拒且审计留痕；SA 未自动挂载 token；生产无 SSH 通道
- **回滚命令 / 步骤**：`kubectl apply -f policies/rbac/@<上一 tag>`；应急临时授权须写入例外登记并设定到期时间
- **回滚验证**：`verify.sh` 通过，审计事件完整
