## 读者视角

- **读者带着什么问题来**：前 5 章讲了一堆原则和地图，我到底什么时候能真的把应用跑起来？
- **学完你能……**：从一份 Dockerfile 出发，在 kind 里把 `order-demo` 的 gateway 跑通并 `curl` 到 200，且能用一条命令退回上一个版本。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：一个镜像 + Deployment/Service + ConfigMap，`curl http://localhost:8080/healthz` 返回 200（`ch06-first-loop`）。

## 一句话核心问题

**在引入 Helm、GitOps、Operator 之前，一份「能晋升、能回滚」的最小应用定义，最少要包含哪些东西？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 镜像必须不可变且用 git SHA 打标签；同一标签重复推送会让「回滚到上一版」失去意义 | L1 | Kubernetes Images / ImagePullPolicy 官方文档；OCI Image Spec |
| 2 | 最小可运行闭环 = 镜像 + Deployment + Service + ConfigMap，四者缺一就无法验证「配置改了是否生效、流量是否进来」 | L1 | Kubernetes Deployment / Service / ConfigMap 概念与教程 |

## 反模式（3 条）

1. 一上来就用 `latest` + `imagePullPolicy: Always` → 各节点拉的镜像不一致、无法追溯 → 本章改为 `git-<sha7>` 固定标签 + 显式 pull policy
2. 把配置硬编码进镜像或 Dockerfile 的 `ENV` → 每改一个环境参数就要重建 → 本章用 ConfigMap 注入，第 9 章再做不可变化与密钥分离
3. 只写一个 Deployment 就宣布「跑通了」 → 没有 Service 就没有稳定入口，没有 ConfigMap 就无法验证配置生效 → 本章要求四件套齐全并给出 curl 验证

## 选型矩阵

本章**不做工具横比**（工具从第 10 章起）。但含一张「最小闭环四件套」对照表：组件 / 为什么必须有 / 缺了会出现什么现象 / 后续哪章加固它。

| 组件 | 为什么必须有 | 缺了的现象 | 加固章 |
|---|---|---|---|
| 镜像 | 产物可追溯 | 无法回滚到确定版本 | 12、24 |
| Deployment | 声明副本数与终态 | 裸 Pod 删了不会重建 | 7、8、13 |
| Service | 稳定入口与负载均衡 | Pod IP 变了就访问不到 | 19 |
| ConfigMap | 配置与产物分离 | 改配置要重建镜像 | 9、10 |

## 验证与回滚

- **验证命令**：
  ```
  ./hack/kind-up.sh
  ./hack/verify.sh
  curl -i http://localhost:8080/healthz
  kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.template.spec.containers[0].image}'
  ```
- **通过标准**：`healthz` 返回 200；`GREETING` 的值来自 ConfigMap；image 字段为 `git-<sha7>` 而非 `latest`
- **回滚命令 / 步骤**（回滚方案先于发布方案，本章第一次示范）：
  ```
  kubectl -n order-demo-dev rollout undo deployment/gateway
  kubectl -n order-demo-dev rollout status deployment/gateway
  ```
  若回滚目标是明确的上一版产物，则改用 `kubectl -n order-demo-dev set image deployment/gateway gateway=registry.example.com/order-demo/gateway:git-<上一个sha7>`，并重新执行 `verify.sh`
- **回滚验证**：image 字段回到上一个 SHA，且 `healthz` 仍为 200
