## 读者视角

- **读者带着什么问题来**：同一套清单要发三个环境、还要给别的团队用，是 Kustomize、Helm 还是干脆写代码生成？

## 一句话核心问题

**配置该用 patch、模板还是代码生成，判断依据是什么，以及渲染产物该在哪一步被审查？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | Kustomize 是无模板 patch/overlay，Helm 是模板 + 包管理 + release 状态；二者解决不同问题，不是竞品式的二选一 | L1 | Kustomize 官方 FAQ；Helm Chart Template Guide；Helm Chart Best Practices（已核验） |
| 2 | 必须 review 的是渲染产物而非模板本身；CI 里要有 kubeconform / conftest / `helm lint` / `ct` 四道关卡 | L1 | kubeconform、conftest、chart-testing 项目文档；Helm Provenance and Integrity |
| 3 | 模板化程度应与「谁在用这份配置」成正比：同源多环境用 overlay，对外分发用 Chart，大规模平台才考虑用代码生成 | L2 | Thoughtworks Technology Radar（模板化取舍，候选待核验）；Humble & Farley《Continuous Delivery》(2010)（候选待核验） |
| 4 | 抽象过度比重复更贵：生成物不可读时，排障成本会转嫁给值班的人 | **本书观点** | 不设背书；论证见「过度工程警戒线」，反例见第 31 章反模式速查 |

## 反模式（3 条）

1. overlay 继承链套了五六层 → 没人知道某个字段最终来自哪 → 限制层级、把差异写在同一处
2. values 爆炸（几百个键、大量条件分支）→ 模板难调试、release 状态漂移 → 拆 Library Chart、限制可配置项
3. 只 review 模板 PR 不看渲染 diff → 一个默认值改动悄悄改了全部环境 → 渲染产物进 PR 附件

**Helm 4.x / Kustomize 5.x / Jsonnet·CDK8s 对比**：本质 / 最适 / **不选** / 主要风险 / 回滚方式（`helm rollback <release> <rev>` vs 切回上一个 overlay 目录 vs 回退生成代码重渲染）。列数与大纲第 10 章矩阵一致，不另造维度。

## 验证与回滚

- **验证命令**：`helm template order-demo deploy/charts/order-demo -f values-dev.yaml > /tmp/a.yaml`；`kustomize build deploy/overlays/dev > /tmp/b.yaml`；`diff /tmp/a.yaml /tmp/b.yaml`；`./hack/render-diff.sh`
- **通过标准**：两条渲染路径产物一致；四道 CI 关卡通过；渲染 diff 只含预期变更
- **回滚命令 / 步骤**：Helm 路径 `helm rollback order-demo <rev> -n order-demo-dev`；overlay 路径 `kubectl apply -k deploy/overlays/dev@<上一 tag>`；生成代码路径回退生成器版本并重渲染
- **回滚验证**：`kubectl -n order-demo-dev get deploy -o jsonpath='{..image}'` 回到上一版 SHA，`verify.sh` 通过
