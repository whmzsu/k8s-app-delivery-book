## 读者视角

- **读者带着什么问题来**：我明明 `kubectl edit` 改了副本数，怎么一会儿又被改回去？K8s 到底在替我管什么？
- **学完你能……**：用「期望状态 → 控制器 → 实际状态」解释任意一次变更的最终结果，并说清平台方与应用方各自负责哪一层。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：沿用 `ch01-incident` 的最小环境；`kubectl get deploy -o yaml` 找到 owner 链（`ch02-model`）。

## 一句话核心问题

**声明式终态之下，「改配置」和「改运行状态」到底有什么区别，谁有权改？**

## 结论（3 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 控制器持续比对实际状态与期望状态并收敛；手工直接改运行对象会被收敛回去，这不是 bug 而是模型本身 | L1 | Kubernetes Controllers / Declarative Management / Objects 概念页 |
| 2 | Pod 不是虚拟机：它是可调度的、可被丢弃的最小执行单元，OwnerReference 决定级联删除与重建 | L1 | Kubernetes Pod Lifecycle / Owners and Dependents |
| 3 | 编排系统的核心价值是把运维知识固化为可收敛的期望状态，平台方管「收敛机制」，应用方管「期望状态写什么」 | L2 | Borg, Omega, and Kubernetes（已核验入口）；Kelsey Hightower《Kubernetes the Hard Way》（L2 候选，待核验） |

## 反模式（2 条）

1. 把 Pod 当虚机登录后改文件 → 重建即丢失、且无法复现 → 本章用 OwnerReference 与重建实验说明边界
2. 平台方与应用方职责不分 → 双方都能改同一份清单，漂移无人负责 → 本章给出责任边界表（控制面 / 平台 / 应用）

## 验证与回滚

- **验证命令**：`kubectl -n order-demo-dev scale deploy/gateway --replicas=5 && sleep 5 && kubectl -n order-demo-dev get deploy gateway -o jsonpath='{.spec.replicas}'`；再 `kubectl edit deploy gateway` 改回清单值
- **通过标准**：`kubectl scale` 改的是 `Deployment.spec.replicas`（期望状态），在原生 K8s（L0）**会生效且持久**，不会被控制器改回；只有进入 GitOps（第 14 章）后才会被漂移检测纠正回 Git 值。生产正道是改清单并合入 Git，而非命令式 `scale`（CL-S-04）
- **回滚命令 / 步骤**：`kubectl -n order-demo-dev apply -f deploy/base/deployment.yaml`（回到声明值）
- **回滚验证**：`kubectl get deploy,replicaset,pod` 与清单一致
