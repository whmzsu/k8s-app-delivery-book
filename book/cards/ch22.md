## 一句话核心问题

**什么样的告警值得把人从床上叫起来，以及噪音该在哪个环节被消掉？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 告警应基于 SLO 燃尽率的多窗口规则（快燃尽 paging、慢燃尽 ticket），而不是单条静态阈值 | L1 | Prometheus Alertmanager 文档；Prometheus 告警规则文档；Google SRE Workbook《Alerting on SLOs》方法对应的规则示例 |
| 2 | 每条 paging 告警必须可行动、指向 runbook、有明确升级路径；原因型告警只做上下文 | L2 | Google SRE Workbook《Alerting on SLOs》（候选待核验）；Rob Ewaschuk《My Philosophy on Alerting》（候选待核验）；Google SRE Book《Monitoring Distributed Systems》（已核验入口） |
| 3 | 噪音治理是分级路由 + 抑制 + 静默 + 定期复盘四件事，不是把阈值调高 | **本书观点** | 不设背书；论证见「噪音治理四步」，反例见公开告警疲劳复盘 |
| 4 | 告警即代码：规则进 Git、走 PR、有测试；手工在 UI 里加的规则必然漂移 | **本书观点** | 不设背书；论证见告警仓库化，与第 14 章 Git 唯一真相呼应 |

## 反模式（3 条）

1. 每个容器 CPU 都发一条告警 → 无关噪音淹没真信号 → 只保留症状型告警
2. 告警内容只有「异常」两个字 → 值班得现查怎么办 → 强制 runbook 链接与处置首步
3. 直接在 Alertmanager UI 改路由 → 与 Git 不一致、无法回滚 → 规则配置进仓库

## 选型矩阵

**告警分级表**：级别（paging / ticket / 记录）/ 触发条件 / 路由目标 / 响应时限 / 何时不该 paging。另含**规则模板**（含 `for`、多窗口燃尽率、runbook 注解）与**抑制/静默规则表**。
