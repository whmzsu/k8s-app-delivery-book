## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | Service 做集群内发现与负载均衡，Gateway API 是 Ingress 的继任者且按角色拆分资源（GatewayClass / Gateway / HTTPRoute） | L1 | Gateway API spec；Kubernetes Service / Ingress；Network Policies |
| 2 | NetworkPolicy 是「默认允许、加了才拒绝」，必须显式写默认拒绝基线；能力取决于 CNI 实现 | L1 | Kubernetes Network Policies；Cilium / Calico 文档；Gateway API 实现文档 |
| 3 | 超时、重试、熔断应在离调用方最近且可观测的一层配置；层层都配会放大重试风暴 | L2 | Istio Traffic Management 文档（L1 交叉支撑）；Gateway API GEP / SIG Network 设计说明（候选待核验）；Thoughtworks Technology Radar（服务网格取舍，候选待核验） |
| 4 | 服务网格不是默认项：只有当需要 mTLS、细粒度流量策略或统一可观测，且团队能承担运维成本时才值得上 | **本书观点** | 不设背书；论证见「该不该上网格」决策树，反例见第 5 章警戒线 |

## 反模式（3 条）

1. 只给入站加白名单、不限制出站 → 数据外联无约束 → 默认拒绝双向基线
2. 重试在网关、Sidecar、客户端各配一遍 → 故障时被放大成重试风暴 → 单层负责、其余禁用
3. 证书靠人工续期 → 过期即全站不可用 → cert-manager + 到期告警（第 22 章）
