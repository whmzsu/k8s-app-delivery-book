## 一句话核心问题

**requests 与 limits 分别买到了什么，以及为什么「CPU limit」常常是延迟抖动的元凶？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | requests 决定调度与 QoS 等级，limits 决定上限；CPU 超限是被限流（cfs quota），内存超限是被 OOMKill，二者后果不同 | L1 | Kubernetes Resource Management for Pods and Containers；QoS；Node-pressure Eviction |
| 2 | LimitRange 给默认值、ResourceQuota 给命名空间总量、PriorityClass 决定驱逐顺序，三者作用在不同层次 | L1 | LimitRange；ResourceQuota；Pod Priority and Preemption |
| 3 | 过载时系统行为由最弱一环决定；资源基线应来自压测而非拍脑袋，并保留突发余量 | L2 | Borg 论文（EuroSys 2015，候选待核验）；Google SRE Book《Handling Overload》（候选待核验） |
| 4 | 把 CPU limit 设得和 requests 一样「好算」，是以牺牲尾延迟换可预测性；对在线服务通常不划算 | **本书观点** | 不设背书；论证见「CPU 限流陷阱」，反例给压测数据 |

## 反模式（3 条）

1. 不填 requests → 调度无依据、QoS 为 BestEffort，最先被驱逐 → 全工作负载强制基线
2. CPU limit 过小 → 请求堆积、P99 抖动却看不到 CPU 打满 → 在线服务放宽或去掉 CPU limit
3. 只看「平均使用率」定基线 → 峰值被削平 → 用分位数与压测曲线
