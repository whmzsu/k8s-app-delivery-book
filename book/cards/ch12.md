## 读者视角

- **读者带着什么问题来**：构建在 CI 里跑得好好的，为什么生产还是会出现「没测过的那个包」？
- **学完你能……**：搭出一条 fail fast 的流水线，推一个 commit 自动产出带 SHA 的唯一镜像，且各环境晋升的是同一个产物。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：进入 CI；推一个 commit 自动产出带 SHA 的镜像（`ch12-ci`）。

## 一句话核心问题

**流水线怎样保证「一次构建、多处晋升」，而不在每个环境悄悄重做一遍？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 构建产物必须由提交 SHA 唯一标识，后续所有阶段只传递制品引用，不重新构建 | L1 | SLSA Build Levels；GitHub Actions《Security hardening》（已核验）；OCI Image Spec |
| 2 | fail fast 顺序是 lint → 单测 → 集成测试 → 构建 → 校验；越晚发现的错误越贵 | L1 | GitHub Actions 官方文档；各 CI 平台官方文档 |
| 3 | 第三方 Action 按 commit SHA 锁定而非 tag，机密脱敏，依赖缓存可复用但不可跨信任边界 | L1（规范） + L2（共识） | GitHub Actions《Security hardening》（已核验）；SLSA；Martin Fowler《ContinuousDelivery》（已核验入口） |
| 4 | flaky 测试要么修要么删，保留「重跑一下就好」的测试会让整条流水线失去信号价值 | **本书观点** | 不设背书；论证见「信号质量」小节，反例见第 31 章反模式速查 |

## 反模式（3 条）

1. 每个环境跑一遍 build → 环境间产物不同、回滚目标不明 → 构建阶段只跑一次，产出制品引用
2. Action 用 `@v1` 而非 SHA → 上游被篡改即供应链失守 → 按 SHA 锁定 + 依赖更新自动化
3. 把生产密钥放进 CI 变量到处打日志 → 泄露面扩大 → 机密脱敏、OIDC 短期凭据（第 26 章深化）

## 验证与回滚

- **验证命令**：`git commit --allow-empty -m "test ci" && git push`；`./hack/promote-artifact.sh --from dev --to staging --sha <sha7>`
- **通过标准**：只产生一个镜像 digest；staging 的 image 字段与 dev 完全相同；未触发第二次构建
- **回滚命令 / 步骤**：`./hack/promote-artifact.sh --sha <上一个sha7>`，或 `kubectl -n order-demo-dev set image deployment/gateway gateway=...:git-<上一个sha7>`
- **回滚验证**：`verify.sh` 通过，`healthz` 为 200
