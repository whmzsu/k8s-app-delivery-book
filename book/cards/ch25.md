## 读者视角

- **读者带着什么问题来**：怎么强制「非 root、不许 privileged、镜像必须来自可信仓库」，又不把发布流程堵死？
- **学完你能……**：选定策略引擎，把 Pod Security Standards 从 warn 渐进推到 enforce，并给策略写测试与灰度。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：Kyverno / VAP 策略库；特权容器在 CI 与准入两处被拦（`ch25-policy`）。

## 一句话核心问题

**护栏该用哪个引擎表达，怎样灰度上线才不会在半夜把整个发布挡住？**

## 结论（3 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | Kyverno（声明式策略）、Gatekeeper（Rego）、VAP（原生 CEL）能力边界不同；简单校验优先原生，复杂变更/生成才上策略引擎 | L1 | Kubernetes Pod Security Standards；Admission Controllers；ValidatingAdmissionPolicy；Kyverno / Gatekeeper 文档 |
| 2 | PSS 应走 warn → audit → enforce 渐进落地，先看清违规面再阻断 | L1 | Pod Security Standards / Pod Security Admission 官方文档 |
| 3 | 策略也是代码：进 Git、有单元测试、有灰度与绕过审批；没有测试的策略比没有策略更危险 | L2 | CNCF Cloud Native Security Whitepaper v2（正式链接待补）；Thoughtworks Technology Radar（策略即代码，候选待核验） |

## 反模式（3 条）

1. 一上来全量 enforce → 历史工作负载集体起不来 → warn/audit 观察窗口
2. 策略只在集群侧、CI 不校验 → 开发者到发布才被拒，反馈太晚 → 离线校验（第 11 章）与准入同源
3. 绕过流程靠口头打招呼 → 审计断链 → 例外登记 + 到期自动失效

## 验证与回滚

- **验证命令**：提交一个 privileged Pod 清单；`kubectl -n order-demo-dev apply --dry-run=server -f policies/tests/fail.yaml`；离线执行 conftest/kyverno CLI
- **通过标准**：CI 与准入两处都拦截，报错可读；审计里能看到拦截事件
- **回滚命令 / 步骤**：把策略从 `Enforce` 改回 `Audit`：`kubectl apply -f policies/pss-audit.yaml`；紧急时 `kubectl delete -f policies/require-nonroot.yaml` 并登记例外
- **回滚验证**：发布恢复，审计事件完整保留
