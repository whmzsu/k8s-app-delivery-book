## 读者视角

- **读者带着什么问题来**：滚动、蓝绿、金丝雀，到底哪个适合我们？为什么上次回滚没成功？
- **学完你能……**：按容量、回退速度与风险承受度算出该用哪种策略，并在发布前写出且演练回滚方案。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：三种策略对比与回滚演练；执行 `kubectl rollout undo` 成功恢复（`ch13-strategy`）。

## 一句话核心问题

**在「容量有限、必须可回退」的约束下，一次发布该选哪种策略，回滚方案怎么写才算数？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 滚动更新由 `maxSurge` / `maxUnavailable` 控制容量账；高峰期余量不足时，参数再保守也会 5xx | L1 | Kubernetes Deployments（滚动更新 / maxSurge / maxUnavailable）；PodDisruptionBudget |
| 2 | 蓝绿需要双倍容量与流量整体切换，金丝雀需要指标判定与流量分层；二者成本结构完全不同 | L2 | Martin Fowler《BlueGreenDeployment》（已核验）；Danilo Sato《CanaryRelease》（已核验）；Humble & Farley《Continuous Delivery》(2010)（候选待核验） |
| 3 | **回滚方案必须先于发布方案**：没有在 staging 演练过的回滚，等于没有回滚 | L2 | Google SRE Book《Release Engineering》；Martin Fowler《ContinuousDelivery》（已核验） |
| 4 | 数据 schema 不兼容时，应用层的回滚是假回滚；这条限制由第 16 章的 expand–contract 解决 | **本书观点** | 不设背书；论证见章末「回滚的边界」，反例见第 16 章 |

## 反模式（3 条）

1. 「先发再说，坏了就回滚」→ 从未演练过 rollback，命令与权限都没验证 → 发布门禁强制要求回滚演练记录
2. `maxUnavailable: 0` + `maxSurge: 1` 却没算节点余量 → 新 Pod Pending，发布卡死 → 容量计算表
3. 蓝绿切流后立刻删旧版本 → 发现问题已无回退目标 → 保留旧版本至观察窗口结束

## 选型矩阵

**滚动 / 蓝绿 / 金丝雀对比**：容量成本 / 回退速度 / 流量控制粒度 / 适用前提 / **何时不该用** / 回滚命令。附**容量计算表**（副本数、surge、unavailable、节点可分配量、峰值余量）。

## 验证与回滚

- **验证命令**：`./hack/rollback-drill.sh`；`kubectl -n order-demo-staging rollout status deploy/gateway`；`./hack/rolling-5xx-test.sh`
- **通过标准**：回滚演练在时限内完成且 `healthz` 恢复 200；容量计算表有余量；发布期零 5xx
- **回滚命令 / 步骤**：`kubectl -n order-demo-prod rollout undo deployment/gateway --to-revision=<n>`；蓝绿路径把 Service selector 切回 `version=<旧sha7>`；金丝雀路径见第 15 章自动回滚
- **回滚验证**：`kubectl -n order-demo-prod get deploy -o jsonpath='{..image}'` 为上一版 SHA，连续请求恢复
