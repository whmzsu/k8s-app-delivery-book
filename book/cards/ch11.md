## 读者视角

- **读者带着什么问题来**：改一行 YAML 就要走一遍完整发布才能知道对不对，有没有更短的回路？
- **学完你能……**：在本地 kind 集群里热更新验证，并让同一个错误字段在提交时被 CI 拦下。
- **此刻 `order-demo` 长什么样 / 本章可验证动作**：接入 kubeconform / conftest / kuttl 与 kind 版本矩阵；提交一个错误字段被 CI 拦下（`ch11-validate`）。

## 一句话核心问题

**怎样把「这份清单到底对不对」的验证，压缩到提交之前，并且不会随 K8s 版本升级而失效？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | 校验应分四层：语法/结构（kubeconform）→ 组织策略（conftest）→ 声明式行为测试（kuttl / chainsaw）→ 真实集群冒烟（kind 版本矩阵） | L1 | kubeconform、conftest、kuttl、kind 官方文档；Kubernetes SIG Testing 材料 |
| 2 | CI 里跑多版本 K8s 矩阵是防止书中示例与全书配置过时的机制，不是可选项 | L1 | kind 官方文档；Kubernetes 版本与版本偏差策略 |
| 3 | 本地热更新回路（Tilt / Skaffold）的价值在于缩短反馈，但绝不能成为绕过渲染产物审查的路径 | L2 | Kubernetes SIG Testing 材料（L2 候选，待核验）；Thoughtworks Technology Radar（候选待核验） |
| 4 | 临时预览环境应该由 PR 自动生成、随 PR 关闭自动销毁；生命周期不绑定 PR 的预览环境一定会变成成本黑洞 | **本书观点** | 不设背书；论证见「预览环境生命周期」，反例见第 18 章成本归因 |

## 反模式（3 条）

1. 只在单一 K8s 版本上验证 → 集群一升级示例全失效 → kind 多版本矩阵
2. 热更新工具直接把本地文件推到共享集群 → 绕过 Git 与渲染审查 → 只允许指向个人/临时命名空间
3. 声明式测试写成一堆 sleep → 又慢又 flaky → 用 kuttl 的断言与超时

- **验证命令**：`./hack/validate.sh`；在 PR 里故意提交 `replicas: "three"` 观察 CI 失败；`kubectl apply -k deploy/overlays/dev --dry-run=server`
- **通过标准**：四层校验全部通过；三个 K8s 版本 job 全绿；错误字段被拦且有可读报错
- **回滚命令 / 步骤**：本章只加校验不改应用；若新规则误伤，回退 `validate.yml` 到上一版并标注误伤原因，`kubectl apply -k deploy/overlays/dev@<上一 tag>` 恢复应用
- **回滚验证**：`verify.sh` 与 `healthz` 仍通过
