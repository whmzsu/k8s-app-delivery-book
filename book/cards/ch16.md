## 一句话核心问题

**当发布牵涉数据格式时，怎样让新旧版本共存，从而保住回滚能力？**

## 结论（4 条）

| # | 结论 | 类型 | 计划引用（名称级） |
|---|---|---|---|
| 1 | StatefulSet 提供稳定标识与有序启停，但不提供数据库本身的备份、故障转移与升级语义 | L1 | Kubernetes StatefulSets；Velero 官方文档 |
| 2 | expand–contract（扩展 → 双写 → 回填 → 收缩）让新旧版本在同一 schema 上共存，是保住回滚能力的关键 | L2 | 《Refactoring Databases》(Ambler & Sadalage)（候选待核验）；Martin Fowler《BlueGreenDeployment》中 schema 排序（已核验） |
| 3 | 备份的价值等于恢复演练的成功率；没演练过的备份不算备份 | L2 | Google SRE Book《Managing Incidents》（SRE Book 入口已核验）；Velero 官方文档（L1 交叉支撑） |
| 4 | 用 Operator 管数据库还是买托管服务，应按团队的故障恢复能力决定，而非按技术偏好 | **本书观点** | 不设背书；论证见「能力边界表」，反例见第 29 章 Operator 成熟度评估 |

## 反模式（3 条）

1. 发布时直接 `ALTER TABLE DROP COLUMN` → 旧版本立刻报错，回滚无效 → expand–contract
2. 卸载 CRD/Operator 不检查 finalizer → 资源卡住、PVC 残留 → 卸载清单与检查命令
3. 只做备份从不恢复 → 真出事时发现备份不可用 → 每季度演练并出报告

## 验证与回滚

- **验证命令**：`./db/migrate.sh --phase expand`；`./hack/restore-drill.sh`；新旧版本同时读写订单表
- **通过标准**：迁移各阶段新旧版本均可服务；恢复到新集群后数据一致且有演练报告
- **回滚命令 / 步骤**：应用侧 `kubectl rollout undo`；schema 侧**只回退到上一个共存阶段**，禁止直接逆向 DROP；数据侧 `velero restore create --from-schedule <name>`
- **回滚验证**：旧版本启动后读写正常，`verify.sh` 通过
