# 文风指南：专业但不吃力（v1.0）

版本 `v0.1` · 2026-11-11 · 适用于全书 31 章正文
配套文档：`book/prose-standard.md`（句级可读性）、`book/chapter-spec.md`（七段结构）

> 目标读者是**凌晨三点被叫起来的人**。他在手机上翻这一章，需要的是「这跟我有什么关系、我错在哪、下一步敲什么」，而不是一份语气中立的技术公报。
> 本章指南定义"幽默有趣"在**技术决策书**里的可行边界：不是加段子，是让行文有温度、有现场、有人的位置。

---

## 一、诊断：为什么会"吃力"

2026-11-11 实测全书 34 万字，句长分布健康（>120 字仅 0.5%、填充语 0 处），所以吃力感**不来自句子长度**，而来自三个结构性缺失：

| 缺失 | 实测证据 | 读者的感受 |
|---|---|---|
| **没有人称** | 全书「你会」仅 **1 处**、「我见过」0 处 | 全程旁观，像读一份不属于自己的说明书 |
| **没有呼吸** | 每句都是「定义 + 判断 + 两个 `[R-]` 角标」三合一 | 每读一句都要处理三件事，认知负载高 |
| **没有现场** | 事故写成法医报告（「T+90：值班收到告警…」），不写人的慌乱、误判、口头禅 | 知道发生了什么，但感受不到"我也会这样" |

结论：**技术密度不能降，语气必须变。** 排版学上这叫「信息密度高、但视觉与语义上有落脚点」。

## 二、五条手法（按性价比排序）

### 手法 1：把人放回句子里（最高优先，成本最低）

把「值班同学」「工程师」「某团队」换成「你」「我们」，把被动句换成主动句。

- 前：`数据库抖了 400 毫秒，全部 api 副本的 liveness 同时失败`
- 后：`数据库只抖了 400 毫秒——短到你连告警都来不及看一眼——全部 api 副本的 liveness 同时失败了`

- 前：`值班同学面对的是「一半流量 5xx、一半 Pod 在 CrashLoop」的现场`
- 后：`你打开终端，看到的是「一半流量 5xx、一半 Pod 在 CrashLoop」`

> 约束：只在**叙述层**用第二人称。判据、命令、检查清单里不许出现「你」，那会削弱权威感（`CL-08-05` 不算「我们建议」，它是硬闸门）。

### 手法 2：短句独立成段，制造呼吸（次高优先）

长论证后放一个 10 字以内的短句收口，读者的眼睛会自动停一下。

- `这不是三个可以互换的开关。这是三条命运不同的控制回路。`
- `数据库没事。你的服务死了。`
- `回滚不是修复。回滚是止血。`

> 约束：每节 ≤2 处。**用多了就变成 PPT**，失去论述的连贯性。

### 手法 3：反差与自嘲（本书已有的基因，继续用）

技术书最好笑的地方，永远是"教科书这么说，现实那么做"。本书其实已有这类基因（`何时不该用` 列里写「想用它防 OOM / 节点宕机 / 滚动更新——都不归它管」），只是没在正文铺开。

- 教科书式：`liveness 用于检测进程是否存活。`
- 有温度式：`liveness 字面意思是"你还活着吗"，它其实只关心一件事：进程的事件循环有没有卡死。它不关心数据库在不在——但你如果非要让它关心，它会用重启整栋楼的方式来回答你。`

> 约束：**只自嘲"从业者"，不嘲笑"受害者"**。事故里被坑的值班同学是读者本人，笑点是「这套机制很反直觉」「这类错误人人会犯」，绝不是「这个团队真蠢」。

### 手法 4：一个精准比喻，胜过三段解释

只在**概念最容易混淆处**用比喻，且比喻必须能反向推导出正确做法，否则是噪音。

- 三类探针：`readiness 是门卫（决定你能不能进），liveness 是急诊医生（判断你还救不救得回来），startupProbe 是产房门口那块"请勿打扰"的牌子（前两个在那段时间内都不许插手）。`
  - 可反推：门卫判错 → 人进不来但没死；医生判错 → 人被杀；牌子撤早了 → 医生冲进去把正在出生的孩子当死人。

> 约束：**每章 ≤5 个比喻**，且必须是同一个隐喻体系内（如"门卫/医生/牌子"同属"医院"）。混用「水管」「高速公路」「交响乐」会让读者更累。

### 手法 5：给清单加一句"人话翻译"

负面清单、反模式列表是本书密度最高的地方，每条末尾加一句半句的口语总结，能显著降疲劳。

- 原文：`根因：探针路径拼写错、应用根本没实现该端点…`
- 加尾注：`说白了：探针在敲一扇不存在的门，而且它每次敲门失败都会杀一次进程。`

> 约束：只在**反模式/清单**加，判据表（通过标准、检查清单）不加——那张表是要打印出来打勾的。

## 二·五、力度档位：松档（v1.1，2026-11-11 用户裁定）

首轮 6–10 处/章试行后，用户判定「还不够松」，全书统一升到**松档**。松档在五条手法之上额外允许四件事：

| 新增许可 | 具体做法 | 边界 |
|---|---|---|
| **写人的心理活动** | 事故时间线里补一句「他当时的想法是…」「心里想的是『应该没事』」 | 只写**判断与误判**，不写情绪表演；不虚构具体公司/人名 |
| **写往返对话** | 允许 2–4 轮对话还原现场（谁说了什么、对方怎么答），而非只给结论 | 每章 ≤2 段对话，且必须承载一个决策点 |
| **短句独立成段** | 每节可到 3 处；允许连续两个短句成段制造重击 | 不能把论证拆成 PPT 碎片 |
| **作者旁白** | 允许「作者跳出来说一句」，如「这一章我劝你别做的事只有一件」 | 每章 ≤2 处，不用于表达个人偏好 |

密度：**每章 10–12 处**温度注入，比喻 ≤5 个/章，每节 ≤3 处。

不变的底线：技术内容零改动、`[R-]` 角标零改动、**判据层（通过标准 / `CL-*` / 回滚命令 / 本书观点）零幽默**、不用会过期的梗。

### 手法 6：把事故还原成对话（v1.2，最强但最贵的一招）

事故章节最容易写成法医报告：时间、现象、根因、处置，四段干净利落，读起来毫无温度。**但真实的事故现场是几个人在群里互相说服的过程**——有人提出过正确的问题，被一句「本地测过」挡回去；有人犹豫过，被沉默推着往前走。把这些还原出来，读者才会在「这不就是我吗」的瞬间记住这一章。

做法：
- 保留原有的技术时间线（T+0、T+10…），**在关键决策点插入 3–5 轮对话块**，标时间与角色（值班 / 同事 / 主管）
- 对话必须承载一个**具体的误判**，不能只是聊天；每段对话后紧跟一句「这段里没有一句错话，问题在……」的点破
- 允许写沉默：`（群里安静了几秒，没人再说话。）`——沉默在群里会被读成同意，这是事故里最便宜的一次审批
- 允许写被挡回去的正确提问：`同事：1 秒够吗？` `值班：本地测过，够。`

约束：
- **每章最多 2 段对话块**，每段 3–5 轮，总增量控制在 500 字内
- 引用真实公开复盘的章节，必须标注「按公开复盘共性还原，非原话」，不得虚构具体公司、人名与时间
- 对话里出现的数值、命令、字段必须与正文一致，不得为戏剧性改动
- 判据层（通过标准 / `CL-*` / 回滚命令）仍然零对话

## 三、四条红线（不许做）

1. **不动技术内容**：论断、数值、版本、配置、命令、`[R-NN-x]` 角标一律不改。文风改造只改**叙述层的措辞与句界**。
2. **不用会过期的梗**：网络流行语、影视台词、时事梗一律不用。这本书的 shelf life 是 5 年，梗的 shelf life 是 5 个月。
3. **不刷段子**：每节 ≤3 处温度注入（松档）。幽默密度过高会让读者怀疑专业性——**技术书的幽默是盐，不是主菜**。
4. **判据层保持严肃**：`通过标准`、`CL-*` 检查清单、`回滚命令`、`本书观点` 标注块——这四处必须零幽默。读者靠它们做发布决策，玩笑会稀释权威。

## 六、执行流程

1. **样板章先行**：先改 1 章（ch08）→ 人工判定尺度 → 定稿手法。
2. **按篇分批**：每批 4–6 章（同篇内文风最易统一），每批改完跑全闸门 + 人工抽读。
3. **回写记录**：每批改完在本文档第七节追加「章 / 加了几处 / 用了哪些手法」。
4. **终检**：全书改完后，用 `grep` 复核「你会/我们」覆盖率、比喻数量、判据层零幽默。
