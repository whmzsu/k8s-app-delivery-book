| 文件 | 内容 |
|---|---|

## 二、章首固定块（三行，缺一不可）

```markdown
# 第 N 章　<标题，取自 hooks.md 的坐标标签总表>

> 位置：<…> ｜ 横切：<…> ｜ 成熟度 <…>
>
> **此刻 `order-demo` 长什么样**：<case-evolution.md 第三节对应行> ｜ **本章可验证动作**：<同表> ｜ 复现：`git checkout <tag>`。
>
> **初稿状态**：本章为 v1.0 完整初稿，七段齐全；终稿目标 <卡片字数目标>，扩写点见章末「终稿扩写清单」。
```

第 1 章与第 31 章为专题章，章首仍需三行，但正文按叙事组织。

## 三、七段模板（主线章）

章内小节编号用 `N.1` … `N.7`：

| 段 | 小节名 | 必须写什么 |
|---|---|---|
| 1 | `N.1 问题与反模式` | 一个具体翻车场景（合成案例须显式标注「合成案例」）；2–3 条反模式，每条按「现象 → 根因 → 本章替代做法」，关键论断带 `[R-NN-x]` 角标 |
| 2 | `N.2 范式与决策树` | 本章要回答的决策问题；可判定、可验证的范式；一棵文字决策树或一张判据表；**本书观点**若在本章，用独立引用块，写明「主张 / 论证 / 反例与适用前提」，并显式标注「不需要外部背书」 |
| 3 | `N.3 工具选型` | 选型矩阵，列含「何时不该用」；每工具带主版本；**唯一示例实现**必须取 `book/decisions.md` 的固定值，其他工具只在矩阵里作对比；给最小接入 diff 与升级/回滚路径 |
| 4 | `N.4 落地配置` | **完整可应用**的 YAML / 命令 / diff，不写省略号、不写「略」；标注 `apiVersion` 与适用 K8s 版本，小版本指向附录 A；字段严格沿用 `case-evolution.md` 配置契约 |
| 5 | `N.5 验证与回滚` | 四段齐全：可复制的验证命令、逐条通过标准、回滚命令/步骤、回滚验证；**回滚方案先于发布方案**；生产环境变更必须回到 Git，不得与公理 5 冲突 |
| 6 | `N.6 上线检查清单` | 四列表格：编号 / 检查项 / 怎么查 / 通过标准 / 失败处置；3–5 条本章专有项 `CL-NN-xx`；引用 2–3 条母版 `CL-G-xx`；**固定含 2–3 条 `CL-S-xx` 安全项** |
| 7 | `N.7 依据与延伸阅读` | `[R-NN-x]` 编号列表，每条写「级别｜标题｜机构｜版本｜访问日期｜支撑 §N.x 哪个论断」；**不写裸 URL**（D-09）；≥1 条 L1、≥2 条 L2（选型章 ≥2 条 L1），反模式/故障/演练章 ≥1 条 L3；「本书观点」单列说明，不计入背书数量；2–3 条延伸阅读 |

第 7 段之后，按 `book/hooks.md` 决定是否写「回到第 1 章」：**只有 8 个主责章必须写**（2、3、8、9、13、14、22、23），其余章按 9.7 不硬凑。第 31 章收 H1–H8 做首尾闭环。

最后固定两行：

```markdown
**终稿扩写清单**：① …（约 N 字）；② …；③ …
**一致性备注**：<本章与哪些章有耦合、有无待裁决冲突；无则写「无」>
```

### 模板分层（9.6，必须遵守）

- **横切章 24–26**：精简三段，即「问题与护栏 → 落地策略/门禁 → 检查清单」，再加「依据与延伸阅读」；**不硬塞工具选型矩阵**
- **专题 / 收尾章 1、23、31**：按叙事组织，不强制工具小节；但检查清单与依据段落仍要有

## 四、术语与概念梯度

- 术语定义以 `book/glossary.md` 为准；「首次提及 → 正式定义 → 深入展开」以 `book/concept-ladder.md` 为准
- **在正式定义章之前**提到某术语，必须给一句白话解释并写「详见第 X 章」，禁止拿它当推理前提
- 工具首次出现带主版本（`Helm 4.x`），小版本只在附录 A 与配置文件里锁定
- 章内引用写「见第 X 章」，不写「上文/下一章」
- 资源名保持官方大小写：`Deployment`、`PodDisruptionBudget`、`topologySpreadConstraints`

## 五、引用与背书

1. 正文只出现 `[R-NN-x]` 角标，**严禁裸 URL**；章末列表不写 URL，完整链接放 `references/chNN.yaml`
2. 优先从 `references/_verified.md`（已核验链接池）取来源；池外来源在 YAML 里 `url: ""` + `status: pending_url`，**绝不编造 URL**
3. 三级来源：L1 规范与官方（标版本）｜L2 权威人士/共识（≥2 个不同机构、无利益关联）｜L3 公开案例实证
4. 「本书观点」必须给论证与反例，**禁止硬凑引用**；合成案例不得写成真实事件
5. `references/chNN.yaml` 每条必填 `id / title / author_or_org / level / url / version_or_date / accessed / archive_url / supports / status`

## 六、`order-demo` 配置契约速查（不得改动）

| 项 | 值 |
|---|---|
| 命名空间 | `order-demo-dev` / `order-demo-staging` / `order-demo-prod` |
| 镜像 | `registry.example.com/order-demo/<component>:git-<sha7>`，禁用 `latest` |
| 公共标签 | `app.kubernetes.io/name=order-demo`、`component=<组件>`、`version=<SHA>`、`managed-by=<工具>` |
| Service / 端口 | `gateway` 8080、`api` 8081、`db` 5432 |
| 探针路径 | `/healthz` liveness、`/readyz` readiness、`/startup`（仅 api） |
| 终止宽限 | `terminationGracePeriodSeconds: 30`，`preStop` 先摘流 |
| ConfigMap / Secret | `order-demo-config`（第 9 章起 `immutable: true`）；`order-demo/db-credentials` 由 ESO 注入，不入 Git |
| 资源基线（api） | requests `cpu: 100m, memory: 128Mi`；limits `cpu: 500m, memory: 256Mi` |
| 唯一示例实现 | 见 `book/decisions.md` 与 `case-evolution.md` 第五节 |

## 七、篇幅与质量红线

- 初稿每章 **3000–6000 中文字**（含代码块）；宁可写透一个决策，也不要罗列 API 字段
- 每章至少 1 张选型矩阵或判据表、1 组完整配置、1 组回滚命令、1 张四列检查清单
- 不写工具安装/入门教程（官方文档负责）；每个工具必须回答「什么时候不该用」
- 命令必须可复制执行，带验证命令与通过标准
- 不出现「待补」「略」「TODO」等占位；不确定处写成「本章观点：…，适用前提：…」
- 不写具体云厂商单价；成本只给相对比例与归因口径
